版本 1.0　状态：**阶段性设计**——结构性设计已完成并自洽，若干格式细节待对应阶段冻结

> 本文记录存储层的设计结论。需求见 [requirements.md](requirements.md)，总体设计见 [design.md](design.md)。
> 本文不宣称已实现，也不宣称格式已冻结——标注为"待冻结"的项在对应阶段前可能调整。

## 1 总览

### 1.1 层次结构

```text
实例
├── 全局控制文件（2 份）            管控的文件清单 + 文件系统池
├── 缓冲池（实例级共享）            分区为工作集，每分区绑一个写线程（§5.10、§11.7）
├── 文件系统池                      一组挂载点（§2.8）
│
└── 工作区（互不干扰；故障域亦在此收敛，§11.8）
    │
    ├── 主位置（池中某一文件系统上）
    │   ├── 控制文件（2 份）        该工作区的恢复锚点
    │   ├── redo（2 组 × 2 成员）   组大小创建工作区时指定
    │   └── data/
    │       ├── file 0   元数据（**数据字典**，结构与普通表通用）
    │       ├── file 1   Undo
    │       ├── file 2   Temp（不持久化；打开工作区时重置）
    │       └── file 3+  数据段
    │           └── 段 ── 区（8 页 = 128KB）── 页（16KB）
    │               段有 **LIVE / DEAD** 两态：删除先失效，空间惰性回收（§4.7）
    │
    └── 池中散布的部分（可落在不同文件系统上）
        ├── 数据文件（file 3+）     每个独立放置；可自动扩展、可 MOVE（§3.3、§3.4）
        ├── assets/<v>/…            **外部对象**（模型、文档、图片）——
        │                           按 **16 个卷**分布，路径由资产 ID 推导（§2.9、§2.10）
        └── staging/                上传暂存——须与其 assets 卷同一文件系统（§2.9）
```

> **工作区不是一个物理目录**，而是一个**跨文件系统的命名空间**——
> 它的容量上限因此是**整个池**，而不是池中最大的那个盘（§2.10）。

### 1.2 三条贯穿全局的原则

| 原则 | 含义 | 影响 |
| --- | --- | --- |
| **一个引擎 + 表选项** | ROWID、文件布局、控制文件、WAL 基础设施与**页头**全部统一；表间差异收敛为**表级选项**。**页体按页类型自定义**（§5.1——格式服务于访问模式） | 备份、恢复、检查器、配额、诊断只做一套 |
| **存储层不承载版本与事务语义** | 行内无版本号、无时间戳、无事务 ID；可见性由 Undo + 快照判定 | 行更紧凑；业务多版本由数据模型层用额外的行/节点表达 |
| **隔离在文件层落地** | 每工作区独立文件，不共享、不硬链接、不跨用户去重 | 隔离失败属发布阻断项 |

### 1.3 规模约束

| 维度 | 范围 |
| --- | --- |
| 单工作区节点数 | **1 万 ~ 1000 万**（跨 3 个数量级） |
| 边数 | ≤ 10 × 节点数（平均度 ≤ 10） |
| 向量 | **部分节点有，可能一个都没有** |
| 页大小 | **16KB**，实例内固定 |

**由规模推出的两条硬约束**：

1. **向量必须是可选列**——某工作区无向量时不得有任何向量相关文件、索引或内存占用。
2. **ANN 索引必须磁盘型**——极端场景向量达 60GB，装不进 32GB 基准机内存。

## 2 工作区存储布局

### 2.1 目录

```text
<工作区根>（主位置）/  根目录名由服务端生成的不透明 ID，不拼接用户输入
│                      主位置自身位于**文件系统池**中的某个文件系统上（§2.8）
├── control/           control01.ctl  control02.ctl
├── wal/               redo_g1_m1  redo_g1_m2  redo_g2_m1  redo_g2_m2
└── data/
      <ws>_meta        file 0    工作区固定开销（小），不参与池
      <ws>_undo        file 1
      <ws>_temp        file 2
      <ws>_data_NN     file 3..  **数据文件**——可分布在池中任意文件系统上（§2.8）

<池中某文件系统>/<工作区根 ID>/
├── assets/<v>/…       外部对象——按**卷**分布：<v> 由资产 ID 首字符决定，
│                      16 个卷可各自落在不同的文件系统上（§2.9、§2.10）
└── staging/           资产上传暂存——**必须与其对应的 assets 卷在同一文件系统**（§2.9）
```

**工作区不是一个物理目录，而是一个跨文件系统的命名空间**——工作区的容量上限因此是
**整个池**，而不是池中最大的那个盘（§2.10）。

**数据文件的实际位置**：`<池中该文件系统的挂载点>/<工作区根 ID>/data/<ws>_data_NN`

即——**同样的相对路径，挂在不同的文件系统下**。只有挂载点随池槽位变化，
命名规则与相对路径都不变。
**这条完整路径记在工作区控制文件的数据文件记录里**（§2.6"文件路径"一节）——
工作区必须自包含到能独立定位自己的全部文件。

### 2.2 文件角色约定

| 文件号 | 角色 | 说明 |
| --- | --- | --- |
| **0** | 元数据 | **数据字典**（字典表，结构与普通表通用）+ 引导页。**不承载用户数据行** |
| **1** | Undo | 仅记录 Undo 的表产生 |
| **2** | Temp | 排序/哈希/分词溢出；不持久化、不进备份。**按段分配**，见 §4.8 |
| **3..N** | 数据 | 数据段，可动态新增 |

**三个好处**：① 备份与恢复按角色定策略（temp 不备份）；② 用户数据**只可能在 file ≥ 3**，ROWID 寻址空间干净；③ 配额按角色分别设。

### 2.3 两级控制文件

| | 工作区控制文件 | 全局控制文件 |
| --- | --- | --- |
| 位置 | `<ws>/control/` | 平台控制目录 |
| 份数 | 2 | 2 |
| 内容 | 该工作区的文件清单、检查点位置、redo 序列号、格式版本 | **数据库管控的文件清单** |
| 更新时机 | **日志切换时** | 建/删工作区、新增数据文件时（**低频**） |
| 是否恢复锚点 | **是** | 否（丢失可由各工作区自描述重建） |
| 含私有内容 | 否（仅结构） | **否** |

**控制文件必须独立于表空间**——恢复要先知道"该打开哪些文件、检查点在哪"，若控制信息藏在 file 0 内则形成循环依赖（要先打开 file 0 才知道要打开 file 0）。

**全局控制文件绝不在提交关键路径上**——工作区的每次提交不得触碰它，否则造成跨工作区耦合与写热点。

### 2.4 Redo

- **每工作区独立**：redo 记录**包含用户数据本身**（行级修改描述），共享即泄漏。
- **2 组 × 2 成员 = 4 个文件**：组提供循环复用空间，成员提供镜像冗余。同组成员**大小必须完全一致**。
- **组大小创建工作区时指定**——小工作区配小 redo，大工作区可上百 MB。
  - 下限：必须能容纳一个检查点周期的日志量（待冻结）
  - 变更：运行后**只能增加组数，不能改已有组大小**
  - **另一条独立下限：组大小 ≥ 最大单条记录**（§11.5.1）。记录大小以"页"为界（§11.5.3），
    故该下限约为 **一页 + 24B 头 ≈ 16.4KB**——很低，容易满足；真正的约束来自"一个检查点周期"
### 2.5 归档

**归档是时间点恢复、在线备份与备库的共同前提**——它保留**连续的日志链**，为恢复提供从备份点到目标点的全部变更历史。若无归档，redo 组被循环覆盖时日志链即断，上列能力全部失效。

**机制**：日志组在被覆盖**之前**先复制到归档目标（对应成熟产品的 ARCn 归档进程）。因此需要一条额外约束：

> **未完成归档的日志组不得被覆盖。**

这条约束**影响 redo 的空间管理与日志切换逻辑**，必须与 WAL 层同时设计（见 §13 待冻结项）。

**归档必须每工作区独立**：归档内容与 redo 一样**含用户数据**（行级修改描述），共享即泄漏。归档目标须落在该工作区的受控目录内，与 redo 同级隔离。

**归档与两类数据的关系**：

| 数据 | 是否归档 | 后果 |
| --- | --- | --- |
| `logging = full` / `redo_only` | 归档 | 支持在线备份与时间点恢复 |
| `logging = none` | **无 redo 可归档** | **不参与**备份与恢复；需保留时只能用离线迁移工具 |

**归档前的一致性要求**：做时间点恢复或基于备份的恢复前，必须先强制归档当前日志组（对应 `ALTER SYSTEM ARCHIVE LOG CURRENT`），确保日志序列连续、无缺口。

### 2.6 控制文件的结构

#### 定长设计

控制文件**定长**，大小在建工作区时按上限确定。这样更新是**原地覆盖写**，不必重写整个文件。

**数据文件记录数组固定 1024 项**——与 ROWID 的 `file_id` 位宽一致，两者天然对齐。

**估算**：文件头 256B + 工作区条目 64B + 检查点进度 128B + Redo 条目约 1KB + 数据文件记录 1024×32B = 32KB + 归档记录 256B ≈ **34KB**，取整为 **64KB**（留余量并对齐）。

#### 记录的两类复用语义（对照 Oracle）

Oracle 的控制文件由**带类型号的记录段**组成，`X$KCCCF.INDX` 给出完整枚举。它的第一层划分**不是"内容"，而是复用方式**：

| | 非循环复用 | 循环复用 |
| --- | --- | --- |
| 语义 | **每个实体一条，位置固定** | **历史流水，写满即环形覆盖最旧** |
| Oracle 记录 | 库信息(0)、检查点进度(1)、redo 线程(2)、日志文件(3)、数据文件(4)、文件名(5)、表空间(6)、临时文件(7) | 日志历史(9)、归档日志、离线范围、RMAN 备份集/片/副本 |
| 上限 | 建库时定死 | 环形空间 |

**这条划分比"有哪些段"更重要**——它决定每类的**容量策略**与**写满时的行为**：
非循环记录写满 = **结构上限到顶**（Oracle 的表现是需要重建控制文件，这正是 `MAXDATAFILES` 一类参数的由来）；
循环记录写满 = **静默丢弃最旧历史**。

我们采用同一划分：

| 段 | 类别 | 写满时 |
| --- | --- | --- |
| 文件头、工作区条目、检查点进度、Redo 条目、数据文件记录 | **非循环** | 到顶即**拒绝新增**（如数据文件记录固定 1024 项，与 ROWID 的 `file_id` 对齐，§7），**不重建控制文件** |
| 归档记录 | **循环** | 环形覆盖最旧——但受**"未归档组不得覆盖"**约束（§2.5） |

**刻意不采用的 Oracle 记录类型**：

| Oracle 记录 | 为什么不需要 |
| --- | --- |
| `KCCDERTH` redo 线程 | 单实例，无 RAC 多线程概念 |
| `KCCDETBS` 表空间 | **工作区即表空间**，一一对应（§3.1.1） |

> **`KCCDENAM`（file NAMe record）是采用，不是省略**——Oracle 的控制文件**存完整路径**，
> 我们现在也存。原因见下"文件路径"。
| RMAN 系列（备份集 / 备份片 / 副本 / 删除） | 备份元数据的存放位置**尚未定**——见 §13 |

#### 工作区控制文件的段

| 段 | 内容 |
| --- | --- |
| **文件头** | 格式版本、各段偏移表、**副本序号**、校验和 |
| **工作区条目** | `workspace_id`、创建时间、**`derived_from` + `derived_at_seq`**（克隆血缘，§2.7） |
| **检查点进度** | 检查点提交序号、**检查点 LSN（= 恢复起点）**、当前提交序号、**最老快照提交序号** |
| **Redo 条目** | 组数、成员数、每组的序列号与状态、当前组 |
| **数据文件记录** | 每文件的 `file_id`、**完整路径**、**角色**、状态、**创建时大小**、创建时间 |
| **归档记录** | 归档模式、归档目标、最后归档的日志序列号 |

**检查点进度里的"恢复起点"**：Oracle 的检查点进度记录（`X$KCCCP`）不只存检查点位置，还存**两个 RBA**——
`low_rba`（检查点队列中最早的脏块）与 `on_disk_rba`（DBWR 已落盘到哪），二者之差就是崩溃后要重放多少。
其含义是：**恢复起点是"最早的脏块"，而不是"最后一次检查点动作的位置"**。
我们的"检查点 LSN"必须按同一语义定义——即**该 LSN 之前的修改已全部落盘**。

**数据文件记录存"创建时大小"而非"当前大小"**：Oracle 的 `FECSZ` 全称是 *creation file size*，
当前大小由**文件头自述**（Oracle 另有 `FEBSZ` 记录每文件的块大小；我们统一 16KB，故不需要）。
控制文件只保存**创建后不变**的属性，可变量一律以文件自身为准——与 §5.2 的字段准入纪律同源。

**文件路径：存，而不是省**

（原设计为"不存路径"，引入文件系统池后**已推翻**。来路值得记下：当初能省，是因为
**把文件位置约束到了"工作区根"**；文件系统池重新引入了"任意位置"，
**于是回到了 Oracle 的处境**——而它的控制文件本来就存路径，即 `KCCDENAM`。）

数据文件的完整路径**必须记在工作区控制文件里**，因为**它是恢复锚点，必须自包含**：

> 若只存一个指向文件系统池的**槽位号**，那么全局控制文件一旦丢失，
> 槽位号就无从解析，**所有数据文件都定位不到**——恢复锚点就依赖了另一份可丢的东西。

存路径之后，"池里有哪些文件系统"也能从各工作区控制文件里的路径**前缀**反推出来，
这恰好与"全局控制文件不是恢复锚点、丢失可由各工作区重建"（§2.6）的性质吻合。

| 信息 | 存放 | 性质 |
| --- | --- | --- |
| **池**（有哪些文件系统） | 全局控制文件 | 权威，但**可重建**（从工作区侧的路径前缀反推） |
| **每个数据文件的完整路径** | 工作区控制文件 | **权威且自包含**，恢复时不依赖任何外部配置 |

**代价与缓解**：存路径重新引入了当初省掉它的那类安全问题。缓解与其它文件操作一致
（REQ-ISO-007）：路径**不是用户输入**，而是创建文件时的**服务端决策**；
打开时**校验路径落在池中的某个文件系统之下**，并做路径穿越与符号链接检查。
被篡改的路径因此在**打开阶段就会失败**，而不是被悄悄读走。

**一处刻意的省略：不存 Undo 段信息。** Undo 信息在 **Undo 段头部与目录**中，
不属于控制文件——这一点与成熟产品一致。

#### 全局控制文件的段

| 段 | 内容 |
| --- | --- |
| 文件头 | 格式版本、序号、校验和 |
| 库条目 | 库标识、创建时间、格式版本 |
| 工作区记录数组 | `workspace_id`、状态、文件数、总大小、最后更新时间 |

**只存结构摘要，不存私有内容**；**不是恢复锚点**——丢失后可由各工作区控制文件重建。

#### 双副本的一致性协议

- **序号单调递增**，每次更新 +1
- 更新顺序：**先写副本 A，成功后写副本 B**
- 打开时读两副本，取**有效且序号较大**的
- 若两副本都无效 → **该工作区无法启动**（与成熟产品一致，属设计上接受的取舍）

**为什么定长 + 原地覆盖能安全**：定长使单次更新是**局部覆盖**，配合页尾式校验与副本序号，崩溃后总能判定哪一份是完整且较新的。变长则需整体重写，崩溃窗口更大。

#### 更新时机与关键路径

| 触发 | 更新 | 频率 |
| --- | --- | --- |
| 日志切换 | 工作区控制文件 | 高 |
| 检查点 | 工作区控制文件 | 中 |
| 归档 | 工作区控制文件 | 中 |
| 新增数据文件 | 工作区 + 全局 | 低 |
| 建/删工作区 | 全局 | 极低 |

**控制文件的更新不在提交关键路径上**——提交只需 WAL 持久化；控制文件在日志切换与检查点时更新。**这是它敢用"双副本 + fsync"而不拖慢事务的前提**。

#### 与 redo 的关系

控制文件记录的检查点**可能落后于数据文件的实际状态**——这没问题，因为重做本身是**幂等**的（按页 `page_lsn` 判定跳过已包含的修改），从稍旧的检查点起重做会自然收敛到正确状态。

但**控制文件本身丢失（两副本皆坏）则无法启动**——与成熟产品一致。全局控制文件例外，它可由各工作区重建。

### 2.7 工作区的克隆与分支

工作区是**自包含的多文件集合**（file 0..N + redo + 控制文件），这使它天然适合用
**文件系统的写时复制（COW）**做近乎瞬时的整区克隆——XFS 的 `reflink` 与 btrfs 都支持。
克隆出来的是一个**独立的工作区**：有自己的目录、自己的 redo，独立演进。

**这是管理员操作**，普通用户无权限——它要读另一个工作区的文件。

#### 一致点：冻结 → 检查点 → 克隆 → 解冻

克隆必须取自一个**一致的时刻**，否则克隆出的工作区需要先做实例恢复。

```text
① 冻结源工作区（拒绝新事务）
② 强制检查点：刷全部脏页 + 刷控制文件
③ 对全部文件执行 reflink 克隆（纯元数据操作，毫秒级）
④ 解冻源工作区
```

③ 必须在冻结窗口内完成。reflink **不搬数据**、只建共享引用，所以窗口极短——
这正是它比"备份 + 恢复"快几个数量级的原因。

> **与成熟产品一致**：Oracle 的本地 PDB 克隆要求"源 PDB 只读，**或**启用 LOCAL UNDO
> 且处于归档模式以支持热克隆"。我们走的是**只读那一支**（冻结）。
> 热克隆那一支我们也具备前提（每工作区独立 undo + 归档），但 **V1.0 不实现**。

#### 克隆后必须重新解释的三样东西

**① `workspace_ref` 的语义是"数据血统"，不是"工作区身份"**

页头的 `workspace_ref` 由 `H(workspace_id)` 得出（§7）。克隆后新工作区的 `workspace_id` 变了，
但**页上的 `workspace_ref` 保持不变**——分支的数据确实源自同一血统。

三个方案里只有这一个可行：

| 方案 | 代价 |
| --- | --- |
| **继承源的 `workspace_ref`**（采用） | 无，且语义正确——ref 要回答的是"这页属于我正在打开的数据世系吗" |
| 克隆时重写所有页的 `workspace_ref` | O(页数)，**摧毁"快速"这个唯一价值** |
| 新工作区沿用源的 `workspace_id` | 不可行——全局控制文件会冲突 |

这反过来要求把 `workspace_ref` 的定义说准：**它标识数据的血统根，不是工作区的当前身份**。
（它本来也不是密码学边界，§7 已声明。）

**② LSN 必须在新工作区里继续单调**

被克隆的页上带着源的 `page_lsn`。新工作区第一次修改某页时，若新 LSN **小于**该页的 `page_lsn`，
`page_lsn` 的幂等判定会认为"这页已包含该修改"而**跳过重放**——错误。

解法：**新工作区的 LSN 起点取源日志序列的下一个整组边界**：

```text
新工作区起点 LSN = 把源的当前 LSN 向上对齐到 redo 组大小
```

于是新 LSN **严格大于**克隆点的 LSN（即页上所有 `page_lsn`），且新工作区的组内偏移从 0 开始。
代价最多浪费一个组大小的 LSN 空间，48 位下可忽略。

> **顺带确定 LSN 的编码**（原为待冻结项）：LSN 是**单调递增的字节位置**，
> 文件与文件内偏移由它**推导**，而不是编进它——这正是 PG 的做法：
> `组号 = LSN / 组大小`、`组内偏移 = LSN & (组大小 - 1)`。
> 它要求 **redo 组大小是 2 的幂**（掩码运算），这是一个新增的硬约束。

**③ `redo` 从零开始**

克隆点已经是一次检查点，数据文件是一致的，**不需要克隆点之前的日志**。
新工作区的 redo 从空开始写。

#### 血缘记录

克隆出的工作区**自描述其血缘**——在工作区控制文件的"工作区条目"里加两个字段：

| 字段 | 说明 |
| --- | --- |
| `derived_from` | 源工作区标识（非克隆工作区为空） |
| `derived_at_seq` | 派生点的提交序号 |

> 成熟产品同样把这件事记在数据库自身：Oracle 用数据库标志 `KCCDICLO` 标明"本库是克隆出来的"，
> 因为它的克隆库"数据文件可能基于备份获取，打开时可能需要额外的恢复或日志应用"。
> 我们的克隆点是**一致**的（冻结 + 检查点），打开时**不需要**额外恢复——这一点比基于备份的克隆更强。

全局控制文件里也记一份（便于管理面列出派生关系），但**权威在工作区控制文件**——
与"工作区自包含"一致。

#### 允许什么、不做什么

- **允许链式派生**（分支的分支）。链长由管理面限制，存储层不设限。
  > 成熟产品在**快照轮播**这类场景里禁止"基于快照再建快照"，但那是快照存储区的限制；
  > 我们直接对文件做 reflink、没有中间层，链式派生在存储层没有额外代价。
- **不支持合并**（把分支的改动并回主线）。那需要比对两个工作区的数据与日志并定义冲突语义，
  是另一个量级的工程，且与"存储层不做版本化"的边界冲突。**V1.0 不做，也不预留格式。**
- **不自动清理**：源工作区被删除后，分支因其 reflink 共享而**依然完整**——
  COW 的引用计数由文件系统维护，与工作区管理无关。

#### 前提：reflink

克隆要求工作区目录位于**支持 reflink 的文件系统**上（btrfs、XFS with `reflink=1`）。
它与"原子页写"是**两条彼此独立**的文件系统能力——一个文件系统可以满足其一而不满足其二，
**必须分开评估**。**能力档位表与区别说明集中在 §11.6**，
其中一条尤其要记住：**XFS 满足 reflink 克隆，但不提供原子页写**。

### 2.8 文件系统池

**工作区的文件不必落在同一个文件系统上。** 数据库维护一个**文件系统池**——
一组可供放置数据文件的挂载点。池是**实例级**的：它属于平台，不属于某个工作区。

#### 池的增删

| 操作 | 前置条件 |
| --- | --- |
| **加入** | 无——新加入的文件系统立即参与后续分配 |
| **移出** | **该文件系统上不得有任何数据文件** |

**"移出"的前置条件是硬性的**。理由不是保守，而是**职责边界**：池只管"文件放在哪"，
不管文件内容；若允许带着文件移出，那些文件就脱离了数据库的管控范围，
而它们的**恢复锚点（控制文件）仍在数据库手里**——形成一个数据库无法负责的状态。

所以顺序永远是：**先 `Move` 走全部文件（§3.4），再移出**。

#### 池定义存全局控制文件，文件路径存工作区控制文件

| 信息 | 存放位置 | 性质 |
| --- | --- | --- |
| **池本身**（有哪些文件系统） | **全局控制文件**（§2.6） | 权威，但**可重建**——从各工作区控制文件里的路径**前缀**反推 |
| **每个数据文件的完整路径** | 该工作区的**工作区控制文件** | **权威且自包含**——恢复时不依赖任何外部配置 |

**为什么存路径而不是池槽位号**：工作区控制文件是**恢复锚点**，必须**自包含**。
只存槽位号的话，全局控制文件一旦丢失，槽位号就无从解析，
**所有数据文件都定位不到**。存完整路径则让池配置也能从工作区侧反推，
正好与"全局控制文件可重建"的性质吻合。详见 §2.6 的 ①。

**职责因此很清晰**：**新增文件时**才需要池配置（决定放哪个文件系统）；
**打开已有文件时**直接用存的路径——不依赖任何全局状态。

#### 自动创建文件前必须先看容量

**自动新增数据文件前，必须先探测候选文件系统的可用空间**，选取**容量足够**的那个；
**谁也不够时直接报错**，而不是硬写下去、等 `ENOSPC` 在半路炸出来。

| 规则 | 说明 |
| --- | --- |
| **选择策略** | 多个候选都够时选**可用空间最多**的——避免文件都堆在同一个盘上 |
| **"足够"的判据** | 至少放得下新文件的 `initial_size`，并留出余量 |
| **不依赖预分配** | 检查与创建之间有窗口，期间别人可能吃掉空间。这个窗口由**创建失败时重试**处理，不靠 `fallocate` 之类的预占——它在不同文件系统上语义不一致，不该作为正确性依据 |

### 2.9 外部对象（资产）的存储布局

大对象（模型、文档、图片）**不进库**——它们由 `ASSET_REF` 引用，内容是工作区内的
**受管理外部文件**（REQ-AST-001、§6.6）。这些文件在磁盘上怎么摆，是本节的事。

#### 禁止平铺：一个目录装不下

**资产目录不得平铺**。把几十万个文件塞进一个目录会同时压垮三件事：
目录项查找退化为线性扫描、`ls` 一类运维动作不可用、部分文件系统在大目录下性能塌陷。

#### 按 ID 分片成目录树

资产由 **128 位 ID** 标识（D-01），**路径由 ID 直接推导**：

```text
<卷所在文件系统>/<工作区根 ID>/assets/<v>/<s1>/<s2>/<s3>/<asset_id>

（`<v>` 是**卷**，由 ID 首字符决定——卷级的意义与放置见 §2.10。）
```

- 每级取 ID 的一段作为**分片槽位**
- **基数 B**（每级多少槽位）与**层数 L** 共同决定容量：`B^L`
- **每个目录的条目数 ≤ B**

| 基数 B | 层数 L | 容量 | 每目录条目 |
| --- | --- | --- | --- |
| 16（十六进制 1 位） | 4 | 6.6×10⁴ | ≤ 16 |
| **256（十六进制 2 位）** | **3** | **1.67×10⁷** | **≤ 256** |
| 100（十进制 2 位） | 4 | 1×10⁸ | ≤ 100 |

**推荐十六进制 2 位 × 3 级**：ID 本来就是十六进制，分片可以直接切字符串、不需要转换；
每目录 256 个条目仍远在常见文件系统的舒适区内（ext4 的 htree 要到数百至数千条目才真正吃紧，
且那时工作良好）。这个形态也是成熟工具长期验证过的（Git 的对象库即两级十六进制）。

> 若确实要把每目录压到 100 以内，用十进制两位 × 4 级（容量 10⁸）——
> 代价是 ID 需要一次进制转换。**具体取值见 §13 待冻结项 41。**

#### 为什么路径必须由 ID 推导

**因为查表会引入第二个真相源。** "ID → 路径"若靠一张映射表，这张表本身就要持久化、
要保证一致性、要参与恢复——而它能表达的信息（文件在哪）**已经由 ID 唯一确定了**，
存它纯属冗余（违反 §5.2 的字段准入纪律）。推导则零状态、零成本、天然一致。

#### 上传暂存与原子发布

资产的写入路径是**两段式**：

```text
① 上传 → 写入 staging/<临时名>（可分块、可断点续传）
② 提交 → rename 到 assets/<v>/<s1>/<s2>/<s3>/<asset_id>
```

**`rename` 是原子的**，所以第 ② 步是"要么完全没有，要么完整存在"——
不会出现"元数据说资产存在、文件却只写了一半"。

> **由此得到一条硬约束**：**staging 目录必须与 assets 在同一文件系统上**。
> `rename` 跨文件系统会退化成"复制 + 删除"，原子性随即消失。
> 若资产分布在**文件系统池**（§2.8）的多个文件系统上，staging 也必须在**每个**上各有一份，
> 且第 ② 步的 rename 只在**同池内**进行。

#### 与数据文件的三处不同

| | 数据文件 | **资产文件** |
| --- | --- | --- |
| 位置 | 文件的**完整路径**记在控制文件（§2.6） | **不记**——路径由 ID 推导 |
| 可变性 | 原地更新 | **不可变**——只允许读取、范围读取与删除（REQ-AST-001） |
| 恢复 | 受 redo 保护 | **不受 redo 保护**——它是外部文件，不进 WAL |

**第一行是本节最值得注意的对比**：数据文件必须存路径（因为它的位置**不可推导**，§2.6），
资产文件**不存**（因为位置**完全由 ID 决定**）。两者不是"一个存一个不存"的随意取舍，
而是**同一把尺子量出来的两个结果**：**能推导的就不存。**

**第二行解释了第三行**：资产不可变，所以它没有"崩溃后要恢复成什么样"的问题——
一个已经发布（rename 完成）的资产就是完整的；一个还在 staging 的就是不存在的。
**这正是"内容不可变"换来的简单性。**
### 2.10 工作区在池中的放置

核心问题：**怎么保证一个大工作区有足够空间？**

答案**不是**"把工作区放到一个足够大的文件系统上"——那要求存在一个足够大的盘，
而大工作区会长到超出其中任何一个。答案是：

> **工作区不被绑定到单个文件系统。**

#### 工作区是一个跨文件系统的命名空间

工作区**不是**一个物理目录。它由一个**主位置**加若干**可散布的部分**组成：

| 部分 | 放置 |
| --- | --- |
| `control/`、`wal/`、file 0/1/2 | **主位置**（某一个文件系统）——小，且需要低延迟 |
| **数据文件**（file 3+） | 池中**任意**文件系统，**每个独立放置**（§2.8） |
| **资产**（`assets/`） | 按**卷**分布，见下 |

于是工作区的容量上限是**整个池**，而不是池中最大的那个文件系统。

#### 资产按"卷"分布

在 §2.9 的分片树之上，再加**一级卷**：

```text
<卷所在文件系统>/<工作区根 ID>/assets/<v>/<s1>/<s2>/<s3>/<asset_id>
```

- **卷号由 ID 的首字符决定**（16 个卷）——路径**完全由 ID 推导**，某个资产存在哪不需要记录
- **卷 → 文件系统**的映射记在**工作区控制文件**里（**16 条路径**，很小）
- ID 是随机的，所以 **16 个卷天然均分资产**——不需要主动平衡

**这一级同时解决两个问题**：

1. 资产可以**横跨池中的多个文件系统**——大用户的资产不再被单个盘卡住
2. **迁移的单位是"卷"**（一棵子树），既不是整棵 assets 树，也不是整个工作区——**粒度合适**

#### 放置：自动、指定、迁移

| 方式 | 说明 |
| --- | --- |
| **自动** | 创建时按各文件系统的**可用容量**分配：数据文件逐个选，资产卷按比例摊 |
| **指定** | 管理员可显式指定某个数据文件或某个卷落在哪个文件系统 |
| **迁移** | 数据文件按 §3.4 的 MOVE；资产卷按**整体搬迁**（同一手法） |

#### 为什么"只看当前空闲"会失败——以及我们为什么不依赖它

贪心放置有一个经典陷阱。池里两个 1TB 的盘都空着：

```text
工作区 A 预估 400GB → 放盘 1
工作区 B 预估 400GB → 盘 1 只剩 600GB → 放盘 2
A 实际长到 900GB     → 盘 1 装不下，盘 2 上却还有 600GB
                       池里总共有空间，A 却增长不了
```

**我们的设计绕开了它，靠的不是更聪明的预估，而是不依赖预估**：

> 数据文件与资产卷**都允许落在任意文件系统上**——A 长到 900GB 时，
> 新数据文件自然会落到盘 2。**不需要一开始就把 A 放对地方。**

于是"按容量自动分配"退化成一个**简单且足够**的规则：

```text
为新数据文件 / 新卷选址 → 选当前可用空间最多的文件系统
```

**选错了也不要紧**——最多是某个盘先满，**由迁移纠正**（§3.4）。
**迁移的存在，让初始放置不必精确。**

#### 空间紧张时的处置阶梯

```text
① 池中还有空间     → 新数据文件 / 新卷落到最空的盘
② 某个盘快满       → 迁移该盘上的**卷**或**数据文件**到别处
③ 池整体快满       → 加入新文件系统（§2.8），再迁移
④ 池整体满         → 报错——与 §3.3 的配额 / 物理上限走同一条报错路径
```

**第 ② 步的粒度是关键**：迁的是**一个卷**（一子树资产）或**一个数据文件**，
不是整个工作区。**整工作区迁移太贵，会让"纠正"本身变得不可行**——
而不可行的纠正等于没有纠正。

> 这条正是 §2.9 把资产切成 16 个卷、§2.8 让每个数据文件独立放置的**共同目的**：
> 它们给出的不是"更快地迁移"，而是**可执行的迁移粒度**。

## 3 表空间文件

### 3.1 file 0：元数据文件与数据字典

file 0 相当于 Oracle 的 **SYSTEM 表空间**——工作区的全部元数据以**字典表**的形式存放在这里。

关键性质：**字典表使用与普通表完全相同的结构与访问路径**（段 + 页 + 行 + ITL + 槽位目录 + ROWID + 索引），
**不存在第二套"目录格式"**。工作区因此不需要为元数据单独写一套读写、校验与恢复代码。

内部结构，按块顺序：

| 块 | 内容 |
| --- | --- |
| 0 | **文件头页**（`page_type = 11`） |
| 1 | **引导页**（`page_type = 12`），格式**永久固定** |
| 2 | 引导页的第 2 份副本 |
| 3.. | **字典表的段**——起始位置由引导页给出，之后按 §4 的区分配增长 |

**为什么字典表要用普通表结构**：

1. **一套代码**——字典表的读写、页校验、ITL、WAL 保护、崩溃恢复全部复用表引擎。"元数据"不是特例，
   也就不会成为恢复路径上唯一没被日常验证过的分支。
2. **要索引**——按名查对象、按 `obj#` 查列都是 B+Tree 点查，DDL 与启动不随对象数线性退化。
   Oracle 正因如此为 `obj$` 建了 `I_OBJ1` / `I_OBJ2` / `I_OBJ4`。
3. **DDL 天然事务化**——建表 = 向若干字典表插入行。它与用户事务共用同一套 undo / WAL / 提交序号，
   不需要单独设计"元数据变更日志"，并自动获得 **DDL 可回滚**与**恢复后字典自洽**。

#### 引导页（对应 Oracle `bootstrap$`）

- 要读 `obj$`，得先知道 `obj$` 的段头在哪；而这个位置本身存在 `seg$` 里。
- 解法：**块 0 / 块 1 的格式硬编码**，内核读取路径**不依赖任何字典表**；引导页直接给出**最小自举集**的段头位置。

引导页条目：

| 字段 | 说明 |
| --- | --- |
| `dataobj#` | 数据对象号 |
| `seg_type` | 段类型（表 / 索引） |
| `seg_header` | 段头 ROWID（6 字节） |
| `iniexts` | 初始区数 |

**最小自举集**：

| 表 | 作用 |
| --- | --- |
| `obj$` | 对象命名空间、类型、`dataobj#` |
| `tab$` | 表专有属性（**七项表选项在此**） |
| `col$` | 列定义（含向量列扩展） |
| `ind$` | 索引专有属性（`bobj#` 指向基表） |
| `icol$` | 索引键列组成 |
| `seg$` | 段目录（`dataobj#` → 段头 ROWID、段类型） |
| `undo$` | Undo 段（file 1） |

**索引也是自举对象**——Oracle 的 `I_OBJ1` / `I_OBJ2` 属 bootstrap 核心（`obj# < 56`），
是"数据库 warmstart 所必需"，甚至禁止对其执行 `alter index rebuild`。
同理，每个自举表至少有一个唯一索引**并同样进引导页**——否则自举之后仍无法按名/按号定位字典行。
**条目数 = 自举表数 + 自举索引数**。

**与 Oracle 的一处刻意不同**：

| | Oracle `bootstrap$` | 我们的引导页 |
| --- | --- | --- |
| 形式 | **表**：`LINE# / OBJ# / SQL_TEXT` | **固定格式的一页** |
| 内容 | **DDL 文本**，含 `EXTENTS (FILE 1 BLOCK 360)` | 结构化条目 |
| 启动时 | 解析 SQL 文本，"在内存中创建"对象 | 直接按段头位置读 |

**不存 DDL 文本的理由**：① 自举**不能依赖 SQL 解析器**——解析器自己也是被自举的对象；
② 文本与实现的漂移是静默的，编译期常量不会漂移。字典表的列定义作为**内核常量**存在，
引导页只回答一件事：**它的段在哪**。

**自举链**：

```text
块 0 文件头（格式硬编码）
  └─ 块 1 引导页（格式硬编码）：最小自举集的段头位置
       └─ 读 obj$ / col$ / seg$ —— 至此其余一切（含字典表自身）的定义与位置都可查到
            └─ 用户对象
```

**位置约定一旦发布不可变更**（或必须以 `format_version` 区分）。

**自描述与恢复**：`obj$` / `tab$` / `col$` / `ind$` / `seg$` 中**都含字典表自己**的行——
与 Oracle 一致（`tab$` 里有 `OBJ$` / `TAB$` / `COL$` 自己的记录）。
由此得到一条恢复路径：**引导页两副本皆坏时，可扫描 file 0 找段头页**（段头页带 `dataobj#`）重建引导页。
引导页因此不是单点——但仍**保留两份持久副本**（与 InnoDB 那种"双写缓冲"不是一回事：
这里存的是两份**持久副本**，不是一次写之前的临时副本）。它太小，而重建有成本。

**冗余副本范围收敛为引导页**：字典表**不做副本**——它们是普通段，由页校验、WAL 与备份保护。
原设计"表空间头 / 段目录 / 对象目录各写两份"随固定目录格式一并取消。

> **注意其局限**：副本防的是**页级**损坏，**不防文件丢失**。file 0 整个文件损坏仍会导致表空间不可用——文件级冗余由控制文件与备份承担。

**一个工作区一份字典**：每个工作区（含 `public` 与 `system`）自包含一套字典表，与"无跨工作区读写"的隔离模型一致（§12）。
对象号只需**工作区内唯一**。

**字典表段只存在于 file 0**；file 0 可**动态增长**（append 至文件末尾）以容纳元数据增长。

#### 字典表清单

**① 自举层**——上表 7 张表及其唯一索引，位置在引导页中。

**② 普通字典表**——由自举层描述，可增删：

| 表 | 作用 | 备注 |
| --- | --- | --- |
| `stat$` | 访问计数、行数估计等**启发式统计** | **非事务表**：`logging = redo_only`，统计可丢，不参与恢复 |

**V1.0 不设的字典表**（是"推迟"，不是"不需要"）：

| 表 | 为什么不设 |
| --- | --- |
| `con$` / `ccol$` | **V1.0 不支持约束对象**。唯一性由**唯一索引**提供——那是 `ind$` 上的索引属性；列可空性由 `col$` 的标志位表达——那是列属性。两者都不是"约束" |
| `dependency$` | V1.0 不支持视图，无依赖关系可记 |

→ **V1.0 的字典表 = 自举 7 张 + `stat$`**。

**③ 明确不需要的**——照抄 Oracle 会把用不上的东西一并搬进来：

| Oracle 表 | 为什么不需要 |
| --- | --- |
| `user$` | **一个工作区一个属主**，无授权模型；属主身份记在控制文件（§2.6），不进字典 |
| `ts$` | **工作区即表空间**，一一对应，无多表空间概念 |
| `file$` | 文件清单的唯一权威是**控制文件**（§2.6）——见下方说明 |
| `tsq$` | 无表空间配额，工作区独占自己的文件 |
| `uet$` / `fet$` | 那是**字典管理**表空间的区分配方式；我们用**页分配位图**（§3.2） |
| `tabpart$` / `indpart$` | V1.0 不做分区 |
| `cluster$` | 不支持簇表；本库的聚簇需求由图表的邻接页承担（§5.6、§8） |
| `bootstrap$` | 由**引导页**承担，且不存 DDL 文本 |

**`file$` 与 `ts$` 的取舍（关键）**：Oracle 的控制文件存 `file$` 的**冗余副本**、`file$` 是权威，
两者必须一致，不一致即 `ORA-011xx`。我们**反过来**：控制文件本来就定长、可直接读、
且必须在任何字典表之前读出（否则解不开自举），它天然就是权威。
再维护一份 `file$` 只会制造一致性负担而无收益。
**运行期的查询需求由引擎内置的只读伪表暴露**（内容取自控制文件的内存映像，不落盘）。

**字典表用什么表选项**（属 §8 的五种表类型之一，选项上无特殊）：

| 选项 | 值 | 理由 |
| --- | --- | --- |
| `transactional` | ✅ | DDL 必须可回滚、可恢复 |
| `logging` | `full` | 字典不一致 = 工作区打不开，不是"丢少量数据" |
| `update_mode` | `in_place` | 字典行会被更新（`status`、`mtime`），且字典表小、行迁移风险低 |
| 其余 | 默认 | |

→ 字典表就是**普通关系表**。这一点本身即"结构通用"的直接结果。

### 3.2 数据文件（file 3+）

每个数据文件的头部含文件头与**区分配位图**。

**区分配位图放每个文件头部**（不集中在 file 0）：文件因此**自描述**——单独移动、校验、恢复时能自证；区分配操作只触碰目标文件。

数据文件的**增长方式**（自动扩展、自动新增、到顶报错）见 §3.3。

### 3.3 数据文件的增长

空间不足时有**四级阶梯**，前两级完全不出段、不出文件：

```text
① 段内找空间（页级 → 区级，§4.5）
② 回收失效段（§4.7）——不扩任何文件
③ 扩展已有数据文件（自动扩展）
④ 新增数据文件（自动新增；创建前须先探测容量，§2.8）
────────────────────────────────
⑤ 到顶 → 明确报错
```

**前两级几乎总是够用**——这是"不主动回收"（§4.7）换来的：回收的成本被推迟到
真正需要空间时才付，而付的时候正好解决了问题。

#### ③ 扩展已有文件：便宜，且不碰控制文件

创建数据文件时设定四项属性：

| 属性 | 默认 | 说明 |
| --- | --- | --- |
| `initial_size` | 工作区默认 | 创建时的文件大小 |
| `autoextend` | **开** | 不足时自动增长 |
| `next_size` | 工作区默认 | 每次增长多少 |
| `max_size` | 4 TiB | 单文件上限 |

**`max_size` 的 4 TiB 不是随手定的**——它就是 ROWID 的
`block_id 28 位 × 16KB`（§7）。文件不可能超过它，因为超过之后
**页地址就编不进 ROWID 了**。这不是策略选择，是格式的硬边界。

**扩展是"原地长大"，不改控制文件**——这是一个有意设计的便宜：

> 控制文件的数据文件记录只存**创建时大小**（§2.6），**当前大小由文件头自述**。
> 于是扩展只需"追加文件尾部 + 更新文件头"，**一次操作，不碰双副本控制文件**。

这让"扩展"便宜到可以作为常态，而"新增文件"才需要走控制文件的慢路径。
（§2.6 当初把"大小"定义为*创建时*大小，就是为了这个。）

#### ④ 新增数据文件：走控制文件的慢路径

当前文件都到 `max_size` 时，**默认自动创建下一个数据文件**：

- 新文件按**工作区级默认模板**创建（默认大小、自动扩展、上限）
- 需要更新**工作区控制文件 + 全局控制文件**（§2.6 的更新时机表）——**低频**
- **完整路径写进工作区控制文件**（§2.6 的"文件路径"一节）；命名沿用规则 `<ws>_data_NN`（§2.2）

**也可以人工添加**：自动新增是**默认**行为，不是唯一途径。管理员可以显式指定
文件大小与属性来添加——两条路径产出同一种文件，只是触发者不同。

> 自动新增与自动扩展都**不是必须**：`autoextend` 可关，自动新增可关
> （关掉后到上限就报错，等管理员介入）。默认开是因为它更省事，
> 而不是因为系统"猜"用户想要更多空间。

#### ⑤ 到顶：明确失败

**硬上限是 1024 个数据文件**——同样来自 ROWID（`file_id 10 位`，§7）。

到顶时**返回明确的错误**，不静默截断、不降级：
"工作区数据文件数已达上限 1024"。

> 1024 × 4 TiB = **4 PiB/工作区**。对单工作区而言这在物理上不可达，
> 所以这条上限不会成为实际约束——但**报错路径仍须实现**：
> "不可达"是当前的判断，不是永恒的保证。

#### 与配额的关系：两条独立约束

§2.2 的配额按角色分设，它与文件增长的边界**不是一回事**：

| 约束 | 性质 | 达到时 |
| --- | --- | --- |
| `max_size` / 1024 文件 | **物理**上限（由 ROWID 位宽决定） | **无法**再增长 |
| 工作区配额 | **策略**上限（管理员设定） | 不再自动增长，**调额后可继续** |

自动扩展**必须同时受两者约束**——先撞到哪个就停在哪个。两者撞线时**报不同的错误**：
配额撞线是"可调额后重试"，物理上限是"到此为止"。混在一起报会让使用者无从区分
"我该去调额"还是"我该去清理"。

### 3.4 数据文件的 MOVE

把一个数据文件从一个文件系统挪到另一个——用于**加盘后平衡容量、换盘、或把热点分散**。

#### 锁定只覆盖"切换"，不覆盖"复制"

朴素做法是"锁住 → 复制 → 切换 → 解锁"，锁定期与**文件大小**成正比——
一个 4 TiB 的文件要锁很久。**用 redo 把复制挪出锁定期**：

```text
① 冻结该工作区（短暂）——记下 LSN L0
② 解冻；后台把文件内容复制到目标文件系统
③ 复制完成 → 再次冻结（短暂）
④ 从 redo 重放 (L0, 当前] 中针对**该文件**的记录到新副本
⑤ 切换：控制文件的槽位号改指新文件系统；删除旧文件
⑥ 解冻
```

**锁定期 = ① + ④ + ⑤**，与**文件大小无关**，只与"复制期间该文件的修改量"有关。

**第 ④ 步为什么可行**：redo 是**页级的物理增量**，块引用里带 `rdba`（§11.5.2）——
筛出 `file_id = 目标文件` 的记录，就是一次顺序扫描加一个比较。
重放本身**幂等**（按 `page_lsn` 判定，§11.5.4），重复应用安全。

**复制期间为什么可以继续读写**：副本是一份**落后于源的旧快照**，
第 ④ 步把它追平。这期间源文件照常服务，不影响任何事务。

#### 复制越久，第 ④ 步越长——以及怎么压住它

第 ④ 步的耗时与"复制期间该文件累积的修改量"成正比。若复制一个 4 TiB 文件要几小时，
期间修改很多，第 ④ 步就可能从"短暂"变成"很长"。

**压缩办法**：复制期间**周期性追平**——每复制完一段就重放一次增量，
让最后一次 ④ 只剩最后一段的修改量。这与成熟产品的在线数据文件迁移是同一手法。

**V1.0 的取舍**：先实现**不做周期追平**的简单形态（一次复制、一次追平）。
它对常见规模（GB 级文件、分钟级复制）已经够用；周期追平是**纯增量优化**，
不改格式、不改协议，实测需要时再加。

#### ROWID 不受影响——这是 file_id 设计的兑现

**文件挪了窝，页地址没变**：ROWID 里的 `file_id` 是**逻辑文件号**，不是物理位置（§7）。
所以：

> **文件 MOVE 不改变任何 ROWID**——索引、行引用、undo 链统统不需要动。

这是 §7 把 ROWID 定义为"表空间内相对地址"而不是"文件路径 + 偏移"的直接收益。
反过来说，**如果 ROWID 里编了物理位置，这个操作就要重建所有索引**——
和下面那个 `Move` 一样贵。

#### 与 §4.7 的 `Move` 区分（务必分清）

| | §4.7 的 `Move` | **本节的 MOVE** |
| --- | --- | --- |
| 搬什么 | **段**——表的数据 | **文件**——整份数据文件 |
| ROWID | **变化 ⇒ 该表索引全部失效，必须重建** | **不变** |
| 用途 | 整理碎片（§4.7） | 平衡文件系统容量、换盘 |
| 频度 | 低频**重活** | **运维常态** |

两者的名字相近，代价却差一个数量级。**挪文件是常态，挪段是重活。**

## 4 段与区

### 4.1 区

- **区 = 8 页 = 128KB**，一次分配的单位，大小固定。
- 连续区减少碎片；小对象的浪费由"按需申请/释放区"控制。

### 4.2 段

每个段（表、索引、Undo）的首个页是**段头页**（`page_type = 7`），记录：

| 项 | 说明 |
| --- | --- |
| 段类型 | 数据 / 索引 / 邻接 / Undo / 临时 / ANN |
| **表选项副本** | `logging`、`update_mode`、`cleanup` 等 |
| **`itl_max`** | 本段各页的 ITL 槽上限。**段级属性，存于此而非页头** |
| 区清单 | 本段占用的区 |
| 高水位（HWM） | 见 §4.3 |
| 追加位置 | 追加型表的下一可写位置 |

**表选项存在段头**：引擎打开段即可分派行为，不必回查目录；段自描述，利于单文件恢复。

### 4.3 高水位与两类表

**HWM = 段内"已格式化且可能含数据"的边界，删除不降低 HWM。** 堆表下全表扫描会扫过空块。

| 表类型 | HWM 策略 |
| --- | --- |
| `update_mode = in_place` | 采用 HWM；配合段收缩回收 |
| **`update_mode = append_only`** | **不需要 HWM**——追加位置由段头显式记录；整段丢弃时不存在空扫问题 |

### 4.4 段级空间管理（插入时选页）

插入一行前先要回答"**插到哪一页**"。页可能有几十万个，不能线性扫描，需要一个段级的空闲页索引。

**采用分级位图**（参照 ASSM，但**简化为两级**）：

```text
段头
 └── 空闲级别位图块（每块覆盖固定数量的页）
      每页 2 位 → 4 个空闲级别
```

| 级别 | 含义 |
| --- | --- |
| 0 | **FULL**——可用空间低于 PCTFREE 阈值，**不接受插入**，但仍允许 UPDATE 使用预留空间 |
| 1 | 低 |
| 2 | 中 |
| 3 | 高 |

**插入流程**：由行长度估算所需空间 → 选定目标级别 → 在该级别中找一页 → 若实际放不下则降级重试。

**段头保存"最后使用的位图块"提示指针**（参照 ASSM 段头的插入提示字段），避免每次插入都从头扫位图。

> **与成熟产品的差异（有意为之）**：成熟产品的 ASSM 用 **L1/L2/L3 三级位图块树**管理。我们简化为两级——**单工作区的段规模远小于通用库的表**，三级树的收益抵不上其复杂度。这与"轻量级、尽可能高效"一致。
>
> **待冻结**：位图块覆盖的页数、级别划分的具体阈值。

### 4.5 Undo 段：事务表与 Undo 页

Undo 位于 **file 1**。它承担**两种**用途，且二者的要求不同（REQ-TXN-006）：

1. **回滚**——撤销未提交的修改
2. **一致性读**——重建某行在旧快照下的版本

第二条决定了保留策略：**读路径不得因写事务而阻塞**（REQ-TXN-003），所以 undo **不能在提交后立即回收**，
必须保留到"再没有任何快照需要它"为止。

参照 Oracle 的四个结构——`KTUBH`（Undo 块头）、`KTUXE`（事务表槽）、`KTUXC`（事务表控制），
以及回滚段头块的分区——以下是逐项取舍。

#### 4.6.1 Undo 页：与堆表页同构的页体

Oracle 为 undo 块定义了专用块头 `KTUBH`。逐字段对照后，**其中只有一项在通用页格式里没有对应物**：

| Oracle `KTUBH` | 我们的对应 |
| --- | --- |
| `ktubhxid`——唯一使用该块的事务 | 页头 `ITL[0].txn_id`。**一个 undo 页同一时刻只服务一个事务**（Oracle 亦然，这是其明确的隐含假设），故一个 ITL 槽足够 |
| `ktubhcnt`——记录数 | 页头 `slot_count` |
| `ktubhidx`——记录偏移表 | 槽位目录（§5.7），同构 |
| `ktubhflg`——标志 | 页头 `flags` |
| `ktubhseq`——块序列号 | **不需要**——改用链式寻址（见下） |
| `ktubhirb`——回滚起始记录 | **不需要**——我们恒从链上最新记录回滚。Oracle 需要它，是因为两阶段提交可能要求部分回滚 |
| `ktubhicl`——收集阶段记录 | **不需要**——不支持两阶段提交 |

**undo 页只需一个 ITL 槽**（`ITL[0]`），记录"这个页当前由哪个事务使用"。
`ITL[0].undo_ptr` 在 undo 页上**不使用**——因为 undo 链是**记录级**而非页级（§4.6.2），
页这一层不参与，也就不需要在页上再挂一条链。

> **结果**：undo 页的页体**与数据页相同**（槽位目录 + 记录区）——但理由不是"统一"（§5.1），
> 而是**访问模式相近**：两者都装变长记录、都要按槽号随机访问。若将来实测发现差异，
> 按 §5.1 的原则，undo 页体可以自行演化。
> 页头 68 字节、槽位目录、行区从页尾向上生长、ITL、校验——全部照旧。

**undo 页受 WAL 保护**：对 undo 页的修改**同样产生 redo**（§11.1.2）。否则崩溃后 undo 自身无法恢复，未提交事务就再也回滚不了——**这不是"顺带"，是恢复正确性的前提**。

#### 4.6.2 Undo 记录的结构

**Undo 链是"记录级"的，不是"页级"的**——这一点统摄整节。

- 数据页的 `ITL.undo_ptr`（§5.4）指向**一条 undo 记录**：该事务在这个页上最后一次修改写下的那条
- 每条 undo 记录内部存**前一条的位置**，沿它走就能回溯该事务的全部修改
- 于是**整个事务只有一条 undo 链**（事务表槽的 `undo_current` 是链头），
  而各页的 `ITL.undo_ptr` 只是链上的**入口点**

```text
事务表槽.undo_current ─▶ [记录 n] ─▶ [记录 n-1] ─▶ … ─▶ [记录 1] ─▶ 0
                           ▲              ▲
数据页 A 的 ITL.undo_ptr ───┘              │
数据页 B 的 ITL.undo_ptr ──────────────────┘
```

**两个用途共用同一条链**：

| 用途 | 入口 |
| --- | --- |
| **回滚整个事务** | 事务表槽的 `undo_current`（链头），走到底 |
| **一致性读某一行** | 该行所在页的 `ITL.undo_ptr`，沿链走直到该行在快照下可见（§11.2、REQ-TXN-006） |

> 与成熟产品一致——知识库原文：**"每条 Undo 记录都有一条指向该事务前一条 Undo 记录的链；
> 记录可以在同一个 Undo 块里，也可以在不同块里。"**

**一条 undo 记录的内容**：

| 字段 | 宽度 | 说明 |
| --- | --- | --- |
| `prev_undo` | 6B | 前一条记录的地址（**与 ROWID 同构**：`file_id + block_id + 页内偏移`）。**0 = 链首** |
| `op` | 1B | 操作码：插入 / 删除 / 更新 / 转发指针更新 |
| `flags` | 1B | |
| `rowid` | 6B | **被修改的行**——链是全局的，一条记录可能改的是别的行 |
| 载荷 | 变长 | 按 `op` 解释，见下 |

**总长不必存**——undo 记录就是 undo 页里的一个"行"，长度由**槽位目录**给出（§5.7）。

**载荷按操作码解释**：

| `op` | 载荷 | 撤销动作 |
| --- | --- | --- |
| **插入** | 无 | 删除该行 |
| **删除** | 整行旧值 | 恢复该行 |
| **更新** | 变更列的**前像列表**：`列号 2B \| 旧值长度 2B \| 旧值` × n | 逐列写回旧值 |
| **转发指针更新** | 旧的转发目标（6B） | 恢复旧指针 |

**更新只存被改列的前像，不存整行**——这是 undo 体积的关键：改一列就只存一列。

> **地址用 6 字节物理位置而非 LSN**：undo 记录的位置是**页内的物理位置**，
> 与 `ITL.undo_ptr` 的宽度一致（§5.4），回滚时可直接寻址、不必先定位日志。
> **LSN 是日志的位置，不是 undo 的位置**——两者不可混用（CONV §3）。

#### 4.6.3 事务表：undo 段头页中的一组槽

事务表放在 **undo 段头页（`page_type = 7`）的页体**中——与 Oracle 把事务表放在回滚段头块一致。
段头页的其余部分（区清单、HWM）沿用 §4.2 的通用格式。

每个槽对应 Oracle 的 `KTUXE`（其大小为 40 字节）：

| 字段 | 宽度 | 说明 |
| --- | --- | --- |
| `state` | 1B | 空闲 / 活动 / 已提交 / 待回滚 |
| `commit_seq` | 6B | 提交序号 |
| `undo_current` | 6B | **undo 链的链头**——该事务最新一条 undo 记录的位置（§4.6.2） |
| `rec_count` | 4B | 链上记录数——容量与回收判断用 |
| `next_free` | 2B | 空闲槽链表 |
| `wrap` | 2B | 槽重用代次 |

**槽的身份是 `(槽号, wrap)`**，两者合成页头 ITL 所用的 `txn_id`：

```text
txn_id 6B = usn 8 | slot 14 | wrap 26
```

- `wrap` 的作用与 §7 曾考虑过的 ROWID"代次"相同——**防止槽被重用后旧引用误匹配**。
  区别是这里它**必须**有：它就是事务身份的一部分，否则槽重用会让两个不同事务的 `txn_id` 相同。
- 位宽的精确切分**待冻结**（§13）。
- `usn`（undo 段号）留在 `txn_id` 里是给多 undo 段留余地。V1.0 单工作区写并发低，
  **一个 undo 段（一页事务表）足够**——16KB 页体按 24 字节/槽可容纳数百个槽，
  即并发写事务的上限。

**刻意省略的 `KTUXE` 字段**：

| Oracle 字段 | 为什么不要 |
| --- | --- |
| `PTX` 父事务 | 为并行 DML 服务，我们不做 |
| `UEL` 的**双重用途** | Oracle 让活动槽用它存"起始区号"、非活动槽用它存"下一空闲槽"——一个字段两种语义。我们**拆成 `undo_current` 与 `next_free`**，不再重载 |
| `DU2` 保留时间 | 我们有明确的提交序号，不需要按秒的保留窗口 |

#### 4.6.4 段控制：`KTUXC` 的对应物

紧跟事务表之后：

| 字段 | 对应 | 说明 |
| --- | --- | --- |
| `reclaim_seq` | `ktuxcscn` | **已回收到的提交序号水位**——低于它的 undo 已被复用 |
| `commit_head` / `commit_tail` | `ktuxcchd` / `ktuxcctl` | **提交链表**：已提交但未回收的事务按提交序号串成链，回收从链头（最老）开始 |
| `slot_count` | — | 事务表槽数 |
| `free_head` | — | 空闲槽链表头 |

**省略**：`INC`（化身号——`wrap` 已覆盖其作用）、`FBP`（空闲块池——我们直接走区分配，不缓存空闲 undo 块）、
两阶段提交相关的 `UBA` 保护、以及未明的 `MGC / VER / XTS / OPT`。

#### 4.6.5 保留与回收：由最老快照封顶

**回收判据**（唯一的）：

> 事务 T 的 undo 可回收 ⟺ T **已提交** 且 `T.commit_seq < 最老快照提交序号`

**为什么是这个条件**：设最老活跃快照为 `S_min`。对任意活跃快照 `S`（`S ≥ S_min`），
凡 `commit_seq < S_min ≤ S` 的事务在所有活跃快照下都**可见**——沿 undo 链反向重建时**不会越过它**。
故它的 undo 不再被任何快照需要。

这正是 §2.6 让控制文件记录**"最老快照提交序号"**的原因：它既是 undo 可用空间的下界，
也是崩溃恢复时判断"undo 链能否走到底"的依据。

**回收顺序**：从 `commit_head` 起，把满足上式的**连续前缀**出链，并推进 `reclaim_seq`。

**长快照与 undo 耗尽**：活跃快照过旧会顶住回收水位，undo 空间随之增长。到达上限时**绝不覆盖仍被需要的旧版本**，
而是按 REQ-TXN-017 报"快照过旧"——**宁可失败，不可返回错误的历史版本**。

### 4.7 段的删除、失效与回收

**空间回收的粒度是段**——不是页，也不是区。

#### 删除分两步：先失效，后回收

```text
① 标记失效（事务内，一步原子）——段立刻从可见世界消失
② 回收其占用的区（延后、幂等）——空间回到可分配池
```

**为什么必须分两步**：若删除要"一步到位"，就得在同一时刻完成
"删字典行 + 清段头 + 还位图 + 释放全部区"，任何一步崩在中间都会留下不一致。
分成两步后，中间态是**明确且安全**的：

| 崩在哪 | 结果 |
| --- | --- |
| ① 未完成 | 段仍然有效——什么都没发生 |
| ① 已完成、② 未完成 | 段已失效（不可访问）；它的区**仍占着，但可被回收**——恢复时补做 ② 即可 |

#### 失效清单就在字典表里

② 需要知道"哪些段失效了"。**不新造结构**——它就是 `seg$` 的一个状态：

| `seg$` 状态 | 含义 |
| --- | --- |
| `LIVE` | 正常 |
| `DEAD` | 已失效，**区尚未回收** |

**为什么状态放字典表而不是段头**：段头是**单页**，改它可以原子完成；但反过来，
要**找出所有失效段**就得扫描整个文件。而 `seg$` 是普通表——有索引、有 WAL 保护，
找失效段只是一次索引扫描。

两步的分工正好各取所长：**段头承载"这个段还在不在"（物理真相），`seg$` 承载"该回收谁"（目录）。**

#### 回收的时机：惰性，不主动

**数据库不主动回收**——没有后台回收线程，也没有定时整理。回收发生在
**分配器找不到空闲区、正准备扩文件之前**：

```text
需要新区 → 空闲池里找
             ├── 找到 → 用
             └── 没有 → 先回收失效段（若清单非空）→ 再找
                           └── 仍没有 → 扩文件 / 新增数据文件（细节见 §3.3）
```

于是**空闲的段在"新的扩展"时被复用**——回收**由需求驱动**：
不发散、不抢占、不需要管理员干预，也不会在系统空闲时白白消耗 I/O。

**回收必须幂等**：一个段的区可能散在多个位图块上，回收过程中崩在中间是可能的。
处理方式是——**重复回收同一个 DEAD 段没有副作用**（位图重复清空是幂等的）。

```text
回收一个段：
  ① 依次清掉它占用的所有区（位图置空闲）——重复执行安全
  ② 全部清完后，删除 seg$ 的 DEAD 行      —— 最后一步，此前崩了重做即可
```

**顺序不能反**：先删 `seg$` 行再清位图，崩在中间就**再也找不到这个段**，
它占的区会永久泄漏。所以清单行**最后删**。

#### 迁移只由显式命令触发

**数据库不做任何主动迁移**——没有后台整理、没有自动 shrink、没有碎片回收扫描。
需要搬家时，由管理员的 **`Move`** 命令显式执行。

**`Move` 的语义**（对应成熟产品的 `ALTER TABLE ... MOVE`）：把段的内容**重写到一个新段**，
旧段随后失效。用途是整理碎片，或把段搬到另一个数据文件。

**它有一个必须写明的后果**：**行的 ROWID 会变**——数据搬到了新位置。于是：

> **`Move` 之后，该表的所有索引全部失效，必须重建。**

这不是缺陷，是"搬数据"的必然。也正因如此，**`Move` 是低频管理操作，不是日常手段**：
代价与数据量成正比，还附带一次全量索引重建。

#### 与 `cleanup` 表选项的关系

§8 的 `cleanup = segment_drop | row_delete` 决定**表的清理方式**，其中一条正是本节的用户：

| 选项 | 语义 | 与本节的接口 |
| --- | --- | --- |
| `row_delete` | 逐行删除，空间由页内 defrag 与区回收处理 | 段长期存在，**不触发本节** |
| `segment_drop` | **按段丢弃**——追加型表按时间分段，到期整段失效 | **正是本节机制** |

`segment_drop` 是本节最主要的用户：会话表、记忆表这类追加型表按时间分段后，
过期就是**一整段失效**——一次元数据操作，不需要逐行扫描。
这正是"回收粒度是段"的价值所在。

### 4.8 临时段（file 2）

**临时空间按段分配**——与数据段**同一套机制**（段 + 区），不另立体系。

#### 分配：按需创建 N 个区，N ≥ 1

一个需要溢出的操作（排序、哈希、分词）开始时，为它**创建一个临时段**，
并按预估量**一次性申请 N 个区**；不够时再追加。

```text
溢出开始 → 创建临时段，申请 N 个区（N ≥ 1）
              └── 用尽 → 追加区（可反复）
溢出结束 → 删除该段
```

**为什么 N 最小为 1**：N 是**按需**的。多数溢出很小，起步就给多个区是浪费；
真正大的溢出靠"追加区"接住。N 的默认取值见 §13 待冻结项 37。

**为什么按段而不是"散装区"**：段给了三样东西，散装区都没有——
**归属明确**（诊断能回答"谁在用临时空间"）、**一次性回收**（删段即全部归还）、
**与数据段共用申请/释放路径**（不新增代码）。

#### 回收：删段即可，因为不持久化

**临时段不持久化**——它是查询执行期的中间结果，查询一结束就没有意义。于是它
在几个关键点上与数据段分道扬镳：

| | 数据段 | **临时段** |
| --- | --- | --- |
| 崩溃后 | 需要恢复（§11.2） | **不需要**——内容定义为可丢 |
| 回收方式 | 先失效、后惰性回收（§4.7） | **直接删段**——不经过失效态 |
| WAL | 受保护 | **不记**（见下） |

**为什么可以直接删**：§4.7 那套"先失效、后回收"是为了**崩溃后能找回"该回收谁"**。
临时段没有这个问题——崩溃后整个 file 2 都要重置，那份清单本身就是多余的。

#### file 2 的打开与重置

**打开工作区时，file 2 直接重置为空**（重写文件头与页分配位图）。

- **不需要恢复逻辑**：临时数据定义为可丢，重置比恢复更快也更简单
- **不需要判断上次是否正常关闭**：无论上次是正常关闭还是崩溃，
  临时数据在两次会话之间都没有意义
- 于是 file 2 的**页分配位图也不必进 WAL**——它跟着一起被重置

> 注意边界：§11.4"位图必须受 WAL 保护"指的是**数据文件**的位图——
> 那里丢了是**整个表空间不可用**。file 2 的位图丢了只是临时空间要重建，量级完全不同。

#### 并发与耗尽

**每个溢出操作一个临时段**——查询之间天然不共享，不需要额外隔离。
同一工作区内的多个并发查询各拿各的段，互不干扰。

**耗尽时的行为**：临时空间有上限（§2.2 的配额按角色设）。达到上限时，
该操作**失败并返回明确的资源错误**（含可重试条件），**不做"回退到内存"之类的隐式降级**——
隐式降级会让内存用量变得不可预测，而内存比磁盘更紧，不该由一次排序把它悄悄吃掉。

## 5 页

### 5.1 页的三段：头、体、尾

**只有头和尾是全类型统一的；页体是每种页类型自己的事。**

```text
┌──────────────────────────────────────────────────────┐
│ 页头 68B（**全类型统一，不可变**）                     │
│   描述区 32B │ 事务区 32B │ 空间区 4B                  │
├──────────────────────────────────────────────────────┤
│ 页体（**由 page_type 决定，各自定义**）                │
│   数据页   ：槽位目录 + 行区（§5.7、§6.7）             │
│   Undo 页  ：槽位目录 + 记录区（§4.6.1）               │
│   索引叶页 ：**有序条目数组**（§9.1.3）                │
│   索引分支页：有序条目数组 + 最左子指针（§9.1.3）      │
│   邻接页   ：按 (src, edge_id) 聚簇的顺序区（§9.2）    │
│   ANN 页   ：metapage / element / neighbor（§9.3.3）   │
├──────────────────────────────────────────────────────┤
│ 页尾（**由 page_type 决定大小**）                      │
│   一般页 4B（仅页尾校验）；索引叶页 16B（含双链）      │
└──────────────────────────────────────────────────────┘
```

#### 页头为什么必须统一

页头承载的是**恢复与事务所需的一切**——`page_lsn`（幂等判定的依据）、ITL（可见性与行锁）、
`workspace_ref`（隔离兜底）、校验。这些是**所有页类型共同参与**的机制：
恢复要重放每一页，事务要锁每一页的行。

**若页头按类型不同，恢复路径就要按类型分支**——而恢复是最不能出错、
又最难被日常操作覆盖到的路径。这一条不可让步。

#### 页体为什么必须可以不统一

不同页类型的**访问模式不同**，强行统一就是拿一种模式的结构去套另一种。最明显的例子：

> **索引页的条目必须按键有序**（要二分查找），而**槽位目录是无序的**（按插入顺序）。
> 给索引页套槽位目录，等于让它在一个无序结构里做有序查找——
> **格式与访问模式直接冲突**。

同理：ANN 页的向量是定长的、邻接页的边是按 `src` 顺序追加的——它们都不需要
"变长行 + NULL 位图 + 变长偏移"那一整套为多列可变行准备的结构。

#### 界线划在哪

| 层 | 是否统一 | 理由 |
| --- | --- | --- |
| **页头** | **必须统一** | 恢复与事务的正确性基础；分支即意味着恢复路径分支 |
| **页尾** | 按类型 | 已如此（§5.8） |
| **页体** | **按类型自定义** | 格式服务于访问模式；强求一致是拿效率换整齐 |

**代价必须写明**：页体各自定义意味着**空间管理、插入/删除、defrag 要按类型实现**。
这是真实的成本，不是免费的灵活性。

界线的一句话版本：**页头与恢复相关的机制必须共享；页体可以按访问模式优化。**
**不为一致性付效率的账，也不为效率付正确性的账。**

> 因此 §5.7 的槽位目录、§5.9 的 PCTFREE 都是**页体层的机制**，
> 适用范围要各自说明，**不再是"所有页通用"**。

### 5.2 字段准入纪律

**页头只含"崩溃后无法重建"的落盘信息。** 判断标准只有一条：

> 这个字段，在进程崩溃重启、且**没有它**的情况下，能否从页的其余内容或外部结构**重建**？**能重建的就不进页格式。**

**由此划清与缓冲区头的界限**（此处极易混淆）：

| | 页头（**落盘**） | 缓冲区头（**仅在内存**） |
| --- | --- | --- |
| 归属 | 数据块本身的一部分 | BufferPool 的内存结构 |
| 内容 | 身份、完整性、事务、空间信息 | pin 计数、latch、LRU 链指针、脏标志、touch count |
| 定义位置 | 本文 §5 | 另行展开 |

**两者不必有任何字段对应关系**——缓冲区头不迁就页格式，页格式也不为缓存便利加字段。

> **命名警示**：Oracle 的 `kcbh`（字面 "kernel **cache** block header"）**是落盘的块头**；只在内存的是另一结构 `kcbbh`（Buffer Header）。两者**只差一个字母**。

### 5.3 描述区（32 字节）

| 偏移 | 长度 | 字段 | 说明 |
| --- | --- | --- | --- |
| 0 | 4 | `checksum` | CRC32C，覆盖全页（本字段置零后计算） |

| 5 | 1 | `page_type` | 见 §5.6 |

| 22 | 6 | `page_lsn` | 最近修改的日志位置（48 位） |
| 28 | 4 | `reserved` | |

**`flags`（只含崩溃后必须存活的状态）**：

| 位 | 含义 |
| --- | --- |
| 0 | 页初始化完成（未完成的页不得使用） |
| 1 | 含跨页行片段 |

**`file_id` 与 `block_id` 分开存**（而非 pack 后的 ROWID）：页头可独立校验，且与 ROWID 位宽解耦。

### 5.4 事务区（32 字节，含默认 1 个 ITL）

**事务区头（8 字节）**

| 偏移 | 长度 | 字段 |
| --- | --- | --- |
| 32 | 2 | `itl_count` |
| 34 | 6 | 保留（`itl_max` 在段头；`last_cleanup` 因采用即时清除而不设） |

**ITL 条目（24 字节，偏移 40）**

字段宽度**按本设计自身的度量推导**，不是照搬任何现有产品：

| 偏移 | 长度 | 字段 | 宽度依据 |
| --- | --- | --- | --- |
| 40 | 6 | `txn_id` | 单调递增、**永不复用**。48 位按 1000 事务/秒可用 8900 年，故不需要三段式回绕结构 |
| 46 | 6 | `undo_ptr` | **与 ROWID 同构同宽**：`file_id(10) + block_id(28) + 页内偏移(10)` |
| 52 | 6 | `commit_seq` | **与 `page_lsn` 同宽**（48 位） |
| 58 | 2 | `lock_cnt` | 本事务在本块锁定的行数——ITL 槽回收条件 |
| 60 | 1 | `flags` | 空闲 / 活动 / 已提交 / 已回滚 |
| 61 | 3 | 保留 | |

**ITL 的两个核心作用**：

1. **可见性判定在块内自包含**——`commit_seq` 存于 ITL，读一页即可判断"改这行的事务提交了没有、提交序号是多少"，**不需要任何全局事务状态表**。
2. **行锁由 ITL 承载，不用全局锁表**——一行的锁状态就是它 `itl_slot` 所指的 ITL 条目（见 §6.1）。无内存开销、无全局争用点、崩溃恢复随数据页自然一致。

**默认 `INITRANS = 1`**：写并发低，1 个槽足够。ITL 槽用尽时**动态扩展**（受段头 `itl_max` 限制）；达上限仍无空槽则该事务**等待**，不得静默失败。

### 5.6 页类型

**页头一致，页体按类型各自定义**（§5.1）。下表是全部页类型：

| 值 | 类型 | 页体 | 所在 |
| --- | --- | --- | --- |
| 1 | **堆表页** | 槽位目录 + 行区（§5.7、§6.7） | file 3+ |
| 2 | **索引叶页** | 有序条目数组 + 页尾双链（§9.1.3） | file 3+ |

| 7 | **段头页** | 段类型、表选项、区清单、HWM（§4.2）；**undo 段头页额外含事务表**（§4.6.3） | 段的首页 |

> **编号在格式冻结前仍可调整，冻结后不可变**。当前格式版本为 1（未冻结），
> 故本次做了整齐化重排。

**`page_type` 不是页体格式的全部**：同一类型下页体仍可能按用途细化。
例如 `update_mode = append_only` 的表**仍用同一个堆表页格式**（`page_type = 1`），
只是空间管理策略不同（§8）——**那是表之间的统一，与页类型之间的分化是两回事**（§5.1）。

### 5.7 槽位目录与空闲管理

**这是「数据页 / Undo 页」这一类页体的组织方式**——它们都装**变长记录、需要按槽号随机访问**。
**索引页不使用它**：索引条目必须按键有序（要二分查找），而槽位目录是无序的（§5.1）。

**每个槽位 2 字节**：

```text
位 15–2 (14 位)：行数据起始偏移（0–16383，恰好覆盖 16KB 页）
位 1–0  (2 位)：状态 —— 0 空闲 / 1 正常行 / 2 转发指针 / 3 片段头
```

**行长不存于槽位**——存于行头。若槽位存 `(偏移, 长度)` 需 4 字节，1024 槽即 4KB（页的 25%）；2 字节方案为 2KB（12.5%）。

**槽位上限 1024** —— 与 ROWID 的 `row_id` 10 位**耦合，两者须同时修改**。

**defrag（页内整理）**：空闲空间分散、无法容纳新行时，将活动行向页尾 compaction，合并空闲区。整理**必须更新所有槽位偏移**且受 WAL 保护。

### 5.8 页尾区

**页尾区大小由 `page_type` 决定**：

| 页类别 | 页尾区 | 内容 |
| --- | --- | --- |
| 数据页、Undo 页等 | 4 字节 | 页尾校验 |
| **索引叶页** | 16 字节 | `link_prev`(6) + `link_next`(6) + 页尾校验(4) |
| **索引分支页**（含根页） | **4 字节** | **仅页尾校验**——分支页没有兄弟链，见下 |

**页尾校验始终在最后 4 字节**——检查器读一页时先看末尾即可，无需先判断页类型。

**为什么分支页不带前后指针**：范围扫描**只沿叶链走**；分支页的访问永远是自顶向下的
单路径遍历，兄弟之间没有横向关系。Oracle 同样只给叶块加 `kdxlenxt`/`kdxleprv`，
分支块没有。给分支页留这 12 字节是白付的，且分裂时要多维护两个字段。

**页尾校验的作用**：页最后 4 字节存放**头部关键字段的副本**（`page_type` + `mod_seq` + `page_lsn` 低位）。读页时**对比头尾**，不一致即为**断裂块**（fractured block）——检出"只写了一半"。

**与校验和互补，不是替代关系**：

| 机制 | 职责 | 成本 |
| --- | --- | --- |
| 页尾校验 | 检出**断裂块**（部分写入） | 极低——一次 4 字节比较 |
| `checksum` | 完整**数据完整性** | 全页计算 |

> 不记日志的表**依赖这两层**检出撕裂页。

### 5.9 页内空闲空间与 PCTFREE

#### 生长方向

**行数据从页底向上生长**（与成熟产品一致）：

```text
低地址 ┌──────────────────────┐
       │ 固定头 68B            │
       │ 槽位目录 ↓ 向高地址增长 │
       ├──────────────────────┤
       │                      │
       │      空闲空间         │   ← 两块相向生长，中间即空闲
       │                      │
       ├──────────────────────┤
       │ 行数据 ↑ 向低地址增长  │   ← 从页底向上
       │ 页尾区（4/16B）        │
高地址 └──────────────────────┘
```

两端**相向生长**，中间是**单一连续空闲区**。好处：空闲空间大小就是两个指针之差，无需维护碎片链；代价是碎片化时空闲区会分散，需要 defrag（见下）。

#### 空闲空间的记账

- **页头存 `free_end`**（行区上界）；**`free_start` 可推导**：`固定头末尾 + slot_count × 2`
- **可用空间** = `free_end − free_start`
- 页头**不存 `free_size`**——两个指针之差即可算出，存了就是冗余（违反 §5.2 的字段准入纪律）

#### PCTFREE

**语义**：**插入后必须保留的最小空闲空间比例**，为已有行的后续更新预留，以降低行迁移概率。

| 项 | 规定 |
| --- | --- |
| 默认值 | 10（待冻结） |
| 取值范围 | 0–99 |
| 判定 | `可用空间 − 行长 ≥ PCTFREE% × 页大小` 时才允许插入 |
| **是下限不是上限** | 实际空闲空间**可以大于**该比例（删除、更新变短都会让页变空），PCTFREE **只阻止插入，不阻止页变得更空** |

**表页与索引页的语义不同**（照搬成熟产品的行为，理由见右）：

| | 表页 | 索引页 |
| --- | --- | --- |
| PCTFREE 何时生效 | **持续生效**——每次插入都判定 | **仅在建索引时预留**，之后不再强制 |
| 理由 | 更新会加长行，预留空间直接降低迁移 | 索引项按键序插入；严格强制会导致**过早分裂、空间浪费**。这与 B+Tree 的常规行为也更一致 |

> **必须显式记录这条差异**：两类页在"空间是否允许插入"上判定不同，是实现与测试都容易踩错的地方。

#### defrag（页内整理）

当空闲区被行删除切碎、**总空闲够但连续空闲不够**时触发：将活动行向页底 compaction，合并空闲区。

- **必须更新所有槽位偏移**，且**受 WAL 保护**
- **触发条件与阈值待冻结**（见 §13）

**defrag 与 PCTFREE 的关系**：整理后页可能变得很空，但**空不代表可插入**——插入仍受 PCTFREE 阈值约束。

### 5.10 缓冲池

**数据库不直接读写文件**——所有页的读写都经过内存里的缓冲池（DB Cache）。
这不是实现细节，而是上层一批机制存在的**前提**：正因为修改先落在内存里的副本上，
才有了"脏页""写回""检查点"这些概念，也才有了 `steal + no-force`（§11.2）与
检查点（§11.7）。

**缓冲池是实例级共享的**——所有工作区共用一个池、一套后台写线程（§11.7），
不按工作区各建一份。因此**池的键必须带工作区标识**（§7 早已要求）：
不同工作区会出现相同 ROWID，只按 RDBA 索引会串页。

#### 两种"页头"必须分清

| | 页头（**落盘**） | 缓冲区头（**内存专有**） |
| --- | --- | --- |
| 位置 | 页的前 68 字节 | 缓冲池中的独立结构，**不落盘** |
| 内容 | 只含"崩溃后无法构建"的信息（§5.2） | 运行时状态：链指针、latch、引用计数、脏标志、**首次变脏的 LSN** |
| 生命周期 | 与页同寿 | 随缓冲块生灭 |

> Oracle 的命名陷阱值得记一笔：它的 `kcbh` 是"kernel **cache** block header"——
> 名字里有 cache，却**是落盘的**；真正内存专有的是 `kcbbh`（多一个 b）。
> 一字之差，检索资料时极易混淆。

**这条纪律的意义**：缓冲区头里全是"重启即可重建"的信息。把它们放进落盘页头，
既白白消耗磁盘格式，又让磁盘格式随内存实现变动——一旦定错就要改磁盘格式。

#### 缓冲区头的内容

| 字段 | 作用 |
| --- | --- |
| **页标识：工作区标识 + RDBA** | 哈希键。缓冲池实例级共享，键**必须带工作区标识**——不同工作区会出现相同 ROWID |
| **脏标志 + 首次变脏的 LSN** | 挂入脏链；决定写出顺序（§11.7 的检查点队列） |
| 引用计数 | 正在持有它的读者/写者数 |
| latch | 保护缓冲块 |
| LRU / 脏链指针 | 见下 |
| 状态位 | 正在读入 / 正在写出 / 已固定 |

#### 两条链

| 链 | 排序 | 用途 |
| --- | --- | --- |
| **LRU 链** | 最近使用 | 挑淘汰对象 |
| **脏链（检查点队列）** | **每个工作区一条，各自按首次变脏的 LSN 升序** | DBWR 按序写回（§11.7） |

**脏链为什么按"首次变脏的 LSN"排序**：恢复起点要求"**该点之前的修改已全部落盘**"，
它只能是**连续前缀**。乱序写会让低水位推不动，检查点位置无法前进，恢复时间失控。

**为什么是"每工作区一条"而不是池级一条**：LSN 是**每工作区独立**的（每个工作区有自己的
redo 序列），**跨工作区不可比**——一条混排的链根本排不出有意义的全序。
而且低水位是每工作区一个（§11.7），链也必须跟着分。

#### 缓冲池划分为工作集（参照 Oracle `kcbwds`）

缓冲池不是一个整体，而是划分为若干**工作集（working set）**——每个工作集是一个独立分区，
**自带一条 LRU 链、一组脏链、以及保护它们自己的 latch**。每个缓冲块**静态归属于一个工作集**。

Oracle 的描述符叫 `kcbwds`，其中记录 WS 状态、**WS ID**、所属缓冲池、NUMA 信息、
**使用的 DBWR 号**与闩锁；**每个 buffer header 里也存一份工作集 ID**——这就是缓冲块与工作集的关联方式。
每个工作集由**两个 latch**保护：`cache buffer lru chains` 与 `checkpoint queue`。

**为什么分区**：减少 latch 争用。全局一条 LRU 链意味着所有读者与写者抢同一把 latch；
分区后各工作集并行推进。

**我们的分区依据是工作区**——这是与 Oracle 的关键差别：

| | Oracle | 我们 |
| --- | --- | --- |
| 缓冲块如何归属 | **轮询分配，与数据无关**（一个表的数据散在所有工作集里） | **随工作区**——一个工作区的全部缓冲落在**同一个工作集** |
| 分区依据 | **硬件**（CPU 数 / NUMA） | **工作区** |
| 为什么这样分 | 它的争用来自"许多前台进程抢 latch"，与访问哪个表无关 | 我们的争用来自"**每个工作区各自的检查点推进**"，边界天然是工作区 |

**这个差别的收益是具体的**：一个工作区的检查点推进只需碰**一个工作集**的 latch，
**零跨工作集协调**。Oracle 做不到这一点——它的检查点是全局的，注定要碰所有工作集。

**数量有上限**：工作集描述符与 latch 都是固定开销，所以工作集数是**配置项**。
**一个工作区不被拆分**到多个工作集；当活跃工作区多于工作集数时，**多个工作区共享一个工作集**，
但它们各自的脏链仍然独立（§11.7）。

**层级关系一览**（三条约束从图上一目了然）：

```text
缓冲池（实例级，一套）
  ├── 分区 / 工作集 0   ← 自带 LRU 链与 latch；绑定一个写线程
  │     ├── 工作区 A ──▶ 脏链 A（按本工作区的 LSN 升序）
  │     └── 工作区 C ──▶ 脏链 C
  ├── 分区 / 工作集 1
  │     └── 工作区 B ──▶ 脏链 B
  └── …
```

- **工作区不被拆分**——A 的全部缓冲只在一个分区里，不散到别处
- **分区不被拆分**——一个分区只由一个写线程负责，没有两个线程抢同一分区
- **脏链不跨分区**——每条脏链只属于一个分区；分区内的多个工作区各有自己的链，只是共享 latch

**分区是可选能力**：`N = 1` 是**合法配置**，等价于不分区——小规模部署就用一套，
不必为用不上的并行付复杂度。分区数上限与映射函数见 §13 待冻结项 34。

#### 替换策略：steal + no-force

- **steal**：脏缓冲**可以**被淘汰（写回后腾出）。所以恢复必须能撤销（§11.2 的三阶段）。
- **no-force**：提交时**不要求**把该事务的脏页刷盘。

两者合起来，正是"提交只需 WAL 持久化"的由来——**提交的关键路径上没有任何数据页 I/O**。
代价是崩溃恢复必须做撤销阶段。这是自觉的取舍：**用恢复期的复杂度换提交路径的延迟**。

#### 脏页被偷换出去前的写前保证

脏缓冲被淘汰（steal）去写回之前，其修改的 redo **必须已落盘**（WAL 规则 2，§11.1）。
否则崩溃后无法重放这次修改。

实现上这不是额外动作——**页的 `page_lsn` 就是判据**：
写出前检查"redo 是否已持久化到该 `page_lsn`"，未持久化则先推进日志
（此时可能退化为一次同步 `fsync`）。后台维护一个"**已持久化的 LSN 水位**"即可 O(1) 判断。

### 5.11 各页类型的页体

**统一约定**：被日志保护、参与事务的页（类型 1–12）共享 **页头 68B**（§5.3–§5.5）
与**页尾校验 4B**（§5.8）。本节只写**页体**（自偏移 68 起）。

> **两类页不受此约束**：**redo 页与控制文件页是恢复机制本身**——它们不被重放、
> 不参与 ITL。§5.1"页头统一"的理由是"所有页都参与恢复与事务"，
> 而这两个**恰恰是恢复的载体**。它们按自己的需要定义页头。

| # | 页类型 | 页体 | 状态 |
| --- | --- | --- | --- |
| 1 | 堆表页 | 槽位目录 + 行区 | ✅ §5.7、§6.1、§6.7 |
| 2 | 索引叶页 | **有序条目目录 + 条目区** | ✅ 本节 |
| 3 | 索引枝页 | 同 2，**外加最左子指针** | ✅ 本节 |
| 4 | 索引根页 | **同 3** | ✅ 本节 |
| 5 | 邻接页 | — | ⬜ 见 §13 待冻结项 |
| 6 | ANN 索引页 | — | ⬜ 见 §13 待冻结项 |
| 7 | 段头页 | 段类型、表选项、区清单、HWM | ✅ §4.2 |
| 8 | 位图页 | 区分配位图 | ✅ §3.2 |
| 9 | Undo 页 | 槽位目录 + undo 记录区 | ✅ §4.6.1 |
| 10 | 临时页 | **同 1** | ✅ §4.8 |
| 11 | 文件头页 | 文件标识与自描述 | ✅ 本节 |
| 12 | 引导页 | 自举条目数组，**格式永久固定** | ✅ §3.1 |
| 13 | REDO 页 | 自有页头 + 记录流 | ✅ 本节（新定） |
| 14 | 控制文件页 | — | ⬜ **待定**：§2.6 的定长估算须先重做 |

#### 索引页的页体（类型 2 / 3 / 4）

```text
偏移 68    页体头（8B）
              entry_count 2B   条目数
              left_child  6B   **最左子指针**——仅枝/根页有意义，叶页置 0
偏移 76    条目目录（向高地址增长）：每项 2B，**按键升序**，指向条目起始偏移
                 ───── 空闲区 ─────
           条目区（自页尾向上增长，下界 = 16384 − 页尾区）
```

| 页类型 | 页尾区 | 条目内容 |
| --- | --- | --- |
| **2 叶页** | 16B（含双链） | `key_len 2B \| key \| ROWID 6B` |
| **3 枝页** | 4B | `key_len 2B \| 分隔键 \| 子页 ROWID 6B` |
| **4 根页** | 4B | 同枝页 |

**与堆表页的关键差别——目录必须有序**：

| | 堆表页 | **索引页** |
| --- | --- | --- |
| 目录顺序 | **无序**（槽号即 `row_id`，复用无害） | **按键升序**（要**二分查找**） |
| 定位方式 | 按槽号 O(1) | 按二分 O(log n) |
| 插入 | 取一个空槽 | **移动目录项**以维持有序（每项 2B，代价小） |

这正是 §5.1 说的"格式服务于访问模式"——**同一个"目录 + 区"的骨架，
两种截然不同的组织**。

**索引条目没有行级 lock 字节**（Oracle 的索引行有 `lock` 指向 ITL 槽，我们不需要）：
索引项的插入与删除**由页级 ITL + latch 保护**，可见性由**回表时按行的 ITL 判定**——
索引项自身不承载事务状态。这比 Oracle 少一个字段。

**`left_child` 在叶页置 0**：叶页没有子页，这个字段是为枝/根页的
"n 个条目对应 n+1 个子页"准备的（§9.1.3）。**保留 6 字节而非按类型改变页体头**——
页体头定长使解析统一，而 6 字节的代价远小于"页体头变长"带来的复杂度。

#### 文件头页（类型 11）——每个文件的块 0

```text
偏移 68    file_id        2B    本文件的编号（与 ROWID 的 file_id 一致）
           role           1B    0 元数据 / 1 Undo / 2 Temp / 3+ 数据（§2.2）
           format_version 1B
           flags          2B
           **当前大小**   6B    以块为单位——**权威在这里，不在控制文件**（§2.6）
           workspace_ref  8B    与页头同源，用于"打开错了文件"的快速否决
           reserved       …
```

**"当前大小"记在这里，而不是控制文件**——这是 §2.6 那条决定的对偶：
控制文件只存**创建时大小**（创建后不变），**可变量一律以文件自身为准**。
于是"扩展文件"是一次自足的原地操作，不碰控制文件的双副本（§3.3）。

#### REDO 页（类型 13）

**redo 文件有页结构**——理由是 **redo log buffer**：有了页，日志缓冲区才能按页
分配、按页回收、按页刷盘，缓冲管理才有单位。

```text
偏移 0    校验          4B    覆盖整页
偏移 4    页位置        6B    本页在日志中的**起始 LSN**——恢复时校验顺序
偏移 10   已用长度      2B    页内有效字节数（自页体起算）——恢复扫描的终止依据
偏移 12   flags         1B
偏移 13   reserved      1B
偏移 14   reserved      2B
偏移 16   页体：记录流，从偏移 16 开始
```

**页体是"记录流"**，不是"目录 + 区"——redo 的记录是**只追加**的，
没有删除、没有随机访问，目录在这里没有意义。**这又是一个"格式服务于访问模式"的例子**。

**记录不跨页**：一条记录放不下当前页的剩余空间时，**当前页尾部补零**（或标记），
记录从下一页开始。

> 这条与"**记录不跨文件边界**"（§11.5.1）是同一个思路，而且它**消除了 PG 的跨页问题**：
> PG 允许记录跨页，代价是落一条记录要拿**全部 8 把 WAL 插入锁**
> （`WALInsertLockAcquireExclusive`）。**我们不允许跨页，那个代价就不存在**。
> 代价是每页尾部可能有几十字节的碎片——对 16KB 的页可忽略。

**待定（见 §13）**：redo 页的大小（是否与数据页同为 16KB），
以及**记录头是否仍需要 4B CRC**——页校验已覆盖整页，记录级 CRC 可能是冗余的。

## 6 行与列的内部布局

### 6.0 三条编码原则

列的物理编码遵循三条原则，**按重要性排序**：

**① 排序友好——编码使「字节比较 = 值比较」**

这是最重要的一条。B+Tree 索引比较键时若必须**解码**才能比较，代价极高；若编码本身就是保序的，索引可以直接比较字节。成熟产品的编码正是为此设计的：`NUMBER` 正数每个数字字节 +1、`DATE` 各字段加固定偏移，都是这个目的。

> 这一条**约束了几个看似合理的优化**：例如整数不能用机器原生小端整数存储（会破坏与 `NUMBER` 的序关系），详见 §6.5。

**② 变长优先**

能变长就变长，省空间。`NUMBER` 只存有效数字字节、`VARCHAR2` 只存实际字符。

**③ 自描述**

类型与长度信息随数据存放，**不依赖外部字典才能解码**。否则读一行的成本会变成"先查字典再读行"。

---

### 6.1 行头

| 偏移 | 长度 | 字段 |
| --- | --- | --- |
| 0 | 1 | `row_flags` |
| 1 | 1 | **`itl_slot`** |
| 2 | 2 | `row_len`（含行头） |
| 4 | 2 | `col_count` |
| 6 | 2 | `null_bitmap_len` |
| 8 | 2 | `var_col_count` |
| 10 | *n* | `null_bitmap` |
| | *2m* | `var_offsets` |
| | | 列数据（定长列在前，变长列在后） |

**`row_flags`**：位 0 = 已删除；位 1 = 已迁移（本槽位是转发指针）；位 2 = 跨页行片段；位 3 = 含大字段。

**`itl_slot`**：指向本页事务区中的 ITL 槽**索引**，`0xFF` 表示无。这是**行 → ITL → Undo** 链条的第一环，一致性读据此定位该行的 Undo 记录。取**单独 1 字节**，不复用 `row_flags` 的位——读取少一次判位分支。

**行头不含**版本号、时间戳、事务 ID。行内只有 `itl_slot` 这个**索引**，事务本身的标识、提交序号、Undo 位置都在 ITL 里（**块级共享**，多行共用一条）。

**NULL 位图**：字段缺失 / JSON null / SQL NULL **在存储层是不同表示**，不可压成一位。

### 6.2 行迁移（转发指针）

行更新后变长、原页放不下时：

```text
原槽位：状态 = 2（转发指针），行体只放 6 字节新 ROWID
新位置：完整行，槽位状态 = 1
```

- **原槽位的 ROWID 保持不变**（稳定入口）——**索引不需要更新**，仍指向原 ROWID，经转发指针到达。
- **转发指针可更新多次**：行再增长就再迁移一次，只需更新原槽位的转发指针。**不设"头片段不二次迁移"那类转换规则**——行迁移在写少读多的画像下本就罕见，二次迁移更罕见，不为小概率事件增加设计复杂度。
- 只有当行**超过单页容量**时才转向**行片段链**（§6.3）——另一个触发条件，与迁移解耦。
- **代价**：多读一页。故需 `PCTFREE` 类预留比例降低迁移概率（待冻结）。

### 6.3 跨页行（行片段链）

行首次插入即超过单页可用空间时（大 JSON、高维向量）：

```text
头片段（槽位状态 = 3）：行头 + flag 位 2 + 指向下一片段的 ROWID
中间片段：片段头（下一片段 ROWID）+ 数据
尾片段：片段头（下一片段 = NULL）+ 数据
```

- 只有**头片段**有稳定 ROWID 并出现在索引中。
- 链**必须受 WAL 保护**——任一点中断后可恢复为一致状态，不得出现半截链。
- 链长度**有界**，超限返回明确错误（上界待冻结）。

> **与 16KB 页的关系**：选 16KB 正是为了让**主流维度向量（≤3072 维，12KB）不落进这条路径**。跨页是例外路径，不是热路径。

### 6.4 删除与槽位复用

| 步骤 | 动作 |
| --- | --- |
| 1 | 置 `row_flags` 位 0（已删除），写 Undo |
| 2 | **索引项随事务一并移除**（删除即移除、回滚即恢复） |
| 3 | 提交后槽位置空，可被复用 |
| 4 | 空间由 defrag 合并，**不在删除时立即回收** |

**为何不需要代次**：索引项与行**同生共死**，不存在"索引项比行活得更久"的窗口。这是**用机制排除**，而非用代次检测。

**已知行为（非缺陷）**：RC 下索引扫描可能漏读语句开始后被并发删除的行——索引项已移除，堆中 Undo 无机会被使用。须在测试基线中断言"**允许漏读**"。

### 6.5 六类标量的物理编码

#### NUMBER

采用**变长基 100 科学计数法**（参照成熟产品）：

```text
字节 0：符号位 + 指数
        最高位（0x80）: 1 = 正数或零，0 = 负数
        低 7 位:       指数 + 65（偏移量）
字节 1..n：数字位，每字节 0–99（基 100，一字节存两位十进制）
        正数：每字节 +1 存储
        负数：每字节 = 101 − 值
特殊：0 编码为单字节 0x80
最多 20 个数字字节（≈40 位十进制，覆盖 p ≤ 38）
```

**为什么 +1 和 101−值**：使**字节序与数值序一致**——正数按字节升序即数值升序；负数的反转处理使数值越大字节越小。这样索引比较无需解码。

**`INTEGER` 的存储**：`INTEGER` 语义为 `NUMBER(38,0)`，**磁盘上使用与 `NUMBER` 完全相同的编码**。

> **为什么不用机器原生整数**：若 `INTEGER` 用小端 64 位整数存储，其字节序与 `NUMBER` 编码**不同序**，同一列内索引比较会错。**整数快路径只允许存在于计算路径，不得改变磁盘编码**——这正是需求中"NUMBER 不使用 double 承载、整数快路径只是优化"的物理含义。

#### DATE

**固定 7 字节**，各字段加偏移后存储：

| 字节 | 字段 | 编码 |
| --- | --- | --- |
| 0 | 世纪 | `(year / 100) + 100` |
| 1 | 年 | `(year % 100) + 100` |
| 2 | 月 | 原值（1–12） |
| 3 | 日 | 原值（1–31） |
| 4 | 时 | `hour + 1` |
| 5 | 分 | `minute + 1` |
| 6 | 秒 | `second + 1` |

**偏移的两个目的**：① **排序兼容**——字节序即时间序；② **支持公元前**——世纪可为负，+100 保证非负。

#### TIMESTAMP

**前 7 字节与 `DATE` 完全一致**，另加小数字段：

| 声明精度 | 存储宽度 |
| --- | --- |
| 0 | **7 字节**（同 DATE） |
| 1–9 | **11 字节**（7 + 4 字节纳秒） |

宽度**由列的声明精度决定**，故每列宽度固定、行内定位简单。精度取 0 时省 4 字节。

#### CHAR

**固定 N 字节**，不足部分**以空格（0x20）填充**。

**空格填充语义必须在存储层体现**：`CHAR` 的比较使用空格填充语义，`VARCHAR2` 不使用——这直接来自编码差异，不是额外的比较规则。

#### VARCHAR2

**变长，只存实际字符**（不填充）。

**与成熟产品的关键差异**：不设**每列长度前缀**。长度由行头的 `var_offsets` 数组相邻项之差得出，末列长度由 `row_len` 界定。

| | 每列长度前缀 | 行头偏移数组（**采用**） |
| --- | --- | --- |
| 取第 k 列 | 需**顺序扫过**前 k−1 列 | **直接定位** |
| 空间 | 每变长列 1–2 字节 | 每变长列 2 字节 |
| 冗余 | 长度信息分散在各列 | 长度可推导，**不重复存** |

读多写少、点查为主的画像下，**随机访问一列的成本更值钱**，故选偏移数组。

### 6.6 扩展类型的物理编码

| 类型 | 编码 | 备注 |
| --- | --- | --- |
| `BOOLEAN` | 1 字节（0/1） | NULL 由 NULL 位图表达，不在数据区 |
| `UUID` | **16 字节**定长 | 大端 |
| `FLOAT32` / `FLOAT64` | IEEE 754，4 / 8 字节 | **见下方警告** |
| `TIMESTAMP_TZ` | 11 字节（同 TIMESTAMP）+ 时区偏移 | 存 **UTC 时刻**，原始时区另存 |
| `JSON` | 二进制 JSON 文档 | **数值必须精确保留**，不得经浮点中转 |
| `VECTOR` | 连续 FLOAT32 数组，小端，无头部 | 长度由列的 `dimension` 决定 |
| `ASSET_REF` | 16 字节（资产 ID） | 资产内容不在此 |

> **⚠ FLOAT 的排序陷阱**：IEEE 754 的字节表示**不保证与数值同序**——负数、±0、NaN 都会破坏"字节比较 = 值比较"。
>
> 若 `FLOAT32`/`FLOAT64` 列需要 **B+Tree 范围索引**，必须做**保序变换**（典型做法：正数翻转符号位、负数全部取反），否则索引范围扫描会返回错误结果。
>
> **待冻结**：是否对浮点列做保序变换，或禁止对浮点列建范围索引。

> **本库没有库内 LOB 类型。** 大对象（模型、文档、图片）走 `ASSET_REF` 引用的
> **受管理外部文件**，其内容**不进库、不进 redo**（`design.md`、REQ-AST-001）。
> 因此"长文本"在本库里只是**普通的变长字符值**——没有 LOB 那套定位器、
> 行内/行外双态与分段读写接口。超长时按 §6.3 的行片段链跨页，见 §6.8。

### 6.7 列在行内的布局

```text
行头
  ↓
NULL 位图（每列 1 位）
  ↓
var_offsets（2 字节 × 变长列数）
  ↓
定长列（按声明顺序，紧密排列，无对齐填充）
  ↓
变长列（按声明顺序，紧密排列）
```

**定长列在前、变长列在后**——定长部分可按下标直接算出偏移，变长部分查 `var_offsets`。

**不做字节对齐填充**：省空间优先；跨平台的非对齐访问由读取代码显式按字节组装处理（与 `REQ-PRT-003`「架构相关代码不得依赖单一架构」一致）。

**NULL 的三种语义在存储层的区分**（`REQ-CFG-002`）：

| 语义 | 存储表示 |
| --- | --- |
| **SQL NULL** | NULL 位图置位，**数据区不占空间** |
| **JSON null** | 在 JSON 文档内部（与 SQL NULL 不同表示） |
| **字段缺失** | JSON 文档中**不存在该键** |

三者不可压成一位——这是需求明确要求的区分，物理上必须能还原。

### 6.8 长文本：内联行片段链，不引入 TOAST

长文本（记忆内容、知识条目、文档片段）用 **§6.3 的跨页行（行片段链）内联存储**，
**不引入 TOAST 那套独立结构**。

#### 前提：本库没有库内 LOB，且超块行占比不高

**本库不支持库内 LOB 类型**——`design.md` 与 REQ-AST-001 已定：大对象（模型、文档、图片）
一律走 `ASSET_REF` 引用工作区内的**受管理外部文件**，只允许读取、范围读取与删除，
**不提供原地更新**。

这条决定在这里有一个重要后果：**大对象根本不进库、也就不进 redo**。
于是落在"行链 vs TOAST"这个决策上的，只剩**库内的长文本**——
记忆内容、知识条目、文档片段这类，通常是 **KB 到几十 KB 量级**。

**第二条量级判断**：**超出块大小的行，占比并不高**。
行链的代价（读取要沿链走、变长更新要重排后续片段）只在它**普遍**时才显著；
占比低时，代价可以忽略。

两条合起来：**行链是这里恰当的手段，不需要为它再引入一条独立的存储路径。**

#### 为什么可以不用 TOAST

TOAST 存在的理由是 **PG 的 redo 约束**，而那条约束在本库不成立。先把依赖链摆清楚：

```text
"一条逻辑修改 = 一条原子 redo 记录"
      ↓
该记录必须能装进一个日志文件
      ↓
所以单个值不能大于日志文件
      ↓
所以长文本必须外置（TOAST）
```

**第一环就只在部分场景成立。** 原子性需要一条边界来承载，而边界有两种：

| 操作类型 | 原子边界 | 是否需要"单条原子记录" |
| --- | --- | --- |
| **系统操作**（区分配、段头、位图） | **没有**——它不是事务 | **需要**——否则崩在中间会留下"位图说已分配、没有段认领"的页泄漏（§11.1.3） |
| **事务性的行修改** | **提交记录** | **不需要**——只要提交记录排在该事务全部修改记录之后，拆分仍是原子的 |

一次行修改跨越 N 个片段页时，拆分出的 N 条记录**由提交记录兜底**：

- 崩溃且事务未提交 → 逐片段回滚（undo 与数据修改**逐片段交错落盘**，§11.1.2）
- 崩溃且事务已提交 → 提交前全部记录必已落盘（WAL 规则 3），全部重放

**所以本库不需要 TOAST。** 记录大小由"**一页**"界定（§11.5.3），与文本长度无关。

#### 与 TOAST 的取舍对比

| | 内联行片段链（采用） | TOAST |
| --- | --- | --- |
| 额外结构 | **无**——复用 §6.3 | 每表一个溢出段 + 指针 + 块链 |
| 访问路径 | 沿片段链走，**同段、局部性好** | 主行 → 指针 → 跳转到独立段 |
| 更新代价 | 变长时重排后续片段 | 重建 chunk（碎片 + 回收压力） |
| 空间 | 除末片外每片满页 | chunk 固定大小，末块浪费 |
| 单值上限 | 由片段链长度上限定（§13 项 4） | 几乎无上限 |

**关键在于本库的画像**：长文本的主要宿主是**追加型表**（记忆、配置）——
**整体写入、整体读取、几乎不更新**。这恰好是：

- TOAST **收益最小**的场景（它的收益主要在"只访问大值的一部分"与"避免行膨胀拖累同行其他列"）
- 而它的开销（多一层间接、独立段的额外 I/O）**最明显**

所以在这个画像下，**内联更优**。

#### 代价与边界

- **读取会读到整个链**。我们的场景是"把记忆内容读出来喂给 LLM"，本就需要全部——
  不是问题。若将来出现"只取前 N 字节"的高频需求，再评估。
- **行片段链长度上限由此变得关键**：它现在直接决定**单个值的大小上限**。
  待冻结项 4 的定位从"兜底约束"升为"值的硬上限"。
- **空间**：除末片外每片都是满页，浪费限于一片。

> 记录一下**刻意放弃**的东西：没有"大值随机访问"，也没有"外置以避免行膨胀拖累同行其他列"。
> 换掉的是：**一个独立的段、一层指针间接、以及一套需要与主行保持同步的回收逻辑**。

## 7 ROWID 与工作区标识

### 7.1 ROWID

```text
ROWID = 48 位 = 6 字节
        file_id   10 位  → 1024 文件（表空间内相对编号）
        block_id  28 位  → 268,435,456 块 × 16KB = 4 TiB/文件
        row_id    10 位  → 1024 槽（与页内槽位上限耦合）
```

| 项 | 规定 |
| --- | --- |
| 容量 | 单文件 **4 TiB**；每表空间 1024 文件 = **4 PiB** |
| 代次 | **不含**（见 §6.4） |
| 作用域 | **表空间内相对地址**——不同工作区会出现相同 ROWID |
| 共享结构 | 缓冲池键、日志、诊断、审计**必须另带工作区标识** |
| 用户可见性 | **否**——不得作为对外持久引用或业务标识。理由**不是**行迁移（转发指针保证稳定），而是**槽位复用**（§6.4）：删除提交后槽位即可复用，旧 ROWID 会指向**另一个新行** |
| 行锁 | **用 ROWID 定位**——行迁移经转发指针保持稳定（§6.2），且锁的存续期内该行不会被删除并复用（删除同样要持锁） |

**`workspace_ref` 的语义是"数据血统根"，不是"工作区当前身份"**——克隆出的工作区（§2.7）
沿用源的 `workspace_ref`，因为它的数据确实源自同一血统。这个区分在引入克隆之前看不出来，
引入之后是必须的：它要回答的是"这页属于我正在打开的数据世系吗"。

### 7.2 页工作区标识 `workspace_ref`

```text
workspace_ref = H(workspace_id) 截断至 8 字节
```

**关键工程性质**：**哈希只在打开工作区时算一次并缓存，每页访问只是一次 8 字节整数比较**。热路径零额外开销。

**威胁模型（先划清边界，避免过度设计）**：

结构性防线在别处——进程 OS 隔离、路径检查、ID 不可猜测。在这三层之下，一个工作区的进程正常**根本打不开**另一个工作区的文件。因此 `workspace_ref` 实际防的是：

| 场景 | 现实性 |
| --- | --- |
| 隔离实现的 **bug**（路径检查被绕过、句柄绑定错误、缓存键复用错误） | **最现实，主要目标** |
| 运维/工具**误操作**（备份恢复错目录、文件搬错） | 现实 |
| **蓄意注入**（把 A 的页写进 B 的文件） | 需同时对两个工作区有文件写权限，OS 隔离下难达成 |

**明确不防**：进程被完全攻破、宿主机 root、备份介质持有者——这些属基础设施信任边界。

> **诚实定位**：`workspace_ref` 是**纵深防御与一致性检查**，**不是密码学边界**。它把"静默的跨区数据串读"降级为"可检出的错误"。**不应据此宣称隔离由它保证。**

**为什么不加密钥**：密钥放工作区自己的文件里，能写该文件的攻击者也能拿到，**不增加防线**；放实例级则需分发到每个进程（一个被攻破即全实例失效），且**恢复到另一实例时密钥变化会导致备份恢复失败**。与威胁模型不匹配。

**为什么是 8 字节而非 4**：4 字节在目标规模会碰撞（1 万工作区约 1.2%，100 万必然碰撞）。

## 9 索引的物理组织

### 9.1 B+Tree

- **三种页类型**：**索引叶页（2）/ 索引枝页（3）/ 索引根页（4）**——页体格式**分开定义**（§5.1）。
- 叶项 = `键 + ROWID(6B)`；枝/根项 = `分隔键 + 子页 ROWID(6B)`（宽度统一，`row_id` 部分置 0），另有**最左子指针**一字段。
- **叶/枝/根不再靠 `flags` 位区分**——它们已是各自的 `page_type`。
- **索引页与数据页共享页头与页尾机制，但页体不同**（§5.1）：索引页的条目必须**按键有序**，
  因此它用**有序条目数组**而非数据页那个**无序的槽位目录**；页尾也只剩叶页需要双链。
- **原地更新 ⇒ 索引项不因更新而变**：本模型是"更新不改 ROWID"的（§6.2，即 USTORE 式），
  所以行的更新**不触发索引维护**——只有当**键列本身**变化改到了索引项时才需要动索引。
  这正是我们不需要 Oracle 那种"索引项随行迁移而更新"、也不需要 PG 那种 HOT 的原因。
- 并发分裂须先形成书面协议再实现；分裂是**系统操作**，需独立恢复协议。

#### 9.1.1 叶页链表：双向

叶页通过 `link_prev` / `link_next` 连成**双向链表**。字段位于**页尾区**（§5.8），
**只有索引叶页付这 12 字节**——分支页、数据页、邻接页、ANN 页的页尾区都只有 4 字节校验。

**为什么双链**：成熟产品的索引叶块即为双向链表，它支持升序与降序两个方向。**"取最近 N 条"是 Agent 场景的高频模式**（最近的会话轮次、最近的记忆），且 SQL 子集含 `ORDER BY`——反向扫描不是边角需求。

**并发分裂时的链维护**：分裂 P 为 P 与 P′ 时，

```text
P.link_next  = P′      ← 碰 P
P′.link_next = Q       ← 碰 P′
P′.link_prev = P       ← 碰 P′
Q.link_prev  = P′      ← ★ 碰第三页 Q
```

只有 `Q.link_prev` 需要碰第三页——这正是单链不需要而双链需要的。

**采用急切更新**（非懒惰修复）：取 Q 的 latch **不会死锁**——分裂一律从左向右推进，锁序单调。多写者低争用下分裂罕见，多取一个 latch 代价很小；而**读路径应保持简单**，不应用懒惰修复给它加逻辑。

#### 9.1.2 空叶页必须仍可在搜索树中定位

索引项随删除事务移除，因此**叶页可能被删空**。

**要求**：空叶页**不得**从搜索树中失联——它仍须能被父页的路由键找到。否则搜索树断裂，导致查不到本应存在的键。

具体实现方式（保留占位项 / 父页保留路由键 / 延迟回收空页）待索引页规格定案，**但"空叶页可定位"这条不变量必须满足**。

#### 9.1.3 索引页的页体：与 Oracle `kdxco` 逐字段对照

Oracle 的索引块有一个专用头 `kdxco`（16 字节），外加叶块专有的 `kdxle`、分支块专有的 `kdxbr`。
逐字段对照后，**绝大多数都不需要——通用页格式已经覆盖了它们**：

| Oracle `kdxco`（公共索引块头） | 我们的对应 |
| --- | --- |
| `kdxcolev` 块层级（0 = 叶，> 0 = 分支，最大 24 层） | 页头 `flags` 的一位（§9.1）。**不需要层级值**——遍历只需区分叶/分支；"所有叶同层"是 B+Tree 的平衡不变量，交给检查器验证 |
| `kdxcolok` 持有块锁的事务 ITL | 页头 **ITL**（§5.4），同构 |
| `kdxcoopc` 服务事务操作码 | **不需要**——我们用 latch 串行化，不靠"操作码"描述在途操作 |
| `kdxconco` 键列数 | **不需要**——`ind$` / `icol$` 已有（字典表） |
| `kdxcosdc` 分裂/删除计数 | **不需要** |
| `kdxconro` 行索引中的行数 | 页头 **`slot_count`**，同构 |
| `kdxcofbo` / `kdxcofeo` 空闲空间起止 | 页头 **`free_end`**（`free_start` 可推导，§5.5） |
| `kdxcoavs` 可用**已提交**空间 | **不需要**——那是 Oracle 延迟块清除时代的产物；我们用 ITL 直接判可见性（§5.4） |

| Oracle `kdxle`（叶块专有） | 我们的对应 |
| --- | --- |
| `kdxlenxt` / `kdxleprv` 前后叶块 | **页尾 `link_next` / `link_prev`**（§9.1.1，各 6B） |
| `kdxlespl` 未锁定分裂空洞占用的空间 | 取决于分裂协议：我们选的是"**取 3 页 latch + 急切更新链**"（§9.1.1），空洞在 latch 内填完，**目前不需要**。若并发分裂协议最终定案为两阶段（L&Y 式半分裂），须重新评估 |
| `kdxlende` 已标记删除的行数 | **待页体规格定**——与删除策略绑定 |
| `kdxledsz` / `kdxlecol` 键数据字节数 / IOT 非键列数 | **不需要**——本库无 IOT |

**行格式**（对照 Oracle 的叶块行 `[flag][lock][key cols][rowid]`）：

| Oracle 叶块行 | 我们的对应 |
| --- | --- |
| `flag` 行标志 | 行头 **`row_flags`**（§6.1）——已删除 / 已迁移 / 跨页片段 / 含大字段 |
| `lock` 行锁字节（**指向 ITL 槽**） | 行头 **`itl_slot`**（§6.1） |
| `key cols` 键列 | 键（字节编码，见下） |
| `rowid` 6B | `ROWID` 6B |

> Oracle 把这四项都放在**索引行**里，我们把前两项放进**行头**（§6.1）——
> **这是同一个设计的两种落法**。重要的是那条链在数据行与索引行上**完全一致**：
> **行 → `itl_slot` → ITL → `undo_ptr` → undo 记录**（§4.6.2）。

**根页、分支页、叶页的结构不同**（与 Oracle 一致）：

| | 叶页 | 分支页 | 根页 |
| --- | --- | --- | --- |
| 层级 | 0 | > 0 | 同分支页 |
| 专有字段 | 无 | **最左子指针**（6B，对应 `kdxbrlmc`） | 同分支页 |
| **页尾前后指针** | **有**（12B） | **无** | **无** |
| 行内容 | `键 \| ROWID(6B)` | `分隔键 \| 子页 ROWID(6B)` | 同分支页 |
| 末行 | — | **终止标记**（对应 Oracle 的 `TERM`） | 同分支页 |

**根页与分支页结构相同**——它只是"树顶的那个分支块"（Oracle 亦然：根块就是一个
level = 树高的分支块）。**它的特殊之处在行为而非结构**：根页是所有查找的必经之路
（单点竞争），且**根分裂需要分配两个新块**（旧根降级为一个分支块，另起一个新根）——
比普通分裂多一步。这两点我们在 §9.1 的分裂协议里要单独处理。

**"最左子指针"为什么必要**：分支页的每个条目是「分隔键 → 右半边的子页」，
而**最左的那个子页没有左边界键**——它是整棵子树的最小侧。所以需要单独一个指针指向它。
这是 B+Tree 分支页的标准形态：**n 个条目对应 n+1 个子页**。

**末行终止标记**（对应 Oracle 的 `TERM`）：标出最后一个条目的位置，
使"第 n 个条目对应的子页"与"第 n+1 个"可区分。

**条目格式**：叶页 = `键 | ROWID(6B)`，分支页 = `分隔键 | 子页 ROWID(6B)`（`row_id` 置 0，宽度统一，§9.1）。

**一处刻意不做 Oracle 的区分**：Oracle 对非唯一索引把 ROWID 作为**额外一列**，对唯一索引把 ROWID 放进**行头**（`kdxledsz` 非零）。**我们统一把 ROWID 放在条目尾部**——我们的"行头"是通用槽位目录，为索引页引入行头扩展会破坏通用性，而收益只有几个字节。

**键比较就是字节比较**——这是 §6.0 三条编码原则在此处的回报：B+Tree 既不必解码键，也不必为每种类型写比较函数。

**分支键的前缀压缩**：Oracle 的分支块存"**足以在两个子树之间作出分支决定的最短键前缀**"，而非完整键。我们采用同样的思路，前缀长度的编码方式在页体规格（§13 待冻结项 8）中确定。

**空叶页可定位**（§9.1.2 的要求）：**定案采用 Oracle 的手段**——叶页的槽位 0 是**锚条目、永不回收**，即使它指向的行已被删除。父页的路由键因此始终有效。保留整条幽灵行还是只保留键，在页体规格中定。

### 9.2 图的边：按 `src` 聚簇

```text
出边：邻接页（page_type = 5），按 (src, edge_id) 聚簇，边数据内联
      → 一跳出边遍历 = 1 次范围读（度 10 的节点通常 1 页）

入边：覆盖索引 (dst) → (src, edge_id, label)
      → "谁指向我、是什么关系" 完全不用回表
```

**为何入边索引要覆盖**：基本形态下入边遍历是「1 次索引扫 + N 次按 (src, edge_id) 回查」，而这 N 次落**不同的 src** 上，大概率 N 次随机 I/O。多存一个 `label` 换掉这 N 次随机 I/O。

**代价**：插入边变为 B+Tree 插入（但图本就事务型，成本相当）；删除节点时入边需索引扫 + 逐个查找；边换端点等于删+增；高度数节点邻接区跨页时**优雅退化**，不做专项优化。

### 9.3 ANN 索引

- **必须磁盘型**（页类型 6），不能假设向量常驻内存。
- 参照 pgvector 的 HNSW 页布局（metapage / element tuple / neighbor tuple）。
- 是可重建的派生索引，以工作区 generation + 源提交水位 + 完整性清单控制激活。

#### 9.3.1 两种算法与选择

| | **HNSW**（主选） | **IVFFlat**（备选） |
| --- | --- | --- |
| 结构 | 多层图：上层稀疏（长跳）、下层密集（精确搜索），搜索复杂度 O(log N) | 倒排文件 + 量化（聚类中心 → 倒排桶） |
| 召回 / 速度 | 更高 | 构建更快、QPS 更高 |
| **空表建索引** | 可以 | **不可以**——必须先有数据才能聚类 |
| 构建内存 | **大**（pgvector 被诟病的主要一点） | 小 |

**HNSW 为主选**。IVFFlat 的"必须先有数据"这一限制，恰好与我们的**派生索引**定位相容
（本就可以延后构建），保留为低内存档的备选。

#### 9.3.2 pgvector 的三条已知问题，我们逐条必须处理

知识库里的实践反馈给出三条，**每一条都落在我们的画像是硬约束**：

**① HNSW 构建内存消耗大。** 基准机 32GB、向量数据可达 60GB（§1.3）——
**不可能要求全量驻留内存**。构建必须**分块进行**：分批插入、分批刷盘，
内存占用与"当前批次"成正比，而不是与总规模成正比。

**② 参数不能要求人工调。** pgvector"缺乏自动调优能力，需人工调整 `probes` / `ef_search` / `m` 等参数"。
本库面向 AI Agent 自用，**要求用户手工调 ANN 参数是不可接受的**——
`m` / `ef_construction` / `ef_search` 须由引擎按**维度、规模、目标召回**给出默认值。

**③ 构建可能失败或中断。** 这与我们"**可重建的派生索引**"的定位天然契合：
索引以 `(工作区 generation, 源提交水位, 完整性清单)` 控制激活，
**构建失败不是灾难**——重建即可，源数据与主路径不受影响。

#### 9.3.3 页面组织

参照 pgvector 的三段结构：

| 段 | 内容 |
| --- | --- |
| **metapage** | 入口元数据：层级、入口点、参数（`m` / `ef_construction`）、格式版本 |
| **element tuple** | 一个向量的数据 + **指向堆行的标识**（pgvector 存 `heap TID`；**我们存 `ROWID`**） |
| **neighbor tuple** | 一个节点的**邻接数组**（每层一组邻居 ID） |

三者都落在**页类型 6**（ANN 索引页）上，**共用同一个页头**（§5.1），
但**页体自行定义**——向量的定长、邻接数组的长度都由 `m` 与维度决定，
与堆表页"变长行 + 槽位目录"的组织方式无关。细部在页体规格（§13 待冻结项 8）中定。

**element tuple 存 ROWID 而非堆指针**：pgvector 存 `heap TID`（页号 + 行号），
我们存 6 字节 `ROWID`——同构，且行迁移经转发指针仍能定位（§6.2）。

> **pgvector 的两条已知缺陷，我们的定位天然规避**：
>
> ① 它**依赖 HOT 避免索引更新**，而 HOT 要求"不修改索引列且新旧元组同页"——
>    高频 UPDATE 下失效，导致索引膨胀、且 VACUUM 收不回。
>    **我们不做 MVCC**：行原地更新，向量变了就是**显式更新索引项**，不存在 HOT 依赖。
> ② 它会出现**索引退化**（更新累积导致召回下降，需外部监控）。
>    我们是**可重建的派生索引**（generation + 源提交水位 + 完整性清单）——
>    退化到阈值就重建，**"重建"在本设计里是常规动作，不是异常处理**。

**距离度量由索引的操作符类决定**（L2 / 余弦 / 内积），见 §10。

## 11 持久化与恢复

### 11.1 WAL 规则

1. 先写 Undo 与日志描述，再修改数据页。
2. 数据页持久化前，其 `page_lsn` 对应的日志**必须已持久化**。
3. **提交响应必须晚于提交日志的耐久确认**（可 group commit）。
4. Snapshot 用**提交序号**，WAL 用 **LSN**，**两者不得混用**（类型层面禁止）。

#### 11.1.1 提交流程与 ITL 更新

由于 ITL 条目承载 `commit_seq`，**提交时需要把提交序号写入该事务修改过的每个块的 ITL**。

**采用即时清除**（非延迟块清除）：

| | 即时清除（采用） | 延迟清除 |
| --- | --- | --- |
| 提交时 | 更新所有已修改块的 ITL | 只标事务表，等首个读者清理 |
| 读路径 | **简单**——ITL 里已有确定的提交序号 | 需在读取时顺便清理 |
| 提交代价 | 与修改块数成正比 | 常数 |
| 适用 | **短事务、写量小、触及块少** | 高并发扩展性 |

**选即时清除的理由**：短事务、低写并发、触及块少，即时更新代价很低；而**读是最该保护的路径**，不应用延迟清除给它增加复杂度。

提交时更新 ITL 只写内存页 + WAL 记录，**不需要等数据页落盘**，因此不拖慢 `fsync` 关键路径。

#### 11.1.2 Undo 自身必须受 redo 保护

**这是恢复正确性的前提，不是优化项。** 推理只有三步：

1. 事务修改一行时，前像被写入 **undo 页**——而这些 undo 页可能还在缓冲区里，崩溃时**与数据页一起丢**。
2. 恢复第三阶段（撤销）依据的正是 undo 里的前像——**undo 自身丢了，未提交事务就再也回滚不了**。
3. 所以 **redo 必须能重建 undo 页**：对 undo 页的修改**同样是 redo 记录**。

**"undo 必须先于数据页持久化"由日志顺序自动成立**——这条推论值得显式写出：

- 一次修改产生两次页修改：先"改 undo 页"（R1），后"改数据页"（R2），故 **`R1.LSN < R2.LSN`**。
- 日志**顺序落盘** ⇒ R2 落盘时 R1 必已落盘。
- 数据页刷盘前其 redo 必须已落盘（§11.1 规则 2）⇒ R2 已落盘 ⇒ R1 已落盘 ⇒ **undo 已持久**。

于是**不需要**为 write-ahead undo 单独设计机制——只要 undo 页的修改进入 redo，顺序就自动成立。
反过来说：**若 undo 不进 redo，这条保证就断了，且没有补救手段**。

**被排除的设计**：有一种做法是"undo 只存在 redo 里、不落 undo 页"，回滚时扫日志。
不采用——redo 组是**循环复用**的（§2.4），长事务的早期 undo 会在它自己的回滚完成之前就被覆盖；
而归档日志是离线恢复路径，不能用于在线回滚。

**无 undo 的表**：`logging = none` 的表不产生 undo（§2.2、§11.4），因此也不产生 undo 的 redo。
它们本就不参与回滚——这与它们"可丢失"的定位一致，不是遗漏。

#### 11.1.3 原子边界的两种载体

**原子性必须由某条边界承载**，而边界有两种，**分别适用于不同的操作**——这个区分是本节的重点：

| 操作类型 | 原子边界 | 记录是否必须单条原子 |
| --- | --- | --- |
| **系统操作**（区分配、段头、位图） | **没有**——它不是事务，无提交记录可依托 | **必须**——见下反例 |
| **事务性的行修改** | **提交记录** | **不必**——拆分仍是原子的，由提交记录兜底 |

**系统操作必须用单条多页记录。** 反例：区分配要同时改"位图页"与"段头页"，
若拆成两条、崩在中间，重放后位图说"这些页已分配给某段"、却没有任何段认领它们——
**页泄漏**，且恢复阶段无从判断该回滚哪一边。

**事务性的行修改则可以拆**——这带来两样东西：

1. **记录大小有界**：一次跨越 N 个片段页的长文本写入拆成 N 条记录，每条只描述一个页，
   内存与恢复开销都与"一页"成正比（§11.5.3）
2. **不必依赖行外存储**（§6.8）

原子性由提交记录保证：

- 崩溃且未提交 → **逐片段回滚**。这要求 undo 与该片段的数据修改**成对、按片段交错落盘**，
  即每个片段都是"先写 undo 的 redo，再写数据页的 redo"（§11.1.2 的 R1/R2）。
  于是任一时刻崩溃，已落盘的片段都恰好配着它自己的 undo。
- 崩溃且已提交 → 提交前全部记录必已落盘（WAL 规则 3），全部重放。

**R1 与 R2 不必合并成一条记录**（上一版这里建议过合并，现予修正）：
两者在同一个片段的边界内成对，R1 先于 R2 **由日志顺序自动保证**（§11.1.2），
不需要靠"同一条记录"来保证先后。拆开反而让粒度更细、记录更小。

### 11.2 缓存策略与恢复

**steal + no-force**，故恢复必须同时处理重做与撤销。三阶段：

1. **分析**：从最近检查点重建事务状态表与脏页表，确定重做起点。
2. **重做**：从重做起点重放；按 `page_lsn` 判定已包含的修改并跳过（**幂等**）。
3. **撤销**：对未完成事务反向应用 Undo，写补偿记录（**可重入**）。

#### 顺序不可颠倒：先重做，再撤销

**重做阶段必须重放全部修改——包括崩溃时尚未提交的事务。** 这不是疏忽，是唯一正确的做法：
**崩溃前的那一瞬间才是自洽的状态，也是 undo 链唯一完整的时刻。**

- 若重做时"跳过未提交事务的修改"：数据页停在半途，而 **undo 链本身也只写了一半**——
  撤销阶段要沿链反向走，链却是断的，**回滚无从下手**。
- 若先撤销再重做：撤销要读 undo 页，而 undo 页自己可能还没被重做出来。

Oracle 的表述可直接引用：

> **重做保护已提交的数据，撤销保护未提交的数据。**

未提交事务的修改必须由 redo 重建，正因为**重建之后才谈得上撤销**。这与 §11.1.2 是同一件事的两面：
undo 页要被 redo 重建，而重建后的 undo 页里**已提交与未提交事务的记录混在一起**——
在撤销完成前，两者本就无法区分，也无须区分。

**恢复完成后才是一致的**：重做只把工作区带回"崩溃前那一刻"（物理一致），
撤销才把它带回"只含已提交事务"（逻辑一致）。**少了任何一步都不算恢复完成。**

#### 一个可以缓一缓的优化：回滚不必挡在开放之前

Oracle 在 **Cache Recovery 完成后就打开数据库**，撤销由 SMON 在后台继续。
它之所以敢这么做，是因为一致性读机制天然处理"读到被未提交事务修改的行"——
读者按 ITL 发现事务仍在进行，就沿 undo 重建旧版本（§5.4、REQ-TXN-003）。

我们**具备同样的机制**，因此这条路是通的。但 **V1.0 先采用更简单的一种：撤销完成后再开放工作区**。

- **理由**：单工作区、写量小，崩溃时遗留的未提交事务规模有限，延时可接受。
- **代价的另一面**："打开后后台撤销"要求恢复与正常读写**并发**操作同一批 undo 页与事务表，
  测试面大得多。恢复路径本就最不能出错，不该在 V1.0 给它加并发。
- 若将来实测启动延时成为问题，再引入——**它不改动任何格式，只是调度问题**，属于纯增量。

### 11.3 控制文件更新时机

| 触发 | 更新哪个 |
| --- | --- |
| 日志切换 | **工作区控制文件**（redo 序列号、检查点） |
| 建/删工作区、新增数据文件 | **全局控制文件** + 工作区控制文件 |

### 11.4 按表类型的持久化差异

| 表类型 | 崩溃后的保证 |
| --- | --- |
| `logging = full` | 已确认提交必存；未提交不可见 |
| `logging = redo_only` | 同上，但**无回滚能力**（表本身无多语句事务） |
| `logging = none` | **可丢最近写入、可出现撕裂页**（由校验和 + 页尾校验检出，该页数据丢弃） |

### 11.5 redo 的文件结构与记录格式

参考 PostgreSQL 的 WAL。它的记录布局是三段式：

```text
XLogRecord 固定头（24B）
  0..N 个 XLogRecordBlockHeader     ← 块引用
  XLogRecordDataHeader[Short|Long]
  block data                         ← 块数据
  main data                          ← 主数据
```

其中两条经验直接可用，两条我们做得更简，另有一条**必须靠行格式配合**。

#### 11.5.1 文件：线性记录流，没有内部页结构

**每个 redo 成员文件是线性写的**（从头写到尾，写满即切换）——环形语义由"2 组轮换"在文件之上提供（§2.4），文件本身是线性的。

**redo 文件由固定大小的页组成**（格式见 §5.11），页是 **redo log buffer 的管理单位**——
有页，日志缓冲区才能按页分配、按页回收、按页刷盘。**无页则缓冲区无单位。**

**与 PG 的区别不在"有没有页"，而在"允不允许记录跨页"**：

> PG 允许记录跨 WAL 页，靠新页头里的 `xlp_rem_len` 续接。**代价是 `WALInsertLockAcquireExclusive`：一次要拿下全部 8 把 WAL 插入锁。**

**我们不允许记录跨页**（§5.11）：一条记录放不下当前页的剩余空间时，页尾补零、从下一页开始。
于是 PG 那条跨页惩罚**根本不存在**，代价只是每页尾部几十字节的碎片。

**页头与记录头分工互补，不是替代**：

| | 回答的问题 |
| --- | --- |
| 页头（`校验`、`已用长度`） | **这一页有没有坏**；页内有效数据到哪为止 |
| 记录头（`tot_len`） | **页内怎么一步步走**下一条 |

**两条边界规则**：

> - **一条记录不得跨越页边界**——页内放不下就补零换页（§5.11）
> - **一条记录不得跨越文件边界**——文件尾空间不够则填充，从下一个文件开始

好处是每个 redo 文件可**独立校验**，恢复扫描不必跨文件拼接。

这条规则给 redo 组大小一个**独立的下限**：

> 组大小 ≥ 取整后的最大单条记录（**约 16.4KB**——记录大小以"页"为界，见 §11.5.3）

它与 §2.4 已有的下限"必须能容纳一个检查点周期"是**两条独立约束，取其大者**。

#### 11.5.2 记录：固定头 + 块段 + 可选主段

```text
┌ 记录头（24 字节，固定）
│   tot_len   4B   整条记录总长——恢复扫描据此跳过或分配
│   lsn       6B   本条记录的 LSN，同时是"应用后该页的 page_lsn"
│   txn_id    6B   产生者（0 = 系统操作）
│   op        1B   语义标签（§11.5.4）
│   flags     1B   bit0 = 存在主段
│   crc       4B   CRC32C，覆盖头（不含 crc）+ 块段 + 主段
│   reserved  2B   对齐至 24B
├ 块段（页修改类记录使用）
│   blk_cnt   1B
│   块引用[]：flags 1B | rdba 5B | chg_cnt 2B
│   块数据[]：每项 offset 2B | len 2B | after_bytes
└ 主段（可选）：data_len 4B | payload
```

**与 PG 的四处差异，都是我们已有的东西换来的**：

| | PG | 我们 |
| --- | --- | --- |
| 块定位 | `RelFileLocator`（12B）+ `BlockNumber`（4B） | **`rdba` 5B**——ROWID 的 `file_id 10 + block_id 28` 本来就够用 |
| `xl_prev` 前向指针链 | 有（构成单向链表） | **省略**——① WAL 追加由 latch 串行化（写少、争用低），不需要用它做无锁追加；② **反向遍历不需要**（undo 有自己的链，§4.6.1）；③ 日志链的连续性由**日志序列号**判定，不靠每条记录的 prev |
| `xl_rmid` + `xl_info` | 资源管理器**决定重放函数** | **`op` 只是语义标签**，不决定 apply——apply 路径唯一（§11.5.4） |
| 主数据段 | 承载逻辑描述 | **仅用于非页修改类的记录**（检查点、日志切换等） |

**只存 after-image，不存 before-image**——前像在 undo 里（§11.1.2）。redo 是"再应用一次"，不需要前像。

**`crc` 在头里却覆盖后面的数据**（PG 亦然），意味着写记录要**两趟**：先拼内容、再补算 CRC。我们在**内存里拼好整条记录后一次落盘**——记录大小有界（§11.5.3），所以内存开销可控。

#### 11.5.3 长文本：按页拆分记录，不需要行外存储

本系统有**长文本**（记忆内容、知识条目、文档片段）。真正的大对象走
`ASSET_REF` 外部文件、不进 redo（§6.8），所以这里讨论的是库内的长文本。
但它**不需要 TOAST**——推导见 §6.8，结论如下：

**长度不构成约束，因为"一条逻辑修改 = 一条 redo 记录"并不是必须的。**
一次跨越 N 个片段页的长文本写入拆成 N 条记录，每条只描述一个页：

- **记录大小有界**（≈ 一页 + 24B 头），**与文本长度无关**
- **内存有界**——不必为一条记录分配与文本等长的缓冲区
- **原子性由提交记录兜底**（§11.1.3）

于是组大小下限与最大文本长度**确实是解耦的**——但解耦的机制不是"把文本挪走"，
而是"**把记录拆开**"。

**唯一需要单条原子记录的是系统操作**（区分配等，没有提交边界）。它们本来就只涉及几页，
不构成压力。

> **由此得到一条更一般的规则**：**redo 记录的大小以"页"为界，不以"逻辑操作"为界。**
> 逻辑操作的原子性由**提交记录**（事务性）或**单条记录**（系统性）承载，
> 与记录的物理大小无关。

#### 11.5.4 记录类型与 torn page 防护

`op` 沿用先前讨论的取值（**不参与 apply**，只用于诊断、统计与组提交识别）：

```text
0x01 日志切换 / 文件头       0x10 页修改（通用）
0x02 检查点                  0x30 提交
0x31 回滚完成
```

**apply 路径唯一**：无论 `op` 是什么，页修改一律按"块引用定位 → 页内字节写入"应用，幂等性由 `page_lsn` 统一判定。这是自觉的取舍——放弃 PG 那种"每个资源管理器一个 `rm_redo` 函数"的表达力，换取**恢复路径只有一条**。恢复恰恰是最不能出错、又最难在日常被覆盖到的路径。

**不做整页镜像，也不做双写区——torn page 防护交给文件系统**

与 PG 默认不同，我们**不采用 full page write**；也不采用 MySQL / openGauss 的**双写区**。
两者都是"在数据库内部再造一份页副本"来对抗部分写，而本库的定位是**尽可能轻量、快速**——
FPW 让检查点后的 WAL 写入量翻倍（PG 自己的话），双写区则要多一条独立的写路径与一个独立的恢复分支。

**这不是省掉一层保护，而是换一个更上游的保证**，而且 **PG 官方文档明确认可这种换法**：

> 如果有减小部分页面写入风险的硬件支持（比如电池供电的磁盘控制器）或者**文件系统支持**
> （比如 ReiserFS 4），并且他们可以把风险降低到一个可以接受的低范畴，那么可以关闭这个选项。
>
> **使用 COW 文件系统（如 ZFS）可关闭 FPW，因为不存在 partial write。**

在 COW 文件系统（ZFS、btrfs）上，一次 16KB 的覆盖写等价于**换指针**——旧数据块原地不动，
**"半新半旧的页"根本不会出现**。FPW 要防的那件事不发生，自然也就不需要防它的机制。

> **这是一项取舍，不是门禁**——为什么它可以被接受，以及各文件系统的能力档位，见 §11.6。

**部署在 XFS 或 ext4 上时它不成立，而这是显式接受的代价**：这两者的文件系统日志只保护**元数据**，
不保护文件数据，一次 16KB 的 `pwrite` 在掉电时仍可能只落一部分。此时 torn page **无法由 WAL 修复**——
我们的 redo 是**物理增量**（offset + bytes），它能重放"改了什么"，**无法重建"一个完整的页"**。
各文件系统的能力档位与接受理由见 §11.6。

**保留的唯一底线是页校验和**：它能**检出**撕裂页，检出后**按损坏处理**（报错、告警、从备份恢复），
而不是静默返回错误数据。PG 对它的定位说得很准：

> **block checksum 可辅助检测不一致块，但无法替代 FPW。**

**四种手段的对照**（同一个目标）：PG 全页写 / MySQL 与 openGauss 双写区 / Oracle 校验和 /
**我们——把原子性推给存储层**。前三种都在数据库内部解决；我们取第四种，代价是**原子性取决于部署在哪个文件系统上**
（§11.6）。正因为它是条件而非默认，工具必须**如实报告档位**，而不是让人以为有保障。

**格式上不为此预留专门字段**：块引用头的 `flags` 尚有未用位，若将来确实要在非 COW 部署上补回 FPW，
加一个标志位即可——**不为不打算做的事增加结构**。



### 11.6 文件系统能力基线

本设计的**崩塌一致性**与**工作区克隆**分别建立在文件系统的两项能力上。
**这两项彼此独立**——一个文件系统可以满足其一而不满足其二。这是最容易出错的地方，
所以在此集中记录，§2.7 与 §11.5.4 均指向本节。

| 文件系统 | **原子页写** | **reflink** | 定位 |
| --- | --- | --- | --- |
| **btrfs** | ✅ | ✅ | **首选**——两项都满足 |
| **XFS**（`reflink=1`） | ❌ | ✅ | **次选**——克隆可用；撕裂页风险是**显式接受的取舍** |
| ZFS | ✅ | 视版本：自身有快照/克隆机制，OpenZFS 2.2 起提供 `FICLONE` | — |
| ext4 默认 | ❌ | ❌ | 可用，但无克隆 |

#### 两项能力分属两个设计决定

| | 被谁依赖 | 缺失时的后果 |
| --- | --- | --- |
| **原子页写** | §11.5.4"不做 FPW、也不做双写区"这个决定 | **接受**——撕裂页由页校验和**检出**，按损坏处理（报错、告警、从备份恢复），**不会静默返回错误数据** |
| **reflink** | §2.7 工作区的克隆与分支 | **功能不可用**——禁用克隆并明确报错，数据本身无损 |

#### `reflink` 不等于"原子页写"

**这是本表存在的理由。** XFS 的 `reflink` 只让**共享的 extent** 在被写时走 COW；
一旦某段变成**私有**，后续写就是**原地写**，与普通文件无异。
XFS 的文件系统日志只保护**元数据**、不保护文件数据。

> 于是有一个反直觉的组合：**XFS 满足 reflink 克隆，但不提供原子页写。**
> **不要从"XFS 支持 COW"推出"XFS 不会撕裂页"**——这两件事没有关系。

#### 为什么原子页写可以是取舍，而不是门禁

撕裂页是**掉电瞬间**的小概率事件，且**页校验和能检出**它。
检出后按损坏处理——失效模式是"**明确的错误**"，不是"错误的答案"。这个区别是它可被接受的原因。

PostgreSQL 对校验和与 FPW 的关系说得准：

> **block checksum 可辅助检测不一致块，但无法替代 FPW。**

因此**不把它作为启动门禁**：部署在 XFS 或 ext4 上允许启动。
但**工具必须能报告**当前文件系统提供了哪些能力——**不得让人误以为有保障**。

> 平台侧的部署建议见 [`platform-support.md`](../../docs/platform-support.md)。

### 11.7 检查点与后台写

检查点是**缓冲池的机制**（§5.10）——它的全部材料都在内存里，落到磁盘上的只有它的**结论**。

#### 两个角色，两件事

| 角色 | 做什么 | **不做什么** |
| --- | --- | --- |
| **写线程**（DBWR 角色） | 把脏缓冲**写回文件** | 不动控制文件 |
| **检查点**（CKPT 角色） | 把**检查点位置**写进控制文件 | **不写数据块** |

Oracle 把它拆成两个进程，理由是并行化。**我们在职责上分开**——因为它们出错时的表现完全不同：
写块失败是 I/O 问题，写检查点位置失败是元数据问题。

**层次是实例级**：两个角色都服务该实例下的**所有工作区**，不按工作区各建一套。
**写线程可以有多个**（Oracle 的 `DB_WRITER_PROCESSES`），但那是**并行手段**，
不是"每个工作区一个"——见下"多个写线程：按工作集绑定"。

> 知识库原文的分工表述可直接引用：**"块写入工作由 DBWR 完成，CKPT 不直接写数据块。"**
> 历史上这项工作曾由 LGWR 兼任，后来才分离出来。

#### 检查点队列就是 §5.10 的脏链

脏缓冲按**首次变脏的 LSN 升序**挂在脏链上，写线程从**最老的一头**开始写。

**脏链是每工作区一条**（§5.10）：LSN 跨工作区不可比，且低水位本就是每工作区一个。
一个工作区的脏页积压**不得阻塞**另一个工作区的检查点推进——这是故障域隔离的基础。

- 写掉最老的那个 → **低水位前移**
- **低水位 LSN = 恢复起点**——该 LSN 之前的修改**已全部落盘**

**写必须按顺序**（知识库原文："由于 CHECKPOINT QUEUE 按 LOW RBA 排序，
DBWR 在处理 CHECKPOINT 批时必须按 RBA 顺序写脏块"），否则低水位推不动。

#### 用增量检查点，不做"停下刷全部"

| | 完全检查点 | **增量检查点**（采用） |
| --- | --- | --- |
| 动作 | 写出**所有**脏缓冲 | 按序持续写，检查点位置**平滑前进** |
| I/O | **尖峰** | 平稳 |
| 用于 | **关闭工作区**、克隆前（§2.7） | **运行期常态** |

Oracle 的增量检查点是 8i 引入的，CKPT **默认每 3 秒**更新一次检查点位置。
我们采用同样的形态：**周期性地把低水位写进控制文件**。

> 这也不在提交关键路径上（§2.6）——控制文件由检查点周期性地写，不频繁。

#### 脏链的数量 = 已打开的工作区数

脏链**按工作区组织——有多少（已打开的）工作区，就有多少条**。
未打开的工作区没有缓冲块，也就没有链。这正是"按需打开"（§11.8）自然带来的：
链的数量随**活跃**工作区伸缩，不随工作区总数增长。

#### 多个写线程：按工作集绑定

写线程**可以有多个**。但知识库给出的三条约束决定了它该怎么接：

> **DBWR 进程数不能超过工作集数；工作集在系统启动时分配给 DBWR；
> DBWR 总是只写入分配给自己工作集的缓冲区。**

我们照此：

| 规则 | 说明 |
| --- | --- |
| 写线程数 **≤ 工作集数** | 多出来的线程无处可管——知识库明说"额外的 DBWR 进程闲置或随机抢工作集，**反而增加管理复杂度**" |
| 工作集在启动时**静态分配**给写线程，之后不变 | 无动态迁移、无跨线程协调 |
| 每个写线程**只写自己工作集里的脏块** | |

**于是"哪个工作区由谁写"是静态确定的**——两步映射在启动时全部定死：

```text
工作区 ──(H(workspace_ref) mod N)──▶ 工作集 ──(启动时分配)──▶ 写线程
```

**一个工作区的检查点推进因此只涉及一个写线程，没有跨线程协调。**
这是"按工作区划分工作集"（§5.10）买到的最主要一笔。

知识库也点明了配置失衡的两头：

| 失衡 | 后果 |
| --- | --- |
| 写线程 **多于**工作集 | 多余线程闲置或抢工作集，**只增加复杂度** |
| 写线程 **少于**工作集 | 部分工作集没有专属写线程，脏缓冲积累，**触发 free buffer waits** |

#### 一个写线程内部的紧迫度调度

多线程**并不取消**调度问题，只是把它的作用域**缩小**：从"全实例 N 条脏链"缩到
"一个写线程所辖的若干工作集、若干条脏链"。

调度仍然必要。否则它辖区内的某些工作区低水位会长期推不动——
表现为**该工作区在日志切换时被迫等待**。症状与"redo 组太小"相同，但成因是**调度**而非容量，
两者处置完全不同，不能混为一谈。

**紧迫度由工作区自己的 redo 余量决定**：

> 该工作区距离"下一组 redo 被覆盖"还剩多少日志空间，就是它的紧迫度。

这个量有两个好处：**每工作区可算**，而且**天然可比**——虽然 LSN 跨工作区不可比（§5.10），
但"剩余日志字节数"是各工作区自己的标量，可以直接比较。

于是调度规则：

> **优先服务"最接近 redo 耗尽"的工作区**；紧迫度相当时轮转，保证没有工作区被饿死。

这比单纯轮转更贴合目标——**检查点推进的目的本就是让日志可被覆盖**，
"谁快没日志空间了"是最直接的信号。

> **它与"公平"是两件事**：这里的调度目标是**正确性**（不让某个工作区的日志链断裂），
> 属硬约束；而资源公平是**性能**目标，由配额与优先级承担（见 §1.3）。

#### 检查点位置：每工作区一个，只写一处

**检查点是每工作区独立的**——每个工作区有自己的 redo、自己的低水位、自己的控制文件。
CKPT 分别为每个工作区发布检查点位置，写进**该工作区自己的控制文件**。

Oracle 写**两处**：所有**数据文件头** + **控制文件**。
**我们只写控制文件。**

> **理由**：Oracle 写数据文件头，是为了让"数据文件 + 控制文件副本"能独立恢复。
> 而我们的数据文件本来就**不承载恢复点**——控制文件是唯一恢复锚点（§2.3），
> 同时每个文件的**页分配位图**已在文件头（§3.2），文件仍是自描述的。
> 少写一处，就少一个可能与控制文件不一致的地方。

#### redo 组大小的下限由此得出

这正是 §2.4 与 §11.5.1 反复引用、却一直没算出来的那个数。

**约束**：redo 只有 2 组轮换。一个组要被**再次使用**时，它上面的日志所对应的修改
**必须已经全部落盘**（检查点已推进过它）。否则那些日志一旦被覆盖，
恢复就再也无法从检查点走到日志末尾——**日志链断裂**。

```text
组大小 ≥ 一个检查点周期内产生的日志量
     ⟺  检查点推进速度 ≥ 日志产生速度（稳态要求）
```

**若跟不上**：日志切换被迫等待检查点推进——表现为**写的延迟尖峰**。这是"组太小"的症状。

**另一头的约束**：恢复重放量 ≤ 2 组（最多有两组的日志还在）。所以——

> **组大小 ↔ 恢复时间**直接挂钩：**组越大，恢复越慢**。

两条合起来定组大小：

| 方向 | 约束 |
| --- | --- |
| **下限** | 能容纳一个检查点周期——否则切换时等待 |
| **上限** | 恢复时间可接受——重放量 ≤ 2 × 组大小 |

小工作区配 256KB/组 ⇒ 恢复重放 ≤ 512KB，几乎瞬时。这正是 §2.4"组大小创建工作区时指定"的用意。

#### "检查点 LSN"的语义（再确认）

控制文件里的**检查点 LSN 就是低水位**——**该 LSN 之前的修改已全部落盘**，
而不是"最后一次检查点动作发生在哪"（§2.6 已记）。

实例恢复从它开始重放即可，它之前的日志可以丢弃。

### 11.8 工作区的独立恢复与故障隔离

**恢复的单位是工作区，不是实例。** 这不是额外设计出来的特性，而是三条既有决定的直接结果：

| 已有决定 | 带来的后果 |
| --- | --- |
| 每个工作区有**自己的控制文件**（恢复锚点，§2.3、§2.6） | 恢复起点、redo 序列、检查点位置**都是每工作区一份** |
| 每个工作区有**自己的 redo**（§2.4） | 重放范围**不跨工作区** |
| 每个工作区**自包含**（§12） | 一个工作区的文件损坏不影响另一个 |

于是：**打开某个工作区时，读它自己的控制文件，就能独立判断"我需不需要恢复"。**

#### 一个脏工作区不阻塞实例

实例启动只做一件事：打开**全局控制文件**、取出工作区清单（§2.6）。它**不逐个打开工作区**。

工作区**按需打开**——第一次被访问时才打开。于是：

- 实例启动时间与工作区数量、大小**无关**
- 某个工作区需要恢复（甚至恢复失败），**别的客户端只是在用别的工作区**，完全不受影响

> 若改成"启动时全部打开"，一个坏工作区就能拖住整个实例的可用性。
> **按需打开让故障域天然收敛在工作区之内。**

#### 打开失败时的三种处置

| 处置 | 语义 | 何时用 |
| --- | --- | --- |
| **正常打开** | 需要恢复则先完成恢复（§11.2 三阶段），再对外服务 | 常态 |
| **隔离** | 该工作区**不可访问**，其余一切照常；原因可经管理接口查询 | 打开失败的**默认**行为 |
| **强制打开** | 跳过恢复的部分检查，允许打开——**可能读到不一致的数据** | 抢救数据时的**显式**管理操作 |

**隔离是默认，"强制打开"必须显式调用**——因为它把一个**本可检测的失败**
换成了一个**静默的错误答案**。这与本设计在别处的一贯取舍一致：
**宁可失败得明确，不可成功得可疑。**

隔离一个工作区时，要把它在**共享缓冲池**里的缓冲块**移除**（脏块丢弃、不写回）——
既避免它的异常波及共享的 DBWR 线程，也避免它的页混进后续任何写回。
**丢弃是安全的**：WAL 保证磁盘状态随时可被重放修复（§11.1），下次正常打开时恢复即可。

#### 这与"共享缓冲池"不矛盾

一个自然的疑问：缓冲池与后台线程都是**实例级共享**的（§5.10、§11.7），
凭什么说故障是隔离的？

因为**共享的是资源，不是状态**：

| 共享 | **不**共享 |
| --- | --- |
| 缓冲池内存、DBWR / CKPT 线程、latch 基础设施 | **全部恢复状态**：检查点位置、低水位、脏链、redo 序列、事务表 |

共享只影响**性能**（一个工作区占用缓冲池会挤压别人），不影响**正确性**。
而性能挤压由配额与调度约束处理（资源预算，见 §1.3），**不是靠各建一套来隔离**——
那样既浪费内存，又让"实例级一套"的简化失效。

## 12 隔离的存储层保证

| 机制 | 说明 |
| --- | --- |
| 文件层 | 每工作区独立文件、不共享、无硬链接、不跨用户去重 |
| 页层 | `workspace_ref` 受校验标识，跨区误读可检出 |
| 缓存层 | 缓冲池键**必须含工作区标识**——不同工作区的 ROWID 会重复 |
| **public 只读** | **不得只靠文件只读性**——成熟产品的只读表空间**不阻止仅改数据字典的 DDL**。必须在**引擎层**拒绝写 public，配合授权层双重保证 |
| **故障隔离** | 恢复以**工作区**为单位——一个工作区需要恢复或打开失败，**不妨碍实例启动与其他工作区**。默认**隔离**，可显式**强制打开**（§11.8） |
