## 9 索引的物理组织

### 9.1 B+Tree（通用索引）

- **三种页类型**：**索引叶页（2）/ 索引枝页（3）/ 索引根页（4）**——页体格式**分开定义**（§5.1）。
- 叶项 = `键 + ROWID(6B)`；枝/根项 = `分隔键 + 子页 ROWID(6B)`（宽度统一，`row_id` 部分置 0），另有**最左子指针**一字段。
- **叶/枝/根不再靠 `flags` 位区分**——它们已是各自的 `page_type`。
- 支持唯一键、复合键、范围访问。
- **索引页与数据页共享页头与页尾机制，但页体不同**（§5.1）：索引页的条目必须**按键有序**，
  因此它用**有序条目数组**而非数据页那个**无序的槽位目录**；页尾也只剩叶页需要双链。
- **原地更新 ⇒ 索引项不因更新而变**：本模型是"更新不改 ROWID"的（§6.2，即 USTORE 式），
  所以行的更新**不触发索引维护**——只有当**键列本身**变化改到了索引项时才需要动索引。
  这正是我们不需要 Oracle 那种"索引项随行迁移而更新"、也不需要 PG 那种 HOT 的原因。
- 并发分裂采用 **B-link（Lehman-Yao）形态**：右链 + 高键，**父页下链允许滞后**——
  协议与恢复见 §9.1.4 / §9.1.5（证据包 `doc/evidence/btree-split-20261004/`）。
- 分裂是**系统操作**，需独立恢复协议（§9.1.5），不得当作业务事务失败忽略。

#### 9.1.1 叶页链表：双向（已确认）

叶页通过 `link_prev` / `link_next` 连成**双向链表**。字段位于**页尾区**（§5.8），
**只有索引叶页付这 12 字节**——分支页、数据页、邻接页、ANN 页的页尾区都只有 4 字节校验。

**为什么双链**：Oracle 的索引叶块即为双向链表，知识库原文称其"**是实现索引范围扫描最关键的技术**"，支持升序与降序两个方向。**"取最近 N 条"在 Agent 场景是高频模式**（最近的会话轮次、最近的记忆），且 SQL 子集含 `ORDER BY`——反向扫描不是边角需求。

**并发分裂时的链维护**：分裂 P 为 P 与 P′ 时，

```text
P.link_next  = P′      ← 碰 P
P′.link_next = Q       ← 碰 P′
P′.link_prev = P       ← 碰 P′
Q.link_prev  = P′      ← ★ 碰第三页 Q
```

只有 `Q.link_prev` 需要碰第三页——这正是单链不需要而双链需要的。

**采用急切更新**（非懒惰修复）：

| | 急切更新（采用） | 懒惰修复 |
| --- | --- | --- |
| 分裂开销 | 3 页、2 个 latch | 2 页 |
| 读者逻辑 | **简单——`link_prev` 永远正确** | 需检出并修正陈旧的 `link_prev` |

取 Q 的 latch **不会死锁**——分裂一律从左向右推进，锁序单调。我们是多写者低争用，分裂本身罕见，多取一个 latch 代价很小；而**读路径应保持简单**，不应用懒惰修复给它加逻辑。

#### 9.1.2 空叶页必须仍可在搜索树中定位

索引项随删除事务移除（REQ-STO-009），因此**叶页可能被删空**。

**要求**：空叶页**不得**从搜索树中失联——它仍须能被父页的路由键找到。

**定案：槽位 1 的高键条目（§9.1.4）——锚即高键，一个机制两件事。** Oracle 的做法（行索引第 1 项指向最后删除的行）只保住"路由能找到这页"，**不能纠正父页下链滞后时期的搜索**（进了左页、找不到、误判"不存在"）；高键条目让空页**可定位、且可继续右移**。父页路由键是**陈旧的最小键**——陈旧但合法，无需维护（§9.1.4）。

**空页的物理回收（从树中摘除）V1.0 不做**——空页留在树中，正确性无碍；PG 的两阶段 `half-dead` 回收（证据包 `btree-split-20261004` 条目 15）可作后续参照。

#### 9.1.3 索引页的页体：与 Oracle `kdxco` 逐字段对照

Oracle 的索引块有一个专用头 `kdxco`（16 字节），外加叶块专有的 `kdxle`、分支块专有的 `kdxbr`。
逐字段对照后，**绝大多数都不需要——通用页格式已经覆盖了它们**：

| Oracle `kdxco`（公共索引块头） | 我们的对应 |
| --- | --- |
| `kdxcolev` 块层级（0 = 叶，> 0 = 分支，最大 24 层） | 页头 `flags` 的一位（§9.1）。**不需要层级值**——遍历只需区分叶/分支；"所有叶同层"是 B+Tree 的平衡不变量，交给检查器验证 |
| `kdxcolok` 持有块锁的事务 ITL | 页头 **ITL**（§5.4），同构 |
| `kdxcoopc` 服务事务操作码 | **不需要**——我们用 latch 串行化，不靠"操作码"描述在途操作 |
| `kdxconco` 键列数 | **不需要**——`ind$` / `icol$` 已有（字典表） |
| `kdxcosdc` 分裂/删除计数 | **不需要** |
| `kdxconro` 行索引中的行数 | 页头 **`slot_count`**，同构 |
| `kdxcofbo` / `kdxcofeo` 空闲空间起止 | 页头 **`free_end`**（`free_start` 可推导，§5.5） |
| `kdxcoavs` 可用**已提交**空间 | **不需要**——那是 Oracle 延迟块清除时代的产物；我们用 ITL 直接判可见性（§5.4） |

| Oracle `kdxle`（叶块专有） | 我们的对应 |
| --- | --- |
| `kdxlenxt` / `kdxleprv` 前后叶块 | **页尾 `link_next` / `link_prev`**（§9.1.1，各 6B） |
| `kdxlespl` 未锁定分裂空洞占用的空间 | **不需要**——分裂定案为**单阶段**（§9.1.5）：页内（新页 + 链）在 latch 内一次完成，没有"空洞"窗口 |
| `kdxlende` 已标记删除的行数 | **不需要**——索引项随删除事务**直接移除**（§9.1.2），空间即时归还，无延迟清除记账 |
| `kdxledsz` / `kdxlecol` 键数据字节数 / IOT 非键列数 | **不需要**——本库无 IOT |

**行格式**（对照 Oracle 的叶块行 `[flag][lock][key cols][rowid]`）：

| Oracle 叶块行 | 我们的对应 |
| --- | --- |
| `flag` 行标志 | 行头 **`row_flags`**（§6.1）——已删除 / 已迁移 / 跨页片段 |
| `lock` 行锁字节（**指向 ITL 槽**） | 行头 **`itl_slot`**（§6.1） |
| `key cols` 键列 | 键（字节编码，见下） |
| `rowid` 6B | `ROWID` 6B |

> Oracle 把这四项都放在**索引行**里，我们把前两项放进**行头**（§6.1）——
> **这是同一个设计的两种落法**。重要的是那条链在数据行与索引行上**完全一致**：
> **行 → `itl_slot` → ITL → `undo_ptr` → undo 记录**（§4.6.2）。

**根页、分支页、叶页的结构不同**（与 Oracle 一致）：

| | 叶页 | 分支页 | 根页 |
| --- | --- | --- | --- |
| 层级（`kdxcolev` 对应） | 0 | > 0 | 同分支页 |
| 专有字段 | 无 | **最左子指针**（6B，对应 `kdxbrlmc`） | 同分支页 |
| **页尾前后指针** | **有**（12B） | **无** | **无** |
| 行内容 | `键 \| ROWID(6B)` | `区分前缀 \| 子页 ROWID(6B)` | 同分支页 |
| 末行 | — | **终止标记**（对应 Oracle 的 `TERM`） | 同分支页 |

**根页与分支页结构相同**——它只是"树顶的那个分支块"（Oracle 亦然：根块就是一个
level = 树高的分支块）。**它的特殊之处在行为而非结构**：根页是所有查找的必经之路
（单点竞争），且**根分裂需要分配两个新块**（旧根降级为一个分支块，另起一个新根）——
比普通分裂多一步。这两点我们在 §9.1 的分裂协议里要单独处理。

**"最左子指针"为什么必要**：分支页的每个条目是「分隔键 → 右半边的子页」，
而**最左的那个子页没有左边界键**——它是整棵子树的最小侧。所以需要单独一个指针指向它。
这是 B+Tree 分支页的标准形态：**n 个条目对应 n+1 个子页**。

**末行终止标记**（对应 Oracle 的 `TERM`）：标出最后一个条目的位置，
使"第 n 个条目对应的子页"与"第 n+1 个"可区分。

**条目格式**：叶页 = `键 | ROWID(6B)`，分支页 = `区分前缀 | 子页 ROWID(6B)`（即分隔键的**后缀截断**形式，§9.1.3 末；`row_id` 置 0，宽度统一，§9.1）。

**一处刻意不做 Oracle 的区分**：Oracle 对非唯一索引把 ROWID 作为**额外一列**，对唯一索引把 ROWID 放进**行头**（`kdxledsz` 非零）。**我们统一把 ROWID 放在条目尾部**——我们的"行头"是通用槽位目录，为索引页引入行头扩展会破坏通用性，而收益只有几个字节。

**键比较就是字节比较**——这是 §6.0 三条编码原则在此处的回报：B+Tree 既不必解码键，也不必为每种类型写比较函数。

**唯一索引与 NULL 键**：**键列全为 NULL 的行不登记索引条目**（唯一与非唯一同规，照 Oracle 语义）——
因此可空列上的唯一索引允许任意多行"全空"（`asset$` 的 `idempotency_key` 即其用例）；
**部分列为 NULL 的复合键照常登记**。

**分支键的区分前缀（后缀截断）**：Oracle 的分支块对键做**后缀截断（suffix truncation）**——只保留"足以在两个子树之间作出分支决定"的前缀；叶块的可选键压缩（`COMPRESS`）本库不做，叶条目存完整键（保持条目自包含、二分无跨条目依赖）。

**定案**：分支条目 = `key_len 2B | 区分前缀 | 子页 ROWID 6B`；前缀在**分裂时**生成——取分裂点两侧相邻键（左页最大、右页最小）的**最长公共前缀 + 1 字节**（取自右页最小键）。**比较仍是纯字节序**（前缀按"短字节串"比较即取舍判据），**无需新比较器**。两条不变量使前缀**永不需要维护**（删除、再分裂都不动它）：①前缀 ≤ 右子树一切现存键；②前缀 > 左子树一切现存键——其后的插入路由使然（`≥ 前缀` 的键只会进入右子树、`< 前缀` 的只会进入左子树），归纳成立（证明思路见证据包 `btree-split-20261004`）。**重复键跨分裂时前缀退化为完整键**。

**空叶页可定位**（§9.1.2 的要求）：**定案——槽位 1 = 高键条目**（§9.1.4）：它是锚（永不回收，空页可定位）、是上界（右移判据）、也是父页路由的依托。**幽灵行不需要保留**——父页路由键用"陈旧的最小键"即可（陈旧但合法，见 §9.1.4）。

#### 9.1.4 高键条目与右移（B-link 形态）

索引页的**槽位 1 恒为高键条目**——本页键的**上界**，也是 §9.1.2"空叶页可定位"的锚。
**为什么是"高键"而不是 Oracle 的"幽灵行"**：幽灵行只保住"路由能找到这页"，
**不能纠正"父页下链滞后"时期的搜索**——读者进了左页、按页内键找不到，会误判"不存在"；
高键则让读者**向右移动**继续找。**锚条目即高键条目——一个机制两件事。**

| 项 | 规则 |
| --- | --- |
| 语义 | 页内**一切有效条目 < 高键**（严格小于）。比较单位：**叶页 = 复合键 `(键, ROWID)`**（ROWID 恒唯一，重复键无歧义）；**枝/根页 = 键字节**（条目尾部的 ROWID 只是子页指针，不参与比较） |
| 编码 | 与同页有效条目**同构**；**最右页**以 `key_len = 0xFFFF` 表示**无上界（∞）**（保留值；合法键长 ≤ 4096） |
| 维护 | **只在建页与分裂时写入**；删除、插入都不动它。分裂 P → P′：**P′ 复制 P 的原高键**（含 ∞ 标记的移转），**P 改存新上界**（= P′ 的最小条目） |
| 查找 | 页内二分在**槽 2..n** 上进行（槽 1 不参与）；**右移**：`目标键 ≥ 本页高键` ⇒ 沿 `link_next` 右移重试 |
| 扫描 | 前进时**闩耦合**：持 P 闩读 `link_next` 得候选 Q、闩住 Q 后**校验 `Q.link_prev == P`**（§9.1.1 的急切双链使该校验恒可判）；不等 ⇒ 期间发生过分裂 ⇒ 重读 `P.link_next` 再前进。降序对称：闩住左邻 Q 后校验 `Q.link_next == P` |
| 终止 | 最右页（∞）右移终止；下行闩耦合**逐层释放父页**，导航栈只在回插时用于重找父页（不持旧闩） |

> 这条不变量是 **Lehman-Yao / B-link** 的正确性核心：**父页 downlink 可以滞后，
> 但"过期的页只可能偏左"**——向右移动必达目标页（证据包 `btree-split-20261004`）。

**父页路由键 = 子页的（陈旧的）最小键**——下行取"最后一个 `≤ 目标键` 的条目"。
它与高键**分工不同、互不替代**：父条目管**快路径**（一次到位），高键管**兜底**（滞后自愈）。
父条目**不因删除而更新**——"曾经的最小键"仍是合法下界；键域只会因分裂而收窄
（分裂时新条目取新右页的最小键）。

#### 9.1.5 并发分裂协议：单阶段 + 父层滞后容忍（已定案）

**并发形态照 PG 的 B-link（Lehman-Yao），骨架照 Oracle 的两式分裂与"叶分裂后分支更新、
根分裂单独处理"。定案：单阶段分裂**——页内（含新页与链）在 latch 内一次完成；
**不需要** Oracle `kdxlespl` 式的"未锁定分裂空洞"，也不做两阶段半分裂。

**分裂步骤**（P 满，需插入新条目）：

1. **下行闩耦合**：父页闩保持到子页闩到手，**读到子页即释放父页**（不持长路径）。
2. 到达叶 P：`新条目 ≥ P.高键` ⇒ **右移**（§9.1.4）后重试；否则取得 P 的排他闩。
3. **选分裂点**：新条目是页内**最大条目**（按复合键判序；即单调追加形态）
   ⇒ **99/1 分裂**——原页内容留守、新键独立成新页（**零搬移**）；否则 **50/50**
   （按字节对半）。依据 Oracle 两式分裂（证据包条目 17/18）。**本库序列 ID 索引
   全是单调追加**（`memory_id`、`edge_id`、`event_id`…），99/1 是**常态路径**而非优化项。
4. **建新页 P′**（**新页先建、旧页后改**）：从空间管理取页，写入：**复制 P 的原高键**
   （P 原为最右页时，∞ 标记随之移转——**最右身份跟着 ∞ 走**）、移入条目
   （99/1 时仅新条目）、`link_prev = P`；随后改 P：`高键 ← P′ 的最小条目`（P 不再是最右）、
   `link_next = P′`；**Q = P 的原 `link_next`** 已闩，改 `Q.link_prev = P′`（§9.1.1 三页四步）。
5. **记 WAL**：**分裂记录**——P′ 的**完整正文随记录**（redo 不依赖重放时读旧盘面，
   幂等可重放），同记录携带 P 与 Q 的变更；页级 LSN 守卫防重复重放。
6. 释放各页闩；**回插父层**：经导航栈**重找父页**（栈可能过期；不持旧闩，重下行校验），
   插入条目 `(P′ 的最小条目 → P′)`。父页有空位即完成；**父页满 ⇒ 按同一协议递归分裂父页**。
   **若在此步之前崩溃**：树处于**可自愈态**——搜索与插入经高键右移全部正确。
   这是 B-link 的**容忍态，不是损坏**。
7. **根分裂**（根无父）：页分裂照常完成后，**一条原子 WAL 记录**完成三件事——
   旧根**改类型 4 → 3**（根页与分支页结构相同，§9.1.3，只是类型字节变化）、
   **新根 N**（类型 4：`left_child = 旧根`、一条目 `(右半最小条目 → 右半)`）建立、
   **段头页树头** `root ← N` 更新。崩溃落在这条记录之前 ⇒ 旧根仍为根、树正确（同第 6 步）。
8. **树头（根页 ROWID）在段头页**（类型 7）的 B+Tree 类型扩展区（§5.11）——
   与 PG metapage 存根指针同形。**空索引**的初始根 = 一张**空叶页**（类型 2），
   首次分裂即走第 7 步。

**恢复协议**：分裂各步都有对应 WAL 记录（① 页分裂 ② 父插入 / ③ 根建立 + 树头）；
redo **只做幂等重放**。崩溃把步骤截断在任一处，恢复后树要么完整、要么处于可自愈态——
**唯一必须守住的不变量**：任何持久态都能被"高键 + 右链"完整搜索。
**检查器口径**（待冻结项 2d 清单⑥的范围）：以**叶链可达 + 键序单调**判索引完整性；
**父页下链缺失不报损坏**（容忍态）；"补插下链"**不作为恢复义务**——PG 明言 downlink
**可能滞后**、未承诺修复（证据包条目 1）；哈希索引的先例同样是"后续操作完成"（条目 12）。

**与 Oracle 的对照**：Oracle 以块级串行化**阻塞**其他操作完成分裂（`KDICBIN` 更新分支、
`KDICRSP` 初始化新根）；我们以"高键 + 右链"把窗口做成**容忍态**——读者最多沿链右移一步，
**不被分裂过程阻塞**。两式分裂、"叶分裂后分支更新、根分裂单独处理"的骨架照 Oracle；
并发形态照 PG。

#### 9.1.6 扫描方式族：唯一 / 范围 / 全扫描 / 快速全扫描（2026-10-05 补设计）

Oracle 的 B*Tree 有一族扫描方式，不是一个。我们按"**先范围、全扫描顺手、
快速全扫描延后**"的次序落地（Oracle 对照见证据包 `scan-mech-20261005`）：

| 方式 | 读什么 | 有序 | I/O 形态 | 回表 | 我们的取舍 |
| --- | --- | --- | --- | --- | --- |
| **唯一扫描** | 根 → 枝 → 叶，定位一条 | —（单条） | 单块读 | 需要则回表 | 范围扫描的退化形态，同一条码路 |
| **范围扫描** | 叶链上 `[低, 高]` 段 | ✅ 索引序 | **单块读**（沿链，非顺序——Oracle 同款，`246255`） | 需要（受**聚簇因子**影响） | **P4 落地**（叶双向链 + 闩耦合协议已设计，§9.1.1/§9.1.5） |
| **索引全扫描 IFS** | 沿叶链从最左叶走到最右叶（**全树按序**） | ✅ | 单块读 | 视需要 | **顺手实现**——就是"范围扫描 + 无谓词"，入口从最左叶起；用于 `ORDER BY` 免排序、小表全索引遍历 |
| **快速全扫描 FFS** | **所有块（枝/根/叶）**，仅用叶数据 | ❌ 不保序 | **多块读**（§5.12 区读；可并行） | 视需要 | **支持但延后**（统计/无条件聚合切片）。要点：**按物理区顺序读**，**不得沿 `link_next`**（那会退化为 IFS 且失去多块读）；块的合法性由页校验 + 块引用自证，不需要叶链协议 |
| 跳过扫描（skip scan） | — | — | — | — | **不做**（复合键前缀场景交给统计 + IFS/范围选择；SQL 子集简单） |

**IFS 与范围扫描共用一套并发协议**（叶链闩耦合，§9.1.5）——IFS 只是不设上界。
**FFS 不参与链协议**：它按区多块读，读到的是"某时刻的各页"; 页级校验自证，
条目损坏按损坏处理；不承诺快照一致性（统计类消费方接受这一点——Oracle 的
FFS 同样不沿链）。

> **顺序保证的差别要在执行器里显式化**：范围扫描/IFS 的产出是**有序流**，
> 可直接满足 `ORDER BY`（省一次排序）；FFS 的产出**无序**，只喂不接受顺序的
> 消费方（聚合/统计）。

**实现（P4 索引切片，2026-10-05）**：新 crate **`bicdb-index`**——页体读写
（`page::{Entry, IndexPage, IndexPageMut}`：正文头 + 有序目录（项 1 恒为高键）
+ 条目区自页尾向上 + 叶尾 12B 双链（页尾区 16B = 12B 链 + 4B 页尾副本））、树算法（`tree::Tree`：点查 / 插入
（99-1 单调追加为常态 + 50/50）/ 删除（空页留树）/ **范围扫描（闭区间，沿叶链）**
/ **IFS（无谓词全扫描）** / `validate` 结构自检）、页存取缝 `store::PageStore`
（执行器接段 + 缓冲池；测试用内存仓 `MemStore`）。树头由 `Tree` 显式携带
（执行器接入时读写段头扩展区），闩锁由接入方提供——单线程实现以"一次一个页"
的纪律串行化（§9.1.5）。`validate` 判据 = **链走到底（尽头必须是 ∞ 页）∧
与根下行清点相符**（链断/叶子失联直接现形）。两处实测坑记档：
① **P′ 必须继承 P 的后继**（三页协议的第三页；漏掉时 P′ 恒以 no_link 收尾、
叶链提前终止——**单调追加看不见**，P 恒最右，乱序插入才暴露）；
② `set_high_key` 把新高键追加在条目区顶部、旧高键字节留作死空间，分裂路径
**必须紧随 `compact`**——否则左半预算比 `adjust_split` 的估算少一份高键
（实测：607B 键、25 条左半恰好差 615B ⇒ NoSpace）。

**接入存储（2026-10-05，P4 索引切片之二）**：

- **树头**（§9.1.5 第 8 步）落段头页扩展区 6B：`segment::{read_tree_head,
  write_tree_head}`（类型 2 的扩展区；非 B+Tree 段与"指向别的文件"均明确拒绝）。
  **高度不存**——从根沿**最左子指针**下行到叶页（页类型自述层级），
  `Tree::open(store, file_id, root)` 即按此推高度。**根页 ROWID 随根分裂变化**：
  执行器在 `InsertOutcome.grew` 为真时重写树头（§9.1.5 第 7 步的"根建立 +
  树头"是那条原子记录的语义）。
- **池存取口**：`index::store::{IndexIo, PoolStore}`——`read` 经缓冲池
  （命中拷副本；未命中由池的定位器读盘），`write`/`allocate` 交给执行器的
  `IndexIo`（**写必须带 redo**：索引项不做独立撤销（§9.1.2），但索引页与数据页
  一样受 WAL 保护；**分裂记录的正文随记录**（第 5 步）⇒ 盘上不存在的新页也能被
  幂等重放重建）。一次一个页（§9.1.5）：池卫兵在每次 `read`/`write` 内取放，
  不跨调用持有。
- **端到端用例**（`crates/index/tests/segment.rs`）：真 `DataFile` + `SegType::BTree`
  段 + 真缓冲池——插入 300 键（跨多页分裂）→ 池内标脏 → 刷回 → **树头写回段头页**
  → 关池重开（新池从盘读）→ `Tree::open` 推高度、全部键可查、`validate` 通过、
  IFS 全扫描保序；redo 镜像断言（每次改页一条**完整正文**、页头自洽、
  重开后的只读路径零写）。

### 9.2 图的边（已确认：按 `src` 聚簇）

**一个图的对象构成**（`spec/GRP.md` §0.2）：顶点表（堆表）+ **出边段（邻接段）**
+ **出边入口索引** + **入边覆盖索引** + 顶点 id 唯一索引（+ 可选属性索引）。

```text
出边：邻接页（page_type = 5），按 (src, edge_id) 聚簇，边数据内联
      → 一跳出边遍历 = 1 次范围读（度 10 的节点通常 1 页）
      → 入口：出边入口索引（B+Tree，(src ROWID) → 首邻接页；链单向只前进）

入边：覆盖索引 (dst) → (src, edge_id, label)
      → "谁指向我、是什么关系" 完全不用回表
```

**为何入边索引要覆盖**：基本形态下入边遍历是「1 次索引扫 + N 次按 (src, edge_id) 回查」，而这 N 次落**不同的 src** 上，大概率 N 次随机 I/O。多存 `label` 换掉这 N 次随机 I/O。

**边标识只有一个 `edge_id`**（48 位序列——对外标识与聚簇键**合一**）见 §5.11 的邻接页一节与 `spec/GRP.md` §0.4：**序列单调 ⇒ 追加即有序、永不需要分裂协议** ✓。

**代价**：插入边变为 B+Tree 插入（但图本就事务型，成本相当）；删除节点时入边需索引扫 + 逐个查找；边换端点等于删+增（边通常不换端点，可接受）；高度数节点邻接区跨页时**优雅退化**，不做专项优化。

### 9.3 ANN 索引

- **必须磁盘型**（页类型 6），不能假设向量常驻内存。
- 参照 pgvector 的 HNSW 页布局（metapage / element tuple / neighbor tuple）。
- 是可重建的派生索引，以工作区 generation + 源提交水位 + 完整性清单控制激活。

#### 9.3.1 两种算法与选择

| | **HNSW**（主选） | **IVFFlat**（备选） |
| --- | --- | --- |
| 结构 | 多层图：上层稀疏（长跳）、下层密集（精确搜索），搜索复杂度 O(log N) | 倒排文件 + 量化（聚类中心 → 倒排桶） |
| 召回 / 速度 | 更高 | 构建更快、QPS 更高 |
| **空表建索引** | 可以 | **不可以**——必须先有数据才能聚类 |
| 构建内存 | **大**（pgvector 被诟病的主要一点） | 小 |

**HNSW 为主选**。IVFFlat 的"必须先有数据"这一限制，恰好与我们的**派生索引**定位相容
（本就可以延后构建），保留为低内存档的备选。

#### 9.3.2 pgvector 的三条已知问题，我们逐条必须处理

知识库里的实践反馈给出三条，**每一条都落在我们的画像是硬约束**：

**① HNSW 构建内存消耗大。** 基准机 32GB、向量数据可达 60GB（§1.3）——
**不可能要求全量驻留内存**。构建必须**分块进行**：分批插入、分批刷盘，
内存占用与"当前批次"成正比，而不是与总规模成正比。

**② 参数不能要求人工调。** pgvector"缺乏自动调优能力，需人工调整 `probes` / `ef_search` / `m` 等参数"。
本库面向 AI Agent 自用，**要求用户手工调 ANN 参数是不可接受的**——
`m` / `ef_construction` / `ef_search` 须由引擎按**维度、规模、目标召回**给出默认值。

**③ 构建可能失败或中断。** 这与我们"**可重建的派生索引**"的定位天然契合：
索引以 `(工作区 generation, 源提交水位, 完整性清单)` 控制激活，
**构建失败不是灾难**——重建即可，源数据与主路径不受影响。

#### 9.3.3 页面组织

参照 pgvector 的三段结构：

| 段 | 内容 |
| --- | --- |
| **metapage** | 入口元数据：层级、入口点、参数（`m` / `ef_construction`）、格式版本 |
| **element tuple** | 一个向量的数据 + **指向堆行的标识**（pgvector 存 `heap TID`；**我们存 `ROWID`**） |
| **neighbor tuple** | 一个节点的**邻接数组**（每层一组邻居 ID） |

**邻居不内联在 element 里，这是与 pgvector 的一处有意不同**：
它把邻居内联，于是"**一条记录必须放下一页**"直接限制了可索引的最大维度
（`vector` 的索引上限 2000，而存储上限 16000）。
**我们独立成槽**（§5.11 的 element / neighbor 用 `kind` 区分）——
于是**向量与邻居各自撑到自己的上限**，不必互相挤。
换算：element 可用约 16200B ⇒ **可索引维度上限约 4000 维**。
（详见 `spec/RET.md` 的「向量与 ANN」一节。）

三者都落在**页类型 6**（ANN 索引页）上，**共用同一个页头**（§5.1），
但**页体自行定义**——向量的定长、邻接数组的长度都由 `m` 与维度决定，
与堆表页"变长行 + 槽位目录"的组织方式无关。**页体细则已定案**（§5.11 的 ANN 小节：定长槽、`kind`、失效标记 `flags` / `version`）。

**element tuple 存 ROWID 而非堆指针**：pgvector 存 `heap TID`（页号 + 行号），
我们存 6 字节 `ROWID`——同构，且行迁移经转发指针仍能定位（§6.2）。

> **pgvector 的两条已知缺陷，我们的定位天然规避**：
>
> ① 它**依赖 HOT 避免索引更新**，而 HOT 要求"不修改索引列且新旧元组同页"——
>    高频 UPDATE 下失效，导致索引膨胀、且 VACUUM 收不回。
>    **我们不做 MVCC**：行原地更新，向量变了就是**显式更新索引项**，不存在 HOT 依赖。
> ② 它会出现**索引退化**（更新累积导致召回下降，需外部监控）。
>    我们是**可重建的派生索引**（generation + 源提交水位 + 完整性清单）——
>    退化到阈值就重建，**"重建"在本设计里是常规动作，不是异常处理**。

**失效、并发与修复——与 pgvector 的对照**（证据包 `ann-page-20261004`）：

| 事项 | pgvector | 我们 |
| --- | --- | --- |
| 源行删除 / 向量更新 | 新元素入图 + 旧元素待回收；VACUUM 三阶段（`RemoveHeapTids` → `RepairGraph` → `MarkDeleted`，MarkDeleted 清向量、断邻居、**递增 4 位版本号**） | **置失效标记 + 版本递增**（§5.11）；**不修图**——正确性由**回查**（`spec/RET.md` REQ-RET-023）保证，退化由**阈值重建**处理 |
| 修复 vs 重建的判据 | 删除 < 10% 用 VACUUM；> 20% 推荐 `REINDEX CONCURRENTLY` | **同判据参照**：失效比例到阈值即**重建**（§9.3.2 ③：重建是常规动作） |
| 并发 | `HNSW_UPDATE_LOCK`（**页 0**）协调插入与修复；`HNSW_SCAN_LOCK`（**页 1**）协调扫描与删除 | **不设全图锁**——页级 latch 照通用规则；跨页的图级不一致**可容忍**（回查过滤 + 完整性清单兜底） |
| 扫描的缓冲策略 | VACUUM 扫描用 `BAS_BULKREAD`，不污染缓冲池 | 无对应——我们没有共享缓冲池置换策略，扫描走常规页读取 |

**WAL 立场**：ANN 页受 WAL 保护（防半页写与链断裂），但**图级一致性不依赖 redo 的原子边界**——崩溃后由 `(generation, 源提交水位, 完整性清单)` 判定"可用 / 重建"（§9.3 的定位）。

**距离度量由索引的操作符类决定**（L2 / 余弦 / 内积），见 §10。

### 9.4 回表与批量：表访问 by ROWID（2026-10-05 补设计）

**rowid 自带定位**：叶项里的 6B ROWID = `file_id + block_id + slot`（与 Oracle
受限 rowid 的 "DBA + 槽号" 同构，证据 `1995236`）。于是回表的第一步不是逐条读，
而是**收集 + 排序**：

```text
索引扫描产出 ROWID 流
  → 攒批（默认 256 条或一个区的行数，两者取小）
  → 按 (file_id, block_id, slot) 排序     ← sort_rowids
  → 按块分组 → 每块一次区读/查池（§5.12）→ 一次 CR 块重建 → 逐行提取
```

**为什么我们的批量收益比 Oracle 更大**：Oracle 对每行做一次 buffer get（回表
成本按块记账，证据 `228665`）；我们的 **CR 是块级重建**（§12.3：一次沿链回放
把整块还原到快照版本）——同块的 N 行**共享同一次重建**，行提取只是页内读。
排序后同块相邻，**CR 只做一次/块**（未排序时最坏退化为"每行一次重建"）。

| 要点 | 设计 |
| --- | --- |
| 排序键 | `(file_id, block_id, slot)`——三级全序，稳定 |
| 攒批大小 | 256 条或一个区的行数取小（控制内存：每批只持 ROWID，不持页） |
| 快照一致性 | 批量**不改变语义**：CR 快照在整个扫描期固定（§12.1），批内批间一致 |
| 覆盖索引 | 查询只碰索引列 ⇒ **不回表**（证据 `1054817`）；执行器标记 index-only，省掉整个 9.4 路径 |
| 聚簇因子 | **统计量**：排序后"相邻 ROWID 同块"的比例（= 索引键序与块序的贴合度）。只影响**需回表**的范围扫描/IFS（证据 `2065847`）；优化器用它估 I/O、在"全表扫描 vs 索引回表"间选择。落统计切片（P5） |

**实现（本切片）**：`storage::scan::{sort_rowids, fetch_rows}`——`fetch_rows`
对分组后的 `(Rdba, 行号)` 逐块：查池/区读 → `cr::reconstruct` → `heap::row`
提取，返回**与请求同序**的结果（`Option`：行不存在/不可见为 `None`）。
