## 11 持久化与恢复

### 11.1 WAL 规则

1. 先写 Undo 与日志描述，再修改数据页。
2. 数据页持久化前，其 `page_lsn` 对应的日志**必须已持久化**。
3. **提交响应必须晚于提交日志的耐久确认**（可 group commit）。
4. Snapshot 用**提交序号**，WAL 用 **LSN**，**两者不得混用**（类型层面禁止）。

#### 11.1.1 提交流程与 ITL 更新

ITL 条目承载 `commit_seq`，所以提交与 ITL 更新之间必须有个安排。
**采用延迟块清除，且必须是"延迟日志"那一版。**

#### 两个版本，差别是决定性的

| | 标准延迟块清除 | **延迟日志块清除（快速提交）** |
| --- | --- | --- |
| 提交时 | **完全不碰数据块** | 对**仍在缓冲池中的**块更新 ITL |
| ITL 变成什么 | 仍是"活动"假象 | 已提交，但序号是**上界近似值** |
| **谁来清除** | **`SELECT` 也会清除** | **只有 DML 才进一步清除** |
| 清除时生成 redo | 是 | **否**（可重导，故不必） |
| 清除时生成 undo | **从不**——清除失败没有代价，再做一次即可 | 同 |

**必须取后者，理由只有一条：标准版的 `SELECT` 会写块**，
而本设计已定"**读路径不得产生同步写**"。
取延迟日志版，**读路径永不写块**——这不是优化，是那条原则的硬要求。

#### 我们的提交：次序

```text
① 分配本次提交序号；写提交记录**进日志流**
② 更新事务表槽：标记已提交，写入该提交序号       ← 这一刻起"已提交"对外成立
③ 释放锁、唤醒等待者——释放与 ② 是同一个动作，③ 单独要做的只有**唤醒**
④ 等日志刷盘，然后回应客户端（提交响应晚于耐久确认）
      ——以上是"提交"；以下是"清理"，与次序无关、可随时进行：
⑤ 遍历"本次事务改过的块"清单（内存）
     块仍在缓冲池     →  把 commit_seq 写进它的 ITL，**不生成 redo**
     块已不在缓冲池   →  忽略——留给延迟清除，由**首次 DML** 完成
     块已被别的事务改过 →  忽略，同上
```

**①②③ 的次序不是随意的** ✗✓：

| 次序 | 为什么 |
| --- | --- |
| **① 先于 ②** | "已提交"一旦可见（②），别人就可能**基于它继续写入并提交**。若它的提交记录尚未进入日志流而系统崩溃，前滚的重放里没有它，后续事务的提交却可能已落盘——**依赖链断裂** ✗。**入流先于可见**，链条才闭合 |
| **② 先于 ③** | 等待者醒来第一件事就是读槽判"已提交"——唤醒若早于标记，它会重新睡回等待（但锁已放，等一个不会再来的释放）✗ |
| **④ 可以最后** | 日志是**单一顺序流**：后一条记录刷盘必然覆盖前一条。**等待者在 ③ 之后就已继续**——这正是组提交的收益 ✓ |

**崩溃在 ① 与 ② 之间**：提交记录已在日志流 ⇒ 恢复判其为**已提交**并补标记——**没有"半个提交"** ✓。

**第 ⑤ 步为什么不生成 redo**：清除是**可重导的**——它只是把提交记录里已确定的
`commit_seq` 抄进 ITL。崩溃后重做时，这个块要么被重放、要么其 ITL 仍是"活动"，
两种情况都能靠**日志中的提交记录**补上。**可重导的幂等动作不需要自己的日志。**

**第 ⑤ 步不生成 undo**：清除失败没有代价——再做一次即可。
**这是一条有用的豁免**：清除不是数据修改，回滚不需要撤销它。

**清单可以是有界的**——溢出的部分**直接从清单里丢掉**，让那些块走标准延迟清除即可。
**正确性不依赖清单的完整性**：清单只决定"哪些块能在提交时被顺手清掉"，
而没被清掉的块由首次 DML 兜底（见下）。**因此大事务不会因为清单而受限。**

#### 读一个"没清除过"的块

块已不在缓冲池时，它的 ITL 仍显示"活动"。读者遇到这种块：

```text
ITL[i].txn_id  →  三段式直接定位事务表槽
   代号匹配 + 槽状态 = 已提交  →  取出准确的 commit_seq 判定          ✓
   代号匹配 + 槽状态 = 活动    →  真的未提交                          ✓
   **代号不匹配**（槽已换人）  →  见下                                ✓
```

**代号不匹配时不需要任何近似值**——因为事务表槽的复用条件是
"**该事务已提交且其 undo 已回收**"，即 `commit_seq < 最老快照`。于是：

```text
槽被复用 ⟹ 旧事务 commit_seq < 最老快照(复用时刻) ≤ 最老快照(现在) ≤ S
        ⟹ **该版本对所有有效快照可见**
```

> **这正是 `txn_id` 三段式 + 代次的回报**：它让读者**直接定位**事务表槽，
> 而代次让"槽已换人"这件事**可判定**。
> 于是我们**不需要**那种"上界提交序号"近似机制——
> 它是为"事务表槽可以先于 undo 回收而复用"准备的。
> 我们的复用条件更严，换来的是结论确定、且**少一类"快照过旧"**。

#### 真正的清除：由 DML 完成

**只有 DML 才进一步清除**——一个事务首次修改某块时，顺手把该块的过期槽清掉：
写入准确的 `commit_seq`、回收槽位空间。**这一步生成 redo，与它自己的 redo 合并。**

**这也是"ITL 槽位复用"唯一被允许发生的时机。**

> 提交时更新 ITL 只写**内存页** + 清单，**不需要等数据页落盘**，
> 因此不拖慢 `fsync` 关键路径。

#### 11.1.2 Undo 自身必须受 redo 保护

**这是恢复正确性的前提，不是优化项。** 推理只有三步：

1. 事务修改一行时，前像被写入 **undo 页**——而这些 undo 页可能还在缓冲区里，崩溃时**与数据页一起丢**。
2. 恢复第三阶段（撤销）依据的正是 undo 里的前像——**undo 自身丢了，未提交事务就再也回滚不了**。
3. 所以 **redo 必须能重建 undo 页**：对 undo 页的修改**同样是 redo 记录**。

**"undo 必须先于数据页持久化"由日志顺序自动成立**——这条推论值得显式写出：

- 一次修改产生两次页修改：先"改 undo 页"（R1），后"改数据页"（R2），故 **`R1.LSN < R2.LSN`**。
- 日志**顺序落盘** ⇒ R2 落盘时 R1 必已落盘。
- 数据页刷盘前其 redo 必须已落盘（§11.1 规则 2）⇒ R2 已落盘 ⇒ R1 已落盘 ⇒ **undo 已持久**。

于是**不需要**为 write-ahead undo 单独设计机制——只要 undo 页的修改进入 redo，顺序就自动成立。
反过来说：**若 undo 不进 redo，这条保证就断了，且没有补救手段**。

**被排除的设计**：有一种做法是"undo 只存在 redo 里、不落 undo 页"，回滚时扫日志。
不采用——redo 组是**循环复用**的（§2.4），长事务的早期 undo 会在它自己的回滚完成之前就被覆盖；
而归档日志是离线恢复路径，不能用于在线回滚。

**无 undo 的表**：`logging = none` 的表不产生 undo（§2.2、§11.4），因此也不产生 undo 的 redo。
它们本就不参与回滚——这与它们"可丢失"的定位一致，不是遗漏。

#### 11.1.3 原子边界的两种载体

**原子性必须由某条边界承载**，而边界有两种，**分别适用于不同的操作**——这个区分是本节的重点：

| 操作类型 | 原子边界 | 记录是否必须单条原子 |
| --- | --- | --- |
| **系统操作**（区分配、段头、位图） | **没有**——它不是事务，无提交记录可依托 | **必须**——见下反例 |
| **事务性的行修改** | **提交记录** | **不必**——拆分仍是原子的，由提交记录兜底 |

**系统操作必须用单条多页记录。** 反例：区分配要同时改"位图页"与"段头页"，
若拆成两条、崩在中间，重放后位图说"这些页已分配给某段"、却没有任何段认领它们——
**页泄漏**，且恢复阶段无从判断该回滚哪一边。

**事务性的行修改则可以拆**——这带来两样东西：

1. **记录大小有界**：一次跨越 N 个片段页的长文本写入拆成 N 条记录，每条只描述一个页，
   内存与恢复开销都与"一页"成正比（§11.5.3）
2. **不必依赖行外存储**（§6.8）

原子性由提交记录保证：

- 崩溃且未提交 → **逐片段回滚**。这要求 undo 与该片段的数据修改**成对、按片段交错落盘**，
  即每个片段都是"先写 undo 的 redo，再写数据页的 redo"（§11.1.2 的 R1/R2）。
  于是任一时刻崩溃，已落盘的片段都恰好配着它自己的 undo。
- 崩溃且已提交 → 提交前全部记录必已落盘（WAL 规则 3），全部重放。

**R1 与 R2 不必合并成一条记录**（上一版这里建议过合并，现予修正）：
两者在同一个片段的边界内成对，R1 先于 R2 **由日志顺序自动保证**（§11.1.2），
不需要靠"同一条记录"来保证先后。拆开反而让粒度更细、记录更小。

#### 11.1.4 提交序号：作用域与增长边界

**提交序号是本设计的 SCN 对应物**，但它的**作用域与 Oracle 不同**——
而那处不同恰好消掉了 Oracle 最麻烦的一类问题。

##### 作用域：每工作区一条，不同工作区之间不可比

| | Oracle 的 SCN | **我们的提交序号** |
| --- | --- | --- |
| 作用域 | **全实例共享**（RAC 下跨节点同步） | **每工作区一条** |
| 谁读它 | 所有数据文件、所有节点 | **只有本工作区的页、undo、redo** |
| 跨库比较 | **要**——Data Guard、DB Link、分布式事务都要求 SCN 可比 | **从不**——无跨工作区事务，无分布式事务 |

**它为什么天然是每工作区的**：控制文件是每工作区一份（§2.3），
而"当前提交序号"就记在工作区控制文件的检查点进度里（§2.6）。
**这不是新决定，是既有结构的推论**——但此前从未写明。

**于是"两个工作区的提交序号能不能比大小"这个问题不存在**：
没有任何路径会把它们放在一起比。**不可比，也不需要可比。**

##### 与 Oracle 的 SCN headroom 问题的关系

Oracle 的 SCN 有 48 位上限，而它必须与**别的库**保持可比——
于是一个失控节点（或一次指向高 SCN 库的 DB Link）把 SCN 推高之后，
这个库就**再也无法与别人通信**。所以它必须盯着"SCN 增速是否合理"
（对照墙上时间算一个上限，越界即告警 `SCN headroom`，最终 `ORA-19706`）。

> **问题的根不在"48 位会用完"，而在"SCN 必须跨库可比"。**
> 48 位全速跑也要几百年，真正出事的是"比别人高出一大截"。

**我们没有被比较的对象**，所以那条链整个不存在：

| Oracle 的触发条件 | 我们 |
| --- | --- |
| 多节点 SCN 同步 | **单实例**，无 RAC |
| 跨库 SCN 可比（DG / DB Link / 分布式事务） | **都不做**（§3 的排除项） |
| 失控节点牵连全库 | **每工作区独立**——一个工作区的序号飙高**碰不到别人** |

##### 残余风险与对策

剩下的只有一条：**单个工作区的提交序号逼近 48 位上限**。
48 位按 1000 提交/秒可用 8900 年（§5.4），正常负载下不成问题；
风险来自**异常增长**——比如一个失控的重试循环把提交速率推高几个数量级。

| | |
| --- | --- |
| **影响范围** | **仅该工作区**——这正是"每工作区一条"买到的东西（§11.8 的故障隔离延伸到了序号） |
| **对策** | 对照墙上时间做**增速合理性检查**；越界即告警并**拒绝继续分配**，不是静默继续 |

**增速与处置已定**（§14 第 55 项）：告警 → 连续越界拒绝分配；`public` 只告警不拒绝。

> **一处必须点明的例外：`public` 不能被重建。**
>
> 普通工作区的序号若真走到尽头，还有**重建工作区**这条路（导出 → 重建 → 导入）来重置；
> 而 `public` 持有实例级管理元数据，**没有"重建"这条路**。
>
> 好在 `public` 上只有**低频的管理操作**（建工作区、改配额、增删文件系统），
> 它的序号增长速度**天然就低**——**这一点使它的不可重建不构成风险**。
> 但它是"每工作区一条"这个设计里**唯一没有退路的那一个**，应当记在明处。

### 11.2 缓存策略与恢复

**steal + no-force**，故恢复必须同时处理重做与撤销。三阶段：

1. **分析**：从最近检查点重建事务状态表与脏页表，确定重做起点。
2. **重做**：从重做起点重放；按 `page_lsn` 判定已包含的修改并跳过（**幂等**）。
3. **撤销**：对未完成事务反向应用 Undo——**逆操作本身写 redo**
   （它即可重入的"补偿"：崩溃后续做 = 重走整链，见 §4.6.6 的 ③）。

#### 顺序不可颠倒：先重做，再撤销

**重做阶段必须重放全部修改——包括崩溃时尚未提交的事务。** 这不是疏忽，是唯一正确的做法：
**崩溃前的那一瞬间才是自洽的状态，也是 undo 链唯一完整的时刻。**

- 若重做时"跳过未提交事务的修改"：数据页停在半途，而 **undo 链本身也只写了一半**——
  撤销阶段要沿链反向走，链却是断的，**回滚无从下手**。
- 若先撤销再重做：撤销要读 undo 页，而 undo 页自己可能还没被重做出来。

Oracle 的表述可直接引用：

> **重做保护已提交的数据，撤销保护未提交的数据。**

未提交事务的修改必须由 redo 重建，正因为**重建之后才谈得上撤销**。这与 §11.1.2 是同一件事的两面：
undo 页要被 redo 重建，而重建后的 undo 页里**已提交与未提交事务的记录混在一起**——
在撤销完成前，两者本就无法区分，也无须区分。

**恢复完成后才是一致的**：重做只把工作区带回"崩溃前那一刻"（物理一致），
撤销才把它带回"只含已提交事务"（逻辑一致）。**少了任何一步都不算恢复完成。**

#### 一个可以缓一缓的优化：回滚不必挡在开放之前

Oracle 在 **Cache Recovery 完成后就打开数据库**，撤销由 SMON 在后台继续。
它之所以敢这么做，是因为一致性读机制天然处理"读到被未提交事务修改的行"——
读者按 ITL 发现事务仍在进行，就沿 undo 重建旧版本（§5.4、REQ-TXN-003）。

我们**具备同样的机制**，因此这条路是通的。但 **V1.0 先采用更简单的一种：撤销完成后再开放工作区**。

- **理由**：单工作区、写量小，崩溃时遗留的未提交事务规模有限，延时可接受。
- **代价的另一面**："打开后后台撤销"要求恢复与正常读写**并发**操作同一批 undo 页与事务表，
  测试面大得多。恢复路径本就最不能出错，不该在 V1.0 给它加并发。
- 若将来实测启动延时成为问题，再引入——**它不改动任何格式，只是调度问题**，属于纯增量。

### 11.4 按表类型的持久化差异

| 表类型 | 崩溃后的保证 |
| --- | --- |
| `logging = full` | 已确认提交必存；未提交不可见 |
| `logging = redo_only` | 同上，但**无回滚能力**（表本身无多语句事务） |
| `logging = none` | **可丢最近写入、可出现撕裂页**（由校验和 + 页尾校验检出，该页数据丢弃） |

### 11.5 redo 的文件结构与记录格式

参考 PostgreSQL 的 WAL。它的记录布局是三段式：

```text
XLogRecord 固定头（24B）
  0..N 个 XLogRecordBlockHeader     ← 块引用
  XLogRecordDataHeader[Short|Long]
  block data                         ← 块数据
  main data                          ← 主数据
```

其中两条经验直接可用，两条我们做得更简，另有一条**必须靠行格式配合**。

#### 11.5.1 文件：线性记录流，**页是缓冲区的管理单位**

**每个 redo 成员文件是线性写的**（从头写到尾，写满即切换）——环形语义由"2 组轮换"在文件之上提供（§2.4），文件本身是线性的。

**redo 文件由固定大小的页组成**（格式见 §5.11），页是 **redo log buffer 的管理单位**——
有页，日志缓冲区才能按页分配、按页回收、按页刷盘。**无页则缓冲区无单位。**

**与 PG 的区别不在"有没有页"，而在"允不允许记录跨页"**：

> PG 允许记录跨 WAL 页，靠新页头里的 `xlp_rem_len` 续接。**代价是 `WALInsertLockAcquireExclusive`：一次要拿下全部 8 把 WAL 插入锁。**

**记录允许跨页**（§5.11）：放不下当前页的剩余空间时，**跨到下一页继续**，
由**分片头**串联；分片序列被截断则整条记录丢弃。

> **跨页对我们没有额外代价**——PG 那条惩罚（`WALInsertLockAcquireExclusive` 要拿全部 8 把锁）
> 是它**无锁追加**设计的代价；我们的 WAL 追加本来就是 **latch 串行化**的（§11.5.2），
> **跨不跨页都要拿那把 latch**。详见 §5.11 的更正说明。

**页头与分片头分工互补，不是替代**：

| | 回答的问题 |
| --- | --- |
| 页头（`校验`、`已用长度`） | **这一页有没有坏**；页内有效数据到哪为止 |
| 分片头（`rec_id`、`frag_no`、`frag_cnt`） | **跨页的记录怎么串起来** |

**唯一的边界规则**：

> **一条记录不得跨越文件边界**——文件尾空间不够则填充，从下一个文件开始

好处是每个 redo 文件可**独立校验**，恢复扫描不必跨文件拼接。

这条规则给 redo 组大小一个**独立的下限**：

> 组大小 ≥ 最大单条记录（**17 KiB**，§11.5.2 已定量）。记录虽可跨页（§5.11），
> 但**不得跨文件**——所以这条下限由"不跨文件"决定，实际值就是**一页 + 分片头**

它与 §2.4 已有的下限"必须能容纳一个检查点周期"是**两条独立约束，取其大者**。

#### 11.5.2 记录：固定头 + 块段 + 可选主段

```text
┌ 记录头（20 字节，固定——照 §14 第 46 项去掉 4B CRC）
│   tot_len   4B   整条记录总长（含本头，不含分片帧）——恢复扫描据此跳过或分配
│   lsn       6B   本条记录的 LSN，同时是"应用后该页的 page_lsn"
│   txn_id    6B   产生者（0 = 系统操作）
│   op        1B   语义标签（§11.5.4）
│   flags     1B   bit0 = 存在块段，bit1 = 存在主段
│   reserved  2B   对齐至 20B
├ 块段（页修改类记录使用）：blk_cnt 1B
│   块引用[]：flags 1B | rdba 5B | chg_cnt 2B（每项 8B，blk_cnt 项）
│   块数据[]：按块顺序，每块 chg_cnt 项：offset 2B | len 2B | after_bytes
└ 主段（非页修改类记录使用）：payload——**无长度字段**，
    长度 = tot_len − 20 − 块段长度（能推导的不存）
```

**与 PG 的四处差异，都是我们已有的东西换来的**：

| | PG | 我们 |
| --- | --- | --- |
| 块定位 | `RelFileLocator`（12B）+ `BlockNumber`（4B） | **`rdba` 5B**——ROWID 的 `file_id 10 + block_id 28` 本来就够用 |
| `xl_prev` 前向指针链 | 有（构成单向链表） | **省略**——① WAL 追加由 latch 串行化（写少、争用低），不需要用它做无锁追加；② **反向遍历不需要**（undo 有自己的链，§4.6.1）；③ 日志链的连续性由**日志序列号**判定，不靠每条记录的 prev |
| `xl_rmid` + `xl_info` | 资源管理器**决定重放函数** | **`op` 只是语义标签**，不决定 apply——apply 路径唯一（§11.5.4） |
| 主数据段 | 承载逻辑描述 | **仅用于非页修改类的记录**（检查点、日志切换等） |

**只存 after-image，不存 before-image**——前像在 undo 里（§11.1.2）。redo 是"再应用一次"，不需要前像。

**记录不带 CRC**（§14 第 46 项已结）：页尾校验覆盖每页，分片重组由 `rec_id` / `frag_no` / `frag_cnt` / `frag_len` 把关——省掉"拼内容 → 补 CRC → 再落盘"的两趟写，记录一次成型。**块段与主段也不带长度字段**（由 `tot_len` 推导）——"能推导的不存"贯彻到底。

**与 Oracle 重做记录的对照**（证据包 `redo-bytes-20261004`）：

| Oracle | 我们 | 差异理由 |
| --- | --- | --- |
| 记录头：线程号 / RBA / 记录长度 / **VLD** / SCN + 子 SCN | `txn_id` / `lsn` 6B / `tot_len` / **页校验 + 分片帧** / **无 SCN** | 单实例无线程号；LSN 是单调字节位置、位置可推导（§2.7）；可见性走 `commit_seq`，SCN 不混入日志（CONV §3） |
| 变更向量（CV）：描述**单块**变更；头含 opcode / 块类 / 绝对文件号 + 相对 DBA / **变更前 SCN** / 序列号；随长度数组 + **4B 对齐**数据 | 块段的"块引用 + 块数据"即 CV 的等价物；**无 per-CV opcode**；块定位 = `rdba` 5B；**无 before-SCN**（页自带 `page_lsn`，重放幂等统一判定）；**不强制对齐**（顺序 memcpy） | 表达力换恢复路径唯一（§11.5.4） |
| 记录**从块边界开始**；跨块跳过中间块头 | 页内**线性打包**；每页 12B 分片头 | 512B 页下补零浪费大 |
| CV 可跨多个连续块 | 可跨多个 redo 页（分片），**不得跨文件**（§11.5.1） | 每文件可独立校验 |

**大记录的上限与"不跨文件"的定量**：最坏单条记录 = **重写一整个数据页**——内容 = 记录头 20B + 块段（1 + 8 + 4 + 16384）= **16,417B**；分片后跨越 **34 个 redo 页 = 17 KiB**（每页净装 484B）。**组大小下限 ≥ 17 KiB** 由此而来（§2.4）。

#### 11.5.3 长文本：按页拆分记录，不需要行外存储

本系统有**长文本**（记忆内容、知识条目、文档片段）。真正的大对象走
`ASSET_REF` 外部文件、不进 redo（§6.8），所以这里讨论的是库内的长文本。
但它**不需要 TOAST**——推导见 §6.8，结论如下：

**长度不构成约束，因为"一条逻辑修改 = 一条 redo 记录"并不是必须的。**
一次跨越 N 个片段页的长文本写入拆成 N 条记录，每条只描述一个页：

- **记录大小有界**（≈ 一页 + 24B 头），**与文本长度无关**
- **内存有界**——不必为一条记录分配与文本等长的缓冲区
- **原子性由提交记录兜底**（§11.1.3）

于是组大小下限与最大文本长度**确实是解耦的**——但解耦的机制不是"把文本挪走"，
而是"**把记录拆开**"。

**唯一需要单条原子记录的是系统操作**（区分配等，没有提交边界）。它们本来就只涉及几页，
不构成压力。

> **由此得到一条更一般的规则**：**redo 记录的大小以"页"为界，不以"逻辑操作"为界。**
> 逻辑操作的原子性由**提交记录**（事务性）或**单条记录**（系统性）承载，
> 与记录的物理大小无关。

#### 11.5.4 记录类型与 torn page 防护

`op` 沿用先前讨论的取值（**不参与 apply**，只用于诊断、统计与组提交识别）：

```text
0x01 日志切换 / 文件头       0x10 页修改（通用）
0x02 检查点                  0x30 提交
0x31 回滚完成
```

**主段格式（按 `op`；均无长度字段——由 `tot_len` 推导）**：

| `op` | 主段内容 |
| --- | --- |
| 0x01 日志切换 | 组号 1B │ 新日志序列号 4B |
| 0x02 检查点 | 与控制文件"检查点进度"同构的 24B：检查点提交序号 6B │ 检查点 LSN 6B │ 当前提交序号 6B │ 最老快照提交序号 6B |
| 0x30 提交 | `commit_seq` 6B——提交可见性与延迟块清除据此 |
| 0x31 回滚完成 | 空——信息全在头部的 `txn_id` |
| 0x10 页修改 | 无主段（用块段） |

**apply 路径唯一**：无论 `op` 是什么，页修改一律按"块引用定位 → 页内字节写入"应用，幂等性由 `page_lsn` 统一判定。这是自觉的取舍——放弃 PG 那种"每个资源管理器一个 `rm_redo` 函数"的表达力，换取**恢复路径只有一条**。恢复恰恰是最不能出错、又最难在日常被覆盖到的路径。

**不做整页镜像，也不做双写区——torn page 防护交给文件系统**

与 PG 默认不同，我们**不采用 full page write**；也不采用 MySQL / openGauss 的**双写区**。
两者都是"在数据库内部再造一份页副本"来对抗部分写，而本库的定位是**尽可能轻量、快速**——
FPW 让检查点后的 WAL 写入量翻倍（PG 自己的话），双写区则要多一条独立的写路径与一个独立的恢复分支。

**这不是省掉一层保护，而是换一个更上游的保证**，而且 **PG 官方文档明确认可这种换法**：

> 如果有减小部分页面写入风险的硬件支持（比如电池供电的磁盘控制器）或者**文件系统支持**
> （比如 ReiserFS 4），并且他们可以把风险降低到一个可以接受的低范畴，那么可以关闭这个选项。
>
> **使用 COW 文件系统（如 ZFS）可关闭 FPW，因为不存在 partial write。**

在 COW 文件系统（ZFS、btrfs）上，一次 16KB 的覆盖写等价于**换指针**——旧数据块原地不动，
**"半新半旧的页"根本不会出现**。FPW 要防的那件事不发生，自然也就不需要防它的机制。

> **这是一项取舍，不是门禁**——为什么它可以被接受，以及各文件系统的能力档位，见 §11.6。

**部署在 XFS 或 ext4 上时它不成立，而这是显式接受的代价**：这两者的文件系统日志只保护**元数据**，
不保护文件数据，一次 16KB 的 `pwrite` 在掉电时仍可能只落一部分。此时 torn page **无法由 WAL 修复**——
我们的 redo 是**物理增量**（offset + bytes），它能重放"改了什么"，**无法重建"一个完整的页"**。
各文件系统的能力档位与接受理由见 §11.6。

**保留的唯一底线是页校验和**：它能**检出**撕裂页，检出后**按损坏处理**（报错、告警、从备份恢复），
而不是静默返回错误数据。PG 对它的定位说得很准：

> **block checksum 可辅助检测不一致块，但无法替代 FPW。**

**四种手段的对照**（同一个目标）：PG 全页写 / MySQL 与 openGauss 双写区 / Oracle 校验和 /
**我们——把原子性推给存储层**。前三种都在数据库内部解决；我们取第四种，代价是**原子性取决于部署在哪个文件系统上**
（§11.6）。正因为它是条件而非默认，工具必须**如实报告档位**，而不是让人以为有保障。

**格式上不为此预留专门字段**：块引用头的 `flags` 尚有未用位，若将来确实要在非 COW 部署上补回 FPW，
加一个标志位即可——**不为不打算做的事增加结构**。



### 11.6 文件系统能力基线

本设计的**崩塌一致性**与**工作区克隆**分别建立在文件系统的两项能力上。
**这两项彼此独立**——一个文件系统可以满足其一而不满足其二。这是最容易出错的地方，
所以在此集中记录，§2.7 与 §11.5.4 均指向本节。

| 文件系统 | **原子页写** | **reflink** | 定位 |
| --- | --- | --- | --- |
| **btrfs** | ✅ | ✅ | **首选**——两项都满足 |
| **XFS**（`reflink=1`） | ❌ | ✅ | **次选**——克隆可用；撕裂页风险是**显式接受的取舍** |
| ZFS | ✅ | 视版本：自身有快照/克隆机制，OpenZFS 2.2 起提供 `FICLONE` | — |
| ext4 默认 | ❌ | ❌ | 可用，但无克隆 |

#### 两项能力分属两个设计决定

| | 被谁依赖 | 缺失时的后果 |
| --- | --- | --- |
| **原子页写** | §11.5.4"不做 FPW、也不做双写区"这个决定 | **接受**——撕裂页由页校验和**检出**，按损坏处理（报错、告警、从备份恢复），**不会静默返回错误数据** |
| **reflink** | §2.7 工作区的克隆与分支 | **功能不可用**——禁用克隆并明确报错，数据本身无损 |

#### `reflink` 不等于"原子页写"

**这是本表存在的理由。** XFS 的 `reflink` 只让**共享的 extent** 在被写时走 COW；
一旦某段变成**私有**，后续写就是**原地写**，与普通文件无异。
XFS 的文件系统日志只保护**元数据**、不保护文件数据。

> 于是有一个反直觉的组合：**XFS 满足 reflink 克隆，但不提供原子页写。**
> **不要从"XFS 支持 COW"推出"XFS 不会撕裂页"**——这两件事没有关系。

#### 为什么原子页写可以是取舍，而不是门禁

撕裂页是**掉电瞬间**的小概率事件，且**页校验和能检出**它。
检出后按损坏处理——失效模式是"**明确的错误**"，不是"错误的答案"。这个区别是它可被接受的原因。

PostgreSQL 对校验和与 FPW 的关系说得准：

> **block checksum 可辅助检测不一致块，但无法替代 FPW。**

因此**不把它作为启动门禁**：部署在 XFS 或 ext4 上允许启动。
但**工具必须能报告**当前文件系统提供了哪些能力——**不得让人误以为有保障**。

> 平台侧的部署建议见 [`platform-support.md`](../../docs/platform-support.md)。

### 11.7 检查点与后台写

检查点是**缓冲池的机制**（§5.10）——它的全部材料都在内存里，落到磁盘上的只有它的**结论**。

#### 两个角色，两件事

| 角色 | 做什么 | **不做什么** |
| --- | --- | --- |
| **写线程**（DBWR 角色） | 把脏缓冲**写回文件** | 不动控制文件 |
| **检查点**（CKPT 角色） | 把**检查点位置**写进控制文件 | **不写数据块** |

Oracle 把它拆成两个进程，理由是并行化。**我们在职责上分开**——因为它们出错时的表现完全不同：
写块失败是 I/O 问题，写检查点位置失败是元数据问题。

**层次是实例级**：两个角色都服务该实例下的**所有工作区**，不按工作区各建一套。
**写线程可以有多个**（Oracle 的 `DB_WRITER_PROCESSES`），但那是**并行手段**，
不是"每个工作区一个"——见下"多个写线程：按工作集绑定"。

> 知识库原文的分工表述可直接引用：**"块写入工作由 DBWR 完成，CKPT 不直接写数据块。"**
> 历史上这项工作曾由 LGWR 兼任，后来才分离出来。

#### 检查点队列就是 §5.10 的脏链

脏缓冲按**首次变脏的 LSN 升序**挂在脏链上，写线程从**最老的一头**开始写。

**脏链是每工作区一条**（§5.10）：LSN 跨工作区不可比，且低水位本就是每工作区一个。
一个工作区的脏页积压**不得阻塞**另一个工作区的检查点推进——这是故障域隔离的基础。

- 写掉最老的那个 → **低水位前移**
- **低水位 LSN = 恢复起点**——该 LSN 之前的修改**已全部落盘**

**写必须按顺序**（知识库原文："由于 CHECKPOINT QUEUE 按 LOW RBA 排序，
DBWR 在处理 CHECKPOINT 批时必须按 RBA 顺序写脏块"），否则低水位推不动。

#### 用增量检查点，不做"停下刷全部"

| | 完全检查点 | **增量检查点**（采用） |
| --- | --- | --- |
| 动作 | 写出**所有**脏缓冲 | 按序持续写，检查点位置**平滑前进** |
| I/O | **尖峰** | 平稳 |
| 用于 | **关闭工作区**、克隆前（§2.7） | **运行期常态** |

Oracle 的增量检查点是 8i 引入的，CKPT **默认每 3 秒**更新一次检查点位置。
我们采用同样的形态：**周期性地把低水位写进控制文件**。

> 这也不在提交关键路径上（§2.6）——控制文件由检查点周期性地写，不频繁。

#### 脏链的数量 = 已打开的工作区数

脏链**按工作区组织——有多少（已打开的）工作区，就有多少条**。
未打开的工作区没有缓冲块，也就没有链。这正是"按需打开"（§11.8）自然带来的：
链的数量随**活跃**工作区伸缩，不随工作区总数增长。

#### 多个写线程：按工作集绑定

写线程**可以有多个**。但知识库给出的三条约束决定了它该怎么接：

> **DBWR 进程数不能超过工作集数；工作集在系统启动时分配给 DBWR；
> DBWR 总是只写入分配给自己工作集的缓冲区。**

我们照此：

| 规则 | 说明 |
| --- | --- |
| 写线程数 **≤ 工作集数** | 多出来的线程无处可管——知识库明说"额外的 DBWR 进程闲置或随机抢工作集，**反而增加管理复杂度**" |
| 工作集在启动时**静态分配**给写线程，之后不变 | 无动态迁移、无跨线程协调 |
| 每个写线程**只写自己工作集里的脏块** | |

**于是"哪个工作区由谁写"是静态确定的**——两步映射在启动时全部定死：

```text
工作区 ──(H(workspace_ref) mod N)──▶ 工作集 ──(启动时分配)──▶ 写线程
```

**一个工作区的检查点推进因此只涉及一个写线程，没有跨线程协调。**
这是"按工作区划分工作集"（§5.10）买到的最主要一笔。

知识库也点明了配置失衡的两头：

| 失衡 | 后果 |
| --- | --- |
| 写线程 **多于**工作集 | 多余线程闲置或抢工作集，**只增加复杂度** |
| 写线程 **少于**工作集 | 部分工作集没有专属写线程，脏缓冲积累，**触发 free buffer waits** |

#### 一个写线程内部的紧迫度调度

多线程**并不取消**调度问题，只是把它的作用域**缩小**：从"全实例 N 条脏链"缩到
"一个写线程所辖的若干工作集、若干条脏链"。

调度仍然必要。否则它辖区内的某些工作区低水位会长期推不动——
表现为**该工作区在日志切换时被迫等待**。症状与"redo 组太小"相同，但成因是**调度**而非容量，
两者处置完全不同，不能混为一谈。

**紧迫度由工作区自己的 redo 余量决定**：

> 该工作区距离"下一组 redo 被覆盖"还剩多少日志空间，就是它的紧迫度。

这个量有两个好处：**每工作区可算**，而且**天然可比**——虽然 LSN 跨工作区不可比（§5.10），
但"剩余日志字节数"是各工作区自己的标量，可以直接比较。

于是调度规则：

> **优先服务"最接近 redo 耗尽"的工作区**；紧迫度相当时轮转，保证没有工作区被饿死。

这比单纯轮转更贴合目标——**检查点推进的目的本就是让日志可被覆盖**，
"谁快没日志空间了"是最直接的信号。

> **它与"公平"是两件事**：这里的调度目标是**正确性**（不让某个工作区的日志链断裂），
> 属硬约束；而资源公平是**性能**目标，由配额与优先级承担（见 §1.3）。

#### 检查点位置：每工作区一个，只写一处

**检查点是每工作区独立的**——每个工作区有自己的 redo、自己的低水位、自己的控制文件。
CKPT 分别为每个工作区发布检查点位置，写进**该工作区自己的控制文件**。

Oracle 写**两处**：所有**数据文件头** + **控制文件**。
**我们只写控制文件。**

> **理由**：Oracle 写数据文件头，是为了让"数据文件 + 控制文件副本"能独立恢复。
> 而我们的数据文件本来就**不承载恢复点**——控制文件是唯一恢复锚点（§2.3），
> 同时每个文件的**页分配位图**已在文件头（§3.2），文件仍是自描述的。
> 少写一处，就少一个可能与控制文件不一致的地方。

#### redo 组大小的下限由此得出

这正是 §2.4 与 §11.5.1 反复引用、却一直没算出来的那个数。

**约束**：redo 只有 2 组轮换。一个组要被**再次使用**时，它上面的日志所对应的修改
**必须已经全部落盘**（检查点已推进过它）。否则那些日志一旦被覆盖，
恢复就再也无法从检查点走到日志末尾——**日志链断裂**。

```text
组大小 ≥ 一个检查点周期内产生的日志量
     ⟺  检查点推进速度 ≥ 日志产生速度（稳态要求）
```

**若跟不上**：日志切换被迫等待检查点推进——表现为**写的延迟尖峰**。这是"组太小"的症状。

**另一头的约束**：恢复重放量 ≤ 2 组（最多有两组的日志还在）。所以——

> **组大小 ↔ 恢复时间**直接挂钩：**组越大，恢复越慢**。

两条合起来定组大小：

| 方向 | 约束 |
| --- | --- |
| **下限** | 能容纳一个检查点周期——否则切换时等待 |
| **上限** | 恢复时间可接受——重放量 ≤ 2 × 组大小 |

**取值**：

| | 值 | 依据 |
| --- | --- | --- |
| **默认** | **256KB / 组** | 两个组 × 两个成员 = **4 个文件共 1MB**（§2.4）。恢复重放 ≤ 512KB，**几乎瞬时** |
| 范围 | **256KB – 256MB** | 下限见上表；上限由"恢复时间可接受"决定 |

**默认值取小而不是取大**：这是本库画像决定的——单机、小工作区、短事务。
**组小则恢复快、固定开销低**；真出现"检查点跟不上日志"的延迟尖峰，
说明该工作区的写量已超出默认假设，**那时再调大**。
这正是 §2.4"组大小创建工作区时指定"的用意。

#### "检查点 LSN"的语义（再确认）

控制文件里的**检查点 LSN 就是低水位**——**该 LSN 之前的修改已全部落盘**，
而不是"最后一次检查点动作发生在哪"（§2.6 已记）。

实例恢复从它开始重放即可，它之前的日志可以丢弃。

#### 另一类后台：可选的应用级后台任务

**除了 CKPT 与写线程，引擎还有一类可选的后台** ✗✓——
典型形态是"**会话 → 记忆的提取**"（§8.2）。它**不是库外进程**：

> **库外进程很难标准化** ✗——每个使用方都要自己写一遍提取逻辑 ✓，
> **而"底座要友好"正要求它开箱可用** ✓。

**它与 CKPT / 写线程的区别与共同点，要同时说清**：

| | CKPT / 写线程 | **应用级后台任务** |
| --- | --- | --- |
| 属于 | **存储层** ✓ | **语义层** ✗ |
| 跑什么 | 固定的存储动作 | **由配置决定**（提示词、模型）✗ |
| 要不要外部服务 | 不要 ✓ | **要**（LLM / 嵌入服务）✗ |
| **共同点** | **每工作区一份；可重启；只产出派生数据** ✓✓ | 同 ✓ |

##### 四条设计约束

**① 可选——配了才启，启不了就不启** ✓

**没有配置、或外部服务不可用 ⟹ 进程不启动** ✓——**不是"启动了再失败"** ✗。
**库的其余部分不受影响**：会话照写、记忆照查、检索照做 ✓。

**② 每工作区一个** ✓

与 §11.7 的"脏链的数量 = 已打开的工作区数"同构 ✓。
**而这一条顺带解决了隔离** ✓✓：它只读写**本工作区**的数据，
**不存在"全用户索引"那条问题**（REQ-RET-011）✓。

**③ 故障重启即可，不是关键进程** ✓✓

**理由不是"它不重要"，而是"它的产物是派生数据"** ✗✓：

```text
失败  ⟹  重跑      （水位在，从断点继续）
结果错 ⟹  丢弃重建
永不损坏权威数据    （它只往派生侧写）
```

**而 LLM 调用经常异常** ✓——**所以这必须是一条设计前提，不是异常处理** ✓。

**④ 产出走正常写路径** ✓

记忆表是 `logging = redo_only`（§8.2）✓——**刚好** ✓：
它**可重建**（是派生），但**不能像会话表那样丢**（**它是恢复点**，§8.2）✓✓。

##### 与嵌入派生是同一个机制的两个实例

| | 嵌入（§8.1 的 `embed`） | **提取** |
| --- | --- | --- |
| 确定性 | **确定** ✓ | **不确定** ✗ |
| 要不要留痕 | 不必 ✓ | **必须**（出处 + 操作者 + 原因）✓ |
| 可选 / 后台 / 派生 / 可重跑 | **完全相同** ✓✓ | 同 ✓ |

> **所以"确定性 vs 非确定性"这条判据的准确含义是** ✗✓：
> 它决定的是**产出要不要带出处** ✓，**不是"能不能进后台"** ✓。
> **两者都能进后台**；差别只在留痕 ✓。

##### 归属在库内，进程可以独立

**"内建"与"同进程"是两件事** ✗✓——**它们必须分开说**：

| | |
| --- | --- |
| **归属** | **库的一部分** ✓——内建、有配置、**库管它的启动与重启** ✓ |
| **进程** | **可以是独立进程空间** ✓——**不与引擎同进程** ✓ |
| **粒度** | **每工作区一个** ✓ |

**分开的理由是具体的**（四条，都不是口味问题）：

| | |
| --- | --- |
| **模型依赖不该是引擎的依赖** ✗✓ | 模型运行时、权重、GPU 驱动——**链接进引擎，引擎就被它们绑架** ✓ |
| **LLM 调用经常异常** ✓ | 崩了**不该带倒引擎** ✓——独立进程天然保证 ✓ |
| **资源隔离** | 模型吃内存 / 显存 ✗——独立进程才限制得住 ✓ |
| **可替换** | 换模型实现 = **换那个进程** ✓——引擎不动 ✓ |

**而它与 §11.8 的故障隔离是同一条**：**一个工作区的提取进程崩了，只影响它自己** ✓✓。

##### 关键：它用**正常接口**读写，没有特权通道

**独立进程 ⟹ 它就是一个"库自带的客户端"** ✓✓——**它不共享引擎的内存** ✗，
**而是和任何调用方一样，通过会话接口读会话表、写记忆表** ✓：

```text
提取进程（独立进程空间，每工作区一个）
   │  普通会话接口
   ▼
引擎：读会话表增量（按水位）→ 【调模型】→ 写 memory / memory_version / derived_link
```

**没有特权通道，这一点是设计价值而不是限制** ✓✓：

| 因为 | 所以 |
| --- | --- |
| 它用**同一个接口** | **它受同一套隔离与事务约束** ✓——**不会越权** ✓ |
| 它**不共享内存** | 引擎与模型之间**没有隐蔽的耦合面** ✓ |
| 它可以**被替换成任何实现** | 只要用同一个接口 ✓ |

> **"库自带"不等于"库内部"** ✗✓——**它自带的是"能力与生命周期管理"** ✓，
> **不是"特权"** ✓。这与 §13.6 的"用不提供实现禁止"同源：
> **没有特权通道，就不存在"谁能走特权通道"这个问题** ✓。

##### 提取器的版本 = generation

提示词或模型变了 ⟹ **提取行为变了** ✗——与 `RET` 的 generation 同构 ✓。

**默认只影响"之后提取的"，不回溯改写已有记忆** ✓✓——
**回溯改写就是重写历史** ✗，违反 REQ-MEM-006（新版本取代旧版本），
**而 A-MEM 的教训正在此** ✓（见 `spec/MEM.md` 的六条路线对比）。

**要重跑旧会话，须显式触发** ✓——不是一个自动动作 ✓。

### 11.8 工作区的独立恢复与故障隔离

**恢复的单位是工作区，不是实例。** 这不是额外设计出来的特性，而是三条既有决定的直接结果：

| 已有决定 | 带来的后果 |
| --- | --- |
| 每个工作区有**自己的控制文件**（恢复锚点，§2.3、§2.6） | 恢复起点、redo 序列、检查点位置**都是每工作区一份** |
| 每个工作区有**自己的 redo**（§2.4） | 重放范围**不跨工作区** |
| 每个工作区**自包含**（§13） | 一个工作区的文件损坏不影响另一个 |

于是：**打开某个工作区时，读它自己的控制文件，就能独立判断"我需不需要恢复"。**

#### 一个脏工作区不阻塞实例

实例启动只做一件事：打开**全局控制文件**、取出工作区清单（§2.6）。它**不逐个打开工作区**。

工作区**按需打开**——第一次被访问时才打开。于是：

- 实例启动时间与工作区数量、大小**无关**
- 某个工作区需要恢复（甚至恢复失败），**别的客户端只是在用别的工作区**，完全不受影响

> 若改成"启动时全部打开"，一个坏工作区就能拖住整个实例的可用性。
> **按需打开让故障域天然收敛在工作区之内。**

#### 打开失败时的三种处置

| 处置 | 语义 | 何时用 |
| --- | --- | --- |
| **正常打开** | 需要恢复则先完成恢复（§11.2 三阶段），再对外服务 | 常态 |
| **隔离** | 该工作区**不可访问**，其余一切照常；原因可经管理接口查询 | 打开失败的**默认**行为 |
| **强制打开** | 跳过恢复的部分检查，允许打开——**可能读到不一致的数据** | 抢救数据时的**显式**管理操作 |

**隔离是默认，"强制打开"必须显式调用**——因为它把一个**本可检测的失败**
换成了一个**静默的错误答案**。这与本设计在别处的一贯取舍一致：
**宁可失败得明确，不可成功得可疑。**

隔离一个工作区时，要把它在**共享缓冲池**里的缓冲块**移除**（脏块丢弃、不写回）——
既避免它的异常波及共享的 DBWR 线程，也避免它的页混进后续任何写回。
**丢弃是安全的**：WAL 保证磁盘状态随时可被重放修复（§11.1），下次正常打开时恢复即可。

#### 这与"共享缓冲池"不矛盾

一个自然的疑问：缓冲池与后台线程都是**实例级共享**的（§5.10、§11.7），
凭什么说故障是隔离的？

因为**共享的是资源，不是状态**：

| 共享 | **不**共享 |
| --- | --- |
| 缓冲池内存、DBWR / CKPT 线程、latch 基础设施 | **全部恢复状态**：检查点位置、低水位、脏链、redo 序列、事务表 |

共享只影响**性能**（一个工作区占用缓冲池会挤压别人），不影响**正确性**。
而性能挤压由配额与调度约束处理（资源预算，见 §1.3），**不是靠各建一套来隔离**——
那样既浪费内存，又让"实例级一套"的简化失效。

### 11.9 日志切换与归档

本节是 §2.5 那条约束——**未完成归档的日志组不得被覆盖**——的完整机制。
它改变日志切换与 redo 空间管理，故与 WAL 层同期定案（待冻结项 14）。

#### 组的两条状态轴（落在控制文件的 2 字节上）

控制文件为每组存两个状态字节（§2.6）——**运行状态**与**归档状态**两条轴，互不替代
（照 Oracle：`v$log.STATUS` 与 `v$log.ARC` 是两列）：

| 运行状态（1B） | 含义 |
| --- | --- |
| 0 `UNUSED` | 从未使用，或新增尚未使用（**序列号 = 0**） |
| 1 `CURRENT` | LGWR 正在写（全实例至多一组） |
| 2 `ACTIVE` | 已写满；**检查点尚未越过其结尾**——其 redo 仍可能需要崩溃恢复，**不可复用** |
| 3 `INACTIVE` | 检查点已越过其结尾——运行状态上可复用 |

| 归档状态（1B） | 含义 |
| --- | --- |
| 0 `NONE` | 无需归档（非归档模式；或该组未写满即被弃用） |
| 1 `NEEDED` | 待归档 |
| 2 `IN_FLIGHT` | 归档中 |
| 3 `DONE` | 已归档 |

**可复用（唯一判据）**：`运行状态 = INACTIVE` ∧（非归档模式 ∨ `归档状态 = DONE`）。
它把 Oracle 的两类"不能重用"（`ACTIVE` / 未归档）合成一条判据。

#### 切换协议

**触发**：① 当前组写满——或剩余空间放不下下一条记录时提前收尾（**记录不得跨组**，§11.5.1）；
② **强制切换**（管理操作：备份 / PITR / 克隆之前、优雅关闭）。

**步骤**：

1. 按可复用判据选下一个组；**无可复用组 ⇒ 写者等待**——按缺的条件分两类（见"等待与告警"）。
2. 在**新组的第一条位置**写入**切换记录**（`0x01`，主段 = 组号 1B │ 新日志序列号 4B）。
3. 新组 → `CURRENT`；旧组 → `ACTIVE`，若为归档模式其归档状态 → `NEEDED`。更新控制文件 Redo 条目。
4. 检查点周期性推进时，把"结尾 LSN ≤ 检查点低水位"的 `ACTIVE` 组降为 `INACTIVE`；
   此后该组按归档轴决定能否复用。

**序列号**：每被选为 `CURRENT` 一次，序列号 = 上一个 + 1（**单调、不复用**）；
`UNUSED` 组序列号为 0；克隆出的新工作区按 §2.7 的起点规则重新计数。

#### 归档线程（ARCn 角色）

- **实例级后台角色**（形态照 §11.7 的写线程与检查点）：按工作区维护**待归档队列**
  （内存；启动时从控制文件重建）。
- **每工作区同时至多一个归档在进行**——序列号天生有序，不需要并行。
- **归档文件 = 组的逐字节副本**：组本身即线性记录流（§11.5.1）、页校验自证；文件头 32B：
  `magic 4B │ workspace_ref 8B │ 日志序列号 4B │ 起始 LSN 6B │ 字节数 4B │ crc32 4B │ 保留 2B`。
- **命名 `<序列号 10 位>.arc`**——按日志序列命名，REQ-OPS-013 的连续性校验据此。
- **原子发布**：写 `.tmp` → fsync → rename → **之后才**更新控制文件（`DONE` + 归档记录的最后序列号）。
  崩溃窗口重置：`IN_FLIGHT` 重启后回退 `NEEDED` 重做；目标已存在且文件头校验通过则直接标 `DONE`（幂等）。
- **清理**按保留双条件由后台执行（REQ-OPS-013）。
- **成员（2 份）**：LGWR 写组时两成员同写；某成员写失败 → 标 `STALE`
  （各成员文件头页，§5.11）+ 告警 + 用剩余成员继续；后台从完好成员重建。

#### 等待与告警（写者侧，按 §14 第 33 项的三档归位）

短时滞后由"提频 → 节流辖区写者"消化；**到"无组可切"才暂停**，按缺的条件分两类：

| 缺的条件 | 暂停原因（诊断标识） | 对应 Oracle 等待 |
| --- | --- | --- |
| 组已写满且未归档 | 日志切换等待**归档** | `log file switch (archiving needed)` |
| 已归档（或非归档模式）但检查点未越过 | 日志切换等待**检查点** | `log file switch (checkpoint incomplete)` |

- **暂停 + 告警**：诊断日志与管理面**双通道**——证据包里就有"目标满导致挂起、
  且告警缺失"的现网案例，告警必须可靠。
- **不提供"跳过归档"的开关**（REQ-OPS-013 的显式排除）——那等于自己剪断日志链。
- 归档目标不可写：归档侧重试 + 上报积压；积压到"无组可切"，写者按上表暂停——**不停机、不丢链**。

#### 与崩溃恢复、PITR 的关系

- **归档不在崩溃恢复路径上**：崩溃恢复只读**在线组**；复用判据保证在线组始终覆盖
  "检查点以来"的全部 redo（§11.8 的独立恢复同样成立）。
- 归档服务**离线路径**：PITR、在线备份、备库。做这些之前**强制切换并等待当前组归档完成**
  （§2.5 的一致性要求）——管理操作，可等待。
- 恢复 / PITR 前按序列号校验归档链**无缺口**；有缺口 → 拒绝并指认缺口点（REQ-OPS-013）。

#### 运行中增加组数

组数**只增不减**（§2.4：运行后不改变已有组大小）：管理操作创建新成员文件 →
控制文件 Redo 条目加一项（`UNUSED`，序列号 0）→ 立即可参与复用。
减少组数与改组大小在 V1.0 都不提供。

#### 归档模式的取值时机

归档模式在**创建工作区时指定**（默认**开启**——PITR 与备份依赖它）；V1.0 不提供运行中切换。
