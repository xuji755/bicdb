## 8 表类型与存储选项

### 8.1 选项

```text
transactional : bool                    是否参与显式多语句事务
logging       : full | redo_only | none
update_mode   : in_place | append_only
retention     : none | <时长>           TTL
version_keep  : none | <个数>           版本保留数，超出自动淘汰
cleanup       : none | segment_drop | row_delete
embed         : none | async            向量自动派生
                                        ——**确定性的派生计算**，可重建；
                                          与非确定性的语义判断（库内不做）分界见 `spec/MEM.md`
```

### 8.2 五种表

| 表类型 | transactional | logging | update_mode | 其他 |
| --- | --- | --- | --- | --- |
| 普通关系表 | ✅ | full | in_place | — |
| 配置表 | ❌ | redo_only | append_only | `version_keep`，插入时内联淘汰 |
| 会话表 | ❌ | **none** | append_only | TTL + **整段丢弃** |
| 图数据 | ✅ | full | in_place | 边按 `src` 聚簇；顶点表置 `table_opts.graph = 1`（§14 第 58 项） |
| 记忆表 | ❌ | redo_only | append_only | `version_keep` |

> `cleanup = segment_drop` 的执行机制见 §4.7（段的删除、失效与回收）。

#### 会话信息存哪：三层，判据是"事务 / 检索 / 大小"

**"Agent 的会话与工具输出存表还是存外部"——答案是分层** ✓：

| 内容 | 存哪 | 判据 |
| --- | --- | --- |
| **对话消息**（文本） | **会话表** ✓ | 要**可检索**（"上次我们怎么解决的"）、要有界 |
| — | — | **每一行带 `agent_id` 与 `session_id`** ✗✓——见下 |
| **工具输出的引用** | **记忆表的 `task_checkpoint`** ✓ | 小而关键——**恢复要靠它**（`REQ-MEM-001`） |
| **工具输出本身 / 中间产物** | **外部资产（`ASSET_REF`）** ✓ | **大、不需检索** |
| **提炼出的记忆** | **记忆表** ✓ | 见 `spec/MEM.md` |

**判据是三条，要同时问**：
**① 要不要参与事务与可见性？② 要不要被检索？③ 多大？**
——①②为"是"就进表 ✓；都否且大，进外部资产 ✓。

**最硬的理由是 redo**：**进表的每一字节都进 `redo`** ✗——
而 §8.3 已算过："`logging = none` 省下的**主要不是写日志的 CPU**，
而是**提交时的 `fsync` 等待**" ✓✓。
**一次 10MB 的工具输出进库，就是"每次提交都要等那 10MB"** ✗✗。

**第二条理由**：`REQ-TXN-018` 已写明外部资产"**不得冒充与页日志同一原子存储**" ✓——
**它是刻意不参与事务的** ✓。

#### 分层靠"恢复不依赖会话原文"而闭合

**会话表是 `logging = none`**（§8.3："追加型表的撕裂页只出现在追加前沿，
损失限于最近少量记录"）✗——于是**对话原文可丢** ✓。
**而恢复不靠它** ✓✓：

> **恢复靠 `task_checkpoint`**（记忆表，`logging = redo_only`，**有日志**）✓——
> 这正是 `REQ-MEM-001` 要求"**恢复游标**"的原因 ✓。
> **两件不同的事，不同的持久化保证**：**对话原文是可丢的上下文，
> 检查点是不可丢的恢复点** ✓。

#### 会话行必须带归属：`agent_id` 与 `session_id`

**这是端到端走查走出来的** ✗✓——**原先会话表只有一个"表"，没有维度** ✗：

| 缺什么 | 后果 |
| --- | --- |
| **`agent_id`** | **提取进程无法知道这段会话属于哪个 Agent** ✗ |
| **`session_id`** | 无法"把这次会话的对话拿出来" ✗ |

**第一行的后果最重** ✗✓：提取的产物是**记忆** ✓，而记忆**要带 `agent_id`** ✓
（否则检索时的 agent 过滤无从谈起，`MEM` 的 `agent_id` 就白定义了 ✗）。
**没有这个字段，提取进程只能从内容里猜归属** ✗——**而那是策略，不该由库猜** ✓✓。

**为什么每一行都带，而不是另立一张会话表头** ✗✓：
会话表是 **`append_only`** ✓——**每行自描述**才与追加式写入相容 ✓
（另立表头意味着"写会话时还要改另一张表"，那会引入跨表的顺序问题 ✗）。

**而"位置"也必须稳定** ✗：`source_record` 要指向"读过的会话位置" ✓——
**不能用 ROWID**（段会被 `segment_drop` 丢掉，指向它的 ROWID 就悬空了 ✗✓）。
**用 `(agent_id, session_id, 序号)` 一类** ✓——**§7 早定了"ROWID 不得作为对外持久引用"** ✓，
**这里是那条规定的又一个用例** ✓。

**会话表带 `embed async`** ✓ ⟹ **对话历史是可向量检索的** ✓——
**"上次我们怎么解决这个问题"是 Agent 的常见用法** ✓，
**而这正是它必须进表的原因** ✗✓（外部文件检索不了 ✗）。

> 与 `REQ-RET-001` 的关系：那条列的全文检索五类面向里**没有对话** ✗——
> **不是矛盾**（它没说"仅限"），但**对话历史要可检索应当在 `RET` 域写明** ✓。

#### 会话 → 记忆的自动提取：库不做的、库要提供的

**会话表里的数据由一个后台进程提取为记忆** ✓——
**它是引擎的一个可选后台任务**（详见 §11.7 的"另一类后台"）✓：

| | CKPT / 写线程 | **提取进程** |
| --- | --- | --- |
| 属于 | **存储层** ✓ | **语义层** ✗ |
| 会不会跑 | 总是在（有脏页就跑）✓ | **配了才启，启不了就不启** ✗ |
| 调模型 | 不调 ✓ | **调** ✗ |
| **共同点** | **每工作区一份；可重启；只产出派生数据** ✓✓ | 同 ✓ |

**"库外进程"曾被考虑过，但被否掉了** ✗：它**很难标准化**——
每个使用方都要自己写一遍提取逻辑 ✓，**而"底座要友好"正要求它开箱可用** ✓。

**而引擎提供的是"提取进程"这个能力** ✓：**"提取得对不对、提什么"在提示词与配置里** ✗——
**那才是策略，而它仍在调用方手里** ✓✓。

**库为它提供三样东西** ✓：

| 库提供 | 说明 |
| --- | --- |
| **会话的增量读** | 按**水位**读新会话（会话表是 `append_only`）✓ |
| **产出侧的幂等与不回退** | 与其他派生一样（`REQ-RET-014`）✓ |
| **`source_record`** | 提取产出的记忆**指向它读过的会话位置** ✓——于是可追溯 ✓ |

#### 两处必须写明的后果

**① "提取还没跑就崩" ⟹ 那段会话永远不进记忆** ✗

```text
会话写入 → 【崩】 → 提取进程还没读到这里 → 会话尾部丢失
        → 这段内容**永远不会进入记忆**
```

**这不是缺陷，是那个取舍的具体形态** ✓——
"丢失不会引起大问题"**在已经提取过的部分成立** ✓，
**而未提取的那一段是真的没了** ✓。写明它，才知道 `logging = none` 交出了什么。

**② 保留期必须长于提取的最坏延迟** ✗✓

会话表的 `cleanup = segment_drop` 是**整段丢弃**（§4.3：TTL 退化为整段操作）——
**若一段会话在提取之前就被丢，那段内容同样永远进不了记忆** ✗✗。

> **这是一条硬约束：`保留期 > 提取的最坏延迟`** ✓——
> **而两者分属不同域**（TTL 在存储侧，提取延迟在 agent 侧）✗，
> **所以必须写在明处，否则会各自调参调到互相打架** ✓。

**③ 水位不能存在会话表里** ✗✓

提取进程要知道"读到哪了"，**而水位本身不能跟会话表一起丢** ✗——
**否则重启后不知道读到哪** ✓。

> **水位必须存在有日志的一侧**（记忆表或 `public`）✓——
> 这是通用规则：**可丢的数据不能承载不可丢的进度** ✓。

### 8.3 不记日志的边界（关键）

| 对象 | 产生 redo | 理由 |
| --- | --- | --- |
| **数据页** | ❌ | 追加型表的撕裂页只出现在**追加前沿**，损失限于最近少量记录 |
| **页分配位图、数据字典、段头页** | ✅ **必须** | 这类元数据损坏导致**整个表空间不可用**，不是"丢少量数据" |

> **注意"受保护"不等于"产生 redo"**——原先把控制文件与引导页也列在这一行是**错的**，
> 它们各有自己的机制（见 §5.11 的"各页类型的 redo 参与"表）。

### 8.4 追加型与原地更新型共用同一套页格式

`update_mode = append_only` 的表**仍使用同一套数据页格式**，只是空间管理策略不同（见 §4.3）。**不引入第二套页格式**——这是"一个引擎"的底线。
