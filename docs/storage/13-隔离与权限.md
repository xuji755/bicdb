## 13 隔离与权限：存储层保证什么，不保证什么

§12 讲的是"读一行时发生什么"。这一节讲的是"**读错了会怎样、我们靠什么不让它发生**"。

### 13.1 先把边界划清：存储层挡"误"，上层挡"意"

隔离由**多层**共同提供，而**存储层只承担其中一部分**。
把不属于存储层的责任写进存储层，是"看起来安全、实际不安全"的典型来源。

**一条判据，但要分两段说**：

> **页 / 段 / 文件这一层**的机制全是**完整性检查**——它们检出**错误**
> （放错了文件、读错了块、缓冲池键碰撞）。
> 这一层里**没有一条能挡"有意的越权"**，因为它里面**没有"用户"这个概念**。
>
> **但整条读路径上有一个例外，而且必须有这个例外**：
> **`public` 的过滤层**（§13.5）——它就在读路径上，而且它**就是访问控制**，
> 不是完整性检查。**它靠的是"会话所属工作区"这个概念——存储层本来就有它**（§7.2）。

**所以"存储层"不能被当成一个整体来看**：

| | 挡什么 |
| --- | --- |
| 页 / 段 / 文件层 | **误**——放错、读错、碰撞 |
| **`public` 的过滤层** | **意**——谁能看见哪些行（§13.5） |
| 引擎层的授权 | **意**——谁能对哪些对象做什么 |

**授权与过滤挡"意"；页/段/文件挡"误"。**
把两者混着说，就会得出"我们已经有四层隔离了"（§13.2）或"过滤只能在上层"（§13.4）
这类错误结论——**两个方向都错。**

**本节只划边界，不重复规格。** 每一处"上层该做什么"，都在 **ISO 规格域**
（`spec/ISO.md`）有对应条目——授权模型、三档身份、以及那张"刻意不提供的原语"清单。

### 13.2 五层防线，各自挡什么

| 层 | 挡什么 | **挡不住什么** |
| --- | --- | --- |
| **进程 / OS 隔离** | 一个工作区的进程打不开另一个的文件——**结构性防线** | 同一进程内的逻辑错误 |
| **文件层** | 共享、硬链接、跨用户去重（§2.1：独立文件、不共享） | 有意的越权 |
| **页层** | **跨区误读**——放错文件、读错块（`workspace_ref`，§7.2） | 有意的越权 |
| **缓存层** | 缓冲池键碰撞（不同工作区的 ROWID 会重复，故键**必须含工作区标识**） | 有意的越权 |
| **`public` 的过滤层与写侧** | 读：按会话所属工作区过滤行（§13.5）。写：**直接 DML 一律拒绝**，只有标准接口（§13.6）。——**这是访问控制，不是防误** | 用户**自己**工作区内的越权 |
| **引擎层（授权）** | 有意的越权 | —— |

**前四层全是"误"，后两层才是"意"。** 把它们混着说，就会得出
"我们已经有四层隔离了"这种错误结论——**四层都是防错的，不是防人的。**

### 13.3 一个工作区打不开另一个

三道防线，强度依次递减，**必须按这个顺序讲**：

| 防线 | 性质 |
| --- | --- |
| **进程 / OS 隔离** | **结构性**——不是"我们检查了"，而是"它们本就不在同一个进程里" |
| **路径检查**（REQ-ISO-007 / 008） | 拒绝路径穿越、符号链接、检查与使用间竞态；根目录名**不经用户输入** |
| **`workspace_ref`**（§7.2） | **纵深防御与一致性检查**——把"静默的跨区数据串读"降级为"可检出的错误" |

> **`workspace_ref` 不是密码学边界**（§7.2 已划定）：
> 它实际防的是隔离实现的 **bug** 与运维**误操作**，不是有意的攻击。
> **不应据此宣称隔离由它保证。**

### 13.4 `public`：两条相反的需求，用一个专用层解决

`public` 被两条需求指着，方向**相反**：

| 需求 | 要求 |
| --- | --- |
| **REQ-ISO-004** | **所有用户可读** public 的公共数据 |
| **REQ-ISO-006** | 普通会话**不能判断**别的工作区的对象是否存在——管理元数据**整体不可见**（§2.11） |

**于是同一份文件既要人人可读，又要对普通会话隐藏其中一部分。**

**解法不是"在每处读取点各查一次"，而是给它一个专用过滤层。** 见下节。

### 13.5 `public` 的对外读取：一个专用过滤层

```text
                          ┌──────────────────┐
 管理路径（admin） ───────▶│                  │──▶  public 的全部数据
                          │  public 的过滤层  │
 普通会话 ────────────────▶│                  │──▶  只有本会话可见的部分
                          └──────────────────┘
```

**"一层"与"每处检查一次"的区别，就是"不可绕过"的全部来源**：

| | 每处检查（错） | **一个专用层（对）** |
| --- | --- | --- |
| 实现 | 分散在若干读取点 | **一处** |
| 新增读取路径 | 要记得加检查——**忘了就是漏洞** | **必须接进这一层，否则读不到 public** |
| 审计 / 统计 / 诊断 | 各自为政，容易漏 | **没有豁免** |

**所以它的强度不来自"检查得多严"，而来自"没有第二条路"。** 这与 §13.6
"用不提供实现禁止"是同一条原则的两种用法。

#### 层内的两个决定

| 决定 | 依据 |
| --- | --- |
| **表级**：这张表对本会话是否可见 | REQ-ISO-006 要求"**与不存在不可区分**"——所以不返回"无权限"，而是**在名字解析上就当作不存在** |
| **行级**：这一行对本会话是否可见 | **行带归属**：`0` = 全局可读，`<工作区号>` = 只有该工作区的会话可见 |

```text
行的归属列 owner：
   0              →  全局可读，所有会话可见
   <工作区号>      →  只有该工作区的会话可见
会话的判据：本会话所属工作区的号
```

**注意两个决定落在不同的位置**：表级要报"不存在"，那是**名字解析**的语义；
行级要"看不见的行不进入扫描"，那是**扫描范围**的语义。
**过滤层横跨这两处——这正是它必须是一个独立层次、而不是一处检查的原因。**

#### 行级过滤："不可绕过"的准确含义

**它指过滤必须是扫描范围的一部分，而不是返回后的剔除。** 这个区别是设计的关键：

| | 事后剔除（错） | **扫描范围的一部分（对）** |
| --- | --- | --- |
| 代价 | 索引扫描读入全部行再丢弃 | **不可见的行根本不进入扫描** |
| **泄露** | **暴露"存在多少不可见的行"**——违反 REQ-ISO-006 的"不得泄露精确规模" | 无 |
| 索引 | 索引项仍参与扫描 | **归属列是索引键的一部分** |

**所以归属列必须能进索引键、扫描边界由它限定。** 这不是性能优化——
**事后剔除即使结果正确，也仍然泄露规模**。

#### 六个旁路，逐一封堵

| 旁路 | 封堵 |
| --- | --- |
| 堆扫描 | 走过滤层 |
| **索引扫描** | **同一条路径**；归属列进索引键，**不靠回表过滤** |
| `SELECT` / `UPDATE` / `DELETE` | **不提供按语句类型分别开关**——凡读此表一律过滤 |
| 写入的目标行 | 写入的行必须满足"归属 = 自己或全局"（对应 Oracle VPD 的 `update_check`） |
| 统计 / 采样 / 诊断 | 走**同一条扫描路径**，没有第二条 |
| 内部接口 | **不提供"关闭过滤"的开关**——连管理路径也不给 |

> **最后一行是与 Oracle VPD 的一处有意差异**：`DBMS_RLS` 有 `enable` 参数，
> 关掉即绕过。**我们不设这个参数。**
>
> 需要看全部的行，走**另一条明确命名的管理路径**，而不是"把过滤关掉"。
> **"关掉"是隐式的——它在调用点看不出来；"换一条路径"是显式的——它在调用点看得见。**

#### 与 §12 的可见性是两件事

| | §12 的可见性 | **本节的过滤** |
| --- | --- | --- |
| 判据 | **快照**（提交序号）——"哪个版本" | **工作区归属**——"谁可以看" |
| 属于 | 多版本一致性 | 访问控制 |
| 生效点 | 行 → ITL → `commit_seq` vs S | 扫描范围（索引键）与名字解析 |

**两者在同一次扫描里同时生效，但彼此独立**：先由归属限定扫描范围，
再由快照决定每个可见行给出哪个版本。
**不要把过滤写成"可见性的一种"**——那会把访问控制混进 MVCC，两边的推理都会失真。

#### 归属列占多宽

**2 字节**——它存的是**工作区号**，工作区号在 `public` 里分配（`ws$` 增一列）。

| 不用什么 | 为什么 |
| --- | --- |
| `workspace_id`（48 位序列值） | 每行 6 字节的访问控制开销不可接受 |
| `workspace_ref`（8B） | 它是**哈希**，为"检出跨区误读"而设计；这里要的是**可排序、可进索引键的紧凑序号** |

**工作区号永不复用**——与对象号同一条纪律（§3.1.3）。
复用会让**旧行归属到另一个工作区**——那是访问控制错误，不是数据错误。

#### 两个必须裁决的点

**① admin 读全部行，算不算 REQ-ISO-003 禁止的"代理读取"？**

**不算。** 那些行**在 `public` 里**，而 public 是所有人的公共区域（REQ-ISO-004）——
不是某个用户的工作区。**代理读取针对的是"读进别人的工作区"**，
而这里读的是公共区域内的数据。**这个判断需要写明，否则会被反复质疑。**

**② 这些行由谁写？** —— **由 `public` 的标准接口写**（§13.6）。
普通会话的**直接 DML 一律被拒**；接口是唯一入口，**归属由接口填、不由调用方指定**。
**发布流程本身尚未展开**（数据模型 / API 规格域），
**但归属列、过滤层与写侧拒绝必须先立**——它们是那条流能否安全实现的前提。

#### 落点清单（待冻结项 57 · 读侧——已定）

| 项 | 定案 |
| --- | --- |
| **归属列** | **`owner`**——**2 字节整数**、**隐藏系统列、行内第一列**（`col# = 0`，`col$` 带隐藏标志；`SELECT *` 不展开、不可显式引用）。取值照上图：**0 = 全局**，**1..65535 = 工作区号**。**它是工作区号，不是用户属主**——与 `ISO` 的属主概念无关 ✓ |
| **工作区号的分配** | `ws$` 增列 **`ws#`**（2 字节，唯一索引）；分配器 = **`public` 的 `seq$`**（序列名 `workspace_no`）——**从 1 起**（0 留给全局；与 ID 的从 1 起、0 保留同一纪律）、**永不复用**（与 `ws$` 插行同事务，天然成立）、**65535 耗尽 → 拒绝建区、不回绕**（照对象号政策）。**2 字节是刻意的**：宽一档就要重排全部过滤表的行格式 ✗ |
| **表级开关** | **`tab$` 增列 `shared`**（布尔）：1 = 公共数据表——行级过滤 + 只读经标准接口写。**管理元数据表的不可见不由它表达**——那是名字解析层的**管理表清单**（`user$` / `ws$` / `fs$` / 固定表 `file$`） |
| **归属列进索引键的方式** | **公共数据表上创建的每个索引，引擎自动以 `owner` 作首列**（隐式前缀；不可关闭、无需声明）✗✓——于是过滤条件 `owner ∈ {0, 本区号}` **永远落在键范围里**（一段前缀相等扫描），而不是回表后剔除 ✓。B+Tree、表达式索引、图属性索引**同一规则** |

### 13.6 `public` 的写入：只有标准接口一条路

**读有一个过滤层（§13.5），写有一个镜像**：

| | 读 | **写** |
| --- | --- | --- |
| 普通会话 | 经过滤层，只见本会话可见的行 | **不提供**——直接 `INSERT` / `UPDATE` / `DELETE` **一律拒绝** |
| 写入途径 | —— | **只有一条：`public` 提供的标准接口** |

**工作区是可以往 `public` 写的**，但**必须通过标准接口**，不能直接 DML。
**安全控制在接口内做**；存储层的责任是**让"直接写"这条路不存在**。

> **需求文字里有一处容易混**：REQ-ISO-004 的验收写着"普通用户对 public 的写入被拒绝"。
> **被拒的是"直接写"，不是"写"本身**——否则工作区就永远无法向公共区域贡献任何东西，
> 而 §2.13 的"public 发布审计"正是为这条流准备的。**两句话要一起读。**

#### 为什么"拒绝 DML + 只留接口"比"给表写权限"强

| | 给表写权限 | **拒绝 DML，只留接口** |
| --- | --- | --- |
| 控制的粒度 | 表 / 行 | **一次操作的完整语义** |
| 能约束什么 | 行可见性 | **归属 + 行可见性 + 字段合法性 + 状态机 + 审计** |
| 绕过面 | 每一处 DML 都要过滤对 | **没有 DML 可绕** |

**"一次操作的完整语义"是关键。** 发布不是"插入一行"，它是
"**以我的工作区为归属，把一个对象发布到公共区域**"——
**归属由接口决定，不由调用方指定**。

若允许直接 `INSERT`，调用方就能把归属填成**别人的工作区**（或"全局"），
**而那正是过滤层要防的事**——**写侧的一个疏漏，会让读侧整套过滤失效。**

#### 存储层的责任边界

| 谁 | 做什么 |
| --- | --- |
| **存储层** | **拒绝普通会话对 `public` 的任何 DML**——一条都不放行。并保证**没有第二条写路径**：§3.1.2 已定 DDL 与 DML 共用同一套事务，故不存在"绕过事务直接改字典"的旁路 |
| **标准接口** | 身份、**归属（由接口填，不由调用方指定）**、字段与状态机校验、审计 |

> **接口在哪一层？** **不是存储过程**——V1.0 没有 PL/SQL（REQ-TYP-009）。
> 所以"标准接口"是**引擎内的受控操作**，由 API 层调用，**不是用户可以自由调用的 SQL**。
>
> **这带来一个额外的好处**：接口的入口是**枚举的**（有一份清单），
> 而"表上的 DML 权限"不是——**枚举的入口可以被审计，一张权限矩阵不能。**

#### 与读侧同一条原则

读侧的强度来自"**没有第二条读路径**"，写侧来自"**没有第二条写路径**"。
两者都是下节那条原则的应用：**能被绕过的控制不是控制。**

#### 标准接口清单（待冻结项 57 · 写侧——已定）

**接口是引擎内的受控操作（不是 SQL、不是存储过程），V1.0 枚举为三个** ✗✓：

| 接口 | 语义 | 校验 | 归属 |
| --- | --- | --- | --- |
| **`publish`** | 把一个对象发布到公共：`(表, 行键, 内容, scope)` | 身份、字段合法性（照表定义）、幂等键（`API`） | **由接口填**——`scope = global → owner# = 0`；`scope = workspace → owner# = 调用方自己的工作区号`。**不允许指定别的区** ✗✓ |
| **`amend`** | 修改自己发布的公共行（内容 / 范围） | 同上 + **新归属 ∈ {0, 自己的区}** | 同左（不能改成别人的 ✗） |
| **`unpublish`** | 撤回：**删除该行**（留痕在发布审计 ✓） | 幂等（重复撤回成功 ✓） | — |

**每一条都做四件事**：身份、**归属填充**、**状态机校验**（发布 / 撤回的合法转换，留痕照 `CONV` §6）、**发布审计**（`OPS` REQ-OPS-004 的那条流 ✓）。

**拒绝直接 DML 的落点**：**绑定期**（`SQL` REQ-SQL-003 的第 5 步写目标检查）——
非 admin 会话对 `shared = 1` 表（及管理元数据表）的 `INSERT` / `UPDATE` / `DELETE`，
**在解析目标时就拒绝**（无写入口类错误）；**读不受影响** ✓。
**且没有第二处**——DML 只有这一条解析路径 ✓（不提供入口的又一次应用）。

> **admin 不走这条线**：它是 `public` 的属主，直接 DML 照常 ✓——
> 拒绝直接 DML 针对的是**普通会话**，不是对公共区域的写入本身。

### 13.7 用"不提供"实现禁止

**成熟产品都提供了跨库通道**：

| | 通道 |
| --- | --- |
| **Oracle** | `CONTAINERS()`（从 Root 跨所有 PDB 查询）、**PDB 间的 Database Link**、Proxy PDB |
| **PostgreSQL** | `dblink` 扩展、外部数据包装器（FDW） |

**我们不提供。**

这不是"少做"，而是**"禁止"的两种实现里更强的那一种**：

| 实现方式 | 强度 |
| --- | --- |
| **拒绝请求** | 依赖**每一次**都拒绝正确——**一处漏判即越权** |
| **不提供入口** | **没有可漏判的东西** |

于是下面 §13.9 那张清单**本身就是安全机制**，不是功能缺口。
**它必须被当作需求来维护**：任何一次"顺手加个跨工作区的便利接口"，
都在拆掉这一层——而这种改动在代码评审里看起来只是**方便**。

### 13.8 与成熟产品的对照

| | Oracle PDB | PostgreSQL | **我们** |
| --- | --- | --- | --- |
| 隔离粒度 | PDB（共享实例） | database（共享实例） | **工作区** |
| 跨库查询 | **提供**（`CONTAINERS()` / DB Link） | **提供**（dblink / FDW） | **不提供**（REQ-ISO-003） |
| 管理元数据的位置 | CDB root 的**共享字典** | **独立表空间** `pg_global`（`$PGDATA/global`，路径特殊处理） | **一个普通工作区 `public`** |
| 每库 undo | 12.2 起 **local undo** | 无（全实例一套 WAL） | **每工作区 file 1** |
| 克隆 | `CREATE PLUGGABLE DATABASE ... FROM` | `CREATE DATABASE ... TEMPLATE` | **reflink**（§2.7） |
| 人人可读的共享区 | 无直接对应 | 无直接对应 | **`public`**（REQ-ISO-004） |
| **行级过滤** | **VPD / FGAC**：策略绑在**表**上、自动重写查询附加谓词、可分别覆盖语句类型、**有 `enable` 开关可关掉** | **RLS**：`CREATE POLICY` 定义策略，**有 `BYPASSRLS` 属性可绕过** | **一个专用过滤层**（§13.5）——**不设开关**，要看全部走另一条明确命名的管理路径 |

**三处我们与两家都不同，各有理由**：

| 不同 | 理由 |
| --- | --- |
| **管理元数据放在一个普通工作区里**，而不是共享全局结构 | **可就地查询、事务、建索引**（§2.11）。代价是"不可见"只能靠上层过滤（§13.4）——**这是拿存储层的简单换授权层的责任**，是有意的 |
| **不提供跨库通道** | REQ-ISO-003 禁止授权与代理读取。**用不提供代替拒绝**（§13.7） |
| **`public` 作为人人可读的共享区** | 两家都没有直接对应——**它是本设计特有的一层**（REQ-ISO-004），带来 §13.4 那个两难，由 §13.5 的专用层解决 |

### 13.9 本设计刻意不提供的原语

**这张表是安全机制的一部分，不是待办清单。** 每一项"没有"都是有意的：

| 不提供 | 为什么 |
| --- | --- |
| **跨工作区的句柄 / 事务 / 游标** | REQ-ISO-003：无代理读取、无跨工作区事务（§3 排除项） |
| **跨工作区的数据文件共享**（硬链接、reflink 去重） | 共享会让"删自己的数据"影响别人；且两个工作区的 `workspace_ref` 校验会互相打架 |
| **工作区内的"用户"概念** | 一个工作区一个属主（RES §2.11）；多用户多权限是**上层**的事，存储层只认工作区 |
| **绕过事务修改字典的后门** | §3.1.2：DDL 与 DML 共用同一套事务。**没有后门，上层的拒绝才是不可绕过的** |
| **对 `public` 的直接 `INSERT` / `UPDATE` / `DELETE`** | 写入只能走标准接口（§13.6）。**归属必须由接口填**——允许直接写就等于让调用方自己指定"这行归谁"，**读侧整套过滤会被写侧的一个疏漏作废** |
| **静态加密 / 密钥管理** | `workspace_ref` 不加密钥的理由见 §7.2。**加密属于平台层**，存储层不假装提供 |
| **"强制打开任意工作区"的存储层接口** | §11.8 的强制打开是**管理操作**，有明确的后果声明与审计；**它不是存储层随时可用的开关** |

> **维护这张表的方式**：任何新增能力，先问"**它会不会给上层制造一个必须拒绝的入口**"。
> 会，就先证明拒绝不可绕过，再决定加不加。
