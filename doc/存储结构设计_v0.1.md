## 1 总览

```text
实例
├── 全局控制文件（默认 2 份）         ← 数据库管控范围内的文件清单
│     全库结构：有哪些工作区、各工作区的文件
│     低频更新；**不在提交关键路径上**
│
└── 每个工作区（互不干扰）
     ├── control/                    工作区控制文件（默认 2 份）
     │     control01.ctl             该工作区的检查点、redo 序列号、文件清单
     │     control02.ctl             ← 该工作区的**恢复锚点**
     │
     ├── wal/                        redo（默认见 §3）
     │     ...
     │
     └── data/                       表空间文件
           <ws>_meta      file 0     表空间元数据 + bootstrap
           <ws>_undo      file 1     Undo
           <ws>_temp      file 2     临时空间
           <ws>_data_01   file 3+    数据段
```

### 分层职责

| 层 | 承载 | 变更频率 | 是否恢复锚点 |
| --- | --- | --- | --- |
| 全局控制文件 | 数据库管控的文件清单、工作区注册 | 极低（建/删工作区、加数据文件） | 否 |
| 工作区控制文件 | 该工作区的文件清单、检查点、redo 序列号、格式版本 | 高（日志切换时） | **是** |
| 表空间 file 0 | 该表空间的段目录、对象目录、文件角色表、bootstrap | 中 | 否 |
| 表空间 file 1..N | Undo / 临时 / 数据段 | 高 | 否 |

## 2 两级控制文件

### 2.1 为什么控制文件必须独立于表空间

**恢复时要先知道"该打开哪些文件、检查点在哪"，然后才能打开数据文件。** 如果控制信息藏在 file 0 内，就形成循环依赖（要先打开 file 0 才知道要打开 file 0）。Oracle 把控制文件排除在表空间之外，根因在此。

### 2.2 工作区控制文件

- **默认 2 份副本**，内容相同。
- 内容：该工作区的文件清单（含各文件角色与路径）、检查点位置、redo 序列号、格式版本、库标识。
- **在日志切换时更新**（与 Oracle 一致）。
- 是该工作区**唯一的恢复锚点**：任何恢复流程从此文件开始。

### 2.3 全局控制文件

- **默认 2 份副本**。
- 内容：**数据库管控范围内的文件清单**——有哪些工作区、每个工作区的根目录与文件构成。
- **只存结构信息，不存私有正文、向量或文件内容**（总体方案 §4 对平台控制目录的约束）。
- **不是恢复锚点**：丢失后可由各工作区自描述 + 注册信息重建。
- **绝不在提交关键路径上**：工作区的每次提交不得触碰全局控制文件，否则会造成跨工作区耦合与写热点。

> 两级的分界原则是**变更频率**：工作区的检查点/日志序列号按每次日志切换变化，必须留在本区；全库文件清单只在建/删工作区或新增数据文件时变化，可以集中在全局。

## 3 WAL（redo）

### 3.1 必须每工作区独立

**redo 记录包含用户数据本身**（redo 记录是行级修改的描述，重放即恢复数据）。因此：

- 跨用户共享 redo = A 的数据直接出现在 B 能读到的文件里，且恢复时可能被应用。
- redo **必须每工作区一份**，与控制文件一同放在工作区目录下。

### 3.2 为什么 redo 不放进表空间的文件编号

| 维度 | 数据文件 | redo |
| --- | --- | --- |
| 访问模式 | 随机访问、持续增长 | **顺序追加、循环复用** |
| 冗余方式 | 不需要内部冗余 | **多成员镜像** |
| 生命周期 | 不覆盖 | **循环覆盖** |

Oracle 同样把 redo 排除在表空间之外。设计文档 §4 已将每工作区的 `wal` 目录单列，与此一致。

### 3.3 结构（Oracle 式）

- **日志组（group）**：逻辑分组，循环复用。**至少 2 组**，否则写满后无处可切。
- **成员（member）**：组内物理副本，**大小必须完全一致**，应在不同磁盘。
- **写入语义**：同时写组内所有成员；某成员写失败则继续写其他成员并记录错误。
- **日志切换**：组写满或强制切换 → 日志序列号递增 → **更新工作区控制文件**。

### 3.4 归档：V1.0 不做

归档服务于时间点恢复（PITR），总体方案 §21 明确"在线备份与 WAL 归档另立项"。因此 **redo 组循环复用即可，不做归档**。

## 4 表空间与文件编号约定

采用**固定文件角色**：同一 tablespace 内，文件号即角色。

| 文件号 | 角色 | 说明 |
| --- | --- | --- |
| **file 0** | 元数据 | 表空间头、段目录、对象目录、文件角色表、bootstrap。**不承载用户数据行** |
| **file 1** | Undo | 该工作区事务的 Undo |
| **file 2** | Temp | 排序 / 哈希 / 分词溢出 |
| **file 3..N** | 数据 | 数据段，**可按需动态新增** |

**该约定对 system 与 public 表空间同样适用**，规则统一。

### 4.1 这个约定带来的三个好处

1. **备份与恢复可按角色定策略**——file 2（temp）不进备份；文件角色固定，规则无需查目录。
2. **ROWID 寻址空间干净**——用户数据**只可能在 file ≥ 3**，ROWID 指向的行不可能落在元数据或 undo/temp 中，消掉一整类边界情况。
3. **配额可按角色分别设**——undo 与 temp 各有额度，不与数据互相挤占。

### 4.2 数据文件动态新增

- file 3 之后可按需新增（file 4、5…）。
- 新增是**结构变更**，必须受 WAL 保护（REQ-STO-011），且需更新**本工作区控制文件**与**全局控制文件**的文件清单。
- 由于是低频事件，更新全局控制文件可接受。
- **影响 ROWID 的 `file_id` 位宽**（见 §8 待确认）。

### 4.3 关于 file 0/1/2 的初始开销

每个 tablespace 固定有 3 个非数据文件。对只有几十张表的小用户，固定开销占比可能可观。建议：

- file 1（undo）、file 2（temp）**初始极小、按需增长**；
- file 2 可为**零长度占位**，首次实际使用时才分配。

（待确认，见 §8）

## 5 file 0 的内容

### 5.1 职责（已收窄）

控制文件独立后，file 0 **只负责表空间内的逻辑结构**，不再承担物理层的文件清单：

| 内容 | 说明 |
| --- | --- |
| 表空间头 | 标识、格式版本、状态 |
| **文件角色表** | 本表空间各文件的角色、大小、状态（1=undo、2=temp、3+=data） |
| **段目录** | 本表空间内有哪些段、各自占用哪些区 |
| **对象目录** | 本表空间内有哪些对象（表/索引/图/向量集合） |
| **bootstrap 数据** | 自举数据，见 §5.2 |
| 版本与校验 | 格式版本、校验信息 |

### 5.2 bootstrap（参考 Oracle `bootstrap$`）

**问题**：要查表得先知道表结构，但表结构存在字典表里——先有鸡还是先有蛋。

**Oracle 的解法**（知识库实测）：`bootstrap$` 的**位置是硬编码的**——创建时同时指定段头位置（`file 1 block 377`）、初始区大小（50K）、对象号（objno 56）。内核**不依赖任何字典**就知道去哪读它；读出的 `sql_text` 是创建字典表结构的语句，据此孵化出 `c_obj#`、`tab$` 等核心字典表。

**我们的设计**：

- bootstrap 数据放在 **file 0 内固定的块偏移**（紧跟引导块之后的连续若干块），**内核硬编码知道其位置**，不依赖任何目录结构去定位。
- 内容：描述**本表空间元数据自身的结构**——即"段目录/对象目录长什么样"的定义，使内核能在无任何目录的情况下读起目录。
- 位置约定一旦发布**不可变更**（或必须以格式版本区分）。

### 5.3 file 0 的冗余：关键结构双写

（已确认）表空间头、段目录、对象目录**各写两份**（位于 file 0 内不同页）。

- 作用：防**单页损坏**与部分页写入。
- **注意其局限**：双写防的是页级损坏，**不防文件丢失**——file 0 整个文件损坏仍会导致表空间不可用。文件级冗余由工作区控制文件与备份承担。

## 6 区管理与段空间管理（两个独立维度）

| 维度 | 解决什么 | 我们的选择 | 位图位置 |
| --- | --- | --- | --- |
| **区管理** | 数据文件里**哪些块已分配给段** | **本地管理**（LMT 式） | **每个数据文件头部各一份**（已确认） |
| **段空间管理** | 段内**哪些块还能放新行** | **ASSM 式位图** | 段头块 |

**已确认：每个数据文件头部持有本文件的区分配位图**（不集中在 file 0）。理由：文件因此**自描述**——单独移动、校验、恢复时能自证；区分配操作只触碰目标文件。

**不采用字典管理**（Oracle 已淘汰）：其产生递归空间操作、数据字典争用与额外回滚生成；本地管理还能**自动合并相邻空闲区**。

**不采用 FREELIST（MSSM）**：高并发插入时造成段头热块。

## 7 隔离与安全

| 机制 | 说明 |
| --- | --- |
| 工作区独立文件空间 | 不共享文件、不使用硬链接、不跨用户去重（总体方案 §4） |
| 页头工作区映射 | 数据页含**受校验的工作区映射**，跨区误读可被检出（总体方案 §7） |
| 缓存键含工作区 | 因不同工作区的表空间可能出现相同的 `(file_id, page_id)`，**所有共享结构（缓冲池键、日志、诊断、审计）必须携带工作区标识** |
| **public 只读必须在引擎层强制** | Oracle 的只读表空间**不阻止仅改数据字典的 DDL**（可 `DROP TABLE`），因此不能只靠文件只读性（见 `spec/STO.md` 相关条目） |
