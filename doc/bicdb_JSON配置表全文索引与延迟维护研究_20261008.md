# JSON、配置表全文索引与批量延迟维护研究

日期：2026-10-08。状态：**可行性研究和实现设计，未实现**。

对应用户要求：JSON 只索引几个字段；兼容非普通关系表的配置表；避免在源写入时更新全文索引；先记内部字典表，再批量建索引并清理。

## 1. 结论与现状

可以实现，采用**选定 JSON 路径 + 来源适配器 + 持久变更字典 + 后台批量倒排维护**。普通列、JSON 列、原生配置表和文档对象共用批量维护框架，但各自提供正确的内容与版本读取接口。写入不等待正文解析/分词/倒排合并；轻量字典写入和后台资源竞争仍有成本，不能承诺零性能影响。

当前代码事实：

| 能力 | 实际状态与依据 |
| --- | --- |
| B+tree 索引 | 已实现，`crates/sql/src/dml_index.rs` 在源写入路径插入普通索引键 |
| JSON 类型与路径 | CFG/TYP 有设计，`crates/sql/src/bind/statement.rs` 的类型绑定明确拒绝 JSON；SQL `json_get` 等尚未接线 |
| 原生配置表 | 设计为 redo_only/append_only；当前建表选项只允许普通关系表，config 明确拒绝 |
| 全文倒排、分词、批量维护 | `crates/retrieval/src/lib.rs` 是骨架，没有生产 API |
| 库内附件扫描 | `attachment$` / `attachment_grep` 已实现，字面扫描，无全文索引 |
| 数据库 WAL | `crates/wal/src/record.rs` 是页差异和提交记录，不是现成的逻辑 CDC 数据流 |
| 原生服务并发 | `crates/cli/src/service.rs` 每工作区仅一条业务连接；另开后台客户端会被拒绝 |

因此这是可落地的新增能力，不能声称已有 JSON/配置表全文接口已经能运行。SQL 语法见[主设计](bicdb_全文与文档索引SQL设计_v0.1.md)。

## 2. 官方资料与选型依据

Oracle 的 JSON 全文设计可以通过 INCLUDE 指定 JSON 路径，从而减少非目标字段的索引内容；说明“选择文档中的字段”与全文检索兼容。[Oracle 官方 JSON 全文说明](https://blogs.oracle.com/coretec/json-full-text-search-with-oracle-ai-database-26ai)。

Oracle 的自动维护使用后台任务处理待更新、插入和删除，按变更队列调度同步，而非要求每个业务写入直接维护倒排；也提供手工/周期同步方式。[Oracle 自动维护文档](https://docs.oracle.com/en/database/oracle/oracle-database/26/ccapp/using-automatic-maintenance-index.html)。

PostgreSQL 的全文函数能将 JSON 字符串值转换为词项，筛选字符串/数字/键等类别；这说明需要明确“抽取哪些内容”，不能把结构包含索引与自然语言全文混为一谈。[PostgreSQL 全文函数](https://www.postgresql.org/docs/current/functions-textsearch.html)。

PostgreSQL GIN fastupdate 使用待处理条目延后主索引合并；但待处理列表过大可能触发前台清理，查询还需搜索待处理条目。bicdb 借鉴批量合并，但不把分词后的 pending list 清理强加给写请求。[PostgreSQL GIN 实现](https://www.postgresql.org/docs/current/gin.html#GIN-FAST-UPDATE)。

以上为成熟产品的机制证据。以下关于 bicdb 的内部字典、批量参数、调度与成本目标均为**本项目设计判断**，不是引用产品的保证。

## 3. JSON 与配置表的目标抽取

### 3.1 JSON 列

```sql
CREATE FULLTEXT INDEX ft_cases
ON cases (
    JSON_TEXT(payload, 'question'),
    JSON_TEXT(payload, 'answer.summary')
)
WITH (maintenance = 'batch', sync_interval_ms = 5000, batch_rows = 256);
```

只从这两个路径提取字符串，保留路径 ID 与位置边界。不会索引未选择的字段、JSON 键名、对象序列化结果或数字。使用已有 CFG 受限路径模型，不引入任意 JSONPath。其他类型有显式诊断，不默默转为文本。

后台解析原生二进制 JSON 时先验证表示再按路径读取；文本 JSON 列后台验证并解析，同一列只解析一次。源更新只需知道该列被修改，不要求在写请求中比较所有 JSON 子路径。后台将选定文本的哈希与上次结果比较，只有投影改变才重写对应词项。

已有的 JSON 写入完整性验证仍需执行；这里避免的是**为全文索引额外进行的**投影、分词和倒排写入，不绕过源类型本身的校验。

### 3.2 配置表

```sql
CREATE FULLTEXT INDEX ft_config
ON agent_config (JSON_TEXT(payload, 'description'))
WITH (revisions = 'active', maintenance = 'batch', sync_interval_ms = 30000);
```

配置表来源读取逻辑配置接口，不要求普通关系表 DML。索引正文身份为 `(config_id, revision)`；活动指针、不可变修订和保留范围都要纳入事件。

| 配置事件 | 全文处理 |
| --- | --- |
| 追加新修订 | 后台提取选定路径；可预建非活动修订词项 |
| CAS 切换活动修订 | 更新活动选择关系；查询仍回查活动引用 |
| 回滚到旧修订 | 复用仍保留的旧修订词项；缺失时提取，不能取“最大 revision”代替活动版本 |
| 版本淘汰 | 移除对应词项与可见关系，查询立即排除已淘汰版本 |

默认搜索 active，显式 retained 搜索已保留历史。配置表不参与多语句事务，但它的原子追加/切换要同时持久化来源变更，不能假定可直接执行普通 outbox 表事务。活动引用的来源 API 尚须实现；新修订和活动切换间的语义必须与 CFG-009 对齐。

## 4. 用户提出的内部字典批量方案

### 4.1 字典职责

| 原生内部字典（拟新增） | 职责 |
| --- | --- |
| `fti$` | 索引定义、类型/来源、维护配置、已发布 generation、水位、每索引消费进度 |
| `ft_delta$` | 来源变更日志，供多个索引共享消费 |
| `ftq$` | 构建/同步任务、批次租约、重试、发布状态 |

`ft_delta$` 受原生持久化与恢复保护；它是**可清理的持久待处理数据**，不是临时会话表。客户端可以只读 SELECT 自己工作区的记录，不能直接 DELETE 来伪造索引已同步。可通过 `ft_index$` 汇总查询 pending_count/lag_ms/reason。

拟定变更记录字段：`event_id、source_object_id、record_key、revision、operation、txn_id、commit_seq、created_ms`。操作枚举包含 `UPSERT / DELETE / ACTIVATE / RETIRE / RESCAN`。commit_seq 从真实提交事实获取，不能把尚未提交的预约序号当已提交。原生来源没稳定逻辑键时采用页/表脏标记并重扫，不把物理 ROWID 当永久唯一身份。

**默认不存完整正文、JSON、before-image 或分词结果。** record_key 与 revision 定位源数据，分词数据由后台生成。源库已有正文复制一份到字典会扩大 WAL、占空间且增加写入耗时。若未来来源允许正文在维护前不可恢复地消失，又要求搜索消失内容，必须增加独立持久快照保留契约；本版索引仅对仍可读取、仍有效来源负责。

### 4.2 原子写入

```text
业务原子操作：
  修改/追加源数据
  追加轻量 ft_delta$ 标记（按来源共享，而非每索引一份）
  同一次提交确认，沿用源提交 WAL 持久化

后台批次：
  捕获已提交来源视图 S 和一批变更 E
  读取正文 → 指定路径/格式提取 → 分词 → 排序 → 倒排段合并
  写完并耐久新 generation G
  原生提交：发布 G + 覆盖水位/消费游标 + 已处理进度
  在所有相关消费者已确认后，批量清理 ft_delta$ 已处理记录
```

关系表使用事务 outbox，源事务回滚也撤销事件。配置表 redo_only 必须由其原生单操作原子边界涵盖源与标记。字典自身的存储失败不能仍确认严格可靠来源变更；“不用同步倒排”不等于“忽略任务丢失”。

一个事务反复修改同一源记录可合并为最终变化，语句回滚仍保留正确事件集合；此去重必须与 statement rollback mark 配套，不仅在提交后随意删除中间事件。

### 4.3 批次与清理

1. 按已提交可见记录取有限批次，不处理未提交/已回滚事件。
2. 同一可变记录去重读取最终可见版本；不同保留配置 revision 不合并，活动切换保留最终引用语义。
3. 分批生成新的倒排段，按批次身份和源修订幂等处理。
4. 原子发布新代及进度后才允许清理；不能先删除记录再落盘索引。
5. 同一来源有多个索引时，记录清理以各消费者进度为准；不能因第一个索引成功就删另一个仍需要的记录。
6. 不能用 `max(event_id)` 代替完整提交水位：事件 ID 分配顺序与事务提交顺序不同。发布覆盖水位必须确保所有在来源视图 S 中已提交的变化已覆盖，包括本批之外的事件；受批大小限制时，只推进已证明覆盖的边界，并记录未完成集合。

后台读取中又出现新写入，由下一批处理。source_seq 是源视图序号，不是 SQL 查询碰巧看见的最大 ID；水位出现空洞时不能跳过尚未处理事件。

崩溃窗口：生成未发布文件时重启删除/复用未引用代，事件仍待处理；发布后未清理时重启按进度幂等清理；部分文档错误时不确认其成功，持久记录重试/错误，旧代保持可用。解析故障不导致正在写入的普通业务事务回滚，只有源变更标记不能可靠落盘才影响源提交。

### 4.4 大积压、暂停与多个索引

积压不能触发业务线程现场倒排清理。队列超预算时，在原生原子操作中将对应消费者标为 `NEEDS_RESCAN`，以持久来源脏区/表重扫标记覆盖将被压缩的事件，再回收细粒度日志。查询明确显示积压/重扫状态。

manual/PAUSE 消费者不会无限钉住日志：可转为 NEEDS_RESCAN 后解除历史事件保留，但后续 SYNC 必须重扫仍有效来源。清脏采用 epoch 比较，扫描期间发生新写入不能被覆盖为“已干净”。压缩只改变维护成本，不能凭它宣称索引已同步。

若磁盘已满到连原子脏标记都无法持久化，则源写入可能失败；可靠任务追踪与无条件接受写入不能同时保证。正常资源范围内不等待倒排、无额外全文 fsync。

## 5. 调度与性能

建议默认 `maintenance='batch'`；时间与批大小由参数决定，内置兜底为 `sync_interval_ms=5000、batch_rows=256`。拟增 `bicdb.ini` 的 `[fulltext]` 参数节提供实例默认，索引显式选项优先；未覆盖索引继续继承实例有效参数，目录报告有效值和来源。索引可 SQL 在线改为 30000/60000 毫秒，不重建、不打断在跑批次；实例配置按现有规则重启装载。或设 `maintenance='manual'` 后显式 `ALTER INDEX ... SYNC`。0/负数不合法，禁用自动维护使用 manual/PAUSE。这些是**设计初值，未实测**；不会改动当前运行配置。

```sql
ALTER INDEX ft_config SET (sync_interval_ms = 60000);
SELECT index_name, sync_interval_ms, interval_source FROM ft_index$;
```

同一索引批次不重叠，调度使用单调时钟；显式 SYNC 绕过周期等待立即排入任务。维护间隔不替代 SYNC WAIT 的请求超时。参数定义和生效规则以[SQL 设计 §2.5](bicdb_全文与文档索引SQL设计_v0.1.md#25-维护时间参数用户补充)为准。

还有按服务配置控制的批次字节上限、CPU 时间片、worker 内存、I/O 预算和重试退避。batch_rows 只限制一批事件量，不承诺每批能在固定时间完成。多索引共享来源解析缓存，避免重复读取大 JSON。

实际可检索延时约为 `等待下一调度 + 排队 + 正文提取/分词/合并 + 发布`，5 秒间隔不代表最多 5 秒。状态必须报告 backlog、最老事件年龄、lag_ms 和 last_error。

**现有单连接限制必须解决调度接口，不能通过第二个 SQL 客户端实现后台。** 服务内引擎拥有者按小批捕获提交视图、复制有限输入；计算线程只处理已捕获的数据和派生文件；发布由引擎线程短事务执行。网络等待也需可唤醒处理维护请求，不能持续阻塞在用户输入上。不能跨会话并发共用可变 Session，也不能让长 BEGIN 把大量未提交正文送给后台。

源读取与发布避免持有引擎借用/锁执行分词，主写者优先；长用户事务期间先延迟后台原生写阶段，明确体现滞后。单写者模型下仍可能有短时资源竞争，调度改造是性能验收的组成部分。

## 6. 查询新鲜度

| 模式 | 行为 | 用途 |
| --- | --- | --- |
| `eventual` | 读已发布索引，报告水位，不扫描 backlog，不驱动 SYNC | 大量读取、允许延迟 |
| `strict`（默认） | 原生来源视图上索引 + 有限补查；预算不足明确未就绪 | 写后立即读、核验 |

两者都回查属主、正文版本、撤销、过期及配置活动版本。允许遗漏新版本不意味着可以返回旧配置作为当前配置。strict 的补查还要覆盖 BM25 统计；无法覆盖的历史快照必须扫描或报错。eventual 的评分按已发布代语料，不能称为当前完整排名。

```sql
SELECT config_id, revision, _ft_snippet, _ft_covered_seq, _ft_complete
FROM fulltext_search('ft_config', '数据库诊断', '{"freshness":"eventual"}');

ALTER INDEX ft_config SYNC WAIT;

SELECT * FROM fulltext_search('ft_config', '数据库诊断');

SELECT source_object_id, record_key, revision, operation, commit_seq
FROM ft_delta$;
```

空查询结果也需要协议诊断中的水位/完整性，不能只通过结果行表明滞后。

## 7. 落地与验收

先实现普通列/显式 JSON 文本路径 + 持久变更字典 + SQL batch/manual；原生 JSON 类型、配置表逻辑内容/活动版本接口完成后接配置来源。文档格式适配器复用同一批量队列；不用三套索引管理流程。

现有 WAL 只有物理页差异，直接从 WAL 还原业务变化需要事务识别、行/对象映射、历史重构和日志保留机制；这不是“读一下 redo”就能消除任务开销。首版采用轻量字典方案，后续只有经过测量才能考虑逻辑日志替代。

验收矩阵至少包括：无索引基线、仅记字典且后台暂停、后台正常批量维护、大积压、同来源多个全文索引、长事务、崩溃恢复，以及普通列/大 JSON/配置修订/HTML 附件。测吞吐、p50/p95/p99 写入耗时、WAL 字节增量、队列增长和滞后。

初步评审目标为正常资源条件下 p50 写入增幅不超过 5%、p95 不超过 10%；这是**待基准检验的目标**，不是已测结果或产品承诺。未达目标时先优化来源共享标记/批量字典和后台预算，不能把后台合并塞回写线程。崩溃、乱序、回滚、重复处理、多个消费者、清理前后断电和配置活动回滚必须另测正确性。

本次研究不编译、不发布运行程序；将设计定为已实现必须有代码、真实服务测试和自动发布 SHA 证据。
