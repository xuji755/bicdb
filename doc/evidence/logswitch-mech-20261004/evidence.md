## 结论

1. **切换的动作序列（LGWR 一侧）**：① 把日志缓冲中尚未写入当前日志的记录**刷入当前
   日志**；② 把**最后一条 redo 记录的 SCN 作为 High SCN 写回当前日志文件头**，然后
   **关闭当前日志**；③ 打开新组并写其文件头——**序列号 = 上一序列 +1**（每线程独立）、
   低 SCN、**EOT 置位**、`nab` 置 ∞（打开时）、`hws`（头写序号）递增；④ 把
   **thread#｜序列号｜低 SCN｜低 SCN 时间戳｜下一 SCN** 写进控制文件的日志文件记录
   （非循环记录，切换时**原地覆盖**）。（证据 1–4、9）
2. **日志链与切换的崩溃窗口**：当前日志的 `Next SCN` = **全 F（无穷大）**，其余日志的
   `Next SCN` **指向下一日志的 Low SCN**——链由此连续；知识库明言"**日志切换被假定为
   原子操作**"，切换中崩溃会使 Next SCN 丢失、链断，**恢复需扫描全部日志重建顺序**。
   `EOT`（线程结束标记）落在当前/最后日志的文件头里，使恢复到"线程终点"**不依赖控制
   文件**；用**过时 EOT 的备份在线日志**恢复会停在错误 SCN——是已知故障模式。
   （证据 5、6）
3. **候选判据与等待分类**：可复用候选必须满足"**线程检查点 SCN 已越过该日志的最高
   SCN**"（实例恢复不再需要它；归档模式下再加"已归档"）；切换触发一次 **log switch
   checkpoint**（8i 起为增量式、不阻塞；频繁切换积压 ⇒ `checkpoint not complete`
   等待）。写者/前台在无组可切时按缺的条件分两类（`archiving needed` /
   `checkpoint incomplete`），另有表示"**切换本身尚未完成**"的 `log file switch
   completion`（LGWR 需写完当前日志并打开新日志）与手动的 `switch logfile command`。
   （证据 7、8、10–13）
4. **状态迁移算法（CKPT 驱动）**：`ACTIVE` 的判据是"**该日志中的变化尚未被检查点
   全部写入数据文件**"——表述为"日志内最大 SCN > CKPT SCN"；检查点推进越过它 ⇒
   转 `INACTIVE` ⇒ 可复用（证据 22）。官方定义（`V$LOG.STATUS`）：`ACTIVE` =
   **崩溃恢复仍需要**、`INACTIVE` = **实例恢复不再需要**——**与归档与否无关**
   （证据 21）。驱动者是 **CKPT**：每约 3 秒把"检查点进度记录"（当前检查点 RBA +
   目标 RBA）写进控制文件（证据 23、24）；RBA 只有在 DBWR 实际写出脏块后才前移
   （证据 24）。另有 `CLEARING` / `CLEARING_CURRENT` 两态，仅服务于
   `ALTER DATABASE CLEAR LOGFILE`（证据 21）。

## 本项目自主决策

1. **切换标记 = 新组首条位置的"切换记录"**（`0x01`，主段 = 组号 1B │ 新序列号 4B，
   §11.9 已定）——Oracle 的切换落点是**文件头 + 控制文件**；我们的 redo 文件无独立
   头页，流内切换记录使"组序／序列号／切换点"**在日志流内自描述**：崩溃中断后
   扫描即可重建组序，正是证据 5 所述崩溃窗口的**正面对策**。
2. **记录不得跨组**：剩余空间放不下下一条记录即**提前切换**（§11.5.1 已定）——
   超出 Oracle "写满才切"的形态（Oracle 记录跨文件行为未确认，见 `redo-bytes-20261004`）。
3. **不采用 EOT / `hws` / `nab` 字段**：单实例单写线程；"线程终点"由控制文件的
   CURRENT 组 + 切换记录链表达；控制文件丢失 = 工作区不能启动（`controlfile-bytes-20261004`
   已接受的取舍）。
4. **不采用 Oracle 的选组链表**（其实际顺序未核验）：V1.0 固定 2 组轮换，按可复用
   唯一判据选组（`archive-mech-20261004` 已定）。
5. **诊断形态参照**：切换时输出 alert 形如 `Thread 1 advanced to log sequence N
   (LGWR switch)` 的同构消息（组号、序列号、成员路径），并叠加双通道告警
   （`archive-mech-20261004` 的暂停告警）；不采用证据 20 的"切换中写 alert 阻塞
   提交路径"——我们的告警走**维护线程**，不在写者关键路径上。
6. **降级与低水位"同区间"原子发布**：Oracle 的控制文件更新粒度未在条目中展开；
   我们按 §2.6 的单连续区间协议（≤512B、undo 记录保证）把"检查点进度 + 组状态降级"
   并入**同一次更新**——比"先低水位、后降级"的兜底次序更强（§11.9 发布纪律）。
7. **不设 `CLEARING` / `CLEARING_CURRENT`**：这两态绑定 `ALTER DATABASE CLEAR LOGFILE`；
   本设计未提供该操作（全部阶段与需求均未列入），故状态机为四态；
   若未来引入需扩展（§11.9 已注明）。
