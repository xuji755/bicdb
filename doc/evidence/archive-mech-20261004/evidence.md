# 证据包：日志切换与归档机制定案（Oracle 参照）

模块：存储架构 §11.9（新增）/ §2.5（约束）/ §2.6（CF 字段取值）　对应：**待冻结项 #14（结案）**
核验日期：2026-10-04　原始输出：`raw/01–06`（同目录）

## 结论

1. Oracle 的重做组有**四个运行状态**——`CURRENT`（LGWR 正在写）/ `ACTIVE` / `INACTIVE` /
   `UNUSED`（从未使用或刚新增，**序列号 = 0**）；**归档与否是独立的一列**（`v$log.ARC`，
   CURRENT 组恒为 NO）——**两条轴**（运行状态 × 归档状态）。`ACTIVE` 的语义是
   **检查点未完成**（等待其变 `INACTIVE` 是标准处置）。
   → 我们的控制文件为每组存**两个状态字节**（§2.6 已有布局），取值同构。
2. 切换的等待机制：后台在空间不足时请求日志切换（`kcrfwr()` / `kcrfws()`）；
   切换可因两类条件**等待**——`log file switch (archiving needed)`（组未归档）与
   `log file switch (checkpoint incomplete)`（检查点未完成）；
   `V$INSTANCE.LOG_SWITCH_WAIT` ∈ {ARCHIVE LOG, CLEAR LOG, CHECKPOINT, NULL}。
   → 我们"**无组可切时写者暂停**"的处置（#33 三档的末档）按**缺的条件分成两类**并给出诊断标识。
3. **归档目标满 → 实例挂起**是现网典型故障（还有"归档无法清理且**告警缺失**导致未被发现"的案例）。
   → 我们的处置与 `REQ-OPS-013` 一致：**节流 → 暂停 + 双通道告警；不提供"跳过归档"的开关**
   （跳过 = 自己剪断日志链）；**不停机、不丢链**。

## 本项目自主决策

1. **可复用的唯一判据**：`运行状态 = INACTIVE` ∧（非归档模式 ∨ `归档状态 = DONE`）——
   把 Oracle 的两类"不能重用"（ACTIVE / 未归档）合成一条判据。
2. **切换记录写在新组首条**（`0x01` 主段 = 组号 + 新序列号）；旧组转 `ACTIVE` 并（归档模式）转 `NEEDED`。
3. **归档文件 = 组的逐字节副本 + 32B 文件头**（magic │ `workspace_ref` │ 序列号 │ 起始 LSN │
   字节数 │ CRC32），命名 `<序列号 10 位>.arc`（满足 `REQ-OPS-013` 的按序列校验）；
   **原子发布**：`.tmp` → fsync → rename → 才更新控制文件；重启以控制文件为准、`IN_FLIGHT` 回退重做（幂等）。
4. **归档线程为实例级后台角色**（照 §11.7 的写线程/检查点形态），每工作区至多一个归档在进行。
5. **成员镜像的失效处置**：成员写失败 → 标 `STALE`（成员文件头页）+ 告警 + 剩余成员继续；
   后台从完好成员重建。
6. **归档模式在创建工作区时指定（默认开启）**；V1.0 不做运行中切换；组数**只增不减**。
7. **归档不在崩溃恢复路径上**——在线组即可完成崩溃恢复；归档服务 PITR / 备份 / 备库（离线路径）。
