# 证据包：资产内容检索定案（倒排 / n-gram 两段式与 ripgrep 扫描语义参照）

模块：`spec/RET.md` REQ-RET-028 / `spec/AST.md` REQ-AST-013 / `spec/SQL.md` REQ-SQL-011 / `spec/ENG.md` REQ-ENG-010
对应：**待冻结项 #64（结案）**　核验日期：2026-10-04　原始输出：`raw/01–02`（同目录）

## 结论

1. **全文检索的成熟形态 = 分词 + 倒排**（知识库命中：GIN 把每个词元映射到行 id 列表；场景条目明确"全文检索需要分词器和倒排索引"）。我们"按包为单位"的全文索引即此形态——**分词与记忆路线同一分析器版本**（REQ-RET-002）。
2. **"索引加速子串 / 正则"的成熟做法 = n-gram 两段式**（PG `pg_trgm`）：从模式**提取 n-gram → 索引给出候选**（可能满足，`GIN_MAYBE`）→ **回表重查**（recheck；`EXPLAIN` 的 `Rows Removed by Index Recheck`）；**假阳性可容忍、假阴性零容忍**；提取不出 n-gram 的模式退化为扫描（甚至更差）。
   ——这正是我们"**超集 + 回读验证 + 尾扫**"完整性纪律、以及"子串索引（n-gram）为 grep 加速扩展位"的模板（REQ-RET-028 的扩展位注）。
3. **grep 的工程形态 = 行式扫描**（ripgrep）：行缓冲、行号、**上下文行**（`-C/-A/-B`）、**二进制检测**（NUL；默认跳过，`-a/--text` 可强制）、编码处理。"扫描恒新鲜、无索引依赖"正与我们给 grep 的定位一致。
   **要避开的坑**：ripgrep 在 mmap / read 两种策略下**二进制检测结果可能不一致**——我们的验收要求**结果不随内部策略变化**（确定性）。
4. 由此定案（正文四域）：grep 恒扫描；全文按包索引（库外派生区，**按需命令显式构建**、**不经 SQL 接口**）；读侧开放——**SQL 表值函数**（`asset_grep` / `file_search`）与**查找命令**（直连）；无索引 → **明确错误**（不伪装空结果）。

## 本项目自主决策（#64 定案）

1. **按包**建索引；载体 = **库外派生区**（可重建）；**建索引不经 SQL 接口**——按需命令显式触发（CLI `bicdb index build/drop/status`）。
2. 读侧开放：**SQL 表值函数**（`asset_grep` / `file_search`，可进 SELECT 参与过滤 / JOIN / 聚合）+ 查找命令（CLI / MCP 直连）；**grep 恒扫描**（精确且新鲜）。
3. **完整性 = 超集 + 验证 + 尾扫**；截断显式；正则护栏（长度 / 超时 / 结果上限——数值 P0 冻结）。
4. 资产**不可变** ⇒ 索引更新只有"增 / 删成员"；索引缺失 / 损坏不构成数据面错误。
