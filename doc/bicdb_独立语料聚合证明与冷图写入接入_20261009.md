# 独立语料聚合证明与冷图写入接入（2026-10-09）

## 已实现范围

独立语料聚合证明已经接入 SQL 原生图存储。新建、旧图升级、快照恢复、完整写入和 `ALTER GRAPH ... REBUILD STORAGE` 都在实体、属性索引、全文变更、证明与最终 manifest 的同一事务中发布。进程重启或无关表提交后，具备证明的新图可以直接进行有界局部写入，不再依赖运行期“已完整验证”缓存。

旧 124/148 字节 manifest 继续兼容读取；带证明的格式为 180 字节。旧格式只读不升级，第一次成功的完整写入、显式升级或存储重建会生成证明。有证明标记但根记录缺失、损坏或与语料不符时拒绝读写，不会降级为旧格式。

## 证明模型

- 每个节点或关系贡献包含种类、48 位 ID、规范 JSON 摘要和字节数、原始记录字节数。节点同时保留实际 checksum/chunks 长度，兼容历史非规范 JSON；关系继续使用原生邻接记录，不复制第二套拓扑。
- 种类和 ID 的摘要选择 4096 个桶。桶内严格排序并拒绝重复实体；二叉 Merkle 树承诺节点数、关系数、规范字节和原生记录字节。根绑定工作区、图对象、文件及六条物理路由、分配器水位和 generation。
- 点写只读取实际查询和唯一索引回查观察到的源实体、相应桶和共享路径页。`verify_source` 同时核对存在性、实体摘要与原始记录长度；本轮首次原值和最终值生成证明 delta。证明读取与图读取使用同一个 `ReadView` 和事务 owner。
- 完整加载会从真实节点和关系重建全部贡献，并与持久证明逐项比较。证明内部一致不能替代实体核验；局部写也不能用未观察实体的证明冒充本轮源数据。
- manifest 的全图数量、规范 JSON 总量、原生记录总量和 generation 必须与证明根一致。请求工作、字节和截止时间由查询、唯一候选回查、证明路径共同消耗，不能通过阶段边界重置。

## 物理格式和更新纪律

逻辑地址为 `Root / Bucket(0..4095) / HashPage(0..127)`，映射到 graph ordinal 的 kind-5，与 kind-1 节点和其他索引空间隔离。每个逻辑记录包含一行 SHA-256 和最多 1023 个 4096 字节数据块；数据块有逻辑长度前缀，尾部必须为零。

证明记录缩短或删除时保留原有块高水位，并用固定大小原位更新或墓碑表示。以后重新增长复用同一组物理地址，避免反复增删为 B-tree 累积历史候选。缺块、非连续块、短块、非零填充、外来 ordinal、重算校验和后的错误根和超限都具名拒绝。

写入顺序如下：

1. 冻结 manifest 与源 `ReadView`，按查询实际需要读取节点、关系、索引候选和证明路径。
2. 核对 manifest 承诺、证明根和全部观察源；计算净实体变更、索引变更、全文事件和证明 delta。
3. 在现有语句 savepoint 内写入节点、邻接、索引、全文队列和 kind-5 证明记录。
4. 再次锁定并比较当前 manifest，拒绝旧快照覆盖；最后发布包含新统计、generation 和证明根的 180 字节 manifest。
5. 任一预算错误、唯一冲突、源变化、证明损坏、回滚或崩溃都不会发布部分新版本。

## 已验证边界

- 2000 节点冷图在进程重启后可执行有界点写；无关表 DDL 不使图证明失效。
- 未缓存唯一候选仍从持久索引回查并核对源；旧快照写入在 manifest/证明栅栏处拒绝。
- 证明根即使重新计算内外校验和，只要 generation 或语料不匹配，写入仍原子拒绝。
- 创建、迁移、重建、模板恢复、旧 manifest、旧视图、全文队列、刷盘失败和真实崩溃恢复继续通过。
- 24 轮同键创建/删除后，固定块和墓碑不会持续增加证明地址候选；受限点写在索引重建后恢复容量。
- 数据库工作区 973 项、冻结 Store 接口 60 项、真实旧版升级 9 项通过，合计 1042 项；数据库中的 12 项 ignored 是崩溃子进程和本地基准，Store 的 9 项 ignored 已用真实旧版程序单独执行。格式、clippy `-D warnings` 与 Rust 1.80 检查通过。

命令和原始日志见[SQL 接入证据](evidence/bicdb-graph-corpus-proof-sql-20261009/README.md)。独立证明解决的是冷启动局部写入的持久准入，实际多连接写并发、Move/GC、类型化引用/句柄、精确内存/部分结果协议和大型性能验收仍在[图增强验收清单](bicdb_图增强验收清单_20261009.md)中继续推进。没有连接或修改 Neo4j。
