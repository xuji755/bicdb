## 1 规模画像（已确认）

| 维度 | 范围 | 跨度 |
| --- | --- | --- |
| 单工作区节点数 | **1 万 ~ 1000 万** | 3 个数量级 |
| 边数 | **≤ 10 × 节点数**（平均度 ≤ 10） | — |
| 向量 | **部分节点有，可能一个都没有** | — |
| 工作区数量 | 活跃数受预算限制，空闲进程可退出（总体方案 §2） | — |

**两条最要紧的约束**：

1. **跨度 3 个数量级** —— 同一套代码要同时服务 1 万节点和 1000 万节点的工作区，不能只优化一端。
2. **平均度 ≤ 10** —— 图**不是稠密的**。但幂律分布仍会造成个别高度数节点，设计目标是**优雅退化**而非专项优化。

## 2 容量测算

### 2.1 图数据（不含向量）

| 规模 | 节点 | 边（≤10×） | 节点行 | 边行+索引 | 合计 |
| --- | --- | --- | --- | --- | --- |
| 小 | 1 万 | ≤10 万 | ~2.5 MB | ~6.5 MB | **~9 MB** |
| 中 | 100 万 | ≤1000 万 | ~250 MB | ~650 MB | **~900 MB** |
| 大 | 1000 万 | ≤1 亿 | ~2.5 GB | ~6.5 GB | **~9 GB** |

（节点行按 ~250B/条、边按 ~50B + 出/入索引 ~20B×2 估算）

### 2.2 向量（FLOAT32，1536 维 = 6KB/条）

| 带向量的节点占比 | 1000 万节点工作区 | 说明 |
| --- | --- | --- |
| 0% | 0 | **可能的真实场景**（纯图与关系） |
| 10% | **6 GB** | 常见 |
| 100% | **60 GB** | 极端；`halfvec` 可减半至 30GB |

**结论**：

- 向量**必须是可选列**，不能有任何全局向量结构。某工作区一个向量都没有时，不应产生任何向量相关的文件、索引或内存占用。**pgvector 的列式做法正好满足**。
- 极端情况下向量仍是最大单项（60GB），但典型情况下量级已可控。`halfvec` 保留为后续扩展的优化项，不作为 V1.0 必选。

### 2.3 小工作区的固定开销

1 万节点的工作区只有 **~9 MB 数据**，而固定开销包括：

| 项 | 可做到的最小 |
| --- | --- |
| file 0（元数据） | 地址空间 ~13 MB（核心带 4 MB + 副本带 4 MB + 位图区 5 MB + 数据区）；**实际写入 ~1 MB 级**（预留带不写入、稀疏）——见 `目录详设` §2.1 |
| 控制文件 ×2 | ~32 KB |
| redo（**2 组 × 2 成员**） | **可配置 —— 这是关键** |
| file 1 undo | ~1 MB（按需增长） |
| file 2 temp | 0（零长度占位） |

**redo 组大小创建工作区时指定**（已确认），这解决了主要问题：小工作区配小 redo（如 256KB/组，4 个文件共 1MB），固定开销降到约 **1–2 MB**，相对 9MB 数据可接受。

**需要配套三点**：

| 项 | 规定 |
| --- | --- |
| 下限 | 必须能容纳**一个检查点周期**内的日志量，否则会频繁日志切换。具体下限须在 P0 依据检查点策略给出 |
| 默认值 | 未指定时按工作区预期规模给几档默认值 |
| 变更方式 | 工作区运行后**只能增加组数，不能改已有组的大小**（改大小须重建组） |

## 3 向量索引必须是磁盘型

在 1000 万节点、10% 带向量的场景下向量为 6GB；极端情况 60GB。而总体方案 §21 冻结的基准机是 **8 核 32GB**。

**结论：ANN 索引必须走磁盘页结构，不能假设向量常驻内存。** pgvector 的 HNSW 即为磁盘型（有 metapage / element tuple / neighbor tuple 的页布局），我们参照实现。

**连带影响**：向量查询延迟受 I/O 限制，`REQ-PERF-008`（读吞吐随线程数近似线性扩展）在向量场景下需重新审视——**磁盘 I/O 是共享瓶颈，线性扩展不成立**。该条应限定适用范围，或对向量路径给出独立指标。

## 4 图的物理组织（已确认：方案 B）

### 4.1 结构

```
出边：聚簇结构，键 (src, edge_id)，边数据内联
      → 一跳出边遍历 = 1 次范围读（度 10 的节点通常 1 页搞定）
      → 入口：出边入口索引（B+Tree，(src ROWID) → 首邻接页）

入边：覆盖索引 (dst) → (src, edge_id, label)
      → "谁指向我、是什么关系" 完全不用回表
```

> **一个边标识，两个角色**（`spec/GRP.md` §0.4 已定）：`edge_id` 由 48 位**序列**产生
> （`CONV` §1）——对外标识与聚簇键**合一**：**序列单调 ⇒ 追加即有序、永不需要分裂协议**。
> 邻接条目另带 `flags` + `itl_slot`，与行同构地参与可见性判定
> （`spec/GRP.md` REQ-GRP-002、存储架构 §5.11）。

### 4.2 为什么入边索引要做覆盖

按基本形态，入边遍历是「1 次索引扫 + N 次按 (src, edge_id) 回查」。而这 N 次回查落在**不同的 src** 上，大概率是 N 次随机 I/O，比出边遍历贵得多。

入边索引多存一个 `label` 字段后，Agent 场景里最常见的"谁指向我、是什么关系"**完全不用回表**，只有确实需要读边属性全文时才多一次查找。**多存几字节换掉 N 次随机 I/O**。

### 4.3 代价（如实记录）

| 项 | 影响 |
| --- | --- |
| 插入边 | 从"追加"变为"B+Tree 插入" —— 但图是事务型的，本来就要维护索引，成本相当 |
| 删除节点 | 出边连续删（快），入边需索引扫 + 逐个查找（稍慢） |
| 边的 `src` 变更 | 等于删 + 增（聚簇键不能原地改）—— 边通常不换端点，可接受 |
| 高度数节点 | 度数上千时邻接区跨多页，退化为多次 I/O。**目标为优雅退化，不做专项优化** |

### 4.4 超级节点的处理策略

平均度 ≤ 10 使"整图都是超级节点"不成立，但幂律长尾仍在。策略：

- **不设专门的超级节点结构**
- 保证高度数节点的遍历**受预算约束**（见 §5），不会失控
- 度数超过阈值的节点可考虑**邻接块独立聚簇**，但列为 P0 待评估项，不进 V1.0 必须范围

## 5 遍历预算：边数为主，跳数为次（重要修正）

总体方案 §13 现写"建议初始上限 **5 跳**"。按平均度 10 计算：

| 跳数 | 最坏展开路径数（度 10） |
| --- | --- |
| 2 | 10² = 100 |
| 3 | 10³ = 1,000 |
| 5 | **10⁵ = 100,000** |

**跳数是个很弱的约束** —— 2 跳就可能摸到几千条边。真正兜底的是**扩展边数预算**。

**修正**：图遍历的**主约束为扩展边数**，跳数降为次要约束。`REQ-GRP-008` 的措辞需相应调整，把"建议初始上限 5 跳"改为"边数预算为主约束，跳数为次要约束，两者均须在 P0 冻结"。

## 6 验收档位必须上调

总体方案 §13 现写"至少验证 **10 万顶点和 100 万边**档位"。按实际规模，这个低 10～100 倍。

**建议调整**：

| 档位 | 节点 | 边 |
| --- | --- | --- |
| 小 | 1 万 | 10 万 |
| 中 | 100 万 | 1000 万 |
| 大 | **1000 万** | **1 亿** |

**并新增专项**：

- **高度数图**专项：构造度 ≥ 1000 的节点，验证遍历受预算约束、不失控、可优雅退化
- **无向量工作区**专项：验证纯图与关系场景下无任何向量相关开销
- **小工作区**专项：验证 1 万节点工作区的固定开销占比达标
