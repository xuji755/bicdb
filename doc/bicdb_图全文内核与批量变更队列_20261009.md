# 图全文内核与批量变更队列（2026-10-09）

后续进度：同日已接入图全文 SQL 与原生手动发布，见[SQL 实施记录](bicdb_图全文SQL与原生持久化_20261009.md)。随后接入源写事务和原生共享队列、分批 SYNC 与持久暂停/恢复，见[共享队列实施](bicdb_图全文共享变更队列与批量维护_20261009.md)。下文保留内核阶段的验证边界；服务定时调度仍未接入。

## 当前交付边界

本阶段完成 `bicdb-graph` 中可复用的全文内核、原生记录/倒排键编码，以及共享变更队列状态机。
核心算法全部使用 Rust。本阶段没有连接 Neo4j，也没有改变 Neo4j 数据、索引、配置或服务。
测试使用合成图与 bicdb 原生 B-tree 页；现有数据库服务回归在独立临时工作区进行。

**这还不是可通过 SQL 使用的持久化全文索引。** 新内核尚未注册到数据库字典、图写事务或
服务维护循环；没有新增 `CREATE FULLTEXT`、`SYNC`、自动定时 batch 或全文查询过程。
现有 `bicdb.searchNodes` 仍返回 `mode=bounded_scan`。不能将编码的重载测试称为数据库
事务/崩溃恢复验收，也不能将队列状态机测试称为后台任务已经运行。

## 全文数据模型

- `Definition` 指定节点或关系，最多 16 个标签/关系类型与 16 个固定 JSON 路径。标签/类型
  之间为 OR；JSON 路径支持对象键和固定数组下标，叶子仅接受字符串或字符串数组。
- 不索引未选中的 JSON 字段。缺失、NULL、错误类型分别计数；混合数组只接受字符串元素。
- 源对象必须具有非空字符串 `db_type`。查询必须明确指定该域；倒排候选与统计都以域隔离。
  标签、属性和域变化都会改变源修订，旧版本不能通过源修订复核。
- 源修订使用 SHA-256，节点/关系规范 JSON 与原生图实体记录的校验内容一致。关系修订包括
  两端节点 ID、类型与属性；独立关系 ID 保留，平行边不会折叠。

`bic_mixed_v1` 为版本化混合分析器：英文、数字、下划线标识符按连续词元转小写；
汉字、假名、韩文使用单字位置，并为普通词项检索增加相邻双字。没有语言词典、词干化
或 Lucene 查询语言兼容声明。

三种通道明确区分：

| 通道 | 语义 |
| --- | --- |
| Terms | 查询词项为 AND，可以分布于选定字段；中文等含单字及相邻双字词项 |
| Phrase | 连续词元必须在同一字段、同一数组元素；忽略分隔符，不跨字段/元素 |
| Exact | 匹配完整词法标识符；不是整个字段的等值比较；查询只能含一个词法标识符 |

例如 `innodb_buffer_pool_instances` 是完整标识符，`buffer_pool` 不会匹配它；Exact 查询
`buffer` 可以匹配字段 `buffer pool` 中独立的 `buffer`。原始 UTF-8 字节偏移用于片段和行号，
片段限制为 256 字节并保持字符边界。超过 512 字节的单词不入索引并计入诊断；同样过长的
查询报错，不静默截断。

## 排名、候选与资源约束

统计键为 `(db_type, field, channel)`，域外语料不会影响本域排名。各字段等权相加：

```text
idf = ln(1 + (N - df + 0.5) / (df + 0.5))
score(term) = idf * tf / (tf + 1.2 * (1 - 0.75 + 0.75 * length / avg_length))
```

`N` 为该域/字段/通道含词项的文档数，词频、长度和文档频率按该分析器产生的词项计算。
采用 BM25 的 IDF 和长度归一化形式；这里定义自己的分数，不承诺与 Lucene 的数值、
norm 编码或分析器完全一致。公式与参数参考 [Lucene BM25Similarity 官方说明](https://lucene.apache.org/core/7_6_0/core/org/apache/lucene/search/similarities/BM25Similarity.html)。
Neo4j 的字符串/字符串数组、节点/关系全文与延迟维护能力参考
[Neo4j 全文索引官方说明](https://neo4j.com/docs/cypher-manual/current/indexes/semantic-indexes/full-text-indexes/)。
只阅读公共文档，没有执行其示例中的数据库写操作。

普通查询使用倒排交集；原生 B-tree 候选入口再次复核域、选定字段、词项/短语和当前源修订。
已删除或已变更的源不会作为旧答案返回。稳定排序为分数降序、ID 升序；选择最高得分字段
生成片段。字段轮转融合单独提供，按字段内排序轮转去重，不比较来自不同字段索引的分数。

默认逻辑预算为 100 MiB、100000 个文档、1000000 个存储词元、128 个查询词元和 10000
个结果。收集文档时逐条计费，防止先保留整个过大语料再报错。预算包含文本、词元和数组
记录估算，不是进程 RSS 限制。超预算明确报错；SQL 层后续必须先执行过滤，再应用用户 LIMIT，
不能在索引内隐式截断候选而漏掉过滤后的答案。

## 原生存储编码

`bicdb-graph-fulltext-v1` 的不可变 generation 保存定义、generation 号、完整覆盖水位、文档文本、
位置与源修订。原生 heap 行最大 4096 字节；头记录从 key 0 开始，文档基键为
`(1 << 60) | (element_id << 10)`，分片 0 为 SHA-256，1..1023 为连续 JSON 分片。
重载校验记录类型、ID、分片、校验和、字段形状、UTF-8 位置和词元顺序，直接恢复已存词元，
不重新分词。文档记录的单条 JSON 上限为 1023 个分片，超过时构建失败。

倒排键包含版本/通道、域、字段序号、词项及 32 字节源修订，payload 为 48 位元素 ID。
词项有明确长度前缀，查询提供精确范围边界；最长键不超过现有 B-tree 的 4088 字节限制。
实测向原生 B-tree 插入合成倒排项，触发页分裂、重开根、范围扫描，再复核候选并与内存
倒排结果比较。这验证键与页格式适配，尚未验证 SQL 字典注册或 WAL 原子发布。

## 共享 batch 变更队列

`fulltext_journal` 是纯状态机。事件只包含对象类别、元素 ID、递增序号、修订或删除标记、
首次待处理时间，不包含源文本或分词结果。同图多个全文索引共享每个元素的一条合并事件；
再次更新替换最新修订，保留首次等待时间。没有消费者时不产生事件。

每个索引记录 `cursor`、`covered_seq` 与暂停状态：

- cursor 表示已经应用的部分批次位置；covered_seq 只有当前待处理变更全部应用后才推进。
  合并事件可能把较早的脏修订覆盖为较新序号，因此部分 cursor 不能冒充完整覆盖水位。
- 在途 batch 处理期间发生的新更新保留在更高序号，旧 batch 确认不能清除它。重复确认
  已完成批次幂等；来源不一致或跳过未处理记录的确认拒绝。
- 暂停/较慢消费者仍保留历史。只清理不高于全部消费者最小 covered_seq 的事件；注销索引
  后重新计算清理界限。新消费者必须在当前一致源水位完成初始构建后注册，不能使用已被
  清理的旧历史冒充同步成功。
- 队列原生编码为 `bicdb-graph-fulltext-journal-v1`：元数据校验/数据对为 0/1；事件基键为
  `(3 << 60) | (element_id << 10)`，每条事件一个校验/数据对。重载检查消费者水位、事件唯一
  序号、孤立事件和预算。最多 64 个消费者。

计划与 generation 都返回新的对象；构建或批次失败保留原对象。**实际数据库事务保证尚需
接线**：源变更及队列差异必须同事务提交，索引文档/倒排发布及确认/清理必须在一个维护
事务中完成。这里的不可变计划没有替代数据库 undo/WAL。

## 下一阶段接线顺序

1. 新增受保护的全文数据/队列对象与自定义倒排索引字典类型；禁止普通 DML 按 ROWID 解释
   元素 ID。创建、失败回滚、重启及工作区权限必须采用现有原生事务流程。
2. 图写事务只写每个变化元素的轻量队列差异，不在用户线程里分词，也不整表重写队列。
   当前纯计划的 clone 不能直接当作高吞吐写入实现，必须验证实际增量行数与 WAL 增量。
3. 接独立 SQL 图全文创建/查询/重建/同步/暂停接口，继续区别于关系表字段、配置表逻辑字段
   和受管文档对象索引。当前 SQL 全文设计仍以
   [全文与文档索引 SQL 设计](bicdb_全文与文档索引SQL设计_v0.1.md) 为方案，不能当作已支持语法。
4. 服务使用单一数据库执行者，在事务边界处理维护任务；不能另起写线程共享 Session。
   等待请求的增量 frame 缓冲必须保留半帧，不能通过读超时丢掉网络数据。用户事务期间
   不发布维护事务。
5. 接定时 batch 和手动维护。默认建议间隔 5000ms、batch_rows=256；参数继承顺序为
   索引覆盖值 > 实例参数 > 默认值。单调时钟调度；暂停状态持久化。以上数值尚未进入
   当前 INI/SQL 运行配置，当前也不存在定时维护延迟保证。
6. 完成固定目标水位 WAIT、严格模式尾部合并、eventual 模式陈旧项过滤、发布故障恢复及
   写入性能/WAL/队列延迟基准。覆盖水位只有追平才推进的保守内核需要任务协调层保证固定
   WAIT 目标不会因持续新写而无限推迟，不能仅把 source_seq 当作已经同步的结果。
