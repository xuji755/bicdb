## 1 总览

### 1.1 层次结构

```text
实例
├── 全局控制文件（2 份）              数据库管控的文件清单
│
└── 工作区（互不干扰）
    ├── 控制文件（2 份）              该工作区的恢复锚点
    ├── redo（2 组 × 2 成员）         组大小创建工作区时指定
    └── 表空间
        ├── file 0   元数据 + bootstrap
        ├── file 1   Undo
        ├── file 2   Temp（不持久化）
        └── file 3+  数据段（可动态新增）
            └── 段
                └── 区（8 页 = 128KB）
                    └── 页（16KB）
```

### 1.2 三条贯穿全局的原则

| 原则 | 含义 | 影响 |
| --- | --- | --- |
| **一个引擎 + 表选项** | 页格式、ROWID、文件布局、控制文件、WAL 基础设施全部统一；表间差异收敛为**表级选项** | 备份、恢复、检查器、配额、诊断只做一套 |
| **存储层不承载版本与事务语义** | 行内无版本号、无时间戳、无事务 ID；可见性由 Undo + 快照判定 | 行更紧凑；业务多版本由数据模型层用额外的行/节点表达 |
| **渲染隔离在文件层** | 每工作区独立文件，不共享、不硬链接、不跨用户去重 | 隔离失败属发布阻断项 |

### 1.3 规模约束（驱动全部容量决策）

| 维度 | 范围 |
| --- | --- |
| 单工作区节点数 | **1 万 ~ 1000 万**（跨 3 个数量级） |
| 边数 | ≤ 10 × 节点数（平均度 ≤ 10） |
| 向量 | **部分节点有，可能一个都没有** |
| 页大小 | **16KB**，实例内固定 |

**由规模推出的两条硬约束**：

1. **向量必须是可选列**——某工作区无向量时不得有任何向量相关文件、索引或内存占用。
2. **ANN 索引必须磁盘型**——极端场景向量达 60GB，装不进 32GB 基准机内存。

## 2 工作区存储布局

### 2.1 目录

```text
<workspace root>/            根目录名由服务端生成的不透明 ID，不拼接用户输入
├── control/
│     control01.ctl
│     control02.ctl
├── wal/
│     redo_g1_m1  redo_g1_m2    组 1
│     redo_g2_m1  redo_g2_m2    组 2
└── data/
      <ws>_meta     file 0
      <ws>_undo     file 1
      <ws>_temp     file 2
      <ws>_data_01  file 3
      <ws>_data_02  file 4   （按需动态新增）
```

### 2.2 文件角色约定

| 文件号 | 角色 | 说明 |
| --- | --- | --- |
| **0** | 元数据 | 表空间头、段目录、对象目录、文件角色表、bootstrap。**不承载用户数据行** |
| **1** | Undo | 仅 `logging = full` 的表产生 |
| **2** | Temp | 排序/哈希/分词溢出；不持久化、不进备份 |
| **3..N** | 数据 | 数据段，可动态新增 |

**该约定对 system 与 public 表空间同样适用**，规则统一。

**三个好处**：① 备份与恢复按角色定策略（temp 不备份）；② 用户数据**只可能在 file ≥ 3**，ROWID 寻址空间干净；③ 配额按角色分别设，undo/temp 不与数据挤占。

### 2.3 两级控制文件

| | 工作区控制文件 | 全局控制文件 |
| --- | --- | --- |
| 位置 | `<ws>/control/` | 平台控制目录 |
| 份数 | 2 | 2 |
| 内容 | 该工作区的文件清单、检查点位置、redo 序列号、格式版本 | **数据库管控的文件清单**：有哪些工作区、各自根目录与文件构成 |
| 更新时机 | **日志切换时** | 建/删工作区、新增数据文件时（**低频**） |
| 是否恢复锚点 | **是** | 否（丢失可由各工作区自描述重建） |
| 含私有内容 | 否（仅结构） | **否** |

**控制文件必须独立于表空间**——恢复要先知道"该打开哪些文件、检查点在哪"，若控制信息藏在 file 0 内则形成循环依赖（要先打开 file 0 才知道要打开 file 0）。

**全局控制文件绝不在提交关键路径上**——工作区的每次提交不得触碰它，否则造成跨工作区耦合与写热点。

### 2.4 Redo

- **每工作区独立**：redo 记录**包含用户数据本身**（行级修改描述），共享即泄漏。
- **2 组 × 2 成员 = 4 个文件**：组提供循环复用空间，成员提供镜像冗余。同组成员**大小必须完全一致**。
- **组大小创建工作区时指定**——小工作区配小 redo（如 256KB/组），大工作区可上百 MB。这解决了小工作区固定开销占比过高的问题。
  - 下限：必须能容纳**一个检查点周期**的日志量（P0 依据检查点策略给出）
  - 变更：运行后**只能增加组数，不能改已有组大小**
- **不归档**：归档服务于 PITR，属 V1.0 范围外。redo 组循环复用。

## 3 表空间文件

### 3.1 file 0：元数据与自举

内部结构，按块顺序：

| 块 | 内容 |
| --- | --- |
| 0 | **引导页**（`page_type = 5`），格式**永久固定** |
| 1..k | **bootstrap 数据**，位置固定 |
| k+1.. | 段目录、对象目录、**文件角色表**、位图 |

**引导页与 bootstrap**（解决先有鸡还是先有蛋）：

- 要读段目录，得先知道段目录的结构；而目录结构本身存在目录里。
- 解法：**块 0 格式硬编码**，内核不依赖任何字典即可读；它指向**固定偏移的 bootstrap 数据**，内容是"段目录/对象目录长什么样"的定义。
- 参照 Oracle `bootstrap$`——其段头位置（`file 1 block 377`）、对象号、初始区大小都是硬编码的。
- **位置约定一旦发布不可变更**（或必须以 `format_version` 区分）。

**关键结构双写**：表空间头、段目录、对象目录在 file 0 内**各写两份**（不同页），防单页损坏与部分页写入。

> **注意其局限**：双写防的是**页级**损坏，**不防文件丢失**。file 0 整个文件损坏仍会导致表空间不可用——文件级冗余由控制文件与备份承担。

### 3.2 数据文件（file 3+）

每个数据文件的头部含：

| 项 | 说明 |
| --- | --- |
| 文件头 | file_id、所属表空间、格式版本、大小 |
| **区分配位图** | 本文件内哪些块已分配给段（`page_type = 8`） |

**区分配位图放每个文件头部（不集中在 file 0）**：文件因此**自描述**——单独移动、校验、恢复时能自证；区分配操作只触碰目标文件。

## 4 段与区

### 4.1 区

- **区 = 8 页 = 128KB**（16KB × 8），一次分配的单位，大小固定。
- 连续区减少碎片；小对象的浪费由"按需申请/释放区"控制。

### 4.2 段

每个段（表、索引、Undo）的首个页是**段头页**（`page_type = 9`），记录：

| 项 | 说明 |
| --- | --- |
| 段类型 | 数据 / 索引 / 邻接 / Undo / 临时 / ANN |
| **表选项副本** | `logging`、`update_mode`、`cleanup` 等 |
| **`itl_max`** | 本段各页的 ITL 槽上限（对应 Oracle 的 `MAXTRANS`）。**段级属性，存于此而非页头**——见 §5.4 |
| 区清单 | 本段占用的区 |
| 高水位（HWM） | 见 §4.3 |
| 追加位置 | append-only 表的下一可写位置 |

**表选项存在段头**：引擎打开段即可分派行为，不必回查目录；段自描述，利于单文件恢复。

### 4.3 高水位与两类表

**HWM = 段内"已格式化且可能含数据"的边界，删除不降低 HWM。** 堆表下全表扫描会扫过空块。

| 表类型 | HWM 策略 |
| --- | --- |
| `update_mode = in_place` | 采用 HWM；配合段收缩（`TRUNCATE`/重组）回收 |
| **`update_mode = append_only`** | **不需要 HWM**——追加位置由段头显式记录；`cleanup = segment_drop` 时整段丢弃，不存在空扫问题 |

> 这是 append-only 相对堆表的**实质优势**：省掉 HWM 空扫代价，TTL 退化为整段操作。

### 4.4 段的空间管理

| 表类型 | 空间管理 |
| --- | --- |
| `in_place` | 页内空闲区 + defrag（§5.4）；页由位图分配 |
| `append_only`（保留版本） | 顺序追加；旧版本按 `version_keep` **内联淘汰**（插入版本 N 后删除第 N−keep 个） |
| `append_only` + `segment_drop` | **按时间分段**，TTL 到期整段丢弃 |

## 5 页

### 5.1 页布局

```text
偏移 0         描述区（32B）
偏移 32        事务区（32B，含默认 1 个 ITL）
偏移 64        空间区（4B）          ← 固定头合计 68B
偏移 68        槽位目录（向高地址增长）→
                     [空闲区]
               ← 行数据（向低地址增长，下界 = 16384 − 页尾区大小）
               ┌── 页尾区（大小由 page_type 决定）────────────┐
               │ 一般页   4B   仅页尾校验                     │
               │ 索引页  16B   link_prev 6 | link_next 6 | 校验 4 │
               └──────────────────────────────────────────────┘
偏移 16380     页尾校验（4B，**始终在页的最末尾**）
```

| 页类别 | 固定头 | 页尾区 | 非行空间合计 |
| --- | --- | --- | --- |
| 数据页、Undo 页等 | 68 | 4 | **72** |
| 索引页 | 68 | 16 | 84 |

**链指针放页尾而非通用描述区**：只有索引页付这 12 字节，数据页省下来。数据页数量远多于索引页，故这是净收益。

页尾区大小随 `page_type` 变，但只影响**行区下界**这一个数——`free_end` 语义、空闲区计算、defrag 逻辑均不变，**不是结构分叉**。

**页尾校验始终在最后 4 字节**：检查器读一页时先看末尾即可，无需先判断页类型。

### 5.2 字段准入纪律（先于具体字段）

**页头只含"崩溃后无法重建"的落盘信息。** 判断标准只有一条：

> 这个字段，在进程崩溃重启、且**没有它**的情况下，能否从页的其余内容或外部结构**重建**？**能重建的就不进页格式。**

这条纪律比任何字段清单都重要——它是将来加字段时的取舍依据。

**由此划清与缓冲区头的界限**：

| | 页头（**落盘**） | 缓冲区头（**仅在内存**） |
| --- | --- | --- |
| 归属 | 数据块本身的一部分 | BufferPool 的内存结构 |
| 内容 | 身份、完整性、事务、空间信息 | pin 计数、latch、LRU 链指针、脏标志、touch count |
| 定义位置 | 本章 | `REQ-STO-006`，另行展开 |

**两者不必有任何字段对应关系**——缓冲区头不迁就页格式，页格式也不为缓存便利加字段。

> **命名警示**：Oracle 的 `kcbh`（字面 "kernel **cache** block header"）**是落盘的块头**；只在内存的是另一结构 `kcbbh`（Buffer Header）。两者**只差一个字母**，极易混淆——这是本节存在的直接原因。

### 5.3 描述区（32 字节）

| 偏移 | 长度 | 字段 | 说明 |
| --- | --- | --- | --- |
| 0 | 4 | `checksum` | CRC32C，覆盖全页（本字段置零后计算） |
| 4 | 1 | `format_version` | 从 1 起 |
| 5 | 1 | `page_type` | 见 §5.6 |
| 6 | 1 | `flags` | 见下 |
| 7 | 1 | `mod_seq` | 修改序列号，与页尾校验对比 |
| 8 | 8 | `workspace_ref` | 工作区受校验标识，见 [`workspace_ref设计_v0.1.md`](workspace_ref设计_v0.1.md) |
| 16 | 2 | `file_id` | 有效 10 位 |
| 18 | 4 | `block_id` | 有效 28 位（与 ROWID 一致） |
| 22 | 6 | `page_lsn` | 最近修改的日志位置（48 位） |
| 28 | 4 | `reserved` | |

**`flags`（只含崩溃后必须存活的状态）**：

| 位 | 含义 |
| --- | --- |
| 0 | 页初始化完成（未完成的页不得使用） |
| 1 | 含跨页行片段 |
| 2 | **索引叶页**（仅 `page_type = 2` 时有意义） |
| 3–7 | 保留 |

> **不得放进页格式的状态**：「有空闲槽位可复用」可从槽位目录推导；「待回收」是运行期状态。这类信息属于空间管理/缓存层面，按 §5.2 的纪律排除。

**链指针不在描述区**——放在**页尾区**（§5.5、§9.1.1），使数据页不必付这 12 字节。

**没有 `generation` 字段**：文件重建时**分配新的 `file_id`、永不复用**，陈旧页引用由 `file_id` 不匹配检出，无需额外代次字段。

**`file_id` 与 `block_id` 分开存**（而非 pack 后的 ROWID）：页头可独立校验，且与 ROWID 位宽解耦。

**`workspace_ref` 校验成本为零**：哈希只在打开工作区时算一次并缓存，每页访问只是一次 8 字节整数比较。

### 5.4 事务区（32 字节，含默认 1 个 ITL）

**事务区头（8 字节）**

| 偏移 | 长度 | 字段 | 说明 |
| --- | --- | --- | --- |
| 32 | 2 | `itl_count` | 当前 ITL 槽数（从 `INITRANS` 起，动态扩展） |
| 34 | 6 | 保留 | 见下 |

> `itl_max` **不在页头**——它是**段级属性**（对应 Oracle 的 `MAXTRANS`），存于**段头**（§4.2）。页头只留 `itl_count`。
> `last_cleanup` 暂不设字段（我们采用即时清除，见 §11.1.1）；保留区在 P0 确认后可作他用。

**ITL 条目（24 字节，偏移 40）**

字段宽度**按本设计自身的度量推导**，不是照搬 Oracle：

| 偏移 | 长度 | 字段 | 宽度依据 |
| --- | --- | --- | --- |
| 40 | 6 | `txn_id` | 单调递增、**永不复用**。48 位按 1000 事务/秒可用 8900 年，故**不需要** Oracle 那种 `usn.slot.wrap` 三段式回绕结构 |
| 46 | 6 | `undo_ptr` | **与 ROWID 同构同宽**：`file_id(10) + block_id(28) + 页内偏移(10)`。因 Undo 存于 file 1 的页中，物理地址比 LSN 更直接，且与已定的页复用规则一致 |
| 52 | 6 | `commit_seq` | **与 `page_lsn` 同宽**（48 位）。同样按 1000 提交/秒可用 8900 年 |
| 58 | 2 | `lock_cnt` | 本事务在本块锁定的行数——ITL 槽回收条件。页内槽位上限 1024，11 位足够 |
| 60 | 1 | `flags` | 空闲 / 活动 / 已提交 / 已回滚 |
| 61 | 3 | 保留 | |

**合计 24 字节**——结果与 Oracle 相同，但构成更简单：**无回绕序号**（`txn_id` 单调不复用）、**无 FREELIST 空闲空间信用**（我们不使用 FREELIST）。

**各字段的作用**：

| 字段 | 作用 |
| --- | --- |
| `txn_id` | 锁冲突判定（这行是不是我自己锁的） |
| `undo_ptr` | 一致性读重建旧版本时的 Undo 入口 |
| `commit_seq` | **提交序号**；未提交为特殊值 |
| `lock_cnt` | ITL 槽回收条件 |
| `flags` | 状态位 |

**`commit_seq` 是 ITL 的核心**：它让**可见性判定在块内自包含**——读一页即可判断"改这行的事务提交了没有、提交序号是多少"，**不需要任何全局事务状态表**。这是本设计敢不设全局事务表的前提。

**行锁由 ITL 承载，不用全局锁表**：一行的锁状态就是它的 `itl_slot` 所指的 ITL 条目——判断"这行被锁了吗"＝读该 ITL 的 `txn_id`；判断"是不是我自己锁的"＝比对 `txn_id`。

| | ITL 式（采用） | 全局锁表式 |
| --- | --- | --- |
| 锁信息位置 | 数据块内 | 内存全局结构 |
| 内存开销 | 无 | 与活动锁数成正比 |
| 全局热点 | **无** | 锁表是全局争用点 |
| 崩溃恢复 | 随数据页自然一致 | 需重建锁表 |

这使 `REQ-TXN-002`（行锁）的实现方式明确为"ITL 槽占用"，而 `REQ-TXN-005`（读路径不加锁）的精确含义是：**读只读 ITL 条目判断可见性，不获取、不等待任何锁**。

**默认 `INITRANS = 1`**：写并发低，1 个槽足够。

#### 5.4.1 ITL 槽的扩展与耗尽

1. 事务修改块中行前，先找空闲槽（`flags` 示空闲，或 `lock_cnt = 0` 且已提交）
2. 未找到则**动态扩展** `itl_count`（受 `itl_max` 限制）——页头向后推移，空闲区相应减少
3. 达 `itl_max` 仍无空槽 → 该事务**等待**，**不得静默失败**

`itl_max` 的默认值与上限 P0 冻结。

### 5.5 空间区（4 字节）

| 偏移 | 长度 | 字段 | 说明 |
| --- | --- | --- | --- |
| 64 | 2 | `slot_count` | 槽位数（含已删槽） |
| 66 | 2 | `free_end` | 空闲区结束（行数据起始） |

> 固定头合计 **68 字节** = 描述区 32 + 事务区 32 + 空间区 4（4 字节对齐）。
> 若 `itl_count > 1`，每增一槽页头后移 24 字节。

**`free_start` 可推导**：`固定头末尾 + slot_count × 2`，不单独存——按 §5.2 的纪律，能推导的不进页格式。

### 5.6 页类型

| 值 | 类型 | 用途 |
| --- | --- | --- |
| 1 | 数据页 | 堆表行 |
| 2 | 索引页 | B+Tree 分支与叶 |
| 3 | 邻接页 | 按 `src` 聚簇的边 |
| 4 | 元数据页 | file 0 内的目录 |
| 5 | 引导页 | file 0 块 0，格式永久固定 |
| 6 | Undo 页 | file 1 |
| 7 | 临时页 | file 2，不持久化 |
| 8 | 位图页 | 区分配位图 |
| 9 | 段头页 | 段的首页 |
| 10 | ANN 索引页 | HNSW / IVFFlat |

### 5.7 槽位目录与空闲管理

**每个槽位 2 字节**：

```text
位 15–2 (14 位)：行数据起始偏移（0–16383，恰好覆盖 16KB 页）
位 1–0  (2 位)：状态 —— 0 空闲 / 1 正常行 / 2 转发指针 / 3 片段头
```

**行长不存于槽位**——存于行头。若槽位存 `(偏移, 长度)` 需 4 字节，1024 槽即 4KB（页的 25%）；2 字节方案为 2KB（12.5%）。

**槽位上限 1024** —— 与 ROWID 的 `row_id` 10 位**耦合，两者须同时修改**。

**空闲区**：页内只有一个连续空闲区 `[free_start, free_end)`，`free_start` 由 §5.5 推导。

**defrag（页内整理）**：空闲空间分散、无法容纳新行时，将活动行向页尾 compaction，合并空闲区。这是 Oracle"块内重组"的对应机制。整理**必须更新所有槽位偏移**且受 WAL 保护。

### 5.8 页尾区

**页尾区大小由 `page_type` 决定**，位于页的最末尾：

| 页类别 | 页尾区 | 内容 |
| --- | --- | --- |
| 数据页、Undo 页等 | 4 字节 | 页尾校验 |
| **索引页** | 16 字节 | `link_prev`(6) + `link_next`(6) + 页尾校验(4) |

偏移（索引页）：`link_prev` 在 16368–16373，`link_next` 在 16374–16379，校验在 16380–16383。

**页尾校验始终在最后 4 字节**——检查器读一页时先看末尾即可，无需先判断页类型。

#### 页尾校验的作用

页最后 4 字节存放**头部关键字段的副本**（`page_type` + `mod_seq` + `page_lsn` 低位）。

**作用**：读页时**对比头尾**，不一致即为**断裂块**（fractured block）——检出"只写了一半"。

**比固定哨兵强在哪**：固定哨兵只能检出"尾部没写"；头尾副本对比还能检出"头部是新的、尾部还是旧的"（或反之），覆盖面更广。

**边界（必须写明）**：头尾匹配**不能保证数据无损坏**——那由 `checksum` 负责。**两者互补，不是替代关系**：

| 机制 | 职责 | 成本 |
| --- | --- | --- |
| 页尾校验 | 检出**断裂块**（部分写入） | 极低——一次 4 字节比较 |
| `checksum` | 完整**数据完整性** | 全页计算 |

> `logging = none` 的表**依赖这两层**检出撕裂页。
> 本机制参照 Oracle 的 `tailchk`（块尾保存 SCN Base 低位、块类型、SCN Seq 的副本）。

## 6 行

### 6.1 行头

| 偏移 | 长度 | 字段 |
| --- | --- | --- |
| 0 | 1 | `row_flags` |
| 1 | 1 | **`itl_slot`** |
| 2 | 2 | `row_len`（含行头） |
| 4 | 2 | `col_count` |
| 6 | 2 | `null_bitmap_len` |
| 8 | 2 | `var_col_count` |
| 10 | *n* | `null_bitmap` |
| | *2m* | `var_offsets` |
| | | 列数据（定长列在前，变长列在后） |

**`row_flags`**：位 0 = **已删除**；位 1 = 已迁移（本槽位是转发指针）；位 2 = 跨页行片段；位 3 = 含大字段。

**`itl_slot`**：指向本页事务区中的 ITL 槽**索引**，`0xFF` 表示无。这是**行→ITL→Undo** 链条的第一环，一致性读据此定位该行的 Undo 记录（见 §5.4）。

取值方式：**单独 1 字节**，不复用 `row_flags` 的位——读取少一次判位分支，行头的可读性与访问速度比这 1 字节值钱。

**行头不含**版本号、时间戳、**事务 ID**。行内只有 `itl_slot` 这个**索引**，事务本身的标识、提交序号、Undo 位置都在 ITL 里（块级共享，多行共用一条）——与"存储层不承载版本与事务语义"一致，且避免行头膨胀。

**NULL 位图**：字段缺失 / JSON null / SQL NULL **在存储层是不同表示**，不可压成一位。

### 6.2 行迁移（转发指针）

行更新后变长、原页放不下时：

```text
原槽位：状态 = 2（转发指针），行体只放 6 字节新 ROWID
新位置：完整行，槽位状态 = 1
```

- **原槽位的 ROWID 保持不变**（稳定入口）——**索引不需要更新**，仍指向原 ROWID，经转发指针到达。
- **转发指针可更新多次**：行再增长就再迁移一次，只需更新原槽位的转发指针。**不需要**"头片段不二次迁移"那类转换规则——行迁移在写少读多的画像下本就罕见，二次迁移更罕见，**不为小概率事件增加设计复杂度**。
- 只有当行**超过单页容量**时才转向**行片段链**（§6.3）——那是另一个触发条件，与迁移解耦。
- 转发指针受 WAL 保护。
- **代价**：多读一页。故需 `PCTFREE` 类预留比例降低迁移概率（P0 冻结）。

### 6.3 跨页行（行片段链）

行首次插入即超过单页可用空间时（大 JSON、高维向量）：

```text
头片段（槽位状态 = 3）：行头 + flag 位 2 + 指向下一片段的 ROWID
中间片段：片段头（下一片段 ROWID）+ 数据
尾片段：片段头（下一片段 = NULL）+ 数据
```

- 只有**头片段**有稳定 ROWID 并出现在索引中。
- 链**必须受 WAL 保护**——任一点中断后可恢复为一致状态，不得出现半截链。
- 链长度**有界**，超限返回明确错误（上界 P0 冻结）。
- 页头 `frag_used` 用于空间核算。

> **与 16KB 页的关系**：选 16KB 正是为了让**主流维度向量（≤3072 维，12KB）不落进这条路径**。跨页是例外路径，不是热路径。

### 6.4 删除与槽位复用

| 步骤 | 动作 |
| --- | --- |
| 1 | 置 `row_flags` 位 0（已删除），写 Undo |
| 2 | **索引项随事务一并移除**（删除即移除、回滚即恢复） |
| 3 | 提交后槽位置空（状态 0），可被复用 |
| 4 | 空间由 defrag 合并，**不在删除时立即回收** |

**为何不需要代次**：索引项与行**同生共死**，不存在"索引项比行活得更久"的窗口，因此不会出现陈旧索引项指向被复用槽位的情形。这是**用机制排除**，而非用代次检测。

**已知行为**（非缺陷）：RC 下索引扫描可能漏读语句开始后被并发删除的行——索引项已移除，堆中 Undo 无机会被使用。此为 Oracle 同类模型的既有取舍，须在测试基线中断言"**允许漏读**"。

## 7 ROWID

```text
ROWID = 48 位 = 6 字节
        file_id   10 位  → 1024 文件（表空间内相对编号）
        block_id  28 位  → 268,435,456 块 × 16KB = 4 TiB/文件
        row_id    10 位  → 1024 槽（与页内槽位上限耦合）
```

| 项 | 规定 |
| --- | --- |
| 容量 | 单文件 **4 TiB**；每表空间 1024 文件 = **4 PiB** |
| 代次 | **不含**（见 §6.4） |
| 作用域 | **表空间内相对地址**——不同工作区会出现相同 ROWID |
| 共享结构 | 缓冲池键、日志、诊断、审计**必须另带工作区标识**；页头 `workspace_ref` 作为兜底 |
| 用户可见性 | **否**——不得作为对外持久引用或业务标识 |
| 行锁 | **不得**用 ROWID 定位行锁（须用逻辑行标识） |

| --- | --- | --- |

## 9 索引的物理组织

### 9.1 B+Tree（通用索引）

- 页类型 2；叶项 = `键 + ROWID(6B)`；分支项 = `键 + 子页指针(6B)`（宽度统一，`row_id` 部分置 0）。
- **叶页/分支页的区分**用 `flags` 位 2（不额外占字节）。
- 支持唯一键、复合键、范围访问。
- **索引页与数据页结构完全相同**，只有 `page_type` 不同——空间管理、槽位目录、defrag、页尾校验全部复用。
- 并发分裂协议须**先产出证据包**再实现（涉及 Lehman-Yao 类协议与 right-link）。
- 分裂是**系统操作**，需独立恢复协议，不得当作业务事务失败忽略。

#### 9.1.1 叶页链表：双向（已确认）

叶页通过 `link_prev` / `link_next` 连成**双向链表**。字段位于**页尾区**（§5.8），**只有索引页付这 12 字节**——数据页的页尾区仅 4 字节校验。

**为什么双链**：Oracle 的索引叶块即为双向链表，知识库原文称其"**是实现索引范围扫描最关键的技术**"，支持升序与降序两个方向。**"取最近 N 条"在 Agent 场景是高频模式**（最近的会话轮次、最近的记忆），且 SQL 子集含 `ORDER BY`——反向扫描不是边角需求。

**并发分裂时的链维护**：分裂 P 为 P 与 P′ 时，

```text
P.link_next  = P′      ← 碰 P
P′.link_next = Q       ← 碰 P′
P′.link_prev = P       ← 碰 P′
Q.link_prev  = P′      ← ★ 碰第三页 Q
```

只有 `Q.link_prev` 需要碰第三页——这正是单链不需要而双链需要的。

**采用急切更新**（非懒惰修复）：

| | 急切更新（采用） | 懒惰修复 |
| --- | --- | --- |
| 分裂开销 | 3 页、2 个 latch | 2 页 |
| 读者逻辑 | **简单——`link_prev` 永远正确** | 需检出并修正陈旧的 `link_prev` |

取 Q 的 latch **不会死锁**——分裂一律从左向右推进，锁序单调。我们是多写者低争用，分裂本身罕见，多取一个 latch 代价很小；而**读路径应保持简单**，不应用懒惰修复给它加逻辑。

#### 9.1.2 空叶页必须仍可在搜索树中定位

索引项随删除事务移除（REQ-STO-009），因此**叶页可能被删空**。

**要求**：空叶页**不得**从搜索树中失联——它仍须能被父页的路由键找到。

Oracle 的做法可参考：即使行数为 0，**行索引的第一个条目仍然有效并指向最后删除的行**，从而使空叶块可被定位。

具体实现方式（保留占位项 / 父页保留路由键 / 延迟回收空页）须在索引页规格中定案，**但"空叶页可定位"这条不变量必须满足**——否则搜索树会断裂，导致查不到本应存在的键。

### 9.2 图的边（已确认：按 `src` 聚簇）

```text
出边：邻接页（page_type=3），按 (src, edge_id) 聚簇，边数据内联
      → 一跳出边遍历 = 1 次范围读（度 10 的节点通常 1 页）

入边：覆盖索引 (dst) → (src, edge_id, label)
      → "谁指向我、是什么关系" 完全不用回表
```

**为何入边索引要覆盖**：基本形态下入边遍历是「1 次索引扫 + N 次按 (src, edge_id) 回查」，而这 N 次落**不同的 src** 上，大概率 N 次随机 I/O。多存 `label` 换掉这 N 次随机 I/O。

**代价**：插入边变为 B+Tree 插入（但图本就事务型，成本相当）；删除节点时入边需索引扫 + 逐个查找；边换端点等于删+增（边通常不换端点，可接受）；高度数节点邻接区跨页时**优雅退化**，不做专项优化。

### 9.3 ANN 索引

- **必须磁盘型**（页类型 10），不能假设向量常驻内存。
- 参照 pgvector 的 HNSW 页布局（metapage / element tuple / neighbor tuple）。
- 是可重建的派生索引，以工作区 generation + 源提交水位 + 完整性清单控制激活。

## 10 向量

- **列类型**（pgvector 式），不是独立集合：`VECTOR(n)`，维度写在类型里。
- **只能是可选列**——无向量的工作区零开销。
- 距离度量由**索引的操作符类**决定（L2 / 余弦 / 内积），与 pgvector 一致。
- 模型元数据（`embedding_model`、`model_revision`）建议挂**列级**，用于阻止跨模型混搜（pgvector 本身不跟踪模型）。
- `halfvec`（半精度）保留为后续扩展的优化项，不作 V1.0 必选。

## 11 持久化与恢复

### 11.1 WAL 规则（继承总体方案 §8）

1. 先写 Undo 与日志描述，再修改数据页。
2. 数据页持久化前，其 `page_lsn` 对应的日志**必须已持久化**。
3. **提交响应必须晚于提交日志的耐久确认**（可 group commit）。
4. Snapshot 用**提交序号**，WAL 用 **LSN**，**两者不得混用**（类型层面禁止）。

#### 11.1.1 提交流程与 ITL 更新

由于 ITL 条目承载 `commit_seq`（§5.4），**提交时需要把提交序号写入该事务修改过的每个块的 ITL**。

**采用即时清除**（而非 Oracle 的延迟块清除）：

| | 即时清除（采用） | 延迟清除（Oracle） |
| --- | --- | --- |
| 提交时 | 更新所有已修改块的 ITL | 只标事务表，等首个读者清理 |
| 读路径 | 简单——ITL 里已有确定的提交序号 | 需在读取时顺便清理 |
| 提交代价 | 与修改块数成正比 | 常数 |
| 适用 | **短事务、写量小、触及块少** | 高并发扩展性 |

**选即时清除的理由**：我们的画像是短事务、低写并发、触及块少，即时更新的代价很低；而**读是我们最该保护的路径**，不应用延迟清除给它增加复杂度。

**代价**：事务需在内存中跟踪"我改过哪些块"。短事务可接受；若将来出现大事务，再评估是否需要延迟清除。

> 提交时更新 ITL 只写内存页 + WAL 记录，**不需要等数据页落盘**——因此不拖慢 `fsync` 关键路径（规则 3）。

### 11.2 缓存策略与恢复

steal + no-force，故恢复需同时处理重做与撤销。三阶段：

1. **分析**：从最近检查点重建事务状态表与脏页表，确定重做起点。
2. **重做**：从重做起点重放；按 `page_lsn` 判定已包含的修改并跳过（**幂等**）。
3. **撤销**：对未完成事务反向应用 Undo，写补偿记录（**可重入**）。

### 11.3 控制文件更新时机

| 触发 | 更新哪个 |
| --- | --- |
| 日志切换 | **工作区控制文件**（redo 序列号、检查点） |
| 建/删工作区、新增数据文件 | **全局控制文件** + 工作区控制文件 |

**全局控制文件绝不在提交关键路径上。**

### 11.4 按表类型的持久化差异

| 表类型 | 崩溃后的保证 |
| --- | --- |
| `logging = full` | 已确认提交必存；未提交不可见 |
| `logging = redo_only` | 同上，但**无回滚能力**（表本身无多语句事务） |
| `logging = none` | **可丢最近写入、可出现撕裂页**（由校验和检出，该页数据丢弃） |
