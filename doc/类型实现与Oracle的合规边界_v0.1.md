# 类型实现与 Oracle 的合规边界（v0.1）

**性质**：**工程备忘，不是法律意见。** 目的是把"为什么可以照着 Oracle 的类型内部实现来做"
这个判断的**依据、边界与红线**记在明处，供设计评审与后续外部咨询使用。

日期：2026-10-04　　适用：`spec/TYP.md` 及全部类型编码实现

---

## 1 结论

**照着 Oracle 的类型内部编码实现，风险可控。** 三条理由：

| # | 理由 |
| --- | --- |
| **1** | **格式是 Oracle 主动公开的。** Oracle 自己的 OCI 文档给出了 `NUMBER` 的逐字节布局——符号位、基 100 指数（偏移 65）、尾数每字节基 100、正数 `+1` / 负数 `101−值`、负数尾部补 `102`、最多 20 个尾数字节、38 位精度。**公开披露的信息不构成商业秘密**，也不需要我们做任何反编译 |
| **2** | **那个时代的专利早已过期。** `NUMBER` / `DATE` 的格式自 1980s–90s 沿用至今，按专利 20 年期限已过 |
| **3** | **公开检索未发现"格式本身"的专利。** 检索到的相关专利保护的是**别的东西**（§3） |

**并且我们只承诺行为、不承诺字节**（REQ-TYP-004）——见 §5。这一条是兜底：

> **万一某一项编码将来确实撞上专利，改编码即可，不必推倒重来。**

---

## 2 三条法律路径，各自的暴露

| 路径 | 保护什么 | **我们的暴露** | 对策 |
| --- | --- | --- | --- |
| **专利** | 具体技术方案（**权利要求项**） | **低** | §3、§4 |
| **著作权** | 代码与文档的**表达** | **中**——风险**不在"用它的格式"，在照抄它的文字或代码** | §4 |
| **商业秘密** | **未公开**的信息 | **低**——只要不接触源码 | §4 的红线 |

**关键判断**：**格式属于"功能与事实"，不属于"表达"。**
著作权保护表达、不保护功能与接口，这是长期稳定的框架
（`Google v. Oracle` 走的也是这条路，且核心争议在 API 声明与实现，不在数据格式）。

## 3 检索到的相关专利，以及它们保护什么

| 专利 | 谁 | 保护什么 | 对我们的意义 |
| --- | --- | --- | --- |
| **JP2013210838A** / **US20120259906** | 第三方（富士通系） | **硬件算术电路**——电路**直接对 Oracle NUMBER 格式做运算** | **Oracle 的格式对它们是"现有技术"**。它们能申请的是"用电路直接算"这件事，**不是格式**。我们不造那种电路，**不落入其权利要求** |
| **US10685021B2**（Oracle，2017 申请、2020 授权） | Oracle | **基于类型系统的编译期编码推断**——查询编译时插入 transcode 算子，为向量化避免反复解码 | **唯一一项"Oracle 近年在类型系统上仍在申请专利"的证据。** 权利要求是那套**编译期推断机制**，与"实现一套类型的编码与算术"不是一回事。**但它说明类型系统不是专利空白区**——涉及隐式转换与编码推断时须单独检索 |

> **检索不到"格式专利"不等于不存在。** 诉讼和解多不公开；
> 正式结论需要专利律师做 **FTO（自由实施）检索**，逐项比对**权利要求**与**期限**
> （含续案、分案），并**分地域**——专利有地域性，国内实施看中国专利。

## 4 红线与纪律

### 4.1 硬红线

> **团队不得接触 Oracle 源码。**

一旦有人拿过，"独立开发"的抗辩就弱了——**这是唯一一条一旦破坏就无法补救的**。
现有的知识库来自公开 MOS 条目、博客与块转储，**不含源码**，这条红线目前是干净的。

### 4.2 要小心的一件事

**不要把知识库里的文档原文搬进我们的规范。**

| 可以 | 不可以 |
| --- | --- |
| 使用**事实**——"指数字节的低 7 位是偏移 65 的基 100 指数" | **照抄文字**——整段搬运 Oracle 文档的措辞 |
| 使用**行为**——空字符串等同于 NULL | 复制其**示例、表格排版、注释** |

**凡引用处记出处**——知识库条目本就带源，保持这一点即可。

### 4.3 主动做的一件事

**把 conformance suite 当证据来建设。**

clean-room 实务里被反复点名为"**行为兼容而非文本复制**的最强实际证据"的就是它。
REQ-TYP-008 已经要求"不少于 1 万条生成用例，记录版本、NLS、SQL、绑定与结果"——
**那正是 conformance suite**。

> **它原来是为质量提的，顺带就是证据。** 这一点必须写进文档：
> 将来做的人可能只当它是测试要求，从而丢掉版本记录、丢掉可复现性——
> **而那些字段正是它作为证据的部分。**

## 5 REQ-TYP-004 的法律价值

需求原文：

> 类型兼容是声明、取值、赋值、转换、比较与客户端往返的**行为契约**，
> **不要求内部字节编码相同**。

**这一句同时是最佳工程判断与最佳法律位置**：

| 角度 | 含义 |
| --- | --- |
| **工程** | 内部编码是我们的实现细节，不该成为对外契约——**改了不该影响任何调用方** |
| **法律** | 我们承诺的是**行为**，不是**字节**。**撞上专利时改编码即可**，对外契约不受影响 |

**"完全参考 Oracle 的实现"与这一条不冲突**：前者是我们**当前的选择**（因为它被证明高效、
适用面广），后者是我们**保留的自由**。**选择可以变，自由不能丢。**

## 6 未决与后续

| 项 | 什么时候做 |
| --- | --- |
| **FTO 检索**（中国 / 美国 / 欧洲，逐项比对权利要求与期限） | 正式立项时，由专利律师做 |
| **隐式转换与编码推断**的单独检索（对应 `US10685021B2` 的方向） | 实现隐式转换之前 |
| 类型名的商标评估（`NUMBER` / `VARCHAR2` / `DATE`） | 对外发布前。**注：功能性类型名，且大量兼容产品在用**（OceanBase、PolarDB、GaussDB、达梦、金仓、LightDB 等） |
| conformance suite 的**证据形态**（版本、NLS、绑定、结果的可复现记录） | 随 REQ-TYP-008 的建设一并定 |

## 7 一处必须防止的误读

**"别家也在做兼容、也没被起诉"不是法律保障。**

兼容产品的广泛存在说明**商业上可行**，但检索不到诉讼记录，
**既可能因为没发生，也可能因为和解不公开**。

**本备忘的结论建立在 §1 的三条理由上，不建立在他人的行为上。**
