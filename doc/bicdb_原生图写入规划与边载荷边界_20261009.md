# 原生图写入规划与边载荷边界（2026-10-09）

## 问题与行为

v3 图的物理边已在邻接页中，但此前完整写入加载仍把它们转换成 v2 的 checksum/chunk 行，再用于差异规划。这个中间表示重复构造全图边记录，并错误地把 v2 完整边 JSON 的 1023 块上限应用于 v3：合法的原生载荷位于边界时，额外的 id/source/target 字段会使旧表示超限。

本轮 v3 写入规划的 StorageImage 只保留节点记录、逻辑 header 和每条边的规范字节数。已解码的原生边直接进入 Graph，不再构造或保留 kind-2 行。完整边 JSON 逐实体编码用于总载荷预算，大小缓存用于后续增长、缩小、删除的净字节计算。节点记录仍执行原有校验和、连续块、身份和预算验证；原生边仍验证唯一身份、端点、类型、属性和声明计数。

这个 image 是规划用表示，不能当作完整 v2 图序列化或另存为第二份拓扑。它的 rows 包含节点及逻辑 header，但不包含 header 声明的边；拓扑持久化必须使用显式原生计划。

## 快照与模板恢复

逻辑快照预验证使用原生规划 image，真实原生边载荷验证与实际写入共享同一个函数。导入目标升级并重新读取空目标的原生 image 后，分别生成节点记录补丁、属性/访问索引增量和原生节点/边计划，再联合持久化。已删除通过中间 kind-2 补丁重新推导原生拓扑的旧路径。辅助全文及队列仍使用记录补丁；对图主体没有显式拓扑计划的持久化请求直接拒绝。

原生边属性修改可能既不改变节点行，也不改变分配器、节点数、边数。如果目标尚无用户索引或全文队列，heap/index 补丁都可能为空。跳过写入的判断现在同时检查原生计划：只有所有记录、索引和原生操作均为空才提前返回。这样模板首次边属性修改也会实际写入，并保持旧快照、回滚、全文维护及重启的一致性。

## 保持的边界与剩余成本

本轮没有扩大属性或单边载荷限制。属性映射仍最多 1 MiB；原生类型及属性文档仍最多 4096 × 1023 字节（4092 KiB），并受工作区 max_text_bytes 约束。边界用例使用很长的关系类型及小属性映射，验证原生文档刚好达到上限及超过一个字节拒绝；它不是 100 MiB 单属性支持声明。

普通写入仍完整加载并验证 Graph，大小缓存仍为 O(edges)，逐实体精确计算仍有序列化成本。没有完成部分图加载、修改覆盖层、持久索引唯一性探测、一般 NodeMove、旧版本 GC 或 RSS 证明。manifest 的计数/分配器 header 在真实边属性更新后可以不变；未来 SQL 并发提交校验不能仅依赖这个 header，必须另有源版本/提交代或等价并发证明。
