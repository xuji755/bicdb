## 1 架构原则：一个引擎 + 表选项

**已确认**：不做多套存储引擎。页格式、ROWID、文件布局、控制文件、WAL 基础设施**全部统一**；表之间的差异收敛为**表级选项**。

理由：若一表一套引擎，备份、恢复、检查器、配额、诊断这些横切能力都要做多套，复杂度不成比例。表选项能拿到绝大部分收益，成本低一个数量级。

## 2 表选项

```text
表选项
├── transactional : bool                    是否参与显式多语句事务
├── logging       : full | redo_only | none
├── update_mode   : in_place | append_only
├── retention     : none | <时长>           数据过期（TTL）
├── version_keep  : none | <个数>           版本保留数，超出自动淘汰
├── cleanup       : none | segment_drop | row_delete
└── embed         : none | async            向量自动派生
```

### 2.1 各选项的语义与代价

| 选项 | 取值 | 含义 | 关键代价 |
| --- | --- | --- | --- |
| `transactional` | `true` | 参与显式多语句事务，可回滚 | 需要 Undo |
| | `false` | **单行原子**，无多语句事务、无回滚 | 写入不能被回滚，需调用方接受 |
| `logging` | `full` | Undo + Redo | 最安全，最贵 |
| | `redo_only` | 只记 Redo | **无回滚能力**，但崩溃原子性与持久性保留 |
| | `none` | 都不记 | **撕裂页与丢已确认写入均可发生**，见表 2.2 |
| `update_mode` | `in_place` | 允许原地更新 | — |
| | `append_only` | 只追加，引擎拒绝 UPDATE | 可省 Undo；但需业务层接受"改 = 追加新版本" |
| `cleanup` | `segment_drop` | 按时间分段，**整段丢弃** | 需按时间聚簇；过期效率极高 |
| | `row_delete` | 逐行删除 | 实现简单，但有空间碎片与回收成本 |

### 2.2 `logging = none` 的边界（重要）

数据页可以不记 Redo，**但结构元数据不行**。

| 对象 | 是否必须受 WAL 保护 | 理由 |
| --- | --- | --- |
| 数据页 | ❌ 可不记 | 追加型表的撕裂页只出现在**追加前沿**，损失被限制在最近少量记录 |
| **页分配位图、段目录、控制文件** | ✅ **必须** | 这类元数据损坏会导致**整个表空间不可用**，不是"丢少量数据" |

**另需注意**：`logging = none` 省下的主要不是"写日志的 CPU"，而是**提交时的 fsync 等待**。收益来自同步不落盘。

## 3 五种表类型

| # | 表类型 | transactional | logging | update_mode | retention | version_keep | cleanup | embed |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 普通关系表 | ✅ | full | in_place | — | — | — | — |
| 2 | 配置表 | ❌ | redo_only | append_only | — | ✅ | row_delete | — |
| 3 | 会话表 | ❌ | **none** | append_only | ✅ | — | **segment_drop** | ✅ async |
| 4 | 图数据 | ✅ | full | in_place | — | — | — | — |
| 5 | 记忆表 | ❌ | redo_only | append_only | 见 §4.5 | ✅ | row_delete | ✅ async |

### 3.1 配置表

- **每次修改产生一个新版本**，不原地改字段。
- 建表时声明**保留版本数**，超出后**在插入时内联淘汰**（插入版本 N 后删除第 N−keep 个）。配置写入量小，内联是确定性的，不需要额外的后台任务与新鲜度语义。
- 需要 Redo（用户已确认）：配置丢失是用户可见的，而配置写入稀少，Redo 成本近零。

### 3.2 会话表

- 记录 Agent 会话历史，**只追加**。
- **`logging = none`**（用户确认）：接受丢失少量会话，换取写入效率。
- **`cleanup = segment_drop`**：按时间分段，TTL 到期**整段丢弃**，而非逐行删除。这是会话表最该优化的点——避开了"删除不降低 HWM"那类问题，也不需要逐行回收。
- **`embed = async`**：写入时不同步生成向量，由派生管线异步补。见 §5。

### 3.3 图数据

- `transactional = full`、`in_place`：图是**可原地更新**的，与追加型表不同。
- 边的物理组织见 `doc/存储容量与规模基线_v0.1.md` §4（按 `src` 聚簇 + 入边覆盖索引）。

## 4 记忆表设计

### 4.1 状态拆解（**建议，待确认**）

设计文档 §10 提出的 `candidate / confirmed / superseded / expired / deleted` **混淆了四个不同维度**，建议拆开：

| 原枚举值 | 实际是什么 | 建议表达 |
| --- | --- | --- |
| `candidate` / `confirmed` | **来源权威性**（自动提取 vs 显式确认） | 创建时确定的**不可变属性** `authority` |
| `superseded` | **记忆之间的关系** | **图上的边**：`M2 -[supersedes]-> M1`（软失效） |
| `expired` | **时间计算的结果** | 由 `valid_to` 与当前时间**算出**，不存储 |
| `deleted` | **生命周期标记** | 追加 **tombstone**，不做硬删除 |

**收益**：记忆内容表变成**纯追加、无状态字段、无原地更新**，从而可以 `redo_only` 且不需要状态表。原先设想的"内容追加 + 状态原地更新需跨表事务"问题自动消失。

**代价**：查"当前有效记忆"变成组合条件（取最新版本 + 时间过滤 + 图上排除 superseded + 排除删除），图推理延迟高于向量检索。**可能需要异步物化"当前有效记忆"视图**（又一条带水位的派生管线）。

### 4.2 业界印证

| 我们的设计 | 业界对应 |
| --- | --- |
| 内容纯追加 | **mem0 v3 已从 ADD/UPDATE/DELETE 转向单遍 ADD-only**，文档原话："add() 是提交新的可记忆证据，**不是对当前状态表做 upsert**" |
| superseded 用图上的软失效 | Mem0g 用**软失效**而非删除，支持时间推理 |
| 不硬删除（用 tombstone） | mem0 v2 的**硬删除丢历史**是明确缺陷 |
| 时间区间表达有效性 | mem0 **缺一等的时间有效性**（不如 Graphiti），我们相对更强 |

### 4.3 三层与衰减（**建议，待确认**）

参考 PowerMem 的三层模型（映射认知科学）：

| 层 | 分数门槛 | 衰减率 | 我们的对应 |
| --- | --- | --- | --- |
| working | < 0.6 | 0.5（最快忘） | 会话表（短 TTL） |
| short_term | ≥ 0.6 | 1.5 | 中期记忆 |
| long_term | ≥ 0.8 | 2.0（最慢忘） | 长期记忆 |

**关键做法是惰性求值**：衰减**连续计算**（数学函数），但"遗忘/提升/归档"的决策**只在被访问时执行**，**不做后台批量扫描**。

因此 `current_retention` **不存储**，是算出来的；只需存少量字段（`initial_retention`、`last_reviewed`、`access_count`）。

### 4.4 访问跟踪：方案 C（**已确认**）

**问题**：PowerMem 的 `access_count++` 意味着**读操作产生写**。对读占绝对多数的画像，这会让读量直接变成写量，前提被破坏。

**选定方案 C**：**内存累积 + 定期批量刷盘**。

| 项 | 规定 |
| --- | --- |
| 性质 | 访问计数是**启发式数据**，非事务数据，**不受事务/Undo 保护** |
| 路径 | 累积在内存，定期批量落盘 |
| 崩溃影响 | 丢失上次刷盘点之后的计数 —— **仅使衰减曲线略偏，不是数据错误** |
| 必须写明 | 记忆的衰减与强化是**启发式**，**不保证精确**；需求文档与接口文档均须注明 |

> 这条约束是对"读多写少"画像的保护：**读路径不得产生同步写**。

### 4.5 长期记忆的 TTL（**建议，待确认**）

建议**不给长期记忆设 TTL**，只用显式删除（tombstone）。理由：长期记忆的价值就在"长期"，自动过期会丢掉事实；设计文档 §10 强调的"可遗忘性"是**用户主动要求删除**的场景。TTL 留给会话表与中期记忆。

### 4.6 中期记忆归类（**建议，待确认**）

建议归**普通关系表**（`transactional`、`full`、`in_place`）。理由：任务检查点会被**原地更新**（步进、恢复游标推进），不是追加型；且它需要与工作区事务同源，一致性要求最高。

### 4.7 去重与压缩是上层算法，不是存储职责

业界做法（PowerMem）：

- 精确去重：内容哈希
- 语义去重：embedding 余弦相似度 ≥ 0.95
- 压缩：贪心聚类 ≥ 0.85 + LLM 生成摘要

数据库只提供**能力**（哈希列、向量距离、聚类扫描），**判断权不在数据库**——与设计文档 §10"数据库不运行 LLM 判断价值"一致。

## 5 异步派生管线

会话表的向量生成（`embed = async`）与记忆的自动提取**是同一类东西**：**带水位的异步派生管线**。

| 需求 | 已有机制 |
| --- | --- |
| 知道哪些数据已处理过 | **水位**（REQ-RET-013 outbox 记录提交水位） |
| 记忆 ← 来源的可追溯 | **derived_link**（设计文档 §10） |
| 延迟期间检索的一致性 | **strict / eventual 新鲜度模式**（REQ-RET-015） |

### 5.1 提取服务的位置（**建议：库外**）

"自动提取"需要 LLM 判断哪些内容值得记，而设计文档 §1/§9/§10 把库内模型调用排除在 V1.0 之外。

**建议：提取服务在 bicdb 之外**——bicdb 只提供"按水位读会话数据"与"写记忆"两个接口，提取进程是独立配套服务（可同一发布包，架构上分开）。

**业界印证**：OceanBase 自己做 PowerMem 也选择了**中间件形态**（`StorageAdapter` 架在 OceanBase/PG/SQLite 之上），而非把记忆算法做进数据库内核。

### 5.2 对工作负载画像的影响

自动提取是**持续的后台写入**，不是偶发。虽量不大，但属"背景噪音"式写负载，需在需求文档 §2.2 补一行说明。

## 6 检索路径（**一条建议待确认**）

设计文档 §11 目前定的是"词项 + 向量"两路融合。

PowerMem 用**四路**：向量 + 全文 + **稀疏向量** + **图**。

建议**补上稀疏向量**作为第三路：它对精确标识符与长尾词效果好，而我们的场景里参数名、错误码、模型名这类精确词项很常见。图扩展我们已具备（设计文档 §11 已提"图扩展在候选之后"），但尚未纳入融合评分。

## 7 图并发写的治理（**建议，待确认**）

业界指出知识图在**多写者**下治理薄弱——"谁有权改写一条关系"未定义，KG 常被当作特例绕过事务。

我们的图是**多写者**的。建议在设计文档 §13 显式写明：

- 图上所有写**走工作区事务 + 行锁**，与普通表**一致**，不做特例
- "谁能改"由**工作区隔离**决定——不存在跨用户边
- 图的更新不得绕过 `REQ-TXN-*` 的任何一条

这项澄清的必要性在于：业界的警示针对的正是"KG 被当成特例"。
