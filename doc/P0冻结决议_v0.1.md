## 追加冻结项评审（2026-10-06）：实例级工作内存目标 `work_memory_target`

**背景**：工作内存/溢出管理（`doc/执行算子设计_v0.1.md` §4.2 的 WMM）需要
实例级全局硬上界——Oracle 形态的 `PGA_AGGREGATE_TARGET` 对应物。它是
`CONV` §8 名称清单**之外的新名字**（REQ-RES-001 的"查询内存"维度此前只有
工作区侧的 `max_query_memory`），故走一次冻结项评审。

**冻结值（✎ 初始值，按基准机推导）**：`work_memory_target = **4 GiB**`（默认；
可配置，调整走变更控制）。

**推导**：

| 步骤 | 数 | 依据 |
| --- | --- | --- |
| 物理内存 | 32 GiB | 第 1 项（基准机） |
| 给 OS 留 20% 后可用 | ≈ 25.6 GiB | 照 Oracle 的出发点（Note:223730.1 的 80%） |
| 已冻缓存预算 | 16 GiB | 第 1 项 |
| 剩余（连接/会话结构/工作内存） | ≈ 9.6 GiB | — |
| Oracle 指导值 | OLTP ≈ 5.1 GiB / DSS ≈ 12.8 GiB | Note:223730.1（80%×20% / 80%×50%） |
| **本库取 4 GiB** | = 缓存的 1/4、物理的 12.5%、余量的 ≈42% | 落在 OLTP 指导值下沿、偏保守——agent 负载以短查询为主，溢出有 temp 段兜底（4 GiB 配额） |

**共享池口径**（用户口径 2026-10-06）：`work_memory_target` 是**实例级共享池**
——所有租户、所有并发执行、所有**算子内存区**（work area，排序/哈希等单个
算子）都从这一个池按需分配；**不为算子内存区设任何参数**（这正是自动模式
取代 `sort_area_size`/`hash_area_size` 的意义）。`max_query_memory` 是**租户
配额**（我们的多租户隔离面），不是算子参数。

**并发核算**：8 执行线程；单算子内存区上限 = `min(池 × 5%, 该租户剩余额度)`
= min(204.8 MiB, 256 MiB) = **204.8 MiB**（5% 规则为**内部策略**、非配置项，
照 Oracle `3257077`）。常态 8 并发各 1 个内存区 ≈ 1.6 GiB ⇒ 余 ~2.4 GiB 应对
"一个查询多内存区"的叠加——超界即压缩/改档，**三态计数可见**（§4.2 监测
口径），这正是共享池该起的作用。

**备选与否决**：

| 备选 | 否决/采纳理由 |
| --- | --- |
| 2 GiB | 更保守，但 8 线程大排序易压入 one-pass；先 4 GiB、**以实测顾问口径回调** |
| 8 GiB | 贴近 DSS 档；挤占 OS 与非库进程余量（余量只剩 ~1.6 GiB） |
| 不设实例目标（只用每查询 256 MiB） | **= PG 形态**，并发下无全局上界（§4.2 已否决） |

**影响面**：① `CONV` §8 名称清单**新增一名** `work_memory_target`（实例侧
查询内存上限）；② REQ-RES-001"查询内存"维度的实例总上限获得名字；③ WMM
设计 §4.2；④ 验收：压小/压大预算时三态计数与 extra bytes 应对应变化
（顾问口径：**增大目标直到外存 I/O 不再明显下降且过分配计数 = 0**，
`2239823`/`786554.1`）。

**状态**：✅ **已冻结（2026-10-06，初始值）**；调数走需求变更控制
（需求文档 §9）。
