## 0 模型总述

### 0.1 三条检索路径，一条融合

| 路径 | 输入 | 产出 |
| --- | --- | --- |
| **词项**（REQ-RET-004） | 查询文本 | 按 BM25 评分的 `memory_id` 列表 |
| **向量**（REQ-RET-021） | 查询向量 | 按距离排序的 `memory_id` 列表 |
| **图扩展**（REQ-RET-009） | 前两者的候选 | 沿边扩展出的候选 |

**三者产出的是"不可比较的分数"** ✗——所以需要一个 **融合** 步骤（REQ-RET-007）✓，
而 **REQ-RET-008 明确禁止把分数直接相加** ✗✓。见 REQ-RET-007。

### 0.2 两条检索域：必须**分开执行**，不能"事后加过滤"

**REQ-RET-011 是这一域最重要的一条**：

> `public` 与私有**分开执行并显式融合**，
> **不得在全用户索引中事后添加 `user_id` 过滤**——"**架构上不存在全用户索引**"。

**它同时是安全要求与架构要求**：

| | |
| --- | --- |
| **安全** | 一个全用户索引意味着**所有用户的词项与向量混在一个结构里** ✗。任何一处过滤遗漏都是跨用户泄露 ✗ |
| **架构** | 它逼着我们把"每条检索路径"都做成**按工作区独立**的 ✓——而 §12 的存储侧本来就是按工作区独立的（REQ-ISO-001）✓ |

**所以：本域的一切索引都是"某工作区自己的索引"** ✗✓。
**REQ-RET-005 是同一条理由的另一种说法**：
"索引文件归属工作区；**不得跨用户构建全局词典与正文缓存**" ✓——
**跨用户的词典**会同时泄露"别人有什么词" ✗，且与 §13.9 的"不跨主体内容去重"同源 ✓。

### 0.3 派生索引：可重建、不参与事务

**REQ-RET-013 / 014 / 022 三条合起来定义一个机制**：

```text
写事务提交
  └─ 在该工作区内写一条 outbox 记录（目标 revision、提交水位）
       └─ 异步任务消费它
            └─ 构建 / 更新派生索引（记录 generation + 源提交水位 + 完整性清单）
                 └─ 满足完整性才**激活**——否则它是残缺的，没人会读它
```

**四条性质**：

| 性质 | 来自 |
| --- | --- |
| **幂等**——重复任务不产生额外效果 | REQ-RET-014 |
| **不回退**——**旧任务不得覆盖新 revision** | REQ-RET-014（乱序投递是常态，不是异常） |
| **可重建**——源数据是权威，索引丢了就重建 | REQ-RET-020 / 022 |
| **不激活残缺索引**——构建中断 → 不激活 | REQ-RET-022 |

> **"可重建"是本域最省力的一个定位**：它把一大批"索引出问题"的情况
> 从**故障处理**降级为**常规动作** ✗✓——
> 构建中断、索引退化、格式升级，**都走同一条路：重建**。

### 0.4 向量与 ANN：参照 pgvector

**本域的向量部分以 pgvector 的实现为参照**——它与我们的需求形状非常接近：
磁盘型索引、可重建、操作符类决定距离。存储架构 §9.3 已吸收其主要设计，
本节补**它踩过的坑**与**我们逐条怎么处理**。

#### pgvector 的三段页组织，以及我们的一处改动

| 段 | 内容 |
| --- | --- |
| **metapage** | 入口点（块号 + 偏移 + **层级**）、`m`、`ef_construction`、维度、格式版本 |
| **element** | 向量值 + 邻接数组 + 指向堆行的标识 |
| **neighbor** | 一个节点的邻接数组（每层一组） |

**我们的改动：邻居不内联在 element 里，而是独立的槽。** 为什么——

> pgvector 把邻居**内联**在 element 里，于是**"一条记录必须放下一页"**
> 直接限制了可索引的最大维度 ✗（`vector` 的索引上限 2000 维，
> 而存储上限是 16000）✓✓。
>
> **我们把邻居独立成槽**（§5.11 的"element / neighbor 用定长槽、由 `kind` 区分"）——
> 于是**维度只受"向量本身要放下一页"约束**，而**邻居的数量由独立的槽承担** ✓。
> 两者各自撑到自己的上限，不必互相挤。

**上限的换算**（页 16KB，页头 68B、页尾 4B、页体头 8B）：

```text
element 可用 ≈ 16200B − element 头
每维 FLOAT32 = 4B  →  可索引维度上限约 4000 维
```

**超过一页的向量走行片段链**（REQ-RET-020："高维向量支持跨页存储"）✓——
而**原始向量是权威数据**，索引只是派生 ✓。

#### pgvector 的四个已知问题，逐条对应

| # | pgvector 的问题 | **我们** |
| --- | --- | --- |
| **①** | **构建内存大**——基准机 32GB、数据可达 60GB（§1.3），不可能全量驻留 | **分块构建**：分批插入、分批刷盘，内存与**当前批次**成正比而非与总规模成正比（§9.3.2） |
| **②** | **参数要人工调**（`m` / `ef_construction` / `ef_search`） | **引擎按维度、规模、目标召回给默认值**（§9.3.2）。**运行期参数**（`ef_search` 一类）仍可调，但**有一个能用的默认** |
| **③** | **构建会失败或中断** | **可重建的派生索引**——失败不是灾难，"重建"是常规动作（§0.3） |
| **④** | **过滤下的召回塌陷**——先取 `ef_search` 个候选再过滤，高选择性过滤后"不足 K" ✗ | 见下 |

**④ 值得单说，因为它正是 REQ-RET-023 / 026 针对的那个问题**：

> pgvector 的早期版本中，带 `WHERE` 过滤的 ANN 查询会**先取候选、再过滤**，
> 于是**过滤性强的时候返回数远少于 K** ✗。它后来加了**迭代索引扫描**
> （取一批、过滤、不够再取，而不是一次取完）✓。
>
> **我们的 REQ-RET-023 从另一头堵**："每个候选回查源 revision、事务可见性、
> 状态及过滤条件；**不足 K 时不得补入不合法候选**" ✓——
> **宁少给，不给不该给的** ✓。
> 而 REQ-RET-026 说高选择性过滤**先过滤精确搜索**——即**放弃 ANN 走精确扫描** ✓，
> 这与迭代扫描是同一思路的两种实现，**且精确扫描的结果是确定的** ✓。

#### 距离度量由操作符类决定

pgvector 用**操作符类**绑定距离（`vector_l2_ops` / `vector_ip_ops` / `vector_cosine_ops`），
**用错距离的查询走不了那个索引** ✗。

**我们同构**（§9.3）：**距离度量由索引的操作数决定**（L2 / 余弦 / 内积，§10）。
**约束是硬的**：一个索引只服务一种距离 ✗——
要用另一种距离，就建另一个索引 ✓。**这与"一个索引一种排序"是同一条道理。**

### REQ-RET-001　全文检索的面向对象

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §11

#### 语义

全文检索面向**文档分块、参数名、错误码、SQL 标识符、模型名与实体名称**。

#### 规格

**这个列表本身是规格**——它划定了"检索要能命中的东西"，而且**它们的分词需求不同**：

| 类别 | 特征 | 影响 |
| --- | --- | --- |
| **文档分块** | 自然语言 | 需要**分词** |
| **参数名 / SQL 标识符** | 标识符——`snake_case`、`camelCase`、含下划线 | 分词器**会把它们切碎** ✗ |
| **错误码** | `BICDB-TXN-017` 一类**结构化串** | **必须整串命中** |
| **模型名 / 实体名称** | 混用 | 两者都要 |

**两组需求方向相反**（REQ-RET-002/003 正是针对这个）：
自然语言要**切碎**才检索得到，标识符**切碎就废了** ✗。
**所以字段必须分开存**——见 REQ-RET-003。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 固定数据集上的召回 | **可测**（REQ 的验收）——即需要一个基准集 |

#### 验收要点

- **构造**：覆盖上述五类的固定数据集。
- **预期**：**召回可测**，五类各有可判定的结果。

### REQ-RET-002　中文分词与固定分析器版本

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §11

#### 语义

支持**中文分词**与**精确词项字段**；**固定分析器版本**。

#### 规格

- **分析器版本是索引格式的一部分** ✗——换版本 ⇒ **旧索引的词项对不上** ✗；
- 所以：**分词版本变更触发新 generation 构建**（REQ 的验收）✓——
  这正是 §0.3 的"可重建"派上用场的地方 ✓；
- **中文分词必须有确定版本**：分词算法更新会改变切分结果 ✗，
  而**词项一旦切错，索引就查不到** ✗。

> **"固定版本"不是保守，是必需**：可变的分词器让**同一份文本在不同时间索引出不同结果** ✗，
> 而索引是**一次写、多次读**的——**读的时候不可能重新分词** ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 分析器版本变更 | **触发新 generation 构建**，不就地改旧索引 |
| 文档含分析器无法处理的字符 | **保留为单字符词项**，不丢弃 |

#### 验收要点

- **构造**：中文文本、混合中英、含标识符。
- **预期**：切分结果**由版本决定且可复现**；版本变更后**新 generation 的词项正确**。

### REQ-RET-003　标识符不能只靠自然语言分词

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §11

#### 语义

标识符**不应仅依赖自然语言分词**。

#### 规格

**解法是"两条索引路，不是一个聪明的分词器"**：

| 字段 | 处理 | 服务谁 |
| --- | --- | --- |
| **正文词项** | 分词后入倒排索引 | 自然语言检索 |
| **精确词项** | **整串**入倒排索引（不做分词） | 标识符、错误码、模型名 |

**为什么不做"聪明的分词器"**：一个"既能切中文、又能保住标识符"的分词器，
**它的行为会变得不可预测** ✗——而这正与 REQ-RET-002 的"固定版本"相冲突 ✓。
**两条路各自确定，比一条路猜得准更好。**

**并且要能被查询分开选择**：一个查询可以指定走哪条路（或都走，然后融合 ✓）。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 精确标识符查询 | **命中**（REQ 的验收）——且**不依赖分词结果** |
| 同名字符串既是标识符又是自然语言 | **两条路都有它**——由查询选路 |

#### 验收要点

- **构造**：`SELECT * FROM t`、`BICDB-TXN-017`、`embedding_model`。
- **预期**：**精确查询全部命中**。

### REQ-RET-004　有界的倒排索引与明文评分

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §11

#### 语义

首版实现**有界倒排索引**、**词项与短语子集**、**字段过滤**与 **BM25 或明确的基础评分**。

#### 规格

| 项 | 首版范围 |
| --- | --- |
| **索引** | **有界**倒排索引——**词项数、文档数、posting 长度都有上限** |
| **查询** | 词项；**短语子集**（不是任意布尔表达式） |
| **过滤** | 按字段 |
| **评分** | **BM25**，或另一套**有公开公式**的评分 |

**"有界"是重点**：无界的倒排索引在**长尾词项**上会让 posting 列表无限增长 ✗。
**上限触顶时的行为要定义**（丢弃最低频词项？拒绝？）——见待确认汇总。

**"评分公式有明文规格"（REQ 的验收）为什么重要**：
评分一旦是黑箱，**结果就不可解释、不可回归** ✗——
而检索结果的**排序变化**是最难定位的一类问题 ✓。

**字段过滤必须在倒排层做，不在事后做** ✗——理由与 REQ-RET-011 同：
事后过滤会让**"先取 top-K 再过滤"**重演 pgvector 的过滤塌陷 ✗（§0.4 ④）。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 词项超出索引上限 | 按明文规则处理（见待确认汇总），**不静默丢** |
| 短语超出支持的子集 | **拒绝**，指出不支持的构造 |

#### 验收要点

- **预期**：**评分公式有明文规格**；固定数据集上**评分可复现**。

### REQ-RET-005　索引按工作区独立

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §11

#### 语义

索引文件**归属工作区**；**不得跨用户构建全局词典与正文缓存**。

#### 规格

**与 REQ-RET-011 同源，这里补两处具体的东西**：

| 不得 | 为什么 |
| --- | --- |
| **全局词典** | 词典本身泄露"**别人有什么词**" ✗——它是**内容的存在性**，与 §13.9 拒绝跨主体去重是同一条理由 ✓ |
| **全局正文缓存** | 缓存的是**正文** ✗——比词典更直接 |

**"索引文件归属工作区"是结构性的**：索引的段在**工作区自己的文件**里 ✓
（§2.1：每工作区独立文件、不共享）。**所以"全局索引"在我们这里不是被禁止，是放不下** ✗✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 试图构建跨工作区词典 | **不存在这条路径** |
| `public` 的检索 | **它是另一个工作区的检索**——分开执行（REQ-RET-011） |

#### 验收要点

- **构造**：多工作区各自建索引。
- **预期**：**每工作区独立**（REQ 的验收）；**不存在跨工作区的索引结构**。

### REQ-RET-006　混合检索的输入

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §11

#### 语义

混合检索输入包含**查询文本、可选向量、类型与时间过滤、来源范围、`top_k` 与资源预算**。

#### 规格

| 输入 | 说明 |
| --- | --- |
| 查询文本 | 词项路 |
| 可选向量 | 向量路——**没有它就走纯词项检索** |
| 类型 / 时间过滤 | **在检索层生效**（不在事后）——见 REQ-RET-004 |
| 来源范围 | 限定检索哪些来源 |
| `top_k` | 期望条数 |
| **资源预算** | **本域特有的一项**——见下 |

**"资源预算"为什么必须在输入里**：ANN 的召回与**算力直接挂钩** ✗
（`ef_search` 越大召回越好、越慢）✗。**把预算作为输入**，
让"**在给定预算下给最好的结果**"成为契约 ✓，而不是"引擎自己猜该花多少" ✗。

**它同时是 REQ-RET-009 的落点**（图扩展"限定跳数与节点预算"✓）。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 预算不足以保证召回 | **返回结果 + 明确标注**（不假装完整）——见 REQ-RET-025 |
| 参数不可用 | **拒绝**，不静默忽略 |

#### 验收要点

- **预期**：**参数均可生效**（REQ 的验收）——即每个输入都可在结果中观察到它的作用。

### REQ-RET-007　融合：秩融合，不合并分数

**优先级**：应当　**阶段**：P2　**追溯**：总体方案 §11

#### 语义

词项与向量候选在**可见性校验后**去重融合；建议先采用 **RRF 等可解释的秩融合**。

#### 规格

**顺序不能颠倒**：

```text
各路检索 → **可见性校验** → 去重 → 融合
```

**"可见性校验在融合之前"** ✗✓——否则一个**不可见的**条目会占掉一个融合名额 ✗
（REQ-RET-012 的要求同此）。

**融合用秩，不用分数**（REQ-RET-008 的禁令）：

| | 分数相加（禁止）✗ | **秩融合（采用）** ✓ |
| --- | --- | --- |
| 前提 | 各路分数**可比**——而它们不可比 ✗ | **只需要排名** ✓ |
| RRF | — | `Σ 1/(k + rank_i)` |
| 可解释性 | 低——"为什么这条排第一"说不清 | **高——每路的原始排名都留着** ✓ |

**"记录各路原始分数与排名"（REQ 的验收）是本条的实质**：
只输出融合后的结果，**出问题时无从定位是哪一路错了** ✗。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 某一路失败（如索引不可用） | **降级为其余路**，并在结果中**标注**——不静默 |
| 同一 `memory_id` 出现在多路 | **去重**，保留各路排名 |

#### 验收要点

- **构造**：同一查询跑多路。
- **预期**：**记录各路原始分数与排名**（REQ 的验收）；融合结果**可由它们复算**。

### REQ-RET-008　不得把不可比较的分数相加

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §11

#### 语义

**不得把不可比较的分数直接相加**。

#### 规格

**这条是一条禁令，它约束的是实现里最自然的那个动作。**

| 路 | 分数是什么 | 量纲 |
| --- | --- | --- |
| 词项 | BM25 | 无上界，随语料变化 |
| 向量 | 距离（L2 / 余弦 / 内积） | **越小越好**（余弦）或**越大越好**（内积）✗ |
| 图扩展 | 边权或跳数 | 与上面两者无关 |

**它们连方向都不一致** ✗✓——"相加"不只是量纲错，是**连方向都错**。

> **为什么这条必须写成明文禁令**：把两路分数**归一化后加权求和**
> 看起来是"更精细的做法" ✗，而且在**单次测试里往往表现更好** ✗
> ——因为归一化参数是照着那一次调的。**它坏在跨查询、跨语料时不稳**，
> 而那时已经很难归因了 ✓。

**"融合逻辑有明文依据"（REQ 的验收）** = 用秩融合，或写出并冻结一套可复算的加权规则 ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 代码中出现的跨路分数相加 | **缺陷**——代码评审的检查项 |
| 同路内部的分数运算 | 允许（如 BM25 的各项） |

#### 验收要点

- **构造**：检查融合实现。
- **预期**：**融合逻辑有明文依据**；不存在跨路分数相加。

### REQ-RET-011　public 与私有分开执行

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §11

#### 语义

`public` 与私有**分开执行并显式融合**；
**不得在全用户索引中事后添加 `user_id` 过滤**。

#### 规格

**§0.2 已说清它的安全与架构两面。这里补"显式融合"的含义**：

```text
检索 = 私有路的结果  ⊕  公开路的结果        （两路各自检索、各自校验）
       ——不是——                            ✗
检索 = 在"全用户索引"上检索 → 事后过滤掉别人的
```

| | 分开执行（采用） | 全用户索引 + 事后过滤 ✗ |
| --- | --- | --- |
| 结构 | **不存在**能同时看到两人的索引 | 存在，且**每一处都要过滤对** |
| 遗漏一处 | 不可能——没有可遗漏的结构 | **跨用户泄露** ✗ |
| `top_k` | 两路各取，融合后截断 | 过滤后**远少于 K** ✗（同 pgvector 的过滤塌陷） |

**第三行是它顺带修掉的一个功能缺陷** ✓：
事后过滤在全用户索引上取 `top_k` 再过滤，**高选择性时结果会塌陷** ✗——
**而分开执行天然没有这个问题** ✓（每一路都是在自己的集合里取 `top_k`）✓。

**"架构上不存在全用户索引"是 REQ 的验收** ✓——
**它验收的是"结构不存在"，不是"过滤正确"** ✗✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 结果中出现另一工作区的条目 | **不可能**——那一路根本看不到它 |
| `public` 的过滤（§13.5 的过滤层） | **仍然生效**——公开路也要过滤（有些行只对某工作区可见） |

#### 验收要点

- **构造**：两个工作区各写数据，互相检索；再检索 `public`。
- **预期**：**互不可见**；`public` 的结果**经过滤层**；**不存在全用户索引**。

### REQ-RET-014　幂等与不回退

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §11

#### 语义

重复任务**幂等**；**旧任务不得覆盖新 revision**。

#### 规格

**两条不同的性质，别混**：

| | 保证 | 靠什么 |
| --- | --- | --- |
| **幂等** | 同一任务执行多次 = 执行一次 | 任务带**目标 revision**，重复执行结果相同 |
| **不回退** | 旧任务不覆盖新结果 ✗ | **写入时比较 revision / 水位**，落后就丢弃 ✓ |

**为什么"旧任务"一定会出现**：任务是异步的 ✗——
乱序投递、重试、并发消费，**都是常态** ✓✓。
**所以"不回退"不能靠"任务按序到达"，只能靠"写入时判新旧"** ✓。

**这与索引的 `generation` 是一回事**（REQ-RET-022）：
**每次写入都声明"我是基于哪个版本算的"，落后的自己退出。**

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 同一任务投递两次 | **结果相同** |
| 旧任务在新任务之后到达 | **丢弃**，不覆盖 |

#### 验收要点

- **构造**：乱序投递。
- **预期**：**不产生回退**（REQ 的验收）。

### REQ-RET-019　三种距离与边界值

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §12

#### 语义

支持 **L2、余弦与内积**；定义**零向量、NaN、无穷值与浮点计算误差**。

#### 规格

| 距离 | 公式要点 | 注意 |
| --- | --- | --- |
| **L2** | 欧氏距离 | 对归一化向量与余弦**单调等价** ✓ |
| **余弦** | `1 − (a·b)/(|a||b|)` | **零向量的余弦未定义** ✗ |
| **内积** | 负内积（越小越近） | **要求调用方保证归一化**，否则"最近"无意义 ✗ |

**边界值必须定义，因为它们全都会出现**：

| 值 | 处理 |
| --- | --- |
| **零向量** | **余弦与内积的除法未定义** ✗——写入时**拒绝**，还是查询时返回空？**必须定一种** |
| **NaN** | **拒绝**——`NaN` 与任何值的比较都是假，会**让排序失去全序** ✗✗ |
| **无穷** | **拒绝**（与 `NUMBER` 的取值域一致，§REQ-TYP-001） |
| **浮点误差** | **评分是近似的**，召回指标必须按"距离在容差内即算命中"定义 ✓ |

**NaN 那条最严重** ✗✓：排序需要一个**全序**，
而 `NaN` 让"小于"关系失效 ✗——**排序结果会随实现而变化** ✓。
**所以它在入口就得被挡住。**

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 写入含 NaN / 无穷的向量 | **拒绝** |
| 写入零向量 | 按冻结的规则（见待确认汇总）——**默认拒绝余弦空间** |
| 距离计算出现精度争议 | **按容差判定**，不按精确相等 |

#### 验收要点

- **构造**：零向量、NaN、无穷、极小值、极大量级差。
- **预期**：**边界用例确定**（REQ 的验收）。

### REQ-RET-020　高维向量与原始向量的权威性

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §12

#### 语义

高维向量支持**跨页存储**；**原始向量是权威数据**。

#### 规格

| | |
| --- | --- |
| **跨页** | 超出一页的向量走**行片段链**（§6.8），**上限 1MB** ⇒ **约 26 万维** ✓ |
| **索引上限** | **约 4000 维**（§0.4：element 要放下一页） |
| **权威** | **堆表里的向量是权威** ✗✓，索引里的只是**副本 + 邻接结构** |

**"索引里也存了向量"这一点必须说清**：为了搜索时**不必回表取向量**，
element 里存了一份 ✗——**于是同一个向量有两份** ✗✓。

**它们的关系是"副本"，不是"两份数据"** ✓：
索引可重建（REQ-RET-022），**源数据丢了索引再准也没用** ✓。
**这个定位决定了出错时的处置**：**索引与源不一致 ⇒ 重建索引，不动源** ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 索引损坏 | **重建**（REQ 的验收："索引损坏可重建"） |
| 主数据损坏 | **走恢复**，不是"重建索引"能解决的 ✗ |

#### 验收要点

- **构造**：超一页的高维向量。
- **预期**：**写入成功、可检索**；删除索引后**重建结果一致**。

| 情形 | 行为 |
| --- | --- |
| 候选回查不通过 | **丢弃**，**不补** |
| 合法的候选不足 K | **返回不足 K 的结果** + 标注 |

#### 验收要点

- **构造**：强过滤用例（`REQ` 的原文）。
- **预期**：**正确**——不掺不合法候选。

### REQ-RET-026　高选择性过滤的策略

**优先级**：应当　**阶段**：P8　**追溯**：总体方案 §12

#### 语义

高选择性过滤采用**先过滤精确搜索、候选扩展或可解释回退**。

#### 规格

**这是 §0.4 ④ 那个问题的正面解法**（pgvector 的过滤塌陷）✓：

```text
过滤后剩余比例很低（高选择性）
  →  先按过滤条件选出集合，再在其中做精确扫描        （首选）
  →  或：先 ANN 取候选，再扩展候选（迭代式）        （次选）
  →  或：明确回退并标注                            （兜底）
```

| 策略 | 何时 |
| --- | --- |
| **先过滤 + 精确搜索** | 过滤后集合小——**精确扫描的代价可以接受** ✓ 且**结果确定** ✓✓ |
| **候选扩展** | 过滤后集合中等——迭代取候选直到够 K 或预算耗尽 |
| **可解释回退** | 预算不足以给出可信结果 → **明说** |

**"先过滤 + 精确搜索"为什么通常最优**：过滤后剩得少 ✗，
**ANN 的价值（避免全扫）本来就在于集合大** ✓——集合小了，**全扫反而更准更快** ✓✓。

**"过滤正确性单独评分"（REQ 的验收）**：这一路的召回**不与 ANN 的混在一起评** ✗——
它们的失败模式不同 ✓（前者是"选错了集合"，后者是"图走岔了"）。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 回退发生 | **在结果中标注**——不静默 |
| 过滤条件极强（剩几条） | 精确扫描 |

#### 验收要点

- **构造**：从极强到极弱的过滤梯度。
- **预期**：**过滤正确性单独评分**（REQ 的验收），且**结果与精确扫描一致**（强过滤段）。

### REQ-RET-027　首版只承诺当前 RC 语句检索

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §12

#### 语义

首版**只承诺当前 RC 语句检索**；
**历史时点 ANN 查询延后**——**但只延后这一种，见下** ✗✓。

#### 规格

**措辞必须精确，因为"历史检索"是三类东西，只有一类贵** ✗✓——
原先把它们一起延后是**推过头了** ✓：

| 问什么 | 靠什么 | 成本 | 首版 |
| --- | --- | --- | --- |
| **"当时我们记的是什么"** | 按 `record_time` ≤ T 过滤（`MEM` REQ-MEM-008） | **便宜** | **要** ✓ |
| **"事情当时是怎样的"** | `valid_from` / `valid_to` 区间覆盖 T | **便宜** | **要** ✓ |
| **"当时的向量近邻"** | 保留**当时的整份图** | 贵 ✗ | **延后** |

**前两类是普通的时间过滤，不需要 ANN 的历史版本** ✗✓；
**而它们对 Agent 是刚需**（"记忆是怎么演进的"是它的日常）✗✓。
**只有第三类真的需要保留旧图** ✓。

**这一条与 §12 的 MVCC 直接相接，边界必须说清**：

| | 首版 | 延后 |
| --- | --- | --- |
| **检索用的可见性** | **当前语句的 RC 快照**（§12.1） | 历史时点 |
| **"历史时点的 ANN"** | ✗ | 比如"这条向量的近邻在**昨天**是什么样" |

**为什么历史时点 ANN 特别难** ✗：

> 普通表的历史版本可以**沿 undo 重建**（§12.3）✓。
> 但**ANN 的"历史版本"不是一个已知的图** ✗——
> 索引是**派生**的（REQ-RET-020/022），它只有"**当时构建的那一份**" ✗，
> 而**两个时点之间索引可能已重建过若干次** ✗。
> 要回答"昨天此刻的近邻"，需要**保留当时的那份图** ✗——那是一份完整的索引副本 ✗。

**所以延后不是难度排序，是范围控制** ✓——
**它与"检索结果的 revision 必须回查"（REQ-RET-010/023）是两件事** ✗✓：
后者**能做到**，且必须做 ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 请求历史时点的 ANN 查询 | **拒绝**（范围控制项） |
| 检索结果带 `revision` | **仍然要做**（REQ-RET-010） |

#### 验收要点

- **预期**：**范围控制项**（REQ 的验收）——接口清单中不存在历史时点 **ANN**；
  而按 `record_time` / `valid` 区间过滤的历史查询**必须存在** ✓。
