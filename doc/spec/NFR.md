## 0 总述

### 0.1 画像与四条取向——所有门槛的推导依据

**需求文档 §2.2 的画像**（读占绝对多数、写并发有限、读并发高、短事务、
单次写量小、读延迟敏感、写延迟不敏感）推导出四条取向：

| # | 取向 | 本域的用法 |
| --- | --- | --- |
| 1 | **读路径无锁化** | PERF-003 / 008 / 009 的共同依据 |
| 2 | **写路径正确性不降级** | REL 全族：低并发**不是**放松持久化的理由 |
| 3 | **不为不存在的负载付费** | 性能门禁只对画像内的场景设门槛 |
| 4 | **版本化留在数据模型层** | PERF 不为"多版本膨胀"设预算（`REQ-STO-015` 的 ADR 门） |

### 0.2 本域的性质：**能力在别处设计，契约与验收在这里定**

**这是本域与其他 13 个域的根本不同** ✗✓：NFR 不重新设计快照、恢复或隔离——
那些都已在 `TXN` / `STO` / `ISO` 等域定稿。本域为每一条需求给出：

| 部分 | 内容 |
| --- | --- |
| **可测契约** | 什么指标、什么场景、什么判据 |
| **设计落点** | 该能力**已经**在哪个域/节定稿（防止本域变成第二处真相） |
| **验收配方** | 构造 / 注入 / 预期——可直接转为测试用例 |

### 0.3 三层门槛

| 层 | 何时定 | 例子 |
| --- | --- | --- |
| **P0 冻结**（数值） | P0 评审 | 基准机、缓存预算、并发档位、各资源默认额度 |
| **P7 基线**（性能） | P7 首次测量 | p50/p95/p99、吞吐、冷启动、构建、恢复、备份时长 |
| **门禁**（阻断/警告） | 每阶段 | 回归 > 10% 阻断；阻断缺陷清单（REL-007） |

**数值未冻结前，本域的门槛只写"形态"**（测什么、怎么比），不写假数 ✗✓。

### REQ-PERF-001　基准机与档位冻结

**优先级**：必须　**阶段**：P0　**追溯**：总体方案 §21

#### 语义

P0 冻结**基准机规格、实例总缓存预算、活跃工作区档位、资产规模与索引规模**。

#### 规格

**冻结项 = 验收基线的输入**（需求文档 §8 第 1 项）：冻结值进入一切性能门禁的
"相同条件"定义——**任何性能数字不附基准机与档位即不可比** ✗✓。

**档位的形态**（数值 P0 填）：活跃工作区数 × 每区数据规模 × 向量规模 × 图规模
的**四维档位表**；测试报告必须声明所用档位 ✓。

#### 验收要点

- **构造**：P0 评审记录。
- **预期**：冻结值进入验收基线（REQ 验收原文）；后续所有性能报告引用它。

### REQ-PERF-003　读延迟是首要门禁

**优先级**：必须　**阶段**：P7 起　**追溯**：需求文档 §2.2 画像

#### 语义

**读路径 p99 作为首要性能门禁**；读场景有独立基线。

#### 规格

- **设计落点**：读路径无锁（`TXN` REQ-TXN-005）、无同步写（§8 的既定点）、
  ITL 块内自包含判定（§12.2）——**这三条就是"读得快"的结构性保证** ✓；
- **门禁形态**：读场景（点查 / 检索 / 范围 / 图遍历）**各自**的 p99 基线；
  任何一条劣化 ≥ 10% 触发 PERF-004 的回归流程 ✓；
- **写延迟不设 p99 门禁**（画像：写延迟不敏感）——但**耐久性要求不因此放松**（REL 族）✓。

#### 验收要点

- **构造**：四条读场景分别压测。
- **预期**：各有独立基线；报告不把读写混成一个数。

### REQ-PERF-004　P7 基线与 10% 回归门禁

**优先级**：必须　**阶段**：P7 起　**追溯**：总体方案 §21

#### 语义

P7 形成性能基线；后续**相同条件**下无**未解释的超过 10% 回退**。

- 回归检测在 CI 的**长周期档**（`MNT` REQ-MNT-009 的每周档）运行 ✓。

#### 验收要点

- **构造**：对同条件前后两次报告做差分。
- **预期**：无未解释的 > 10% 回退（REQ 验收"回归检测"）。

### REQ-PERF-005　不删门禁

**优先级**：必须　**阶段**：贯穿　**追溯**：总体方案 §21

#### 语义

绝对业务目标不足时**缩小范围或继续优化**，**不得删除质量门禁**。

"删门禁"与"改需求"的区别在这里：删门禁是**假装通过**。

#### 验收要点

- **构造**：评审确认。
- **预期**：门禁历史只增不删（配置在版本控制中留痕）。

### REQ-PERF-006　冷启动纳入指标

**优先级**：应当　**阶段**：P7 起　**追溯**：总体方案 §4

#### 语义

**冷启动与工作区唤醒**耗时纳入性能指标。

#### 规格

- 冷启动 = 实例启动到可接受连接；工作区唤醒 = 打开工作区到可用（**含恢复**）；
- 与 `OPS` REQ-OPS-005 的"工作区启动延迟"指标是同一数据的两个口径 ✓；
- **V1.0 的恢复策略**（撤销完成后再开放，§11.2）使唤醒时间 ∝ 崩溃时未提交事务量——
  报告须附该量级 ✓。

#### 验收要点

- **构造**：干净启动 / 崩溃后启动各测一轮。
- **预期**：两者分开报告（REQ 验收"有测量"）。

### REQ-PERF-007　按需进程不固定占缓存

**优先级**：必须　**阶段**：P0/P2　**追溯**：总体方案 §4

#### 语义

按需进程**不得**让每个用户固定占用大额缓存；监督器以**总预算**分配。

#### 规格

- **设计落点**：缓冲池是**实例级**的（§5.10 的工作集分区），不按用户"分蛋糕"；
  用户进程只持有执行态内存（受 `RES` 的 `max_query_memory` 约束）✓；
- **可测**：空闲用户数与 RSS 的关系曲线——应**无正相关**（除每进程固定开销）✓；
- 总预算冻结在 PERF-001 ✓。

#### 验收要点

- **构造**：创建 M 个空闲用户，测总 RSS 随 M 的变化。
- **预期**：**内存总量受控**（REQ 验收原文）；无"每用户一块大缓存"。

### REQ-PERF-008　读吞吐近似线性扩展

**优先级**：必须　**阶段**：P7 起　**追溯**：需求文档 §2.2、总体方案 §15

#### 语义

读吞吐应随执行线程数**近似线性扩展**至 P0 冻结的并发档位；
**读路径不得存在全局串行点**。

#### 规格

- **设计落点**（全局串行点的逐一排查——这是本条的实际内容）：

| 候选串行点 | 设计 | 结论 |
| --- | --- | --- |
| 行锁 | 读不取锁（REQ-TXN-005） | 无 ✓ |
| 全局事务状态表 | 没有这张表（§12.2 块内自包含） | 无 ✓ |
| 缓冲池 LRU latch | **按工作集分区**（§5.10） | 有界、非全局 ✓ |
| WAL 追加 latch | 只被**写**路径碰 | 读路径无 ✓ |
| 最老快照集合 | 语句开始/结束登记——**读路径上唯一的共享写** ✗✓ | **须测**：高并发短语句下是否成为拐点 |

- **最后一行是本条要盯的真点**：快照注册表是读路径上唯一的共享可变结构——
  它的实现（分片/原子操作）必须使扩展曲线**无拐点式塌陷**（验收原文）✓。

#### 验收要点

- **构造**：并发 1→档位的扫描测试，画扩展曲线。
- **预期**：近似线性至档位；**无拐点式塌陷**（REQ 验收原文）。

### REQ-PERF-009　读不受写入的无界影响

**优先级**：必须　**阶段**：P7 起　**追溯**：需求文档 §2.2、REQ-TXN-005

#### 语义

读操作**不得因并发写入量增加而出现无界延迟增长**。

#### 规格

- **设计落点**：读无锁、不等待写 ✓；写者的延迟不能"传染"给读者；
- **要盯的两个有界延迟源**（都是"有界但可增长"，须证明界）✗✓：
  ① **undo 链长度**——读重建旧版本时沿链走；链长 ∝ 该行的修改次数，
     而**修改次数被事务持有时间封顶**（短事务画像）✓；
  ② **行迁移/跨页链**——链长有上限（`REQ-STO` 的片段上限）✓；
- **验收配方**：注入递增写负载（到 P0 级），读 p99 **保持有界**（验收原文）——
  有界的判据：[写负载翻倍时读 p99 的劣化 < 写负载翻倍比例] ✗✓。

#### 验收要点

- **构造**：阶梯式写负载 + 恒定读负载。
- **预期**：读 p99 有界；记录拐点（若有）并解释。

### REQ-REL-001　已确认的提交必须保存

**优先级**：必须　**阶段**：P3–P4　**追溯**：总体方案 §17

#### 语义

**已收到成功提交的事务必须保存**。

#### 规格

- **设计落点**：REQ-TXN-010（提交响应晚于耐久确认）+ §11.1.1 的提交次序
  （提交记录入日志流 → 标记可见 → 释放锁 → 等刷盘回应）✓；
- **验收配方**：断电注入（杀进程 + 断电模拟）于**响应已返回**之后 → 恢复后该事务在 ✓；
- **反向用例**：响应**未**返回时的崩溃 → 允许未知（REL-003），**不得**部分存在 ✓。

#### 验收要点

- **构造**：提交响应与断电的交错注入（响应前 / 后各 N 次）。
- **预期**：**响应后必存**（REQ 验收"断电注入验证"）。

### REQ-REL-004　随机崩溃测试

**优先级**：必须　**阶段**：P3 起　**追溯**：总体方案 §17

#### 语义

**至少 1 万次随机崩溃**并验证**恢复中再次中断**；每次恢复执行检查器并与参考历史对照。

#### 规格

**测试装置三件套**（缺一不可）✗✓：

| 件 | 内容 |
| --- | --- |
| **随机崩溃** | 崩溃点覆盖：提交切点、检查点、段回收（§4.7）、分裂（索引/邻接）、资产七步（`AST`）、DDL、克隆/备份（`OPS`）——**崩溃点按权重随机** |
| **恢复中再中断** | 恢复过程本身可被再次打断 N 次，最终仍收敛 ✓（恢复的幂等性在此受检） |
| **双重裁判** | ① **检查器**（结构一致性：`db_check` 的逻辑检查项，待冻结项 2d）；② **参考历史**（逻辑层：按提交/回滚序列应得的状态）✓ |

#### 验收要点

- **构造**：1 万次随机崩溃 + 恢复中再中断。
- **预期**：每次恢复通过双裁判（REQ 验收原文"检查器与参考历史对照"）。

- **预期**：**报告留档**（REQ 验收原文）。

### REQ-REL-007　阻断缺陷清单

**优先级**：必须　**阶段**：发布门禁　**追溯**：总体方案 §19

#### 语义

**隔离、错误结果、成功提交丢失、不可恢复损坏与提前文件回收**均为**阻断缺陷**。

#### 规格

**五类，逐一对应本设计的保证**（发布门禁即这五条的回归集全绿）：

#### 验收要点

- **构造**：发布评审检查五类回归集。

### REQ-MNT-007　比较规范

**优先级**：必须　**阶段**：贯穿　**追溯**：总体方案 §20

#### 语义

**无排序的结果集按多重集比较**；ANN 按**召回与过滤正确性分别**评分。

#### 规格

| 规则 | 含义 |
| --- | --- |
| **多重集比较** | 无 `ORDER BY` 的结果**行序无意义**——比较时排序后再比（或计数比较）✗✓；有 `ORDER BY` 时才比序 |
| **ANN 分开评分** | **召回**（近邻找没找到）与**过滤正确性**（不该出现的没出现）是两个分数，**不得合并**——合并会掩盖一类错误（`RET` 的验收同规）✓ |
| 浮点比较 | 按 `TYP` 的精度规则（不引入"近似相等"的自由裁量）✓ |

#### 验收要点

- **构造**：测试规范审查（REQ 验收原文）；抽查含浮点与 ANN 的用例。
