## 0 模型总述

### 0.1 先画三条线（本域的三条纪律）

| 线 | 一侧 | 另一侧 |
| --- | --- | --- |
| **管理面**（REQ-OPS-001） | 状态、额度、进程健康、**聚合**性能 | **私有业务内容**——没有 SQL、没有文件接口 |
| **日志与审计**（REQ-OPS-002） | 指纹、ID、行数、错误码 | **完整参数、JSON 正文、文档片段、向量**——默认不记 |
| **备份归属**（REQ-OPS-008/011/017） | 备份是**原工作区的**、身份不可变 | **不是**数据转让通道、不是跨区共享介质 |

**三条线是同一种写法的三次出现**：**不提供那个入口** ✗✓——
管理面没有读内容的接口、日志路径没有写正文的分支、恢复没有改身份的选项。

### 0.2 数据分档：一张表统摄备份 / PITR / 迁移

```text
┌─ 受 REDO 保护：logging = full / redo_only（表、图、配置、记忆、字典…）
│    备份：✅（物理像）    PITR：✅（备份点 + 归档日志重放）    迁移工具：✅
└─ 不记日志：logging = none（会话表等）
     备份：✅（物理像——文件照样复制！）
     PITR：❌ ——**没有日志可重放**，它将停在备份点
     迁移工具：✅ ——**它是不记日志数据唯一的保留途径**（REQ-OPS-014）
```

**"备份覆盖全部、PITR 不覆盖全部"必须分清** ✗✓——
这是最容易含混的一句：**备份是物理复制，它不问表怎么配**；
**PITR 是重放，它只能重放有日志的东西** ✓。
所以"能不能恢复到昨天下午三点"的准确回答是：
**受 redo 保护的数据能；不记日志的表停在备份点那一刻**（REQ-OPS-015 的声明义务）✓。

### 0.3 四条恢复/搬运路径，互不混淆（方案 §21 的落实）

| 路径 | 用什么 | 谁触发 | 覆盖 |
| --- | --- | --- | --- |
| **实例恢复** | **仅在线 redo** | 崩溃后自动 | 全部受 redo 保护的数据 |
| **介质恢复** | **备份 + 归档日志** | 管理员 | 备份覆盖的全部数据（含 `logging = none` 的备份点状态） |
| **时间点恢复（PITR）** | **备份 + 归档日志（到目标点）** | 管理员 | 受 redo 保护的数据到目标点；其余停在备份点 |
| **离线迁移** | **逻辑导出/导入工具** | 管理员 | **全部数据**（含 `logging = none`）——跨机与升级 |

### 0.4 管理面清单（REQ-OPS-001 的闭集）

**admin 可见**（全部是状态与聚合，**没有一条返回业务内容**）：

| 类别 | 内容 |
| --- | --- |
| 工作区 | 状态、额度与占用（按角色四数）、启动延迟、最近备份/归档状态 |
| 进程 | 健康、线程池、写线程紧迫度、检查点进度 |
| 性能 | 聚合指标（REQ-OPS-005 的清单，§下详） |
| 介质 | 文件系统池、卷分布、备份位置状态 |

**admin 可做**（管理动作，枚举）：建 / 删 / 克隆工作区、改配额、池增删、`MOVE`、
发起备份 / 恢复、请求诊断转储（**生成**✓，导出另论——REQ-OPS-006）。

**admin 不可做**（本条的验收判据）：

- 读任何用户工作区的**业务内容**——没有这样的 SQL 接口，也没有这样的文件接口 ✓；
- 读用户审计（`ISO` REQ-ISO-003 的"代理读取"禁止，§2.13 已论证）✓；
- 导出未授权的诊断转储（REQ-OPS-006 的阻断项）✓。

### REQ-OPS-001　管理面只给状态与聚合

**优先级**：必须　**阶段**：P11　**追溯**：总体方案 §21

#### 语义

管理员只获得**工作区状态、额度、进程健康与聚合性能**；
**不提供读取私有业务内容的 SQL 或文件接口**。

#### 规格

**§0.4 的闭集即为规格**。实现上的一条硬约束：

> **管理接口与用户接口是两条不同的通道** ✗✓——管理面**从不**"以 admin 身份连进用户工作区"
> 再过滤输出（那是代理读取的变体）；它读的是**引擎自身的状态结构**（检查点、配额计数、
> 指标聚合、控制文件），**与业务表无关** ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 管理接口请求"某工作区某表的行数" | **不存在这个接口**——行数是业务内容侧的信息 ✓ |
| admin 想读自己管理的 `public` 数据 | 允许——**因为它是 `public` 的属主**，走用户通道 ✓ |

#### 验收要点

- **构造**：枚举管理接口清单。
- **预期**：**零个**接口可返回业务内容（REQ 验收原文）。

### REQ-OPS-002　日志与审计的脱敏

**优先级**：必须　**阶段**：P11　**追溯**：总体方案 §21

#### 语义

默认**不记录完整 SQL 参数、JSON 正文、文档片段与向量**。

#### 规格

| 位置 | 记什么 | **不记什么** |
| --- | --- | --- |
| 运行日志 | 规范化语句的**指纹**（哈希）、对象 ID、行数、错误码、耗时 | 完整参数值、JSON / 文档正文、向量 |
| 审计（REQ-OPS-003） | §该条的字段表 | 同上 |
| 错误响应 `message` | 人类可读的**结构性描述** | 行值——`CONV` §4.2 的既有约束（REQ-OPS-002）✓ |
| redo / undo | 必需的数据字节 | **不在本条范围内**——那是数据本身，不是"日志文本" ✓ |

**调试模式**：显式开启（工作区级）才记录正文；**开启动作本身记入审计**；
**自动过期**（建议初始 1 小时，可配）✗✓——"忘了关"是这类开关的常态。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 抽查发现日志含 JSON 正文 / 向量 | **验收失败**（REQ 验收原文"日志抽查无敏感正文"） |
| 调试模式下的转储 | 按 REQ-OPS-006 的授权流程走 ✓ |

#### 验收要点

- **构造**：跑含大 JSON、向量、长文本参数的工作负载；抽查全部日志流。
- **预期**：无敏感正文；调试开关的记忆状态可审计。

### REQ-OPS-003　审计字段

**优先级**：必须　**阶段**：P11　**追溯**：总体方案 §21

#### 语义

审计记录**身份、Agent、请求、对象 ID、动作、结果、版本与错误码**。

#### 规格

**落点：`audit` 表**（每工作区一张预置表；**属主只读**——写只经引擎的审计路径，
`SQL` §0.4：无 DML / DDL 入口）✓。列：

| 列 | 内容 |
| --- | --- |
| `ts` | 墙钟时间（+ 提交序号——可判定顺序，`CONV` §7 的区分） |
| `user_id` / `agent_id` | 身份与 Agent（Agent 为空的 = 主体级操作） |
| `request_id` | 请求（`API` 的封套字段） |
| `object_kind` / `object_id` | 被作用的对象（表、图、记忆、资产…） |
| `action` | 动作（枚举，`CONV` §6 的"显式状态集"同规） |
| `result` | 成功 / 失败 |
| 版本 | 对象的 `revision` / `generation`（有则记） |
| `code` | 失败时的稳定错误码 |

**写入时机的两条规则**（关键，因为"失败"没有自己的事务）✗✓：

| 情形 | 何时写 |
| --- | --- |
| 操作**成功** | **随业务事务一起提交**——审计与业务同生共死 ✓ |
| 操作**失败** | 业务事务**回滚后**，引擎以**独立小事务**追加一条——失败也要留痕 ✓ |

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 审计写失败但业务成功 | **业务不回滚**（留痕尽力而为）——但要**告警**（审计链有洞是运维事件）✓ |
| 缺字段 | 验收失败（"审计字段完整"） |

#### 验收要点

- **构造**：成功 / 失败 / 回滚 / 调试模式开启，各取一条审计比对字段。
- **预期**：字段完整；失败操作**有**审计（独立事务路径）。

### REQ-OPS-004　审计的隔离

**优先级**：必须　**阶段**：P11　**追溯**：总体方案 §21

#### 语义

**用户只能查看本人审计**；**public 发布审计独立保存**。

#### 规格

**实现方式在存储架构 §2.13 已经给出，本域不另设机制** ✗✓：

| 审计流 | 在哪 | "只能看本人"靠什么 |
| --- | --- | --- |
| 用户操作审计 | **用户自己的工作区**（`audit` 表） | **隔离模型本身**——别人的工作区打不开 ✓ |
| public 发布审计 | **`public` 的 `audit` 表** | 它本来就对所有人只读（REQ-ISO-004）✓ |

**查询路径**：属主 `SELECT … FROM audit`（预置名，`SQL` §0.4）；
admin 读用户的 = 代理读取 = 不存在（§2.13）✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 跨用户查看审计 | 不存在这条路径（跨区打不开） |
| 属主想删自己的审计 | **SQL 层无 DML 入口**——但这不是防篡改（§2.13 的诚实定位，待冻结项 53）✓ |

#### 验收要点

- **构造**：两个主体各自产生审计；互相尝试查看。
- **预期**：**跨用户审计不可见**；public 发布审计含发布动作。

### REQ-OPS-006　诊断转储：两段式

**优先级**：必须　**阶段**：P11　**追溯**：总体方案 §21

#### 语义

诊断转储**按用户单独生成**，并由**本人授权导出**；
**不得以运维账号绕过读取策略**。

#### 规格

**拆成两段，各自有明确的门** ✗✓：

```text
① 生成：admin 请求 → 引擎按**单个工作区**生成转储（页镜像、结构统计、检查点信息…）
        ——产物**可能含业务数据**，落在该工作区受控目录，权限 = 属主
② 导出：**需要属主授权**——属主以本人会话签发导出授权（记录进审计），
        导出动作才被允许
```

**"按用户单独生成"** = 转储的粒度是**工作区**，不是实例——一份转储不混两个工作区 ✓。

**阻断项**：admin **单独无法**完成导出（没有"以运维账号读取"的路径）✓——
这条与 REQ-OPS-001 的验收并案检查。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| admin 试图直接读取转储文件 | **阻断**（授权缺失）——验收的阻断项 |
| 属主授权后导出 | 允许；授权与导出**双双入审计** ✓ |

#### 验收要点

- **构造**：admin 生成转储 → 尝试不经授权导出。
- **预期**：**阻断**；属主授权后可导出；全过程审计完整。

### REQ-OPS-007　离线一致备份

**优先级**：必须　**阶段**：P11　**追溯**：总体方案 §21

#### 语义

V1.0 提供**离线一致备份**：暂停目标工作区写入 → 完成检查点与资产发布 →
固定资产清单 → 复制数据/控制/日志/资产 → 校验大小与哈希。

#### 规格

```text
① 冻结：拒绝新写；等待活动写事务结束——超时则**中止备份并解冻**（不无限挂起）✗✓
② 强制检查点：刷全部脏页 + 刷控制文件（§2.6）——一致点由此确定
③ 完成资产发布：把已进入发布流程的资产走完（rename + fsync，AST 七步的 ⑤⑥）；
   此后的 staging 残留**不在一揽子范围内**（它们本就不可见）✓
④ 固化清单：检查点位置（提交序号）、全部文件（大小）、资产清单（asset_id + 大小 + 校验和）
   ——**备份产物自带清单**（落待冻结项 26 ✓，见下）
⑤ 复制到独立备份位置：与源同文件系统可用 reflink（秒级）；否则普通复制——
   **冻结贯穿复制**（"离线"的含义）
⑥ 校验：逐文件比对大小与哈希；全部通过后写**完成标记**
⑦ 解冻
```

**"清单 + 完成标记"的判据** ✗✓：
**有完成标记 ⟺ 备份可用**——清单在复制前固化（⑤的依据），
完成标记在校验后写入（⑥的结论）；中断的备份**没有完成标记**，恢复端直接拒绝 ✓。

**代价如实记录**：普通复制下**冻结时长 ∝ 数据量**——这是"离线"二字的含义。
**不暂停写的在线备份**不在 V1.0（与待冻结项 15 同期）。

**备份元数据放哪（待冻结项 26 的落地）**：**由备份产物自带** ✗✓——
若放控制文件，灾难恢复时**控制文件本身也丢了**，目录比数据先死 ✗。
自描述与克隆的血缘自述是同一条精神：**产物能自己解释自己** ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 冻结超时（长事务不退） | 中止备份、解冻、明确错误——**不抢事务** ✓ |
| 复制中途失败 | 无完成标记 ⇒ 不可用于恢复；重新备份 |
| 校验失败 | 同上；**明确指认**哪个文件不符 |

#### 验收要点

- **构造**：全量备份 → 恢复 → 校验；在各步骤注入中断。
- **预期**：**备份可恢复并校验**（REQ 验收原文）；中断产物被拒用。

### REQ-OPS-008　备份归属与恢复校验

**优先级**：必须　**阶段**：P11　**追溯**：总体方案 §21

#### 语义

备份**属于原工作区**，存入**独立备份位置**并控制介质权限；
恢复验证 **owner、WorkspaceId、版本与完整引用**。

#### 规格

| 环节 | 规则 |
| --- | --- |
| 归属 | 清单里记 `owner` + `workspace_id`——**身份随备份走，不可改**（REQ-OPS-011） |
| 位置 | **独立于工作区目录**；介质权限受控（OS 层手段：属主、权限位/ACL——具体手段归实施） |
| 恢复校验 | ① `owner` / `workspace_id` 与目标一致；② **格式版本** ≤ 引擎支持（REQ-OPS-010）；③ **完整引用**：资产清单逐项存在且校验和相符——**缺一件即拒绝恢复**（不完整备份不恢复）✓ |
| 不匹配的响应 | **"别人的备份"与"损坏的备份"不可区分**（`ISO` REQ-ISO-006 的既有结论，`ISO.md` 已有此验收）✓ |

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 跨用户恢复 | **拒绝**（REQ 验收"跨用户恢复被拒绝"） |
| 资产缺一件 | 拒绝恢复（不是"尽力恢复"）✗✓ |

#### 验收要点

- **构造**：恢复 A 的备份到 B 的身份；删掉备份里一个资产后恢复。
- **预期**：两种情形**均拒绝**，且响应不可区分（前者）。

### REQ-OPS-009　public 版本与私有备份分开

**优先级**：必须　**阶段**：P11　**追溯**：总体方案 §21

#### 语义

`public` 版本与私有备份**分别保存**；跨区恢复**不承诺全局同一时刻**。

#### 规格

| 情形 | 行为 |
| --- | --- |

#### 验收要点
