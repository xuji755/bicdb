# 隔离、主体与权限（ISO）

需求文档 §3。公共约定见 [`CONV.md`](CONV.md)。

---

## 0 模型总述

**本域的形状参照 PostgreSQL 的权限模型**——因为**我们的隔离粒度与 PG 的
"一个实例多个数据库"同构**，而 PG 已经把那种形状下的权限问题解过一遍。

| | PostgreSQL | **我们** |
| --- | --- | --- |
| 隔离粒度 | database（共享实例） | **工作区** |
| 主体 | **role**——统一用户与组，**实例级** | **`user$`**——实例级，放在 `public` 里 |
| 属主 | 对象有 owner，隐式拥有全部权限 | **工作区有属主**；**一个主体可以有多个工作区**（REQ-ISO-012 要求） |
| 超级用户 | `superuser` / `BYPASSRLS` | **admin** |
| 共享区 | 每个库里有一个 `public` **模式**；另有 `pg_global` **共享目录** | **`public` 是一个工作区**——既不是模式，也不是目录 |
| 跨库 | 不提供（须 dblink / FDW） | **不提供** |
| 行级过滤 | RLS | **一个专用过滤层** |
| 对象级授权 | 完整矩阵（表 / 列 / 函数 / 序列…） | **不提供** |

### 只取 PG 的"形状层"，不取它的"矩阵层"

**这是本域最重要的一句话。** PG 的权限模型有两层，价值截然不同：

| 层 | 内容 | 我们 |
| --- | --- | --- |
| **形状层** | 主体是**实例级的角色**；工作区有**属主**；有一个**人人可读的共享区**；有一个**超级用户** | **全部采纳**——这是"一个实例多个数据库"必然带来的形状 |
| **矩阵层** | `GRANT SELECT ON t TO r` 那样的**对象级授权矩阵** | **不采纳**——REQ-ISO-003 明文禁止"跨用户授权、所有权转移、代理读取" |

**所以"参考 PG"是指参考它的形状，不是照搬它的 `GRANT`。**

**一处不采纳的具体理由**：PG 的 role 可以互相嵌套（这就是它的"组"）。
**我们不做**——嵌套的价值在于"多人共享一套权限"，
而我们的模型里**没有"共享权限"这回事**：一个主体恰好一个工作区（1:1），
**没有第二个主体能进入它**。给一个不存在的场景建机制，只会留下一个可被误用的入口。

### 两类主体

| 主体 | 说明 |
| --- | --- |
| **admin** | 实例级管理主体（PG 的 `superuser` 对应物）。**它管的是实例，不是数据**——建/删工作区、改配额、增删文件系统、读写 `public` 的全部数据 |
| **普通主体** | 身份来自**认证结果**（REQ-ISO-002），名下**可以有多个工作区**（REQ-ISO-012 要求"同一 owner 范围内"可克隆，否则该条为空） |

### 三种访问，各自的规则

| 访问对象 | 谁 | 规则 |
| --- | --- | --- |
| **自己的工作区** | 属主 | **全部权限**——这里没有"授权"这回事，因为**没有第二个主体能进来** |
| **`public`** | 任何普通主体 | **只读** + **经标准接口发布**；读**经过滤层**（REQ-ISO-004） |
| **别人的工作区** | 任何人，**含 admin** | **不存在这条路径**——不是"拒绝"，是**没有入口** |

**第三行是 REQ-ISO-003 的形态**，也是本域与 PG 最接近的一处：
PG 跨库要么不提供、要么必须显式装 dblink；我们**连 dblink 都没有**。

### 实现只有三处，而且热路径上没有权限查询

**本域的机制总共只有三处**，都不在热路径上重复发生：

| 时机 | 判定 | 频次 |
| --- | --- | --- |
| **打开工作区** | 身份 → 该主体的工作区 | **一次**——之后这个连接只看得见这一个工作区 |
| **读 `public`** | 过滤层：行归属 vs 会话工作区 | 行级**一次整数比较**，且不可见的行**根本不进入扫描** |
| **写 `public`** | 标准接口入口校验归属与状态机 | **一次** |

**除此之外没有任何权限判定。** 尤其是——
**自己工作区内的任何操作，一次判定都没有**。

> 这不是优化，是"**没有第二个主体能进来**"这个前提的直接结果：
> **没有可判的事，所以没有判定。**

**与 PG 的关键差别也在这里**：PG 的对象级授权矩阵意味着
**每次访问一个对象都要查一次 ACL**。
**我们不提供那张矩阵，所以那些查询一次都不存在。**

> **REQ-ISO-003 禁止跨用户授权，在性能上是一件好事**——这不是巧合：
> **一个不提供的机制，既没有绕过的风险，也没有判定的成本。**
> 简单与快，在这里是同一件事。

### REQ-ISO-001　每个主体一个独立工作区

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §3、§4

#### 语义

每个主体具有独立工作区；私有数据、索引、日志、临时文件与资产**不得与其他工作区混放**。

#### 规格

**隔离由多道防线共同提供，且必须分清各挡什么**（详见存储架构 §13）：

| 防线 | 性质 | 挡什么 |
| --- | --- | --- |
| 进程 / OS 隔离 | **结构性** | 一个工作区的进程打不开另一个的文件 |
| 文件层 | 每工作区独立文件、**不共享、无硬链接、不跨用户去重** | 共享导致的连带影响 |
| 页层 | 工作区受校验标识 | **跨区误读**（放错文件、读错块） |
| 缓存层 | 缓冲池键**含工作区标识** | 键碰撞（不同工作区的 ROWID 会重复） |

**四道全是挡"误"的，没有一道挡"意"。** `workspace_ref` 不是密码学边界——
**不得据此宣称隔离由它保证**。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 尝试打开他人工作区 | **报"不存在"**，不得报"无权限"（REQ-ISO-006） |
| 被隔离的工作区 | 见 `NFR-OPS` 域的管理接口语义 |

#### 验收要点

- **构造**：两个主体 + `public` 各自独立根目录。
- **预期**：测试工作者**无法**打开他人目录；四道防线的任意一道被绕过时，**仍有其他道检出**。

### REQ-ISO-002　身份来自认证结果

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §3

#### 语义

**用户标识必须来自认证结果**，不得以请求体中的 `user_id` 作为可信身份。

#### 规格

- 认证发生在**引擎之外**（平台 / API 层）——本库**不做认证**，它**消费**认证结果。
- 引擎只见**已认证的主体标识**，并把请求**路由到该主体自己的工作区**——
  **请求体里的任何"工作区"字段都不参与路由**。
- **路由是身份的函数，不是请求参数的函数。** 这一条是 REQ-ISO-001 与 -003 的
  共同前提：只要路由掺入请求参数，跨工作区访问就有了入口。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 请求体伪造 `user_id` | **被忽略**——路由只认认证结果 |
| 请求体指定"另一个工作区" | **被忽略**，同样路由到本人工作区 |

#### 验收要点

- **注入**：伪造 `user_id` 的请求。
- **预期**：被拒绝，或**被路由到本人工作区**（两者都可接受，关键是不发生越权）。

### REQ-ISO-003　不提供跨主体授权

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §3、§13

#### 语义

不得提供任何**跨用户授权、所有权转移、代理读取或共享链接**能力。

#### 规格

**用"不提供"实现禁止**——比"每次拒绝"强，因为**没有可漏判的东西**：

| 实现方式 | 强度 |
| --- | --- |
| 拒绝请求 | 依赖**每一次**都拒绝正确——**一处漏判即越权** |
| **不提供入口** | **没有可漏判的东西** |

**本库刻意不提供的原语**（这一张表**本身就是安全机制**，不是功能缺口）：

| 不提供 | 为什么 |
| --- | --- |
| 跨工作区的句柄 / 事务 / 游标 | 代理读取 |
| 跨工作区的数据文件共享（硬链接、reflink 去重） | 会互相打架，且"删自己的数据"会影响别人 |
| 对象级授权矩阵（`GRANT`） | 跨用户授权本身 |
| 所有权转移 | REQ-ISO-005 |
| 角色嵌套 / 组 | **没有"共享权限"这个场景**（§0） |
| `SET ROLE` 一类身份切换 | 代理读取 |
| 对 `public` 的直接 DML | 归属会被调用方指定——**写侧的一个疏漏会让读侧整套过滤失效** |

> **维护方式**：任何新增能力，先问"**它会不会给上层制造一个必须拒绝的入口**"。
> 会，就先证明拒绝不可绕过，再决定加不加。
> **这种改动在代码评审里看起来只是"方便"**——所以它必须被当成需求来维护。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 接口清单中出现上述能力 | **范围评审失败**，不得进入实现 |
| 尝试以 admin 身份读用户工作区 | **不存在这条路径**（见 §0 第三行） |

#### 验收要点

- **构造**：遍历接口清单。
- **预期**：上述七类能力**一项都不存在**；不是"存在但被拒"。

### REQ-ISO-004　`public` 只读共享

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §3

#### 语义

只有 `public` 工作区向所有主体只读共享；`public` 是**保留工作区与数据所有者**，
**不是 SQL 的 PUBLIC 角色**。

#### 规格

| | `public` 的公共数据 | `public` 的管理元数据 |
| --- | --- | --- |
| admin | 可读写 | 可读写 |
| 普通主体 | **只读，且经过滤层** | **不可见** |

**两条需求方向相反，靠一个专用层同时满足**：

| 需求 | 要求 |
| --- | --- |
| REQ-ISO-004 | **所有用户可读**公共数据 |
| REQ-ISO-006 | 管理元数据**整体不可见** |

**实现要点**（详见存储架构 §13.4–§13.6）：

1. **读有一个专用过滤层**——它是**一层**，不是"每处检查一次"。
   强度不来自"检查得多严"，而来自"**没有第二条路**"。
2. **行级过滤必须是扫描范围的一部分，而不是返回后的剔除**——
   事后剔除即使结果正确，**也仍然泄露"存在多少不可见的行"**。
3. **写入只有标准接口一条路**——直接 `INSERT` / `UPDATE` / `DELETE` **一律拒绝**。
   被拒的是"直接写"，**不是"写"本身**。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 普通主体对 `public` 直接 DML | **拒绝** |
| 普通主体读到无权的行 | 该行**不进入扫描**——不是"读出后丢弃" |
| 普通主体查询管理元数据的表 | **报"表不存在"**，与真的不存在不可区分 |

#### 验收要点

- **构造**：普通主体对 `public` 执行直接 DML；再执行标准接口写入。
- **预期**：前者全部被拒，后者成功且**归属由接口填、不由调用方指定**。

### REQ-ISO-005　owner 不可变，无跨工作区关系

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §3、§14

#### 语义

owner 不可变；不提供**跨工作区外键、可写联结或级联关系**。

#### 规格

**两条都靠"不提供"实现，而不是靠检查**：

| 不做 | 机制 |
| --- | --- |
| owner 变更 | `ws$` 的 `user_id` **不提供任何修改路径**——没有 `ALTER` 能改它，只有建工作区时写一次 |
| 跨工作区外键 | **没有跨工作区的事务，所以外键天然不可能**——它不是"被禁止"，是**表达不出来** |

**第二条值得单说**：外键要求"引用目标在同一事务里可见且可加锁"，
而本设计**没有跨工作区写事务**（REQ-TXN-019）。
**所以外键不是被规则挡住的，是缺了成立的前提。**

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 任何试图修改 owner 的 DDL | **语法上不存在** |
| 跨工作区外键 | **语法上不存在** |

#### 验收要点

- **构造**：穷举 DDL 清单中所有涉及所有权或跨区引用的语法。
- **预期**：**零匹配**。

### REQ-ISO-006　"不可区分"是响应契约

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §3

#### 语义

普通主体**不能判断**另一用户的对象是否存在；**拒绝响应不得泄露名称、内容或精确规模**。

#### 规格

**这一条最容易做错，因为它约束的是"响应的形状"，不是"判断的逻辑"。**

**做法只有一条：让"无权"与"不存在"走同一条路径、返回同一个东西。**

| 不得泄露 | 靠什么 | 代价 |
| --- | --- | --- |
| **存在性** | **"无权"根本不作为一种结果存在**——查不到就是"不存在"，没有分支 | **零**——少一个分支 |
| **名称** | 拒绝时**不回显调用方给的名称** | **零** |
| **精确规模** | 行数、字节数、工作区数**一律不给** | **零** |
| **时序** | 见下 | **零** |

> **时序不靠"调节"，靠"同一条路径"。**
>
> 若实现成"先查了再决定拒绝"，两条路径的耗时天然不同——
> 这时再去想办法凑时间，既是性能负担，也永远凑不准。
>
> **正确做法是：让它们本来就是同一件事**——
> 查不到 → "不存在"；**无权在实现里不构成一个可达的状态**。
> 于是形状与耗时**同时**一致，**没有一行代码是为它写的**。
>
> **这是"不可区分"最简单也最可靠的实现**：不是把两个东西做得一样，
> 而是**让第二个东西不存在**。与 §0"用不提供实现禁止"是同一条思路。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 猜测他人工作区名 | 与猜一个**根本不存在**的名字，**响应完全一致** |
| 同名对象探测 | **同上** |
| `public` 过滤掉的行 | **不得**让调用方察觉"被过滤掉了多少"——所以过滤必须在扫描范围内完成 |

#### 验收要点

- **构造**：对"存在但无权"与"不存在"两组输入各若干，比对响应。
- **预期**：**错误码、响应形状、字段、状态码全部一致**；响应时间的分布**不可区分**。
- **交叉验证**：至少 1 万组对比样本。

### REQ-ISO-007　文件操作的路径安全

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §4

#### 语义

文件操作必须检查**路径穿越、符号链接与检查使用间竞态**（TOCTOU）。

#### 规格

**第一道也是最有效的一道是 REQ-ISO-008**：根目录名**不经用户输入**，
路径穿越就失去了构造材料。其余两道是纵深：

| 威胁 | 对策 |
| --- | --- |
| 路径穿越（`../`） | 根目录**由服务端生成**，用户输入**不参与拼接**（REQ-ISO-008） |
| 符号链接 | 打开时**不跟随符号链接**（`O_NOFOLLOW` 一类），并在打开后**校验实际对象** |
| **TOCTOU** | **检查与使用之间路径可能被换掉**——因此**以句柄为准，不以路径为准**：检查的是**已打开的描述符**，之后的操作全部基于它 |

**第三条是关键**："先检查路径、再按路径打开"永远有窗口；
**打开一次、之后只用句柄**才没有。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 含 `..` 或绝对路径的用户输入 | **无法到达文件层**——它进不了根目录名 |
| 工作区根目录是符号链接 | **拒绝打开**（并在告警日志留痕） |

#### 验收要点

- **注入**：恶意路径与符号链接用例。
- **预期**：全部拒绝；**且 TOCTOU 用例在竞争条件下仍不越界**。

### REQ-ISO-008　根目录名不经用户输入

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §4

#### 语义

工作区根目录使用**服务端生成的不透明 ID**，**不得直接拼接用户输入**。

#### 规格

- 根目录名 = **服务端生成的不透明 ID**，与主体的名称、工作区的 `name` **都无关**。
- **这条带来两个额外收益**（都不是附带，是被用到的）：
  1. **改名不碰文件系统**——`ALTER WORKSPACE ... SET NAME` 只是 `public` 上的
     一次本地事务（存储架构 §2.11）
  2. **路径穿越失去构造材料**——REQ-ISO-007 的第一道由此成立

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 用户输入含目录分隔符 | 它**不参与拼接**，因此无影响 |
| 目录名与主体名相同 | **不可能**——两者来源不同 |

#### 验收要点

- **构造**：以各种含特殊字符的主体名/工作区名建工作区。
- **预期**：目录名**恒为不透明 ID**，不可由输入推导。

### REQ-ISO-009　备份恢复校验身份与版本

**优先级**：必须　**阶段**：P11　**追溯**：总体方案 §4、§21

#### 语义

备份恢复必须**校验 WorkspaceId 与格式版本**，不得把用户 A 的备份导入用户 B 的工作区。

#### 规格

- 恢复前校验**备份中的 WorkspaceId** 与**目标工作区的 WorkspaceId** 一致；
- 校验**格式版本**：不兼容的版本**拒绝**，不做"尽力而为"的解释；
- **与 REQ-ISO-001 同一条理由**：跨工作区导入不是"权限问题"，
  是**数据血统问题**——页上的工作区受校验标识会让它大量报错，
  但**不能等信息到那一层才发现**。

> **依赖**：备份产物的存放位置与清单格式**尚未定**（存储架构 §14 项 26），
> 故本条的**校验时机与载体**待那一项冻结后补齐。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| WorkspaceId 不匹配 | **拒绝**，且**不区分**"别人的备份"与"损坏的备份"（REQ-ISO-006） |
| 格式版本不兼容 | **拒绝**，并给出可判定的版本信息 |

#### 验收要点

- **注入**：跨主体恢复、跨格式版本恢复。
- **预期**：全部拒绝；**错误响应不泄露备份的来源主体**。

### REQ-ISO-010　隔离失败是发布阻断项

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §3

#### 语义

隔离失败**不得以概率或平均成功率验收**——用例通过率必须为 **100%**。

#### 规格

**这条约束的是验收方式，但它有一个更重要的推论**：

> **隔离不能靠"很难触发"来保证。概率低不等于不存在。**

- 隔离用例**零容忍**：**一条失败即阻断发布**，不做"影响面评估"
- **不得用"未观察到失败"代替"不可能失败"**——两者的区别正是本域要防的
- **"偶发失败"视为失败**——偶发正是竞态的表现，不是可接受的噪声
- 与时序相关的用例（REQ-ISO-007 的 TOCTOU）必须在**竞争条件下重复运行**

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 隔离用例失败 1 条 | **阻断发布** |
| 用例"偶发通过" | 按**失败**处理 |

#### 验收要点

- **预期**：隔离用例**全部通过**，且**重复运行多次全部通过**。

---

### REQ-ISO-011　不做跨主体内容去重

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §4

#### 语义

私有工作区之间**不使用硬链接、不共用资产目录、不做跨用户内容去重**；
校验和相同的资产**仍各自独立存储与计费**。

#### 规格

**去重是性能优化，但它会制造三条不该有的耦合**：

| 去重带来 | 后果 |
| --- | --- |
| 物理共享 | 删除一个主体的数据**影响另一个**——隔离被绕过 |
| **可检测的共享** | 上传一个文件，**通过存储占用或计时的变化**就能判断"别人是否已有同样内容" |
| 计费归属 | "这条数据算谁的"没有答案 |

**第二条是拒绝去重的决定性理由**：它把**"某个内容是否存在"泄露给了另一个主体** ✗——
正是 REQ-ISO-006 要挡的东西。

**去重的收益在大规模多租户下才显著；本库的隔离底线不允许它。**
简单方案在这里同时是安全方案。

**克隆不是去重**：它在**同一 owner 范围内**（§2.7 是管理员操作），
reflink 的两个工作区属于同一个主体——**REQ-ISO-012 正是这条边界**。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 两个工作区上传校验和相同的资产 | **各自独立存储**，各算各的占用 |
| 试图跨工作区共享资产目录 | **不存在这条路径** |

#### 验收要点

- **构造**：两个主体上传**字节相同**的资产。
- **预期**：存储占用**各自增加**；任一方的删除**不影响另一方**。

---

### REQ-ISO-012　克隆不是跨主体转让通道

**优先级**：必须　**阶段**：P11　**追溯**：总体方案 §3、§21

#### 语义

克隆**不得作为跨用户数据转让通道**——**只能在同一 owner 的范围内执行**。

#### 规格

**克隆的能力与 REQ-ISO-003 正好顶上**：reflink 复制一个工作区的**全部数据**。
**若允许跨 owner，它就是一条完整的、绕过所有隔离的"数据转让"通道。**

**所以 owner 范围不是一条"权限检查"，它是这个操作定义的一部分**：

| 克隆 | 允许？ |
| --- | --- |
| **同一 owner 的工作区之间** | ✅——reflink 的收益（快速分支）正在此处 |
| **跨 owner** | ❌——**不存在这条路径** |

**这句话反过来定死了一件事**：**一个 owner 可以有多个工作区**。
若一个 owner 只有一个工作区，"同一 owner 范围内"就是空的——
**与本域 §0 的两类主体表一致**。

**克隆的属主就是源的属主**，不是发起人：
§2.7 定的是"这是管理员操作"——**admin 管实例，不管数据**（§0），
它执行克隆，但**不因此获得数据**。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 跨 owner 克隆 | **不存在这条路径** |
| admin 发起跨 owner 克隆 | **同上**——admin 不因管理身份获得数据 |
| 以"owner 已变更"为由绕过 | **不可能**——owner 不可变（REQ-ISO-005） |

#### 验收要点

- **构造**：跨 owner 克隆；admin 发起跨 owner 克隆。
- **预期**：全部**不存在这条路径**。

## 待确认汇总（ISO 域）

### 已随本域定案

| 项 | 结论 |
| --- | --- |
| 模型的形状取自哪里 | **PostgreSQL 的 role / owner / superuser / 共享区**，参照其"一个实例多个数据库" |
| 对象级授权矩阵 | **不采纳**（REQ-ISO-003） |
| 角色嵌套 / 组 | **不做**——没有"共享权限"的场景 |
| 身份来源 | **认证结果**；路由是**身份的函数**，与请求参数无关 |
| owner 不可变、跨区外键 | **靠不提供**，不靠检查 |
| 一个主体几个工作区 | **可以有多个**——REQ-ISO-012 的"同一 owner 范围内"以此为前提 |
| 跨主体内容去重 | **不做**——它会泄露"某内容是否存在"，且解法更简单 |
| 隔离验收方式 | **100% 通过率为门槛**，不接受概率与"偶发" |
| `public` 的读写 | 读经**过滤层**；写经**标准接口**；直接 DML 一律拒绝 |
| 路径安全 | **根目录不经用户输入**是第一道；**以句柄为准**消除 TOCTOU |
