**写并发模型：多写者、低争用**（已确认）。

### REQ-TXN-001　Read Committed 语句快照

**优先级**：必须　**阶段**：P3–P4　**追溯**：总体方案 §8、§18

#### 语义

每个语句在**开始执行时**取一次快照；语句执行全程使用该快照判定可见性。同一事务内的不同语句可取到不同快照。未提交数据在任何情况下不可见。

#### 规格

- 快照表示为**提交序号上界 S**：语句开始时已提交的最大提交序号。
- 可见性判定：记录对某事务可见 ⟺ 该记录的写入事务已提交**且**其提交序号 ≤ S。
- 快照在语句内**固定**，不得因语句执行期间的其他提交而刷新。
- 语句结束即释放该快照（登记到最老快照集合中移除）。
- 只读语句同样取快照（保证语句内一致性）。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 语句执行中其他事务提交 | 本语句不可见该提交；**下一语句**可见 |
| 语句执行中读到被未提交事务修改的行 | 经 Undo 重建该行在本快照下的版本（REQ-TXN-006） |
| 快照所需的 Undo 已被回收 | 返回 `BICDB-TXN-xxx`（快照过旧）；见 REQ-TXN-017 |

#### 验收要点

- **构造**：表含一行 `k=1`；事务 A 与 B 并发。
- **注入**：A 执行 `SELECT`，中途 B 提交对 `k` 的修改，A 继续遍历。
- **预期**：A 的该语句看不到 B 的修改（结果等于语句开始时的状态）；A 的下一条语句能看到。
- **交叉验证**：至少 1 万组随机历史符合独立 RC 参考模型（总体方案 §18）。

### REQ-TXN-002　多写事务与行锁

**优先级**：必须　**阶段**：P4　**追溯**：总体方案 §8、§18

#### 语义

允许同一工作区内多个写事务并发；对同一行的并发写通过行级排他锁串行化。

#### 规格

- **锁模式只有 X（排他）**。读不加任何锁（REQ-TXN-005）。因此不存在 S/X 兼容矩阵。
- **锁对象**：`(workspace_id, object_id, ROWID)`。ROWID 是**稳定入口**——行迁移经**转发指针**保持原槽位 ROWID 不变（REQ-STO-005），而锁的存续期内该行不可能被删除并复用（**删除同样要持锁**）。
- **加锁时机**：写操作在**修改前**必须已持有该行 X 锁。
- **释放时机**：**持有至事务结束**（提交或回滚）。不做语句级释放。
  - 理由：语句级释放会在 RC 下引入更复杂的重读语义，且与"低争用"画像不匹配，收益不足。
- **锁等待**：等待时必须可被取消、可超时，且**等待期间不得持有 latch**（REQ-STO-007）。
- **写-写冲突**：后到者等待；等待超时返回资源/冲突类错误（见 CONV §4.3）。
- **不做锁升级**：不存在表锁，故无升级路径。
- **不做间隙锁/谓词锁**：RC 下允许幻读（REQ-TXN-009）。

#### 边界与错误

| 情形 | 行为 | 类别 |
| --- | --- | --- |
| 两事务写同一行 | 后到者等待，超时后返回冲突 | 可重试冲突 |
| 死锁 | 检测并牺牲一个（REQ-TXN-003） | 可重试冲突 |
| 等待中客户端取消 | 释放等待，不改变已持有锁 | — |
| 事务结束 | 一次性释放全部锁 | — |

#### 验收要点

- **构造**：两个客户端并发更新同一行，循环 N 次。
- **预期**：最终值等于串行执行的结果之一；无丢失更新；无永久挂起。
- **覆盖**：2、8、32 客户端读写交错（总体方案 §18）。
- **并发检查**：TSan 无未解释竞态。

### REQ-TXN-003　语句回滚、事务回滚与死锁检测

**优先级**：必须　**阶段**：P3–P4　**追溯**：总体方案 §8

#### 语义

提供三种粒度的失败恢复：语句失败回滚、事务回滚、死锁牺牲者回滚。三者都必须保证不留下部分修改。

#### 规格

**语句失败回滚**
- 语句开始前登记 Undo 标记位置；失败时反向应用到该标记。
- 语句级回滚**不释放**该语句已获取的行锁（锁持有至事务结束）。
- 语句级回滚**不回滚**该语句之前已成功语句的效果。

**事务回滚**
- 反向应用该事务全部 Undo 记录，然后释放全部锁。
- 回滚必须幂等：重复回滚不产生额外效果。

**死锁检测**（待确认 D-03、D-04）
- 维护**等待图**：节点为事务，边 `T1 → T2` 表示 T1 等待 T2 持有的锁。
- 周期检测环；发现环后选择**牺牲者**（推荐：已修改行数最少者，代价最小）。
- 牺牲者事务回滚，向该客户端返回**可重试冲突**类错误；其他事务继续。
- 锁等待含**超时**（推荐默认 5 秒，可配置）。超时返回资源/冲突类错误，**不等同**于死锁检测失败。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 语句中途约束冲突 | 语句回滚；事务仍可继续或由客户端决定回滚 |
| 死锁环含 3 个以上事务 | 牺牲代价最小者 |
| 牺牲者回滚失败（Undo 损坏） | 升级为严重错误，触发恢复流程 |
| 等待超时后又获锁 | **不得**继续使用旧快照结果（REQ-TXN-015） |

#### 验收要点

- **构造**：A 锁行 1 再锁行 2，B 锁行 2 再锁行 1。
- **预期**：其一被牺牲并返回可重试错误，另一个成功；无永久挂起。
- **交叉验证**：至少 1 万组随机历史符合 RC 参考模型（总体方案 §18）。
- **否定**：构造不构成环的等待链，验证**不**误杀。

### REQ-TXN-005　读路径无锁化

**优先级**：必须　**阶段**：P4　**追溯**：总体方案 §8、§11；需求文档 §2.3

#### 语义

读操作不获取行锁、不阻塞写、不被写阻塞、不依赖写路径进展。这是本产品读多写少画像的**核心要求**。

#### 规格

- 读路径**不调用**任何锁管理器接口。实现上应在读路径的依赖中**不包含**锁模块。
- 读需要某行在快照 S 下的版本时：
  1. 若当前版本对 S 可见 → 直接返回；
  2. 否则沿 Undo 链反向重建至可见版本（REQ-TXN-006）。
- 读路径**不得**因等待写事务而阻塞。若重建所需 Undo 不可用，返回错误而非等待（REQ-TXN-017）。
- 读路径的 latch 仅保护内存结构，持有时间有界（REQ-STO-007）。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 读遇到正在被修改的行 | 经 Undo 重建旧版本；不等待 |
| 读所需 Undo 已被回收 | 返回快照过旧错误 |
| 读遇到正在分裂的索引页 | 按索引并发协议处理（STO 域）；不得阻塞在事务上 |

#### 验收要点

- **构造**：长读事务（大范围扫描）与高频写事务并发。
- **预期**：读不等待写，写不等待读；两者均正常完成。
- **性能**：注入写负载时读 p99 保持有界（REQ-PERF-009）。
- **结构**：读路径的模块依赖中不含锁管理器（构建期检查）。

### REQ-TXN-006　Undo 的双重用途

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §8

#### 语义

Undo 必须**同时**支持两种用途，二者对记录内容的要求不同，必须都满足：

| 用途 | 要求 |
| --- | --- |
| **事务回滚** | 能反向撤销该修改 |
| **一致性读** | 能重建该行在任意更早快照下的版本 |

#### 规格

- 每条 Undo 记录必须包含：所属事务、前一 Undo 的位置（`prevLSN` 或等效链）、被修改对象的定位、**足够重建旧值的信息**。
- 对原地更新的行：Undo 保存**旧值**（而非新值）。
- 对插入：Undo 记录"删除该行"所需信息。
- 对删除：Undo 记录"恢复该行"所需信息。
- **旧版本重建必须可从 Undo 链完成**，不得依赖主堆中保留旧版本（REQ-STO-004）。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 同一行被同一事务多次修改 | Undo 链按逆序应用，逐步回到目标快照 |
| 跨页行被修改 | Undo 需覆盖全部受影响片段 |
| Undo 被回收但仍有快照引用 | **禁止**；回收前必须确认无快照引用（REQ-TXN-017） |

#### 验收要点

- **构造**：对同一行连续做 N 次修改，期间开启多个快照。
- **预期**：每个快照都能重建出正确的历史版本，与独立参考模型逐字段一致。
- **回滚验证**：事务回滚后行内容与事务开始前逐字段一致。

### REQ-TXN-007　修改顺序：先日志后数据

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §8

#### 语义

任何受保护结构的修改必须严格遵循：**先写恢复所需信息，再修改结构**。

#### 规格

标准修改序列，**不得调换**：

1. 写入 Undo 记录（若该修改可回滚）。
2. 写入日志描述记录（redo/undo 描述），分配 LSN。
3. 在**内存中**修改数据页，并将 `pageLSN` 更新为该记录 LSN。
4. 脏页由缓冲池按策略刷盘；**刷盘前必须保证该页 `pageLSN` 对应的日志已持久化**（REQ-TXN-008）。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 日志写入成功但页修改前崩溃 | 恢复重做该修改 |
| 页修改但日志未持久化（违反约束） | **禁止**；由 REQ-TXN-008 的检查拦截 |
| 结构修改（页分裂、分配） | 同序列，且使用单独审查的系统操作协议（REQ-STO-010） |

#### 验收要点

- **注入**：在上述每个步骤之间注入崩溃。
- **预期**：恢复后结构一致，且不出现"数据已落盘但日志缺失"。

### REQ-TXN-008　数据页持久化前 WAL 必须已持久化

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §8

#### 语义

这是 WAL 的核心不变量。任何数据页写盘前，其 `pageLSN` 及之前的日志必须已在稳定存储上。

#### 规格

- 缓冲池刷某页前，检查该页 `pageLSN` ≤ 已持久化的日志位置；不满足则**先刷日志**（日志先行）。
- 检查点必须记录"该点之前所有日志已持久化"的下界，供恢复定位重做起点。
- 该检查与刷页动作必须在同一临界区内完成，不得有检查与刷页之间的窗口。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 日志持久化失败 | 页**不得**刷盘；事务提交不得返回成功 |
| 日志短写 | 按 REQ-TXN-014 的规则处理并判定失败 |

#### 验收要点

- **注入**：在刷页与刷日志之间注入崩溃。
- **预期**：恢复后可判定地重做或判定该页无效，不出现静默不一致。

### REQ-TXN-010　提交响应晚于耐久确认

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §8

#### 语义

向客户端返回"提交成功"之前，该事务的提交日志必须已在稳定存储上。

#### 规格

提交序列，**顺序不得调换**：

1. 分配提交序号。
2. 写入提交日志记录（含事务状态变更）。
3. **等待日志持久化确认**（可 group commit 合并多个事务的 fsync）。
4. 释放锁，登记快照推进。
5. **此时才**向客户端返回成功。

- group commit **允许**：多个事务可共享一次 fsync，但每个事务的响应必须晚于**包含其提交记录的那次** fsync 完成。
- 提交序号可在步骤 1 分配，但**不得**在步骤 3 完成前对读可见。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| fsync 失败 | 提交失败；返回错误并回滚；**不得**返回成功 |
| fsync 期间进程崩溃 | 客户端未收到响应 → 结果未知（REQ-TXN-011） |
| 提交日志已写但未 fsync 时崩溃 | 恢复时该事务未提交，回滚 |

#### 验收要点

- **构造**：发出提交并在收到成功响应后立即断电。
- **预期**：恢复后该事务**必定存在**。
- **反向**：未收到响应的提交，恢复后可能存在也可能不存在，但**不得部分提交**。

### REQ-TXN-011　结果未知状态与消歧

**优先级**：必须　**阶段**：P3、P5　**追溯**：总体方案 §8、§15

#### 语义

网络断开或超时后，客户端无法判定提交是否成功。系统必须保留该不确定性并可被消除，**不得**让客户端盲目重试。

#### 规格

- 事务状态对外可为 `unknown`（见 CONV §4.3 第四类）。
- 消歧途径二选一或并存：
  1. **幂等键**：写请求携带 `idempotency_key`，其结果记录与业务变化**同事务提交**（REQ-API-006）。重试同键同内容返回原结果，不再执行。
  2. **提交结果查询**：客户端用 `request_id` 或事务标识查询最终状态。
- 相同键**不同内容**必须拒绝（不返回原结果）。
- 结果记录的保留期限必须 ≥ 客户端最大重试窗口；具体值 P0 冻结。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 同键同内容重试 | 返回首次结果，不重复执行 |
| 同键不同内容 | 拒绝，返回冲突类错误 |
| 结果记录已过期 | 返回明确错误，**不得**当作首次执行 |
| 客户端未提供幂等键 | 服务端不得自动重试；响应中标注 `txn_status=unknown` 的可能 |

#### 验收要点

- **构造**：提交后断开客户端连接。
- **注入**：客户端重试。
- **预期**：业务效果恰好一次；同键不同内容被拒绝。

### REQ-TXN-012　steal + no-force 下的恢复

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §8、§17

#### 语义

采用 steal（允许未提交页刷盘）与 no-force（提交时不强制刷页）策略，因此恢复必须同时处理**重做已提交**与**撤销未完成**。

#### 规格

恢复三阶段：

1. **分析**：从最近检查点起扫描日志，重建崩溃时刻的**事务状态表**与**脏页表**，确定重做起点。
2. **重做**：从重做起点起，对所有修改（含未提交事务的修改）重放，恢复到崩溃前状态。重做必须**幂等**：已包含该修改的页（按 `pageLSN` 判定）跳过。
3. **撤销**：对未完成事务反向应用 Undo，并写入**补偿日志记录**。

**可重入**：恢复过程本身被中断后再次恢复必须能继续。实现方式为：撤销阶段先写补偿记录再改页（与正常运行同序），使进程可再次分析并从断点继续。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 日志尾部截断 | 按定义规则判定有效日志边界，丢弃不完整尾部 |
| 页校验失败 | 该页判定损坏，触发相应处理（STO 域） |
| 恢复中再次崩溃 | 下次恢复从中断处继续，不重复已完成的补偿 |

#### 验收要点

- **注入**：至少 1 万次随机崩溃，**覆盖页、位图、Undo、控制文件、日志短写、部分页**（总体方案 §17）。
- **中途再断**：在恢复过程中再次中断，验证仍可继续。
- **对照**：每次恢复执行检查器并与参考历史对照。

---

### REQ-TXN-013　日志内容与可重入

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §8

#### 规格

日志记录必须包含：

| 字段 | 用途 |
| --- | --- |
| 事务标识 | 归属判定 |
| `prevLSN`（或等效链） | 撤销时定位同事务前一条 |
| 记录类型 | 重做/撤销的分派 |
| 目标定位 | 页、槽位、或结构对象 |
| 修改描述 | 足以重做与撤销的内容 |
| 结构变化记录 | 页分裂、分配、位图等 |
| 补偿记录 | 撤销阶段产生，使恢复可重入 |

- 重做与撤销**都必须可重入**（幂等）。
- 日志必须有校验，能识别短写与尾部不完整。

#### 验收要点

- **构造**：对每种记录类型分别构造崩溃点。
- **预期**：重放两次与重放一次结果相同（幂等性）。

### REQ-TXN-014　部分页写入保护

**优先级**：必须　**阶段**：P2–P3　**追溯**：总体方案 §8

#### 语义

存储层可能发生"部分页写入"（页只写了部分扇区）。恢复必须能识别并修复。

#### 规格

- 采用**完整页映像**（full page image）或经评审的等效保护。
- 具体策略（何时记录完整页映像、如何与检查点配合）须经评审，**不得**默认关闭。
- 独立定义并测试三类异常：**日志短写**、**校验失败**、**尾部截断**。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 页校验失败且无有效完整页映像 | 判定不可恢复损坏（发布阻断级） |
| 日志尾部不完整 | 截断至最后一条完整记录 |

#### 验收要点

- **注入**：模拟部分页写入（仅写部分扇区后崩溃）。
- **预期**：恢复后页内容正确或明确判定损坏，**不得**静默返回错误数据。

### REQ-TXN-015　谓词重检与 Halloween 防护

**优先级**：必须　**阶段**：P4　**追溯**：总体方案 §8

#### 语义

RC 下语句执行期间数据可能变化，导致谓词不再成立或行被重复处理。

#### 规格

- 写操作获取锁后可能**需要重新获取最新版本并重新判定谓词**；若不再满足则跳过该行。
- 语句因锁等待超时/死锁牺牲后重启时，**必须重新评估谓词**，不得沿用旧判定。
- **Halloween 防护**：向正在扫描的表中插入的行**不得**被同一语句重复处理。实现方式须明确（如扫描区间上界在使用前固定）。
- 不得重复修改同一行。

#### 验收要点

- **构造**：`UPDATE t SET x=x+1 WHERE x<100`，同时并发插入满足条件的行。
- **预期**：无行被重复更新；无死循环；结果符合 RC 语义。
- **构造 2**：语句因锁等待重启。
- **预期**：重启后重新判定谓词，不产生重复效果。

### REQ-TXN-016　DDL 使用独立事务与对象锁

**优先级**：必须　**阶段**：P4–P5　**追溯**：总体方案 §8

#### 规格

- DDL 在**独立事务**中执行，不与用户事务混合。
- 使用**对象锁**保护被 DDL 影响的对象。
- 未完成用户事务中发起 DDL 必须**拒绝**。
- DDL 的提交/回滚不得隐式提交用户事务（总体方案明确不推导 PL/SQL 与 DDL 隐式提交语义）。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 活动事务内发起 DDL | 拒绝，返回语法/状态错误 |
| DDL 与并发 DML 冲突 | 按对象锁串行化 |
| DDL 执行中崩溃 | 按独立事务语义回滚 |

#### 验收要点

- **构造**：事务内 `CREATE TABLE`。
- **预期**：拒绝。
- **并发**：DML 执行中发起对同表 DDL，验证串行化正确。

### REQ-TXN-017　长快照、Undo 耗尽与超时

**优先级**：必须　**阶段**：P3–P4　**追溯**：总体方案 §8

#### 语义

系统必须能应对长期快照与 Undo 空间压力，且**绝不覆盖仍被需要的旧版本**。

#### 规格

- 维护**最老活动快照**的提交序号；Undo 回收不得越过该下界。
- Undo 空间不足时：
  1. 优先回收已无快照引用且事务已结束的 Undo；
  2. 仍不足则**拒绝**新事务的写操作，返回资源类错误（`retry_after_ms` 有效）；
  3. **不得**回收仍被引用的 Undo，**不得**强制终止长快照。
- 长事务/长快照超时：返回明确错误（不静默失败），且**不得**在超时后继续持有资源。
- 保留策略（待确认 D-05）：推荐旧版本保留 30 分钟或直到最老快照释放，取先到者。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 读所需 Undo 因超期被回收 | 返回"快照过旧"错误（对应 Oracle ORA-01555 语义类） |
| Undo 空间耗尽 | 拒绝新写，返回资源类错误 |
| 长快照持续占用 | 记录指标（REQ-OPS-005），不强制终止 |

#### 验收要点

- **构造**：开启长快照，同时高频写入以耗尽 Undo。
- **预期**：长快照的读仍正确（若未超期）；耗尽时新写被**拒绝**而非覆盖旧版本。
- **指标**：最老快照年龄可观测。

### REQ-TXN-018　资产与派生索引不冒充同一原子存储

**优先级**：必须　**阶段**：P6–P7　**追溯**：总体方案 §8、§9

#### 语义

外部资产文件与异步派生索引**不在**页日志的原子范围内。文档与接口必须明确这一点，不得让调用方误以为二者与页数据同一事务。

#### 规格

- 资产：使用预留→staging→校验→原子移动→提交元数据的独立协议（AST 域）。
- 派生索引：使用事务 outbox 与水位（RET 域）。
- **不得**提供"资产写入与页数据同一事务原子生效"的语义承诺。
- 三类存储（页数据、资产文件、派生索引）在接口上必须可区分。

#### 验收要点

- **构造**：在资产上传各阶段注入崩溃。
- **预期**：不出现"已提交引用指向未持久化文件"；不出现"索引声称已同步但源数据未提交"。

### REQ-TXN-019　跨区不支持写事务

**优先级**：必须　**阶段**：P5–P6　**追溯**：总体方案 §3、§8

#### 规格

- 私有工作区与 `public` 之间**不支持**写事务、外键或两阶段提交。
- 联合检索分别调用私有区与 public，融合时保留来源、版本与分数。
- 单次融合读取**固定 public 版本令牌**与本人快照；不承诺跨区全局同一时刻。
- public 发布采用**暂存 + 原子版本切换**；读取中的旧版本在引用释放后回收。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 尝试跨区写 | 拒绝 |
| 尝试跨区外键 | 拒绝 |
| 融合查询期间 public 切换 | 本次查询仍用其固定的版本令牌 |

#### 验收要点

- **构造**：在融合读取过程中触发 public 版本切换。
- **预期**：读取结果内部一致（来自同一 public 版本）
