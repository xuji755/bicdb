## 0 模型总述

### 0.1 四层交付——顺序是要求的一部分

```text
① 内核会话接口（引擎内）
② Python SDK（一等交付物）      ┐ REQ-API-002 的先行交付
③ CLI（SDK 之上的薄壳）         ┘
④ HTTP / MCP 适配层（可选、后置）——同一语义的映射，不是第二套语义
```

**SDK 与 CLI 先行不是优先级排序，是接口裁判权的问题** ✗✓：
先有 SDK，协议就被**使用它的代码**检验；先有 HTTP 层，
协议会被"先跑起来"的临时形状绑架 ✓。适配层永远只做**翻译**——
若某个能力在适配层"翻译不过去"，答案是**不加这个能力**，不是改语义 ✓。

### 0.2 一条铁律：身份不在参数里

**工作区与主体身份在会话建立时确定，此后任何请求字段、游标、工具参数都不得覆盖它** ✗✓——
这是 REQ-API-013 的推广，也是本域与 `ISO`、`SQL` 共享的同一条纪律：

| 它出现在哪 | 形态 |
| --- | --- |
| 请求参数 | **没有身份字段**——不认识 `workspace_id` / `user` 这类参数，出现即拒绝 |
| 分页游标 | **绑定工作区**（REQ-API-009）——别人的游标换不来别人的数据 |
| MCP 工具参数 | 同上：**参数覆写身份 = 拒绝**（REQ-API-013） |
| SQL 文本 | 图名、表名都不是工作区入口（`SQL` REQ-SQL-003 / `GRP` REQ-GRP-013） |

**四行是同一件事**：身份是**会话的属性**，不是**请求的属性** ✓。

### 0.3 协议形态：结构化消息 + 独立流 + 会话内串行

| | |
| --- | --- |
| **消息** | 长度前缀分帧；字段**类型化**（不是自由文本）——编码照 `CONV` §5 |
| **版本** | 会话建立时协商（REQ-API-001） |
| **串行** | 一个会话**同时只执行一条命令**（方案 §15）——可流水线发送，结果**按序**返回 |
| **流** | **资产数据走独立通道**（REQ-API-003）——不塞进 SQL 请求体 |
| **取消** | 独立可发的取消命令（按 `request_id`）；幂等；取消后释放锁、页引用与临时空间（方案 §15） |
| **截止时间** | 每条命令可带 deadline；到点按可取消路径中止 |

**"结构化"的边界**：只有 **SQL 文本**与**资产字节**是"用户内容"，
其余每个字段都有类型标签与取值域——**协议不解析自由文本** ✗✓。

### 0.4 响应封套（REQ-API-004 的字段全部在此）

**每条响应**都带：

| 字段 | 内容 |
| --- | --- |
| `request_id` | 服务端必回（客户端可自带；服务端始终回显最终采用的） |
| `txn_status` | `none` / `active` / `aborted` / `unknown`（`CONV` §4.2 的取值） |
| `code` / `retryable` / `retry_after_ms` | 成功时省略；失败时照 `CONV` §4.2 |
| `index_watermark` | **检索类响应必带**：源提交水位（`RET` REQ-RET-015）——"我的数据到哪个提交序号为止已进索引"✓ |
| 截断状态 | 查询类响应带"完整 / 已截断（原因）"（`GRP` REQ-GRP-009、`RET` REQ-RET-025） |

**"重试建议"不是自由文字** ✗✓——它由 `retryable` + `retry_after_ms` + `txn_status`
三个字段共同表达（`CONV` §4.3 的四类判定表）：

| 类别 | 字段组合 |
| --- | --- |
| 可重试冲突 | `retryable = true`（`retry_after_ms` 可空） |
| 资源拒绝 | `retryable = true` + `retry_after_ms` **有效** |
| 已中止事务 | `txn_status = aborted`，`retryable = false`（原事务不可重试） |
| **提交结果未知** | `txn_status = unknown`，`retryable = false`——**消歧靠对账**（REQ-API-014：`sync` / `status`） |

### 0.5 命令族（闭集）

| 族 | 命令 | 说明 |
| --- | --- | --- |
| 会话 | `hello` / `open_session` / `close_session` | 版本协商与身份建立（§0.2） |
| 执行 | `execute {sql, params[], deadline?}` | **SQL 与图语言语句走同一通道** ✗✓——"图语言独立入口"是引擎内的解析分派（`SQL` §0.2），**不是线上的第二通道** |
| 结果 | 行批次流（列元数据 + 类型化值）+ 结束状态 | 流式；截断状态见 §0.4 |
| 资产 | `asset_begin` / 数据帧 / `asset_end` / `asset_abort`；`asset_read` | 独立流（REQ-API-003）；语义见 `AST` REQ-AST-007 的七步 |
| 检索 | `search {…}` | `RET` REQ-RET-006 的六项输入；响应带水位与截断状态 |
| 取消 | `cancel {request_id}` | 幂等 |
| 对账 | `sync {已确认序号}` / `status {request_id 或提交序号}` | 断连后判定未确认请求终态（REQ-API-014）——"不盲目重试"的落点 |

**这张表就是 SDK 的全部表面** ✗✓——SDK 不提供表外的方法；"表面越短、可漏判越少"。

### REQ-API-001　版本化结构化请求

**优先级**：必须　**阶段**：P5　**追溯**：总体方案 §15

#### 语义

协议采用**版本化结构化请求**。

#### 规格

**协商过程**（`hello` 往返，`open_session` 之前）：

```text
客户端 → hello { 支持的协议版本集合, 客户端标识 }
服务端 → { 服务端版本集合, 能力清单, 会话选项 }
客户端 → open_session { 选定版本, 身份凭证 }
```

| 规则 | |
| --- | --- |
| 版本形如 `MAJOR.MINOR` | **大版本不兼容**：无交集 → 稳定错误，会话不建立 |
| **小版本向后兼容** | 同大版本内：**未知的可选字段忽略，未知的必填字段拒绝** ✗✓ |
| 能力清单 | 服务端枚举（如"图""ANN""MCP"）——客户端**以能力为准**，不以版本号推断 ✓ |

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 客户端版本集合与服务端无交集 | `code` = 协议类；`retryable = false`——**可判定**（REQ 验收"版本协商可测"） |
| 同大版本 + 未知可选字段 | 忽略，继续 |
| 未协商就发 `execute` | 拒绝（状态错误） |

#### 验收要点

- **构造**：旧大版本、未知大版本、同版本加未知可选字段。
- **预期**：三者行为**逐一可判定**；能力清单与实际行为一致。

### REQ-API-002　Python SDK 与 CLI 先行

**优先级**：必须　**阶段**：P5　**追溯**：总体方案 §15

#### 语义

**先交付 Python SDK 与 CLI**，再提供**可选** HTTP/MCP 适配层。

#### 规格

**SDK 的表面 = §0.5 的命令族 + 错误的四类异常层级**（REQ-API-012）：

| SDK 构件 | 对应 |
| --- | --- |
| 连接与会话（含版本协商、凭证） | `hello` / `open_session` |
| `execute(sql, params=…)` + 结果迭代器（行批次） | 执行族；**参数只走参数通道**（REQ-API-003） |
| 会话事务方法（begin / commit / rollback）与**声明式重试策略** | REQ-API-012 的纪律 |
| 资产流 `upload` / `download` | 资产族（分块、界内缓冲——`AST` REQ-AST-006） |
| 检索 `search(...)` | 检索族；返回值含**水位**与截断状态 |
| 分页迭代器（游标封装） | REQ-API-009 |
| 四类异常的基类层级 | REQ-API-012——**代码按类型分支，不做字符串匹配** ✓ |

**CLI**：SDK 的薄壳——交互模式 + 非交互（单条命令、参数文件）；
输出形态（表格 / JSON）；退出码：成功 0、失败非 0 且**打印稳定错误码** ✓。

**HTTP / MCP 适配层**（可选、后置）：**纯翻译**（§0.1）——
二进制按适配层的惯例编码（如 base64），**语义零改动**；
MCP 的工具清单见 REQ-API-013。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 适配层想加"更方便"的语义 | **拒绝**——那是新能力，走需求回流 |
| CLI 参数里的 SQL 拼接 | CLI **不提供**模板展开；参数经参数文件/旗标走参数通道 ✓ |

#### 验收要点

- **构造**：P5 用 SDK 完成 §0.5 全部命令族；CLI 跑通同一组用例。
- **预期**：**SDK 可用性以它通过全部域的验收用例为判据**（SDK 是协议的第一个使用者）。

### REQ-API-003　绑定参数；资产流独立

**优先级**：必须　**阶段**：P5　**追溯**：总体方案 §15

#### 语义

SQL **使用绑定参数**；**资产流独立传输**。

#### 规格

| 规则 | |
| --- | --- |
| **执行请求 = SQL 文本 + 参数表**（`:name` → 类型化值） | 参数类型在绑定期推导（`SQL` REQ-SQL-003）；**服务端不解析客户端拼接** |
| **SDK 不提供字符串模板** | 无 `format_sql()` 一类辅助——**没有"把参数拼进文本"的路径** ✗✓（REQ 验收"无字符串拼接路径"= 审查 SDK 表面） |
| **资产字节不进请求体** | 走独立流：`asset_begin`（声明 size / checksum / media_type / 幂等键）→ 服务端回 `{asset_id, 已收长度}`（**续传起点由此推导**）→ 数据帧（**显式偏移**，长度受声明值封顶）→ `asset_end`（服务端校验）|
| 取消 | `asset_abort` = `AST` REQ-AST-008 的"取消"路径；幂等 |

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 数据帧超出声明大小 | **立即拒绝**（`AST` REQ-AST-006） |
| 同幂等键 + 异声明 | 拒绝（`AST` REQ-AST-005） |
| 在 SQL 文本里放资产内容 | 引擎不支持——文本就是文本，**大字节没有文本通道** ✓ |

#### 验收要点

- **构造**：审查 SDK 表面无拼接辅助；上传 1GB 资产，观测服务端内存与连接行为。
- **预期**：**无字符串拼接路径**；内存占用与块大小同阶（与 `AST` 同款验收）。

### REQ-API-004　响应字段

**优先级**：必须　**阶段**：P5　**追溯**：总体方案 §15

#### 语义

返回结果包含 **request_id、事务状态、稳定错误码、重试建议与检索水位**。

#### 规格

**§0.4 的封套即为本条规格**，不再重复。三点补充：

| 点 | 规定 |
| --- | --- |
| **成功响应也带 `txn_status`** | 调用方随时知道"我现在在不在事务里"——尤其是自动提交的语句 ✓ |
| **检索水位在检索类响应中必带** | 最终一致模式下**必须**（`RET` 的硬要求）；严格新鲜度模式带"已补齐"标记 ✓ |
| `message` 不得包含私有数据内容 | `CONV` §4.2 的既有约束（REQ-OPS-002）——错误信息也过这条 ✓ |

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 取消后到达的响应 | 仍带原 `request_id` + `txn_status`（取消的结果**可判定**）✓ |
| 缺字段 | **验收失败**（本条的验收原文"字段完整"） |

#### 验收要点

- **构造**：成功 / 四类错误 / 取消 / 检索，各取一个响应逐个字段比对。
- **预期**：字段完整；四类错误**仅凭字段**可区分（不做字符串匹配）。

### REQ-API-005　编码

**优先级**：必须　**阶段**：P5　**追溯**：总体方案 §15

#### 语义

`NUMBER` 使用**无损十进制编码**；向量使用**明确二进制格式**或受限数组。

#### 规格

**本域不改写编码——照 `CONV` §5 引用** ✗✓：

| 类型 | 编码 | 出处 |
| --- | --- | --- |
| `NUMBER`（含全部数值类型） | 十进制文本，保留声明精度与标度；**不得经二进制浮点中转** | `CONV` §5.1 |
| 向量 | `FLOAT32` 小端、连续数组、**无头部**；长度 = `dimension × 4` | `CONV` §5.2 |
| JSON | 数值同上（不得经浮点中转） | `CONV` §5.3 + `CFG` |
| 文本 / 标识符 | UTF-8；比较按码点 | `CONV` §5.4 |
| 引用值 / 句柄 | 48 位序列值（`vertex_id` / `edge_id` / `memory_id` / `asset_id`）按 6 字节整数 | `CONV` §1.2 |

**"往返无损"是验收方式**：每个类型的边界样例（NUMBER 的 38 位精度、负零；
向量的 ±0 / 最小正规数；JSON 的超长整数）**编码 → 传输 → 解码 → 再编码**必须逐字节一致 ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 向量字节数 ≠ `dimension × 4` | 拒绝（`CONV` §5.2） |
| NUMBER 精度被截断 | **验收失败**——不得静默 |

#### 验收要点

- **构造**：边界样例的往返测试（含大端平台构建——显式转换，`CONV` §5.2 的注）。
- **预期**：**往返无损**（REQ 验收原文）。

### REQ-API-007　expected_revision CAS（**撤销**，2026-10-04）

**优先级**：必须（原）　**阶段**：P5　**追溯**：总体方案 §15

#### 撤销说明

`expected_revision` 字段**撤回**；并发冲突由**事务机制**承担：

- 同一行的并发写由**行级排他锁串行化**（RC，`TXN` REQ-TXN-001）——语义是**等待 + 末位胜**，不是"冲突被拒绝"；

- 原"记忆、配置与检查点使用 CAS"的三处随之撤回。

### REQ-API-008　批量事务限制

**优先级**：必须　**阶段**：P5　**追溯**：总体方案 §15

#### 语义

**批量事务限制行数、字节与时长**。

#### 规格

**批 = 一次请求内的语句序列（单事务）或单语句的大影响面**——两者都受同一组上限：

| 上限 | 建议初始值（**P0 冻结项**，工作区级可配） |
| --- | --- |
| **行数** | 单请求影响行数 ≤ **10 000** |
| **字节** | 单请求体 ≤ **8 MiB**（不含资产流——资产有各自配额） |
| **时长** | 单请求执行 ≤ **30 秒**（调用方 deadline 更小时取小） |

**超限 = 稳定错误**（资源拒绝类，`retry_after_ms` 无效——等待无意义，
须**分批**）✗✓；**不得静默截断批**（与 `REQ-GRP-009` 同一条纪律）✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 批中途第 k 条失败 | 整个事务回滚（一个批一个事务）；错误报告失败语句序号 ✓ |
| 超限 | 资源拒绝类，明确指向哪一项 |

#### 验收要点

- **构造**：行数 / 字节 / 时长各自越界；批中途失败。
- **预期**：**超限返回稳定错误**；回滚无残留（与 `TXN` 的回滚验收同款）。

### REQ-API-009　分页游标

**优先级**：必须　**阶段**：P5　**追溯**：总体方案 §15

#### 语义

分页游标**绑定工作区、查询与有效期**，**不允许他人复用**。

#### 规格

- 游标 = **服务端签发的不透明令牌**（客户端不得构造、不得解读）✗✓；
- 服务端绑定三件套：**{工作区, 查询指纹, 签发时刻 + 有效期}**——
  校验任一不符 → 拒绝；
- **拒绝必须与"无效游标"不可区分** ✗✓——否则一次校验错误就是一次跨区探测
  （REQ-ISO-006 的纪律延伸到游标 ✓）；
- **有效期**：建议初始 **5 分钟**（可配，**P0 冻结项**）；**会话关闭立即失效**；
- 游标是**服务端状态**：引擎重启即失效（分页是短命对象，不值得持久化）✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 别的会话用我的游标 | 拒绝——**响应与垃圾令牌相同** |
| 过期 | 拒绝（同上一行，不可区分） |
| 同一游标并发使用两次 | 拒绝（游标**一次性推进**：一次消费后签发新游标）✓ |

#### 验收要点

- **构造**：跨会话复用、过期复用、并发复用、伪造令牌。
- **预期**：**全部拒绝且响应不可区分**（REQ 验收"跨用户复用被拒绝"）。

### REQ-API-010　长工具执行不保持写事务

**优先级**：必须　**阶段**：P5　**追溯**：总体方案 §15

#### 语义

**长时间工具执行期间不得保持数据库写事务**。

#### 规格

**在接口设计上实现"不提供"** ✗✓（与"不提供入口"同一手法）：

| 层 | 规定 |
| --- | --- |
| **协议** | **没有"挂起事务等外部事件"的原语**——每条命令要么在 deadline 内完成、要么被取消；事务**不能跨会话空闲存活**等一个工具回来 |
| **模式** | 长任务的正确形态 = **短事务三段**：写检查点并提交（`task_checkpoint`，`MEM`）→ 执行工具（**事务已结束**）→ 新事务写回结果 ✓ |
| **兜底** | 会话的活动事务有**空闲超时**（建议初始 **60 秒**，可配——归 `TXN` / `NFR` 定稿）；超时 → 回滚 + `txn_status = aborted`，调用方按"已中止事务"类处理 ✓ |

**为什么兜底是必要的**：协议不提供挂起原语，但客户端可以"自己不发下一条命令"——
空闲超时把这扇被动的门也关上 ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 工具跑 10 分钟后回来继续用旧事务 | **不可能**——事务要么没开，要么已超时回滚 |
| 客户端显式想要长事务 | 协议允许**活跃**长事务（持续发命令）；不允许**空闲**长事务 ✓ |

#### 验收要点

- **构造**：模拟"工具执行"期间不发言 10 分钟。
- **预期**：事务被超时回滚（可判定）；恢复路径（检查点）可继续。

### REQ-API-011　租约与 fencing（条件性契约）

**优先级**：应当　**阶段**：P5　**追溯**：总体方案 §15

#### 语义

任务调度**若提供**租约，必须包含 `expires_at` 与单调 `fencing_token`；
**过期工作者不得覆盖新检查点**。

#### 规格

**V1.0 不提供任务租约** ✗✓——提取进程是"每工作区一个"（`MEM` §11.7），
没有多工作者竞争，租约解决的是**不存在的问题** ✓。
但**契约先行固定**（将来提供多工作者 / 远程工作者时不再重新设计）：

| 字段 | 规则 |
| --- | --- |
| `expires_at` | **墙上时间**；到点租约自动失效，不依赖持有者主动释放 |
| `fencing_token` | **单调递增**；每次租约授予 +1 |
| **写入校验** | 工作者写检查点时携带 token；**引擎拒绝任何 token 小于当前值的写入** ✓✓——过期工作者即使活着也覆盖不了新检查点 |

**fencing 的落点**：检查点对象上记最近接受的 token（一个整数列）——
**校验在写入路径上，一次整数比较** ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 过期工作者写入 | 拒绝（可判定）；它的结果**丢弃** |
| 无租约的 V1.0 | 不存在这条路径（不提供） |

#### 验收要点

- **构造**（在将来提供租约时）：租约过期 → 新工作者接管 → 旧工作者醒来写入。
- **预期**：旧写入被拒；新检查点不被覆盖。

### REQ-API-012　四类错误与自动重试纪律

**优先级**：必须　**阶段**：P5　**追溯**：总体方案 §15

#### 语义

SDK 明确区分**可重试冲突、资源拒绝、已中止事务与提交结果未知**；
**自动重试只用于"重试值安全"的情形**（只读；或经对账确认"未提交"的重发）。

#### 规格

**判定表见 §0.4**（字段组合，不做字符串匹配）。SDK 的**自动重试白名单**：

| 操作 | 自动重试 |
| --- | --- |
| 只读语句 / 检索 | ✅（可重试冲突类） |
| 对账确认"未提交"后的重发 | ✅（重发安全——REQ-API-014） |
| 已中止事务 | ❌——必须**新开事务**重来 |
| **提交结果未知** | ❌——**先对账（`sync` / `status`），按终态决定**（REQ-API-014）；不得盲重试 ✓✓ |
| 资源拒绝 | ❌ 自动；按 `retry_after_ms` 由调用方决定 |

**判据是"重试值不安全否"，不是错误类别** ✗✓——
一个可重试冲突错误，落在只读上就重试、落在未对账的写上就不重试（先对账）。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| SDK 自动重发了未对账的写 | **实现缺陷**（验收判据） |
| 调用方想强制重试 | 显式 API 参数（自担风险，文档写明） |

#### 验收要点

- **构造**：故障注入制造四类错误；审计 SDK 的重试日志。
- **预期**：**四类可区分**；**零次**未对账写的自动重发。

### REQ-API-013　MCP 适配层：身份与工具白名单

**优先级**：必须　**阶段**：P5　**追溯**：总体方案 §15

#### 语义

MCP 传入参数**不能覆写工作区身份**；工具清单**不暴露跨用户管理函数**。

#### 规格

| 规则 | |
| --- | --- |
| **身份来源** | MCP 服务器**启动配置**里绑定的主体与工作区（§0.2 铁律）——不来自工具参数 |
| **参数覆写尝试** | 工具参数中不认识的字段（含 `workspace_id` / `user` 一类）→ **拒绝** ✓✓（选拒绝而非忽略：静默忽略会让调用方以为覆写生效了） |
| **工具白名单** | 枚举式：§0.5 命令族中**对普通主体开放的部分**——**不含** `CREATE / ALTER / DROP WORKSPACE`、不含跨用户查询、不含 `public` 的写（`ISO` REQ-ISO-003、`OPS` REQ-OPS-001 的同一约束）✓ |
| 工具粒度 | 一个工具 = 一个命令族动作（不做"万能 execute"——**白名单要能被审计**，`ISO` §13.6 同款理由）✓ |

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 工具参数带 `workspace_id` | **拒绝**（未知参数） |
| 清单里出现管理函数 | 验收失败 |
| 两个 MCP 会话交错调用 | 各自独立（会话内串行，§0.3） |

#### 验收要点

- **构造**：参数注入身份字段；枚举工具清单对照 §0.5 与 `ISO` 的禁止清单。
- **预期**：**身份参数被拒绝**（REQ 验收原文）；工具清单**零管理函数**。

### REQ-API-014　请求确认与对账（ACK / `sync` / `status`）

**优先级**：必须　**阶段**：P5　**追溯**：总体方案 §15；承 REQ-TXN-011（**取代已撤销的 REQ-API-006 / 007 的消歧职能**）

#### 语义

服务端为**每个请求**给出确定终态；连接中断后，客户端通过**对账**判定未确认请求的终态，据此决定是否重发——"提交结果未知"的**唯一消歧途径**（REQ-TXN-011），"不盲目重试"纪律的实现基础。

**参照**（证据包 `doc/evidence/request-ack-20261004/`）：

- **PG `pg_xact_status`（原 `txid_status`）**：按事务号查提交状态——`committed` / `aborted` / `in progress` / `NULL`；
  官方场景即"连接在 COMMIT 期间断开"；状态在提交日志（CLOG / `pg_xact`）里、随清理截断，**"太旧 → NULL"** ✓。
- **PgQ（SkyTools）**：确认驱动投递（处理完成才 ACK、未确认会重投）；**"工作与确认同事务"**
  （`finish_batch` 与业务同事务提交）；未确认窗口按确认序号裁剪；失败即回滚重投。

#### 规格

- **请求序号**：会话内**单调递增**，服务端分配、回执必带；客户端维护"连续收到回执的最高序号"（**已确认序号**）。
  `request_id` 保留作追踪与取消关联——**不作对账键**（协议序号不复用，无需指纹）✓。
- **终态**（对账可见，穷举四值）：

  | 终态 | 含义 | 客户端动作 |
  | --- | --- | --- |
  | **已提交** | 事务已提交（带提交序号） | 视为成功，不重发 |
  | **未提交** | 已中止 / 未执行 / 已回滚——**可安全重发** | 可重发（新序号 = 新请求） |
  | **在途** | 尚未到达终态 | 稍后重问 |
  | **不可判定** | 超出判定窗口 | 转业务自查（自然键 / 查询）✓ |

- **单点查询 `status {request_id 或提交序号}`**：PG `pg_xact_status` 样板（返回同一组终态）。
- **重连对账 `sync {原会话引用, 已确认序号}`**：返回已确认序号之后各请求的终态（窗口内带结果回放）。
- **持久化与窗口**：终态记录**随提交路径持久化**（提交记录携带请求标签——PgQ"工作与确认同事务"的对应物；**重启后仍可对账**）；按**已确认序号 + 时间/容量上限**裁剪；超出窗口 → **不可判定**（= PG "too old → NULL"）✓。
- **断连处置**：进行中的未提交事务**中止回滚**（PgQ："失败即回滚，重投"）；**已提交不可撤销**。
- **重发规则**：仅"未提交"允许重发；**同序号重发** = 竞态兜底——返回已记录终态，**不重复执行** ✓✓。
- **结果回放**：未确认窗口内尽力回放（内存）；超窗 / 重启后只回终态——**不回结果**（与 PG 只回状态同规）。
- **范围**：写请求参与对账；**读请求不参与**（无副作用，超时直接重发）；**语义级重复**（两次不同请求 = 同一业务动作）不在本协议范围——由数据自然键自理。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 会话不存在 / 记录过旧 | **不可判定**（同 PG "too old"） |
| 同序号重发且已提交 | 返回记录终态，不重复执行 |
| 结果已超容量被截断 | 只回终态 |

#### 验收要点

- **构造**：写请求提交后立即断连（回执丢失）→ 重连 `sync` → 终态"已提交"，**不重发**；
- **构造**：请求未达服务端即断连 → `sync` → "未提交" → 重发 → 效果**恰好一次**；
- **构造**：超出判定窗口后重连 → "不可判定"（PG "too old" 同款）✓。
