## 0 模型总述

### 0.1 先把三件事分开——它们受不同东西保护

资产这个域最容易混的地方，是"文件、元数据、引用"三件事被当成一件 ✗✓。
**它们的持久性来源、事务性、维护者全都不同**：

| | ① 文件本身 | ② 元数据（`asset$`） | ③ 引用登记（`ref$` 的资产侧） |
| --- | --- | --- | --- |
| 在哪 | 工作区文件系统（库外） | 工作区内的**事务表** | 工作区内的**系统表** |
| 受谁保护 | **文件系统 + 本域的协议**（§0.3） | **redo / undo / MVCC**（照常） | 同左（随引用者事务） |
| 可变性 | **不可变**——只读、范围读、删除 | 状态机 + 描述/标签**可事务更新** | 随引用者的写事务维护 |
| 崩溃后 | 完整的在，半截的不在（rename 的原子性） | 由恢复保证（照常） | 由恢复保证（照常） |
| 谁维护 | 上传协议 / 回收任务 | 引擎 | 引擎（拦截写路径） |

**REQ-TXN-018 说的"不冒充同一原子存储"，就是①与②的分界**：
文件**永远不在**页日志的原子范围内；而"文件已持久 + 元数据已提交"这个**联合状态**
由本域的**七步协议**（REQ-AST-007）保证——**不是靠一个事务** ✗✓。

**与 Oracle BFILE 的对照**（知识库证据）：

| | Oracle BFILE | **我们** |
| --- | --- | --- |
| 行内放什么 | **locator**：目录别名 + 文件名（数百字节） | **6 字节 ID**（`ASSET_REF`，48 位序列） |
| 路径从哪来 | 先建 `DIRECTORY` 对象，路径**入库** | **由 ID 推导**（§2.9）——**不存** |
| 事务性 | **不参与事务、不可恢复**，由 OS 保证 | 同左（那是外部文件的共性）✓ |
| 可写性 | 只读 ✓ | 只读 ✓（REQ-AST-001/002） |

**取它的"只读 + 非事务"边界，不取它的"路径入库"** ✓——
`DIRECTORY` 对象正是 REQ-AST-004 要挡的"用户传入任意路径" ✗。

### 0.2 不可变性买到了什么——本域的简单性都来自它

| 因为不可变 | 于是 |
| --- | --- |
| 没有"文件的部分新版本" | **rename 的原子性 = 发布的一致性**——不需要任何文件级 MVCC |
| 内容不会变 | **校验和可长期作准**——幂等、备份清单、清理检查都靠它 |
| 位置由 ID 推导 | **"ID → 路径"不是映射，是函数**——零状态、零恢复（§2.9） |
| 登记进度 = 文件本身（名由 ID 推导） | **进度不需要存**——文件就是进度，"能推导的就不存" |

**修改 = 上传新对象 + 事务切换业务引用**（REQ-AST-002）✗✓——
"原地更新"这条路的**代价**（版本化、部分写、崩溃恢复、并发改写）
全部不必支付；代价是**空间**（旧版本要等回收）与**调用方的两步走** ✓。

### 0.3 上传协议是一台状态机，不是一个事务

```text
staging ──(校验通过 + rename + 提交)──▶ committed ──(逻辑删除)──▶ deleted ──(回收)──▶ 消失
   │
   └──(取消 / 超期清理)──▶ 消失
```

- **`staging` 行是"已提交的行"** ✗✓——因为上传是长流程（REQ-AST-006），
  **不能用一个长事务把整段上传罩住**（那会拖住 undo、锁与快照 ✗）。
  于是"暂存不可见"**靠状态过滤，不靠未提交**：
  一切对外读只认 `committed`；`staging` 行只对上传协议自身可见（按 ID 直取）。
- 状态转换各是一个**短事务**；步骤之间的崩溃由状态机兜住（REQ-AST-008）。

### 0.4 引用登记 `ref$`：表行与图元素共用一张登记表

`GRP` 域先定了 `ref$` 的图元素一侧（`GRP.md` REQ-GRP-012）；本域把它**推广到表行**——
因为**资产不只被图引用**：`memory` 的 `task_checkpoint` 存"工具结果引用"（§8.2）、
任何业务表都可以有 `ASSET_REF` 列 ✓。**登记表一张，引用者有两类**：

```text
ref$（每工作区一张系统表；引擎维护；不提供直接 DML）
  from_obj#   4B   引用者所在对象（业务表 / 图）
  from_rowid  6B   引用者行的 ROWID
  from_sub    6B   0 = 行本身（含图的顶点行）；> 0 = 边的 edge_id（边在 src 行链内）
  to_kind     1B   1 = 记忆，2 = 资产
  to_id       6B   被引用对象 ID（48 位序列值）
  ── 正向唯一键 (from_obj#, from_rowid, from_sub, to_kind, to_id)——幂等
  ── 反向索引   (to_kind, to_id) → 引用者——"谁引用了它"一次定位
```

**维护规则（全部同事务，照 `GRP.md` REQ-GRP-012）**：
写入含引用值的列 / 属性即登记；覆盖与移除即撤销；删除引用者即清空其登记；
**引用目标不存在则写入被拒绝**（"悬空引用不可产生"）。

**"什么算业务引用"的门槛与图同规** ✗✓：
**只有受管引用值**（`ASSET_REF` 列、图属性里的引用标量）；
**普通字符串里的 ID 不是引用**——删除资产不被它阻止，它自己变陈旧（那是调用方的事）✓。

### REQ-AST-001　`ASSET_REF` 与"无库内 LOB"

**优先级**：必须　**阶段**：P6　**追溯**：总体方案 §9

#### 语义

通过 `ASSET_REF` 引用工作区内受管理文件；**不提供库内 BLOB/CLOB 或原地文件更新**。

#### 规格

| | |
| --- | --- |
| `ASSET_REF` 的值 | **6 字节资产 ID**（48 位序列值，`TYP` §6.6）——不含路径、不含类型 |
| 可以出现在 | 任意业务表的列；图元素的属性（引用标量）；记忆表的工具结果引用列 |
| 指向范围 | **只能是本工作区的资产** ✗✓——跨区引用是**普通数据**（存 ID 字符串），不建受管引用（与 `REQ-GRP-011` 同一规则） |
| 库内 LOB | **没有** ——长文本走行片段链（§6.8）、大对象走资产，**两者都不经过通用压缩**（`CFG` §0.2） |
| 原地文件更新 | **没有这条路**（REQ-AST-002） |

**"没有库内 LOB"不是缺点声明，是边界的声明** ✓——
它换到的是：页格式没有 LOB 分支、备份策略不分化、redo 不搬运大块字节。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| `ASSET_REF` 指向不存在的资产 | 写入被拒（受管引用）；普通数据中的 ID 不检查 |
| 指向已删除的资产 | 读取时呈现"**已失效**"（读时判定，照 `REQ-MEM-011` 形状） |
| 试图用 `ASSET_REF` 指向别的区 | **表达不出来**——解析只在本工作区（REQ-AST-004） |

#### 验收要点

- **构造**：建一张带 `ASSET_REF` 列的表与一个引用资产的图元素。
- **预期**：两者都在 `ref$` 中可反查；普通字符串里的同一个 ID **不在**登记里。

### REQ-AST-002　已提交文件不可改写

**优先级**：必须　**阶段**：P6　**追溯**：总体方案 §9

#### 语义

已提交文件**只允许读取、范围读取与删除**；
修改内容通过**上传新对象并事务切换业务引用**完成。

#### 规格

- 打开方式：**只读**——引擎从不以可写方式打开已提交的资产文件 ✗✓；
- **范围读取**（offset, length）是一等接口——大文件的"读一段"不经过"读整个"；
- **元数据 ≠ 内容**：描述、标签**可事务更新**（方案 §9）——不可变的是**文件内容** ✓；
- **"修改"的标准路径**：`上传新资产 → 事务内把引用从旧切到新 → 旧资产解除引用后删除` ✓
  ——其中"切换引用"就是一次普通行更新 / 图属性更新，**没有专门的"替换"接口** ✗✓
  （一个接口 = 一个可能的漏判入口，白名单越短越好）。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 对已提交文件尝试写入 / 截断 | **没有接口**（不是拒绝，是不存在） |
| 更新描述 / 标签 | 正常事务 ✓（元数据行） |
| 内容需要改变 | 新对象 + 切引用（上面那条路径） |

#### 验收要点

- **构造**：上传 → 改描述 → 读内容；再"修改"内容（走新对象路径）。
- **预期**：描述更新可见；两次读到的内容分别是两个完整且各自正确的对象。

### REQ-AST-003　资产元数据

**优先级**：必须　**阶段**：P6　**追溯**：总体方案 §9

#### 语义

资产元数据包含 `asset_id`、WorkspaceId、大小、校验和、媒体类型、存储版本、
创建时间、状态与引用信息。

#### 规格

**落点：`asset$`**（每工作区一张系统表；用户只读；写入只经资产接口）：

| 字段 | 宽度 / 类型 | 说明 |
| --- | --- | --- |
| `asset_id` | 6B（48 位序列） | 主键（`CONV` §1.2） |
| `status` | 1B | **`staging` / `committed` / `deleted`** |
| `size` | 8B | `staging` 期 = **声明值**；`committed` 后 = 实际值（两者必须一致） |
| `checksum` | 32B | SHA-256；`staging` 期 = 声明值，完成时以实际字节校验 |
| `media_type` | 有界字符串（≤128B） | 仅存储与返回，**不驱动任何解析或执行**（REQ-AST-011） |
| `storage_version` | 1B | **资产存储形态的版本**，自 1 起——未来的形态迁移（分块、区内去重等）按它分派 |
| `created_at` | TIMESTAMP | 墙上时间（与 `user$`/`ws$` 的 `ctime` 同规） |
| `description` | 有界字符串 | 元数据，**可事务更新** |
| `tags` | JSON | 元数据，**可事务更新** |
| `idempotency_key` | 有界字符串（可空） | 唯一（非空时）——REQ-AST-005 |
| `expires_at` | TIMESTAMP（可空） | **有效期**：空 = **永久（默认）**；非空 = 临时的，到期后按 REQ-AST-008 / 010 清理（**需求增补**，见待讨论清单回流项 3） |
| `kind` | 1B | **0 = 实体（有文件）/ 1 = 包（虚拟，无文件）**；其余保留 |
| `super_object_id` | 6B | **所属包的 `asset_id`；0 = 无包**（含包自身——两级封顶）；非 0 时指向的必须是一个已提交的**包**（写入时校验） |
| `volume` | 1B | **资产所在卷（0–15）**——**声明时由数据库自动选定**并记入：候选 = 可用 ∧ 放得下，按**容量均衡**（选最空者；并列按 `asset_id mod 16` 打破，§2.10）。**对外不可见**——访问只凭 `asset_id`（对象存储式）；包（无文件）恒为 0 |

**`asset$` 是普通可变表**：引擎经资产接口执行 INSERT / UPDATE / DELETE——
状态迁移、`description` / `tags` 更新、回收删行都是普通事务；用户侧仍**无 DML / DDL 入口**。

**两级对象：包与实体**（**需求增补**，见待讨论清单回流项 4）：

- **包 = 虚拟资产**：**没有文件**——**不经过七步上传协议**（创建 = 单事务建行；
  `size = 0`、`checksum` 全零、`media_type` 空）；
- **两级封顶**：实体可挂一个包；**包不挂包**（包的 `super_object_id` 恒为 0）；
- **成员** = `super_object_id > 0` 的实体（按该列索引列出）；
- **成员关系可变更**：改挂 / 摘除 = 普通事务（UPDATE `super_object_id`）；
- **删除 / 回收验收**：**显式删除**有成员的包 ⇒ **拒绝**（同引用护栏的理由）；
  **到期**则照收（与普通资产同规）——包不可访问，**成员自动脱离**（清理任务把成员的
  `super_object_id` 归 0，普通事务）；
- 包可被 `ref$` 引用（照常）；但"成员关系"**不是引用**——它由 `super_object_id` 表达
  （单一真相，不重复登记）。

**实现定稿（待冻结项 59）**：

- **物理形态**：**普通堆表**（系统表）——复用页、行、索引、WAL、检查器全套，无专用结构；
- **表选项**：`transactional ✅` / `logging = full` / `update_mode = in_place` / `cleanup = none`
  （回收删行由清理任务**显式**执行，无自动清理）；`graph` 位 = 0（非图顶点表）；
- **索引组（四）**：

  | 索引 | 唯一性 | 用途 |
  | --- | --- | --- |
  | **主键 `asset_id`** | 唯一 | 按 ID 直达——对象存储式访问的唯一入口 |
  | **`idempotency_key`** | 唯一（**可空**）——非空时生效，依据"**全空的键不登记索引**"（§9.1） | 幂等（REQ-AST-005） |
  | **`status`** | 非唯一 | 清理 / 回收任务的扫描入口（`staging` / `deleted` 是少数行） |
  | **`super_object_id`** | 非唯一 | **列包成员**（"整包访问"的成员枚举） |

- **协议的其余定稿**：登记式（REQ-AST-006：内容不经数据库）、包/实体两级、到期=**访问硬拒绝**、
  分卷三条件（§2.10）、目录分层取 ID 末尾（§2.9）——回收细则见 REQ-AST-008 / 010 ✓。

**两处"看起来该有、实际不设"的字段** ✗✓（§5.2 字段准入纪律的又一次应用）：

| 不设 | 因为 |
| --- | --- |
| **WorkspaceId 列** | 每工作区一张表 → **归属由所在工作区隐含**（ISO 隔离保证不混放）；对外元数据**返回时带上** WorkspaceId ✓ |
| **引用计数 / 引用清单列** | 那是**第二真相源** ✗——引用信息的权威是 `ref$`；元数据接口的"引用信息"**由反查登记给出**（计数 + 有界枚举）✓ |

**"引用信息"的对外形状**：查询元数据时可选返回
`{引用数, 引用者举例（有界）}`——**全部来自 `ref$` 的反向索引**，不扫描任何表 ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 未完成上传的资产被元数据接口查询 | **不存在**（`staging` 不可见——一切对外读只认 `committed`） |
| 已删除资产的元数据 | 对**新快照**不可见；对**删除前的旧快照**仍可见（MVCC 照常 ✓） |
| **到期资产的访问** | **拒绝**——内容与元数据都视同不存在（**不提供"能下载但标记失效"的软态**）✓；引用它的图属性 / 表列**读到时**呈"引用已失效"标记（不因此报错——那是引用处的读时判定，`REQ-MEM-011` 形状） |

#### 验收要点

- **构造**：上传后查元数据；逐个字段比对；再查引用信息。
- **预期**：字段完整；引用信息与 `ref$` 反查一致。

### REQ-AST-004　路径由服务端生成

**优先级**：必须　**阶段**：P6　**追溯**：总体方案 §9

#### 语义

用户**不得传入任意服务器路径**；对象位置由服务端生成。

#### 规格

**这条要求在本设计里是"表达不出来"，不是"被拒绝"** ✓✓（与 `REQ-ISO-005` 同一修辞）：

| 防线 | 内容 |
| --- | --- |
| **接口里没有路径参数** | 登记 / 读取 / 删除只收 `asset_id` 与声明（size / checksum）——**没有地方可以传路径**，也没有"网络地址"这个形态 ✗✓ |
| **路径是函数**：`path = f(asset_id)` | `<卷>/<根>/assets/<v>/<s1>/<s2>/<s3>/<asset_id>`（§2.9）——ID 是服务端生成的 16 进制定长串，**不可能穿越目录** |
| **不设 `DIRECTORY` 类对象** | 没有"先声明一个目录别名"这一步（BFILE 的进路）——用户连"命名一个位置"的能力都没有 ✓ |
| **staging 位置同样推导** | `staging/<asset_id>`——**同一个 ID，同一个名字**（调用方据此直写，§2.9）✓ |

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 请求里夹带路径类参数 | **参数不存在**——解析期报未知参数 |
| 资产 ID 含非法字符 | **不可能**——ID 是服务端生成的十六进制 |

#### 验收要点

- **构造**：穷举资产接口的全部参数清单；尝试各种路径注入载荷。
- **预期**：**零匹配**——没有参数能影响文件位置。

### REQ-AST-005　幂等键

**优先级**：必须　**阶段**：P6　**追溯**：总体方案 §9

#### 语义

创建操作以 `idempotency_key` 识别重试；**相同键不同内容必须拒绝**。

#### 规格

**"声明"先行** ✗✓——协议第 ⓪ 步就要求 `(size, checksum)` 的**声明值**
（size 是配额预留的依据；checksum 是幂等与完整性的锚）：

| 情形 | 行为 |
| --- | --- |
| **同键 + 声明一致** | 视为同一逻辑上传——返回**同一个 `asset_id`**；未完成的重放登记 ✓ |
| **同键 + 声明不一致** | **立即拒绝**（不是等收完字节）——"重试"与"新对象"是两件事 ✓ |
| 同键 + 首次已完成 + 实际校验和一致 | 返回**已提交的那个** `asset_id` ✓（"重试最多产生一个逻辑结果"） |
| 同键 + 首次已完成 + 实际校验和不同 | **拒绝**——声明骗不过最终校验 ✓ |

**幂等性由唯一键保证**（`asset$` 的 `idempotency_key` 唯一索引）——
并发同键的建行竞争由唯一约束裁决：**一个成功、另一个转入"加入既有的这次上传"** ✓。

**同键并发重试的交错**：不做复杂互斥 ✗✓——内容由**调用方**在暂存位置写入，
**登记以校验和裁决**：交错若产生了不同字节，登记校验会检出并拒绝 ✓
（低并发画像下，这是"用已有的正确性检查兜住，不加新机制"的选择——REQ-AST-006 的同一纪律）。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 键超长 / 非法字符 | 拒绝（`CONV` §1.2：服务端校验长度与字符集） |
| 同键不同声明 | 拒绝（资源/冲突类错误，按 `CONV` 错误模型） |
| 无键的上传 | 允许——每次都是新对象（键是**可选**的幂等设施） |

#### 验收要点

- **构造**：同键重试（声明一致 / 不一致）；并发同键；完成后改内容重试。
- **预期**：**一个逻辑结果**；异声明与异内容全部被拒。

### REQ-AST-006　内容不经数据库（登记式）

**优先级**：必须　**阶段**：P6　**追溯**：总体方案 §9

#### 语义

资产内容**不经过数据库**：调用方先把文件放到**服务端本机的暂存位置**（路径由 ID 推导，§2.9），
登记接口只做**校验与发布**；**不允许网络地址（URL）形态**——没有"由库去某处取文件"这回事。

#### 规格

| 要求 | 落地 |
| --- | --- |
| 引擎不接收字节 | 内容搬运是**文件系统操作**（`rename`）——**不走数据库缓冲区**，"块大小"不适用 ✓ |
| 校验防灌爆 | 校验时**文件长度必须等于声明大小**（不符即失败） |
| 中断恢复 | 进度 = 文件本身（**调用方**在自己填写的暂存位置上管理）；登记**幂等可重放** ✓ |
| 恢复的入口 | 同 `(idempotency_key)` 找回 `staging` 行；或按 `asset_id` 直取 ✓ |
| 服务端不缓存 | 引擎不在内存保留内容副本——校验是**流式读取**（不经数据库缓冲区）✓ |

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 写入超过声明大小 | **立即拒绝**（并保留已收部分，等待调用方修正或取消） |
| 改声明重传 | 声明不可改 → 视作**不一致**（REQ-AST-005） |
| 长时间未登记 | 由**调用方**处理（文件在其暂存位置）；被放弃的取消或清理见 REQ-AST-008（**无宽限期概念**） |

#### 验收要点

- **构造**：调用方在暂存位置写入文件（含中途放弃）；登记重放；声明与实际不符。
- **预期**：引擎不因文件大小分配内存；登记幂等；**校验以实际字节仲裁**。

### REQ-AST-007　上传流程（七步）

**优先级**：必须　**阶段**：P6　**追溯**：总体方案 §9

#### 语义

上传流程为：**预留额度 → 填入 staging（调用方直写）→ 校验大小与校验和 → 同步内容 →
原子移动 → 同步目录 → 提交可见元数据**；
逐点中断后**无"已提交引用指向未持久化文件"**。

#### 规格

```text
⓪ 校验请求：声明 (size, checksum, media_type)；幂等键查重（REQ-AST-005）
① 预留额度：事务 —— 建 staging 行 + 记预留；提交
     ——"预留先于收字节"：否则超额的字节已经落盘
② 填入 staging：调用方把文件放至 staging/<asset_id>（**本机文件系统直写，不经数据库**）
③ 校验：实际 (size, checksum) 与声明比对——不符即失败路径
④ 同步内容：fsync(staging 文件)——★ 内容先于名字持久
⑤ 原子移动：rename 到 assets/<v>/<s1>/<s2>/<s3>/<asset_id>
     ——rename 原子 ⇒ 目标位置"要么没有，要么完整"（§2.9）
⑥ 同步目录：fsync(目标目录)——★ 名字先于元数据持久
⑦ 提交可见元数据：事务 —— status: staging → committed；预留转已用；提交
```

**两个 ★ 是"无已提交引用指向未持久化文件"的全部证明** ✗✓：

- **④ 在 ⑤ 之前**：名字出现时，内容已经在盘上；
- **⑥ 在 ⑦ 之前**：元数据"已提交"时，名字已经可以在崩溃后找回。

**每步中断的语义**（验收表）：

| 中断点 | 崩溃后可见 | 状态 | 恢复路径 |
| --- | --- | --- | --- |
| ① 之前 | 无痕 | — | 重传 |
| ①–② 之间 | 无文件 + `staging` 行 | 无任何对外痕迹 ✓ | 填入暂存后重放登记 / 取消清理 |
| ②–④ 之间 | 未完成的暂存文件 | 同上 | 调用方补全后重放登记 / 取消清理 |
| ④–⑤ 之间 | 完整 staging 文件 | 同上 | 重放登记（重做 ⑤）/ 取消清理 |
| ⑤–⑦ 之间 | **完整文件在最终位置** + `staging` 行 | 同上（**不可见**）✓ | **完成路径幂等**：校验和相符 → 直接补 ⑦ |
| ⑦ 提交后 | 完整 | `committed` ✓ | — |

**完成路径的幂等**：⑤ 之前若最终位置**已有**同校验和的文件，
跳过 ②–⑥ 直接 ⑦ ✓——覆盖"崩在 ⑤ 与 ⑦ 之间"的重放。

**"具体文件系统假设"**（rename 原子性、目录 fsync 的语义）**在 P0 验证**
（方案 §9 明文）——协议在此前提下成立；验证结果回写本域与 §2.9。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| ③ 校验不符 | 失败路径：保留 staging 行等待**显式取消**或清理——**不自动删**（给调用方一次修正 / 重放的机会）✓ |
| ④ / ⑥ 的 fsync 失败 | **上传失败**——宁可失败，不可"以为持久了" |
| ① 预留失败（超额） | 明确错误：**"可调额后重试"**（§3.3 的报错路径）✗✓ |

#### 验收要点

- **构造**：在 ① ～ ⑦ **每两个步骤之间**注入崩溃；磁盘满；网络重试。
- **预期**：**任何中断点都不存在"已提交状态 + 未持久化文件"**；重放后要么不可见、要么完整 ✓。

### REQ-AST-008　孤立对象与清理

**优先级**：应当　**阶段**：P6　**追溯**：总体方案 §9

#### 语义

进程中断后未提交文件可成为孤立对象，由后台**按状态**清理；
清理任务**幂等**，识别孤立文件与重复任务。

#### 规格

**孤立对象有三类，各有判据**（不靠猜测 ✗✓）：

| 类 | 判据 | 处理 |
| --- | --- | --- |
| **被取消的 `staging` 行**（文件可有可无） | 行被显式取消（或调用方放弃） | 删 staging 文件（不存在则跳过）+ 释放预留 + 删行 |
| **无行的 staging 文件** | 目录扫描发现、且无对应 `staging` 行 | 删文件——**行先于文件**（①在②前），无行的文件必是残迹 ✓ |
| **`deleted` 待回收** | 见 REQ-AST-010 的三条 | 见该条 |
| **到期的临时资产** | `expires_at` 已过且行仍为 `committed` | **到期即失效（硬）**：**内容与元数据的访问一律拒绝**（视同不存在，读路径按当前时间直接判定）；随后由清理任务转入 `deleted` 并按其三条回收——**不设引用护栏、不等待、不阻塞**（到期 = 创建者当初设的合同，用户决策 2026-10-04）✓ |

**为什么没有"宽限期"**：资产内容是**登记式**的（REQ-AST-006）——文件由调用方在**本机暂存位置**
自行管理，登记接口只做校验与发布；**不存在"与续传赛跑"的窗口**，也就不需要宽限期。
**判据只看状态机**：残迹 = 无行的文件、或已被取消的行 ✓（能推导的就不存）。

**清理任务的形态**：**实例级、数个 worker、按工作区分片**（一个实例的清理由固定几个 worker 轮流分片，**不需要每工作区一个**）；节拍 **1 小时一轮**、**单轮处理上限 1000 条**——频率刻意压低：清理是后台杂务，不是热路径，太频繁会影响性能 ✓。

**幂等由"能推导的就不存"保证**：清理动作全部可重入——
"文件不存在"不是错误、"行已消失"不是错误、"预留已释放"不是错误 ✓。
**另设一份"清理日志"反而会成为第二真相源** ✗——
**状态机本身即日志**（行在 = 未清完；行不在 = 清完）。

**与登记的互斥**：清理与登记（含取消）按**同一把（按资产的）内存锁**互斥；
清理只看**状态机**（行存在与否）——**不会碰到调用方正在填写的文件**（它的行还在）✓。

**重复任务识别**：同一轮清理发现同一对象两次（如两个线程）——
幂等动作 + 内存锁，重复执行无副作用 ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 清理时文件不存在 | **跳过**（正常路径之一） |
| 清理时行已被删 | 同上 ✓ |
| 清理与完成的竞争 | 完成先拿锁 → 清理看到 `committed` 即放弃 ✓ |

#### 验收要点

- **构造**：制造三类孤立对象；并发跑两次清理；清理中途 kill 再跑。
- **预期**：**幂等**——重复执行结果一致、无报错；正在登记的对象不被误删。

### REQ-AST-009　删除：先标记，引用是护栏

**优先级**：必须　**阶段**：P6　**追溯**：总体方案 §9

#### 语义

删除**先在事务中标记不可见**；**有业务引用时默认拒绝删除**。

#### 规格

```text
删除 = 一个事务：
  ① 反查 ref$ 的 (to_kind=asset, to_id) —— 有引用？→ 拒绝（默认）
  ② status: committed → deleted；提交
  文件不动——回收是异步的（REQ-AST-010）
```

**"默认拒绝"的默认在哪里解除** ✗✓：**没有"强制删除"**——
解除引用在**调用方**：它是普通的数据修改（改引用列 / 删引用行），
改完再来删 ✓。**库不提供"顺手把引用也删了"的参数**——
"删了、顺带把别人的引用也清了"会让丢失变得不可见 ✗。

**拒绝的判据是受管引用（`ref$`）**——**不扫描任何业务表** ✓（REQ-AST-012 的同一纪律）。
普通数据里的 ID **不阻止删除**（REQ-AST-001 的边界）✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 有受管引用 | **拒绝**，错误里给出**引用者数量**（有界枚举接口） |
| 已 deleted 再删 | 幂等——仍返回"已删除"状态 ✓ |
| 删除 staging 中的对象 | 走**取消**（REQ-AST-008），不是删除 |

#### 验收要点

- **构造**：A 表与 B 图元素各引用资产；直接删 → 拒绝；解除其一 → 仍拒绝；全解除 → 成功。
- **预期**：拒绝与放行的判据**只来自 `ref$`**。

### REQ-AST-010　回收等待快照与租约

**优先级**：必须　**阶段**：P6　**追溯**：总体方案 §9

#### 语义

文件回收须**等待旧快照与活动读取租约结束**；
删除前**备份快照所需文件保留到清单完成**。

#### 规格

**回收 = `deleted`（含**到期的临时资产**——到期视同"待回收"）且满足三条**（一条不多、一条不少）：

| # | 条件 | 为什么 |
| --- | --- | --- |
| 1 | **该删除版本对所有活跃快照可见**——删除的提交序号 < 最老活跃快照（§12.7） | 旧快照仍能看到"已提交"的元数据行 → 它有权读文件 ✓ |
| 2 | **无活动读取租约** | 读者可能已经打开了文件（比快照更早的动作） |
| 3 | **无进行中的备份需要它** | 备份 = **一类租约持有者**——它复制/校验期间持租约，**到清单完成才释放** ✓ |

**第 3 条并入租约机制** ✗✓——不新设"备份保留"这条平行规则：
**备份就是读取者**，只是持有时间长（到清单完成）✓。

**读取租约**：

| | |
| --- | --- |
| 登记 | 打开资产流**之前**——按 `(工作区, asset_id)` 计数（内存） |
| 释放 | 流关闭时；**进程崩溃即消失**——方向安全（读没了，租约也该没）✓ |
| 与来源的关系 | 走"标准接口"的跨区读取同样登记（在**资产的家乡**登记）✓ |

**读者与回收的竞态**（"检查存在"与"登记租约"之间被 unlink）：

```text
读者：取按资产的锁 → 登记租约 → 检查状态 → 打开文件 → 放锁
回收：取同一把锁 → 验三条     → unlink    → 放锁
```

**同一把按资产的锁**使"检查 + 动作"成为临界区 ✓——
这是本域唯一需要新加的并发原语，且只在资产生命周期动作上用（热路径上没有）✓。

**回收动作**：`unlink → fsync 目录 → 事务内删除元数据行`——**可重入**：
文件不在则跳过；行不在则完成 ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 长快照长期不释放 | **回收等待**——空间占用是可预期、可解释的（与 undo 保留同一形状）✓ |
| 回收中途崩溃 | 重放：unlink 幂等、行删除是事务 ✓ |
| 备份失败 | 租约释放（失败也是有终点的）✓ |

#### 验收要点

- **构造**：旧快照下读资产 → 删除 → 验证文件仍在、旧快照仍能读；快照结束 → 文件消失。
- **预期**：**长读期间文件不被提前回收**；回收后新快照读=不存在、旧引用呈"已失效"。

### REQ-AST-011　无执行路径

**优先级**：必须　**阶段**：P6　**追溯**：总体方案 §9

#### 语义

存储算法包**不授予执行权限**；数据库**不调用模型、不加载用户共享库、不执行上传脚本**。

#### 规格

**逐项对照，每一项都要能回答"为什么做不到"** ✗✓：

| 禁令 | 为什么做不到 |
| --- | --- |
| 执行上传物 | 资产**只有读取接口**——字节从文件流到调用方，**没有任何路径把它交给执行器** |
| 加载用户共享库 | **没有 `dlopen` 类接口**；引擎的可加载模块是编译期内建的，与工作区数据无关 |
| 调用模型 | 引擎核心**没有模型调用路径**；唯一的模型调用者是**可选的提取进程**（`MEM` §11.7），它的对象是**会话与记忆内容**，且它是**独立进程、走普通读取接口**——资产对它也只是**被读的字节** ✓ |
| 执行上传脚本 | 同上——"脚本"在库里只是文件 ✓ |
| 按媒体类型解析 | `media_type` **仅存储与返回**，不驱动任何分派 ✓ |

**边界说透**：**"能读"与"能执行"是两件事**——
提取进程把某段内容发给 LLM 是**它的策略**（`MEM` 域契约），
不改变"资产不被执行"这条：**库从未把文件当作程序** ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 上传可执行文件 | 正常对象——它只是字节 ✓ |
| 请求"运行这个资产" | **没有接口** |

#### 验收要点

- **构造**：上传各类可执行/脚本内容；穷举资产接口清单。
- **预期**：**零执行路径**——接口清单里没有任何"调用/运行/加载"。

### REQ-AST-012　不做去重

**优先级**：必须　**阶段**：P6　**追溯**：总体方案 §4、§9

#### 语义

不做跨用户文件去重；**校验和相同仍独立归属、配额、存在性检查与删除**。

#### 规格

**本域的选择比要求更严一格**：**不做任何去重**（跨工作区不做，**工作区内也不做**）✗✓：

| 范围 | 做不做 | 理由 |
| --- | --- | --- |
| 跨工作区 | **不做**（REQ-ISO-011：物理共享 → 可检测的共享 → 隔离被绕过） | 见 `ISO.md` |
| 工作区内 | **也不做** | 去重会把"删除"从"一个对象的事"变成"引用计数的事"✗——**删除、配额、回收全都要重新定义**；收益（同一用户重复上传）不抵这个复杂度 ✓ |

**于是每个资产的四件事全部独立**：**存储、配额、存在性、删除** ✓——
校验和只是**完整性**与**幂等**的锚，**不是**共享的依据 ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 同一工作区两次上传相同字节（无幂等键） | **两个资产、两个文件、两份配额** ✓ |
| 期望"第二次秒传" | **不提供**——API 契约里没有"可能已存在"这种模糊返回 ✓ |

#### 验收要点

- **构造**：跨工作区与工作区内各上传字节相同的资产。
- **预期**：占用各自增加；删除互不影响；无任何共享路径。
