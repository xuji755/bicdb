## 0 模型总述

### 0.1 先定边界：`derived_link` 与 GRP 的图**不是同一张图**

`MEM` 域留了一个挂起的问题（`MEM.md` §0.4）：记忆之间的关系（`derived_link`）
与 GRP 的图表是不是同一张图 ✗✓。**本域的回答是：不是，两者并存。**

| | **`derived_link`**（`MEM` 域） | **GRP 的图** |
| --- | --- | --- |
| 是什么 | **记忆之间的关系 + 派生成链** | agent 撰写的**实体 / 内容 / 拓扑图** |
| 写者 | 库（`derived_from`）+ agent（`conflicts_with` / `supersedes`） | agent（图语言） |
| 完整性要求 | **必须完备**——撤销传播靠它反查（REQ-MEM-013） | **内容**——可以很大、可以有界截断 |
| 预算 / 截断 | **不适用**——反查必须完整 ✅ | **适用**（REQ-GRP-008 / 009） |
| 存储 | 普通表 + 正反索引（`MEM` 域） | **邻接段**（按 `src` 聚簇，§9.2）+ 覆盖索引 |
| 语言 | 不进图语言（按关系查询） | 图语言子集（REQ-GRP-004） |
| 生命周期 | 与记忆对象同事务 | 与图元素同事务（REQ-GRP-010） |

**为什么不能合一** ✗：两者对同一条结构提出**互相矛盾**的要求——
`derived_link` 要求"**永远能完整反查**"（漏一个派生物 = 撤销静默失败），
而图要求"**可以有界**"（REQ-GRP-008/009 明文允许截断）。
**一个结构不能同时承担这两个要求** ✓——合一会让"截断预算"渗进撤销路径 ✗，
或让"撤销的完备性"变成图遍历的一个特例 ✗✓。

**两处相接（本域定义的接缝）**：

| 接缝 | 内容 | 落点 |
| --- | --- | --- |
| **① 受管引用登记** | 图元素属性引用记忆 / 资产 ⇒ 登记，供**定向反查**（删除传播不扫 JSON） | REQ-GRP-012 |
| **② 检索图扩展** | `REQ-RET-009` 的"沿边扩展"沿**命名图**走；入口由登记桥接（候选记忆 → 引用它的顶点 → …） | REQ-GRP-005、`RET.md` |

> **一句话记法**：**`derived_link` 是记忆的"户籍"（完备、系统关心），
> 图是 agent 的"地图"（内容、agent 关心）。**

### 0.2 图的形状：一个命名对象 + 一组伴随对象

**每工作区可以有多个命名图**（REQ-GRP-001）。一个图在字典上**不是一种新对象** ✗✓——
它就是**一张表（顶点）+ 它的伴随存储/索引**，因此完整复用既有机制
（`obj$` / `seg$` 登记、区分配、WAL、恢复、`Move`、名字解析）✓：

```text
图 g（工作区内的一个命名对象）
├── 顶点表 g          堆表（表选项 = 「图数据」，§8.2 #4）
│     每行 = vertex_id 6B │ label │ 属性（JSON）
│     索引：顶点 id 唯一索引（B+Tree）
│           [可选] 属性索引（B+Tree，REQ-GRP-002 的"选定属性"）
├── 出边段 g$out      邻接段（seg_type = 3，页类型 = 5）—— 边的家
│     条目按 (src, edge_id) 聚簇；label 与属性内联；单向跨页链（§9.2、§5.11）
├── 出边入口索引 g$o  B+Tree：(src ROWID) → 首邻接页
└── 入边覆盖索引 g$i  B+Tree：(dst ROWID) → (src, edge_id, label)
                        ——"谁指向我、是什么关系"不用回表（§9.2）
```

**顶点是行，边是条目** ✗✓——这是本域最重要的一句形状描述：

| | 顶点 | 边 |
| --- | --- | --- |
| 存在形态 | **堆表里的行** | **邻接段里的条目**（索引组织，无独立堆表） |
| 内部定位 | ROWID（行迁移经转发指针保持稳定，§6.2） | `(src ROWID, edge_id)` |
| 对外标识 | `vertex_id`（48 位序列） | `edge_id`（48 位序列） |
| 关系读 | 直接 `SELECT`（只读） | 经图查询的**表值接口**（REQ-GRP-007） |
| 关系写 | **不提供**（写入只经图语言，入口可枚举） | 同左 |

**与"堆表 + B+Tree"字面表述的差异**（REQ-GRP-002 的文字）✗✓：
顶点、入边、属性索引都照字面；**出边不是"堆表的行 + 索引"**，
而是**索引组织**（边数据内联在邻接段里）。这是存储架构 §9.2 已冻结的选择——
买的是"**一跳出边遍历 = 一次范围读**，而不是 N 次随机 I/O"✓，
而图扩展在检索热路径上（`REQ-RET-009`），这一条是硬的 ✓。
**该差异作为一行文字的回流项记入待确认汇总**（需求 v0.2 时改措辞，验收判据"悬空边不可产生"不变）。

### 0.3 三条参照，各取一样（REQ-GRP-014）

| 参照 | **取什么** | **不取什么** |
| --- | --- | --- |
| **Apache AGE** | **语言面**：openCypher 子集（标签 + 属性图 + `MATCH` 一族）与"图是原生存储"的定位 | **插件形态**（我们不宣称能加载 AGE）；`agtype` 类型；继承式标签表；PG 元组复用 |
| **DuckPGQ / SQL/PGQ** | **表值接口的形状**：图查询产出类型化行集，与 SQL 在同一引擎内结合、不跨系统搬数据 | "图 = 既有关系表上的声明式视图"的模型——**我们的图元素是原生对象**，不是对用户表的映射 |
| **pgGraph / pgvector 的 CSR 局部性** | **聚簇邻接**的组织方式（一跳 = 一次范围读） | "拓扑是派生索引、可整批重建"的定位——我们的邻接段是**边的权威之家**，不是副本 |

**执行节点全部自研**：解析、匹配、扩展、预算记账都是我们自己的算子——
不复用 AGE 的 PG 元组机制，也不依赖任何插件装载 ✓（REQ-GRP-014 的"不宣称"落在此）。

### 0.4 标识：一个边标识，两个角色

| 标识 | 宽度 | 谁的 | 用途 |
| --- | --- | --- | --- |
| **`vertex_id`** | 48 位（6B） | **序列**产生（`CONV` §1.2：每工作区一条） | 顶点的对外标识；`id(v)` 的返回值；图语言的句柄 |
| **`edge_id`** | 48 位（6B） | **序列**产生（同上） | 边的对外标识；`id(r)` 的返回值；**同时是聚簇与二分的键** |
| ROWID | 6B | 引擎 | **顶点行的内部定位**（`src` / `dst` 存它）——不对外（§7） |

**`edge_id` 一个标识担两个角色，为什么合得来** ✗✓（`CONV` §1.1 的序列方案在这里的直接红利）：

| 角色 | 为什么序列值胜任 |
| --- | --- |
| **对外标识** | 序列值区内唯一、不复用（`CONV` §1：从 1 起、跳号不回绕）✓ |
| **聚簇与二分的键** | **序列单调** ⇒ 对任一 `src`，新边的 `edge_id` 大于它**全部**既有边 ⇒ **追加即有序，永不需要分裂协议** ✓✓ |

**"随机 id 不能做聚簇键"这条曾经的顾虑，在序列方案下消失了**——
两个标识**合一**（原 `edge_seq` 已取消，见存储架构 §5.11 的"一个标识，两个角色"）。

**边没有"仅凭 `edge_id` 直接定位"的访问路径** ✗✓——边经**端点**到达
（从 `src` 的链或 `dst` 的覆盖索引）；`WHERE id(r) = $x` 在**已展开的边**上求值 ✓。
（顶点有 id 唯一索引，可以按 id 直取——顶点是锚点，边是从属。）

**引用值**（REQ-GRP-012 的载体）是属性编码里的一个独立标量：
`kind 1B（1=记忆，2=资产）│ id 6B`——编码归 `CFG` 域的 jsonb 标量（新增一种 JEntry 类型）。

### 0.5 一条原则：图元素是**内容**，不是**派生物**

这条决定了好几个边界，单独写出来：

| 推论 | 理由 |
| --- | --- |
| **撤销传播不沿图走** | 撤销传播的对象是**派生物**（`MEM` 域）；图元素是 agent 写的内容，不是任何东西的派生物（§0.1） |
| **图查询可以有界截断** | 内容可以部分返回 + 显式状态（REQ-GRP-008/009）——与派生物"必须完整"相反 |
| **删除被引用对象时，不改写图元素** | 失效是**读时判定**（照 REQ-MEM-011 的形状："不依赖清理任务"）——见 REQ-GRP-012 |
| **图的删除传播靠登记反查** | 不扫描 JSON（REQ-GRP-012）；登记是**系统簿记**，不是业务关系 |

### REQ-GRP-001　命名图与元素模型

**优先级**：必须　**阶段**：P10　**追溯**：总体方案 §13

#### 语义

每工作区支持**多个命名图**。顶点保存 `vertex_id`、`label` 及 JSON 属性；
边保存 `edge_id`、`label`、`src`、`dst` 及 JSON 属性。

#### 规格

**图的创建与删除是一组对象的创建与删除**（§0.2 的形状）：

| 动作 | 做什么 | 事务性 |
| --- | --- | --- |
| 建图 | 建顶点表（表选项「图数据」）+ 出边段 + 出边入口索引 + 入边覆盖索引 + 顶点 id 唯一索引——**同一事务** | 全部成功或全部失败 |
| 删图 | 上列对象一并删除（含其段与登记行，REQ-GRP-012） | 同事务 |
| 伴随对象 | **由引擎维护**——不提供单独删除 / 改名 / 重建伴随索引的语法（"不提供入口"，存储架构 §13.7） | — |
| 属性索引 | **可选、显式声明**（"选定属性索引"）——顶点或边的属性表达式上的 B+Tree；声明语法归 `SQL` 域 | 同事务建 |

**元素的字段**：

| 元素 | 字段 | 类型 / 取值 |
| --- | --- | --- |
| 顶点 | `vertex_id` | **48 位序列**，**图内唯一**（顶点 id 唯一索引保证） |
| | `label` | 有界字符串，**可为空**——空 = 不属于任何标签 |
| | 属性 | JSON 文档（`CFG` 域；深度 / 节点数 / 字节上限照 `CFG`） |
| 边 | `edge_id` | **48 位序列**，图内唯一；**兼作聚簇键**（§0.4） |
| | `src` / `dst` | 顶点的**句柄**（`vertex_id`）——解析后内部存 ROWID |
| | `label` | 有界字符串，可为空 |
| | 属性 | 同上 |

**单标签** ✗✓：V1.0 每个元素**至多一个标签**（照需求文字）。
多标签**不提供**（REQ-GRP-006 的范围控制）——它具有多值属性的一切代价，
而 agent 场景里"类型"用单标签足够 ✓。

**`vertex_id` / `edge_id` 由序列产生**（`CONV` §1.2：每工作区各一条）：
48 位、区内唯一、不复用——与 `memory_id` / `asset_id` 同规 ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 图名在工作区内已存在 | **拒绝**（字典唯一约束——错误码按 `CONV` 错误模型） |
| 图名非法 / 超长 | **拒绝**（标识符规则随 `CONV`） |
| 并发建同名图 | 一个成功、另一个**失败**——不静默复用 |
| 对着已删除的图发查询 | **"不存在"**（REQ-GRP-013） |

#### 验收要点

- **构造**：一个工作区建两个图，各写入同名标签 / 相同属性的元素。
- **预期**：两图的元素互不可见；删图后其伴随对象与登记行一并消失，工作区其余部分不受影响。

### REQ-GRP-002　存储与端点校验

**优先级**：必须　**阶段**：P10　**追溯**：总体方案 §13

#### 语义

底层使用堆表与 B+Tree 入边、顶点与属性索引；出边按 `src` 聚簇（邻接段，索引组织）。
**同一事务内校验端点存在**——悬空边不可产生。

#### 规格

**存储映射**（对象 → 段类型 → 页类型，与存储架构 §8.2 / §9.2 / §5.11 一致）：

| 对象 | 段 `seg_type` | 页类型 | 说明 |
| --- | --- | --- | --- |
| 顶点表 | 1 堆表段 | 1 | 行 = 顶点；`logging = full`、`in_place`（§8.2 #4） |
| 出边段 | **3 邻接段** | **5 邻接页** | 边之家；`ind$.type# = 2`（邻接） |
| 出边入口索引 | 2 索引段 | 2 / 3 / 4 | `(src ROWID) → 首邻接页` |
| 入边覆盖索引 | 2 索引段 | 2 / 3 / 4 | `(dst ROWID) → (src, edge_id, label)` |
| 顶点 id 唯一索引 | 2 索引段 | 2 / 3 / 4 | `(vertex_id) → ROWID` |
| 属性索引（可选） | 2 索引段 | 2 / 3 / 4 | 顶点：`(表达式) → ROWID`；边：`(表达式) → (src, edge_id)` |

**邻接条目的格式**（定案见存储架构 §5.11，本域是提出方）：

```text
每条 = edge_id 6B │ dst 6B │ flags 1B │ itl_slot 1B │ label_len 1B │ payload_len 2B
       │ label（label_len B）│ 属性（payload_len B，JSON 编码）
```

**序列提供单调性**（`CONV` §1）✗✓——对任一 `src`，新边的 `edge_id` 大于其**全部**既有边，
于是插入永远是"追加到链尾"（页满则新页接链），**邻接段永不需要分裂协议** ✓。
**编号不复用**（序列不回绕）；一致读仍靠条目自己的 `itl_slot` + 页内 ITL + `ITL 覆盖` undo 重建（§12.4）✓。

**端点校验（"悬空边不可产生"的实现）**：

1. 边的端点以**句柄**（`vertex_id`）给出 → 在本图的**顶点 id 唯一索引**解析为 ROWID；
   解析失败 = "端点不存在" → **拒绝**；
2. 两行按 **ROWID 升序加写锁**（固定锁序，配合全局死锁检测，`TXN` 域）；
   于是"校验通过后端点被并发删除"**不可能**——删除顶点必须持同一把锁（REQ-GRP-003）；
3. 同事务内刚创建的顶点：按事务自身可见性规则可见 ✓。

**跨图 / 跨工作区边不是"被禁止"，是"表达不出来"** ✓✓（与 REQ-ISO-005 同一修辞）：
句柄只在**本图**的索引里解析；别的图 / 别的区的 `vertex_id` 不在索引里 → 解析失败。
**没有检查，只有"找不到"** ✓。

**存储侧的四处补充**（本域对 `STO` 域的补充要求，已回流进存储文档）：

| # | 补充 | 落点 |
| --- | --- | --- |
| ① | 邻接条目带 `flags` + `itl_slot`——**条目可参与可见性与锁判定**（与行同构） | §5.11 |
| ② | 边标识 `edge_id` = 48 位序列（对外与聚簇键合一；追加即有序、不复用） | §5.11 |
| ③ | 条目的 **undo 定位必须对 defrag 安全**——定位方式随页体细则定稿 | 待冻结项 8 |
| ④ | 邻接页的锁与 ITL 预算**继承通用页头机制**（§5.4），不另设 | §5.4 |

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 端点不存在（含跨图 / 跨区句柄） | **拒绝**——"不存在"，不区分原因（REQ-ISO-006） |
| 端点正被其他事务删除 | 按行锁等待规则等待；超时 / 死锁走 `TXN` 域机制 |
| 属性超限（JSON 上限） | **拒绝**（与 `CFG` 的文档上限一致） |
| `edge_id` 随机碰撞 | 重生成——概率上不可能，但**不做静默覆盖** |

#### 验收要点

- **构造**：并发用例——事务 A 插边（端点 V），事务 B 删 V；以及回滚用例（插边后回滚）。
- **预期**：**任何交错下都不出现悬空边**；回滚后邻接段与两个索引均无残留。

### REQ-GRP-003　删除顶点：默认拒绝，显式 detach

**优先级**：必须　**阶段**：P10　**追溯**：总体方案 §13

#### 语义

删除顶点默认**拒绝存在关联边**；显式 `DETACH DELETE` 受事务与资源预算约束。

#### 规格

**关联边的判定是两次索引探针** ✓：

| 方向 | 判据 | 代价 |
| --- | --- | --- |
| 出边 | 出边入口索引中 `(src)` 是否存在 | O(log n) |
| 入边 | 入边覆盖索引中 `(dst)` 是否存在 | O(log n) |

**默认拒绝**是**显式错误**，不是静默 detach ✗✓——
"删了、顺带把边也删了"会让 agent 永远不知道自己删掉的是拓扑里的哪一段 ✓。

**`DETACH DELETE` 的执行**：

1. 取顶点行写锁；
2. 枚举并删除全部**出边**（沿链走，逐条移除入边索引 / 属性索引条目）；
3. 枚举并删除全部**入边**（覆盖索引扫；逐条到其 `src` 的链上移除，§9.2 已记的代价）；
4. 删除顶点行；
5. 全程**同一事务**——任一步失败**整体回滚**，不留"删了一半"的图 ✗✓。

**资源预算**：单语句 `DETACH DELETE` 的关联边数上限（默认 **10000**，可配）。
**超限 = 拒绝执行 + 明确错误**（提示分批：先用 `DELETE` 语句按模式删边，再删顶点）✗✓——
**不做"删到一半停住"**（那会让 REQ-GRP-009 的"截断"语义渗进写路径 ✗）。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 默认 `DELETE` 一个有关联边的顶点 | **拒绝**，报"存在关联边" |
| `DETACH DELETE` 且关联边数 ≤ 预算 | 全部删除 + 顶点删除，同事务 |
| 关联边数 > 预算 | **拒绝**（资源错误），**零副作用** |
| 删除不存在的顶点 | **拒绝**（前端解析即失败） |

#### 验收要点

- **构造**：有出边 / 入边 / 双向边的顶点各一；先默认删除，再 `DETACH DELETE`。
- **预期**：默认删除全部被拒；detach 后两个方向的索引与链均无残留（用 REQ-GRP-002 的验收同款检查）；
  超预算用例零副作用。

### REQ-GRP-004　语言子集

**优先级**：必须　**阶段**：P10　**追溯**：总体方案 §13

#### 语义

语言范围**固定**：`CREATE`、`MATCH`、`WHERE`、`RETURN`、`LIMIT` 与受控 `SET`、`DELETE` 子集。

#### 规格

**一个语句的形态**（固定顺序，无嵌套）✗✓：

```text
语句 = [ MATCH pattern [, pattern]* [ WHERE 表达式 ] ]
       ( RETURN 投影 [ LIMIT n ]          ← 读
       | SET 属性赋值 [, …]               ← 写（须有 MATCH 锚点）
       | DELETE 元素 [, …]                ← 写（同上）
       | DETACH DELETE 顶点 [, …] )       ← 写（同上）
     | CREATE pattern [, pattern]*        ← 写（独立语句）
```

| 构造 | 子集内 | 说明 |
| --- | --- | --- |
| 顶点模式 | `(v)`、`(v:Label)`、`(v:Label {k: v, …})` | 属性作为匹配条件（相等） |
| 边模式 | `-[r]->`、`-[r:TYPE]->`、`<-[r]-`、`-[r]-`（任意方向）、`{…}` 属性条件 | 方向三种；变长见 REQ-GRP-005 |
| 多模式 | **逗号连接**、变量跨模式共享（即连接语义） | 单一 `MATCH` 子句；**不提供**多个 `MATCH` 块 |
| 表达式 | 属性访问、`id()`、标签 / 类型谓词、比较、`AND` / `OR` / `NOT`、字面量、参数 | **不含聚合、子查询、算术之外的过程性构造**；复杂计算留给外层 SQL |
| `RETURN` | 元素、属性、`id()`、别名；**不去重**（按匹配行） | 无 `ORDER BY` / `DISTINCT` / 聚合——由外层 SQL 做（REQ-GRP-007） |
| `CREATE` | 顶点与边；边的端点必须是**已求值为顶点**的变量 | 端点存在校验见 REQ-GRP-002 |
| `SET` | **仅属性键的设置 / 覆盖 / 移除** | 不改标签、不改端点（换端点 = 删 + 增，§9.2） |
| `DELETE` | 边或顶点；顶点默认拒绝（REQ-GRP-003） | 受控子集 |

**引用值**（REQ-GRP-012）在图语言里由**专用构造式**产生（形如 `ref(memory, '<id>')`；
具体拼写归 `SQL` 域的语法定稿）——这是唯一能写入"受管引用"的路径 ✓。

**执行形态两种**：
① **独立语句**（读写皆可，经会话执行）；
② **表值算子**（读查询作为 SQL 的表源，REQ-GRP-007；具体语法归 `SQL` 域）。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 子集外的构造（见 REQ-GRP-006 清单） | **解析错误**——明确报"不支持"，**不尽力执行、不静默降级** ✓ |
| `SET` / `DELETE` 无 `MATCH` 锚点 | **拒绝**（写必须从匹配出发） |
| `CREATE` 的端点不是已求值顶点 | **拒绝** |

#### 验收要点

- **构造**：每个合法构造与每个非法构造各一例。
- **预期**：合法者行为可判定；非法者**报"不支持"而非语法歧义**。

### REQ-GRP-005　遍历与重复策略

**优先级**：必须　**阶段**：P10　**追溯**：总体方案 §13

#### 语义

支持一跳与**指定有限跳数**的方向遍历；定义路径中重复顶点或边的策略。

#### 规格

**跳数**：

| 写法 | 含义 |
| --- | --- |
| `-[r:TYPE]->` | **一跳**（固定长度） |
| `-[r:TYPE*1..5]->` | 变长，`n..m`，**上界必须写出** ✗✓ |
| `*`、`*1..`、`*..5` | **不提供**（无上界 = 无限变长，REQ-GRP-006 禁止） |
| `m` 的取值 | ≤ 工作区上限（REQ-GRP-008，初始 **5**） |

**方向**：`->`（出边，沿链）、`<-`（入边，走覆盖索引）、`-`（任意方向 = 出 ∪ 入）。
**`-` 的去重**：同一条边若两个方向都符合，**只产生一次**（按边的身份去重）✓。

**重复策略**（这是本条的验收核心）：

| 路径类型 | 顶点 | 边 | 语义名 |
| --- | --- | --- | --- |
| **固定长度**（写了几段就是几段） | 可重复 | 可重复 | walk——写出的模式匹配什么就是什么 |
| **变长 `*n..m`** | **可重复** | **不可重复** | **trail**（openCypher 的默认语义 ✓） |

**为什么变长取 trail** ✗✓：图不保证无环；
walk 语义下"环上绕圈"会让有限跳数的遍历产生**指数级重复路径** ✗——
trail 用"不重复边"把路径数收敛到边数的组合量级 ✓，
且"一条边在一条路径里只走一次"是拓扑/依赖场景的常识语义 ✓。

**路径不是一等值** ✗✓：V1.0 的 `RETURN` 返回元素与属性，**不返回路径对象**——
重复策略决定的是**遍历语义与去重**；路径值类型（及其排序/比较）不在子集内（REQ-GRP-006）。

**自环与多重边**：支持 ✓——自环（`src = dst`）与同 `(src, dst, label)` 的多重边都是合法数据；
匹配按**边的身份**计（多重边产生多行）✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| `m` 超过工作区上限 | **拒绝**（不静默改小——REQ-GRP-008） |
| 环 / 稠密子图 | trail + 预算（REQ-GRP-008/009）保证终止与有界 |
| 无向模式遍历到自环 | 只产生一次 |

#### 验收要点

- **构造**：参考邻接模型比对——匹配、方向、循环、多重边、自环、属性过滤、分页。
- **预期**：与参考模型的匹配集合**逐行一致**（trail 语义按上表）。

全部在外层 SQL 完成 ✓（这也是 REQ-GRP-004 砍掉它们的理由：**一件事只有一个地方做**）。

顶点读两条路（直接 `SELECT` 顶点表 / 图查询匹配），**可见性判定是同一套**（§12）✓；
边只经图查询（边不是行）✓。

**不跨系统搬数据** ✓：图匹配先算出匹配行集，再进 SQL 的关系算子——

- **预期**：关联可用；两条读路径的**可见集合逐行一致**。

### REQ-GRP-008　预算与上限

**优先级**：必须　**阶段**：P10　**追溯**：总体方案 §13

#### 语义

限制最大跳数、扩展边数、结果数、内存与时间；
**建议初始上限 5 跳**（待 P0 冻结——需求文档 §8 第 3 项）；达到边界返回**明确截断状态或资源错误**。

#### 规格

**五类预算，两个层次**（**请求参数 ≤ 工作区配置 ≤ 系统硬上限**）✗✓，
**且"主约束是扩展边数、跳数是形状上限"**（《存储容量与规模基线》§5 的修正）：

| 预算 | 含义 | 初始值（工作区默认） | 角色 |
| --- | --- | --- | --- |
| **扩展边数** | 单语句遍历**展开的边条目数**（含被过滤掉的） | 100 000（建议） | **主约束**——真正兜底的 ✅ |
| **最大跳数** | 变长模式的 `m` 之上限 | **5** | **形状约束**（次要）——按度 10 估，5 跳最坏展开 10⁵ 条边，**它管不住代价** ✗✓ |
| **结果数** | 单语句产出的匹配行数上限（与 `LIMIT` 同时生效，取小） | 10 000 | 可调 |
| **内存** | 单语句图执行的中间态内存预算 | 随 `NFR` / `RES` 域定 | 可调 |
| **时间** | 单语句时限（调用方可给） | 随 `NFR` / `RES` 域定 | 可调 |

**为什么主约束是边数** ✗✓——这是"跳数"最容易骗人的地方：
度 10 时 2 跳就可能摸到上百条边、**5 跳最坏 10⁵ 条** ✗。
**跳数限制的是"形状"（几步之内），边数限制的才是"代价"（走了多少条边）** ✓。
两者都要有，但**真正保证不失控的是后者** ✓——P0 冻结时两条一起冻 ✓。

**记账点必须可判定** ✗✓：

- 每**展开一条边**（无论最终是否入选）**扣 1**——"扩展边数"记的是**代价**，不是结果；
- 每**产出一行**扣 1（结果数）；
- 时间按语句计时；内存按执行器实际持有量。

**参数校验在解析期**：`m` 超上限、预算为负 / 超硬上限 → **拒绝**，
**绝不静默改小**（静默改小 = 把"资源不足"伪装成"答案完整"，正是 REQ-GRP-009 禁止的）✗✓。

**默认值与画像的关系**：5 跳是"**建议初始上限**"，其最终冻结归 P0；
其余四项是"**可调默认**"，工作区层面调整，不随单次请求任意放大（系统硬上限另设）✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 预算耗尽 | **截断状态**（REQ-GRP-009）——返回已得结果 + 原因 |
| 硬错误（如内存耗尽无法继续） | **资源错误**，事务语义照 `TXN` 域 |
| 参数非法 | **解析期拒绝** |

#### 验收要点

- **构造**：稠密图 + 小预算（与 `RET` 的验收同构）；
  **规模档位照《存储容量与规模基线》§6**（小 1 万顶点 / 10 万边起，含高度数专项）。
- **预期**：**超预算返回明确状态**——不静默截断、不超时、不假装完整。

### REQ-GRP-009　截断状态必须显式

**优先级**：必须　**阶段**：P10　**追溯**：总体方案 §13

#### 语义

**不得把截断结果当作完整答案返回**。

#### 规格

**结果随带完整性状态**（照 `RET` REQ-RET-006/025 的先例 ✗✓）：

```text
完整   |  截断（原因 ∈ {跳数, 扩展边数, 结果数, 内存, 时间}）
```

| 情形 | 状态 |
| --- | --- |
| 引擎因**预算**停止 | **截断** + 具体原因（哪一项先耗尽） |
| 调用方写了 `LIMIT` / 外层 SQL 限制 | **完整**——那是**调用方自限**，不是引擎截断 ✗✓ |
| 自然穷尽 | **完整** |

**"调用方自限 ≠ 引擎截断"这一区分是必须的** ✗✓——
否则 agent 无法回答"我看到的是全部吗"：
`LIMIT` 是它自己要的，**截断是引擎没能给完**——两者必须可分辨 ✓。

**截断时返回已得结果 + 状态**（不抛错、不空手）——
与 `REQ-RET-025`"预算不足仍返回、明确标注"同规 ✓；
**只有连部分结果都无法产出**（如内存硬耗尽）才升级为**资源错误** ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 截断但调用方忽略状态位 | 允许——**状态在契约里，不在返回值里藏** ✓ |
| 某实现"截断当完整" | **验收失败**（本条的存在理由） |

#### 验收要点

- **构造**：小预算 + 稠密图；以及同图放宽预算重跑。
- **预期**：两次的（结果, 状态）满足：宽预算的结果**包含**窄预算的、且窄预算那次**状态为截断**。

### REQ-GRP-010　事务与并发

**优先级**：必须　**阶段**：P10　**追溯**：总体方案 §13

#### 语义

图更新、属性、端点约束与索引**共享工作区事务**；故障后**无悬空边**。

#### 规格

**没有新机制** ✓✓——这是本条的要点：图元素就是"行（顶点）"与"条目（边）"，
它们的事务性来自既有机制，**不引入图专用的事务路径**：

| 机制 | 从哪来 |
| --- | --- |
| 原子性 / 回滚 | 行与条目的 undo（§4.6，五种操作码含 `ITL 覆盖`） |
| 隔离 / 快照读 | §12 的三步判定——条目的 `itl_slot` 与行同构（REQ-GRP-002 补充 ①） |
| 提交 / 延迟清除 | §11.1.1 的延迟日志版——图段 `logging = full` 照常参与 |
| 恢复 | redo 重放 / undo 回滚（§11）；段的自描述照旧 |
| 并发控制 | 行锁 + 全局等待图死锁检测（`TXN` 域） |

**四条不变量**（图的正确性全在这四条上）：

| # | 不变量 |
| --- | --- |
| 1 | **边的三处记录同事务原子**：邻接条目、入边覆盖索引、属性索引、`ref$` 登记行——要么都在，要么都不在 ✅ |
| 2 | **端点存在**：端点校验与端点删除**互斥**（同一把行锁，REQ-GRP-002）——**悬空边不可产生** ✅ |
| 3 | **`DETACH DELETE` 全有或全无**（REQ-GRP-003）——不留半删的图 ✅ |
| 4 | **`edge_id` 的唯一性**：同 `src` 的存活条目编号唯一，且**永不复用**（序列不回绕） ✅ |

**故障后**：重放只重放**已提交**的；未提交的按 undo 回滚——
**任何终止点都不会留下"边在索引里、不在链里"这类半状态** ✓
（因为三处记录在同一条 redo/undo 流里，按原子事务重放 ✗✓）。

#### 边界与错误

| 并发场景 | 预期 |
| --- | --- |
| 插边 vs 删端点 | 互斥——后到者等待；删除先成则插边**端点不存在**拒绝 |
| 同时插两条边到同一顶点 | 端点行锁串行化——**多写者低争用画像下可接受** ✓ |
| 并发 `SET` 同一属性 | 行 / 条目锁串行化，后写覆盖（末位胜） |
| `DETACH DELETE` vs 并发插边 | 顶点锁互斥——不产生"detach 之后又挂上的边" |
| 提交前崩溃 | 回滚——三处记录一起消失 |

#### 验收要点

- **构造**：上表每个场景 + 故障注入（提交前 kill）。
- **预期**：**无悬空边、无半条边**；恢复后图结构与约束一致。

### REQ-GRP-011　隔离：跨区与 public

**优先级**：必须　**阶段**：P10　**追溯**：总体方案 §13

#### 语义

禁止跨私有工作区边、外键与可写联结；**public 图只读**，通过独立查询与应用层关联读取；
私有记录可以保存 public 实体版本标识作为**普通数据引用**，但不建立跨区级联关系。

#### 规格

**跨私有工作区的边**：见 REQ-GRP-002——**不可表达** ✓（句柄只在图自己的索引里解析）。
**外键**：不存在（`ISO` REQ-ISO-005：没有跨区事务，外键缺前提）✓。
**可写联结**：不存在（单语句只落一个工作区）✓。

**public 图**（`public` 工作区里的图）：

| 动作 | 路径 |
| --- | --- |
| 读 | **只读**，经 `public` 的**过滤层**（REQ-ISO-004/006 的同一层，§13.5）——**不另设第二套过滤** ✓ |
| 过滤粒度 | **顶点 = 行级过滤**（归属列，§13.5 的机制）；**边的可见性随端点**——`src` 与 `dst` 均可见，边才可见 ✓ |
| 写 | **只经标准接口**（§13.6）——直接图语言写入 `public` 被拒绝 |
| 关联 | **独立查询 + 应用层关联**（需求原文）——不与私有数据的图查询同语句 ✓ |

**"边的可见性随端点"为什么不引入第二条规则** ✗✓：
边引用两个顶点，没有独立于端点的"归属"；
让边随端点可见 = 过滤层**只有一条规则**（行级），在边上**派生**应用 ✓。
这使 `REQ-ISO-006` 的"不可区分"在图上自动成立 ✓。

**私有记录引用 public 对象**：作为**普通数据**（如把 public 对象的 id / 版本标识
存成字符串 / 数值属性）——**不是受管引用**（不登记、不级联、不跨区解析）✓。
`REQ-GRP-012` 的登记**只覆盖本工作区对象** ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 对 public 图发图语言写 | **拒绝**（写侧入口校验） |
| 私有图查询里引用 public 图名 | **"不存在"**（REQ-GRP-013） |
| 单语句跨 private 与 public | **不提供**（两条语句，应用层关联） |

#### 验收要点

- **构造**：两个主体各自的私有图 + `public` 图；读侧过滤用例（归属行）。
- **预期**：public 图可读不可写；过滤行**不进扫描**（REQ-ISO-006）；
  私有记录里的 public id 是普通值（删 public 对象后**无级联**）✓。

### REQ-GRP-012　受管引用登记

**优先级**：必须　**阶段**：P10　**追溯**：总体方案 §13

#### 语义

图属性若引用记忆或资产，**须使用受管依赖登记**；
**删除传播不得靠扫描 JSON 猜测引用**。

#### 规格

**引用值**（"什么算引用"必须可判定 ✗✓）：

```text
引用值 = 属性编码中的独立标量（新增一种 JEntry 类型）
          kind 1B（1 = 记忆，2 = 资产）│ id 6B
```

- **只由专用构造式产生**（REQ-GRP-004 的 `ref(...)`）——普通字符串 / 数值**永远不是引用** ✓；
- 只能**相等比较**与 **id / kind 提取**；不参与排序、不算术运算 ✓；
- 编码落点在 `CFG` 域（jsonb 标量表新增一行）✓。

**登记表 `ref$`**（每工作区一张**系统表**，随工作区创建；引擎维护）——
**图元素是它的一类引用者**，另一类是**表行**（`AST.md` §0.4 的推广：
任何带 `ASSET_REF` 列的行都同样登记）：

| 列 | 含义 |
| --- | --- |
| `from_obj#` | 引用者所在对象号（图 / 业务表——同一工作区共置一表，**反查一次完成** ✓） |
| `from_rowid` | 引用者行的 ROWID（顶点行或边的 `src` 行） |
| `from_sub` | 0 = 行本身（含顶点）；> 0 = 边的 `edge_id` |
| `to_kind` | 1 = 记忆，2 = 资产 |
| `to_id` | 被引用对象 ID（6B 序列值） |

| 索引 | 用途 |
| --- | --- |
| 正向（`from_obj#`, `from_rowid`, `from_sub`, `to_kind`, `to_id`） | 幂等（同一引用只一行）+ 引用者侧维护 |
| **反向（`to_kind`, `to_id`）** | **删除传播的反查**——"谁引用了 M"一次定位 ✓ |

**维护规则（全部同事务）**：

| 触发 | 动作 |
| --- | --- |
| 写入含引用值的属性（`CREATE` / `SET`，含"复制"——表达式取到引用值再写入他处） | **登记**（正向键幂等） |
| 覆盖 / 移除该属性键 | 撤销**该**登记行 |
| 删除元素（含 `DETACH DELETE` / 删图） | 删除其**全部**登记行 |
| 引用目标不存在 | **写入时拒绝**（与端点校验同构："悬空引用不可产生" ✓） |

**失效是读时判定，不改写数据** ✗✓（照 `REQ-MEM-011` 的形状）：

```text
该引用已失效  ⟸  被引用对象已删除 / 已撤销（查询时判定）
```

- **不因目标删除而改写图元素**、**不依赖清理任务** ✓；
- **登记行保留**——反查仍能枚举"哪些元素引用了它"（供 agent 修复 / 审计）✓；
- 读到一个失效引用：呈现**"引用已失效"状态**，不把它当作有效句柄返回 ✓。

**反查的三个用途**：① 删除传播的枚举；② 审计；③ **检索图扩展的入口桥**
（`REQ-RET-009`：候选记忆 → 反查登记 → 引用它的顶点 → 沿图扩展）✓。

**"不扫 JSON"是可验收的** ✓：反查只走 `(to_kind, to_id)` 索引——
验收用"把属性挂在任意深层路径"的构造证明**反查不依赖属性形状**（下节）。

#### 实现定稿（待冻结项 58）

**① 表选项「图数据」的编码**：`table_opts` 2B 位域收回一个保留位——
**`graph 1b`（第 9 位；顶点表 = 1，其余 = 0）**。语义：

- **只有顶点表置位**——出边段由 `seg_type = 3` 标识、伴随索引在 `ind$` 里有所属基表，都不需要它；
- 置位是"这张表是一个图的顶点表"的**唯一标记**；**图名 = 表名**，伴随对象名由此推导
  （`g$out` / `g$o` / `g$i`，§0.2）；
- **不提供 DDL 修改入口**（建图 / 删图是引擎事务，§0.2 的"不提供入口"纪律）。

**② `ref$` 的物理布局**：**普通堆表**（系统表，随工作区创建；复用全部行列机制，无专用页型）：

| 列 | 宽度 | 备注 |
| --- | --- | --- |
| `from_obj#` | 4B | 引用者对象号（图 / 业务表） |
| `from_rowid` | 6B | 引用者行的 ROWID（顶点行或边的 `src` 行） |
| `from_sub` | 6B | 0 = 行本身；> 0 = 边的 `edge_id` |
| `to_kind` | 1B | 1 = 记忆，2 = 资产 |
| `to_id` | 6B | 48 位序列值 |

列编码照通用规则（§6.5 / §6.6）——**不特判**。两个 **B+Tree**：

| 索引 | 键 | 唯一性 |
| --- | --- | --- |
| **正向** | (`from_obj#`, `from_rowid`, `from_sub`, `to_kind`, `to_id`) | **唯一**（登记幂等） |
| **反向** | (`to_kind`, `to_id`) | **非唯一**（一个目标被多方引用）——删除传播与检索桥的反查入口 |

**③ 回收路径：没有专用路径**——`ref$` 行就是普通行：

- 删除即标记（位 0）→ 提交后槽位可复用；defrag 照常（§5.9）；
- 删除来源三条（全同事务，见上文维护规则）：覆盖 / 移除引用值 → 撤销该登记；
  删除元素 → 清空其登记；**引用目标不存在 → 写入拒绝**（不产生悬空）；
- **失效不删行**（读时判定）——**不依赖任何清理任务**；登记行的生命周期 = 引用者的生命周期。

**④ 与 Apache AGE 目录的对照**（参照来源：`apache/age` 源码，2026-10-04 经代理获取，
证据包 `graph-age-20261004`）：

| 面 | AGE | 我们 |
| --- | --- | --- |
| 图与标签的登记 | `ag_catalog` 两张目录表：`ag_graph(graphid, name, namespace)`；`ag_label(name, graph, id, kind('v'/'e'), relation, seq_name)` | **不新增目录表**：图 = 顶点表自身在 `obj$` / `tab$` 的行 + `graph` 表选项位；标签 = **数据字段**（顶点行 / 条目的 `label`），无登记 |
| 元素 id | 64 位复合 `graphid` = **高 16 位标签号（1..65535，0 无效）+ 低 48 位条目号**（每标签独立序列） | **48 位全局序列 + `label` 数据列**（D-01）——**同为"两段式"**：AGE 把标签段编进 id，我们把标签段留在数据里 |
| 每图隔离 | 一个 PG schema（namespace） | 工作区刻度（图共享工作区表空间，伴随对象用命名后缀） |
| 标签 → 表 | `relation` 列（每标签一张继承表） | **单表模型，无映射**（§0.3 明确不取继承式标签表） |

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 引用不存在的对象 | **拒绝**（写入时） |
| 引用 public 对象 | **不是受管引用**——按普通数据处理（REQ-GRP-011） |
| 目标被删后再反查 | **登记行仍在**——枚举正常（对象已不可见，引用呈"已失效"） |
| 登记表被直接 DML | **不提供**（系统表，无写入路径） |

#### 验收要点

- **构造**：顶点 A 引用记忆 M₁、边 B 引用资产 A₁；删除 M₁。
- **预期**：① 读 A 的该引用 = **已失效**，A 的其余属性不变；② 反查 M₁ 能枚举 A（**且实现路径不含 JSON 扫描**）；③ A₁ 的引用不受影响；④ 撤销 M₁ 的**派生物**仍按 `MEM` 域传播（两条路径互不干扰，§0.1）。
