## 0 模型总述

### 0.1 JSON 的内部表示：参照 PostgreSQL 的 `jsonb`

**PostgreSQL 有两个 JSON 类型**，而这个二分本身就值得先说：

| | `json` | **`jsonb`** |
| --- | --- | --- |
| 存什么 | **输入文本的原文** | **二进制的分解表示** |
| 空白 / 键序 / 重复键 | **全部保留** | **全部丢弃**（重复键"后者胜"） |
| 查找一个键 | **线性扫描** | **二分**（键有序且集中） |
| 索引 | 需表达式索引 | 可建倒排索引 |

**我们取 `jsonb` 这一路**——需求已经定了"**二进制 JSON 文档**"（§6.6），
而 `jsonb` 正是那个形状的成熟实现。

```text
值 = 一个变长字节串（就是行里的一个变长列值）

容器（container）
  32 位头
    位 31–28   标志：0x1 标量 / 0x2 对象 / 0x4 数组
    位 27– 0   子项数
  JEntry 数组（每子项 4 字节）
  数据区

JEntry
  位 31– 4   该子项的**结束偏移**（相对数据区起点）
  位  3– 0   类型：字符串 / 数值 / 真 / 假 / null / 容器 / **引用**

数组：每元素一个 JEntry，按数组序
对象：**键全部在前（按键序）**，**值全部在后**——共 2n 个 JEntry
标量：**一个容器，内含一个 JEntry**——于是"标量"与"复合"在格式上同构
```

**第七种类型是"引用"**（`GRP` 域的受管引用，REQ-GRP-012）：
载荷 = `kind 1B │ id 6B`（1 = 记忆，2 = 资产；id 为 48 位序列值）。
它只由图形写路径的**专用构造式**产生、只能做相等比较与 id/kind 提取——
**普通字符串与数值永远不是引用** ✓（边界见 `spec/GRP.md`）。

**三条设计要点，都是照 `jsonb` 的**：

| 要点 | 为什么 |
| --- | --- |
| **对象把键全部排在前面** | 查一个键**只在连续的前半段二分**——不必在键值交错的数据里跳跃。这是"键集中"的收益 |
| **键序 = 长度优先，然后按字节** | **短键集中**，二分时前几次比较就能排除大片 |
| **数值就是 `NUMBER`** | 与 REQ-CFG-003"不得静默转为有损浮点"直接对上（`jsonb` 同样把数值存成 `numeric`） |

**并因此不暴露 JSON 的排序语义**：PostgreSQL 因为"长度优先"的键序，
让对象的 btree 比较产生反直觉的结果（键较短的文档反而"更大"）。
**我们只提供 `=`，不提供 `<` / `>`** ✗——REQ-CFG-005 要的"标量比较"
指的是**取出来的标量**之间的比较，与整个文档的排序无关。

### 0.2 与 PostgreSQL 的四处有意差异

| | PostgreSQL `jsonb` | **我们** | 理由 |
| --- | --- | --- | --- |
| **偏移的记法** | **每 32 个子项记一次偏移，其余记长度** ✗ | **全部记偏移** | 见下——**这是最重要的一处** |
| **大值的存放** | TOAST 指针，行外存储 | **行片段链**（§6.8） | 同一件事的两种做法；我们的上限是 **1MB** |
| **重复键** | **后者胜**——静默丢弃 | **拒绝**（REQ-CFG-004） | 静默丢弃属于"输入与存储不一致"；**拒绝让用户知道** |
| **倒排索引** | GIN（`jsonb_ops` / `jsonb_path_ops`） | **表达式 B+Tree**（REQ-CFG-007） | 我们只提供 B+Tree / ANN / 邻接（§9） |

#### 为什么"偏移的记法"这一处我们必须反过来

PostgreSQL 那个混合策略是**为压缩做的折中**，而它的理由值得完整说一遍——
因为我们的结论正好相反：

> **为什么它混合**：一连串连续的偏移是"**不重复的数据**"，
> 即使输入高度重复，压出来也压不动 ✗。改成"长度"之后，重复的结构才能压得动 ✓
>
> **为什么它不能干脆全改成长度**：查找一个键要靠 `JEntry` 数组上的
> **随机访问二分**，而长度需要**累加前面所有项**才能定位 ✗——**二分就没了**
>
> 于是它折中：**偶尔记一个偏移**（够二分用），**其余记长度**（够压缩用）

**我们不做那个折中，因为折中的前提在我们这里不成立**：

| PostgreSQL 有 | **我们** |
| --- | --- |
| 一套**通用的行外压缩**（TOAST 的 pglz / LZ4） | **没有** ✗——大对象走 `ASSET_REF` 的资产、长文本走行片段链（§6.8），**两者都不经过通用压缩** |

**没有那套压缩器，"为压缩而折中"就没有收益** ✓。
而**全存偏移的代价是 4 字节 × 子项数**——在有 1MB 文档上限的前提下（§0.3），
这点开销换来**任何时候都能二分** ✓。**简单与快在这里又是同一件事。**

### 0.3 三层"没有"

REQ-CFG-002 要求"**字段缺失、JSON null 与 SQL NULL**"三者分别可判定。
在二进制里它们落在三个不同的层，**天然不会混**：

| | 在二进制里的位置 | 判定方式 |
| --- | --- | --- |
| **字段缺失** | **键根本不在对象的键区里** | 键查找**找不到** |
| **JSON null** | 键**存在**，其 `JEntry` 的**类型位是 `null`** | 找到键 → 读类型位 |
| **SQL NULL** | **整个列值是 NULL**——不在 JSON 二进制里 | 行内的 **NULL 位图** |

**第三行是唯一一条"不在 JSON 内部"的** ✗——它属于行格式（§6.1）。
**所以三者的可判定性来自"它们本就在不同层"，不来自任何比较规则** ✓——
这也意味着**实现上不可能把它们混起来**，这是比"写一条规则禁止混用"更强的保证。

### 0.4 配置记录的形状

**一个配置 = 多行（每修订一行）+ 一个活动引用**——这是 REQ-CFG-009 推出来的：

| 要求 | 推出来的形状 |
| --- | --- |
| 修订**不可变** | 每修订**一行**，插入后不改 |
| 以**预期 revision** 条件切换 | 切换是 `UPDATE ... WHERE revision = :expected`——**CAS**，不是读改写 |
| 旧版本**保留** | 不删旧行 |
| 回滚**只切换活动引用** | 回滚 = 把活动引用改回旧修订——**不复制数据** ✓ |

### REQ-CFG-001　JSON 的内部文档表示

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §6

#### 语义

JSON 采用**可校验的内部文档表示**，支持对象、数组、字符串、精确数值、布尔与 `null`。

#### 规格

- **表示**：§0.1 的容器 / `JEntry` 结构；
- **可校验**：**任何字节串都能被验证是不是合法的 JSON 二进制**——
  偏移必须单调、类型位必须合法、容器标志与子项数必须自洽、字符串必须是合法 UTF-8；
- **往返无损**：**类型往返（文本 ↔ 二进制 ↔ 文本）在语义上无损**——
  丢的只是空白、键序与重复键这些**语义上不重要的**（§0.2）；
- **数值是 `NUMBER`**（§0.1）——不是浮点。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 字节串不是合法表示 | **拒绝**，报明确的损坏错误（不是"尽力解析"） |
| 输入 JSON 文本非法 | **拒绝**，报位置 |

#### 验收要点

- **构造**：各类 JSON 文档（含嵌套、空对象、空数组、Unicode、极值数值）。
- **预期**：**类型往返无损**；非法输入**全部拒绝**。

### REQ-CFG-002　字段缺失 / JSON null / SQL NULL

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §6

#### 语义

必须**明确区分**字段缺失、JSON `null` 与 SQL `NULL`。

#### 规格

**§0.3 已经说明：三者落在三个不同的层，天然不会混。**

| | 层 |
| --- | --- |
| 字段缺失 | **JSON 的对象键区**里没有它 |
| JSON `null` | JSON 的**值**是 `null` 类型 |
| SQL `NULL` | **行格式**的 NULL 位图（§6.1） |

**因为分属不同层，所以：**

| 表达式 | 结果 |
| --- | --- |
| 取一个缺失的路径 | **缺失**（不是 null，也不是 SQL NULL） |
| 取一个值是 JSON `null` 的路径 | **JSON `null`** |
| 取一个 SQL NULL 列里的路径 | **SQL NULL** |

**三者两两 `IS DISTINCT FROM`**——这是验收的方式。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 把"取不到"当成 `null` 返回 | **缺陷**——那是把两层压成一层 |
| 把 JSON `null` 当成 SQL NULL | **缺陷** |

#### 验收要点

- **构造**：一个对象含三个字段——缺失的、值为 `null` 的、所在列是 NULL 的。
- **预期**：**三者分别可判定**，互不相等。

### REQ-CFG-003　数值不得静默转为有损浮点

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §6

#### 语义

数字**不得在 SDK 往返时静默转为有损浮点数**。

#### 规格

**内部已经是精确的**——JSON 的数值就是 `NUMBER`（§0.1），十进制、变长、
**不经二进制浮点**（`CONV §5.1`）✓。**问题只会在"出去和回来"的路上** ✗：

| 环节 | 要求 |
| --- | --- |
| **编码 → SDK** | 必须走"**十进制文本，保留声明精度与标度**"（`CONV §5.1`），**不得经 double** |
| **SDK → 解码** | 同上 |
| **SDK 自身的语言类型** | **SDK 的责任**——若宿主语言只有 `double`，SDK 必须**要么用十进制库，要么明确报错**，**不得静默转换** ✗ |

**第三行是这条需求的真正着力点**：库这边是精确的，
**损坏发生在宿主语言的类型上** ✗——而它离库很远，容易被当成"不是我们的问题"。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 数值超出宿主语言的浮点精度 | **SDK 必须报错或用十进制类型承载**，不得静默截断 |
| 数值超出 `NUMBER` 范围 | **写入时拒绝**（§REQ-CFG-004 的上限） |

#### 验收要点

- **构造**：高精度数值（如 38 位、多位小数、`1e125`）逐值往返。
- **预期**：**逐位一致**。

### REQ-CFG-004　重复键策略与四项上限

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §6

#### 语义

P0 冻结**重复键策略**（建议拒绝），并定义 **Unicode、数值范围、最大深度、节点数及文档字节限制**。

#### 规格

| 项 | **取值** | 理由 |
| --- | --- | --- |
| **重复键** | **拒绝** | 见下 |
| **Unicode** | **必须是合法 UTF-8**；非法字节与**不成对的代理**一律拒绝 | 不合法就报错，不"修复" |
| **数值范围** | **`NUMBER` 的取值域**（§REQ-TYP-001）；超出**拒绝** | 与类型系统一致，不另立一套 |
| **最大深度** | **32** | 深度决定**递归解析与序列化的栈**；32 层足以表达配置与工具参数 |
| **节点数上限** | **65536** | 与字节上限一起约束**解析的内存与时间** |
| **文档字节上限** | **1MB** | **与行片段链的上限一致**（§6.8）——不是独立选的 |

**重复键为什么拒绝而不"后者胜"**：

> PostgreSQL 的 `jsonb` **后者胜**——**静默丢弃**先出现的那一个 ✗。
> 那属于"**输入与存储不一致**"：用户写了两遍，系统只留一个，**而且不告诉他**。
>
> **拒绝让用户知道** ✓。而且拒绝**实现更简单**——去重的"哪一个胜"
> 本身就需要一条规则（PG 还专门用一个索引字段记录原始顺序来定它）✓

**文档字节上限与行片段链的一致性是刻意的**：JSON 就是**一个变长列值**，
它走的是**所有变长值共用的那条路**（§6.8）✓。给它单独一个上限，
就制造了"两种长值、两套规则" ✗。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 重复键 | **拒绝**，指出是哪一个键 |
| 深度 > 32 | **拒绝**（写入时） |
| 节点数 > 65536 | **拒绝**（写入时） |
| 字节 > 1MB | **拒绝**（写入时） |
| 非法 UTF-8 | **拒绝**，指出字节位置 |

**全部在写入时报**——不是读到一半才发现。

#### 验收要点

- **构造**：恰好在上限、上限 +1 的用例，逐项。
- **预期**：上限内通过、上限 +1 **拒绝且错误稳定**。

### REQ-CFG-005　路径操作

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §6

#### 语义

提供**路径取值、存在判断、标量比较、有限数组访问、完整替换与受控局部修改**。

#### 规格

| 操作 | 说明 |
| --- | --- |
| **路径取值** | 按路径取一个子树或标量 |
| **存在判断** | 键或路径是否存在（对应 REQ-CFG-002 的"缺失"层） |
| **标量比较** | **取出来的标量**之间的比较——**不是整个文档的排序**（§0.1） |
| **数组访问** | **受限**：按下标取、取长度——**不做切片、不做任意表达式** |
| **完整替换** | 用一个新文档替换整个值 |
| **受控局部修改** | 改一个字段——实现见 REQ-CFG-006 |

**"有限"与"受控"是刻意写的**：本库**不支持任意 JSONPath** ✗（REQ-CFG-007 同一条精神）。
路径语法只要**够用且可判定**——**路径集合有限，才能为它建表达式索引** ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 路径语法不支持 | **拒绝**，指出不支持的构造 |
| 数组下标越界 | **缺失**（不是错误，也不是 null） |

#### 验收要点

- **构造**：每种操作各一组确定用例。
- **预期**：**各操作有确定结果**（REQ 的验收原文）；不支持的路径**明确拒绝**。

### REQ-CFG-006　局部修改

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §6

#### 语义

局部修改在**数据库事务内**完成；**不要求原地修改 JSON 编码**，
**允许重新编码并使用跨页行**。

#### 规格

**"允许重新编码"是本设计最大的简化之一，应当明说它的分量：**

> **JSON 的修改 = 读整值 → 改 → 重新编码 → 写回。** 没有原地修改 ✗。
>
> **代价是 O(值大小)**：改一个 1MB JSON 里的一个字段，写回 1MB ✗。
> **而这个代价的界就是 1MB**（REQ-CFG-004）——不是无界的 ✓。
>
> **换来的是**：JSON **没有"部分更新"这条路径** ✗，
> 于是**页格式、undo、redo、WAL 都不必为它开例外** ✓✓——
> 它就是**一个普通的变长列值**，和任何 `VARCHAR2` 走完全相同的路 ✓。

**两处必须写明的关联**：

| | |
| --- | --- |
| **undo 的体积** | 整个值的**前像**——即"改一个字段要写 1MB 的 undo"（§4.6.2 的"更新只存被改列的前像"）✗ |
| **行片段链** | 超出一页的 JSON 走片段链（§6.8）；**没有"JSON 专用的行外存储"** ✗ |

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 事务回滚 | **JSON 无残留变更**（REQ 的验收）——靠整值的 undo 前像 |
| 修改后超出 1MB | **拒绝**，整个修改回滚 |

#### 验收要点

- **构造**：事务内做局部修改后回滚。
- **预期**：**JSON 逐字节回到修改前**。

### REQ-CFG-007　索引

**优先级**：应当　**阶段**：P2　**追溯**：总体方案 §6

#### 语义

索引**先采用选定路径的表达式 B+Tree**，**后实现受限倒排索引**；
**不默认支持任意复杂 JSONPath**。

#### 规格

| 阶段 | 做什么 |
| --- | --- |
| **先** | **选定路径的表达式 B+Tree**——`CREATE INDEX ... ON t (取出路径 expr)` |
| **后** | **受限倒排索引**——受限的含义：**只支持枚举出的那几种路径形态** |

**表达式 B+Tree 为什么能成立**：取出来的标量是 `NUMBER` 或 `VARCHAR2` 一类，
**编码保序**（§6.5）✓——所以**范围扫描天然可用** ✓。

**而这也解释了 REQ-CFG-005 为什么要"有限"**：

> **表达式索引的键是一个确定类型的值** ✗。
> 若路径语法任意，**它的类型就不确定** ✗——索引无从建立。
> **所以"路径有限"不是一个功能取舍，是索引能否存在的前提** ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 路径返回值类型不确定 | **建索引时拒绝**——要求显式指定类型 |
| 用不支持的 JSONPath 建索引 | **拒绝** |

#### 验收要点

- **构造**：对选定路径建索引后做范围查询。
- **预期**：**走索引**，结果与全表扫一致。

### REQ-CFG-008　配置记录的字段

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §6

#### 语义

配置记录包含 `config_id`、`revision`、`schema_id`、`payload`、`content_hash`、
`created_at` 及 `active` 状态。

#### 规格

| 字段 | 说明 |
| --- | --- |
| `config_id` | 配置的逻辑标识——**它在修订之间不变** ✓ |
| `revision` | 修订号——**同一 `config_id` 内单调递增** |
| `schema_id` | 模式版本（REQ-CFG-012） |
| `payload` | **JSON 值**（REQ-CFG-001 的表示） |
| `content_hash` | 对 `payload` 的**内容摘要**——用于比较与去重 |
| `created_at` | **时间点**——按 `CONV §2`，这是"何时发生"，故用 `TIMESTAMP_TZ` 或提交序号 |
| `active` | 活动状态——见 REQ-CFG-009 |

**`content_hash` 的用途要写清**：它是**比较用的**，**不是完整性校验** ✗——
完整性由页校验与 WAL 负责（§5.8）。**它不是安全边界** ✗（不防篡改）。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 缺任一必填字段 | 拒绝 |
| `content_hash` 与 `payload` 不符 | **拒绝写入**——两者由同一次操作产生，不符说明有缺陷 |

#### 验收要点

- **预期**：七个字段**完整可查**（REQ 的验收）。

### REQ-CFG-009　配置修订不可变

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §6

#### 语义

配置修订**不可变**；以**预期 revision** 执行**条件切换**；
**旧版本保留**，**回滚只切换活动引用**。

#### 规格

**§0.4 已经从这四条推出了形状。这里是操作规则：**

| 操作 | 做法 |
| --- | --- |
| **新建修订** | `INSERT` 一行，`revision = 当前 + 1` |
| **条件切换** | `UPDATE ... WHERE revision = :expected`——**CAS，不是读改写** ✓ |
| **回滚** | 把活动引用改回旧 `revision`——**不复制数据** ✓ |
| **删除** | 不提供——旧版本保留（否则回滚失去意义） |

**"不可变"如何强制**：**不提供 `UPDATE payload` 这条路径** ✓——
与 §13.7"用不提供实现禁止"同一条原则 ✓。
**比起一条"禁止修改"的检查，不提供更彻底** ✓。

**条件切换为什么必须是 CAS**：两个会话同时基于 revision 5 切换，
**只有一个能成** ✓；另一个的 `WHERE` 不匹配 → **0 行受影响 → 拒绝** ✓。
"读出来比一比再写"在两者之间留了窗口 ✗。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 并发条件更新冲突 | **被拒绝**（REQ 的验收）——受影响行数为 0 |
| 试图 `UPDATE` 已有修订的 `payload` | **不存在这条路径** |
| 切换到不存在的 revision | 拒绝 |

#### 验收要点

- **构造**：两个会话同时基于同一 revision 切换。
- **预期**：**只有一个成功**，另一个被拒且不产生中间状态。

### REQ-CFG-010　密钥使用引用

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §6

#### 语义

配置中的密钥使用**密钥引用**，**不得保存到普通 JSON 正文与日志**。

#### 规格

- 配置里存的是**引用**（指向外部密钥管理），**不是密钥本身** ✗；
- **不得进入的四处**：配置 `payload`、**redo 日志**、**undo**、**错误信息与审计** ✓；
- **这条的难点在处理路径而非存储路径** ✗：存储只要"不写就行"，
  而**报错时容易把值带进消息里** ✗——那是最常见的泄露点。

> **一条可检验的规则**：**任何错误路径都不得回显受影响的值的内容**。
> 这条与 REQ-ISO-006 的"拒绝时不得回显名称"是同一个形状 ✓——
> **在报错路径上，少说一句比多说一句安全。**

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 正文中出现疑似密钥 | **由上层检测**——存储层不做内容识别 |
| 错误消息含值的内容 | **缺陷** |

#### 验收要点

- **构造**：写入含密钥引用的配置，然后**制造各类错误**。
- **预期**：**日志与正文中都没有密钥明文**（REQ 的验收）。

---

### REQ-CFG-011　仅作为数据

**优先级**：必须　**阶段**：P2　**追溯**：总体方案 §6

#### 语义

工作流、工具参数、提示模板与模型配置**仅作为数据保存**；
**数据库不得据此自动加载代码或执行指令**。

#### 规格

**这条针对的是一类具体的误设计**：把工具定义存在库里，然后**按它去加载插件** ✗。
那样一来，**一次配置写入就变成了代码执行** ✗✗。

| | |
| --- | --- |
| **本库** | **只存、只取、只校验结构**——不知道字段的"含义" |
| **执行** | 在**上层**，且**必须由上层自己决定信任边界** |

**"不知道含义"是一件要守住的事**：一旦引擎开始"理解"某个字段
（比如看到 `"type": "http"` 就去联网），**数据与代码的边界就没了** ✗。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 配置内容触发任何加载或执行 | **缺陷**——本库**没有代码加载路径**（REQ 的验收） |

#### 验收要点

- **构造**：写入形似可执行内容的配置。
- **预期**：**没有任何加载或执行发生**；取出来**逐字节等于写进去的**。

### REQ-CFG-012　模式升级用版本化迁移

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §6

#### 语义

模式升级使用**版本化迁移**，**禁止后台无记录地改写已有配置**。

#### 规格

- 迁移是**一次显式、有记录的操作** ✓——**不是后台的静默改写** ✗；
- 迁移**产生新的修订**（REQ-CFG-009 的不可变因此不被破坏 ✓）——
  **改配置只能靠"加一个新修订"，不能靠"就地改旧修订"** ✓；
- **`schema_id` 随之变化**（REQ-CFG-008）——于是"这条修订是按哪个模式写的"可查 ✓。

**"后台无记录地改写"为什么必须禁止**：

> 它是**不可回滚、不可追溯**的 ✗。而配置的价值恰恰在于"**当时的配置是什么**"——
> 一个被静默改写的配置，让所有基于它的历史判断都失去依据 ✗。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 迁移未留记录 | **缺陷** |
| 迁移直接改旧修订 | **不存在这条路径**（REQ-CFG-009 的不可变） |

#### 验收要点

- **构造**：执行一次模式迁移。
- **预期**：**迁移有记录可追溯**（REQ 的验收）；**旧修订逐字节未变**。

## 待确认汇总（CFG 域）

### 已随本域定案

| 项 | 结论 |
| --- | --- |
| 内部表示 | **参照 PostgreSQL `jsonb`**：容器 + `JEntry` + 键集中的对象布局 |
| 偏移记法 | **全部记偏移**（不学它的"每 32 项一次偏移"折中——**那个折中的前提是通用压缩器，我们没有**） |
| 数值 | **就是 `NUMBER`**，十进制精确 |
| 三层"没有" | 字段缺失 / JSON `null` / SQL NULL **分属三层，天然不混** |
| 重复键 | **拒绝**（`jsonb` 是"后者胜"，我们换成拒绝——静默丢弃是"输入与存储不一致"） |
| 上限 | 深度 **32**、节点 **65536**、字节 **1MB**（与行片段链一致） |
| 局部修改 | **读改写整值**——换来 JSON 不开任何格式例外 |
| 索引 | **表达式 B+Tree**；"路径有限"是它能否存在的前提 |
| 配置形状 | **多行（每修订一行）+ 活动引用**；切换用 **CAS** |
