## 0 模型总述

### 0.1 先划三条边界——它们决定了取舍

2023 年以来的 Agent Memory 项目已经形成几条清晰路线（§0.2）。
**但我们的约束与它们几乎全都不同**，所以"优选"不是挑最好的，而是
**挑"与这三条边界相容"的**：

| # | 我们的边界 | 与主流项目的差别 |
| --- | --- | --- |
| **①** | **库内不跑 LLM**（REQ-MEM-010） | mem0 / PowerMem / Cognee / Zep **全都把 LLM 放进记忆层**——用它抽取事实、评估重要性、做反思、甚至改写已有记忆 |
| **②** | **每个工作区独立，不提供跨工作区原语**（§13.9） | PowerMem 的"**共享 = 检索时过滤，不复制记录**"在我们这里**不可能**——跨主体共享只能经 `public` |
| **③** | **多版本由数据模型层表达，存储层不做版本化**（§1.2、REQ-STO-014） | 多数项目把"记忆的版本"放在应用层或图里；我们要求它是**行**，且**明确不等于 Undo 快照**（REQ-MEM-006） |

> **第①条是最强的约束，也是最好的一条。**
>
> "什么值得记"是一个**判断**✗——而判断需要模型 ✗。
> **把判断留在上层、把载体与约束留给库**，换来三样东西：
> **可重复**（同一输入同一次判断）、**可审计**（谁在何时把它提升为长期是显式记录）、
> **不受污染**（一次 LLM 出错不会在库里留下"半改过的历史"）✗✓。
>
> A-MEM 的分析者已经指出了后者的代价（§0.2 的"已知缺陷"），
> **而我们是靠边界避免它，不是靠工程纪律。**

### 0.2 六条路线

| 路线 | 代表 | 核心机制 | 记忆模型 | **与我们的关系** |
| --- | --- | --- | --- | --- |
| **A. LLM 提取洞察 + 向量检索** | **mem0** | 后台 Memory Agent 抽取"事实/偏好"，与已有记忆比对后**合并/更新** | `{id, text, metadata, embedding, 时间戳}`；作用域 Application / Agent / Thread / User | **机制不能采纳**（库内无 LLM）；**"作用域分层"采纳**（→ 我们的 `scope` 字段与工作区边界） |
| **B. 认知科学 + 遗忘曲线** | **PowerMem**（OceanBase） | 重要性评估（LLM 六维 + 规则回退）→ **艾宾浩斯衰减 `R = e^(−t/S)`** → 分级路由（长期 / 短期 / 遗忘） | 五层：User Profile / Private / Short-term / Long-term / Shared | **衰减采纳为"排序因子"**✓，**不采纳为"可见性规则"**✗（见 §0.3）；**"共享=过滤"不采纳**（第②条边界） |
| **C. LLM-as-OS，自管内存** | **Letta (MemGPT)** | 代理**自己管理**记忆层级；无 schema 的文本层 | 无知识图谱、无时间事实 | **不采纳**——无 schema 与我们的"可查询、可审计"相反 ✗ |
| **D. 双时态知识图谱** | **Zep / Graphiti** | 事实带 **`t_valid` / `t_invalid`**；embedding + BM25 + 图遍历；**保留被取代的事实以供审计** | 双时态 KG | **最优的一处对应**——REQ-MEM-008 与它同构；**"保留被取代的事实"与 REQ-MEM-006 同构** |
| **E. 图 / GraphRAG** | **Cognee** | ECL 管道抽取 S-R-O 三元组，建**类型化图**；图补全回答 | 类型化 KG | **骨架采纳**（关系显式化）；**抽取不采纳**（库内无 LLM）；与 `GRP` 域分工见 §0.4 |
| **F. 记忆流 + 反思** | **Stanford Generative Agents** | **检索 = recency × importance × relevance**（指数衰减 0.99）；**反思**在累积重要性过阈值时触发，生成更高层记忆 | 自然语言条目流 | **评分采纳**✓；**反思的"触发"不采纳**（那是 LLM 判断）✗；**"反思产物也是记忆"采纳**✓ |
| **G. Zettelkasten 原子笔记 + 动态链接** | **A-MEM** | 原子笔记 `{内容, 时间戳, 关键词, 标签, 上下文, 嵌入, 链接}`；**链接由 LLM 判定**；**记忆演化**可改写旧笔记 | 活的笔记图 | **对象模型采纳**✓（对应我们的五个对象）；**"演化改写旧笔记"必须改为版本化取代**✗✓ |

#### 两处来自 A-MEM 的教训，我们已经在做

**A-MEM 的分析者自己指出的缺陷**，恰好指向我们已经定的两条：

> "**记忆演化**实际上在**改写旧笔记**；**没有版本化历史就难以调试、且可能不安全**——
> 建议实现为**版本化的取代/失效链，并带来源**，而不是**静默改写**。"

| 它建议的 | 我们已有的 |
| --- | --- |
| 版本化的取代链 | **REQ-MEM-006**：记忆更新产生**新业务 revision**，旧 revision 留存 |
| 带来源 | **REQ-MEM-004** 的 `source_record`；**REQ-MEM-010** 提升须提供来源 |
| 不静默改写 | **REQ-MEM-005** 的状态转换**保留操作者与原因** |

**这不是巧合**：它们的缺陷来自"让 LLM 改历史"✗，
而我们从一开始就把"改历史"换成了"加新版本"✓。

### 0.3 优选：取哪几部分，为什么

| 取自 | 是什么 | 为什么合适 |
| --- | --- | --- |
| **D（Zep / Graphiti）** | **双时态**：`valid_from` / `valid_to` 与实际记录时间分离 | **REQ-MEM-008 就是它**——事件时间、记录时间、生效区间三者分开保存 |
| **D** | **保留被取代的事实** | REQ-MEM-006 的"旧 revision 留存"+"可审计" |
| **G（A-MEM）** | **原子笔记的对象模型** | 对应 REQ-MEM-004 的 `memory` / `memory_version` |
| **F（Generative Agents）** | **`recency` / `importance` / `relevance` 三个排序因子** | 一个经过验证的检索打分骨架，且**三个因子都能由我们现成的结构算出来**（见下） |
| **B（PowerMem）** | **衰减作为排序因子** | 采纳"越久未用越靠后"，**但不采纳"越久越不可见"** ✗ |
| **E（Cognee）** | **关系显式化**（不把关系藏在嵌入里） | `derived_link` + 邻接页（§9.2） |

#### 三处明确不采纳，以及为什么

| 不采纳 | 来自 | 理由 |
| --- | --- | --- |
| **库内 LLM 判断"什么值得记"** | A、B、E | **REQ-MEM-010 明文禁止**。判断在上层，库只记"谁在何时把哪条提升为长期" |
| **衰减作为可见性规则**（越久越不可见） | B | **可见性必须是确定的** ✗✓。衰减是**启发式** ✗——把它接进可见性，会让"同样的查询在不同的时刻结果不同"✗，而**这是最难排查的一类问题** ✓。**衰减只影响排序** ✓ |
| **"共享 = 检索时过滤"** | B | 第②条边界。**架构上不存在跨工作区的结构** ✗✓（REQ-RET-011）——共享只能经 `public`，且**经过滤层**（§13.5） |

#### 三个排序因子，我们各自从哪来

**Generative Agents 用 LLM 算 `importance`** ✗——**我们不能**。但三个因子在库里都有确定的来源：

| 因子 | 我们怎么得到 |
| --- | --- |
| **`recency`** | **`last_accessed` 时间戳**（对应 GA 的 `last_retrieved`）✗——**它是一个字段，不是计算** ✓ |
| **`importance`** | **上次调用方写入的分数**（`confidence` / 显式重要性）✗——**它是数据，不是判断** ✓（REQ-MEM-007） |
| **`relevance`** | **向量距离**（`RET` 域）✓ |

**关键在于后两个是"记录下来的判断"，不是"库里做的判断"** ✓✓——
**库不产生它们，只保存和使用它们** ✓。这与 REQ-MEM-007 是同一条：
"**confidence 仅作为数据，不得自动代表正确性**" ✓。

> **并因此：三个因子只影响排序，不影响可见性** ✗✓。
> 是否可见由 **`status` + TTL**（REQ-MEM-011/012）决定，两者是**正交的** ✓——
> **一条 `confirmed` 但久未访问的记忆，排序靠后，但依然可见** ✓。

### 0.4 对象模型

**REQ-MEM-004 的五个对象**，以及它们各自对应哪条路线的哪个概念：

| 对象 | 是什么 | 对应 |
| --- | --- | --- |
| **`memory`** | 一条**逻辑记忆**（身份）——**它在各版本之间不变** | A-MEM 的"笔记身份" |
| **`memory_version`** | 该记忆的**某一版内容**——**不可变** | Zep 的"事实"，带双时态 |
| **`task_checkpoint`** | 中期记忆：任务目标、检查点、阶段结论、工具结果引用、待办与恢复游标 | B 的"短期层"，但**有结构** ✓ |
| **`source_record`** | 来源记录——含**撤销** | D 的 provenance |
| **`derived_link`** | 记忆之间的关系 | G 的"链接"、E 的"三元组" |

#### `memory` 与 `memory_version` 分开，与 `CFG` 的配置是同一个形状

| | `CFG` | **`MEM`** |
| --- | --- | --- |
| 逻辑标识 | `config_id` | **`memory_id`** |
| 不可变的修订 | 每修订一行 | **每修订一行** |
| 活动引用 | 切换活动引用 | **`active_revision`** |
| 回滚 | 只切引用 | **只切引用** |

**同一个形状解决两个问题**——这是"用同一套机制解决新问题"的又一例 ✓。
**它带来的性质也一样**：回滚不复制数据、历史不丢、并发用 CAS 切引用 ✓。

#### `derived_link` 同时是"图的边"的候选

**REQ-MEM-009 的 `conflicts_with` 就是一条 `derived_link`** ✓。

而 §9.2 给图表（GRP 域）配了**邻接页**（按 `src` 聚簇、一次范围读一跳出边）✓——
**两者是不是同一张图，是 `GRP` 域要定的边界** ✓：
若"记忆之间的关系"就是图的边，则**邻接页直接服务 `derived_link`** ✓；
若 `GRP` 的图是"实体关系"（记忆**提到**的实体，而非记忆本身），
则两者并存、各有各的存储 ✓。**记入待确认汇总。**

### REQ-MEM-001　中期记忆：围绕任务与会话

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

中期记忆围绕**任务与会话**：**任务目标、检查点、阶段结论、工具结果引用、待办及恢复游标**。

#### 规格

**这个列表决定了 `task_checkpoint` 的字段——它是"可恢复的执行状态"，不是"对话记录"** ✗✓：

| 字段 | 作用 |
| --- | --- |
| **任务目标** | 这件事要做什么——**恢复时要靠它重建意图** |
| **检查点** | 推进到哪一步（有序） |
| **阶段结论** | 已完成部分的**结论**（不是原始轨迹）✓ |
| **工具结果引用** | **引用**，不是结果本身 ✗——大结果在 `AST` 域或 `source_record` |
| **待办** | 还没做的 |
| **恢复游标** | **从哪继续** |

**"引用而非结果"是关键的一处** ✗✓：工具结果可能很大（一次检索、一个文件），
**把它塞进检查点会让检查点本身变成大对象** ✗。
检查点要的是**小而能恢复** ✓。

**"恢复游标"是这一条区别于"聊天历史"的地方** ✓：
它要求这一组字段能**独立支撑一次恢复**——不依赖会话上下文 ✗。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 检查点缺恢复游标 | **允许**（任务还没开始执行），但"可恢复"不成立 |
| 工具结果引用指向已撤销的来源 | **该检查点的恢复应能察觉**（REQ-MEM-013） |

#### 验收要点

- **构造**：中途中断一个任务，用检查点恢复。
- **预期**：**能恢复到中断点**，且不依赖会话原文。

### REQ-MEM-002　长期记忆：强调来源、时间、版本与可遗忘性

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

长期记忆保存**确认事实、偏好、经验、知识片段及实体关系**，
强调**来源、有效时间、版本与可遗忘性**。

#### 规格

**四类内容，与四个强调项是两组东西**：

| 内容 | 落到哪 |
| --- | --- |
| 确认事实 / 偏好 | `memory_version.content`（JSON，`CFG` 的表示） |
| 经验 | 同上——**经验通常带情境，故更依赖 `source_record`** |
| 知识片段 | 同上 + **向量**（`RET`） |
| **实体关系** | **`derived_link`**（或 `GRP` 域，见 §0.4） |

| 强调项 | 落成什么 |
| --- | --- |
| **来源** | `source_record`（REQ-MEM-010 要求提升时提供） |
| **有效时间** | `valid_from` / `valid_to`（REQ-MEM-008） |
| **版本** | `memory_version.revision`（REQ-MEM-006） |
| **可遗忘性** | `status` 的 `expired` / `deleted` + **TTL**（REQ-MEM-012） |

**"可遗忘"要能真的忘掉** ✗✓——所以它不是"标记一下不返回" ✗（那是可见性），
而是**最终能从介质上消失** ✓——**但 REQ-MEM-014 会说明它止步在哪** ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 无来源的长期记忆 | **允许写入但状态只能是 `candidate`**——见 REQ-MEM-010 |
| 已过 `valid_to` 的事实 | **仍然可见**（它是"当时为真"的记录）✗✓——**除非状态另有变化** |

**第二行需要强调**：`valid_to` 过期不等于 `expired` ✗✓——
前者是**事实的有效区间**（历史属性）✓，后者是**记忆的生命周期**（管理属性）✓。
**两者可以独立变化** ✓。

#### 验收要点

- **预期**：四类内容可存；四个强调项**都可判定**。

### REQ-MEM-003　中期与长期共享底层事务

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

中期与长期**共享底层事务**，**生命周期由独立业务字段表达**。

#### 规格

**这条排除了一个很自然的误设计：把中期与长期做成两张表或两个库** ✗。

| | 分成两套 ✗ | **共享事务（采用）** ✓ |
| --- | --- | --- |
| 一件事跨中期与长期 | **无法原子**✗ | 一个事务 ✓ |
| 索引 / 检索 | 两套 ✗ | 一套，**按字段过滤** ✓ |
| 生命周期 | 两套规则 ✗ | **`status` + TTL 字段** ✓ |

**"生命周期由独立业务字段表达"** = **不是靠"在哪张表"来区分** ✓，
而是靠 **`kind` / `status` / TTL 这些字段** ✓。

**这条与 §0.1 第③条同源**：存储层不做版本化、不做分层 ✗——
**分层是数据模型的事，表达为字段** ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 一次操作同时改中期与长期记忆 | **同一事务内完成** |
| 提升（中期 → 长期） | **是一次字段变更，不是一次"搬家"** ✓ |

#### 验收要点

- **构造**：一个事务内写中期与长期各一条。
- **预期**：**原子生效或原子回滚**。

### REQ-MEM-004　五个对象

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

提供 `memory`、`memory_version`、`task_checkpoint`、`source_record`、`derived_link` 对象。

#### 规格

**形状见 §0.4。这里补字段层面的规定。**

| 对象 | 键 | 要点 |
| --- | --- | --- |
| `memory` | `memory_id`（UUID） | **逻辑身份**，跨版本不变；含 `status`、`active_revision`、`kind`、TTL 字段 |
| `memory_version` | `(memory_id, revision)` | **不可变**；含 `content`、双时态四字段、`confidence`、来源引用、**操作者与原因** |
| `task_checkpoint` | `(task_id, checkpoint_seq)` | REQ-MEM-001 的六个字段 |
| `source_record` | `source_id`（UUID） | 含 `revoked_at`（REQ-MEM-013） |
| `derived_link` | `(from, relation, to)` | 含 `relation` 区分 `conflicts_with` / `supersedes` / `derived_from` |

**`memory_version` 的四个时间字段放在同一处，这是 REQ-MEM-008 的落点** ✓：

| 字段 | 含义 |
| --- | --- |
| `event_time` | **事件何时发生** |
| `record_time` | **我们何时记下它** |
| `valid_from` | 该事实**从何时起为真** |
| `valid_to` | 该事实**到何时为止为真**（可空 = 至今） |

**它们四个可以两两不等** ✗✓——**这正是把它们分开的理由** ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| `record_time` < `event_time` | **允许**（补记）——但**必须保留两者的差**，不做归一 ✗ |
| `valid_to` < `valid_from` | **拒绝** |

#### 验收要点

- **预期**：五个对象**齐备**，字段完整可查。

### REQ-MEM-005　状态机与转换留痕

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

状态**至少**包含 `candidate`、`confirmed`、`superseded`、`expired`、`deleted`；
**转换保留操作者与原因**。

#### 规格

```text
candidate ──确认──▶ confirmed ──被新版本取代──▶ superseded
    │                   │
    └──拒绝/丢弃──┐      └──TTL 到期──▶ expired
                  ▼                        │
               deleted ◀───────────────────┘
                  │
                  └──（异步清理）──▶ 物理删除
```

| 状态 | 含义 | 检索可见？（REQ-MEM-011） |
| --- | --- | --- |
| `candidate` | **生成物，未经确认** | **默认可见**，但**必须能区分**（REQ-MEM-007）✗ |
| `confirmed` | 已确认 | 可见 |
| `superseded` | 被新版本取代 | **默认不可见**——但**行还在**（REQ-MEM-006） |
| `expired` | TTL 到期 | **默认排除**（REQ-MEM-011） |
| `deleted` | 已删除（逻辑） | **默认排除** |

**转换留痕的落点**：**每次转换写一个新的 `memory_version`** ✓——
而不是更新 `memory` 行上的一个"谁改的"字段 ✗✓。
**因为"谁在何时、为什么把它确认了"本身是一条要保留的历史** ✓
（与 REQ-MEM-006 同一条理由）✓。

> **`candidate` 默认可见是一个需要明说的选择** ✗✓。
> 另一种做法是"默认只返回 `confirmed`"——**那更安全，但也更保守** ✗：
> 上层刚写入的生成物立刻查不到，会把"写入-检索"的基本用法堵死 ✗。
> **选择"可见但可区分"** ✓——**把判断留给调用方** ✓，
> 这与 REQ-MEM-007"confidence 仅是数据"是同一个姿态 ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 从 `deleted` 回到 `confirmed` | **不存在这条路径** ✓——删除是单向的 |
| 未经 `candidate` 直接 `confirmed` | **允许**（用户直接确认的事实）✓ |
| 转换未记操作者或原因 | **缺陷** |

#### 验收要点

- **构造**：走遍每条转换。
- **预期**：**状态流转可审计**（REQ 的验收）——每次转换的操作者与原因可查。

### REQ-MEM-006　业务版本 ≠ Undo 快照

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

记忆更新产生**新业务 revision**，旧 revision **按保留策略留存**；
**该版本不等于 Undo 快照**。

#### 规格

**这条在防一个概念混淆，而且方向必须说清**：

| | **业务 revision**（`memory_version`） | **Undo**（§4.6） |
| --- | --- | --- |
| 是什么 | **数据模型层的版本**——业务上"这条记忆的第 3 版" | **存储层的机制**——用于回滚与一致性读 |
| 存活多久 | **按保留策略**——可能很久 ✓ | **由最老快照封顶**——可能很短 ✗ |
| 谁能看见 | **业务查询可见** ✓ | **业务不可见** ✗——它是实现细节 |
| 谁产生 | **上层显式调用** | **任何一次写**，自动 |
| 是不是一回事 | **不是** ✗✓ | **不是** |

**最容易出的错是"用 Undo 当版本"** ✗：
它**看起来能省一张表** ✗，但 Undo 是**会消失的**（`commit_seq < 最老快照` 即回收，§4.6.5）✗✗——
**于是"第 3 版"会在某个时刻无声消失** ✗，而业务以为它会一直在 ✓。

**反过来也要防**：**不要因为业务要版本，就去改存储层** ✗✓——
**§1.2 已定"存储层不承载版本与事务语义"** ✓，`STO` 域亦有同名条目 ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 一致性读重建旧版本 | **走 Undo**（§12.3）——**与业务 revision 无关** |
| 业务查询历史版本 | **走 `memory_version`** |
| 旧 revision 被保留策略清理 | **允许**——但它是**显式策略**的结果，不是"悄悄消失" ✓ |

#### 验收要点

- **构造**：连续更新一条记忆多次，同时长事务读它。
- **预期**：**两条路各返回各自该给的版本**，互不干扰。

### REQ-MEM-007　生成物与确认事实必须区分

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

**生成记忆与用户确认事实必须区分**；**`confidence` 仅作为数据，不得自动代表正确性**。

#### 规格

**区分靠两个独立的东西，不是一个分数** ✗✓：

| 区分的维度 | 载体 |
| --- | --- |
| **来源**——它是生成的还是用户说的 | **`status`（`candidate` vs `confirmed`）+ `source_record`** |
| **把握**——生成物自己有多确信 | **`confidence`**（仅数据） |

**"`confidence` 不得自动代表正确性"的准确含义** ✗✓：

| 不成立 ✗ | 成立 ✓ |
| --- | --- |
| `confidence > 0.9` ⇒ 自动 `confirmed` | **`confidence` 不参与任何状态转换** ✗✓ |
| `confidence` 低 ⇒ 检索时排除 | **它只影响排序**（§0.3）✓ |
| `confidence` 可替代用户确认 | **确认只能由调用方显式调用**（REQ-MEM-010）✓ |

> **这三条是同一个意思：分数不能提权** ✗✓。
> 一旦"分高就自动确认"成立，**一次模型出错就变成一条"确认事实"** ✗，
> 而确认事实是有后果的 ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| `candidate` 与 `confirmed` 混在结果里且不可区分 | **缺陷** |
| 依据 `confidence` 自动转换状态 | **缺陷** |

#### 验收要点

- **构造**：一批 `candidate` 与 `confirmed`。
- **预期**：**两者可区分**；**状态不因分数变化**。

### REQ-MEM-008　三种时间分开保存

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

**事件时间、记录时间与事实生效区间分开保存**。

#### 规格

**这是本域取自 Zep / Graphiti 的双时态模型的那一条** ✓——四个字段见 REQ-MEM-004。

**为什么要分开** ✗——四个例子：

| 场景 | 三个时间的关系 |
| --- | --- |
| **补记**——今天记录昨天发生的事 | `record_time` > `event_time` |
| **预告**——记下一个将来生效的规则 | `valid_from` > `record_time` |
| **追溯修正**——新证据表明旧事实当时就不成立 | `valid_from` 早于 `record_time` ✗ |
| **废止**——事实曾经为真，现在不再为真 | **`valid_to` 有值，而 `record_time` 是废止的时刻** |

**第三行是双时态的价值所在** ✗✓：
"**我们当时以为它成立**"与"**它当时是否成立**"是**两个不同的事实** ✓——
把它们压成一个时间戳，**就无法同时表达"我们曾经错了"和"现在纠正了"** ✗✓。

**查询因此可以问两个不同的问题** ✓：

| 问题 | 用哪个时间 |
| --- | --- |
| "**当时我们记的是什么**" | `record_time` |
| "**事情当时是怎样的**" | `event_time` / `valid_from`/`valid_to` |

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 只填 `record_time`，其余留空 | **允许**——但**不能把它们互相填充** ✗✓ |
| `valid_to` 早于 `valid_from` | 拒绝 |

> **"不能互相填充"要写成规定** ✗✓：实现里最自然的动作是"没给 `event_time` 就用
> `record_time` 顶上" ✗——**那会让"我们从不知道它何时发生"与
> "它就发生在记录的时刻"变得不可区分** ✓。

#### 验收要点

- **构造**：上述四种场景各一组。
- **预期**：**三种时间分别可查、可比较**；**未填的保持为空**。

### REQ-MEM-009　冲突并存

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

允许两条**冲突记忆并存**并建立 `conflicts_with` 关系；
**不得以最新写入覆盖全部历史**。

#### 规格

**"并存"是一个反直觉的选择，理由必须写清** ✗✓：

| | 后写覆盖（常见做法）✗ | **并存 + `conflicts_with`（采用）** ✓ |
| --- | --- | --- |
| 冲突 | 消失 ✗ | **保留** ✓ |
| "为什么改了主意" | 不可查 ✗ | **可查** ✓ |
| 谁是当前结论 | 唯一的最后一条 | **需要判定** ✗ |

**第三条是代价** ✗✓：并存之后，"当前该信哪条"不再由写入顺序决定 ✗。
**解法是把判定显式化** ✓——用 `status` 与 `active_revision`，
**而不是用"谁最后写"** ✓（那正是 REQ-MEM-006 的版本化）。

**加上双时态，冲突就有了时间轴** ✓：
两条记忆的 `valid_from`/`valid_to` **可能只在某一段区间重叠** ✗——
**"它们冲突"因此可以是一个关于区间的事实** ✓，而不只是一个标记 ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 两条 `confirmed` 记忆互相冲突且区间重叠 | **允许**——这是数据，不是错误 |
| 用"最后写入"隐式地决定当前结论 | **缺陷** |

#### 验收要点

- **构造**：写入两条冲突记忆。
- **预期**：**两条都在**，`conflicts_with` 可查；历史未被覆盖。

中期提升为长期由**上层明确调用**并提供**来源**；

- **预期**：提升**可追溯**；**库内无 LLM 调用**。

**这条把"过期"定义成一个可见性问题，而不是一个清理任务** ✗✓：

| --- | --- | --- |

| 清理延迟 | **不影响结果** ✓ | **直接影响** ✗——清理没跑完，过期数据还在返回 |
| 长事务 | **见下** | — |

**"后台清理可以延迟"因此是免费的** ✓：
清理只影响**空间**，**不影响正确性** ✓。

**所以"过期"应当与快照同时确定** ✓。

> 而"查询时刻"在 RC 下**就是该语句取快照的时刻** ✓✓。

| 情形 | 行为 |
| --- | --- |
| 清理任务未跑 | **不影响可见性**——过期的已经不返回 |
| 长事务内 TTL 到期 | **按该语句的快照时刻判定** |
| 时间基准 | **P0 固定**（`CONV §2` 要求） |

#### 验收要点

- **构造**：TTL 到期的边界，跨一个长事务。
- **预期**：**过期即不可见**，与清理任务是否跑过无关；长事务内**视角一致**。

### REQ-MEM-013　撤销：同步阻止，异步清理

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

撤销记忆时**同步阻止其派生物继续返回**，再**异步清理**实体文件与索引。

**"同步 / 异步"的分工是这一条的全部内容** ✗✓：

| 阶段 | 做什么 | 何时 |
| --- | --- | --- |

| 情形 | 行为 |

| 撤销后派生物仍被返回 | **缺陷**——REQ-RET-012/024 的"已撤销来源不得返回" |
| 清理失败或延迟 | **允许**——可见性已由判定保证 ✓ |

#### 验收要点

- **构造**：检索后撤销来源，再检索（与 REQ-RET-012 同一用例）。
- **预期**：**撤销后不返回**——**在清理任务未运行的前提下** ✓。

### REQ-MEM-015　`public` 内容可共享但不自动可信

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

`public` 内容**可共享但不自动可信**；
**检索内容不能改变认证、执行权限与系统指令**。

#### 规格

**这是本域的安全核心，它防的是一类具体的攻击** ✗✓：

```text
不可信内容（public 里别人发布的一段文字）
   → 被检索出来
      → 进入模型的上下文
         → 【不能】改变：认证、执行权限、系统指令   ✗✗
```

**"检索内容不能改变"是三条禁令**：

| 不得被内容改变的 | 为什么 |
| --- | --- |
| **认证** | 内容不能成为身份的来源 ✗ |
| **执行权限** | 内容不能授权任何操作 ✗ |
| **系统指令** | **内容与指令必须分层** ✗✓——这是 prompt injection 的定义 |

**这一条的落点其实是"分层"，不是一个检查** ✗✓：

| 层 | 来源 | 可信度 |
| --- | --- | --- |
| **指令层** | 系统 / 调用方 | 可信 |
| **数据层** | **检索结果、`public` 内容、记忆内容** | **一律不可信** ✗ |

**"可共享但不自动可信"正是这个分层的一句话表述** ✓：
共享解决的是**可达性** ✗，可信解决的是**来源** ✗——**两者无关** ✓✓。

> **与 `CFG` REQ-CFG-011 是同一件事的两面** ✓：
> CFG 说"配置仅作为数据，库不得据此加载代码或执行指令"；
> MEM 说"检索内容仅作为数据，不得改变认证、权限与指令"。
> **同一条原则在两个域落成两条需求** ✓——**这不是重复，是它在两处的具体形态不同** ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 检索结果中出现形似指令的内容 | **它仍然是数据** ✓——**引擎不解释它** |
| 库据此改变任何权限判定 | **缺陷** |

#### 验收要点

- **构造**：在 `public` 发布形似指令的内容，再检索它。
- **预期**：**检索结果无法影响权限判定与系统指令**（REQ 的验收）。
