## 0 模型总述

### 0.1 先划三条边界——它们决定了取舍

2023 年以来的 Agent Memory 项目已经形成几条清晰路线（§0.2）。
**但我们的约束与它们几乎全都不同**，所以"优选"不是挑最好的，而是
**挑"与这三条边界相容"的**：

| # | 我们的边界 | 与主流项目的差别 |
| --- | --- | --- |
| **①** | **非确定性的判断不进库**（REQ-MEM-010） | mem0 / PowerMem / Cognee / Zep **全都把 LLM 放进记忆层**——用它抽取事实、评估重要性、做反思、甚至改写已有记忆。**注意：这不是"库内不跑模型"——嵌入早就在我们的派生管道里**（§8.1 的 `embed` 选项），见下 |
| **②** | **每个工作区独立，不提供跨工作区原语**（§13.9） | PowerMem 的"**共享 = 检索时过滤，不复制记录**"在我们这里**不可能**——跨主体共享只能经 `public` |
| **③** | **多版本由数据模型层表达，存储层不做版本化**（§1.2、REQ-STO-014） | 多数项目把"记忆的版本"放在应用层或图里；我们要求它是**行**，且**明确不等于 Undo 快照**（REQ-MEM-006） |

> **第①条的准确表述是——分界不在"LLM 与否"，在"确定性"。**
>
> 本设计**早就在派生管道里跑模型** ✗✓：§8.1 的 **`embed : none | async`**——
> "向量自动派生"——**派生向量必须调用嵌入模型** ✓。**模型调用不是要不要的问题，是放在哪的问题。**
>
> | | 例 | 进不进派生管道 |
> | --- | --- | --- |
> | **确定性**的模型调用 | **嵌入**（同模型同输入同输出）✓ | **不必留痕**——**可重建** ✓✓ |
> | **非确定性**的生成与判断 | 抽取、评估、合并、反思 ✗ | **必须留痕**（出处 + 操作者 + 原因）✓ |
>
> **判据是"能不能重建"** ✗✓：
> 可重建的（嵌入）失败就重算 ✓，**不必留痕**；
> **不可重建的（判断）必须记下"谁在何时凭什么做的"** ✓——
> **否则历史无法复现** ✗，而**这正是 A-MEM 踩的坑** ✓（§0.2）。
>
> **注意这条判据的范围** ✗✓：它管的是**留痕**，**不是"能不能进后台"** ✓。
> **两者都能进后台**——引擎的可选应用级后台任务（存储架构 §11.7）
> 同时承载嵌入与提取 ✓，差别只在**产出要不要带出处** ✓。
>
> 所以第①条买到的三样东西是：**可重复**（判断有明确的调用与记录）、
> **可审计**（提升是显式动作）、**不受污染**（判断不会在库里留下"半改过的历史"）✓。
> **而我们是靠这条边界避免它，不是靠工程纪律。**

### 0.2 六条路线

| 路线 | 代表 | 核心机制 | 记忆模型 | **与我们的关系** |
| --- | --- | --- | --- | --- |
| **A. LLM 提取洞察 + 向量检索** | **mem0** | 后台 Memory Agent 抽取"事实/偏好"，与已有记忆比对后**合并/更新** | `{id, text, metadata, embedding, 时间戳}`；作用域 Application / Agent / Thread / User | **机制不能采纳**（库内无 LLM）；**"作用域分层"采纳**（→ 我们的 `scope` 字段与工作区边界） |
| **B. 认知科学 + 遗忘曲线** | **PowerMem**（OceanBase） | 重要性评估（LLM 六维 + 规则回退）→ **艾宾浩斯衰减 `R = e^(−t/S)`** → 分级路由（长期 / 短期 / 遗忘） | 五层：User Profile / Private / Short-term / Long-term / Shared | **衰减采纳为"排序因子"**✓，**不采纳为"可见性规则"**✗（见 §0.3）；**"共享=过滤"不采纳**（第②条边界） |
| **C. LLM-as-OS，自管内存** | **Letta (MemGPT)** | 代理**自己管理**记忆层级；无 schema 的文本层 | 无知识图谱、无时间事实 | **不采纳**——无 schema 与我们的"可查询、可审计"相反 ✗ |
| **D. 双时态知识图谱** | **Zep / Graphiti** | 事实带 **`t_valid` / `t_invalid`**；embedding + BM25 + 图遍历；**保留被取代的事实以供审计** | 双时态 KG | **最优的一处对应**——REQ-MEM-008 与它同构；**"保留被取代的事实"与 REQ-MEM-006 同构** |
| **E. 图 / GraphRAG** | **Cognee** | ECL 管道抽取 S-R-O 三元组，建**类型化图**；图补全回答 | 类型化 KG | **骨架采纳**（关系显式化）；**抽取不采纳**（库内无 LLM）；与 `GRP` 域分工见 §0.4 |
| **F. 记忆流 + 反思** | **Stanford Generative Agents** | **检索 = recency × importance × relevance**（指数衰减 0.99）；**反思**在累积重要性过阈值时触发，生成更高层记忆 | 自然语言条目流 | **评分采纳**✓；**反思的"触发"不采纳**（那是 LLM 判断）✗；**"反思产物也是记忆"采纳**✓ |
| **G. Zettelkasten 原子笔记 + 动态链接** | **A-MEM** | 原子笔记 `{内容, 时间戳, 关键词, 标签, 上下文, 嵌入, 链接}`；**链接由 LLM 判定**；**记忆演化**可改写旧笔记 | 活的笔记图 | **对象模型采纳**✓（对应我们的五个对象）；**"演化改写旧笔记"必须改为版本化取代**✗✓ |

#### 两处来自 A-MEM 的教训，我们已经在做

**A-MEM 的分析者自己指出的缺陷**，恰好指向我们已经定的两条：

> "**记忆演化**实际上在**改写旧笔记**；**没有版本化历史就难以调试、且可能不安全**——
> 建议实现为**版本化的取代/失效链，并带来源**，而不是**静默改写**。"

| 它建议的 | 我们已有的 |
| --- | --- |
| 版本化的取代链 | **REQ-MEM-006**：记忆更新产生**新业务 revision**，旧 revision 留存 |
| 带来源 | **REQ-MEM-004** 的 `source_record`；**REQ-MEM-010** 提升须提供来源 |
| 不静默改写 | **REQ-MEM-005** 的状态转换**保留操作者与原因** |

**这不是巧合**：它们的缺陷来自"让 LLM 改历史"✗，
而我们从一开始就把"改历史"换成了"加新版本"✓。

### 0.3 优选：取哪几部分，为什么

| 取自 | 是什么 | 为什么合适 |
| --- | --- | --- |
| **D（Zep / Graphiti）** | **双时态**：`valid_from` / `valid_to` 与实际记录时间分离 | **REQ-MEM-008 就是它**——事件时间、记录时间、生效区间三者分开保存 |
| **D** | **保留被取代的事实** | REQ-MEM-006 的"旧 revision 留存"+"可审计" |
| **G（A-MEM）** | **原子笔记的对象模型** | 对应 REQ-MEM-004 的 `memory` / `memory_version` |
| **F（Generative Agents）** | **`recency` / `importance` / `relevance` 三个排序因子** | 一个经过验证的检索打分骨架，且**三个因子都能由我们现成的结构算出来**（见下） |
| **B（PowerMem）** | **衰减作为排序因子** | 采纳"越久未用越靠后"，**但不采纳"越久越不可见"** ✗ |
| **E（Cognee）** | **关系显式化**（不把关系藏在嵌入里） | `derived_link` + 邻接页（§9.2） |

#### 三处明确不采纳，以及为什么

| 不采纳 | 来自 | 理由 |
| --- | --- | --- |
| **库内 LLM 判断"什么值得记"** | A、B、E | **REQ-MEM-010 明文禁止**。判断在上层，库只记"谁在何时把哪条提升为长期" |
| **衰减作为可见性规则**（越久越不可见） | B | **可见性必须是确定的** ✗✓。衰减是**启发式** ✗——把它接进可见性，会让"同样的查询在不同的时刻结果不同"✗，而**这是最难排查的一类问题** ✓。**衰减只影响排序** ✓ |
| **"共享 = 检索时过滤"** | B | 第②条边界。**架构上不存在跨工作区的结构** ✗✓（REQ-RET-011）——共享只能经 `public`，且**经过滤层**（§13.5） |

#### 三个排序因子，我们各自从哪来

**Generative Agents 用 LLM 算 `importance`** ✗——**我们不能**。但三个因子在库里都有确定的来源：

| 因子 | 我们怎么得到 |
| --- | --- |
| **`recency`** | **`last_accessed` 时间戳**（对应 GA 的 `last_retrieved`）——**它是一个字段，不是判断** ✓。**但它的更新路径有硬约束，见下** ✗ |
| **`importance`** | **上次调用方写入的分数**（`confidence` / 显式重要性）——**它是数据，不是判断** ✓（REQ-MEM-007） |
| **`relevance`** | **向量距离**（`RET` 域）✓ |

#### `recency` 的更新路径：它不能是"每次检索写一次"

Generative Agents 的 `last_retrieved` **每次检索都更新** ✗——**照搬到我们这里会撞上一条已定的原则**：

> **读路径不得产生同步写**（§8：`stat$` 的"计数在内存累积后定期刷入"就是为它立的）。

**所以 `last_accessed` 必须走与 `stat$.access_cnt` 完全相同的路** ✓：

| | |
| --- | --- |
| 更新时机 | **内存累积，定期刷入** ✓——不是每次检索 ✗ |
| 崩溃后 | **丢的是访问时间，不是数据** ✓ |
| 因此 | **`recency` 是近似的** ✗ |

**这个近似可以接受，而理由与 §0.3 是同一条** ✓✓：
**`recency` 只影响排序、不影响可见性** ✓——
**一条记忆不会因为"访问时间没刷准"而变得可见或不可见** ✓。

> **两条结论互相印证**：正因为排序与可见性正交（§0.3），
> 才容得下"排序因子可以是近似的"✓；反过来，
> 若当初让衰减参与可见性，这里就只能同步写 ✗——**两个选择是有牵连的** ✓。

**关键在于后两个是"记录下来的判断"，不是"库里做的判断"** ✓✓——
**库不产生它们，只保存和使用它们** ✓。这与 REQ-MEM-007 是同一条：
"**confidence 仅作为数据，不得自动代表正确性**" ✓。

> **并因此：三个因子只影响排序，不影响可见性** ✗✓。
> 是否可见由 **`status` + TTL**（REQ-MEM-011/012）决定，两者是**正交的** ✓——
> **一条 `confirmed` 但久未访问的记忆，排序靠后，但依然可见** ✓。

### 0.4 对象模型

**REQ-MEM-004 的五个对象**，以及它们各自对应哪条路线的哪个概念：

| 对象 | 是什么 | 对应 |
| --- | --- | --- |
| **`memory`** | 一条**逻辑记忆**（身份）——**它在各版本之间不变** | A-MEM 的"笔记身份" |
| **`memory_version`** | 该记忆的**某一版内容**——**不可变** | Zep 的"事实"，带双时态 |
| **`task_checkpoint`** | 中期记忆：任务目标、检查点、阶段结论、工具结果引用、待办与恢复游标 | B 的"短期层"，但**有结构** ✓。**它是"不可丢的恢复点"**——与**可丢的对话原文**（会话表，`logging = none`）分属两处，见存储架构 §8.2 |
| **`source_record`** | 来源记录——含**撤销** | D 的 provenance |
| **`derived_link`** | 记忆之间的关系 | G 的"链接"、E 的"三元组" |

#### `memory` 与 `memory_version` 分开，与 `CFG` 的配置是同一个形状

| | `CFG` | **`MEM`** |
| --- | --- | --- |
| 逻辑标识 | `config_id` | **`memory_id`** |
| 不可变的修订 | 每修订一行 | **每修订一行** |
| 活动引用 | 切换活动引用 | **`active_revision`** |
| 回滚 | 只切引用 | **只切引用** |

**同一个形状解决两个问题**——这是"用同一套机制解决新问题"的又一例 ✓。
**它带来的性质也一样**：回滚不复制数据、历史不丢、并发用 CAS 切引用 ✓。

#### 内容与它的派生：JSON 是权威，向量是派生

**一条记忆存三样东西，但只有一样是权威** ✗✓：

| | 是什么 | 权威？ | 可丢？ |
| --- | --- | --- | --- |
| **`memory_version.content`** | **JSON**（`CFG` 的表示） | **权威** ✓ | ✗——丢了就是丢了 |
| **向量**（`memory_embedding`） | 对**选定路径**的嵌入 | 派生 ✗ | **可以**——重建即可 ✓ |
| **全文索引** | 倒排 | 派生 ✗ | 同上 ✓ |

**为什么不能只存向量** ✗：向量是**有损投影** ✓——
换模型**无法重建**（原文没了）✗、拿不出**证据片段**（REQ-RET-010）✗、
不可审计"为什么检索到它" ✗。

**为什么不能只存文本** ✗：检索会退化成全表扫 ✗——
而 §1.3 的画像里向量数据可达 60GB，**每次查询现算嵌入不可行** ✓。

#### 向量不是"列"，是伴随结构

**`REQ-RET-018` 要求模型升级时"新建向量空间并切换活动引用"** ✓——
**这意味着同一份内容可以有多个向量**（旧模型一份、新模型一份）✗。
**向量一旦是列，就装不下第二份** ✗✗。

```text
memory_version.content     ← 权威（JSON）
memory_embedding           ← 派生：
                              (memory_id, revision, 路径, model, model_revision,
                               dimension, metric, normalization, 向量)
```

**它是派生结构，不是业务对象** ✓✓——
所以 **REQ-MEM-004 的五个业务对象一个都不用加** ✓，
而它可以**随时丢弃与重建** ✓。

**`REQ-RET-018` 的"新建向量空间"就落成"新的 `(model, model_revision)` 组"** ✓。

#### 向量的粒度 = 表达式路径的粒度

**整条记忆一个向量会把长内容平均掉** ✗✓——嵌入会把"标题"和"正文的三百字"
混成一个点 ✓。
**所以对选定路径各建一个向量** ✓——**与 `REQ-CFG-007` 的"选定路径的表达式索引"
是同一个概念、两处用** ✓✓。

#### 与 `REQ-RET-020` 的"原始向量是权威"不是一回事

| | 谁 | 权威？ |
| --- | --- | --- |
| **用户的 `VECTOR` 列** | 调用方显式存入的向量（他自己算的） | **权威** ✓（REQ-RET-020） |
| **记忆内容的嵌入** | 本库按 `embed` 选项派生 | **派生** ✗ |

**两者形状相同、地位相反** ✗✓——把它们混起来，会导致"重建索引用错数据源" ✓。

#### 异步窗口为什么是安全的

改了文本、向量还没重算的窗口里，**检索命中的是旧内容的向量** ✗——
但**回查会按 revision 校验**（REQ-RET-023）✓✓，**所以不会返回错的内容** ✓。

> **这正是"每个候选回查源 revision"最具体的价值** ✗✓：
> 它不是为了"更严谨"，而是**异步派生必然带来的窗口**所必需的 ✓。

#### 三层：权威 → 行级派生 → 集合级派生

把上面几处合起来看，**从内容到检索是一条三层的派生链** ✓：

```text
memory_version.content         权威        丢了就是丢了
      │  （embed: async，确定性、可重算）
      ▼
memory_embedding               行级派生     随行走；多模型可并存
      │  （构建索引）
      ▼
ANN 索引 / 倒排索引             集合级派生   有 generation + 源水位 + 完整性清单
```

**三层的"可重建性"逐层不同** ✗✓：

| 层 | 重建什么 | 触发 |
| --- | --- | --- |
| 内容 | —— | 不可重建 ✗——所以它是权威 ✓ |
| **行级派生** | **重算这一行的嵌入** | 换模型、内容变更、**嵌入失败重试** ✓ |
| **集合级派生** | **重建整个索引** | 索引损坏、退化、格式升级 ✓（`REQ-RET-022`） |

**两层的粒度不同，所以重建的代价与触发条件都不同** ✓——
**分清楚它们，才能回答"出问题时重建哪一层"** ✓。
（`REQ-RET-020` 的"索引损坏可重建"指的是第三层 ✓。）

#### `derived_link` 同时是"图的边"的候选

**REQ-MEM-009 的 `conflicts_with` 就是一条 `derived_link`** ✓。

而 §9.2 给图表（GRP 域）配了**邻接页**（按 `src` 聚簇、一次范围读一跳出边）✓——
**两者是不是同一张图，是 `GRP` 域要定的边界** ✓：
若"记忆之间的关系"就是图的边，则**邻接页直接服务 `derived_link`** ✓；
若 `GRP` 的图是"实体关系"（记忆**提到**的实体，而非记忆本身），
则两者并存、各有各的存储 ✓。**记入待确认汇总。**

### 0.5 底座的边界：能力归库，策略归 agent

**bicdb 为 Agent 专用。记忆的"管理"是 Agent 的事** ✗——**本库提供的是底座** ✓。

这句话可以直接变成一个**检验任何新功能的判据** ✗✓：

> **任何新功能先问：这是"能力"还是"策略"？**

| | 归谁 | 例 |
| --- | --- | --- |
| **能力** | **本库** ✓ | 存、查、关系、时间、版本、事务、过滤、幂等、混合检索、图扩展 |
| **策略** | **Agent** ✗ | 什么值得记、何时合并、何时反思、如何摘要、**如何装配上下文** |

**策略进库的代价是具体的** ✗：
它把 Agent 的判断藏进引擎里——**既不可审计**（看不出"谁决定把它记下来"）✓，
**也不可替换**（换一套记忆策略要改引擎）✗。

**判据的用法**：凡"库该不该做 X"的争论，先问 X 是能力还是策略 ✓。

#### 底座要"友好"，友好有七处可检验

| # | 友好在哪 | 本库 |
| --- | --- | --- |
| 1 | **一次调用拿到装配好的上下文** | 混合检索（`RET` REQ-RET-006）+ 图扩展 + 过滤 + 预算 ✓ |
| 2 | **幂等写入**（Agent 一定会重试） | `CONV §1.2` 已有 `idempotency_key` 概念 ✓——**`MEM` 要用上** |
| 3 | **"自上次以来发生了什么"** | 按 `record_time` / 提交序号顺序扫描 ✓ |
| 4 | **冲突与关系随结果一起返回** | `conflicts_with` 有，但**检索默认不返回** ✗ |
| 5 | **历史时点查询便宜且默认可用** | **见下——原先被我推后了** ✗✓ |
| 6 | **批量与原子** | 事务 ✓ |
| 7 | **用错会被拦住** | 跨模型混搜拒绝（REQ-RET-018）、`public` 写走标准接口（§13.6）✓ |
| 8 | **会话能自动变成记忆** | 见下——**引擎提供可选的提取后台**（配了才启、可重启、非关键），库另提供增量读、幂等与 `source_record` ✓ |

#### 会话 → 记忆：库提供入口，进程在库外

**"会话表里的数据由后台进程提取为记忆"** ✓——**它是引擎的一个可选后台任务**
（设计见存储架构 §11.7 的"另一类后台"）✓：

| | CKPT / 写线程 | **提取进程** |
| --- | --- | --- |
| 属于 | 存储层 ✓ | **语义层** ✗ |
| 会不会跑 | 总是在 ✓ | **配了才启，启不了就不启** ✗ |
| 调模型 | 不调 ✓ | **调** ✗ |
| **共同点** | **每工作区一份；可重启；只产出派生数据** ✓✓ | 同 ✓ |

**曾考虑过"库外进程"，被否掉了** ✗：它**很难标准化**——
每个使用方都要自己写一遍 ✓，**而"底座要友好"正要求它开箱可用** ✓。

**引擎提供的是"提取进程"这个能力** ✓；**"提取得对不对、提什么"在提示词与配置里** ✗——
**那才是策略，仍在调用方手里** ✓✓。

**"内建"与"同进程"是两件事** ✗✓：**归属在库内**（内建、有配置、库管启动与重启）✓，
而**进程可以是独立的、不与引擎同进程** ✓——理由有四条（模型依赖不该是引擎的依赖、
LLM 经常异常不该带倒引擎、资源隔离、可替换）。

**而独立进程带来一个关键性质**：它就是一个"**库自带的客户端**" ✓✓——
**用普通会话接口读写，没有特权通道** ✗✓。
**于是它受同一套隔离与事务约束，不会越权** ✓。
**"库自带"不等于"库内部"**：自带的是**能力与生命周期管理**，不是**特权** ✓。

**库为它提供三样** ✓：**增量读**（按水位）、**产出侧的幂等与不回退**（`REQ-RET-014`）、
**`source_record`**（产出的记忆指向它读过的会话位置 ✓）。

**三处硬约束**（详见存储架构 §8.2）：

| | |
| --- | --- |
| **未提取的会话若丢失，就永远进不了记忆** | 这是 `logging = none` 交出代价的具体形态——**不是缺陷**，但必须写明 ✓ |
| **会话的保留期必须 > 提取的最坏延迟** | 否则一段会话在提取前被 `segment_drop` 丢掉 ✓。**两者分属不同域，必须写在明处** ✓ |
| **提取水位不能存在会话表里** | **可丢的数据不能承载不可丢的进度** ✓——水位存在有日志的一侧 ✓ |

#### 历史查询分三类，只有第三类贵

**原先 `REQ-RET-027` 把"历史时点检索"整体延后了** ✗——**那推得过头**：

| 问什么 | 靠什么 | 成本 | 首版 |
| --- | --- | --- | --- |
| **"当时我们记的是什么"** | 按 **`record_time ≤ T`** 过滤 | **便宜** | **要** ✓ |
| **"事情当时是怎样的"** | **`valid_from` / `valid_to` 区间**覆盖 T | **便宜** | **要** ✓ |
| "当时的向量近邻" | 保留**当时的整份图** | 贵 ✗ | 延后 |

**前两类根本不需要 ANN 的历史版本** ✗✓——**它们只是普通的时间过滤** ✓✓。
**而双时态存在的理由正是让它们便宜** ✓（`Zep` / `Graphiti` 的 `t_valid` / `t_invalid` 点的就是这个）。

**这对 Agent 是刚需** ✗✓：**"记忆是怎么演进的"是它的日常** ✓——
**把这两类延后，等于把底座最该有的一块拿掉了** ✗。

### REQ-MEM-001　中期记忆：围绕任务与会话

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

中期记忆围绕**任务与会话**：**任务目标、检查点、阶段结论、工具结果引用、待办及恢复游标**。

#### 规格

**这个列表决定了 `task_checkpoint` 的字段——它是"可恢复的执行状态"，不是"对话记录"** ✗✓：

| 字段 | 作用 |
| --- | --- |
| **任务目标** | 这件事要做什么——**恢复时要靠它重建意图** |
| **检查点** | 推进到哪一步（有序） |
| **阶段结论** | 已完成部分的**结论**（不是原始轨迹）✓ |
| **工具结果引用** | **引用**，不是结果本身 ✗——大结果在 `AST` 域或 `source_record` |
| **待办** | 还没做的 |
| **恢复游标** | **从哪继续** |

**"引用而非结果"是关键的一处** ✗✓：工具结果可能很大（一次检索、一个文件），
**把它塞进检查点会让检查点本身变成大对象** ✗。
检查点要的是**小而能恢复** ✓。

**"恢复游标"是这一条区别于"聊天历史"的地方** ✓：
它要求这一组字段能**独立支撑一次恢复**——不依赖会话上下文 ✗。

#### 写入的幂等：`(task_id, checkpoint_seq)` 就是幂等键

**Agent 一定会重试** ✗——而检查点是**恢复点** ✓，
**重复写会让恢复不确定**（取哪一行？）✗✓。

**主键即幂等键** ✓：`(task_id, checkpoint_seq)` 是主键 ✓，于是——

| 情形 | 行为 |
| --- | --- |
| 重复写**同一个 seq、内容相同** | **幂等成功** ✓（比对 `content_hash`，与 `CFG` 的配置修订同形 ✓） |
| 重复写**同一个 seq、内容不同** | **拒绝** ✗——那说明调用方算错了 seq，**静默覆盖会丢掉一个真实的检查点** ✗✗ |

> **`content_hash` 在这里的用法与 `CFG` 一致**（`REQ-CFG-008`）✓——
> **同一个模式第二处出现**：**用内容摘要判定"这是不是同一次写入"** ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 检查点缺恢复游标 | **允许**（任务还没开始执行），但"可恢复"不成立 |
| 工具结果引用指向已撤销的来源 | **该检查点的恢复应能察觉**（REQ-MEM-013） |

#### 验收要点

- **构造**：中途中断一个任务，用检查点恢复。
- **预期**：**能恢复到中断点**，且不依赖会话原文。

### REQ-MEM-002　长期记忆：强调来源、时间、版本与可遗忘性

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

长期记忆保存**确认事实、偏好、经验、知识片段及实体关系**，
强调**来源、有效时间、版本与可遗忘性**。

#### 规格

**四类内容，与四个强调项是两组东西**：

| 内容 | 落到哪 |
| --- | --- |
| 确认事实 / 偏好 | `memory_version.content`（JSON，`CFG` 的表示） |
| 经验 | 同上——**经验通常带情境，故更依赖 `source_record`** |
| 知识片段 | 同上 + **向量**（`RET`） |
| **实体关系** | **`derived_link`**（或 `GRP` 域，见 §0.4） |

| 强调项 | 落成什么 |
| --- | --- |
| **来源** | `source_record`（REQ-MEM-010 要求提升时提供） |
| **有效时间** | `valid_from` / `valid_to`（REQ-MEM-008） |
| **版本** | `memory_version.revision`（REQ-MEM-006） |
| **可遗忘性** | `status` 的 `expired` / `deleted` + **TTL**（REQ-MEM-012） |

**"可遗忘"要能真的忘掉** ✗✓——所以它不是"标记一下不返回" ✗（那是可见性），
而是**最终能从介质上消失** ✓——**但 REQ-MEM-014 会说明它止步在哪** ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 无来源的长期记忆 | **允许写入但状态只能是 `candidate`**——见 REQ-MEM-010 |
| 已过 `valid_to` 的事实 | **仍然可见**（它是"当时为真"的记录）✗✓——**除非状态另有变化** |

**第二行需要强调**：`valid_to` 过期不等于 `expired` ✗✓——
前者是**事实的有效区间**（历史属性）✓，后者是**记忆的生命周期**（管理属性）✓。
**两者可以独立变化** ✓。

#### 验收要点

- **预期**：四类内容可存；四个强调项**都可判定**。

### REQ-MEM-003　中期与长期共享底层事务

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

中期与长期**共享底层事务**，**生命周期由独立业务字段表达**。

#### 规格

**这条排除了一个很自然的误设计：把中期与长期做成两张表或两个库** ✗。

| | 分成两套 ✗ | **共享事务（采用）** ✓ |
| --- | --- | --- |
| 一件事跨中期与长期 | **无法原子**✗ | 一个事务 ✓ |
| 索引 / 检索 | 两套 ✗ | 一套，**按字段过滤** ✓ |
| 生命周期 | 两套规则 ✗ | **`status` + TTL 字段** ✓ |

**"生命周期由独立业务字段表达"** = **不是靠"在哪张表"来区分** ✓，
而是靠 **`kind` / `status` / TTL 这些字段** ✓。

**这条与 §0.1 第③条同源**：存储层不做版本化、不做分层 ✗——
**分层是数据模型的事，表达为字段** ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 一次操作同时改中期与长期记忆 | **同一事务内完成** |
| 提升（中期 → 长期） | **是一次字段变更，不是一次"搬家"** ✓ |

#### 验收要点

- **构造**：一个事务内写中期与长期各一条。
- **预期**：**原子生效或原子回滚**。

### REQ-MEM-004　五个对象

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

提供 `memory`、`memory_version`、`task_checkpoint`、`source_record`、`derived_link` 对象。

#### 规格

**形状见 §0.4。这里补字段层面的规定。**

> **五个是"业务对象"**——它们**都是权威数据** ✓。
> **派生结构不在此列**（向量、全文索引）：它们随 `embed` 选项产生，
> **可随时丢弃与重建** ✓（§0.4）。

| 对象 | 键 | 要点 |
| --- | --- | --- |
| `memory` | `memory_id`（UUID） | **逻辑身份**，跨版本不变；含 `status`、`active_revision`、`kind`、**`agent_id`**、**`task_id`（可空）**、**行级 TTL 字段** |
| `memory_version` | `(memory_id, revision)` | **不可变**；含 `content`、双时态四字段、`confidence`、来源引用、**操作者与原因** |
| `task_checkpoint` | `(task_id, checkpoint_seq)` | REQ-MEM-001 的六个字段 |
| `source_record` | `source_id`（UUID） | 含 `revoked_at`（REQ-MEM-013） |
| `derived_link` | `(from, relation, to)` | 含 `relation` 区分 `conflicts_with` / `supersedes` / `derived_from` |

#### `agent_id`：多智能体作用域在**工作区之内**

**生态里最常见的生产形态是"共享的用户记忆 + 按 agent 隔离的任务记忆"** ✗——
而**我们的模型原本表达不了它** ✗：工作区的语义是"**一个主体一个**"（REQ-ISO-001），
而**跨工作区没有任何原语**（§13.9）✗。

**结论是：agent 的划分在工作区之内，不把工作区切碎** ✓✓：

| `agent_id` | 含义 |
| --- | --- |
| **空** | **主体级记忆**——该主体的**全部 agent 共享** ✓ |
| **有值** | **某个 agent 的私有记忆** ✓ |

**这样做反而加固了隔离** ✓：REQ-ISO-003（不跨主体）不受影响 ✓——
**agent 是主体的内部划分，不是新的隔离边界** ✓。
若反过来"一个 agent 一个工作区"，则同一主体的两个 agent **无法共享任何记忆** ✗——
因为它们之间隔着工作区 ✗。

**检索因此默认按 `agent_id` 过滤** ✓：可见的 = 本 agent 的 + 主体级共享的 ✓。

#### TTL 是**行级字段**，而记忆表不用表级 `retention`

**这是一个结构性的点，容易想错** ✗✓：

| | |
| --- | --- |
| `retention` 是**表选项**（`tab$.retention`，§8.1） | **表级** ✗ |
| 而"中期 / 长期"是**行级**的（`kind` 字段）✗ | **所以它们的 TTL 也必须是行级的** ✓✓ |

**一条中期记忆要过期、一条长期记忆不该** ✗——**表级的一个值给不了** ✓。
**`REQ-MEM-003` 其实已经点破了**："中期与长期共享底层事务，
**生命周期由独立业务字段表达**" ✓✓——"独立业务字段"就是**行级的 `expires_at`** ✓。

**所以记忆表**：

| 项 | 取值 |
| --- | --- |
| **TTL** | **行级字段**（`expires_at`，空 = 不过期）✓ |
| `retention`（表选项） | **不使用** ✓——表级值在同一张表里表达不了两种生命周期 ✗ |
| `cleanup` | **`row_delete`** ✓——不是一个 `segment_drop` 能解决的：**同一段里既有要留的长期记忆，也有要清的中期记忆** ✗✓ |
| 清理 | **异步** ✓（可见性由查询时判定，§REQ-MEM-012 ✓） |

> **会话表能用 `segment_drop`，记忆表不能** ✗✓——
> 差别在于**会话是按时间追加的、整段同寿命** ✓（§4.3：TTL 退化为整段操作 ✓），
> 而**记忆是按内容分寿命的** ✗。**同一个"TTL"概念，两张表要两种清理方式** ✓✓。

#### `memory_version` 的四个时间字段放在同一处，这是 REQ-MEM-008 的落点 ✓：

| 字段 | 含义 |
| --- | --- |
| `event_time` | **事件何时发生** |
| `record_time` | **我们何时记下它** |
| `valid_from` | 该事实**从何时起为真** |
| `valid_to` | 该事实**到何时为止为真**（可空 = 至今） |

**它们四个可以两两不等** ✗✓——**这正是把它们分开的理由** ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| `record_time` < `event_time` | **允许**（补记）——但**必须保留两者的差**，不做归一 ✗ |
| `valid_to` < `valid_from` | **拒绝** |

#### 验收要点

- **预期**：五个对象**齐备**，字段完整可查。

### REQ-MEM-005　状态机与转换留痕

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

状态**至少**包含 `candidate`、`confirmed`、`superseded`、`expired`、`deleted`；
**转换保留操作者与原因**。

#### 规格

```text
candidate ──确认──▶ confirmed ──被新版本取代──▶ superseded
    │                   │
    └──拒绝/丢弃──┐      └──TTL 到期──▶ expired
                  ▼                        │
               deleted ◀───────────────────┘
                  │
                  └──（异步清理）──▶ 物理删除
```

| 状态 | 含义 | 检索可见？（REQ-MEM-011） |
| --- | --- | --- |
| `candidate` | **生成物，未经确认** | **默认可见**，但**必须能区分**（REQ-MEM-007）✗ |
| `confirmed` | 已确认 | 可见 |
| `superseded` | 被新版本取代 | **默认不可见**——但**行还在**（REQ-MEM-006） |
| `expired` | TTL 到期 | **默认排除**（REQ-MEM-011） |
| `deleted` | 已删除（逻辑） | **默认排除** |

**转换留痕的落点**：**每次转换写一个新的 `memory_version`** ✓——
而不是更新 `memory` 行上的一个"谁改的"字段 ✗✓。

> **但它的语义要说准，否则会读成冗余** ✗✓：
>
> `memory_version` **不是"内容快照"，是"一次变更事件"** ✗——**内容与状态都在里面** ✓：
> 一次确认（内容没变、状态变了）**也是一条事件** ✓。
>
> **判断依据是"agent 要问什么"** ✗✓：它要问"**这条记忆为什么变成 `confirmed`**" ✓——
> 而回答那个问题需要的正是**操作者、原因、时刻** ✓，它们**天然属于"一次事件"** ✓。
> 若把状态放在 `memory` 行上，**只剩当前值，历史的"为什么"就没了** ✗。
>
> **所以"内容没变的版本"不是浪费** ✓——**它记录的是"状态变化这件事发生过"** ✓。
> `active_revision` 指向**最新的事件** ✓。

> **`candidate` 默认可见是一个需要明说的选择** ✗✓。
> 另一种做法是"默认只返回 `confirmed`"——**那更安全，但也更保守** ✗：
> 上层刚写入的生成物立刻查不到，会把"写入-检索"的基本用法堵死 ✗。
> **选择"可见但可区分"** ✓——**把判断留给调用方** ✓，
> 这与 REQ-MEM-007"confidence 仅是数据"是同一个姿态 ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 从 `deleted` 回到 `confirmed` | **不存在这条路径** ✓——删除是单向的 |
| 未经 `candidate` 直接 `confirmed` | **允许**（用户直接确认的事实）✓ |
| 转换未记操作者或原因 | **缺陷** |

#### 验收要点

- **构造**：走遍每条转换。
- **预期**：**状态流转可审计**（REQ 的验收）——每次转换的操作者与原因可查。

### REQ-MEM-006　业务版本 ≠ Undo 快照

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

记忆更新产生**新业务 revision**，旧 revision **按保留策略留存**；
**该版本不等于 Undo 快照**。

#### 规格

**这条在防一个概念混淆，而且方向必须说清**：

| | **业务 revision**（`memory_version`） | **Undo**（§4.6） |
| --- | --- | --- |
| 是什么 | **数据模型层的版本**——业务上"这条记忆的第 3 版" | **存储层的机制**——用于回滚与一致性读 |
| 存活多久 | **按保留策略**——可能很久 ✓ | **由最老快照封顶**——可能很短 ✗ |
| 谁能看见 | **业务查询可见** ✓ | **业务不可见** ✗——它是实现细节 |
| 谁产生 | **上层显式调用** | **任何一次写**，自动 |
| 是不是一回事 | **不是** ✗✓ | **不是** |

**最容易出的错是"用 Undo 当版本"** ✗：
它**看起来能省一张表** ✗，但 Undo 是**会消失的**（`commit_seq < 最老快照` 即回收，§4.6.5）✗✗——
**于是"第 3 版"会在某个时刻无声消失** ✗，而业务以为它会一直在 ✓。

**反过来也要防**：**不要因为业务要版本，就去改存储层** ✗✓——
**§1.2 已定"存储层不承载版本与事务语义"** ✓，`STO` 域亦有同名条目 ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 一致性读重建旧版本 | **走 Undo**（§12.3）——**与业务 revision 无关** |
| 业务查询历史版本 | **走 `memory_version`** |
| 旧 revision 被保留策略清理 | **允许**——但它是**显式策略**的结果，不是"悄悄消失" ✓ |

#### 验收要点

- **构造**：连续更新一条记忆多次，同时长事务读它。
- **预期**：**两条路各返回各自该给的版本**，互不干扰。

### REQ-MEM-007　生成物与确认事实必须区分

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

**生成记忆与用户确认事实必须区分**；**`confidence` 仅作为数据，不得自动代表正确性**。

#### 规格

**区分靠两个独立的东西，不是一个分数** ✗✓：

| 区分的维度 | 载体 |
| --- | --- |
| **来源**——它是生成的还是用户说的 | **`status`（`candidate` vs `confirmed`）+ `source_record`** |
| **把握**——生成物自己有多确信 | **`confidence`**（仅数据） |

**"`confidence` 不得自动代表正确性"的准确含义** ✗✓：

| 不成立 ✗ | 成立 ✓ |
| --- | --- |
| `confidence > 0.9` ⇒ 自动 `confirmed` | **`confidence` 不参与任何状态转换** ✗✓ |
| `confidence` 低 ⇒ 检索时排除 | **它只影响排序**（§0.3）✓ |
| `confidence` 可替代用户确认 | **确认只能由调用方显式调用**（REQ-MEM-010）✓ |

> **这三条是同一个意思：分数不能提权** ✗✓。
> 一旦"分高就自动确认"成立，**一次模型出错就变成一条"确认事实"** ✗，
> 而确认事实是有后果的 ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| `candidate` 与 `confirmed` 混在结果里且不可区分 | **缺陷** |
| 依据 `confidence` 自动转换状态 | **缺陷** |

#### 验收要点

- **构造**：一批 `candidate` 与 `confirmed`。
- **预期**：**两者可区分**；**状态不因分数变化**。

### REQ-MEM-008　三种时间分开保存

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

**事件时间、记录时间与事实生效区间分开保存**。

#### 规格

**这是本域取自 Zep / Graphiti 的双时态模型的那一条** ✓——四个字段见 REQ-MEM-004。

**为什么要分开** ✗——四个例子：

| 场景 | 三个时间的关系 |
| --- | --- |
| **补记**——今天记录昨天发生的事 | `record_time` > `event_time` |
| **预告**——记下一个将来生效的规则 | `valid_from` > `record_time` |
| **追溯修正**——新证据表明旧事实当时就不成立 | `valid_from` 早于 `record_time` ✗ |
| **废止**——事实曾经为真，现在不再为真 | **`valid_to` 有值，而 `record_time` 是废止的时刻** |

**第三行是双时态的价值所在** ✗✓：
"**我们当时以为它成立**"与"**它当时是否成立**"是**两个不同的事实** ✓——
把它们压成一个时间戳，**就无法同时表达"我们曾经错了"和"现在纠正了"** ✗✓。

**查询因此可以问两个不同的问题，而且都很便宜** ✓✓（不需要 ANN 的历史版本）：

| 问题 | 用哪个时间 |
| --- | --- |
| "**当时我们记的是什么**" | `record_time` |
| "**事情当时是怎样的**" | `event_time` / `valid_from`/`valid_to` |

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 只填 `record_time`，其余留空 | **允许**——但**不能把它们互相填充** ✗✓ |
| `valid_to` 早于 `valid_from` | 拒绝 |

> **"不能互相填充"要写成规定** ✗✓：实现里最自然的动作是"没给 `event_time` 就用
> `record_time` 顶上" ✗——**那会让"我们从不知道它何时发生"与
> "它就发生在记录的时刻"变得不可区分** ✓。

#### 验收要点

- **构造**：上述四种场景各一组。
- **预期**：**三种时间分别可查、可比较**；**未填的保持为空**。

### REQ-MEM-009　冲突并存

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

允许两条**冲突记忆并存**并建立 `conflicts_with` 关系；
**不得以最新写入覆盖全部历史**。

#### 规格

**"并存"是一个反直觉的选择，理由必须写清** ✗✓：

| | 后写覆盖（常见做法）✗ | **并存 + `conflicts_with`（采用）** ✓ |
| --- | --- | --- |
| 冲突 | 消失 ✗ | **保留** ✓ |
| "为什么改了主意" | 不可查 ✗ | **可查** ✓ |
| 谁是当前结论 | 唯一的最后一条 | **需要判定** ✗ |

**第三条是代价** ✗✓：并存之后，"当前该信哪条"不再由写入顺序决定 ✗。
**解法是把判定显式化** ✓——用 `status` 与 `active_revision`，
**而不是用"谁最后写"** ✓（那正是 REQ-MEM-006 的版本化）。

**加上双时态，冲突就有了时间轴** ✓：
两条记忆的 `valid_from`/`valid_to` **可能只在某一段区间重叠** ✗——
**"它们冲突"因此可以是一个关于区间的事实** ✓，而不只是一个标记 ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 两条 `confirmed` 记忆互相冲突且区间重叠 | **允许**——这是数据，不是错误 |
| 用"最后写入"隐式地决定当前结论 | **缺陷** |

#### 验收要点

- **构造**：写入两条冲突记忆。
- **预期**：**两条都在**，`conflicts_with` 可查；历史未被覆盖。

#### 语义

中期提升为长期由**显式调用**并提供**来源**；
数据库**不对记忆内容做语义判断**。

**§0.1 第①条已说明这条的价值。这里补操作层面的规定：**

| 谁做 | 做什么 |
| --- | --- |
| **上层（调用方）** | **判断**——要不要提升、提升哪条、给什么来源与分数 |

**"必须提供来源"是一条硬约束** ✗✓：
一次提升若不指向 `source_record`，**这条长期记忆就不可追溯** ✗——

| 不做 | 为什么 |
| --- | --- |
| 判断"这条值不值得长期保留" | **非确定性**——同一输入两次可能不同 ✗ |
| 自动合并相似记忆 | 同上——而且合并是**改写历史**，A-MEM 的教训在此（§0.2） |
| 自动生成摘要 / 反思 | 同上 |
| 按 `confidence` 自动确认 | REQ-MEM-007 |
| **计算嵌入向量** | **做**——它**确定性且可重建** ✓（§8.1 的 `embed` 选项） |

| 情形 | 行为 |
| --- | --- |
| 提升未提供来源 | **拒绝**（或只允许写为 `candidate`——见 REQ-MEM-002） |
| 库里出现任何模型推理 | **缺陷**——范围控制项 |

#### 验收要点

- **预期**：提升**可追溯**；**库内无 LLM 调用**。

#### 语义

检索**默认排除 `expired` 与 `deleted`** 状态，
**以及"来源已撤销"** 的记忆（`REQ-MEM-013`）。

**完整的不可见判据是一个表达式，不是一条清单** ✗✓：

```text
不可见  ⟸  status ∈ { expired, deleted }
        ∨  其来源已撤销（source_record.revoked_at 非空）
```

**第二项原先只在 `REQ-MEM-013` 里，没进可见性判据** ✗——
**而"撤销后不返回"（`REQ-RET-012` / `REQ-RET-024`）正是靠它** ✓✓。
**两条需求写的是同一件事的两面，必须有一处把表达式写全** ✓。

#### 规格

**默认排除的只有这两个，`superseded` 与 `candidate` 的处理要分别说** ✗：

| 状态 | 默认 | 能否显式包含 |
| --- | --- | --- |
| `confirmed` | 包含 | — |
| `candidate` | **包含**（REQ-MEM-005 已说明理由） | 可显式排除 |
| `superseded` | **默认排除** | **可显式包含**——"历史版本"是有用的查询 |

| **`deleted`** | **排除** | **可显式包含**（审计用） |

**"可显式包含"不是可选的** ✗✓：

**默认值的选择理由**：默认要**符合直觉**（用户要的是"现在的记忆"）✓，
而**例外要能显式表达**（审计）✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 默认检索返回 `expired` / `deleted` | **缺陷** |
| 显式查询历史状态 | **允许**，且**受同一套权限约束**（§13） |

#### 验收要点

- **构造**：五种状态各一条。
- **预期**：**默认只有三种返回**；显式查询能取到五种。

### REQ-MEM-012　TTL 以查询时可见性规则生效

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

TTL 以**查询时可见性规则**生效，**后台物理清理可以延迟**；
**时间基准与长事务行为 P0 固定**。

#### 规格

**这条把"过期"定义成一个可见性问题，而不是一个清理任务** ✗✓：

| | 查询时判定（采用）✓ | 后台清理时判定 ✗ |
| --- | --- | --- |
| 何时"过期" | **查询的那一刻**，由 `TTL 截止 ≤ 现在` 判定 | 等清理任务跑到 |
| 清理延迟 | **不影响结果** ✓ | **直接影响** ✗——清理没跑完，过期数据还在返回 |
| 长事务 | **见下** | — |

**"后台清理可以延迟"因此是免费的** ✓：
清理只影响**空间**，**不影响正确性** ✓。

#### 长事务的行为必须固定（REQ 要求 P0 固定）

**问题**：一个长事务先取了快照 S（§12.1），运行中某条记忆的 TTL 到期——
**它以哪个时刻判定？**

| 选择 | 含义 |
| --- | --- |
| **A. 事务开始时刻** | 与快照一致 ✓——**整个事务看到一个一致的"过期视角"** ✓ |
| **B. 每行的语句时刻** | 同一事务内不同语句可能不同 ✗ |

**A 与 §12 的语句快照语义一致** ✓✓——**RC 下每语句一个快照** ✓，
**所以"过期"应当与快照同时确定** ✓。

> **这与 `CONV §2` 的"过期属于可见性规则，以查询时刻判定"是同一条** ✓，
> 而"查询时刻"在 RC 下**就是该语句取快照的时刻** ✓✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 清理任务未跑 | **不影响可见性**——过期的已经不返回 |
| 长事务内 TTL 到期 | **按该语句的快照时刻判定** |
| 时间基准 | **P0 固定**（`CONV §2` 要求） |

#### 验收要点

- **构造**：TTL 到期的边界，跨一个长事务。
- **预期**：**过期即不可见**，与清理任务是否跑过无关；长事务内**视角一致**。

### REQ-MEM-013　撤销：同步阻止，异步清理

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

撤销记忆时**同步阻止其派生物继续返回**，再**异步清理**实体文件与索引。

#### 规格

**"同步 / 异步"的分工是这一条的全部内容** ✗✓：

| 阶段 | 做什么 | 何时 |
| --- | --- | --- |
| **同步** | 在**撤销那个事务内**，让**所有派生物即刻不可返回** | 提交即生效 ✓ |
| **异步** | 清理实体文件、索引项 | 之后随意 ✓ |

**`source_record` 指向的"会话位置"必须稳定** ✗✓——

**不能用 ROWID** ✗：会话表会**整段丢弃**（`segment_drop`）✓——
段一丢，指向它的 ROWID 就悬空了 ✗。
**而 §7 早就定了"ROWID 不得作为对外持久引用"** ✓✓——
**这里是那条规定的又一个用例** ✓。

**用 `(agent_id, session_id, 序号)` 一类** ✓——**它由数据自己定义，不依赖物理位置** ✓。

**"同步阻止"必须靠可判定的东西，不能靠"清理已经跑完"** ✗✓：

```text
派生物的可见性  ⟸  其来源未撤销
```

**落点**：`source_record.revoked_at` **不为空 ⇒ 该来源及其派生物不可见** ✓。
**这是一个查询时判定**（与 TTL 同形，REQ-MEM-012 ✓）——
**不依赖清理任务** ✓✓。

**"派生物"的范围要靠 `derived_link` 反查** ✓：
撤销一条记忆 ⇒ 沿 `derived_from` / `derived_link` **反向**找出所有派生物 ✓。
**这要求 `derived_link` 有反向索引** ✓（`(to, ...)` 上的索引）——
**否则撤销会变成一次全表扫描** ✗。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 撤销后派生物仍被返回 | **缺陷**——REQ-RET-012/024 的"已撤销来源不得返回" |
| 清理失败或延迟 | **允许**——可见性已由判定保证 ✓ |

#### 验收要点

- **构造**：检索后撤销来源，再检索（与 REQ-RET-012 同一用例）。
- **预期**：**撤销后不返回**——**在清理任务未运行的前提下** ✓。

### REQ-MEM-015　`public` 内容可共享但不自动可信

**优先级**：必须　**阶段**：P3　**追溯**：总体方案 §10

#### 语义

`public` 内容**可共享但不自动可信**；
**检索内容不能改变认证、执行权限与系统指令**。

#### 规格

**这是本域的安全核心，它防的是一类具体的攻击** ✗✓：

```text
不可信内容（public 里别人发布的一段文字）
   → 被检索出来
      → 进入模型的上下文
         → 【不能】改变：认证、执行权限、系统指令   ✗✗
```

**"检索内容不能改变"是三条禁令**：

| 不得被内容改变的 | 为什么 |
| --- | --- |
| **认证** | 内容不能成为身份的来源 ✗ |
| **执行权限** | 内容不能授权任何操作 ✗ |
| **系统指令** | **内容与指令必须分层** ✗✓——这是 prompt injection 的定义 |

**这一条的落点其实是"分层"，不是一个检查** ✗✓：

| 层 | 来源 | 可信度 |
| --- | --- | --- |
| **指令层** | 系统 / 调用方 | 可信 |
| **数据层** | **检索结果、`public` 内容、记忆内容** | **一律不可信** ✗ |

**"可共享但不自动可信"正是这个分层的一句话表述** ✓：
共享解决的是**可达性** ✗，可信解决的是**来源** ✗——**两者无关** ✓✓。

> **与 `CFG` REQ-CFG-011 是同一件事的两面** ✓：
> CFG 说"配置仅作为数据，库不得据此加载代码或执行指令"；
> MEM 说"检索内容仅作为数据，不得改变认证、权限与指令"。
> **同一条原则在两个域落成两条需求** ✓——**这不是重复，是它在两处的具体形态不同** ✓。

#### 边界与错误

| 情形 | 行为 |
| --- | --- |
| 检索结果中出现形似指令的内容 | **它仍然是数据** ✓——**引擎不解释它** |
| 库据此改变任何权限判定 | **缺陷** |

#### 验收要点

- **构造**：在 `public` 发布形似指令的内容，再检索它。
- **预期**：**检索结果无法影响权限判定与系统指令**（REQ 的验收）。

## 待确认汇总（MEM 域）

### 已随本域定案

| 项 | 结论 |
| --- | --- |
| 取值来源 | **六条路线的对比**（§0.2）：取 **D（双时态）**、**G（原子笔记的对象模型）**、**F（三个排序因子）**、**E（关系显式化）**、**B（衰减作排序因子）** |
| **不采纳** | ① **库内 LLM 判断**（REQ-MEM-010）② **衰减作可见性规则** ③ **"共享 = 过滤"** |
| **对象模型** | `memory` / `memory_version` 分离——**与 `CFG` 的"逻辑标识 + 不可变修订 + 活动引用"同构** |
| **双时态** | 四个时间字段（`event_time` / `record_time` / `valid_from` / `valid_to`）**不得互相填充** |
| **排序 vs 可见性正交** | `recency` / `importance` / `relevance` **只影响排序**；可见性由 `status` + TTL 决定。**`recency` 因此可以是近似的**——它走 `stat$` 那条"内存累积 + 定期刷入"的路，读路径不写盘 |
| **判据是确定性而非 LLM** | 确定性的派生计算（**嵌入**）进派生管道，可重建；非确定性的判断（抽取/评估/合并/反思）**必须显式调用并留痕** |
| **多智能体作用域** | 在**工作区之内**用 `agent_id` 表达：空 = 主体级共享，有值 = agent 私有。**不把工作区切碎** |
| **历史查询分三类** | "当时记的什么"（`record_time`）与"当时是怎样的"（`valid` 区间）**便宜且首版就要**；只有"历史时点的向量近邻"延后 |
| **底座判据** | 任何新功能先问：**能力还是策略**？能力归库，策略归 agent。**"能不能进后台"由"是不是派生数据"决定；"要不要留痕"由"是不是确定性"决定**——两件事 |
| **记忆存什么** | **JSON 是权威**（`memory_version.content`），**向量与全文索引是派生**（可丢可重建）。**向量不是列而是伴随结构** `memory_embedding`——因为它要能同时存在多份（每模型一份）|
| **分数不能提权** | `confidence` 不参与任何状态转换，只作数据 |
| **冲突并存** | 不以最新写入覆盖历史；冲突用 `conflicts_with` 显式表达 |
| **过期与撤销** | 都是**查询时判定**（TTL 截止 / `revoked_at`），**不依赖清理任务** |
| **注销** | 逻辑删除 ≠ 介质级擦除——**不得如此宣称** |
