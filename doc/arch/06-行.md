## 6 行

### 6.0 三条编码原则

列的物理编码遵循三条原则，**按重要性排序**：

**① 排序友好——编码使「字节比较 = 值比较」**

这是最重要的一条。B+Tree 索引比较键时若必须**解码**才能比较，代价极高；若编码本身就是保序的，索引可以直接比较字节。成熟产品的编码正是为此设计的：`NUMBER` 正数每个数字字节 +1、`DATE` 各字段加固定偏移，都是这个目的。

> 这一条**约束了几个看似合理的优化**：例如整数不能用机器原生小端整数存储（会破坏与 `NUMBER` 的序关系），详见 §6.5。

**② 变长优先**

能变长就变长，省空间。`NUMBER` 只存有效数字字节、`VARCHAR2` 只存实际字符。

**③ 自描述**

类型与长度信息随数据存放，**不依赖外部字典才能解码**。否则读一行的成本会变成"先查字典再读行"。

### 6.1 行头

| 偏移 | 长度 | 字段 |
| --- | --- | --- |
| 0 | 1 | `row_flags` |
| 1 | 1 | **`itl_slot`** |
| 2 | 2 | `row_len`（含行头） |
| 4 | 2 | `col_count` |
| 6 | 2 | `null_bitmap_len` |
| 8 | 2 | `var_col_count` |
| 10 | *n* | `null_bitmap` |
| | *2m* | `var_offsets` |
| | | 列数据（定长列在前，变长列在后） |

**`row_flags`**：位 0 = **已删除**；位 1 = 已迁移（本槽位是转发指针）；位 2 = 跨页行片段（链上任一片段都置）；位 3 = 含大字段。

**`itl_slot`**：指向本页事务区中的 ITL 槽**索引**，`0xFF` 表示无。这是**行→ITL→Undo** 链条的第一环，一致性读据此定位该行的 Undo 记录（见 §5.4）。**它的每次变更随行修改进 undo**（§4.6.2）——它是版本链的**锚**，不是缓存：锚移动了也要能撤销 ✓。

取值方式：**单独 1 字节**，不复用 `row_flags` 的位——读取少一次判位分支，行头的可读性与访问速度比这 1 字节值钱。

**与 Oracle 的对照——`struct kdrh` 是三个字节**（知识库源码级确认）：

| Oracle `kdrh` | 我们的对应 |
| --- | --- |
| `kdrhflag`（KDRHFH / KDRHFF / KDRHFL 等标志位） | **`row_flags`**——行状态位 |
| **`kdrhlock`**（**锁字节**，指向 ITL 编号） | **`itl_slot`**——同一个职责 |
| `kdrhccnt`（列数） | `col_count` |
| `kdrhnrid`（下个分片地址 6B） | **不需要**——行迁移用槽位状态（转发指针，§6.2），不占行头 |

**"行头几个字节"要先分清三种说法**——知识库里同一结构有三种尺寸，各有出处：

| 说法 | 是哪一种行头 |
| --- | --- |
| **3 字节** | **数据行的行头**：`kdrhflag` + `kdrhlock` + `kdrhccnt`（列数据从第 4 字节起） |
| **9 字节** | **链式行的非末分片**：3 字节之后另加 6 字节 `kdrhnrid`（下一分片地址：dba 4B + 行号 2B）；**末分片仍为 3 字节** |
| **2 字节** | **索引行**（B 树条目）的行头——与数据行不同 |

**"2 字节 / 16 位"的印象通常来自数据行行头的前两个字节**（`kdrhflag` + `kdrhlock`，恰好 16 位）——
**第三个字节是列数**（`kdrhccnt`）。**我们的前两字节与 Oracle 完全同构**（`row_flags` + `itl_slot`）；
列数我们用 2 字节的 `col_count`，且行头固定部分共 **10 字节**——
多出的部分买的是"**不设每列长度前缀**"（长度由 `var_offsets` 相邻项之差得出）。

**为什么锁是"一整字节"而不是 `row_flags` 里的一个位** ✗✓：
**一位只能回答"有没有人锁"，答不了"是谁锁的"**——
而"是谁"是必需的："是不是我锁的"要与 `txn_id` 比对（§5.4），
死锁的等待图要靠它找到持锁事务（§5.4.2）。**所以 Oracle 用一整字节指向 ITL 条目，我们的取舍相同。**

**"当前是否被锁"不在行上判** ✗✓——行上的字节只说
"**最近一次修改它的是哪个事务**"；"锁没锁"由该 ITL 条目的状态回答（活动 / 已提交 / 已回滚，§5.4）：
**块级一处、不随行数增长**。若把"锁定中"做成行上的一个位，
提交 / 回滚就要**回访每一行去清位**——热路径写放大 ✗。
**因此这个字节在提交时不被清**：它一直指着**最近一次修改它的事务**；
槽后来被清除、复用时，它指向的就是那个新占用者——**历史由 undo 兜住，不由这个字节兜住**（§12.4）。

**行头不含**版本号、时间戳、**事务 ID**。行内只有 `itl_slot` 这个**索引**，事务本身的标识、提交序号、Undo 位置都在 ITL 里（块级共享，多行共用一条）——与"存储层不承载版本与事务语义"一致，且避免行头膨胀。

**NULL 位图**：字段缺失 / JSON null / SQL NULL **在存储层是不同表示**，不可压成一位。

### 6.2 行迁移（转发指针）

行更新后变长、原页放不下时：

```text
原槽位：状态 = 2（转发指针），行体只放 6 字节新 ROWID
新位置：完整行，槽位状态 = 1
```

- **原槽位的 ROWID 保持不变**（稳定入口）——**索引不需要更新**，仍指向原 ROWID，经转发指针到达。
- **转发指针可更新多次**：行再增长就再迁移一次，只需更新原槽位的转发指针。**不需要**"头片段不二次迁移"那类转换规则——行迁移在写少读多的画像下本就罕见，二次迁移更罕见，**不为小概率事件增加设计复杂度**。
- 只有当行**超过单页容量**时才转向**行片段链**（§6.3）——那是另一个触发条件，与迁移解耦。
- 转发指针受 WAL 保护。
- **代价**：多读一页。故需 `PCTFREE` 类预留比例降低迁移概率（P0 冻结）。

### 6.3 跨页行（行片段链）

行首次插入即超过单页可用空间时（大 JSON、高维向量）：

```text
头片段（槽位状态 = 3）：行头 + flag 位 2 + 下一片段 ROWID + 数据
中间片段（槽位状态 = 3）：行头 + flag 位 2 + 下一片段 ROWID + 数据
尾片段（槽位状态 = 3）：行头 + flag 位 2 + 下一片段 = NULL + 数据
```

- **链上每个片段都是页里的一"行"，与普通行同规**——各有**行头**（`row_flags` 位 2 标识片段身份、`itl_slot` 参与可见性，§6.1），各有**各自的 undo 与回收**。**这是与 TOAST chunk 的根本区别：片段不是"裸字节"**（Oracle 的多片行同构：每片带**行片段标志与 NRID 链接**，逐片校验）。
- 只有**头片段**有稳定 ROWID 并出现在索引中；其余片段各有**物理 ROWID 用于链寻址**（不在索引里，可随重排变化）。
- **删除 = 链上每个片段都置删除标志**；每片段的删除记录承载**该片段的全部字节**（合计 ≈ 一行大小，与普通行的"整行旧值"同量级）。**回收与普通行无区别**：提交 + 置空后即可复用；一致性读由"整片段旧值 undo + `ITL 覆盖`"照常兜住（§4.6.2）——**不存在"片段空间与最老快照挂钩"的特判**。
- **变长重排**（§6.8 的更新代价）按**每片段写前像 undo** 进行——与普通行更新同规。
- 链**必须受 WAL 保护**——任一点中断后可恢复为一致状态，不得出现半截链。
- 链长度**上限 64 个片段** ⇒ **单个值上限约 1MB**（每片段可用约 16200B，§5.11）。
  超限返回明确错误，且**在写入时报**，不是读到一半才发现。

> **为什么是 64 而不是更大**：本库的大对象**走 `ASSET_REF` 的受管理外部文件**
> （§6.6），**不进库、不进 redo**。所以库里最长的值只是"**长文本**"——
> 1MB 已远超这个需要，**再长就该走资产**。
>
> 链再长还有两处代价：读一个值要更多次随机 I/O（片段可能不连续），
> 以及每次修改要写更多 undo 记录。**上限定得大，是在为用不上的场景付这两笔钱。**
- 片段就是页里的**普通槽位行**——空间核算走通用的槽位目录与空闲区机制，**不需要专门的片段计数**（原"页头 `frag_used`"的提法随之撤除）。

> **与 16KB 页的关系**：选 16KB 正是为了让**主流维度向量（≤3072 维，12KB）不落进这条路径**。跨页是例外路径，不是热路径。

### 6.4 删除与槽位复用

| 步骤 | 动作 |
| --- | --- |
| 1 | 置 `row_flags` 位 0（已删除），写 Undo——**跨页行按片段逐块执行**（§6.3） |
| 2 | **索引项随事务一并移除**（删除即移除、回滚即恢复） |
| 3 | 提交后槽位置空（状态 0），可被复用 |
| 4 | 空间由 defrag 合并，**不在删除时立即回收** |

**为何不需要代次**：索引项与行**同生共死**，不存在"索引项比行活得更久"的窗口，因此不会出现陈旧索引项指向被复用槽位的情形。这是**用机制排除**，而非用代次检测。

**已知行为**（非缺陷）：RC 下索引扫描可能漏读语句开始后被并发删除的行——索引项已移除，堆中 Undo 无机会被使用。此为 Oracle 同类模型的既有取舍，须在测试基线中断言"**允许漏读**"。

### 6.5 六类标量的物理编码

#### NUMBER

采用**变长基 100 科学计数法**（参照成熟产品）：

```text
字节 0：符号位 + 指数
        最高位（0x80）: 1 = 正数或零，0 = 负数
        低 7 位:       指数 + 65（偏移量）
字节 1..n：数字位，每字节 0–99（基 100，一字节存两位十进制）
        正数：每字节 +1 存储
        负数：每字节 = 101 − 值
特殊：0 编码为单字节 0x80
最多 20 个数字字节（≈40 位十进制，覆盖 p ≤ 38）
```

**为什么 +1 和 101−值**：使**字节序与数值序一致**——正数按字节升序即数值升序；负数的反转处理使数值越大字节越小。这样索引比较无需解码。

**`INTEGER` 的存储**：`INTEGER` 语义为 `NUMBER(38,0)`，**磁盘上使用与 `NUMBER` 完全相同的编码**。
**`FLOAT32` / `FLOAT64` 同理**——它们是 `NUMBER` 的子类型，编码完全相同（§6.6）。
**三者共用一套编码**，所以"保序"这个性质**一次实现、三处受益**，
字典表的索引、整数列的范围扫描、浮点列的范围扫描都因此成立。

> **为什么不用机器原生整数**：若 `INTEGER` 用小端 64 位整数存储，其字节序与 `NUMBER` 编码**不同序**，同一列内索引比较会错。**整数快路径只允许存在于计算路径，不得改变磁盘编码**——这正是需求中"NUMBER 不使用 double 承载、整数快路径只是优化"的物理含义。

#### DATE

**固定 7 字节**，各字段加偏移后存储：

| 字节 | 字段 | 编码 |
| --- | --- | --- |
| 0 | 世纪 | `(year / 100) + 100` |
| 1 | 年 | `(year % 100) + 100` |
| 2 | 月 | 原值（1–12） |
| 3 | 日 | 原值（1–31） |
| 4 | 时 | `hour + 1` |
| 5 | 分 | `minute + 1` |
| 6 | 秒 | `second + 1` |

**偏移的两个目的**：① **排序兼容**——字节序即时间序；② **支持公元前**——世纪可为负，+100 保证非负。

#### TIMESTAMP

**前 7 字节与 `DATE` 完全一致**，另加小数字段：

| 声明精度 | 存储宽度 |
| --- | --- |
| 0 | **7 字节**（同 DATE） |
| 1–9 | **11 字节**（7 + 4 字节纳秒） |

宽度**由列的声明精度决定**，故每列宽度固定、行内定位简单。精度取 0 时省 4 字节。

#### CHAR

**固定 N 字节**，不足部分**以空格（0x20）填充**。

**空格填充语义必须在存储层体现**：`CHAR` 的比较使用空格填充语义，`VARCHAR2` 不使用——这直接来自编码差异，不是额外的比较规则。

#### VARCHAR2

**变长，只存实际字符**（不填充）。

**与成熟产品的关键差异**：不设**每列长度前缀**。长度由行头的 `var_offsets` 数组相邻项之差得出，末列长度由 `row_len` 界定。

| | 每列长度前缀 | 行头偏移数组（**采用**） |
| --- | --- | --- |
| 取第 k 列 | 需**顺序扫过**前 k−1 列 | **直接定位** |
| 空间 | 每变长列 1–2 字节 | 每变长列 2 字节 |
| 冗余 | 长度信息分散在各列 | 长度可推导，**不重复存** |

读多写少、点查为主的画像下，**随机访问一列的成本更值钱**，故选偏移数组。

### 6.6 扩展类型的物理编码

| 类型 | 编码 | 备注 |
| --- | --- | --- |
| `BOOLEAN` | 1 字节（0/1） | NULL 由 NULL 位图表达，不在数据区 |
| `UUID` | **16 字节**定长 | 大端 |
| `FLOAT32` / `FLOAT64` | **同 `NUMBER`**（§6.5）——**不是 IEEE 754** | 见下 |
| `TIMESTAMP_TZ` | 11 字节（同 TIMESTAMP）+ 时区偏移 | 存 **UTC 时刻**，原始时区另存 |
| `JSON` | **二进制 JSON 文档**——容器 + `JEntry`，对象键集中排布（`CFG.md`） | **数值必须精确保留**，不得经浮点中转；**内部就是 `NUMBER`** |
| `VECTOR` | 连续 FLOAT32 数组，小端，无头部 | 长度由列的 `length` 给出（该列存 VECTOR 的维度） |
| `ASSET_REF` | 6 字节（资产 ID——48 位序列值） | 资产内容不在此 |

> **`FLOAT32` / `FLOAT64` 是 `NUMBER` 的子类型，只为兼容使用习惯而存在。**
> 物理编码与 `NUMBER` **完全一样**——变长基 100 科学计数法（§6.5）。
>
> **这不是新发明**：Oracle 的 `FLOAT` 本身就是 `NUMBER` 的子类型（带二进制精度），
> `BINARY_FLOAT` / `BINARY_DOUBLE` 才是 IEEE 那种。**我们走的是前一条路。**
>
> **换来的是"没有排序陷阱"**：`NUMBER` 的编码**已经保序**——
> §6.5 那套"+1 与 101−值"就是为它设计的。所以
> **FLOAT 列可以直接建 B+Tree 范围索引，不需要任何保序变换**，
> 也不需要"禁止对浮点列建范围索引"这条限制。**一个待冻结项随之消失。**
>
> **代价与边界要写明**：
>
> | | |
> | --- | --- |
> | **失去** | **IEEE 754 的全值域**。`NUMBER` 上限约 **40 位十进制**（§6.5），**装不下 `FLOAT64` 的 ~1e308**——超范围与 `NUMBER` 一样报错 |
> | **不失去** | **定长**——本来就不是。`NUMBER` 的编码是变长的，`FLOAT` 列也因此变长 |
>
> **`FLOAT32` / `FLOAT64` 的差别是"声明的二进制精度"（24 / 53 位），不是编码宽度。**
> 而精度是**声明层的约束**——物理编码不区分两者。

> **与 `VECTOR` 的元素 `FLOAT32` 不是同一个东西，务必分清**：
>
> | | 标量列 `FLOAT32` / `FLOAT64` | **`VECTOR` 的元素** |
> | --- | --- | --- |
> | 编码 | **同 `NUMBER`**（变长基 100） | **IEEE 754 FLOAT32，定长 4 字节** |
> | 为什么这样选 | 兼容使用习惯，且**天然保序** | **定长**才能让 ANN 的定长槽成立——element 与 neighbor 槽的大小由维度与 `m` 决定（§5.11） |
> | 类型从哪来 | 列的类型 | 由 `VECTOR(n)` 隐含 |
>
> **同名不同物，而且必须不同**：向量要的是定长与机器浮点语义，
> 标量列要的是精确与保序。**一个名字覆盖不了这两个需求**——
> 文档里凡出现 `FLOAT32`，都要看它在哪一栏。

> **本库没有库内 LOB 类型。** 大对象（模型、文档、图片）走 `ASSET_REF` 引用的
> **受管理外部文件**，其内容**不进库、不进 redo**（`design.md`、REQ-AST-001）。
> 因此"长文本"在本库里只是**普通的变长字符值**——没有 LOB 那套定位器、
> 行内/行外双态与分段读写接口。超长时按 §6.3 的行片段链跨页，见 §6.8。

### 6.7 列在行内的布局

```text
行头
  ↓
NULL 位图（每列 1 位）
  ↓
var_offsets（2 字节 × 变长列数）
  ↓
定长列（按声明顺序，紧密排列，无对齐填充）
  ↓
变长列（按声明顺序，紧密排列）
```

**定长列在前、变长列在后**——定长部分可按下标直接算出偏移，变长部分查 `var_offsets`。

**不做字节对齐填充**：省空间优先；跨平台的非对齐访问由读取代码显式按字节组装处理（与 `REQ-PRT-003`「架构相关代码不得依赖单一架构」一致）。

**NULL 的三种语义在存储层的区分**（`REQ-CFG-002`）：

| 语义 | 存储表示 |
| --- | --- |
| **SQL NULL** | NULL 位图置位，**数据区不占空间** |
| **JSON null** | 在 JSON 文档内部（与 SQL NULL 不同表示） |
| **字段缺失** | JSON 文档中**不存在该键** |

三者不可压成一位——这是需求明确要求的区分，物理上必须能还原。

### 6.8 长文本：内联行片段链，不引入 TOAST

长文本（记忆内容、知识条目、文档片段）用 **§6.3 的跨页行（行片段链）内联存储**，
**不引入 TOAST 那套独立结构**。

#### 前提：本库没有库内 LOB，且超块行占比不高

**本库不支持库内 LOB 类型**——`design.md` 与 REQ-AST-001 已定：大对象（模型、文档、图片）
一律走 `ASSET_REF` 引用工作区内的**受管理外部文件**，只允许读取、范围读取与删除，
**不提供原地更新**。

这条决定在这里有一个重要后果：**大对象根本不进库、也就不进 redo**。
于是落在"行链 vs TOAST"这个决策上的，只剩**库内的长文本**——
记忆内容、知识条目、文档片段这类，通常是 **KB 到几十 KB 量级**。

**第二条量级判断**：**超出块大小的行，占比并不高**。
行链的代价（读取要沿链走、变长更新要重排后续片段）只在它**普遍**时才显著；
占比低时，代价可以忽略。

两条合起来：**行链是这里恰当的手段，不需要为它再引入一条独立的存储路径。**

#### 为什么可以不用 TOAST

TOAST 存在的理由是 **PG 的 redo 约束**，而那条约束在本库不成立。先把依赖链摆清楚：

```text
"一条逻辑修改 = 一条原子 redo 记录"
      ↓
该记录必须能装进一个日志文件
      ↓
所以单个值不能大于日志文件
      ↓
所以长文本必须外置（TOAST）
```

**第一环就只在部分场景成立。** 原子性需要一条边界来承载，而边界有两种：

| 操作类型 | 原子边界 | 是否需要"单条原子记录" |
| --- | --- | --- |
| **系统操作**（区分配、段头、位图） | **没有**——它不是事务 | **需要**——否则崩在中间会留下"位图说已分配、没有段认领"的页泄漏（§11.1.3） |
| **事务性的行修改** | **提交记录** | **不需要**——只要提交记录排在该事务全部修改记录之后，拆分仍是原子的 |

一次行修改跨越 N 个片段页时，拆分出的 N 条记录**由提交记录兜底**：

- 崩溃且事务未提交 → 逐片段回滚（undo 与数据修改**逐片段交错落盘**，§11.1.2）
- 崩溃且事务已提交 → 提交前全部记录必已落盘（WAL 规则 3），全部重放

**所以本库不需要 TOAST。** 记录大小由"**一页**"界定（§11.5.3），与文本长度无关。

#### 与 TOAST 的取舍对比

| | 内联行片段链（采用） | TOAST |
| --- | --- | --- |
| 额外结构 | **无**——复用 §6.3 | 每表一个溢出段 + 指针 + 块链 |
| 访问路径 | 沿片段链走，**同段、局部性好** | 主行 → 指针 → 跳转到独立段 |
| 更新代价 | 变长时重排后续片段 | 重建 chunk（碎片 + 回收压力） |
| 空间 | 除末片外每片满页 | chunk 固定大小，末块浪费 |
| 单值上限 | 由片段链长度上限定（§14 项 4） | 几乎无上限 |

**关键在于本库的画像**：长文本的主要宿主是**追加型表**（记忆、配置）——
**整体写入、整体读取、几乎不更新**。这恰好是：

- TOAST **收益最小**的场景（它的收益主要在"只访问大值的一部分"与"避免行膨胀拖累同行其他列"）
- 而它的开销（多一层间接、独立段的额外 I/O）**最明显**

所以在这个画像下，**内联更优**。

#### 代价与边界

- **读取会读到整个链**。我们的场景是"把记忆内容读出来喂给 LLM"，本就需要全部——
  不是问题。若将来出现"只取前 N 字节"的高频需求，再评估。
- **行片段链长度上限由此变得关键**：它现在直接决定**单个值的大小上限**。
  待冻结项 4 的定位从"兜底约束"升为"值的硬上限"。
- **空间**：除末片外每片都是满页，浪费限于一片。

> 记录一下**刻意放弃**的东西：没有"大值随机访问"，也没有"外置以避免行膨胀拖累同行其他列"。
> 换掉的是：**一个独立的段、一层指针间接、以及一套需要与主行保持同步的回收逻辑**。
