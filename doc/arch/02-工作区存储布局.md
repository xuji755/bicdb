## 2 工作区存储布局

### 2.1 目录

```text
<工作区根>（主位置）/  根目录名由服务端生成的不透明 ID，不拼接用户输入
│                      主位置自身位于**文件系统池**中的某个文件系统上（§2.8）
├── control/           control01.ctl  control02.ctl
├── wal/               redo_g1_m1  redo_g1_m2  redo_g2_m1  redo_g2_m2
└── data/
      <ws>_meta        file 0    工作区固定开销（小），不参与池
      <ws>_undo        file 1
      <ws>_temp        file 2
      <ws>_data_NN     file 3..  **数据文件**——可分布在池中任意文件系统上（§2.8）

<池中某文件系统>/<工作区根 ID>/
├── assets/<v>/…       外部对象——按**卷**分布：<v> 由资产 ID 首字符决定，
│                      16 个卷可各自落在不同的文件系统上（§2.9、§2.10）
└── staging/           资产上传暂存——**必须与其对应的 assets 卷在同一文件系统**（§2.9）
```

**工作区不是一个物理目录，而是一个跨文件系统的命名空间**——工作区的容量上限因此是
**整个池**，而不是池中最大的那个盘（§2.10）。

**数据文件的实际位置**：`<池中该文件系统的挂载点>/<工作区根 ID>/data/<ws>_data_NN`

即——**同样的相对路径，挂在不同的文件系统下**。只有挂载点随池槽位变化，
命名规则与相对路径都不变。
**这条完整路径记在工作区控制文件的数据文件记录里**（§2.6"文件路径"一节）——
工作区必须自包含到能独立定位自己的全部文件。

### 2.2 文件角色约定

| 文件号 | 角色 | 说明 |
| --- | --- | --- |
| **0** | 元数据 | **数据字典**（字典表，结构与普通表通用）+ 引导页。**不承载用户数据行** |
| **1** | Undo | 仅 `logging = full` 的表产生 |
| **2** | Temp | 排序/哈希/分词溢出；不持久化、不进备份。**按段分配**，见 §4.8 |
| **3..N** | 数据 | 数据段，可动态新增 |

**该约定对 `public` 工作区同样适用**，规则统一。

**三个好处**：① 备份与恢复按角色定策略（temp 不备份）；② 用户数据**只可能在 file ≥ 3**，ROWID 寻址空间干净；③ 配额按角色分别设，undo/temp 不与数据挤占。

### 2.3 两级控制文件

| | 工作区控制文件 | 全局控制文件 |
| --- | --- | --- |
| 位置 | `<ws>/control/` | 平台控制目录 |
| 份数 | 2 | 2 |
| 内容 | 该工作区的文件清单、检查点位置、redo 序列号、格式版本 | **数据库管控的文件清单**：有哪些工作区、各自根目录与文件构成 |
| 更新时机 | **日志切换时** | 建/删工作区、新增数据文件时（**低频**） |
| 是否恢复锚点 | **是** | 否（丢失可由各工作区自描述重建） |
| 含私有内容 | 否（仅结构） | **否** |

**控制文件必须独立于表空间**——恢复要先知道"该打开哪些文件、检查点在哪"，若控制信息藏在 file 0 内则形成循环依赖（要先打开 file 0 才知道要打开 file 0）。

**全局控制文件绝不在提交关键路径上**——工作区的每次提交不得触碰它，否则造成跨工作区耦合与写热点。

### 2.4 Redo

- **每工作区独立**：redo 记录**包含用户数据本身**（行级修改描述），共享即泄漏。
- **2 组 × 2 成员 = 4 个文件**：组提供循环复用空间，成员提供镜像冗余。同组成员**大小必须完全一致**。
- **组大小创建工作区时指定**——小工作区配小 redo（如 256KB/组），大工作区可上百 MB。这解决了小工作区固定开销占比过高的问题。
  - 下限：必须能容纳**一个检查点周期**的日志量（P0 依据检查点策略给出）
  - 变更：运行后**只能增加组数，不能改已有组大小**
  - **另一条独立下限：组大小 ≥ 最大单条记录**（§11.5.1）。记录大小以"页"为界（§11.5.3），
    故该下限 = **17 KiB**（一条记录最多跨越 34 个 redo 页，含分片帧；§11.5.2 已定量）——很低，容易满足；真正的约束来自"一个检查点周期"
### 2.5 归档

**归档是时间点恢复、在线备份与备库的共同前提**——它保留**连续的日志链**，为恢复提供从备份点到目标点的全部变更历史。无归档则 redo 组被循环覆盖、日志链即断，上列能力全部失效。

**机制**：日志组在被覆盖**之前**先复制到归档目标。由此引入一条约束：

> **未完成归档的日志组不得被覆盖。**

这条约束**改变 redo 的空间管理与日志切换逻辑**，因此归档机制**必须与 WAL 层同期设计**（P3），而非事后附加——否则等于重写 WAL 层。

**归档必须每工作区独立**：归档内容与 redo 一样含用户数据（行级修改描述），共享即泄漏；归档目标须落在该工作区的受控目录内。

| 数据 | 是否归档 | 后果 |
| --- | --- | --- |
| `logging = full` / `redo_only` | 归档 | 支持在线备份与时间点恢复 |
| `logging = none` | **无 redo 可归档** | **不参与**；需保留时只能用离线迁移工具 |

**归档前的一致性要求**：做时间点恢复或基于备份的恢复前，必须先强制归档当前日志组，确保日志序列连续、无缺口。

**机制细节**（组状态机、切换协议、归档线程与文件格式、写者等待与告警）集中在 **§11.9**——本节只立约束。

### 2.6 控制文件的结构

#### 定长设计

控制文件**定长**，大小在建工作区时按上限确定。这样更新是**原地覆盖写**，不必重写整个文件。

**数据文件记录数组固定 1024 项**——与 ROWID 的 `file_id` 位宽一致，两者天然对齐。

**估算（已重做——原版未计路径）**：原按 `数据文件记录 1024×32B = 32KB` 算得 34KB → 64KB。
但数据文件记录现在**含完整路径**（见下"文件路径"），每条从 32B 变成 32B + 路径长度，
这一项因此**大一个量级**：

| 方案 | 数据文件记录 | 控制文件合计 |
| --- | --- | --- |
| 每条定长（路径字段 128B） | 1024 × 152B = **152KiB** | ≈ **155KiB** |
| 每条定长（路径字段 256B） | 1024 × 280B = **280KiB** | ≈ **284KiB** |
| 每条定长（路径字段 512B） | 1024 × 536B = **536KiB** | ≈ **540KiB** |
| 记录定长 + **独立的定长路径池**（128KiB） | 1024 × 24B + 128KiB = **152KiB** | ≈ **155KiB** |
| **记录区按需增长**（典型 4–20 个文件） | ≈ **1–6KiB** | ≈ **4–9KiB** |

**单位统一按 KiB**（1KiB = 1024B）——与"页 16KB""区 128KB"同一口径。
表中"每条 24B"是记录的**不带路径部分**；定长方案的每条 = 24B + 路径字段。

**三者之差在"为用不到的文件数付多少"**：ROWID 允许 1024 个文件（§7），
但一个工作区实际往往只有几个。方案一定长但浪费最多；方案三最省，
代价是打破"整体定长"（增长时重写整个控制文件——**只发生在新增文件时，低频**）。

> **取舍见 §14 第 45 项**——它同时决定控制文件的**页大小**。

#### 记录的两类复用语义（对照 Oracle）

Oracle 的控制文件由**带类型号的记录段**组成，`X$KCCCF.INDX` 给出完整枚举。它的第一层划分**不是"内容"，而是复用方式**：

| | 非循环复用 | 循环复用 |
| --- | --- | --- |
| 语义 | **每个实体一条，位置固定** | **历史流水，写满即环形覆盖最旧** |
| Oracle 记录 | 库信息(0)、检查点进度(1)、redo 线程(2)、日志文件(3)、数据文件(4)、文件名(5)、表空间(6)、临时文件(7) | 日志历史(9)、归档日志、离线范围、RMAN 备份集/片/副本 |
| 上限 | 建库时定死 | 环形空间 |

**这条划分比"有哪些段"更重要**——它决定每类的**容量策略**与**写满时的行为**：
非循环记录写满 = **结构上限到顶**（Oracle 的表现是需要重建控制文件，这正是 `MAXDATAFILES` 一类参数的由来）；
循环记录写满 = **静默丢弃最旧历史**。

我们采用同一划分：

| 段 | 类别 | 写满时 |
| --- | --- | --- |
| 文件头、工作区条目、检查点进度、Redo 条目、数据文件记录 | **非循环** | 到顶即**拒绝新增**（如数据文件记录固定 1024 项，与 ROWID 的 `file_id` 对齐，§7），**不重建控制文件** |
| 归档记录 | **循环** | 环形覆盖最旧——但受**"未归档组不得覆盖"**约束（§2.5） |

**刻意不采用的 Oracle 记录类型**：

| Oracle 记录 | 为什么不需要 |
| --- | --- |
| `KCCDERTH` redo 线程 | 单实例，无 RAC 多线程概念 |
| `KCCDETBS` 表空间 | **工作区即表空间**，一一对应（§3.1） |
| RMAN 系列（备份集 / 备份片 / 副本 / 删除） | 备份元数据的存放位置**尚未定**——见 §14 第 26 项 |

> **`KCCDENAM`（file NAMe record）是采用，不是省略**——Oracle 的控制文件**存完整路径**，
> 我们现在也存。原因见下"文件路径"。

#### 工作区控制文件的段

| 段 | 内容 |
| --- | --- |
| **文件头** | 格式版本、各段偏移表、**副本序号**、校验和 |
| **工作区条目** | `workspace_id`、创建时间、**`derived_from` + `derived_at_seq`**（克隆血缘，§2.7） |
| **检查点进度** | 检查点提交序号、**检查点 LSN（= 恢复起点）**、当前提交序号、**最老快照提交序号**。**这些序号都属于本工作区**，不作跨工作区比较（§11.1.4） |
| **Redo 条目** | 组数、成员数、每组的序列号与状态、当前组 |
| **数据文件记录** | 每文件的 `file_id`、**完整路径**、**角色**、状态、**创建时大小**、创建时间 |
| **归档记录** | 归档模式、归档目标、最后归档的日志序列号 |

**检查点进度里的"恢复起点"**：Oracle 的检查点进度记录（`X$KCCCP`）不只存检查点位置，还存**两个 RBA**——
`low_rba`（检查点队列中最早的脏块）与 `on_disk_rba`（DBWR 已落盘到哪），二者之差就是崩溃后要重放多少。
其含义是：**恢复起点是"最早的脏块"，而不是"最后一次检查点动作的位置"**。
我们的"检查点 LSN"必须按同一语义定义——即**该 LSN 之前的修改已全部落盘**。

**数据文件记录存"创建时大小"而非"当前大小"**：Oracle 的 `FECSZ` 全称是 *creation file size*，
当前大小由**文件头自述**（Oracle 另有 `FEBSZ` 记录每文件的块大小；我们统一 16KB，故不需要）。
控制文件只保存**创建后不变**的属性，可变量一律以文件自身为准——与 §5.2 的字段准入纪律同源。

**文件路径：存，而不是省**

（原设计为"不存路径"，引入文件系统池后**已推翻**。来路值得记下：当初能省，是因为
**把文件位置约束到了"工作区根"**；文件系统池重新引入了"任意位置"，
**于是回到了 Oracle 的处境**——而它的控制文件本来就存路径，即 `KCCDENAM`。）

数据文件的完整路径**必须记在工作区控制文件里**，因为**它是恢复锚点，必须自包含**：

> 若只存一个指向文件系统池的**槽位号**，那么全局控制文件一旦丢失，
> 槽位号就无从解析，**所有数据文件都定位不到**——恢复锚点就依赖了另一份可丢的东西。

存路径之后，"池里有哪些文件系统"也能从各工作区控制文件里的路径**前缀**反推出来，
这恰好与"全局控制文件不是恢复锚点、丢失可由各工作区重建"（§2.6）的性质吻合。

| 信息 | 存放 | 性质 |
| --- | --- | --- |
| **池**（有哪些文件系统） | 全局控制文件 | 权威，但**可重建**（从工作区侧的路径前缀反推） |
| **每个数据文件的完整路径** | 工作区控制文件 | **权威且自包含**，恢复时不依赖任何外部配置 |

**代价与缓解**：存路径重新引入了当初省掉它的那类安全问题。缓解与其它文件操作一致
（REQ-ISO-007）：路径**不是用户输入**，而是创建文件时的**服务端决策**；
打开时**校验路径落在池中的某个文件系统之下**，并做路径穿越与符号链接检查。
被篡改的路径因此在**打开阶段就会失败**，而不是被悄悄读走。

**一处刻意的省略：不存 Undo 段信息。** Undo 信息在 **Undo 段头部与目录**中，
不属于控制文件——这一点与成熟产品一致。

#### 全局控制文件的段

| 段 | 内容 |
| --- | --- |
| 文件头 | 格式版本、序号、校验和 |
| 库条目 | 库标识、创建时间、格式版本 |
| 工作区记录数组 | `workspace_id`、状态、文件数、总大小、最后更新时间 |

**只存结构摘要，不存私有内容**；**不是恢复锚点**——丢失后可由各工作区控制文件重建。

#### 字节布局（已定案：§14 第 10 项）

**控制文件 = 20 页 × 16 KiB = 320 KiB**（页对齐；此前的 284 KiB 估算是紧凑排布，未计页对齐）：

```text
页 0        文件头（段偏移表 + 固定偏移的单条 undo 记录）
页 1        固定段：工作区条目 │ 检查点进度 │ Redo 条目 │ 归档记录
页 2–19     数据文件记录数组：1024 × 280B
```

**每页 = 页头 24B + 页体 + 页尾校验 4B**（照数据页惯例）：

```text
CF 页头（24B）
  偏移 0   magic        4B   0x42494346（"BICF"）
  偏移 4   seq          4B   副本内更新序号（仅页 0 使用；每次更新 +1）
  偏移 8   page_no      2B   页号（0 = 文件头页）
  偏移 10  payload_len  2B   本页有效数据长度
  偏移 12  copy         1B   副本号：0 = A / 1 = B
  偏移 13  flags        1B
  偏移 14  reserved     10B
页尾：CRC32C 4B（覆盖页头 + 页体）
```

**页 0 的页体**：

```text
偏移 0    format_version 2B │ page_size 2B（= 16384）
偏移 4    段偏移表：8 项 × 16B（段号 1B │ 起始页号 2B │ 页数 2B │
          条目大小 2B │ 条目数 2B │ 保留 7B）；段 3–7 保留（备份元数据等，§14 第 26 项）
偏移 132  undo 记录（**固定偏移**——崩溃后第一步就要读到它，522B）：
          target_off 4B │ old_len 2B │ old_data[512B] │ 校验 4B；**old_len = 0 即空闲**
```

**页 1 固定段的字段**：

| 字段 | 布局 | 宽度 |
| --- | --- | --- |
| 工作区条目 | `workspace_id` 6B │ 创建时间 8B │ `derived_from` 6B │ `derived_at_seq` 6B │ 保留 38B | 64B |
| 检查点进度 | 检查点提交序号 6B │ 检查点 LSN 6B │ 当前提交序号 6B │ 最老快照提交序号 6B │ 时戳 8B │ 保留 16B | 48B |
| Redo 条目 | 头 4B（组数 │ 成员数 │ 当前组 │ 保留）│ **8 组 × 12B**（序列号 4B │ 状态 1B │ 归档状态 1B │ 保留 6B；**两状态的取值定义见 §11.9**）│ 保留 28B | 128B |
| 归档记录 | 归档模式 1B │ flags 1B │ 最后归档序列号 4B │ **归档目标路径 256B** │ 保留 58B | 320B |

**数据文件记录（280B）**：`file_id` 2B │ `role` 1B │ `status` 1B │ `flags` 2B │ **创建时大小** 6B（块数）│ 创建时间 8B │ 保留 4B │ **完整路径 256B**（§14 第 45 项）。

**更新协议（单次 = 一个连续字节区间，≤ 512B）**：

```text
① 写 undo 记录（目标偏移 + 旧值）        ← 副本
② 写目标字节范围                          ← 主数据（原地覆盖）
③ 写页 0 的 seq（+1）                     ← 本次更新的"发布"
④ 清 undo 记录（old_len ← 0）
```

**四个崩溃点都可判**——①后（回滚 = 无操作）、②中（回滚 = 恢复旧值，这正是它要防的）、②后③前（回滚 = 丢这次更新）、③后④前（回滚 = 丢这次更新，seq 多计一次——无碍，控制文件是**幂等状态发布**，"多退一次可容忍"见 §5.11）。

**为什么"单区间 ≤ 512B"能覆盖**：每个字段都远小于 512B；需要"多处同时原子"的场景被"能推导的不存"消掉了——可变量以文件/段自身为准（§2.6），控制文件里几乎都是**单字段更新**。undo 记录的定长上限 512B 由此而来（= 单次修改的最大旧值）。

#### 双副本的一致性协议

- **序号单调递增**，每次更新 +1（= 页 0 页头的 `seq`；更新协议见上）
- 更新顺序：**先写副本 A，成功后写副本 B**
- 打开时读两副本，取**有效且序号较大**的
- 若两副本都无效 → **该工作区无法启动**（与成熟产品一致，属设计上接受的取舍）

**为什么定长 + 原地覆盖能安全**：定长使单次更新是**局部覆盖**，配合页尾式校验与副本序号，崩溃后总能判定哪一份是完整且较新的。变长则需整体重写，崩溃窗口更大。

#### 更新时机与关键路径

| 触发 | 更新 | 频率 |
| --- | --- | --- |
| 日志切换 | 工作区控制文件 | 高 |
| 检查点 | 工作区控制文件 | 中 |
| 归档 | 工作区控制文件 | 中 |
| 新增数据文件 | 工作区 + 全局 | 低 |
| 建/删工作区 | 全局 | 极低 |

**控制文件的更新不在提交关键路径上**——提交只需 WAL 持久化；控制文件在日志切换与检查点时更新。**这是它敢用"双副本 + fsync"而不拖慢事务的前提**。

#### 与 redo 的关系

控制文件记录的检查点**可能落后于数据文件的实际状态**——这没问题，因为重做本身是**幂等**的（按页 `page_lsn` 判定跳过已包含的修改），从稍旧的检查点起重做会自然收敛到正确状态。

但**控制文件本身丢失（两副本皆坏）则无法启动**——与成熟产品一致。全局控制文件例外，它可由各工作区重建。

### 2.7 工作区的克隆与分支

工作区是**自包含的多文件集合**（file 0..N + redo + 控制文件），这使它天然适合用
**文件系统的写时复制（COW）**做近乎瞬时的整区克隆——XFS 的 `reflink` 与 btrfs 都支持。
克隆出来的是一个**独立的工作区**：有自己的目录、自己的 redo，独立演进。

**这是管理员操作**，普通用户无权限——它要读另一个工作区的文件。

#### 一致点：冻结 → 检查点 → 克隆 → 解冻

克隆必须取自一个**一致的时刻**，否则克隆出的工作区需要先做实例恢复。

```text
① 冻结源工作区（拒绝新事务）
② 强制检查点：刷全部脏页 + 刷控制文件
③ 对全部文件执行 reflink 克隆（纯元数据操作，毫秒级）
④ 解冻源工作区
```

③ 必须在冻结窗口内完成。reflink **不搬数据**、只建共享引用，所以窗口极短——
这正是它比"备份 + 恢复"快几个数量级的原因。

> **与成熟产品一致**：Oracle 的本地 PDB 克隆要求"源 PDB 只读，**或**启用 LOCAL UNDO
> 且处于归档模式以支持热克隆"。我们走的是**只读那一支**（冻结）。
> 热克隆那一支我们也具备前提（每工作区独立 undo + 归档），但 **V1.0 不实现**。

> **备份（§2.14）用的是同一个冻结机制，但窗口内不做检查点**——它要的是**更短的窗口**，
> 恢复端由重放收敛；克隆要"开箱即用"，所以克隆做检查点。取舍不同，理由不同。

#### 克隆后必须重新解释的三样东西

**① `workspace_ref` 的语义是"数据血统"，不是"工作区身份"**

页头的 `workspace_ref` 由 `H(workspace_id)` 得出（§7）。克隆后新工作区的 `workspace_id` 变了，
但**页上的 `workspace_ref` 保持不变**——分支的数据确实源自同一血统。

三个方案里只有这一个可行：

| 方案 | 代价 |
| --- | --- |
| **继承源的 `workspace_ref`**（采用） | 无，且语义正确——ref 要回答的是"这页属于我正在打开的数据世系吗" |
| 克隆时重写所有页的 `workspace_ref` | O(页数)，**摧毁"快速"这个唯一价值** |
| 新工作区沿用源的 `workspace_id` | 不可行——全局控制文件会冲突 |

这反过来要求把 `workspace_ref` 的定义说准：**它标识数据的血统根，不是工作区的当前身份**。
（它本来也不是密码学边界，§7 已声明。）

**② LSN 必须在新工作区里继续单调**

被克隆的页上带着源的 `page_lsn`。新工作区第一次修改某页时，若新 LSN **小于**该页的 `page_lsn`，
`page_lsn` 的幂等判定会认为"这页已包含该修改"而**跳过重放**——错误。

解法：**新工作区的 LSN 起点取源日志序列的下一个整组边界**：

```text
新工作区起点 LSN = 把源的当前 LSN 向上对齐到 redo 组大小
```

于是新 LSN **严格大于**克隆点的 LSN（即页上所有 `page_lsn`），且新工作区的组内偏移从 0 开始。
代价最多浪费一个组大小的 LSN 空间，48 位下可忽略。

> **顺带确定 LSN 的编码**（原为待冻结项）：LSN 是**单调递增的字节位置**，
> 文件与文件内偏移由它**推导**，而不是编进它——这正是 PG 的做法：
> `组号 = LSN / 组大小`、`组内偏移 = LSN & (组大小 - 1)`。
> 它要求 **redo 组大小是 2 的幂**（掩码运算），这是一个新增的硬约束。

**③ `redo` 从零开始**

克隆点已经是一次检查点，数据文件是一致的，**不需要克隆点之前的日志**。
新工作区的 redo 从空开始写。

#### 血缘记录

克隆出的工作区**自描述其血缘**——在工作区控制文件的"工作区条目"里加两个字段：

| 字段 | 说明 |
| --- | --- |
| `derived_from` | 源工作区标识（非克隆工作区为空） |
| `derived_at_seq` | 派生点的提交序号 |

> 成熟产品同样把这件事记在数据库自身：Oracle 用数据库标志 `KCCDICLO` 标明"本库是克隆出来的"，
> 因为它的克隆库"数据文件可能基于备份获取，打开时可能需要额外的恢复或日志应用"。
> 我们的克隆点是**一致**的（冻结 + 检查点），打开时**不需要**额外恢复——这一点比基于备份的克隆更强。

全局控制文件里也记一份（便于管理面列出派生关系），但**权威在工作区控制文件**——
与"工作区自包含"一致。

#### 允许什么、不做什么

- **允许链式派生**（分支的分支）。链长由管理面限制，存储层不设限。
  > 成熟产品在**快照轮播**这类场景里禁止"基于快照再建快照"，但那是快照存储区的限制；
  > 我们直接对文件做 reflink、没有中间层，链式派生在存储层没有额外代价。
- **不支持合并**（把分支的改动并回主线）。那需要比对两个工作区的数据与日志并定义冲突语义，
  是另一个量级的工程，且与"存储层不做版本化"的边界冲突。**V1.0 不做，也不预留格式。**
- **不自动清理**：源工作区被删除后，分支因其 reflink 共享而**依然完整**——
  COW 的引用计数由文件系统维护，与工作区管理无关。

#### 前提：reflink

克隆要求工作区目录位于**支持 reflink 的文件系统**上（btrfs、XFS with `reflink=1`）。
它与"原子页写"是**两条彼此独立**的文件系统能力——一个文件系统可以满足其一而不满足其二，
**必须分开评估**。**能力档位表与区别说明集中在 §11.6**，
其中一条尤其要记住：**XFS 满足 reflink 克隆，但不提供原子页写**。

### 2.8 文件系统池

**工作区的文件不必落在同一个文件系统上。** 数据库维护一个**文件系统池**——
一组可供放置数据文件的挂载点。池是**实例级**的：它属于平台，不属于某个工作区。

#### 池的增删

| 操作 | 前置条件 |
| --- | --- |
| **加入** | 无——新加入的文件系统立即参与后续分配 |
| **移出** | **该文件系统上不得有任何数据文件** |

**"移出"的前置条件是硬性的**。理由不是保守，而是**职责边界**：池只管"文件放在哪"，
不管文件内容；若允许带着文件移出，那些文件就脱离了数据库的管控范围，
而它们的**恢复锚点（控制文件）仍在数据库手里**——形成一个数据库无法负责的状态。

所以顺序永远是：**先 `Move` 走全部文件（§3.4），再移出**。

#### 池定义存全局控制文件，文件路径存工作区控制文件

| 信息 | 存放位置 | 性质 |
| --- | --- | --- |
| **池本身**（有哪些文件系统） | **全局控制文件**（§2.6） | 权威，但**可重建**——从各工作区控制文件里的路径**前缀**反推 |
| **每个数据文件的完整路径** | 该工作区的**工作区控制文件** | **权威且自包含**——恢复时不依赖任何外部配置 |

**为什么存路径而不是池槽位号**：工作区控制文件是**恢复锚点**，必须**自包含**。
只存槽位号的话，全局控制文件一旦丢失，槽位号就无从解析，
**所有数据文件都定位不到**。存完整路径则让池配置也能从工作区侧反推，
正好与"全局控制文件可重建"的性质吻合。详见 §2.6 的 ①。

**职责因此很清晰**：**新增文件时**才需要池配置（决定放哪个文件系统）；
**打开已有文件时**直接用存的路径——不依赖任何全局状态。

#### 自动创建文件前必须先看容量

**自动新增数据文件前，必须先探测候选文件系统的可用空间**，选取**容量足够**的那个；
**谁也不够时直接报错**，而不是硬写下去、等 `ENOSPC` 在半路炸出来。

| 规则 | 说明 |
| --- | --- |
| **选择策略** | 多个候选都够时选**可用空间最多**的——避免文件都堆在同一个盘上 |
| **"足够"的判据** | 至少放得下新文件的 `initial_size`，并留出余量 |
| **不依赖预分配** | 检查与创建之间有窗口，期间别人可能吃掉空间。这个窗口由**创建失败时重试**处理，不靠 `fallocate` 之类的预占——它在不同文件系统上语义不一致，不该作为正确性依据 |

### 2.9 外部对象（资产）的存储布局

大对象（模型、文档、图片）**不进库**——它们由 `ASSET_REF` 引用，内容是工作区内的
**受管理外部文件**（REQ-AST-001、§6.6）。这些文件在磁盘上怎么摆，是本节的事。

#### 禁止平铺：一个目录装不下

**资产目录不得平铺**。把几十万个文件塞进一个目录会同时压垮三件事：
目录项查找退化为线性扫描、`ls` 一类运维动作不可用、部分文件系统在大目录下性能塌陷。

#### 按 ID 分片成目录树

资产由 **48 位 ID** 标识（D-01：系统级序列、六字节、十二位十六进制），**路径由 ID 直接推导**：

```text
<卷所在文件系统>/<工作区根 ID>/assets/<v>/<s1>/<s2>/<s3>/<asset_id>

（`<v>` 是**卷**，由 ID 首字符决定——卷级的意义与放置见 §2.10。）
```

- 每级取 ID 的一段作为**分片槽位**
- **基数 B**（每级多少槽位）与**层数 L** 共同决定容量：`B^L`
- **每个目录的条目数 ≤ B**

| 基数 B | 层数 L | 容量 | 每目录条目 |
| --- | --- | --- | --- |
| 16（十六进制 1 位） | 4 | 6.6×10⁴ | ≤ 16 |
| **256（十六进制 2 位）** | **3** | **1.67×10⁷** | **≤ 256** |
| 100（十进制 2 位） | 4 | 1×10⁸ | ≤ 100 |

**推荐十六进制 2 位 × 3 级**：ID 本来就是十六进制，分片可以直接切字符串、不需要转换；
每目录 256 个条目仍远在常见文件系统的舒适区内（ext4 的 htree 要到数百至数千条目才真正吃紧，
且那时工作良好）。这个形态也是成熟工具长期验证过的（Git 的对象库即两级十六进制）。

> 若确实要把每目录压到 100 以内，用十进制两位 × 4 级（容量 10⁸）——
> 代价是 ID 需要一次进制转换。**取值已定：十六进制 2 位 × 3 级**（§14 第 41 项）。

#### 为什么路径必须由 ID 推导

**因为查表会引入第二个真相源。** "ID → 路径"若靠一张映射表，这张表本身就要持久化、
要保证一致性、要参与恢复——而它能表达的信息（文件在哪）**已经由 ID 唯一确定了**，
存它纯属冗余（违反 §5.2 的字段准入纪律）。推导则零状态、零成本、天然一致。

#### 上传暂存与原子发布

资产的写入路径是**两段式**：

```text
① 上传 → 写入 staging/<asset_id>（可分块、可断点续传）
     ——**暂存名同样由 ID 推导**：同一个 ID、同一个名字，续传按推导找回
② 提交 → rename 到 assets/<v>/<s1>/<s2>/<s3>/<asset_id>
```

> **完整的上传 / 删除 / 回收协议**（七步流程、状态机、宽限期清理、
> 读取租约与回收条件）见 `spec/AST.md`（REQ-AST-007 ～ 010）——
> 本节只管**布局**：路径怎么摆、为什么能推导。

**`rename` 是原子的**，所以第 ② 步是"要么完全没有，要么完整存在"——
不会出现"元数据说资产存在、文件却只写了一半"。

> **由此得到一条硬约束**：**staging 目录必须与 assets 在同一文件系统上**。
> `rename` 跨文件系统会退化成"复制 + 删除"，原子性随即消失。
> 若资产分布在**文件系统池**（§2.8）的多个文件系统上，staging 也必须在**每个**上各有一份，
> 且第 ② 步的 rename 只在**同池内**进行。

#### 与数据文件的三处不同

| | 数据文件 | **资产文件** |
| --- | --- | --- |
| 位置 | 文件的**完整路径**记在控制文件（§2.6） | **不记**——路径由 ID 推导 |
| 可变性 | 原地更新 | **不可变**——只允许读取、范围读取与删除（REQ-AST-001） |
| 恢复 | 受 redo 保护 | **不受 redo 保护**——它是外部文件，不进 WAL |

**第一行是本节最值得注意的对比**：数据文件必须存路径（因为它的位置**不可推导**，§2.6），
资产文件**不存**（因为位置**完全由 ID 决定**）。两者不是"一个存一个不存"的随意取舍，
而是**同一把尺子量出来的两个结果**：**能推导的就不存。**

**第二行解释了第三行**：资产不可变，所以它没有"崩溃后要恢复成什么样"的问题——
一个已经发布（rename 完成）的资产就是完整的；一个还在 staging 的就是不存在的。
**这正是"内容不可变"换来的简单性。**
### 2.10 工作区在池中的放置

核心问题：**怎么保证一个大工作区有足够空间？**

答案**不是**"把工作区放到一个足够大的文件系统上"——那要求存在一个足够大的盘，
而大工作区会长到超出其中任何一个。答案是：

> **工作区不被绑定到单个文件系统。**

#### 工作区是一个跨文件系统的命名空间

工作区**不是**一个物理目录。它由一个**主位置**加若干**可散布的部分**组成：

| 部分 | 放置 |
| --- | --- |
| `control/`、`wal/`、file 0/1/2 | **主位置**（某一个文件系统）——小，且需要低延迟 |
| **数据文件**（file 3+） | 池中**任意**文件系统，**每个独立放置**（§2.8） |
| **资产**（`assets/`） | 按**卷**分布，见下 |

于是工作区的容量上限是**整个池**，而不是池中最大的那个文件系统。

#### 资产按"卷"分布

在 §2.9 的分片树之上，再加**一级卷**：

```text
<卷所在文件系统>/<工作区根 ID>/assets/<v>/<s1>/<s2>/<s3>/<asset_id>
```

- **卷号由 ID 的首字符决定**（16 个卷）——路径**完全由 ID 推导**，某个资产存在哪不需要记录
- **卷 → 文件系统**的映射记在**工作区控制文件**里（**16 条路径**，很小）
- ID 是随机的，所以 **16 个卷天然均分资产**——不需要主动平衡

**这一级同时解决两个问题**：

1. 资产可以**横跨池中的多个文件系统**——大用户的资产不再被单个盘卡住
2. **迁移的单位是"卷"**（一棵子树），既不是整棵 assets 树，也不是整个工作区——**粒度合适**

#### 放置：自动、指定、迁移

| 方式 | 说明 |
| --- | --- |
| **自动** | 创建时按各文件系统的**可用容量**分配：数据文件逐个选，资产卷按比例摊 |
| **指定** | 管理员可显式指定某个数据文件或某个卷落在哪个文件系统 |
| **迁移** | 数据文件按 §3.4 的 MOVE；资产卷按**整体搬迁**（同一手法） |

#### 为什么"只看当前空闲"会失败——以及我们为什么不依赖它

贪心放置有一个经典陷阱。池里两个 1TB 的盘都空着：

```text
工作区 A 预估 400GB → 放盘 1
工作区 B 预估 400GB → 盘 1 只剩 600GB → 放盘 2
A 实际长到 900GB     → 盘 1 装不下，盘 2 上却还有 600GB
                       池里总共有空间，A 却增长不了
```

**我们的设计绕开了它，靠的不是更聪明的预估，而是不依赖预估**：

> 数据文件与资产卷**都允许落在任意文件系统上**——A 长到 900GB 时，
> 新数据文件自然会落到盘 2。**不需要一开始就把 A 放对地方。**

于是"按容量自动分配"退化成一个**简单且足够**的规则：

```text
为新数据文件 / 新卷选址 → 选当前可用空间最多的文件系统
```

**选错了也不要紧**——最多是某个盘先满，**由迁移纠正**（§3.4）。
**迁移的存在，让初始放置不必精确。**

#### 空间紧张时的处置阶梯

```text
① 池中还有空间     → 新数据文件 / 新卷落到最空的盘
② 某个盘快满       → 迁移该盘上的**卷**或**数据文件**到别处
③ 池整体快满       → 加入新文件系统（§2.8），再迁移
④ 池整体满         → 报错——与 §3.3 的配额 / 物理上限走同一条报错路径
```

**第 ② 步的粒度是关键**：迁的是**一个卷**（一子树资产）或**一个数据文件**，
不是整个工作区。**整工作区迁移太贵，会让"纠正"本身变得不可行**——
而不可行的纠正等于没有纠正。

> 这条正是 §2.9 把资产切成 16 个卷、§2.8 让每个数据文件独立放置的**共同目的**：
> 它们给出的不是"更快地迁移"，而是**可执行的迁移粒度**。

### 2.11 public 工作区：实例级管理元数据的载体

**`public` 是一个保留工作区**（REQ-ISO-004：它是保留工作区与数据所有者，**不是** SQL 的 PUBLIC 角色）。
它与普通工作区的结构**完全相同**——有自己的 file 0/1/2、redo、控制文件、字典表（§3.1）。
它多出来的是**职责**：**实例级的管理元数据放在这里**。

#### 为什么放在工作区里，而不是别处

管理元数据（主体、工作区登记、配额、文件系统池）**天然要被查询、审计和批量操作**。
放在全局控制文件里这三件事都做不到——那是定长二进制、由 daemon 维护（§2.6）。

**放进一个普通工作区的普通表，它们就都免费了**：SQL 可查、事务可回滚、可建索引。
这是"用同一套机制解决新问题"的又一处应用。

#### 三张表（就三张）

| 表 | 内容 |
| --- | --- |
| **`user$`** | 主体：`user_id`、登录名、**不可逆的口令验证子**、状态、创建时间 |
| **`ws$`** | 工作区登记：`workspace_id`、**属主 `user_id`**、**`name`**、状态、创建时间、**四条配额** |
| **`fs$`** | 文件系统池：槽位号、挂载点、状态、容量与可用空间 |

**配额并入 `ws$` 而不单列一张表**：它是"按角色分设"的四个数（数据 / undo / temp / 资产，§2.2），
**每工作区一行四个列**——独立成表只会多一次关联。

**主体与工作区仍是两张表**（虽按 REQ-ISO-001 / REQ-ISO-003 是 1:1）：两者的**生命周期不同**——
用户可被停用而工作区保留，工作区可重建而主体不变。**合并会把这个差异藏起来。**

> **`system` 工作区已取消**。它只在早期讨论里出现过（"admin 元数据放 system"），
> **从未进入需求与总设**。多一个特殊工作区就多一套"谁能写"的规则、多一个启动依赖——
> **收敛到 `public` 更简单。**

#### 工作区的名字：标签，不是身份

`ws$` 有 `name` 列。**分配时可设**（`CREATE WORKSPACE ... NAME ...`），**之后可改**
（`ALTER WORKSPACE ... SET NAME = 'xxx'`）。

| 规则 | |
| --- | --- |
| **为空 = 未命名** | 显示时**回退到属主的 `user$.name`**——"分配时没设名字就默认是用户名"由此实现 |
| **默认不落用户名副本** | 若把用户名复制进去，用户名一改它就不跟着变，**成了第二个真相源**。存 `NULL` 让"跟随"这件事本身被表达出来 |
| **`SET NAME = NULL` 就是回到默认** | 即"改回跟随用户名"——这是上一条的自然推论 |
| **身份始终是 `workspace_id`** | `name` 是可以随时改的标签，任何持久引用都不得用它 |

**唯一性：只在同一属主内唯一，靠 `(user_id, name)` 上的唯一索引强制。**

REQ-ISO-006 的验收标准原文是"**同名表探测的响应与'不存在'不可区分**"。
若名字**跨属主唯一**，用户改名时得到一个"已存在"的拒绝，
就等于知道了**别处存在一个叫这个名字的工作区**——**一次改名就是一次探测**。
所以**不做跨属主唯一性检查**：碰撞只可能发生在同一属主内，那里是用户自己的东西。

**一个主体可以有多个工作区**——这一点由 REQ-ISO-012 定死：
它要求克隆"**只能在同一 owner 的范围内执行**"。**若一个 owner 只有一个工作区，
这句话就是空的。** 所以 `ws$` 的 `user_id` **不是唯一索引**。

**改名为什么不碰文件系统、也不碰控制文件**：§2.1 已定根目录用
"**服务端生成的不透明 ID，不拼接用户输入**"——名字**本来就进不了路径**。
于是 `ALTER WORKSPACE ... SET NAME` 只是 `public` 上的**一次本地事务**：
不写控制文件、不动任何文件、不影响 ROWID，也不影响 reflink 克隆（§2.7）。

**这正是把 `name` 放在 `ws$` 而不是控制文件里的收益。** 下面"位置与属性的分工"
那条判据（**可查询、可事务的管理属性 → `ws$`**）在这里又用了一次。

**`ws$(user_id)` 上加唯一索引**：这是 1:1 的**强制手段**，不是优化。
它同时使"名字在同属主内唯一"**自动成立**——不需要为此再建索引。

> **完整的工作区 DDL 面**（`CREATE WORKSPACE ... FOR USER ... NAME ...`、
> `ALTER WORKSPACE ... SET NAME`、`DROP WORKSPACE`、配额变更）属 **SQL / DDL 规格域**，
> 尚未展开。本节只定存储侧：**`name` 是 `ws$` 的一列，不是一个标识**。

#### 权限：管理元数据仅 admin 可见可写

| | 基表 `user$` / `ws$` / `fs$` | `public` 的公共数据 |
| --- | --- | --- |
| **admin** | 可读写 | 可读写 |
| **普通用户** | **不可见** | **只读** |

**普通用户对管理元数据是"不可见"，不是"只读"**——这一条是 REQ-ISO-006 逼出来的：

> 普通用户不能判断另一用户的对象是否存在；拒绝响应不得泄露名称、内容或精确规模。

`ws$` 里有全部工作区，**可读就等于泄露"这个实例上有多少工作区、谁在用"**。
所以管理元数据对普通用户**整体不可见**；`public` 的公共数据仍按 REQ-ISO-004 只读。
**这两条的落点是 §13.5 的过滤层**——一个专用层，不是散落各处的检查。

**"只读"与"不可见"都必须在引擎层落地**——不得只靠文件只读性
（§13 已点明：成熟产品的只读表空间不阻止仅改数据字典的 DDL）。

#### 建工作区：三处要一致，但没有跨工作区事务

建一个工作区要同时动三处：

```text
① 创建并初始化新工作区的文件      幂等——重复执行安全
② 在 public 的 ws$ 里登记         事务性——可回滚
③ 更新全局控制文件（登记位置）
```

而"**无跨工作区写事务**"是明确不做的（§3 的排除项）——**这三步无法原子**。

**用"固定顺序 + 每步幂等 + 可见性最后"来保证**：

| 崩在 | 系统状态 | 处置 |
| --- | --- | --- |
| ① 后 | 有孤儿文件，没有登记 | 清理孤儿（`ws$` 与文件对照即可发现） |
| ② 后 | `ws$` 有条目，但**控制文件里没有** → **该工作区不被认为存在** | 补做 ③，或回滚 ② |
| ③ 后 | 完成 | — |

**关键在顺序：控制文件最后写。** 因为"一个工作区是否存在"的判据是**控制文件里有没有它**
（§2.6：全局控制文件就是"数据库管控的文件清单"）。于是前两步崩在中间时，
系统看到的是**一个"不存在的工作区"**——而不是一个"存在但打不开的工作区"。

> **两种残留哪个更糟？** 一个"指向不存在工作区的登记"会让请求路由到空处，
> 而那个空处**还以为自己存在**——它比孤儿文件难处理得多。**所以顺序不能反。**

#### 位置与属性的分工

| 信息 | 权威 | 性质 |
| --- | --- | --- |
| **每个工作区在哪**（根目录位置） | **全局控制文件** | 启动入口；**不依赖任何工作区** |
| **属主、配额、状态** | **`public` 的 `ws$`** | 管理属性；可查询、可事务 |

**为什么位置仍留在控制文件**：启动时必须知道"有哪些工作区、各自在哪"，
**而读 `public` 需要先知道 `public` 在哪**——若清单只存在 `public` 里，就形成循环依赖。
更实际的是：**`public` 自己坏了不该让整个实例失联**（§11.8 的故障隔离）。

两处都含 `workspace_id`，靠它关联；**允许短暂不一致**——一个是文件层的，一个是管理层的。

### 2.12 工作区的生命周期

工作区有四个动作：**创建**（§2.11）、**克隆 / 分支**（§2.7）、**文件迁移**（§3.4）、
**删除**（§4.7）。它们分散在各节，但**受同一条不变式支配**——所以在这里串一遍。

#### 不变式：可见性只有一个开关，就是全局控制文件

> **"一个工作区是否存在"的判据，永远是全局控制文件里有没有它**（§2.6）。

这条贯穿全部四个动作，并直接给出每个动作的**三步顺序**：

| 动作 | ① 文件层 | ② `public` 的 `ws$` | ③ 全局控制文件 | 崩在中间的残留 |
| --- | --- | --- | --- | --- |
| **创建** | 新建并初始化（幂等） | 插入登记 | **最后写** | 孤儿文件 |
| **克隆** | reflink 复制（幂等） | 插入登记 | **最后写** | 孤儿文件 |
| **迁移** | 复制到目标（暂停写窗口内） | **不动** | 切换该文件的路径 | 见 §3.4（以控制文件为权威） |
| **删除** | 惰性回收（§4.7） | 删除登记 | **最先改** | 孤儿文件 |

**创建与删除的顺序正好相反，而这是同一条规则**：

- **建**：控制文件**最后**写 → 崩在中间时，系统看到的是**一个不存在的工作区**
- **删**：控制文件**最先**改 → 崩在中间时，系统看到的同样是**一个不存在的工作区**，
  留下的是**孤儿文件**，由后台惰性回收

> **两种残留，哪个更糟？** 一个"指向不存在工作区的登记"会让请求路由到空处，
> 而那个空处**还以为自己存在**——它比孤儿文件难处理得多。
>
> **所以"存在"这个状态只允许翻转一次，且必须是原子的一步。**
> 控制文件就是那一步：它**定长、原地覆盖写**（§2.6），
> 这正是它适合当开关的原因——不是因为它"更重要"，是因为它**改得动**。

#### 迁移不属于"可见性"这一类

迁移**不改存在性**，所以要解决的问题完全不同：它要的是"文件正在被搬时
**写访问短暂暂停、读照常**"，于是走 §3.4 的**暂停写协议**。

**把它和创建/删除混为一谈，会推出错误的顺序**——它对"原子的一步"没有要求，
对"**窗口可控**（同盘 reflink 近瞬时；§11.6）"才有要求。

#### 四个动作都不动的东西

| 不动 | 为什么 |
| --- | --- |
| **`workspace_id`** | 它是身份；名字只是标签（§2.11） |
| **页上的 `workspace_ref`** | **连克隆都不动**——它是**数据血统**，不是工作区身份（§2.7） |
| **ROWID** | 文件 MOVE 改的是物理位置，而 ROWID 里的 `file_id` 是**逻辑文件号**（§7、§3.4） |
| **对象号 `obj#`** | **克隆也不动**——克隆是文件的 reflink 副本，字典一并复制，序号空间原样延续。两个工作区因此会有相同的 `obj#`，**这不冲突**：对象号只需**工作区内唯一**（§3.1.2） |

**四行合起来是一句话：工作区层面的动作，不改数据层面的标识。**
唯一例外是克隆——它换的是 `workspace_id`（新身份），而**刻意不换** `workspace_ref`
（同一血统）。**这个不对称是整个克隆设计的支点。**

### 2.13 审计数据的存放

REQ-OPS-003 要求审计记录身份、Agent、请求、对象 ID、动作、结果、版本与错误码；
REQ-OPS-004 要求**用户只能查看本人审计**，且 **public 发布审计独立保存**。

**存放位置：全部写入 `public`（已定案：待冻结项 53）**——用户操作审计与发布审计**同一张 `audit` 表**，
`owner` 列区分工作区（§13.5 的读侧落点）：

| 审计流 | 存在哪 | "只能看本人"靠什么实现 |
| --- | --- | --- |
| **用户操作审计** | **`public` 的 `audit` 表** | **过滤层 + 接口**（§13.5 / §13.6）——查询只命中本人 `owner` 的行 |
| **public 发布审计** | 同表 | 所有人可见、只读（REQ-ISO-004） |

> **与早先论证的差异要如实记下**：旧文把"放在用户工作区"当成隔离的免费推论——
> 那时 `public` 还没有过滤层与标准接口。**§13.5/§13.6 先于本决定立**：共享表 + `owner` 过滤 +
> 绑定期拒绝直写，使"放在 `public`"重新成为**结构性安全**（用户连这个工作区的文件都够不到），
> 并且换来旧方案给不了的东西：**删改权收归 admin**（见下）。

#### admin 与用户审计的关系（读 vs 运维操作）

**REQ-ISO-003 禁止代理读取**——admin 不能把用户工作区当查询目标。审计行在 `public`，
其**查询**同样走过滤层（只能看本人），admin 不是例外。

**但删改权收归 admin**（本决定的要点）：审计行的**删除与修改**只经**管理面闭集**——
保留期清理、合规删除等；**操作本身记入审计**（对审计的审计）。
用户（含属主）对审计行**无任何写路径**：SQL 层无 DML / DDL 入口（绑定期拒绝），接口只读。

#### 防篡改的边界（已定案：待冻结项 53）

**保护是结构性的**（三条，全部先于本决定存在或由本决定立）：

| # | 手段 | 挡住什么 |
| --- | --- | --- |
| ① | **行在 `public`**——用户工作区**没有任何文件路径**到达它（跨工作区无路径，§13） | 属主在文件层面够不到 |
| ② | **写只经引擎的审计路径**——SQL 层无 DML / DDL 入口（绑定期拒绝），接口只读 | 直写不可能 |
| ③ | **删改 admin-only**（管理面闭集），且**操作本身留痕** | 用户（含属主）改不了 |

**仍不防的（如实标注）**：基础设施层的攻破（进程被完全掌控、宿主机 root、
备份介质持有者）——这是既定的信任边界之外（§13）。**"防普通用户篡改"成立；
"合规级证据"仍需外部存证**——定期导出到工作区外的介质，属运维契约，不是本层的能力。

**`audit` 表就是 `public` 里的一张普通表**（+ `owner` 列）——不需要新的存储机制，
只需要在字典里给它一个表。这一点本身即"结构通用"的又一次兑现。

### 2.14 在线备份：快照冻结法（已定案：待冻结项 15）

**简化路线**：不逐文件协调复制，而是**暂停写一个瞬时窗口，用文件系统的时间点副本冻结整个工作区**——
快照拿到即恢复写，复制在窗口之外从容进行。

#### 流程

```text
① 冻结：拒绝该工作区的新写；等活动的写事务结束（超时 60 秒则中止并解冻，REQ-OPS-007 同规）
        并**暂停该工作区的全部控制文件更新**（检查点推进、日志切换、归档进度）
② 快照：对包含本工作区文件的每个文件系统依序打时间点副本
        （btrfs / ZFS 原生快照；LVM 薄卷快照；XFS = 窗口内 reflink 复制——§11.6）
③ 解冻：恢复写。窗口 = 毫秒~秒级；**其他工作区不受影响**
④ 从快照复制到备份介质（不暂停写）
⑤ 校验 + 写完成标记（清单与完成标记沿用 REQ-OPS-007 的判据）
```

#### 为什么这样就够：快照 ≡ 一个合法崩溃镜像

冻结窗口内，工作区的在线文件集（数据文件、undo、redo、控制文件、资产目录）**静止**——
于是对多个文件系统的**顺序快照**等价于**同一个逻辑瞬时的切面**
（这正是必须冻结的理由：文件可能分布在池里的多个文件系统上，跨卷没有原子快照）。

而"某瞬时的全部文件"**本就是一个合法的崩溃镜像**：WAL 规则 2 保证任何已落盘的页
都带着"其修改的 redo 已持久"；控制文件在窗口内不推进，故其记录的检查点与每个文件的
快照互相自洽。**因此恢复时走既有的崩溃恢复路径——不新增任何恢复机制** ✓。

#### 与克隆（§2.7）的两处刻意不同

| | 克隆 | **备份** |
| --- | --- | --- |
| 窗口内检查点 | **强制**（克隆要"开箱即用"，不允许恢复） | **不做**（要更短的窗口；恢复时由重放收敛） |
| 窗口内做什么 | reflink 克隆全部文件 | 打时间点副本（不复制内容） |

#### 备份集与"全备份后要备份 WAL 日志"

**备份集 = 快照拷贝 + 自快照点起的 WAL 归档链**（§11.10 的 PITR 起点即此快照点）：
快照内含截至快照点的在线组；快照点之后，备份任务须**持续把归档复制到备份介质**——
否则 PITR 只能到达快照点。自描述（REQ-OPS-007 的清单 + 完成标记）记录：
工作区标识、格式版本、**快照点（提交序号 + LSN）**、文件与资产清单、所需的最小归档序列号。

**资产不需要单独的"发布"步骤**：资产目录随在线文件集一同冻结，
`asset$` 状态与文件在同一个瞬时上（staging 本就不可见）。

#### 失败与降级

- 任一文件系统快照失败 → **删除已建快照 → 解冻 → 报错**（不留半个备份）。
- 冻结超时（默认 60 秒，可配）→ 中止备份并解冻（REQ-OPS-007 边界表同规）。
- 部署在无快照 / 再链接能力的文件系统上 → **回落离线一致备份**（REQ-OPS-007：
  冻结贯穿复制；代价是窗口 ∝ 数据量）。

### 2.15 离线迁移：按工作区（已定案：待冻结项 17）

**迁移的单位是工作区**——与"工作区自包含"（§13）同构；形态照 Oracle 的可传输表空间：
**"文件 + 元数据恢复数据 + 兼容校验"**。

#### 数据范围

| 包含 | 不包含 |
| --- | --- |
| **表空间文件**（file 0..N，原样物理格式——**不转换**） | **temp 文件**（瞬态，目标端重建） |
| **外部文件**（资产目录整体） | **redo 文件**（目标端重建；LSN 起点按 §2.7 的规则取"源序列下一整组边界"） |
| **元数据恢复数据**（见下） | 归档（属备份域，§2.14） |

**离线 = 静止点**：迁移要求源工作区**已关闭**（无在途七步协议、无未完成发布）——
不需要冻结窗口；资产的 staging 残留本就不可见。

#### 元数据恢复数据（本工作区 + public 侧）

迁移包要能在**任意目标实例**重建注册，所以恢复数据分两份：

| 份 | 内容 | 用途 |
| --- | --- | --- |
| **本工作区** | 工作区标识（`workspace_id`）、创建时间、血缘（`derived_from` / `derived_at_seq`）、文件清单（角色 → **相对路径**）、资产清单 | 导入端的**导入清单**（自描述，随包） |
| **public 侧** | 注册本工作区所需的最小行集：`ws$` 条目字段 + 全局控制文件的条目字段 | 导入端写入**目标实例的 public**（新分配 `ws#`） |

**`workspace_id` 必须保留**——页上的 `workspace_ref` 由它导出（§2.7），换 id 等于重写全部页；
目标实例已有同 id ⇒ **拒绝导入**（明确报错）。`ws#` 是实例级句柄，由**目标的** `seq$` 重新分配 ✓。

**控制文件路径重写**：包内文件按相对布局存放；导入端把它们放进取目标实例的池，
并把新的**绝对路径**写回导入后的工作区控制文件（§2.6）——这是导入步骤的固定一环。

#### 格式与校验

- **载体 = 目录**（规范形态；工具可另打包为单个归档，目录布局不变）。
- **数据文件本体 = 原样物理格式**（页、校验和、字节序全不动——"搬"而不是"转"）。
- **清单为文本格式**（可诊断、可演进；每包带 schema 版本字段）：文件清单
  （相对路径 + 大小 + **哈希**）、资产清单、元数据恢复数据、格式版本、**完成标记**。
- **校验三关**：① 打包端逐文件哈希 → ② 导入端逐文件比对 → ③ **兼容性预检**：
  格式版本、**字节序规则**（`REQ-PRT-003`）、页大小——任一不符**拒绝导入**，具体到条目报出
  （照 TTS 的 `TRANSPORT_SET_CHECK` 形态；但**没有跨平台字节序转换**——本库只声明一族字节序）。

#### 导入流程

```text
① 预检：兼容性三关 + workspace_id 冲突检查 + 目标池空间检查
② 放置：文件落进目标池（相对布局 → 绝对路径）
③ 重写：导入后的工作区控制文件写新路径（+ redo 起点规则，§2.7）
④ 注册：目标实例的 public 写入 ws$ 行 + 全局控制文件条目（分配新 ws#）
⑤ 打开自检：按常规打开（检查器可作入库验证）——通过后迁移完成
```

**失败处置**：①–④ 任一步失败 → 按导入清单**逆序清理**已放置的文件与已注册的行
（注册在最后，绝大多数失败发生在注册前，清理边界清晰）；**完成标记未写 ⇒ 目标拒绝视为可用**。
