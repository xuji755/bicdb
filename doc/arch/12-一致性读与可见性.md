## 12 一致性读与可见性

前面各节把零件分别定好了——§5.4 的 ITL、§6.1 的行头、§4.6 的 undo、
§11.1.4 的提交序号。**这一节把它们装成一台机器**：读一行时究竟发生什么。

### 12.1 快照：一个提交序号

TXN.md 的 REQ-TXN-001 定了语义（Read Committed 语句快照）。存储侧要补的是
"**这个序号从哪来、存在哪、何时登记与注销**"。

| | |
| --- | --- |
| **是什么** | **一个提交序号 S**——语句开始时已提交的最大提交序号 |
| **从哪来** | 读本工作区的**当前提交序号**（内存计数器；控制文件里持久化其副本，§2.6） |
| **存在哪** | **只在内存**——语句的执行上下文里。不落盘、不进页、不进 redo |
| **何时登记与注销** | 语句开始登记进**最老快照集合**，语句结束注销（§12.7） |

**"一个数就够"是本设计最便宜的一处**：提交序号把工作区内**所有**版本全序化了，
于是"可见不可见"只需要一次整数比较——不需要版本链、不需要事务状态表、不需要额外索引。

**它之所以可能，是因为没有跨工作区事务**（§3 的排除项）：
若有，"一个数"就装不下全局顺序。

**快照不加锁、不阻塞写**（REQ-TXN-005）：它只是读者手里的一串数字，
**写者根本不知道它存在**。

> **只读语句同样取快照**——否则同一语句内的两次读可能跨越一次提交，
> 看到自相矛盾的结果。

### 12.2 可见性判定：三步

判一行 R 在当前快照 S 下是否可见：

```text
① 读行头 → itl_slot（1 字节）
     0xFF  →  该行不由任何事务版本化（转发指针一类）  →  **可见**
     i     →  继续

② 读 ITL[i]，按 flags 分派
     空闲             →  该槽未被使用                →  **可见**
     已提交 / 已回滚   →  提交序号准确                 →  转 ③
     活动             →  **状态未知**——真未提交，或**已提交但没清除过**（§11.1.1）
                          →  转 ②′

②′ 用 ITL 的 txn_id **直接定位**事务表槽（三段式的用处，§4.6.3）
     代号匹配 + 已提交   →  取出准确 commit_seq  →  转 ③
     代号匹配 + 活动     →  真的未提交            →  **不可见** → §12.3
     代号不匹配（槽已换人）→  旧事务必已提交且其 undo 已回收
                             ⟹ commit_seq < 最老快照 ≤ S  →  **可见**

③ 比较 commit_seq 与 S
     commit_seq ≤ S   →  **可见**，用页上的版本
     commit_seq >  S  →  **不可见**（它晚于我的快照） → §12.3
```

**②′ 只在"没清除过"时发生，而且它不写块**（§11.1.1）——
这正是采用延迟**日志**版清除换来的性质。

**所以 §5.4 那句"可见性判定在块内自包含"要加一个前提**：

| 块的状态 | 判定代价 |
| --- | --- |
| **已清除**（被 DML 碰过之后） | **完全在块内**——两次整数比较，不访问任何别的结构 |
| **未清除**（提交后没人再改过） | **多一次事务表访问**——一次直接寻址（不是搜索），仍然很轻 |

**"不需要全局事务状态表"这条结论不变**：②′ 用的是**该 undo 段的事务表**
（每工作区、每 undo 段一份，§4.6.3），而 `txn_id` 让它成为**一次直接寻址**。
**没有一处需要"查遍所有活跃事务"。**

### 12.3 重建：在副本上应用 Undo

②③ 判为"不可见"时，读者需要**更早的版本**。做法是**在副本上应用 undo**，
**当前块原地不动**（官方文档称这种副本为 CR clone）。

**关键是它逐段回溯，而不是一次跳转**：

```text
当前块 → ITL[i] 属于 T2，commit_seq > S
   撤销 T2 对本块的修改
     ├─ 行前像            ：被 T2 改过的行恢复
     └─ **ITL 覆盖**（§4.6.2）：ITL[i] 恢复成 T2 占用它之前的内容
          →  取回 T1 与其 UBA
   再判 T1 → 仍 > S → 继续撤销
        └─ 得到 S 时刻的版本  ✓
```

**这一张图解释了本设计里四处看着可疑、实际成立的地方**：

| | |
| --- | --- |
| **行头为什么只有 1 字节 `itl_slot`** | 读到"新占用者"**不是错误判据，而是正确的起点**——历史由 undo 兜住，不由行上的标记兜住 |
| **ITL 槽为什么可以随时复用**（§5.4.1） | **覆盖 ITL 的动作自己也有 undo**，所以复用不必为读者的历史让路 |
| **为什么必须有"ITL 覆盖"这条 op** | 缺了它，回溯就**断在槽被复用的那一刻**（§4.6.2） |
| **行头字节为什么也进 undo**（§4.6.2） | 起点也要能回退——否则**回滚后字节指向已释放的槽**，更早提交的版本会被当成"无版本化"直接可见 |

**T2 即使没改过这一行**（只改了同块的另一行），也必须撤销它对**块事务信息**的修改——
**所以"每行各有一个独立的旧版本指针"这个理解是错的。**

#### 12.3.1 实现注记：回溯起点与终止（P3 切片定案）

上面那张图落在代码里，有三处必须钉死——它们决定了"能收敛"与"错了要报"：

| 项 | 定案 | 为什么 |
| --- | --- | --- |
| **回溯起点** | 取**事务表槽的 `undo_current`**（该事务最新一条记录，权威）。ITL 条目的 `undo_ptr` 只是**占用时登记的提示**——写路径可能不再追更，**不作为起点** | 与 Oracle 取 `ktuxc` 当前撤销指针、而非只信 ITL 的 `uba` 同理；且"需要撤销"的判定（§12.2 ②′）**必然触达事务表槽**——槽已复用时该事务一律可见，不会走到重建 |
| **终止符** | 每个**占用过 ITL 槽**的事务，链上必有一条**本块、该槽的 `ITL 覆盖`记录**（载荷带 `itl_slot`；旧值 `None` = 原为空闲）。它由**占用动作**写下，**先于**该事务对本块的一切数据修改——反向回溯最后才遇到它，遇到即还原 ITL 前像。**按 `payload.itl_slot` 匹配到具体槽**：遇到"更早的别的槽"的覆盖记录只跳过、不停下 | 这是"一轮回溯 = 一个条目状态严格回退"的保证；**找不到它 = 数据不一致**（有本块数据记录却无占用记录），必须**具名报错**，不得静默继续、不得复用 |
| **收敛** | 无环数据下轮数有界；三道防线各报具名错误：**终止符缺失** / **`prev` 成环**（步数 > 槽内 `rec_count`）/ **轮数上限**（前像还原后条目仍需要撤销） | 损坏数据不得造成死循环——宁可报错，不给出"看起来像旧版本"的错误答案 |

**判定的快慢路径**（§12.2 的表）在代码里对应两条捷径：已清除的 `Committed`
条目直接用**页内 `commit_seq`** 比较，不碰事务表；`RolledBack` / 空闲条目
直接可见。**只有"未清除"才多一次直接寻址。**

**链的读取是直读**：CR（与回滚）沿 `undo_current` 读的是**段文件里的字节**，
不走缓冲池。这不会读到过期版本——撤销页经池写后**立即 flush**（§11.1.2 的
实现注记），"池里的写"与"文件里的读"之间没有窗口。将来若把链读改成经池，
必须保持同一纪律，否则起点的权威性会被"池里有更新、文件里没有"破坏。

### 12.4 行迁移与跨页行怎么走这条路

**行迁移**（§6.2）——原槽位变成转发指针，新位置放完整行。转发指针**只有 6 字节
新 ROWID，没有行头、没有 `itl_slot`**，那它的事务信息从哪来？**从它指向的那一行来**：

```text
ROWID → 原槽位（状态 2：转发指针）
          └─ 6B 新 ROWID → 新位置的行 → **读它的 ITL**
```

**两条记录由同一事务写下**（迁移 = 删除旧位置 + 插入新位置），所以新行的 ITL
就是这条链的事务信息。而**转发指针本身被后续事务再次更新**时，靠 §4.6.2 的
`转发指针更新` op 撤销——恢复出旧指针，**再沿旧指针走到上一版的位置**。
**链因此可以任意长，且每一段都受 undo 保护。**

> **实现注记（P4 行迁移切片，2026-10-05）**：`cr::reconstruct` 按块重建——
> 原页上的"迁移"由 `删除` 记录的补偿撤销（转发指针还原为原行），新页上的
> 插入由 `插入` 记录的补偿撤销；两边各自跑到本块的 `ITL 覆盖` 终止符。
> 回归用例 `cr_sees_the_pre_migration_row_through_the_chain`（旧快照：原页见
> 原行、新页不见新行；新快照：原页仍是指针）。读侧"沿指针再判 CR"的执行器
> 算法随 P5。

**跨页行**（§6.3）——片段各自是 undo 页上的记录，`op` 按片段各记一条。
`rowid` 字段记的都是**头片段的 ROWID**，于是"撤销哪些片段"由链的顺序决定。

> **`itl_slot = 0xFF` 的含义：这一行不由任何事务版本化。**
> 它的取值域**恰好两类，且都不需要查 ITL**：
>
> | 情形 | 为什么是 `0xFF` |
> | --- | --- |
> | **转发指针**（§6.2） | 它**没有行头**——行体只有 6 字节新 ROWID。它的事务信息**从它指向的那一行来**（§12.4 的上一小节） |
> | **Undo 页里的 undo 记录**（§4.6.2） | 事务信息在**页级** `ITL[0]`（§4.6.1 的 `ktubhxid` 对应物），**不在行级**。再在每条记录里存一份就是重复 |
>
> **`0xFF` 不表示"已清除"**——本设计**没有行级清除**（不往行里写提交序号）。
> 插入 / 删除 / 更新过的数据行**一律指向某个 ITL 槽**，**没有例外**。
>
> **这条"没有例外"是判定的基础**：读者看到 `0xFF` 就知道这一行**不需要事务判定**，
> 而不是"需要但信息没了"。**两者天差地别**——后者必须报错，前者直接可用。

### 12.5 索引路径

**索引项不承载任何事务状态**（§5.11）——它只有一个键和一个 ROWID。
于是索引扫描的可见性判定**一律在回表时做**：

```text
索引扫描 → ROWID → （可能经转发指针）→ 数据行 → §12.2 的三步
```

**这带来一个必须写明的取舍：索引扫描可能"漏读"。**

| 情形 | 行为 |
| --- | --- |
| 语句开始后，某行被**并发删除** | 索引项已被移除 → 扫描**看不到它** → **漏读**（该行在语句开始时是可见的） |
| 语句开始后，某行被**并发修改** | 索引项仍在 → 回表后按 §12.2 判定 → 走 undo 得到旧版本 ✓ |
| 语句开始后**插入**新的行 | 索引项是新加的 → 若可见性判定通过则**会读到**（RC 允许，见下） |

**漏读是 RC 模型下的既有取舍**（§6.4 已断言），**不是缺陷**——
Oracle 同模型下亦然。**它必须在测试基线里被显式断言为"允许"**，
否则会被当成随机 bug 反复调查。

### 12.6 当前读：写路径不取快照

`UPDATE` / `DELETE` 的 `WHERE` 求值**不能取快照**——它要的是"**最新已提交版本**"：
若按旧快照判定，就会去改一个已经被别人改过的行。

| | 12.1 的快照读 | **本节：当前读** |
| --- | --- | --- |
| 依据 | 语句开始时的提交序号 S | **页上的当前内容** + ITL 的提交状态 |
| 用途 | `SELECT` | `UPDATE` / `DELETE` 的定位 |
| 锁等待 | 不等待（REQ-TXN-005） | **会等待**，并因此重启语句 |

**命中一行后要加锁**——实现方式就是**占用 ITL 槽**（§5.4），
不需要全局锁表。

**锁等待之后必须重新检查谓词**（REQ-TXN-015）：等到的行可能**已经被别人改动**，
原本满足 `WHERE` 的现在不满足了。**不重检就会改错行。**
重检失败则重启语句——**Halloween 防护（自己的插入不被自己的扫描看到第二次）
由同一条规则一并覆盖**。

**死锁**由冲突计数与等待图判定（REQ-TXN-003），解除方式是**回滚触发死锁的那条语句并重启**
（**语句级**，照 Oracle 的 `ORA-00060` 方法；事务其余部分保留）。

### 12.7 最老快照集合

**它是 undo 回收的唯一输入**（§4.6.5），所以在运行期必须随时可答"最小值是多少"。

| | |
| --- | --- |
| **在哪** | **每工作区一份，在内存**——与提交序号同域（§11.1.4） |
| **结构** | 按 S 有序的小结构（小顶堆或有序表），**取最小值 O(1)**；语句数不多，不需要更复杂的结构 |
| **登记 / 注销** | 语句开始 / 语句结束——**只在这两处动它** |
| **持久化** | 随检查点把最小值写进控制文件的检查点进度（§2.6）。那份副本的用途是恢复期判断"undo 链能否走到底"，见 §4.6.5 |

**空集时最小值为"当前提交序号"**——没有活跃快照，就没有谁需要旧版本，
undo 可以一路回收到最新（§4.6.5 的判据自然给出这个结果，不需要特判）。

> **实现注记（P3，2026-10-05）**：`bicdb-txn::snapshot::SnapshotRegistry`——
> 按提交序号排序的 `BTreeMap<CommitSeq, 句柄集合>`（取最小 `O(log n)`、
> 注销 `O(log n)`；同一序号可被多个语句持有）；`register`/`release`/
> `oldest(current)`/`len`。P3 单写者下为普通结构，P4 并发按"读路径唯一共享点"
> 包一层闩锁（名册已在 NFR 点名）。

> **它必须是每工作区的**：undo 是每工作区的（file 1），提交序号也是每工作区的，
> 所以"谁还需要旧版本"这个问题只在工作区内才有意义。

### 12.8 "快照过旧"的检出点

**先分清主次**：§4.6.5 的两个来源里，**只有第一个会真的发生**（undo 已被回收）。
第二个（事务表槽位被复用）在我们的复用条件下不成立——读者反而能给出确定结论
（§12.2 的 ②′）。

**所以这一节只防一件事：undo 没了。** 而它一定会发生——
§4.6.5 开头那个"跑了十分钟、期间该行被反复修改又被删除"的查询就是它。

| 检出点 | 判据 | 代价 |
| --- | --- | --- |
| **取得快照时** | 对照 undo 的回收水位，发现"我要的 S 已超出生效范围" | **一次比较**——应当优先用 |
| **沿 undo 链回溯时** | 需要的下一条记录**不再属于本事务的链**（`prev_undo` 指向的位置已被复用，由 §4.6.3 的 `txn_id` 检查检出） | 一次检查 |

**第一行是新增的**：与其让语句跑了一半才发现历史断了，
不如**在取快照时就判断它是否还可能被满足**——
**代价一次比较，收益是把错误从"跑了一半"提前到"语句开头"。**

**处置由 §4.6.5 定**：空间耗尽时**宣布最老的那个快照过期**，其持有者在下一次判定时报错，
回收水位随即前移——**牺牲读者，保住写者**。

> **绝不静默降级**：任何一处检出都返回明确错误（REQ-TXN-017）——
> **宁可失败，不可返回错误的历史版本。失败是可恢复的，静默错误不是。**
