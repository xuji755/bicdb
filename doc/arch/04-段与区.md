## 4 段与区

### 4.1 区

- **区 = 8 页 = 128KB**（16KB × 8），一次分配的单位。
- 连续区减少碎片；小对象的浪费由"按需申请/释放区"控制。

**区大小固定为 8 页**（V1.0 冻结）。**"固定"这个选择买到四样东西**：

| 买到 | 在哪 |
| --- | --- |
| 分配器**无需按大小匹配**——任何空闲区都能顶替任何空闲区 | §4.4 |
| 区映射条目**可相邻合并**，条目数随**碎片度**增长而非随区数增长 | §5.11 |
| **临时段池无需按大小匹配**——池里任何一块都能顶替任何一块 | §4.8 |
| 段内位图的**粒度固定** | §4.5 |

**代价**：大对象的连续分配不如变长区灵活。**但这条在我们的画像下不成立**——
本库没有 LOB（§6.6），超长值走行片段链（§6.8），需要"更大的连续块"的场景本就少；
而连续分配 + 相邻合并之后，段的物理布局仍然是连续区间（§5.11）。

> **`长度` 字段仍然保留**（§5.11 的区映射条目）——**格式不为当前取值写死**。
> 将来若要引入变长区，不必改条目格式，只需让分配器开始产出不等大的值。

### 4.2 段

**段 = 段头 + 区映射 + 段内位图 + 数据页**（§5.11 有完整结构与布局）。
其中**只有段头是段的锚点**——它是段的第一页（`page_type = 7`），记录：

| 项 | 说明 |
| --- | --- |
| 段类型 | 数据 / 索引 / 邻接 / Undo / 临时 / ANN |
| **表选项副本** | `logging`、`update_mode`、`cleanup` 等 |
| **`itl_max`** | 本段各页的 ITL 槽上限（对应 Oracle 的 `MAXTRANS`）。**段级属性，存于此而非页头**——见 §5.4 |
| **区映射头** | 条目数、**起始位图页**、**溢出链**（§5.11） |
| **区映射条目** | **起始 RDBA + 长度**，逐个区但**相邻者合并**——参 Oracle 的 `ktetb` |
| 高水位（HWM） | 见 §4.3 |
| 追加位置 | append-only 表的下一可写位置 |

**表选项存在段头**：引擎打开段即可分派行为，不必回查目录；段自描述，利于单文件恢复。

**区映射是段的一部分，不是段头的附属**：段头装不下时**溢出到区映射续页**
（同 `page_type = 7`，链式）——参 Oracle 的区映射块（EMB）。**溢出本身是碎片信号**（§5.11）。

### 4.3 高水位与两类表

**HWM = 段内"已格式化且可能含数据"的边界，删除不降低 HWM。** 堆表下全表扫描会扫过空块。

| 表类型 | HWM 策略 |
| --- | --- |
| `update_mode = in_place` | 采用 HWM；配合段收缩（`TRUNCATE`/重组）回收 |
| **`update_mode = append_only`** | **不需要 HWM**——追加位置由段头显式记录；`cleanup = segment_drop` 时整段丢弃，不存在空扫问题 |

> 这是 append-only 相对堆表的**实质优势**：省掉 HWM 空扫代价，TTL 退化为整段操作。

### 4.4 段的空间管理

| 表类型 | 空间管理 |
| --- | --- |
| `in_place` | 页内空闲区 + defrag（§5.4）；页由位图分配 |
| `append_only`（保留版本） | 顺序追加；旧版本按 `version_keep` **内联淘汰**（插入版本 N 后删除第 N−keep 个） |
| `append_only` + `segment_drop` | **按时间分段**，TTL 到期整段丢弃 |

### 4.5 段级空间管理（插入时选页）

插入一行前先要回答"**插到哪一页**"。页可能有几十万个，不能线性扫描，需要一个段级的空闲页索引。

**采用分级位图**（参照 ASSM，但**简化为两级**）：

```text
段头
 └── 空闲级别位图页（`page_type = 8`，`kind = 1`；页体见 §5.11）
      每页 2 位 → 4 个空闲级别；**一个位图页管 65216 页 ≈ 1GB**
```

| 级别 | 可用空间（占**页体**的比例） | 说明 |
| --- | --- | --- |
| **0** | **< PCTFREE 阈值** | **FULL**——**不接受插入**，但仍允许 UPDATE 使用预留空间（§5.9） |
| **1** | `[PCTFREE, 1/3)` | 低 |
| **2** | `[1/3, 2/3)` | 中 |
| **3** | `≥ 2/3` | 高 |

**边界为什么用"占页体的比例"而不是绝对字节数**：页体大小是固定的（16312B，§5.11），
比例与绝对值一一对应，但**比例对 0 级与 PCTFREE 的关系更自然**——
0 级的上界**就是** PCTFREE 阈值，两者是同一个数，不需要各写一遍。

**插入流程**：由行长度估算所需空间 → 选定目标级别 → 在该级别中找一页 →
若实际放不下，**升到更高一级重试**（更高的级别有更多空间）。

> **方向不能写反**：级别 0 是 FULL、3 是"高"，放不下要的是**更多**空间，所以是**升级**。
>
> **级别本身是粗的**（只有三档可插入），所以"估算→选级→放不下→升一级"是常态而非异常。
> **粗粒度是有意的**：级别只用来**缩小候选页的范围**，真正的判定是插入时看实际剩余空间。

**段头保存"最后使用的位图页"提示指针**（`插入提示`字段，参照 ASSM 段头的插入提示字段），
避免每次插入都从头扫位图。段头页的完整页体布局见 §5.11。

> **与成熟产品的差异（有意为之）**：成熟产品的 ASSM 用 **L1/L2/L3 三级位图块树**管理。我们简化为两级——**单工作区的段规模远小于通用库的表**，三级树的收益抵不上其复杂度。这与"轻量级、尽可能高效"一致。
>
> **待冻结**：位图块覆盖的页数、级别划分的具体阈值。

### 4.6 Undo 段：事务表与 Undo 页

Undo 位于 **file 1**。它承担**两种**用途，且二者的要求不同（REQ-TXN-006）：

1. **回滚**——撤销未提交的修改
2. **一致性读**——重建某行在旧快照下的版本

第二条决定了保留策略：**读路径不得因写事务而阻塞**（REQ-TXN-003），所以 undo **不能在提交后立即回收**，
必须保留到"再没有任何快照需要它"为止。

参照 Oracle 的四个结构——`KTUBH`（Undo 块头）、`KTUXE`（事务表槽）、`KTUXC`（事务表控制），
以及回滚段头块的分区——以下是逐项取舍。

#### 4.6.1 Undo 页：与堆表页同构的页体

Oracle 为 undo 块定义了专用块头 `KTUBH`。逐字段对照后，**其中只有一项在通用页格式里没有对应物**：

| Oracle `KTUBH` | 我们的对应 |
| --- | --- |
| `ktubhxid`——唯一使用该块的事务 | 页头 `ITL[0].txn_id`。**一个 undo 页同一时刻只服务一个事务**（Oracle 亦然，这是其明确的隐含假设），故一个 ITL 槽足够 |
| `ktubhcnt`——记录数 | 页头 `slot_count` |
| `ktubhidx`——记录偏移表 | 槽位目录（§5.7），同构 |
| `ktubhflg`——标志 | 页头 `flags` |
| `ktubhseq`——块序列号 | **不需要**——改用链式寻址（见下） |
| `ktubhirb`——回滚起始记录 | **不需要**——我们恒从链上最新记录回滚。Oracle 需要它，是因为两阶段提交可能要求部分回滚 |
| `ktubhicl`——收集阶段记录 | **不需要**——不支持两阶段提交 |

**记录地址与序列号——Oracle 的 UBA 与我们的 `prev_undo`**：Oracle 用 UBA
（= `DBA` + 块序列号 + 记录号）标识一条撤销记录，**块序列号在区切换时递增，用于判定 UBA 是否仍然有效**；
块序列号与记录号还参与 redo↔undo 的配对校验（`ORA-600 [4137]` / `[4194]`：新增记录号必须等于块内最大记录号加一）。**我们两个都不要**：

| Oracle 机制 | 我们的替代 | 为什么足够 |
| --- | --- | --- |
| UBA 的 `seq#`（块序列号，区切换递增） | **回收判据**（§4.6.5） | 陈旧地址**在活跃窗口内不可达**——"还有引用的 undo 必存活"由回收判据保证；回溯时的占用者核对由 `txn_id` 检查兜底（§12 的回溯表） |
| 块内 `rec#`（单调记录号） | **槽号即地址**（D-06：从 1 起） | 重放幂等由**页级 LSN 守卫**承担，不需要"记录号 = 最大 + 1"的配对校验 |

**undo 页只需一个 ITL 槽**（`ITL[0]`），记录"这个页当前由哪个事务使用"。
`ITL[0].undo_ptr` 在 undo 页上**不使用**——因为 undo 链是**记录级**而非页级（§4.6.2），
页这一层不参与，也就不需要在页上再挂一条链。

> **结果**：undo 页的页体**与数据页相同**（槽位目录 + 记录区）——但理由不是"统一"（§5.1），
> 而是**访问模式相近**：两者都装变长记录、都要按槽号随机访问。若将来实测发现差异，
> 按 §5.1 的原则，undo 页体可以自行演化。
> 页头 68 字节、槽位目录、行区从页尾向上生长、ITL、校验——全部照旧。

**undo 页受 WAL 保护**：对 undo 页的修改**同样产生 redo**（§11.1.2）。否则崩溃后 undo 自身无法恢复，未提交事务就再也回滚不了——**这不是"顺带"，是恢复正确性的前提**。

#### 4.6.2 Undo 记录的结构

**Undo 链是"记录级"的，不是"页级"的**——这一点统摄整节。

- 数据页的 `ITL.undo_ptr`（§5.4）指向**一条 undo 记录**：该事务在这个页上最后一次修改写下的那条
- 每条 undo 记录内部存**前一条的位置**，沿它走就能回溯该事务的全部修改
- 于是**整个事务只有一条 undo 链**（事务表槽的 `undo_current` 是链头），
  而各页的 `ITL.undo_ptr` 只是链上的**入口点**

```text
事务表槽.undo_current ─▶ [记录 n] ─▶ [记录 n-1] ─▶ … ─▶ [记录 1] ─▶ 0
                           ▲              ▲
数据页 A 的 ITL.undo_ptr ───┘              │
数据页 B 的 ITL.undo_ptr ──────────────────┘
```

> 图中的 `ITL.undo_ptr` 是**登记时的快照性提示**（"该事务曾在本块活动"）；
> 回溯的**起点一律取事务表槽的 `undo_current`**——它才是不落后的"当前位置"
> （§12.3.1）。两者并存时不冲突：事务表是权威，ITL 是线索。

**两个用途共用同一条链**：

| 用途 | 入口 |
| --- | --- |
| **回滚整个事务** | 事务表槽的 `undo_current`（链头），走到底 |
| **一致性读某一行** | 由本块 ITL 条目的 `txn_id` **直接定位事务表槽**，取**槽的 `undo_current`** 回溯（ITL 的 `undo_ptr` 只作占用时的提示，不作起点）；走到本块的 `ITL 覆盖`记录即还原 ITL，再判更早的占用者，直到该行在快照下可见（§11.2、§12.3.1、REQ-TXN-006） |

> 与成熟产品一致——知识库原文：**"每条 Undo 记录都有一条指向该事务前一条 Undo 记录的链；
> 记录可以在同一个 Undo 块里，也可以在不同块里。"**

**一条 undo 记录的内容**：

| 字段 | 宽度 | 说明 |
| --- | --- | --- |
| `prev_undo` | 6B | 前一条记录的地址（**与 ROWID 同构**：`file_id + block_id + 页内槽号`）。**0 = 链首** |
| `op` | 1B | 操作码：插入 / 删除 / 更新 / 转发指针更新 |
| `flags` | 1B | |
| `rowid` | 6B | **被修改的行**——链是全局的，一条记录可能改的是别的行 |
| 载荷 | 变长 | 按 `op` 解释，见下 |

**总长不必存**——undo 记录就是 undo 页里的一个"行"，长度由**槽位目录**给出（§5.7）。

**与 Oracle 的撤销记录（`KTUBU`）逐项对照**：

| Oracle `KTUBU` | 我们的对应 |
| --- | --- |
| `obn` / `obd` / `tsn` 对象号 / 数据对象号 / 表空间 | **不需要**——`rowid` 的 file_id + block_id 足以定位；对象号在块头（诊断用） |
| `dba` + `rci`（前一块 + 块内记录号） | **`prev_undo` 6B 合一**——一条记录的位置一个字段讲完 |
| `slt` 事务表槽号、`wrp` XID 代次 | **不需要**——链是事务私有的；`txn_id` 三段式在事务表侧管代次（§4.6.4） |
| `opc` 用户操作码 | `op` 1B（五类，见下） |
| `flg`：0x01 多块头片 / 0x02 多块尾片（Oracle8+） | `flags` 1B **同位采用**——**多片头 / 多片尾**（见下） |
| `KTUBL`（首记录内嵌上一控制 UBA / SCN） | **不需要**——不支持两阶段提交；事务表槽（§4.6.4）自己管前值 |

**超长的撤销记录跨页**：一条 undo 记录放不下一页时（**最大行的删除前像**接近 16KB、或大向量的列前像），沿 §6.3 的行片段链**跨页**——首片带"多片头"标志、尾片带"多片尾"，**`prev_undo` 恒指向首片**；上限照 §6.3（64 片）。依据：Oracle8+ 的跨块撤销记录用的是同一套标志位（0x01 / 0x02）。**回收以"记录"为单位**——片不单列，判据仍作用于其所属事务（§4.6.5）。

**载荷按操作码解释**：

| `op` | 载荷 | 撤销动作 |
| --- | --- | --- |
| **插入** | 无 | 删除该行 |
| **删除** | 整行旧值（**含行头**） | 恢复该行 |
| **更新** | **旧 `itl_slot` 1B** │ 变更列的**前像列表**：`列号 2B \| 旧值长度 2B \| 旧值` × n | 逐列写回旧值，并还原行头字节 |
| **转发指针更新** | 旧的转发目标（6B） | 恢复旧指针 |
| **ITL 覆盖** | **被覆盖的旧 ITL 内容**（24B），或"原为空闲" | 恢复该 ITL 槽 |

> **实现补充（P3 回滚切片落地）**：
> ① **`ITL 覆盖` 的载荷带"ITL 槽号 1B"**——它是唯一不针对某一行的（块级）
> 动作，记录里的 `rowid` 只借其 file/block 定位块；没有槽号就落不了笔。
> 共 25B：`itl_slot 1B │ 旧内容 24B`（全零 = 原为空闲）。
> ② **删除保留槽的偏移**（只翻状态位）：回滚"删除"要**原位**整行写回，
> 偏移归零会让原位恢复无从落笔。行区只向下生长，故原区域必在现
> `free_end` 之上——defrag 会破坏这一点，回滚检测到即明确报错。
> ③ **"更新"类回滚暂缓**：它的补偿是"逐列写回旧值"，而列在行内的偏移
> 依赖**行布局（定长区宽度，§6.1）**——由行/更新切片接入；本切片明确
> 拒绝（不静默半做）。
> ④ **并发写者（P4）的硬规则**（由本切片明确）：**删除尚未提交时其槽位
> 不得被复用**——否则"删除"的原位恢复会落在新行上。本库 P3 单写者下
> 不会发生；P4 实现插入路径时钉住（槽位需携带线索或插入前查 ITL）。

> **跨页行（§6.3）的删除前像**：**链上每个片段各有一条**删除记录——各含**该片段的全部字节**
> （与普通行的"整行旧值"同规，合计 ≈ 一行大小）。片段槽位与普通行槽位**同规复用**，
> 一致性读由整片段旧值 undo + `ITL 覆盖`照常兜住——**不需要任何特判**。

**`ITL 覆盖` 是五类里唯一不针对某一行的**——它是**块级**的。
**覆盖一个 ITL 槽本身就是一次块修改，因此它自己也要受 undo 保护。**
没有这条记录，槽一旦被后续事务复用：

- **回滚**：回不到原占用者的状态
- **一致性读**：重建 CR 块时走不到更早的 UBA——**历史断在这里**

有了它，重建是**逐段回溯，而不是一次跳转**：

```text
读当前块 → ITL[i] 属于 T2，其 commit_seq > S  →  不可见
   撤销 T2 对本块的修改
     ├─ 行前像：被 T2 改过的行恢复
     └─ ITL 覆盖：ITL[i] 恢复成 T2 占用它之前的内容
          →  取回 T1 与其 UBA
   再判 T1：commit_seq 仍 > S  →  继续撤销
        └─ 得到 S 时刻的版本  ✓
```

**最后一步的含义要特别指出**：T2 即使**没有**改过这一行（只改了同块的另一行），
也必须撤销它对**块事务信息**的修改——否则取不回被它覆盖的 T1。

> **所以"每行各有一个独立的旧版本指针"这个理解是错的。**
> 行上只有一个 1 字节的 `itl_slot`，它**不需要代次、也不需要被清扫**：
> 读者读到"新占用者"**不是错误判据，而是正确的起点**——
> 历史由 undo 兜住，而不是由行上的标记兜住。

**"历史由 undo 兜住"有一处必须补全** ✗✓：**行头的 `itl_slot` 字节自己也会变**——
一个事务**首次**修改某行时，会把这个字节改指到自己的槽（§5.4.2）。
不把旧值记下来，就留下这样一个洞：

```text
T1 改行 R 并提交（R 的字节 = T1 的槽 k，提交序号 seq₁）
T2 改行 R（字节改指自己的槽 j），随后回滚
     → 内容还原到 T1 的版本；槽 j 释放；**字节仍指着 j**
快照 S < seq₁ 的读者：
     字节 j → 槽 j「空闲」→ §12.2 判"不由任何事务版本化" → 可见 ✗
     —— 读到的却是**晚于自己快照的 T1 版本**，且没有任何入口能发现
```

**所以旧字节随载荷还原**（上表的"更新"与"删除"两行）——
**行头字节是版本链的锚，锚的移动也要能被撤销** ✓。
**邻接条目同规**（§5.11）：条目的 `itl_slot` 同样随载荷还原——这一点上条目与行没有区别。

**更新只存被改列的前像，不存整行**——这是 undo 体积的关键：改一列就只存一列（外加行头字节 1 字节）。

> **地址用 6 字节物理位置而非 LSN**：undo 记录的位置是**页内的物理位置**，
> 与 `ITL.undo_ptr` 的宽度一致（§5.4），回滚时可直接寻址、不必先定位日志。
> **LSN 是日志的位置，不是 undo 的位置**——两者不可混用（CONV §3）。

#### 4.6.3 事务表：undo 段头页中的一组槽

事务表放在 **undo 段头页（`page_type = 7`）的页体**中——与 Oracle 把事务表放在回滚段头块一致。
段头页的其余部分（区清单、HWM）沿用 §4.2 的通用格式。

> **三个"复用"是三件不同的事**——判据与后果都不同，这一条最容易混成一件：
>
> | 复用谁 | 判据 | 复用后如何找回历史 |
> | --- | --- | --- |
> | **ITL 槽位**（§5.4） | 事务已提交、`lock_cnt = 0`，且**该槽已被清除**（§11.1.1 的 DML 清除） | **靠 undo 兜住**——覆盖 ITL 的动作本身有 undo（§4.6.2 的 `ITL 覆盖`） |
> | **事务表槽位**（本节） | 该事务已提交**且其 undo 已回收** | **靠 `txn_id` 的代号检出**——换人即蕴含"该版本对所有有效快照可见"（§12.2 的 ②′） |
> | **undo 空间**（§4.6.5） | `commit_seq < 最老快照` | **找不回，也不该找**——报"快照过旧" |
>
> **ITL 槽位的复用最宽松**：不必等所有旧查询结束，也不必等旧 undo 过期。
> 三者的判据逐级变严，正是因为**它们各自的历史由不同的东西兜住**。

每个槽对应 Oracle 的 `KTUXE`（其大小为 40 字节）：

| 字段 | 宽度 | 说明 |
| --- | --- | --- |
| `state` | 1B | 空闲 / 活动 / 已提交 / 待回滚 |
| `commit_seq` | 6B | 提交序号 |
| `undo_current` | 6B | **undo 链的链头**——该事务最新一条 undo 记录的位置（§4.6.2） |
| `rec_count` | 4B | 链上记录数——容量与回收判断用 |
| `next_free` | 2B | 空闲槽链表 |
| `wrap` | 4B | **槽重用代次**——见下 |

字段合计 **23B，对齐后每槽 24B**。

**`txn_id` 是三段式：由它可以直接算出这个事务在哪个槽**（§5.4 的 ITL 里放的就是它）：

```text
txn_id 6B = usn 8 | slot 8 | wrap 32
```

| 段 | 位宽 | 来自什么 |
| --- | --- | --- |
| `usn` | 8 | 每工作区的 undo 段数上限（256）——V1.0 只用 1，余量留给将来 |
| `slot` | 8 | **事务表的固定槽数 256**（见下）——与它同一个数 |
| `wrap` | 32 | 槽里 `wrap` 字段的宽度，4 字节整 |

**为什么是三段式而不是一个全局序号**：`txn_id` 的职责是**定位**，不是**排序**——
把"哪个 undo 段的哪个槽"直接编进去，**拿到 `txn_id` 就能 O(1) 找到槽**，
不必扫描、不必另建哈希。谁需要这个直接寻址：

| 路径 | 它拿到什么 |
| --- | --- |
| **恢复** | 一个残留 ITL 的 `txn_id` → 该事务的槽 → `state` 与 `undo_current`，据此决定回滚还是等待 |
| **锁等待与死锁检测** | 持锁方的 `txn_id` → 它的状态与等待对象 |
| **诊断** | 由页上任何一个 `txn_id` 反查是哪个事务 |

#### `txn_id` 与 `commit_seq` 是两种不同性质的标识

这一条最容易并成一类，而它们的要求恰好相反：

| | **`txn_id`** | **`commit_seq`** |
| --- | --- | --- |
| 职责 | **定位**——找到事务表槽 | **排序**——判可见性 |
| 要求 | **实例运行期内不重复**即可 | **全局单调、永不复用** |
| 可否回绕 | **可以**——靠 `wrap` 区分同槽的历次占用 | **不可以** |
| 回绕的后果 | 认错事务（因而必须防） | **可见性判据失效** |
| 何时分配 | 事务**开始**时 | 事务**提交**时 |

**只有 `commit_seq` 需要"几千年不回绕"这个性质**——因为可见性判据是
`commit_seq < 最老快照`，任何一次回绕都会让新事务被误判成"很老"。
**`txn_id` 完全没有这个负担**：它不被比较，只被用来寻址——
**它甚至不能用"提交时才分配"的号**，因为锁判定发生在提交之前很久。

> **两个号也不能合并成一个。** 若拿"事务开始时分配的号"当提交号，
> 一个"先开始、后提交"的事务就会拿到**偏小**的序号，可见性判据失效；
> 反过来若拿"提交时的号"当事务号，这个事务在开始到提交之间就**没有身份**，锁无从判定。

**槽被重用不会认错事务**：靠 `wrap`——**`(槽号, wrap)` 才是完整身份**。
`wrap` 正是 §7 曾考虑过、最终**没有**给 ROWID 加的那个"代次"。两处结论相反，
因为情形相反：

| | 旧标识残留时 |
| --- | --- |
| **ROWID**（不加代次） | 指向的是**新行**——这正是"不得作为对外持久引用"要表达的（§7） |
| **`txn_id`**（加代次） | 必须被**判定为不是自己**——否则锁会被误认为仍被持有 |

**`wrap` 真正防的是什么**——不是行锁，是 **undo 链的误入**。

undo 页的页头 `ITL[0].txn_id` 记录"**当前唯一使用该块的事务**"（§4.6.1）。
沿 `ITL.undo_ptr` 走一条 undo 链时，**每一页都要用它确认
"这块 undo 仍然属于我以为的那个事务"**。若没有 `wrap`，一个被重用的槽
会让陈旧引用**恰好匹配**，于是读到**另一个事务**的 undo——
那是静默的错档，回滚会写回错误的旧值。

所以约束来自**引用必须在实例运行期内可区分**，而不是来自锁。
**行锁反而用不上它**：锁的判定还要看 `flags` 为活动（§5.4、§5.4.1），
已提交的槽本就不算"被锁"。

**为什么"实例运行期内不重复"就够**——跨重启为什么可以不要求：

| | 恢复结束时它的状态 |
| --- | --- |
| **未提交事务** | 全部回滚，其 ITL 槽不再指向任何活着的链 |
| **已提交事务** | 可见性靠 `commit_seq` 判定，**不看 `txn_id`** |

**恢复结束后，系统里不存在"仍被引用的旧事务"**，因此 `wrap` 归零是安全的。
`txn_id` 的要求范围由此精确地是"**一次实例运行期**"，多一分都不需要。

**事务表承担两件事**：**由 `txn_id` 直接寻址**（定位），
以及**恢复时枚举活动事务**（扫描）。

**槽数必须固定，且是"与区映射同页共用"逼出来的。** 这一条容易漏：

undo 段头页（§5.11）的页体**同时**装着事务表与**区映射**——两者共用 16312B。
所以槽数**不是"页能装多少就多少"**（那是 679 槽），必须**先扣掉区映射**：

```text
页体可用              16312B
  减 段头公共部分        60B
  减 事务表 N × 24B
  余下全给区映射条目（6B/项）
```

**取 N = 256**：事务表占 6144B，段控制 24B（`KTUXC` 的对应物，§4.6.4），
区映射余 **10084B → 1440 项**（7B/项——宽度修正见 §5.11"区映射条目"）。

> **两处数字的由来**（P3 undo 切片落地时精确化）：原写"10108B → 1684 项"
> 是按 **6B/项**且在扣掉段控制之前算的；条目宽度修正为 **7B**（RDBA 5B +
> 区数 2B，§5.11）后为 16312 − 60 − 6144 − 24 = 10084B ÷ 7 = **1440**。
一个 2GB 的表有 16384 个区，但**相邻合并**后只需几项（§5.11 的区间式清单）——
1440 项对正常布局绰绰有余，**溢出本身就是碎片信号**。

**N 就是该 undo 段可承载的并发写事务上限。** V1.0 单工作区、单 undo 段，
256 对"一个用户的工作区"是宽松的。**取值已定：N = 256**（§14 第 28 项）。

**刻意省略的 `KTUXE` 字段**：

| Oracle 字段 | 为什么不要 |
| --- | --- |
| `PTX` 父事务 | 为并行 DML 服务，我们不做 |
| `UEL` 的**双重用途** | Oracle 让活动槽用它存"起始区号"、非活动槽用它存"下一空闲槽"——一个字段两种语义。我们**拆成 `undo_current` 与 `next_free`**，不再重载 |
| `DU2` 保留时间 | 我们有明确的提交序号，不需要按秒的保留窗口 |

#### 4.6.4 段控制：`KTUXC` 的对应物

紧跟事务表之后：

| 字段 | 对应 | 说明 |
| --- | --- | --- |
| `reclaim_seq` | `ktuxcscn` | **已回收到的提交序号水位**——低于它的 undo 已被复用 |
| `commit_head` / `commit_tail` | `ktuxcchd` / `ktuxcctl` | **提交链表**：已提交但未回收的事务按提交序号串成链，回收从链头（最老）开始 |
| `slot_count` | — | 事务表槽数 |
| `free_head` | — | 空闲槽链表头 |

**省略**：

| Oracle 字段 | 为什么不要 |
| --- | --- |
| `INC` 化身号 | Oracle 用它给**同一个槽的历次占用**编号，是 `KTUXE` 里与 `wrap` **并列的第二个代次**。我们**只留 `wrap` 一个**——两个代次描述的是同一件事（§4.6.3），留两个只会产生"哪个才作准"的问题 |
| `FBP` 空闲块池 | 我们不缓存空闲 undo 块，**直接走区分配**（§4.1）——多一层缓存就多一处需要恢复的状态 |
| `UBA` 两阶段提交保护 | 不做分布式事务 |
| `MGC` / `VER` / `XTS` / `OPT` | 用途未明或与本设计无关 |

#### 4.6.5 保留与回收：由最老快照封顶

**回收判据**（唯一的）：

> 事务 T 的 undo 可回收 ⟺ T **已提交** 且 `T.commit_seq < 最老快照提交序号`

**为什么是这个条件**：设最老活跃快照为 `S_min`。对任意活跃快照 `S`（`S ≥ S_min`），
凡 `commit_seq < S_min ≤ S` 的事务在所有活跃快照下都**可见**——沿 undo 链反向重建时**不会越过它**。
故它的 undo 不再被任何快照需要。

这正是 §2.6 让控制文件记录**"最老快照提交序号"**的原因：它既是 undo 可用空间的下界，
也是崩溃恢复时判断"undo 链能否走到底"的依据。

**回收顺序**：从 `commit_head` 起，把满足上式的**连续前缀**出链，并推进 `reclaim_seq`。

#### 长快照：一个必然会遇到的场景

**这不是理论问题，是我们一定会遇到的。** 典型形态：

> 一个大查询在 T 时刻开始（快照 S），跑了十分钟还没结束。
> 期间它要读的那一行被**多次 update，最后还被 delete 了**——而它**尚未读到**那一行。

**这个查询应当能正常完成**，在本设计下它**确实能**。靠两处机制：

| 环节 | 靠什么 |
| --- | --- |
| 那一行的**多次修改** | 每个事务的 undo 记录自带前像（§4.6.2），沿链逐条回退到 S 时刻的版本 |
| 那一行**最后被删除**，且槽位可能被新行复用 | 删除的 undo 带**整行旧值**；而槽位被新行占用后，撤销新事务时会**恢复它覆盖掉的旧 ITL**（§4.6.2 的 `ITL 覆盖`），从而接回被删事务的链 |

**第二行是"槽位复用不破坏一致性读"的完整答案**，它依赖 `ITL 覆盖` 那条 op——
**缺了它，一次"删除 + 槽位复用"就足以让长查询读错。**

#### 保留由什么封顶：不是时间，是最老快照

**上面那个查询自动被保护**：它的 S 就在最老快照集合里，而它需要读的那些修改
**都晚于 S**（`commit_seq > S ≥ 最老快照`）——**判据的前半段不成立，
所以它们的 undo 一条都不会被回收。只要空间够，这个查询一定能跑完。**

> **这比 Oracle 的 `UNDO_RETENTION` 更强。** Oracle 用**时间下界**（保留至少 N 秒），
> 而且它是 **best-effort**：空间紧张时照样覆盖未过期的 undo，长查询照样报 `ORA-01555`。
>
> **我们不设时间下界**——因为**没有闪回查询**（那才是 Oracle 需要时间下界的原因），
> 而"只要还有人需要就不回收"这个下界**严格强于**"保留 N 秒"。
>
> **代价要写明**：undo 的空间需求**由最老快照决定，因而不受时间约束**。
> 一个挂很久的查询可以顶住很多 undo——**这是"更强的保证"的价格**。

#### 空间耗尽：牺牲读者，保住写者

undo 空间的**物理**上限（工作区配额，§2.2）总会到。到了怎么办？

**不覆盖，而是明确地让读者失败**：

```text
undo 空间达上限
  →  宣布 **最老的那个快照过期**——把它从最老快照集合中移除
  →  其持有者的下一次判定 / undo 遍历报"快照过旧"（REQ-TXN-017）
  →  回收水位前移，写者拿到空间  ✓
```

**两个决定要讲清**：

| 决定 | 为什么 |
| --- | --- |
| **牺牲读者，不牺牲写者** | 顶住水位的是那个长查询。让它失败，空间立刻回来；若反过来让写者失败，**故障会扩散到整个工作区** |
| **不覆盖那批 undo** | 覆盖之后读者**不知道自己读错了**——那比失败严重得多。**失败是可恢复的，静默错误不是** |

> **上限本身是配额**（§2.2 按角色设），所以"多久会撞上限"对使用者是**可预期、可调**的。
> **这正是把它做成配额而不是硬编码的原因。**

#### "快照过旧"的两个来源

它们报同一个错误码，**诊断时要分开看**，而且**主次要分清**：

| 来源 | 什么时候发生 | 缺的是什么 | 在本设计下 |
| --- | --- | --- | --- |
| **所需 undo 已被回收** | 长查询要的旧版本所在的那段 undo 不再可用 | **数据**没了 | **会有**——这是**主要**来源，见本节前两小节 |
| **事务表槽位已被复用** | 能确定旧事务已结束，却取不到它**准确的提交序号** | **判断依据**没了 | **不成立**——见下 |

第二个来源在本设计里不成立，是 `txn_id` 三段式 + 事务表槽**严格复用条件**换来的：

> 事务表槽的复用条件是"该事务已提交**且其 undo 已回收**"（§4.6.3）。
> 于是"槽已换人"这个事实**本身就蕴含** `commit_seq < 最老快照`——
> 读者用 `txn_id` 里的**代号**检出换人之后，**不需要准确的提交序号**就能判定可见
> （§12.2 的 ②′）。

**Oracle 需要"上界提交序号"这类近似机制**，是因为它的事务表槽可以**先于 undo 回收**
而复用——槽没了，准确的提交序号就永远拿不到了。**我们的复用条件更严，代价是槽周转稍慢。**

> **但这不是普适结论**：若将来为并发放宽复用条件，它会立刻回来。
> **它是"更严的复用条件"的产物。**
>
> 而且要说清楚：**消掉的只有第二个来源。第一个——undo 被回收——永远在，
> 它才是要防的那个。** 上文那两小节讲的全是它。

**两个来源都不得被静默降级成某个猜测值**——猜错就是返回错误的历史版本。

#### 4.6.6 事务的生命周期：开始、语句边界、回滚

**§4.6.2 定了 undo 的结构，§11.1.1 定了提交的次序；这里把两头补齐**——
一个事务从分配到消失的全部动作，以及每个动作**需要哪种持久化**。

**① 开始**

| 动作 | 在哪 |
| --- | --- |
| 取事务表的**空闲槽**（`free_head` 链，§4.6.4） | 内存 + 段头页（受 redo 保护） |
| 槽被**重用**时：`wrap` 推进 → 新的 `txn_id`（§4.6.3） | 同上 |
| `state = 活动` | 同上 |
| 建**内存事务对象**：槽号、语句快照、修改块清单（§11.1.1 的 ⑤）、语句回滚点、等待指针（§5.4.2） | 纯内存 |

**开始不需要任何持久化保证** ✗✓——崩溃后活动事务**一律回滚**，
"这个槽是否分配过"在恢复后无关紧要（`wrap` 归零是安全的，§4.6.3）。

**② 语句边界**

语句开始时，在内存事务对象里记下**语句回滚点** = 当时的 `undo_current`。
语句失败时（约束冲突、语句重启、死锁牺牲前的语句清理）：

- 沿 undo 链**从新到旧**反向应用到回滚点——逆操作就是 §4.6.2 的五类"撤销动作"；
- **不释放锁**（TXN REQ-TXN-003）、**不回滚**此前的成功语句；
- **不需要任何持久化动作**——回滚点只在内存里 ✗✓。

**③ 回滚一个事务**

```text
state = 待回滚                  ← 先标记：恢复能识别"未完成的回滚"
沿 undo_current 整链，从新到旧应用逆操作（§4.6.2 的五类）
    每次逆操作是一次页修改 → **各自生成 redo**（§11.1.2 的延伸）
         ——"回滚写回"也必须可重放，否则二次崩溃会把进度丢回去
链走完                          ← 该事务在任何页上都不再被引用
     （ITL 槽已随 `ITL 覆盖` 的逆操作复原）
state = 空闲；undo **立即可回收**
```

**两条结论，都从"逆操作是天然幂等的"推出来** ✗✓——
五类逆操作全是"把某处**置回**记录的旧值"（恢复旧值 / 确保不存在 / 确保存在），
**重复应用不产生额外效果**：

| 结论 | 理由 |
| --- | --- |
| **回滚中断（崩溃）= 重走整链即可**——不需要断点标记 | 整链从新到旧走完的结果 = 事务开始前的状态，**与已走了多少无关**。恢复的撤销阶段**就是普通回滚的重放**——同一条代码路径 ✓ |
| **回滚的事务无保留需求**——undo 立即可回收 | 与提交事务**相反**：§4.6.5 的回收判据只针对已提交事务，而**没有任何快照需要"回滚事务的历史"**（它在所有快照下都不可见）✓ |

**"待回滚"状态的作用**：恢复扫事务表时，`活动`与`待回滚`**都**要回滚
（§11.2 的撤销阶段）；区别在诊断与优先级——`待回滚`意味着崩溃点离完成只差一步。

**④ 事务槽耗尽**

`free_head` 为空 ⇒ **等待**（与锁等待同一套机制与超时，§5.4.2），超时 → 资源错误。
**不静默失败**——与 ITL 耗尽的第 3 步是同一纪律（§5.4.1）✓。
N = 256 对"一个用户的工作区"是宽松的（§4.6.3），但**行为必须有定义** ✗✓。

**⑤ 与恢复的接口**

恢复对活动事务的处理就是本节的 ③：分析阶段判定事务状态
（**提交记录在则前滚补标记、不在则待回滚**），撤销阶段对后者执行 ③ ✓（§11.2）。
**没有"半个提交"**：提交记录已入流的事务，其槽标记即使丢失也会被补上（§11.1.1）。

### 4.7 段的删除、失效与回收

**空间回收的粒度是段**——不是页，也不是区。

#### 删除分两步：先失效，后回收

```text
① 标记失效（事务内，一步原子）——段立刻从可见世界消失
② 回收其占用的区（延后、幂等）——空间回到可分配池
```

**为什么必须分两步**：若删除要"一步到位"，就得在同一时刻完成
"删字典行 + 清段头 + 还位图 + 释放全部区"，任何一步崩在中间都会留下不一致。
分成两步后，中间态是**明确且安全**的：

| 崩在哪 | 结果 |
| --- | --- |
| ① 未完成 | 段仍然有效——什么都没发生 |
| ① 已完成、② 未完成 | 段已失效（不可访问）；它的区**仍占着，但可被回收**——恢复时补做 ② 即可 |

#### 失效清单就在字典表里

② 需要知道"哪些段失效了"。**不新造结构**——它就是 `seg$` 的一个状态：

| `seg$` 状态 | 含义 |
| --- | --- |
| `LIVE` | 正常 |
| `DEAD` | 已失效，**区尚未回收** |

**为什么状态放字典表而不是段头**：段头是**单页**，改它可以原子完成；但反过来，
要**找出所有失效段**就得扫描整个文件。而 `seg$` 是普通表——有索引、有 WAL 保护，
找失效段只是一次索引扫描。

两步的分工正好各取所长：**段头承载"这个段还在不在"（物理真相），`seg$` 承载"该回收谁"（目录）。**

#### 回收的时机：惰性，不主动

**数据库不主动回收**——没有后台回收线程，也没有定时整理。回收发生在
**分配器找不到空闲区、正准备扩文件之前**：

```text
需要新区 → 空闲池里找
             ├── 找到 → 用
             └── 没有 → 先回收失效段（若清单非空）→ 再找
                           └── 仍没有 → 扩文件 / 新增数据文件（细节见 §3.3）
```

于是**空闲的段在"新的扩展"时被复用**——回收**由需求驱动**：
不发散、不抢占、不需要管理员干预，也不会在系统空闲时白白消耗 I/O。

**回收必须幂等**：一个段的区可能散在多个位图块上，回收过程中崩在中间是可能的。
处理方式是——**重复回收同一个 DEAD 段没有副作用**（位图重复清空是幂等的）。

```text
回收一个段：
  ① 依次清掉它占用的所有区（位图置空闲）——重复执行安全
  ② 全部清完后，删除 seg$ 的 DEAD 行      —— 最后一步，此前崩了重做即可
```

**顺序不能反**：先删 `seg$` 行再清位图，崩在中间就**再也找不到这个段**，
它占的区会永久泄漏。所以清单行**最后删**。

#### 迁移只由显式命令触发

**数据库不做任何主动迁移**——没有后台整理、没有自动 shrink、没有碎片回收扫描。
需要搬家时，由管理员的 **`Move`** 命令显式执行。

**`Move` 的语义**（对应成熟产品的 `ALTER TABLE ... MOVE`）：把段的内容**重写到一个新段**，
旧段随后失效。用途是整理碎片，或把段搬到另一个数据文件。

**它有一个必须写明的后果**：**行的 ROWID 会变**——数据搬到了新位置。于是：

> **`Move` 之后，该表的所有索引全部失效，必须重建。**

这不是缺陷，是"搬数据"的必然。也正因如此，**`Move` 是低频管理操作，不是日常手段**：
代价与数据量成正比，还附带一次全量索引重建。

#### 与 `cleanup` 表选项的关系

§8 的 `cleanup = segment_drop | row_delete` 决定**表的清理方式**，其中一条正是本节的用户：

| 选项 | 语义 | 与本节的接口 |
| --- | --- | --- |
| `row_delete` | 逐行删除，空间由页内 defrag 与区回收处理 | 段长期存在，**不触发本节** |
| `segment_drop` | **按段丢弃**——追加型表按时间分段，到期整段失效 | **正是本节机制** |

`segment_drop` 是本节最主要的用户：会话表、记忆表这类追加型表按时间分段后，
过期就是**一整段失效**——一次元数据操作，不需要逐行扫描。
这正是"回收粒度是段"的价值所在。

### 4.8 临时段（file 2）

**临时空间按段分配**——与数据段**同一套机制**（段 + 区），不另立体系。
**但它是唯一一种"分配状态不在盘上"的段**：状态全在内存的池里，重启即消失。
**这不是疏漏，是设计**——下面把它的形态写清楚。

#### 状态在内存：临时段池

**参照 Oracle 的 Sort Extent Pool（SEP）。** 它的演变恰好覆盖了我们原先写错的写法：

> **7.3 之前**：每次操作**创建一个临时段**，操作结束该段成为 drop 候选、由 SMON 清理；
> 下一次操作**重新创建一个全新的段**——"quite possibly reusing exactly the same set of blocks
> as the previous one"。代价是三重的：段创建是**空间管理操作、被 enqueue 串行化**；
> 还要**扫数据字典**找空间、**更新数据字典**登记新段与注销空闲空间。
> 用 Oracle 自己的话说，"make the acquisition of a temporary segment **potentially very expensive**"。
>
> **7.3 引入 SEP**：不再每次创建/删除，而是**把区标记为可用、留在池中**，下次直接复用。
> 池在 SGA 里，由 `latch: sort extent pool` 保护。

**我们照做**：

| | Oracle | 我们 |
| --- | --- | --- |
| 池的位置 | SGA，全实例一份 | **每工作区一份**——临时空间本来就不跨工作区共享 |
| 并发保护 | **一个** latch（有专门的等待事件） | **按 §5.10 的工作集分区**，每分区一份 |
| 段类型 | `KTATSORT` / `KTATHASH` / `KTATDATA` / `KTATINDEX` / `KTATLOBS` / `KTATBTREE` | 同一形式的**开放枚举**；V1.0 至少要有**排序**与**哈希**两种 |

**池里放的是"临时段状态对象"**（对应 Oracle 的 `X$KTSSO`，定义在 `ktst2.h`）：

```text
临时段状态对象
  归属          哪个操作在用（Oracle 存会话地址 + 序列号）
  段类型        排序 / 哈希 / …
  段头位置      file_id + block_id
  用量          已用区数、已用块数
```

**注意它不含区清单**——区清单的权威仍是**段头页**（§5.11 的区映射）。
状态对象是**池的账本**：回答"哪些段还活着、各自归谁、用了多少"，
不是第二份区映射。**两者是互补的，不是重复的。**

**复用规则**：溢出结束**不删段**——把它**留在池里**，下次同类操作直接接管；
池空才去 file 2 的 LMT 里分配新区（§5.11 的区分配图）。

#### 临时段有盘上段头——但它不是权威

Oracle 的状态对象里存着 `KTSSOFNO` / `KTSSOBNO`，字段说明是
"**absolute file # of segment header**"、"**block # of segment header**"。
**所以临时段是有段头页的**，格式与其他段头页相同（§5.11 类型 7）——机制统一。

**但它是内存中的池在同一会话内的附属物，不是持久元数据。** 两条一起保证：

- **file 2 打开即重置**（见下）——盘上遗留的段头一律作废
- **内存池与它同时清空**——两侧一起清，所以不存在"内存说 A、盘上说 B"

**这为什么不算"两个真相源"**：真相源的判据是"**它们可能各自演进、因而可能不一致**"。
而这两者**从不各自演进**——池只在 file 2 打开时与它一同从空开始，之后同生共死。
**§4.8 开头那条"不持久化"，具体形态就是"两侧一起重置"。**

#### 分配：按需取区，N ≥ 1

一个需要溢出的操作（排序、哈希、分词）开始时，向池**申请一个临时段**：
池中有现成的就直接接管，没有才创建（分配 N 个区，N ≥ 1）。不够时再追加区。

```text
溢出开始 → 池中取/建临时段（N 个区）
              └── 用尽 → 追加区（可反复）
溢出结束 → **段留在池中**，区标记为可用（不删、不还给 LMT）
```

**为什么 N 最小为 1**：N 是**按需**的。多数溢出很小，起步就给多个区是浪费；
真正大的溢出靠"追加区"接住。**N 与追加已定**（初始 1 区、倍增封顶 64 区，§14 第 37 项）。

**为什么按段而不是"散装区"**：**复用需要一个有身份的东西**。
散装区无法"留在池里等下次接管"——它没有边界、没有归属、不知道和谁是一批。
段给了这个身份：**归属明确**（诊断能回答"谁在用临时空间"）、
**一次性接管**（整段复用，不必逐区重找）、**与数据段共用申请/释放路径**。

#### 回收：不删，只标记

| | 数据段 | **临时段** |
| --- | --- | --- |
| 崩溃后 | 需要恢复（§11.2） | **不需要**——内容定义为可丢 |
| 回收方式 | 先失效、后惰性回收（§4.7） | **留在池中待复用**——不经过失效态 |
| **WAL (redo)** | 受保护 | **不记**——崩溃后整体重置，重放无意义 |
| **Undo** | 有 | **也有**——临时页用标准页头（含 ITL），故可回滚；但**只服务语句级回滚，崩溃恢复时不重放**（§5.11） |
| **分配状态** | 字典表 | **内存池** |

**为什么不删**：这正是 Oracle 7.3 那次改进的全部内容。删了再建，
等于把"空间管理 + 登记"重做一遍，而**下一批区多半就是刚才那批**。
留在池里省掉的正是这一整轮。

**为什么不需要"先失效、后回收"**（§4.7）：那套是为了**崩溃后能找回"该回收谁"**。
临时段没有这个问题——崩溃后 file 2 与池**一起重置**，那份清单本身就是多余的。
#### file 2 的打开与重置

**打开工作区时，file 2 直接重置为空**（重写文件头与页分配位图），**内存池同时清空**。

- **不需要恢复逻辑**：临时数据定义为可丢，重置比恢复更快也更简单
- **不需要判断上次是否正常关闭**：无论上次是正常关闭还是崩溃，
  临时数据在两次会话之间都没有意义
- 于是 file 2 的**页分配位图也不必进 WAL**——它跟着一起被重置

> 注意边界：§11.4"位图必须受 WAL 保护"指的是**数据文件**的位图——
> 那里丢了是**整个表空间不可用**。file 2 的位图丢了只是临时空间要重建，量级完全不同。

#### 并发与耗尽

**每个溢出操作一个临时段**——查询之间天然不共享，不需要额外隔离。
同一工作区内的多个并发查询各拿各的段，互不干扰。
**但它们共享池**——那正是池的意义：一个查询放回的区，另一个查询立刻能接管。

**池的 latch 是已知热点。** Oracle 有专门的等待事件（`latch: sort extent pool`），
诱因是**区太小**导致分配/释放过频，或排序内存太小导致溢出过频。三条对策：

| 诱因 | 我们的情况 |
| --- | --- |
| 区太小、分配释放频繁 | **区固定 128KB**（§4.1）——比 Oracle 默认的临时区大，频次更低 |
| 一个 latch 管全实例 | **按工作集分区**（§5.10），每分区一份池 |
| 变长区需要按大小匹配 | **区等大**——池里任何一块都能顶替任何一块，**无需匹配** |

**耗尽时的行为**：临时空间有上限（§2.2 的配额按角色设）。达到上限时，
该操作**失败并返回明确的资源错误**（含可重试条件），**不做"回退到内存"之类的隐式降级**——
隐式降级会让内存用量变得不可预测，而内存比磁盘更紧，不该由一次排序把它悄悄吃掉。
