## 5 页

### 5.1 页的三段：头、体、尾

**只有头和尾是全类型统一的；页体是每种页类型自己的事。**

```text
┌──────────────────────────────────────────────────────┐
│ 页头 68B（**全类型统一，不可变**）                     │
│   描述区 32B │ 事务区 32B │ 空间区 4B                  │
├──────────────────────────────────────────────────────┤
│ 页体（**由 page_type 决定，各自定义**）                │
│   数据页   ：槽位目录 + 行区（§5.7、§6.7）             │
│   Undo 页  ：槽位目录 + 记录区（§4.6.1）               │
│   索引叶页 ：**有序条目数组**（§9.1.3）                │
│   索引分支页：有序条目数组 + 最左子指针（§9.1.3）      │
│   邻接页   ：按 (src, edge_id) 聚簇的顺序区（§9.2）    │
│   ANN 页   ：metapage / element / neighbor（§9.3.3）   │
├──────────────────────────────────────────────────────┤
│ 页尾（**由 page_type 决定大小**）                      │
│   一般页 4B（仅页尾校验）；索引叶页 16B（含双链）      │
└──────────────────────────────────────────────────────┘
```

#### 页头为什么必须统一

页头承载的是**恢复与事务所需的一切**——`page_lsn`（幂等判定的依据）、ITL（可见性与行锁）、
`workspace_ref`（隔离兜底）、校验。这些是**所有页类型共同参与**的机制：
恢复要重放每一页，事务要锁每一页的行。

**若页头按类型不同，恢复路径就要按类型分支**——而恢复是最不能出错、
又最难被日常操作覆盖到的路径。这一条不可让步。

#### 页体为什么必须可以不统一

不同页类型的**访问模式不同**，强行统一就是拿一种模式的结构去套另一种。最明显的例子：

> **索引页的条目必须按键有序**（要二分查找），而**槽位目录是无序的**（按插入顺序）。
> 给索引页套槽位目录，等于让它在一个无序结构里做有序查找——
> **格式与访问模式直接冲突**。

同理：ANN 页的向量是定长的、邻接页的边是按 `src` 顺序追加的——它们都不需要
"变长行 + NULL 位图 + 变长偏移"那一整套为多列可变行准备的结构。

#### 界线划在哪

| 层 | 是否统一 | 理由 |
| --- | --- | --- |
| **页头** | **必须统一** | 恢复与事务的正确性基础；分支即意味着恢复路径分支 |
| **页尾** | 按类型 | 已如此（§5.8） |
| **页体** | **按类型自定义** | 格式服务于访问模式；强求一致是拿效率换整齐 |

**代价必须写明**：页体各自定义意味着**空间管理、插入/删除、defrag 要按类型实现**。
这是真实的成本，不是免费的灵活性。

界线的一句话版本：**页头与恢复相关的机制必须共享；页体可以按访问模式优化。**
**不为一致性付效率的账，也不为效率付正确性的账。**

> 因此 §5.7 的槽位目录、§5.9 的 PCTFREE 都是**页体层的机制**，
> 适用范围要各自说明，**不再是"所有页通用"**。

### 5.2 字段准入纪律（先于具体字段）

**页头只含"崩溃后无法重建"的落盘信息。** 判断标准只有一条：

> 这个字段，在进程崩溃重启、且**没有它**的情况下，能否从页的其余内容或外部结构**重建**？**能重建的就不进页格式。**

这条纪律比任何字段清单都重要——它是将来加字段时的取舍依据。

**由此划清与缓冲区头的界限**：

| | 页头（**落盘**） | 缓冲区头（**仅在内存**） |
| --- | --- | --- |
| 归属 | 数据块本身的一部分 | BufferPool 的内存结构 |
| 内容 | 身份、完整性、事务、空间信息 | pin 计数、latch、LRU 链指针、脏标志、touch count |
| 定义位置 | 本章 | `REQ-STO-006`，另行展开 |

**两者不必有任何字段对应关系**——缓冲区头不迁就页格式，页格式也不为缓存便利加字段。

> **命名警示**：Oracle 的 `kcbh`（字面 "kernel **cache** block header"）**是落盘的块头**；只在内存的是另一结构 `kcbbh`（Buffer Header）。两者**只差一个字母**，极易混淆——这是本节存在的直接原因。

### 5.3 描述区（32 字节）

| 偏移 | 长度 | 字段 | 说明 |
| --- | --- | --- | --- |
| 0 | 4 | `checksum` | CRC32C，覆盖全页（本字段置零后计算） |
| 4 | 1 | `format_version` | 从 1 起 |
| 5 | 1 | `page_type` | 见 §5.6 |
| 6 | 1 | `flags` | 见下 |
| 7 | 1 | `mod_seq` | 修改序列号，与页尾校验对比 |
| 8 | 8 | `workspace_ref` | 工作区受校验标识，见 [`workspace_ref设计_v0.1.md`](../workspace_ref设计_v0.1.md) |
| 16 | 2 | `file_id` | 有效 10 位 |
| 18 | 4 | `block_id` | 有效 28 位（与 ROWID 一致） |
| 22 | 6 | `page_lsn` | 最近修改的日志位置（48 位） |
| 28 | 4 | `reserved` | |

**`flags`（只含崩溃后必须存活的状态）**：

| 位 | 含义 |
| --- | --- |
| 0 | 页初始化完成（未完成的页不得使用） |
| 1 | 含跨页行片段 |
| 2–7 | 保留 |

> **不得放进页格式的状态**：「有空闲槽位可复用」可从槽位目录推导；「待回收」是运行期状态。这类信息属于空间管理/缓存层面，按 §5.2 的纪律排除。

**链指针不在描述区**——放在**页尾区**（§5.5、§9.1.1），使数据页不必付这 12 字节。

**没有 `generation` 字段**：文件重建时**分配新的 `file_id`、永不复用**，陈旧页引用由 `file_id` 不匹配检出，无需额外代次字段。

**`file_id` 与 `block_id` 分开存**（而非 pack 后的 ROWID）：页头可独立校验，且与 ROWID 位宽解耦。

**`workspace_ref` 校验成本为零**：哈希只在打开工作区时算一次并缓存，每页访问只是一次 8 字节整数比较。

### 5.4 事务区（32 字节，含默认 1 个 ITL）

**事务区头（8 字节）**

| 偏移 | 长度 | 字段 | 说明 |
| --- | --- | --- | --- |
| 32 | 2 | `itl_count` | 当前 ITL 槽数（从 `INITRANS` 起，动态扩展） |
| 34 | 6 | 保留 | 见下 |

> `itl_max` **不在页头**——它是**段级属性**（对应 Oracle 的 `MAXTRANS`），存于**段头**（§4.2）。页头只留 `itl_count`。
> `last_cleanup` 暂不设字段（我们采用即时清除，见 §11.1.1）；保留区在 P0 确认后可作他用。

**ITL 条目（24 字节，偏移 40）**

字段宽度**按本设计自身的度量推导**，不是照搬 Oracle：

| 偏移 | 长度 | 字段 | 宽度依据 |
| --- | --- | --- | --- |
| 40 | 6 | `txn_id` | **三段式 `usn 8 \| slot 8 \| wrap 32`**。**它只要求实例运行期内不重复**，可以回绕——职责是**定位**，不是排序。由它**直接算出事务表槽的位置**，这就是把它编成三段而非一个序号的理由（§4.6.3） |
| 46 | 6 | `undo_ptr` | **与 ROWID 同构同宽**：`file_id(10) + block_id(28) + 页内槽号(10)`。因 Undo 存于 file 1 的页中，物理地址比 LSN 更直接，且与已定的页复用规则一致 |
| 52 | 6 | `commit_seq` | **全局单调、永不复用**（这是 SCN 的对应物），与 `page_lsn` 同宽。48 位按 1000 提交/秒可用 8900 年。**它与 `txn_id` 的要求正好相反**——可见性判据 `commit_seq < 最老快照` 不容回绕（§4.6.3） |
| 58 | 2 | `lock_cnt` | 本事务在本块锁定的行数——ITL 槽回收条件。页内槽位上限 1024，11 位足够 |
| 60 | 1 | `flags` | 空闲 / 活动 / 已提交 / 已回滚 |
| 61 | 3 | 保留 | |

**合计 24 字节**，与 Oracle 相同。两处简化：**`wrap` 直接编在 `txn_id` 里**，不另设回绕保护字段；**无 FREELIST 空闲空间信用**（我们不使用 FREELIST）。

**各字段的作用**：

| 字段 | 作用 |
| --- | --- |
| `txn_id` | 锁冲突判定（这行是不是我自己锁的）；**并可直接寻址事务表槽**（§4.6.3） |
| `undo_ptr` | 一致性读重建旧版本时的 Undo 入口 |
| `commit_seq` | **提交序号**；未提交为特殊值 |
| `lock_cnt` | ITL 槽回收条件 |
| `flags` | 状态位 |

**`commit_seq` 是 ITL 的核心**：它让**可见性判定在块内自包含**——读一页即可判断"改这行的事务提交了没有、提交序号是多少"，**不需要任何全局事务状态表**。这是本设计敢不设全局事务表的前提。

**行锁由 ITL 承载，不用全局锁表**：一行的锁状态就是它的 `itl_slot` 所指的 ITL 条目——判断"这行被锁了吗"＝读该 ITL 的 `txn_id`；判断"是不是我自己锁的"＝比对 `txn_id`。

| | ITL 式（采用） | 全局锁表式 |
| --- | --- | --- |
| 锁信息位置 | 数据块内 | 内存全局结构 |
| 内存开销 | 无 | 与活动锁数成正比 |
| 全局热点 | **无** | 锁表是全局争用点 |
| 崩溃恢复 | 随数据页自然一致 | 需重建锁表 |

这使 `REQ-TXN-002`（行锁）的实现方式明确为"ITL 槽占用"，而 `REQ-TXN-005`（读路径不加锁）的精确含义是：**读只读 ITL 条目判断可见性，不获取、不等待任何锁**。

**默认 `INITRANS = 1`**：写并发低，1 个槽足够。

#### 5.4.1 ITL 槽的扩展与耗尽

1. 事务修改块中行前，先找空闲槽（`flags` 示空闲，或 `lock_cnt = 0` 且已提交）

> **这个条件比看上去宽松**：它**不要求**"所有旧查询都已结束"，也不要求"旧 undo 已过期"。
> 因为**覆盖 ITL 的动作本身受 undo 保护**（§4.6.2 的 `ITL 覆盖`），
> 一致性读可以沿 undo 把被覆盖的 ITL 恢复出来。**槽的复用不必为读者的历史让路。**
>
> **但它有一个硬约束：槽必须先被清除**（§11.1.1）。一个"活动"外观的槽可能属于
> 一个**早已提交但没清除过**的事务——它不能直接复用，否则那个事务的提交序号
> 就永远取不到了。**清除是复用的前置条件，不是可选的整理动作。**
>
> 三个"复用"是三件不同的事，判据与后果都不同——见 §4.6.3 的对照表。
2. 未找到则**动态扩展** `itl_count`（受 `itl_max` 限制）——页头向后推移，空闲区相应减少
3. 达 `itl_max` 仍无空槽 → 该事务**等待**，**不得静默失败**

**`itl_max` 的默认值与上限**：

| | 值 | 依据 |
| --- | --- | --- |
| **默认** | **1** | 与 `INITRANS = 1` 对应（§5.4）。画像为低写并发（§2.2），1 个槽足够起步 |
| **上限** | **32** | **页头预算**：每多一槽页头后移 24B（§5.4），32 槽 = 68 + 31×24 = **812B**，占页 **5.0%**。（64 槽要 9.6%，对"低写并发"的画像是浪费） |

**上限是段级属性**（§4.2），所以同一个上限对不同表可以取不同值——
写热点表调高，只读表保持 1。**达上限仍无空槽则该事务等待**（第 3 步），不静默失败。

#### 5.4.2 行锁的获取、等待与唤醒

§5.4 定了"锁住在哪"（ITL），§5.4.1 定了"槽从哪来"；这里定**协议**——
一次加锁的完整动作、等待者睡在哪、被谁唤醒。
**先补一条本设计一直隐含、但值得明写的分工** ✗✓：

| | **latch** | **lock** |
| --- | --- | --- |
| 保护什么 | **内存结构**：缓冲页与链、WAL 追加位、临时池（§5.10、§11.5.2） | **业务数据**：行——含顶点行、边条目、字典行 |
| 放在哪 | 内存（缓冲块头等） | **数据页内的 ITL**（§5.4） |
| 持有期 | 极短（一次页访问） | **至事务结束**（TXN REQ-TXN-002） |
| 能否长等 | 不能——**持有 latch 时不得等待业务锁**（TXN REQ-STO-007） | 能（**默认死等**；超时可选配置，D-04） |
| 参与死锁图 | **不参与** | **参与** |

**① 获取（快路径）**

```text
pin + latch 页 → 读行头 itl_slot →
   空闲槽（或 lock_cnt = 0 且已清除，§5.4.1） → 占用：行头指向该槽
                                                 （**旧字节随本行第一条 undo 记录**，§4.6.2）、lock_cnt++ ✓
   槽的 txn_id = 自己                          → 重入，完成 ✓
   槽属他人且 state = 活动                     → 记住持锁者的 txn_id，
                                                 **先放 latch**，进入等待（②）✓
```

**② 等待与唤醒**

等待的结构**按"持锁者的事务槽"组织**（内存）——因为 `txn_id` 就能直接寻址到槽（§4.6.3）：

| 记什么 | 在哪 |
| --- | --- |
| 等待者登记 `(自己的槽, 持锁者的 usn/slot, 起始时刻)` | 按持锁者挂的等待者表 |
| "我在等谁" / "谁在等我" | 各自的事务对象——两半合起来就是**等待图的一条边** |

- **唤醒**：持锁事务结束时**唤醒其全部等待者**——**不做锁移交** ✗
  （移交的竞态与实现复杂度不值；低争用画像下惊群的代价可忽略）✓；
- **醒来后从头重试**：不假设行还在原地、槽还没换人、行还存在——
  重新定位、重新判定（§12.6 的"锁等待之后必须重新检查谓词"在此落地）；
- **超时**：默认 `-1`（**死等**；可配为正秒数，D-04）——死等的安全性由三样兜住：
  **可取消**、可配超时、**死锁检测**（④）；超时（如配置）→ 可重试冲突类错误；
- **取消**：等待可被取消（TXN REQ-TXN-002）——只退出等待，**不动已持有的锁** ✓。

**③ 与提交次序的接口**

**释放锁就是槽状态的改变**（§11.1.1）——所以次序约束落在
"**标记已提交不得早于提交记录进入日志流**"上，唤醒是它的后半步。
理由见 §11.1.1 的次序表：**等待者会基于前者的提交继续写入并提交**——
日志的单流顺序性使链条闭合 ✓。

**④ 死锁检测的接口**

检测器（**方法照 Oracle**：等待超阈值触发 + 环检测，阈值默认 3 秒；牺牲者 = 已修改行数最少者，D-03）**读等待结构建图**——
节点 = 事务槽，边 = ②的两半指针；发现环 → 令牺牲者**语句级回滚**
（§4.6.6 的 ②；`BIC-00060`；**事务其余部分保留**，照 Oracle 的 `ORA-00060` 方法）→
**环即解开**（牺牲者不再等待；其先前持有的锁在事务结束时释放）✓。
检测器对该结构**无锁读**：容忍一次瞬时不精确（下一轮再发现），
**不为它引入新的全局锁** ✗——那会把"检测死锁"本身变成争用点。

**⑤ 对象锁（DDL）的落地**

字典行（`obj$` / `tab$`）**也是行** ⇒ **对象锁 = 对象字典行上的行锁** ✓——
不新设锁类型。与并发 DML 的串行化走**按对象的内存登记**（热路径不碰页）：

```text
事务首次访问某对象 → 在该对象的活跃事务表里登记（事务结束时注销）
DDL → 置"DDL 进行中"（新访问者在此等待）→ 等活跃事务归零
    → 取字典行行锁 → 执行 → 复原
```

"登记"与"置位"用**同一把按对象的 latch** 互斥 ✓——两者不会互相漏过。
拒绝规则与事务边界见 TXN REQ-TXN-016；**DDL 的语法面归 `SQL` 域**。

### 5.5 空间区（4 字节）

| 偏移 | 长度 | 字段 | 说明 |
| --- | --- | --- | --- |
| 64 | 2 | `slot_count` | 槽位数（含已删槽） |
| 66 | 2 | `free_end` | 空闲区结束（行数据起始） |

> 固定头合计 **68 字节** = 描述区 32 + 事务区 32 + 空间区 4（4 字节对齐）。

| 12 | **引导页** | **格式永久固定**（§3.1） | file 0 块 1（两份副本） |
| 13 | **REDO 页** | 自有页头 + 记录流（§5.11）；**记录可跨页**，由分片头串联 | redo 文件 |
| 14 | **控制文件页** | 自有页头 + 自有 undo（§5.11）；**页大小已定 16 KiB、路径定长 256 B**（§14 第 45 项）；**精确字段偏移未定**（第 10 项，P3 前） | 控制文件 |

**分组是按"所在位置"排的**：file 3+ 的数据内容 → 段级结构 → 各专用文件 → 系统结构。

> **编号在格式冻结前仍可调整，冻结后不可变**。当前格式版本为 1（未冻结），
> 故本次做了整齐化重排。

**`page_type` 不是页体格式的全部**：同一类型下页体仍可能按用途细化。
例如 `update_mode = append_only` 的表**仍用同一个堆表页格式**（`page_type = 1`），
只是空间管理策略不同（§8）——**那是表之间的统一，与页类型之间的分化是两回事**（§5.1）。

### 5.7 槽位目录与空闲管理

**这是「数据页 / Undo 页」这一类页体的组织方式**——它们都装**变长记录、需要按槽号随机访问**。
**索引页不使用它**：索引条目必须按键有序（要二分查找），而槽位目录是无序的（§5.1）。

**每个槽位 2 字节**：

```text
位 15–2 (14 位)：行数据起始偏移（0–16383，恰好覆盖 16KB 页）
位 1–0  (2 位)：状态 —— 0 空闲 / 1 正常行 / 2 转发指针 / 3 片段头
```

**行长不存于槽位**——存于行头。若槽位存 `(偏移, 长度)` 需 4 字节，1023 槽即约 4KB（页的 25%）；2 字节方案为 2KB（12.5%）。

**槽位上限 1024** —— 与 ROWID 的 `row_id` 10 位**耦合，两者须同时修改**。

**空闲区**：页内只有一个连续空闲区 `[free_start, free_end)`，`free_start` 由 §5.5 推导。

**defrag（页内整理）**：空闲空间分散、无法容纳新行时，将活动行向页尾 compaction，合并空闲区。这是 Oracle"块内重组"的对应机制。整理**必须更新所有槽位偏移**且受 WAL 保护。

### 5.8 页尾区

**页尾区大小由 `page_type` 决定**，位于页的最末尾：

| 页类别 | 页尾区 | 内容 |
| --- | --- | --- |
| 数据页、Undo 页等 | 4 字节 | 页尾校验 |
| **索引叶页** | 16 字节 | `link_prev`(6) + `link_next`(6) + 页尾校验(4) |
| **索引分支页**（含根页） | **4 字节** | **仅页尾校验**——分支页没有兄弟链，见下 |

偏移（索引**叶**页）：`link_prev` 在 16368–16373，`link_next` 在 16374–16379，校验在 16380–16383。

**为什么分支页不带前后指针**：范围扫描**只沿叶链走**；分支页的访问永远是自顶向下的
单路径遍历，兄弟之间没有横向关系。Oracle 同样只给叶块加 `kdxlenxt`/`kdxleprv`，
分支块没有。给分支页留这 12 字节是白付的，且分裂时要多维护两个字段。

**页尾校验始终在最后 4 字节**——检查器读一页时先看末尾即可，无需先判断页类型。

#### 页尾校验的作用

页最后 4 字节存放**头部关键字段的副本**（`page_type` + `mod_seq` + `page_lsn` 低位）。

**作用**：读页时**对比头尾**，不一致即为**断裂块**（fractured block）——检出"只写了一半"。

**比固定哨兵强在哪**：固定哨兵只能检出"尾部没写"；头尾副本对比还能检出"头部是新的、尾部还是旧的"（或反之），覆盖面更广。

**边界（必须写明）**：头尾匹配**不能保证数据无损坏**——那由 `checksum` 负责。**两者互补，不是替代关系**：

| 机制 | 职责 | 成本 |
| --- | --- | --- |
| 页尾校验 | 检出**断裂块**（部分写入） | 极低——一次 4 字节比较 |
| `checksum` | 完整**数据完整性** | 全页计算 |

> `logging = none` 的表**依赖这两层**检出撕裂页。
> 本机制参照 Oracle 的 `tailchk`（块尾保存 SCN Base 低位、块类型、SCN Seq 的副本）。

### 5.9 页内空闲空间与 PCTFREE

#### 生长方向

**行数据从页底向上生长**（与成熟产品一致）：

```text
低地址 ┌──────────────────────┐
       │ 固定头 68B            │
       │ 槽位目录 ↓ 向高地址增长 │
       ├──────────────────────┤
       │                      │
       │      空闲空间         │   ← 两块相向生长，中间即空闲
       │                      │
       ├──────────────────────┤
       │ 行数据 ↑ 向低地址增长  │   ← 从页底向上
       │ 页尾区（4/16B）        │
高地址 └──────────────────────┘
```

两端**相向生长**，中间是**单一连续空闲区**。好处：空闲空间大小就是两个指针之差，无需维护碎片链；代价是碎片化时空闲区会分散，需要 defrag（见下）。

#### 空闲空间的记账

- **页头存 `free_end`**（行区上界）；**`free_start` 可推导**：`固定头末尾 + slot_count × 2`
- **可用空间** = `free_end − free_start`
- 页头**不存 `free_size`**——两个指针之差即可算出，存了就是冗余（违反 §5.2 的字段准入纪律）

#### PCTFREE

**语义**：**插入后必须保留的最小空闲空间比例**，为已有行的后续更新预留，以降低行迁移概率。

| 项 | 规定 |
| --- | --- |
| 默认值 | **10** |
| 取值范围 | **0–99** |
| 判定 | `可用空间 − 行长 ≥ PCTFREE% × 页大小` 时才允许插入 |
| **是下限不是上限** | 实际空闲空间**可以大于**该比例（删除、更新变短都会让页变空），PCTFREE **只阻止插入，不阻止页变得更空** |

**表页与索引页的语义不同**（照搬成熟产品的行为，理由见右）：

| | 表页 | 索引页 |
| --- | --- | --- |
| PCTFREE 何时生效 | **持续生效**——每次插入都判定 | **仅在建索引时预留**，之后不再强制 |
| 理由 | 更新会加长行，预留空间直接降低迁移 | 索引项按键序插入；严格强制会导致**过早分裂、空间浪费**。这与 B+Tree 的常规行为也更一致 |

> **必须显式记录这条差异**：两类页在"空间是否允许插入"上判定不同，是实现与测试都容易踩错的地方。

#### defrag（页内整理）

当空闲区被行删除切碎、**总空闲够但连续空闲不够**时触发：将活动行向页底 compaction，合并空闲区。

- **必须更新所有槽位偏移**，且**受 WAL 保护**
**触发条件**——**由条件本身保证"整理了就放得下"，因此不需要额外阈值**：

> 一次插入尝试**连续空闲不足**，而**总空闲 ≥ 行长 + PCTFREE 阈值**时，触发 defrag；
> 整理后重试，仍失败则换页。

**这条条件自洽，不会反复触发**：若整理也放不下，条件就不成立、根本不会触发；
而**整理成功后，腾出的空间在页顶是连续的**，下一次插入看到的就是连续空闲。
**所以不需要"多久才允许再整理一次"这类节流**——那类阈值是为了掩盖条件设计得不对。

**defrag 与 PCTFREE 的关系**：整理后页可能变得很空，但**空不代表可插入**——插入仍受 PCTFREE 阈值约束。

### 5.10 缓冲池

**数据库不直接读写文件**——所有页的读写都经过内存里的缓冲池（DB Cache）。
这不是实现细节，而是上层一批机制存在的**前提**：正因为修改先落在内存里的副本上，
才有了"脏页""写回""检查点"这些概念，也才有了 `steal + no-force`（§11.2）与
检查点（§11.7）。

**缓冲池是实例级共享的**——所有工作区共用一个池、一套后台写线程（§11.7），
不按工作区各建一份。因此**池的键必须带工作区标识**（§7 早已要求）：
不同工作区会出现相同 ROWID，只按 RDBA 索引会串页。

#### 两种"页头"必须分清

| | 页头（**落盘**） | 缓冲区头（**内存专有**） |
| --- | --- | --- |
| 位置 | 页的前 68 字节 | 缓冲池中的独立结构，**不落盘** |
| 内容 | 只含"崩溃后无法构建"的信息（§5.2） | 运行时状态：链指针、latch、引用计数、脏标志、**首次变脏的 LSN** |
| 生命周期 | 与页同寿 | 随缓冲块生灭 |

> Oracle 的命名陷阱值得记一笔：它的 `kcbh` 是"kernel **cache** block header"——
> 名字里有 cache，却**是落盘的**；真正内存专有的是 `kcbbh`（多一个 b）。
> 一字之差，检索资料时极易混淆。

**这条纪律的意义**：缓冲区头里全是"重启即可重建"的信息。把它们放进落盘页头，
既白白消耗磁盘格式，又让磁盘格式随内存实现变动——一旦定错就要改磁盘格式。

#### 缓冲区头的内容

| 字段 | 作用 |
| --- | --- |
| **页标识：工作区标识 + RDBA** | 哈希键。缓冲池实例级共享，键**必须带工作区标识**——不同工作区会出现相同 ROWID |
| **脏标志 + 首次变脏的 LSN** | 挂入脏链；决定写出顺序（§11.7 的检查点队列） |
| 引用计数 | 正在持有它的读者/写者数 |
| latch | 保护缓冲块 |
| LRU / 脏链指针 | 见下 |
| 状态位 | 正在读入 / 正在写出 / 已固定 |

#### 两条链

| 链 | 排序 | 用途 |
| --- | --- | --- |
| **LRU 链** | 最近使用 | 挑淘汰对象 |
| **脏链（检查点队列）** | **每个工作区一条，各自按首次变脏的 LSN 升序** | DBWR 按序写回（§11.7） |

**脏链为什么按"首次变脏的 LSN"排序**：恢复起点要求"**该点之前的修改已全部落盘**"，
它只能是**连续前缀**。乱序写会让低水位推不动，检查点位置无法前进，恢复时间失控。

**为什么是"每工作区一条"而不是池级一条**：LSN 是**每工作区独立**的（每个工作区有自己的
redo 序列），**跨工作区不可比**——一条混排的链根本排不出有意义的全序。
而且低水位是每工作区一个（§11.7），链也必须跟着分。

#### 缓冲池划分为工作集（参照 Oracle `kcbwds`）

缓冲池不是一个整体，而是划分为若干**工作集（working set）**——每个工作集是一个独立分区，
**自带一条 LRU 链、一组脏链、以及保护它们自己的 latch**。每个缓冲块**静态归属于一个工作集**。

Oracle 的描述符叫 `kcbwds`，其中记录 WS 状态、**WS ID**、所属缓冲池、NUMA 信息、
**使用的 DBWR 号**与闩锁；**每个 buffer header 里也存一份工作集 ID**——这就是缓冲块与工作集的关联方式。
每个工作集由**两个 latch**保护：`cache buffer lru chains` 与 `checkpoint queue`。

**为什么分区**：减少 latch 争用。全局一条 LRU 链意味着所有读者与写者抢同一把 latch；
分区后各工作集并行推进。

**我们的分区依据是工作区**——这是与 Oracle 的关键差别：

| | Oracle | 我们 |
| --- | --- | --- |
| 缓冲块如何归属 | **轮询分配，与数据无关**（一个表的数据散在所有工作集里） | **随工作区**——一个工作区的全部缓冲落在**同一个工作集** |
| 分区依据 | **硬件**（CPU 数 / NUMA） | **工作区** |
| 为什么这样分 | 它的争用来自"许多前台进程抢 latch"，与访问哪个表无关 | 我们的争用来自"**每个工作区各自的检查点推进**"，边界天然是工作区 |

**这个差别的收益是具体的**：一个工作区的检查点推进只需碰**一个工作集**的 latch，
**零跨工作集协调**。Oracle 做不到这一点——它的检查点是全局的，注定要碰所有工作集。

**数量有上限**：工作集描述符与 latch 都是固定开销，所以工作集数是**配置项**。
**一个工作区不被拆分**到多个工作集；当活跃工作区多于工作集数时，**多个工作区共享一个工作集**，
但它们各自的脏链仍然独立（§11.7）。

**层级关系一览**（三条约束从图上一目了然）：

```text
缓冲池（实例级，一套）
  ├── 分区 / 工作集 0   ← 自带 LRU 链与 latch；绑定一个写线程
  │     ├── 工作区 A ──▶ 脏链 A（按本工作区的 LSN 升序）
  │     └── 工作区 C ──▶ 脏链 C
  ├── 分区 / 工作集 1
  │     └── 工作区 B ──▶ 脏链 B
  └── …
```

- **工作区不被拆分**——A 的全部缓冲只在一个分区里，不散到别处
- **分区不被拆分**——一个分区只由一个写线程负责，没有两个线程抢同一分区
- **脏链不跨分区**——每条脏链只属于一个分区；分区内的多个工作区各有自己的链，只是共享 latch

**分区是可选能力**：`N = 1` 是**合法配置**，等价于不分区——小规模部署就用一套，
不必为用不上的并行付复杂度。

**分区数与映射**：

| | 值 | 依据 |
| --- | --- | --- |
| **默认** | **1**（= 不分区） | 小规模不为用不上的并行付复杂度 |
| **上限** | **64** | 每个工作集有**两把 latch** 加描述符，是固定开销；64 是本库画像下"再加就没有收益"的位置 |
| 取值 | **必须是 2 的幂** | 取模退化为按位与 |

**映射函数：`H(workspace_id) mod N`**，`H` 为稳定哈希。

**为什么是哈希而不是轮询或动态分配**：**同一个工作区每次打开必须落到同一个工作集**——
否则它的**脏链会在写线程之间搬家**，而"分区不被拆分"（§5.10）就破了。
哈希是**无状态的确定性映射**，重启后结果不变——**这正是不引入映射表的理由**。

**写线程数 = 分区数**（§11.7：写线程数 ≤ 工作集数，且工作集启动时静态分配）。

#### 替换策略：steal + no-force

- **steal**：脏缓冲**可以**被淘汰（写回后腾出）。所以恢复必须能撤销（§11.2 的三阶段）。
- **no-force**：提交时**不要求**把该事务的脏页刷盘。

两者合起来，正是"提交只需 WAL 持久化"的由来——**提交的关键路径上没有任何数据页 I/O**。
代价是崩溃恢复必须做撤销阶段。这是自觉的取舍：**用恢复期的复杂度换提交路径的延迟**。

#### 脏页被偷换出去前的写前保证

脏缓冲被淘汰（steal）去写回之前，其修改的 redo **必须已落盘**（WAL 规则 2，§11.1）。
否则崩溃后无法重放这次修改。

实现上这不是额外动作——**页的 `page_lsn` 就是判据**：
写出前检查"redo 是否已持久化到该 `page_lsn`"，未持久化则先推进日志
（此时可能退化为一次同步 `fsync`）。后台维护一个"**已持久化的 LSN 水位**"即可 O(1) 判断。

### 5.11 各页类型的页体

**统一约定**：被日志保护、参与事务的页（类型 1–12）共享 **页头 68B**（§5.3–§5.5）
与**页尾校验 4B**（§5.8）。本节只写**页体**（自偏移 68 起）。

> **两类页不受此约束**：**redo 页与控制文件页是恢复机制本身**——它们不被重放、
> 不参与 ITL。§5.1"页头统一"的理由是"所有页都参与恢复与事务"，
> 而这两个**恰恰是恢复的载体**。它们按自己的需要定义页头。

| # | 页类型 | 页体 | 状态 |
| --- | --- | --- | --- |
| 1 | 堆表页 | 槽位目录 + 行区 | ✅ §5.7、§6.1、§6.7 |
| 2 | 索引叶页 | **有序条目目录 + 条目区** | ✅ 本节 |
| 3 | 索引枝页 | 同 2，**外加最左子指针** | ✅ 本节 |
| 4 | 索引根页 | **同 3** | ✅ 本节 |
| 5 | 邻接页 | 聚簇的边 + 单向跨页链 | ✅ 见下 |
| 6 | ANN 索引页 | 定长槽的 element / neighbor | ✅ 见下 |
| 7 | 段头页 | 选项 + 空间状态 + **区映射**（可溢出到续页） | ✅ 见下 |
| 8 | 位图页 | 位数组（`kind`：区分配 / 段内空闲级别） | ✅ 见下 |
| 9 | Undo 页 | 槽位目录 + undo 记录区 | ✅ §4.6.1 |
| 10 | 临时页 | **同 1** | ✅ §4.8 |
| 11 | 文件头页 | 文件标识与自描述 | ✅ 本节 |
| 12 | 引导页 | 自举条目数组，**格式永久固定** | ✅ §3.1 |
| 13 | REDO 页 | 自有页头 + 记录流 | ✅ 本节（新定） |
| 14 | 控制文件页 | **自有页头 + 自有 undo** | ✅ 见下 |

#### 索引页的页体（类型 2 / 3 / 4）

```text
偏移 68    页体头（8B）
              entry_count 2B   条目数（含槽 1——索引页恒 ≥ 1）
              left_child  6B   **最左子指针**——仅枝/根页有意义，叶页置 0
偏移 76    条目目录（向高地址增长）：每项 2B；**第 1 项恒指高键条目（§9.1.4），
           第 2..n 项按键升序**（二分在 2..n 上进行），指向条目起始偏移
                 ───── 空闲区 ─────
           条目区（自页尾向上增长，下界 = 16384 − 页尾区）
```

| 页类型 | 页尾区 | 条目内容 |
| --- | --- | --- |
| **2 叶页** | 16B（含双链） | 有效条目与高键条目同构：`key_len 2B \| key \| ROWID 6B` |
| **3 枝页** | 4B | `key_len 2B \| 区分前缀 \| 子页 ROWID 6B`（= 分隔键的**后缀截断**，§9.1.3） |
| **4 根页** | 4B | 同枝页 |

**槽位 1 恒为高键条目**（§9.1.4）——本页键的**上界**：建页与分裂时写入，**永不回收**；
最右页以 `key_len = 0xFFFF` 标记**无上界（∞）**。它是 §9.1.2"空叶页可定位"的锚——
**一个条目，三个作用**：上界、锚、右移判据。

**与堆表页的关键差别——目录必须有序**：

| | 堆表页 | **索引页** |
| --- | --- | --- |
| 目录顺序 | **无序**（槽号即 `row_id`，复用无害） | **槽 2..n 按键升序**（要**二分查找**）；**槽 1 固定为高键条目**（§9.1.4） |
| 定位方式 | 按槽号 O(1) | 按二分 O(log n) |
| 插入 | 取一个空槽 | **移动目录项**以维持有序（每项 2B，代价小） |

这正是 §5.1 说的"格式服务于访问模式"——**同一个"目录 + 区"的骨架，
两种截然不同的组织**。

**索引条目没有行级 lock 字节**（Oracle 的索引行有 `lock` 指向 ITL 槽，我们不需要）：
索引项的插入与删除**由页级 ITL + latch 保护**，可见性由**回表时按行的 ITL 判定**——
索引项自身不承载事务状态。这比 Oracle 少一个字段。

**`left_child` 在叶页置 0**：叶页没有子页，这个字段是为枝/根页的
"n 个条目对应 n+1 个子页"准备的（§9.1.3）。**保留 6 字节而非按类型改变页体头**——
页体头定长使解析统一，而 6 字节的代价远小于"页体头变长"带来的复杂度。

**条目的长度上限：4096 字节。** 这个数**不是"页能装多少"**（那是 16300B），
而是**"一页至少要能装下两个条目"**——否则分裂没有意义：
分裂的前提是"塞不下的那个新条目能独立成页"，
若一个条目就占满一页，分裂后新页仍是满的，搜索树无法前进。

取 1/4 而不是 1/2，是给目录项、页尾区、以及分裂后两页各自的增长留余量：

```text
页体 16312B − 页体头 8B − 页尾区 4/16B   ≈ 16300B 可放条目
一页至少两个条目 + 两个目录项 → 单条目上限取 页体的 1/4 = 4078B
取整为 4096B（4KB）
```

**上限在两侧都要拦**：

| 时机 | 拦什么 |
| --- | --- |
| **`CREATE INDEX`** | **键列声明宽度的组合**。`VARCHAR2(4000)` 的键列直接拒绝——与 Oracle 的 `ORA-01450`（键长超限）同一个位置，但**在建索引时就报，不等插入时才炸** |
| **插入 / 更新** | 实际编码后的条目长度。声明的宽度只是上界，实际值可能长或短 |

**这条限制是"长文本内联"的必要配套**（§6.8）：既然值可以很长，
就必须回答"长到多少就不能建索引"，否则问题会推迟到运行期才出现。

#### 文件头页（类型 11）——每个文件的块 0

```text
偏移 68    file_id        2B    本文件的编号（与 ROWID 的 file_id 一致）
           role           1B    0 元数据 / 1 Undo / 2 Temp / 3+ 数据（§2.2）
           format_version 1B
           flags          2B
           **当前大小**   6B    以块为单位——**权威在这里，不在控制文件**（§2.6）
           workspace_ref  8B    与页头同源，用于"打开错了文件"的快速否决
           reserved       …
```

**"当前大小"记在这里，而不是控制文件**——这是 §2.6 那条决定的对偶：
控制文件只存**创建时大小**（创建后不变），**可变量一律以文件自身为准**。
于是"扩展文件"是一次自足的原地操作，不碰控制文件的双副本（§3.3）。

#### REDO 页（类型 13）

**redo 文件有页结构**——理由是 **redo log buffer**：有了页，日志缓冲区才能按页
分配、按页回收、按页刷盘，缓冲管理才有单位。

```text
偏移 0    校验          4B    覆盖整页
偏移 4    页位置        6B    本页在日志中的**起始 LSN**——恢复时校验顺序
偏移 10   已用长度      2B    页内有效字节数（自页体起算）——恢复扫描的终止依据
偏移 12   flags         1B
偏移 13   reserved      1B
偏移 14   reserved      2B
偏移 16   页体：记录流，从偏移 16 开始
```

**页体是"记录流"**，不是"目录 + 区"——redo 的记录是**只追加**的，
没有删除、没有随机访问，目录在这里没有意义。**这又是一个"格式服务于访问模式"的例子**。

**记录在页内线性打包，允许跨页**：记录不按页边界对齐——一条记录接着上一条结束的位置写
（512B 的页上"每条记录都补零到页边界"会浪费平均半页）。放不下当前页剩余空间时，
**跨到下一页继续**，由**分片头**串联（见下）。

> **与 Oracle 的一处形态差异**：它的重做记录"**总是从块边界开始**"
> （块头 → 记录头 → strand 头 → 变更向量），靠大记录摊薄块头开销；
> 我们**线性打包**、每页带 12B **分片头**——512B 页下固定开销约 2.3%，
> 且没有"每条记录补零"的浪费（证据包 `redo-bytes-20261004`）。

**页大小：对齐文件系统的原子写单位**

知识库印证了这个思路，而且成熟产品就是这么做的：

| | redo 页 / 块大小 |
| --- | --- |
| **Oracle** | **512 字节**（Linux/Solaris 默认，HP-UX IA 为 1024）——**等于操作系统块大小**。理由原文：这样"**确保写入磁盘的每个块都是完整的**"；其 redo log buffer 干脆由 N 个"大小 = OS block size"的片段组成，LGWR 以块为单位写 |
| **PostgreSQL** | **8KB**（`XLOG_BLCKSZ`，编译时常量） |

**两家都远小于各自的数据页**（Oracle 8KB 块、PG 8KB 页）——**redo 页不宜太大**：
它是**提交关键路径**上唯一必须持久化的东西，页越小，追加与刷新的粒度越细。

**我们的取值：对齐部署环境文件系统的原子写单位**（典型 512B 或 4KB）。
好处是**一页的写入是原子的**——日志末尾永远不会是半截页。
而 redo 是**恢复的唯一依据**，**它的末尾干净比数据页更要紧**。

**记录允许跨页——靠分片**

一条记录超出当前页的剩余空间时，**跨到下一页继续**，由**分片头**串联：

```text
分片头（每片都带）
  rec_id      6B   记录标识（= 首片的 LSN）
  frag_no     2B   本片序号（自 0 起）
  frag_cnt    2B   分片总数
  frag_len    2B   本片数据长度
```

恢复时：读到 `frag_no = 0` 即知总分片数，连续取后续分片重组；
**分片序列不完整（末尾被截断）则整条记录丢弃**——与"日志末尾不完整就停"同理，一致。

> **⚠ 更正我先前的判断**：上一版我写"记录跨页会带来 PG 那种惩罚"，**那是错的**。
> PG 的惩罚（`WALInsertLockAcquireExclusive` 要拿全部 8 把插入锁）**是它无锁追加设计的代价**——
> 它靠 `xl_prev` 链做无锁插入，跨页时维持不住，只能退化为全锁。
> **而我们的 WAL 追加本来就是 latch 串行化的**（§11.5.2：写少、争用低，不用无锁技巧），
> **跨不跨页都要拿那把 latch**——所以跨页对我们**没有额外代价**。
> Oracle 允许记录跨块也没问题，同理：它的 LGWR 是单写者。

**于是"分片"要解决的不是性能，而是原子性**：让**系统操作**的大记录也能跨页，
同时保持"单条原子"（§11.1.3——系统操作**没有提交边界可依托**，必须单条原子）。

> **推论**：记录的**页内粒度**不再受限，所以它的实际大小由**内容**决定而不是由页决定。
> 但"**记录不得跨文件**"（§11.5.1）仍在，故"组大小 ≥ 最大单条记录"**依然成立**——
> 只是这个值现在等于**一页 + 分片头 = 17 KiB**（34 个 redo 页；一条记录最坏就是重写一整个数据页，§11.5.2 已定量）。
**页大小与记录 CRC——均已定案**（§14 第 46 项）：**页 = 512 B**（对齐部署环境的原子写单位）；**记录头不带 CRC**——页尾校验覆盖每页，分片重组有 `rec_id` / `frag_no` / `frag_cnt` / `frag_len` 把关（"能推导的就不存"）。
#### 各页类型的 redo 参与

**不是所有页都产生 redo。** 三类不产生，理由各不相同：

| # | 页类型 | 产生 redo？ | 由什么保证 |
| --- | --- | --- | --- |
| 1 | 堆表页 | **随表的 `logging` 选项**（§8） | redo，或"可丢" |
| 2–4 | 索引叶/枝/根页 | **随基表** | redo |
| 5 | 邻接页 | **随图表**（`logging = full`） | redo |
| 6 | ANN 索引页 | ❌ **不产生** | **重建**——它是可重建的派生索引（§9.3） |
| 7 | 段头页 | ✅ 必须 | redo——段结构损坏即整段不可用 |
| 8 | 位图页 | ✅ 必须 | redo——位图损坏即**整个表空间**不可用 |
| 9 | Undo 页 | ✅ **必须** | redo——**否则未提交事务再也回滚不了**（§11.1.2） |
| 10 | 临时页 | ❌ **不产生** | 打开工作区时**整体重置**（§4.8）——但**有 undo**，见下 |
| 11 | 文件头页 | ✅ 必须 | redo——"扩展了文件却没更新文件头"会让读落到未初始化区域 |
| 12 | 引导页 | ❌ **不产生** | **创建时写一次，此后不变**；靠**两份副本** + 备份 |
| 13 | **REDO 页** | ❌ **不参与** | **自指无意义**——记录"对日志的修改"会无穷递归 |
| 14 | **控制文件页** | ❌ **不参与 WAL** | 靠 **双副本 + 序号协议**（§2.6）——它本身就是恢复锚点 |

**三类"不产生"的性质完全不同**，不要混为一谈：

| 类别 | 例子 | 为什么可以没有 |
| --- | --- | --- |
| **可丢** | 临时页、`logging = none` 的数据页 | 内容定义为可丢——丢了不是损坏，是"回到没写过" |
| **可重建** | ANN 索引页 | 它是**派生**数据；重建是常规动作（§9.3） |
| **不适用** | REDO 页、控制文件页、引导页 | **它们要么是恢复机制本身，要么写一次就不变**——"用 redo 保护它"在逻辑上不成立或无必要 |

> **最后一行是最容易搞错的**：REDO 页与控制文件页**不是"被保护的数据"，
> 它们是保护机制本身**。把控制文件列进"必须受 WAL 保护"是范畴错误。

**一条容易漏掉的组合：临时页有 undo 而无 redo。**

它用**标准页头**（§5.11 表：临时页 = 堆表页格式），页头里有 ITL——于是临时段内的修改
同样"挂在事务上"，可以回滚。**但它不产生 redo**：崩溃后 file 2 整体重置，重放它毫无意义。

> **由此得到一条边界**：**针对 file 2 的 undo 记录只服务于语句级回滚，
> 崩溃恢复时不重放**——因为那些页已被重置，重放会写到无意义的页上。
> 这与"临时数据定义为可丢"是同一条原则的两个面。


#### 位图页（类型 8）——两种用途，同一页体

位图页承载**两种**位图，**页体头用 `kind` 区分**：

| `kind` | 用途 | 管理的单位 | 每单位几位 | 归属 |
| --- | --- | --- | --- | --- |
| **0** | **区分配图（LMT）** | 一个**区**（128KB） | **1 位**（已分配 / 空闲） | 数据文件 |
| **1** | **段内空闲级别**（§4.5） | 一个**页**（16KB） | **2 位**（FULL / 低 / 中 / 高） | 段 |

```text
偏移 68   页体头（8B）
             kind        1B   0 = 区分配图，1 = 段内空闲级别
             flags       1B
             own_index   2B   **本位图页在本位图块中的序号**——读盘时的自校验
             reserved    4B
偏移 76   位数组（连续，**从低位到高位对应递增的单元号**）
```

**为什么两种位图共用一种页类型**：它们的**页体是同一个东西——连续的位数组**，
差别只在"每位管什么"。`kind` 一个字节就说清了，不必为此再分一种 `page_type`。
（与 ANN 的 element / neighbor 是同一个判断：**页体头一致，就没有拆类型的理由**。）

**`own_index` 的作用**：位图页的内容**不作任何地址标记**——第 i 位属于哪个区，
由"这是第几个位图页"推算。若页被放错位置或读错，位图会**静默地**管错对象。
`own_index` 让这件事能被检出，代价只有 2 字节。

#### 区分配图：文件怎么摆

**容量换算**（页 16KB、区 8 页 = 128KB）：

```text
位图页页体 = 16384 − 68（页头）− 4（页尾校验）− 8（页体头）= 16304B
            = **130432 位**（不是 131072——位数组装不下整页，见下）

一个位图页 → 管 **130432 个区** = **约 15.9 GB**
一个位图区（8 页）→ 管 8 × 130432 = **1043456 个区** = **约 127 GB**
4 TiB 文件（上限）→ 需 ceil(33554432 / 1043456) = **33 个位图区** = 4.125MB
```

> **为什么不是整数**：`130432` 与 `65216` **不是估的，是算出来的**——
> 位数组用完整个页体，而页体要先扣掉**页头 68B、页尾校验 4B、页体头 8B**。
> **早先写 131072（正好是整页的位数）是把这三处都漏掉了**，
> 于是"16GB/页""4 TiB 需 32 个位图区"跟着一起错。
>
> **用尽页体而不取整到 2 的幂**，是为了不浪费空间——
> 覆盖范围由"第几个位图页"乘一个常数得出，**不需要它好看**。

**文件布局**：

```text
块 0            文件头页（类型 11）——**内含"位图空间头"**
块 1 起         数据区（段的区）
…
文件尾部区      位图区（每个 = 1 个区 = 8 页）

位图空间头（在文件头页的页体内）
  bitmap_run_count  1B    已用的位图区数（4 TiB 上限下 ≤ 33，留余量到 40）
  bitmap_runs[]     4B×40 各位图区的**起始块号**
```

**位图区从文件尾部往前分配、数据区从块 1 往后分配**——两者相向而行直到相遇。
这样**位图增长不需要移动任何数据**，而这正是 Oracle 的 LMT 把位图分成"前部 + 后部"
两段所要解决的问题；我们用"位图集中在尾部"达到同样效果，且更简单。

**位图区不需要自己的位图**：4 TiB 上限下最多 33 个，直接列在空间头里更省事。
**这避免了"位图的位图"这种自指结构。**

> **三处与 Oracle 的有意简化**（都写在明处）：
> ① 它的位图分前部 + 后部两段，我们用"尾部集中"；② 它一个位图块管 8 个单元的
> 粒度由 `UNIFORM`/`AUTOALLOCATE` 决定，我们的**区等大**（§4.1），故粒度固定；
> ③ 它区分 MSSM/ASSM 两套空闲管理，我们**只有 ASSM 式的段内位图**（§4.5）。

#### 段的组成：不只是段头

**段 = 段头 + 区映射 + 段内位图 + 数据页**。后三者都是**段的组成部分**，
但**只有段头是段的锚点**（第一页）。

```text
段头页（类型 7）——段的锚点，段的第一页
  ├─ 段标识与选项
  ├─ 空间状态：HWM、追加位置、插入提示
  ├─ **区映射头**：条目数、起始位图页、溢出链
  └─ **区映射条目**（就地存放，装不下则溢出）
区映射续页（类型 7，同类型）
  ├─ 映射头：`next` 指针、条目数
  └─ 区映射条目
段内位图页（类型 8，kind = 1）——§4.5 的空闲级别
数据页（类型 1 / 2–5）
```

#### 区映射条目：起始 RDBA + 长度

**照 Oracle 的 `ktetb`**，每条 = **`起始 RDBA 5B` │ `区数 2B`**（长度以区为单位）：

> **宽度取 5B 而不是 Oracle 的 4B（P3 段切片落地时修正）**：Oracle 的 4B DBA =
> 10 位文件号 + **22 位块号**（它自己的块号宽度）；我们的块号是 **28 位**（§7，
> 与 ROWID 同口径），4B **装不下**——照抄宽度会悄悄截断高 6 位。取 **5B =
> 10 位文件号 + 28 位块号**，与 **redo 块引用的 `rdba` 同一编码**（§11.5）。

| | Oracle `ktetb` | 我们 |
| --- | --- | --- |
| 条目 | 起始 DBA + 长度 | **起始 RDBA 5B + 区数 2B** |
| 粒度 | 逐个区 | **逐个区，但相邻者合并为一条** |
| 溢出 | 区映射块（EMB） | **区映射续页**（同类型 7） |

**"相邻者合并"是我们与 Oracle 的一处有意差异**：

- 我们的区**等大**（8 页，§4.1），且分配器**尽量连续**（§4.1 的原话是"连续区减少碎片"）
- 于是**一个段的区在正常状态下只形成少数几个连续区间**——逐个存是浪费
- 合并后，条目数**随碎片度增长**，而不是随区数增长

> 一个 2GB 的表有 16384 个区：逐个存要 **6 个映射页**；连续分配下**几项就够**。
> **合并是免费的优化**——它不改变条目格式，只改变"存几条"。

**`长度`字段保留**：即便当前区等大，它也让**将来可能的不等大区**不必改格式
（§14 待冻结项 7"区大小是否固定 8 页"尚未冻结）。

#### 溢出：区映射续页

**照 Oracle 的 EMB**，三条规则：

| 规则 | 说明 |
| --- | --- |
| **链式** | 段头的 `next_map_page` 指向第一个续页，续页再指向下一个——与 Oracle 的"链头在段头块"一致 |
| **`last map = 0` 表示没有溢出** | 直接沿用 Oracle 的判据（其段头转储里的 `last map` 字段就是这个含义） |
| **续页从段的区里分配** | Oracle 说 EMB"总是作为第一个区中的第一个块分配"；我们放宽为**从段的区中分配**，位置记在链上 |

> **溢出本身是信号**：它意味着这个段的区**碎得厉害**。§4.7 的 `Move`（搬段整理）
> 正是为这种情形准备的——**不需要专门监控，清单长度自己会说话**。

#### 段的逻辑页号 → 物理块

区映射的用途不只是"列出占用了哪些区"，它同时是**寻址的中间层**：

```text
段的逻辑页号 k
  ├─ 物理块 = 该区起始块 + (k mod 8)
  └─ 区序号 = k / 8  →  查区映射得到它属于哪个区间、区间起始块
```

**段的访问全部走"逻辑页号"**：HWM、追加位置、段内位图页覆盖的范围，都用它。
**物理位置只在区映射里出现一处**——这使段的空间管理与文件的物理布局解耦。

#### 段内位图页怎么找

**不需要映射表**（Oracle 需要 `ktspatb`，是因为它有 L1/L2/L3 **三级**位图）。
我们是**两级**（§4.5），所以：

> **位图页覆盖的页范围由"它是第几个位图页"推算**——第 i 个位图页管逻辑页
> `[i × 65216, (i+1) × 65216)`。段头只记**第一个位图页的位置**（`起始位图页`），
> 其余沿链。

**这是两级相对三级买到的最实质的一笔**：没有"区 → 位图块"的映射表要维护、要溢出、
要在回收时更新。

#### 段头页的页体（类型 7）

**段头页是段的锚点，也是唯一一种"页体内部再分两段"的页**：
**公共部分**所有段都有，**类型扩展区**只有部分段有。

```text
偏移 68    页体头（8B）
              seg_type         1B   段的物理种类——见下
              map_format       1B   **区映射的格式版本**——独立于页格式，
                                    因为区映射的排布会变而页头不会（§3.1.1）
              flags            1B
              reserved         1B
              dataobj#         4B   数据对象号——**冗余一份**，见下

偏移 76    段标识（16B）
              obj#             4B   反向指针——诊断与恢复用（§3.1.1 的"扫 file 0 找段头页"）
              pages_per_extent 1B   每区页数（当前恒 8；§14 待冻结项 7）
              itl_max          1B   段级 ITL 上限（§5.4）
              pctfree          1B   页内预留（§5.9）
              reserved         1B
              table_opts       2B   表选项编码（§8.1）——**打开段即可分派行为**
              reserved         6B

偏移 92    空间状态（24B）
              高水位 HWM       4B   **逻辑页号**；`append_only` 段不用（§4.3）
              追加位置         4B   `append_only` 的下一可写逻辑页号（§4.3）
              起始位图页       4B   第一个段内位图页的逻辑页号；**0 = 尚无**（§4.5）
              插入提示         4B   最后使用的位图页（§4.6）
              已分配区数       2B   对应 Oracle 的 `#extents`
              位图页数         2B
              reserved         4B

偏移 116   区映射头（12B）
              区间数           2B   就地存放的区间项条数
              next_map_page    6B   第一个**区映射续页**；**0 = 无溢出**
                                    （直接沿用 Oracle `last map` 的判据，§5.11）
              reserved         4B

偏移 128   类型扩展区（**固定偏移**，长度由 `seg_type` 决定；多数段为 0）
  **B+Tree 段：树头 = 根页 ROWID 6B**（§9.1.5；空索引指向初始空叶页）
  undo 段：**事务表**——固定槽数 × 24B（§4.6.3）
  ANN 段：`m` / `ef_construction` / 距离度量 / 维度 / 入口点（§5.11 的 ANN 一节）

偏移 128 + 扩展长度   区映射条目（就地存放，向高地址增长）
              区间项[]         7B×n = **起始 RDBA 5B │ 区数 2B**（§5.11）
```

**页内容量**：页 16384B，页头 68B + 页尾校验 4B，故页体可用 **16312B**。
扣公共部分 60B，再扣类型扩展区，余下全是区间项（每项 7B）——
**无扩展的段可放约 2300 项**（16252 ÷ 7 = 2321）。

#### `seg_type`：段的物理种类

| `seg_type` | 段 | 数据页用哪些页类型 | 类型扩展区 |
| --- | --- | --- | --- |
| **1** | **堆表段** | 1（堆表页） | — |
| **2** | **B+Tree 索引段** | 2 / 3 / 4 | **树头：根页 ROWID 6B**（§9.1.5） |
| **3** | **邻接段**（图的边） | 5 | — |
| **4** | **ANN 索引段** | 6 | `m`、`ef_construction`、距离度量、维度、入口点 |
| **5** | **Undo 段** | 9 | **事务表**（§4.6.3） |
| **6** | **临时段** | 10（= 堆表页） | — |

**引导页的 `seg_type` 用同一个枚举**——这正是它存在的理由：读引导页时字典表还不可用（§3.1.1）。

#### 它与 `obj$.type#` 是两条轴，不是一回事

| | 回答什么 | 取值 |
| --- | --- | --- |
| `obj$.type#` | 这是**什么对象** | 表 / 索引 / 过程 / 分区……（§3.1.3） |
| `ind$.type#` | 这是**什么索引** | B+Tree / ANN / 邻接（§3.1.3） |
| 段头 `seg_type` | 这个段**怎么组织** | 上表六种 |

对应关系是**多对一**：`obj$.type# = 1`（索引）**加上** `ind$.type#`
才能定出 2 / 3 / 4 中的哪一个。

**为什么段头还要自己存一份**——这是"两条轴"看着别扭的地方，必须说清：

§4.2 的判据是"**段自描述**——引擎打开段即可分派行为，不必回查目录"。
这条在**恢复**时是硬的：扫 file 0 找段头页重建引导页时（§3.1.1），
**字典表可能正是不可信的那一方**。段头是**自证**，不是缓存。

**`dataobj#` 与 `obj#` 都放进段头，是同一个理由**——它们是段头的**自校验**：
与从 `obj$` 查来的值比对，不一致即"这个段不属于我以为的那个对象"。
代价 8 字节，买的是**"打开错了段"能被检出**，而不是静默串数据。

**`HWM` / `追加位置` / `起始位图页` / `插入提示` 都是逻辑页号**，
与 §5.11"段的访问全部走逻辑页号"一致——**物理位置只在区映射里出现一处**。

#### 邻接页（类型 5）

**一个源节点的出边集合，按 `(src, edge_id)` 聚簇**（§9.2）——一跳出边遍历
因此是**一次范围读**，而不是 N 次随机 I/O。

**借自 pgvector 的 `neighbor tuple` 的是"组织方式"，不是"格式"**：它的邻居数组是
**定长**的（每层 `m` 个 ID，`m` 是索引参数）；而我们的边是**变长**的——边带 `label`
与属性，长度不一。**同构的是"一个节点的邻接集合"这件事，不是它的字节布局。**

```text
偏移 68   页体头（16B）
             src          6B   本页所属的**源节点 ROWID**——一页只服务一个 src
             edge_count   2B
             flags        1B
             next_page    6B   **同一 src 的下一个边页**；0 = 末尾
             reserved     1B
偏移 84   条目目录（2B × n，**按 edge_id 升序**）
                 ───── 空闲区 ─────
          条目区（自页尾向上增长，下界 = 16384 − 4）
             每条 = edge_id 6B │ dst 6B │ flags 1B │ itl_slot 1B
                    │ label_len 1B │ payload_len 2B │ label │ 属性
```

**一个标识，两个角色**（`spec/GRP.md` §0.4）✗✓：**`edge_id` 由序列产生**
（`CONV` §1：48 位、区内单调、不复用）——它**同时**是：

| 角色 | 为什么合得来 |
| --- | --- |
| **对外标识**——`id(r)` 的返回值 | 序列值区内唯一 ✓ |
| **聚簇与二分的键** | **序列单调** ⇒ 对任一 `src`，其新边的 `edge_id` 大于它**全部**既有边 ⇒ **追加即有序，永不需要分裂协议** ✓✓ |

**"随机 id 不能做聚簇键"这条曾经的顾虑，在序列方案下消失了** ✓——
这也是"ID 由序列产生"（`CONV` §1.1）在这里的直接红利：**两个标识合一**。
**附带地：条目编号永不复用**（序列不回绕）——只有 ITL 槽的复用规则照旧（§12.4）✓。

**`flags` + `itl_slot` 让条目与行同构地参与可见性判定**——条目是边的**权威之家**，
没有"回表"可查，所以它必须自带事务信息（`spec/GRP.md` REQ-GRP-002 的存储侧补充）。
**条目可被一致读、可回滚、可延迟清除**；
**条目的 `itl_slot` 与行同规——随 undo 载荷还原**（§4.6.2）。

**三个设计点**：

| 点 | 选择 | 理由 |
| --- | --- | --- |
| **`src` 记在页体头** | 一页只服务一个 src | 这就是"按 `src` 聚簇"的定义；也让"这一页属于谁的边"无需查目录 |
| **跨页用单向 `next_page`** | **只前进，不回退** | 边集合的访问总是**从头顺序扫**（"这个节点指向谁"），不需要反向。索引叶页要双向是因为范围扫描支持降序——邻接页没有这个需求 |
| **条目按键有序** | 按 `edge_id` 升序 | 有序才能二分；而序列单调 ⇒ **插入永远落在现有序之后**——追加即有序 ✓ |

**入口在哪**：一个 `src` 的链从哪开始？
每图有一条 **出边入口索引**（B+Tree）：`(src ROWID) → 首邻接页 ROWID`——
链自身只向前走，**入口索引是链的唯一入口** ✓（§9.2）。

**高度数节点按"优雅退化"处理**（§9.2）：边跨多页时沿 `next_page` 走，
**不做专项优化**——度 ≤ 10 时通常一页装得下，为极端度数做特殊结构不划算。

> **它是唯一"自带链"却不在索引叶页之列**的页体——因为它的链服务于**同一个 src 的
> 边集合跨页**，与索引的兄弟链是两回事。

#### ANN 索引页（类型 6）

**metapage 并入段头页**（类型 7）——不另立一页。理由：metapage 的内容
（`m` / `ef_construction` / 维度 / 距离度量 / **入口点** / 版本）**全是段级属性**，
与段头页已有的"段类型、表选项、区清单"是同一类东西。

> pgvector 把 metapage 放在**索引的第 0 号页**；我们的段头页**就是**段的第 0 页（§4.2），
> 所以这个位置天然对应。它存的 `entry_point` 还有一条隐含职责——
> **入口点被删除时要更新它**（在剩余元素中选最高层级的非入口点），以保证图连通。

**两种页体，由页体头的 `kind` 区分**：

```text
偏移 68   页体头（8B）
             kind      1B   0 = element，1 = neighbor
             flags     1B
             count     2B
             reserved  4B
偏移 76   槽位数组（**定长槽**——element 与 neighbor 的大小都由维度与 `m` 决定）
```

| `kind` | 槽内容 | 定长依据 |
| --- | --- | --- |
| **0 element** | `ROWID 6B`（被索引的行）│ `flags 1B` │ `version 1B` │ 向量 `dim × 4B` │ `neighbor_ref 6B` | 维度在**创建索引时固定** |
| **1 neighbor** | `层数 1B` │ 各层：`count 2B` + 邻居 ID 数组（`6B × count`） | **`m` 是索引参数**，各层上限由它决定 |

**`flags` 与 `version`：照 pgvector 补的两个字节**。源行**删除**或**向量更新**时，对应元素**置 `flags = 已失效`、`version` 递增**——不修图、不原地改向量（**向量更新 = 插入新元素入图 + 旧元素置失效**）。**扫描者读到元素后复验 `version` / `flags`**，以检出扫描期间被并发失效的元素（pgvector 的同一手法：`MarkDeleted` 递增版本号、4 位到 15 回绕；我们取 1B，语义同构）。**正确性仍由回查兜底**（`spec/RET.md` REQ-RET-023）——索引给候选、回查给结果。

**为什么用定长槽而不是"目录 + 行区"**：element 与 neighbor 的长度**都由索引参数唯一决定**——
维度固定、`m` 固定。**没有变长的东西，就不需要为变长准备的那套结构**（§5.1）。
定长槽还带来一个便利：**第 k 个槽的位置 = 页体头 + k × 槽长**，无需目录、无需二分。

**element 与 neighbor 可以不同页**：element 记录里存 `neighbor_ref`（指向该节点的
邻居记录），因此两者不必相邻——这与 pgvector 用 `neighbortid` 连接 element 与 neighbor 同构。
**3072 维 × 4B = 12KB 的 element** 与 **几百字节的 neighbor** 若混排，一页只能装一个，
而分开存放各自都能装下多个。

> **为什么 `kind` 用页体头字段而不是拆成两个 `page_type`**：它们是**同一个索引**的两半，
> 同生共死、一起分配与回收；恢复与检查的分派到"ANN 页"这一级就够了，再细没有收益。
> 这与索引拆成叶/枝/根不同——那里拆是因为**三者的页尾与页体头本就不同**（叶有双链、
> 枝有最左子指针），而这里两者的页体头完全一致。

**element 存 `ROWID` 而非堆指针**：pgvector 存 `heap TID`，我们存 6 字节 `ROWID`——同构，
且行迁移经转发指针仍能定位（§6.2）。

#### 控制文件页（类型 14）

**控制文件有自己的 undo，不用标准的 undo 段。** 理由：标准 undo 服务于"事务内的**多步**修改"，
而控制文件的修改是**单步的、逐字段的**——**只需要追溯一条 undo 记录**，不需要链。

**机制：主数据的副本先落到 undo 位置，再改主数据。**

```text
① 把目标位置的**旧值**写进 undo 记录     ← 副本
② 原地覆盖主数据（§2.6：控制文件定长，更新是原地覆盖写）
③ 清 undo 记录（标记为空闲）
```

**崩溃后的判定极简**——只看 undo 记录空不空：

| undo 记录 | 含义 | 处置 |
| --- | --- | --- |
| **空** | 没有未完成的修改 | 直接用，一致 |
| **非空** | 有一次修改**没走完 ①②③** | **用记录里的旧值回滚目标位置**，再清空 |

**三个崩溃点各自的结果**：

| 崩在 | 主数据的状态 | 回滚的效果 |
| --- | --- | --- |
| ① 后 | 未动 | 回滚 = **无操作** ✓ |
| ② 中 | **写了一半** | 回滚 = 恢复旧值 ✓ **这正是它要防的** |
| ② 后、③ 前 | 已是新值 | 回滚 = **多退一次已完成的修改**——可容忍，见下 |

**为什么"多退一次"可容忍**：**控制文件是幂等的状态发布**，不是数据。
检查点位置、redo 条目、归档记录都会在下一轮再写一次；
即使某次更新丢了，另一份副本的序号更大，取它即可（§2.6）。
**它的修改不像数据页那样"每一次都必须留住"。**

> **它与数据页的 undo 是两回事，不要混**：
>
> | | 数据页的 undo | **控制文件的 undo** |
> | --- | --- | --- |
> | 位置 | file 1 的 undo 页 | **控制文件内** |
> | 形态 | 成链（§4.6.2） | **单条** |
> | 事务性 | 是 | **否** |
> | 受 redo 保护 | **是**（§11.1.2） | **否**——控制文件本来就不产生 redo（§5.11 的表） |

**页结构**：

```text
控制文件 = 20 页 × 16 KiB = 320 KiB
  页 0    文件头（段偏移表 8 项 + 固定偏移 132 的单条 undo 记录）
  页 1    固定段：工作区条目 64B │ 检查点进度 48B │ Redo 条目 128B │ 归档记录 320B
  页 2–19 数据文件记录数组（1024 × 280B）
每页：页头 24B（magic │ seq │ page_no │ payload_len │ copy │ flags）│ 页体 │ 页尾校验 4B
undo 记录（522B，定长）：目标偏移 4B │ 旧值长度 2B │ 旧值[512B] │ 校验 4B —— 长度 0 = 空闲
```

**undo 记录为什么必须定长**：控制文件整体定长（§2.6），undo 记录若变长，
"它有多大"本身就成了一个需要先知道的问题。**定长上限 = 单次修改的最大字段长度。**
