## 3 表空间文件

### 3.1 file 0：元数据文件与数据字典

file 0 相当于 Oracle 的 **SYSTEM 表空间**——工作区的全部元数据以**字典表**的形式存放在这里。

关键性质：**字典表使用与普通表完全相同的结构与访问路径**（段 + 页 + 行 + ITL + 槽位目录 + ROWID + 索引），
**不存在第二套"目录格式"**。工作区因此不需要为元数据单独写一套读写、校验与恢复代码。

内部结构，按块顺序：

| 块 | 内容 |
| --- | --- |
| 0 | **文件头页**（`page_type = 11`；含 `file_scn`——本文件最新持久化位点） |
| 1 | **引导页**（`page_type = 12`），格式**永久固定**（**主**） |
| 2 .. 255 | **核心元数据带**预留（[0, 4 MiB)；不写入，稀疏读零） |
| 256 | 引导页**副本** ┐ 副本带（[4 MiB, 8 MiB)——**与主相隔 4 MiB**：
| 257 | 文件头**副本** ┘ 同一片损坏不可能同时命中主副） |
| 258 .. 511 | 副本带预留（格式上允许将来放更多副本组） |
| 512 .. 831 | file 0 **位图区**（40 区 × 8 页；结构同数据文件，基址后移） |
| 832 .. | **字典表的段**——起始位置由引导页给出，之后按 §4 的区分配增长 |

> **带式排布与副本分离（2026-10-06，用户口径）**：相邻块的两份副本不构成冗余
> （同一片损坏一起完蛋）；主副**空间分离**照 ext4 备份超级块 / Oracle 控制文件
> 多路复用的成熟做法（证据包 `catalog-boot-20261006`）。数据文件（role 1/2/3+）
> **保持现行统一布局不变**（位图 1..320、数据区 321）；`FileLayout` 按 role 取。

**为什么字典表要用普通表结构**：

1. **一套代码**——字典表的读写、页校验、ITL、WAL 保护、崩溃恢复全部复用表引擎。"元数据"不是特例，
   也就不会成为恢复路径上唯一没被日常验证过的分支。
2. **要索引**——按名查对象、按 `obj#` 查列都是 B+Tree 点查，DDL 与启动不随对象数线性退化。
   Oracle 正因如此为 `obj$` 建了 `I_OBJ1` / `I_OBJ2` / `I_OBJ4`。
3. **DDL 天然事务化**——建表 = 向若干字典表插入行。它与用户事务共用同一套 undo / WAL / 提交序号，
   不需要单独设计"元数据变更日志"，并自动获得 **DDL 可回滚**与**恢复后字典自洽**。

#### 3.1.1 引导页（对应 Oracle `bootstrap$`）

- 要读 `obj$`，得先知道 `obj$` 的段头在哪；而这个位置本身存在 `seg$` 里。
- 解法：**块 0 / 块 1 的格式硬编码**，内核读取路径**不依赖任何字典表**；引导页直接给出**最小自举集**的段头位置。（引导页**主副空间分离**：主在块 1、副本在块 256——`目录详设` §2.1。）

引导页条目：

| 字段 | 说明 |
| --- | --- |
| `dataobj#` | 数据对象号 |
| `seg_type` | 段类型——**引导页要它，是因为这里读不了字典表**（§4.2"段自描述"的同一条理由） |
| `seg_header` | 段头 ROWID（6 字节） |
| `iniexts` | 初始区数 |

**最小自举集**：

| 表 | 作用 |
| --- | --- |
| `obj$` | **所有对象的根定义**——名字、种类（`type#`）、指向段的 `dataobj#` |
| `tab$` | 表专有属性（**七项表选项在此**） |
| `col$` | 列定义（含向量列扩展） |
| `ind$` | 索引专有属性（`bobj#` 指向基表） |
| `icol$` | 索引键列组成 |
| `seg$` | **持久段登记**（`dataobj#` → 段头位置）——表段与索引段 |
| `undo$` | **Undo 段本身**（含其段头位置）——它不进 `obj$` / `seg$`，理由见 §3.1.2 |

**索引也是自举对象**——Oracle 的 `I_OBJ1` / `I_OBJ2` 属 bootstrap 核心（`obj# < 56`），
是"数据库 warmstart 所必需"，甚至禁止对其执行 `alter index rebuild`。
同理，每个自举表至少有一个唯一索引**并同样进引导页**——否则自举之后仍无法按名/按号定位字典行。
**条目数 = 自举表数 + 自举索引数**。

**与 Oracle 的一处刻意不同**：

| | Oracle `bootstrap$` | 我们的引导页 |
| --- | --- | --- |
| 形式 | **表**：`LINE# / OBJ# / SQL_TEXT` | **固定格式的一页** |
| 内容 | **DDL 文本**，含 `EXTENTS (FILE 1 BLOCK 360)` | 结构化条目 |
| 启动时 | 解析 SQL 文本，"在内存中创建"对象 | 直接按段头位置读 |

**不存 DDL 文本的理由**：① 自举**不能依赖 SQL 解析器**——解析器自己也是被自举的对象；
② 文本与实现的漂移是静默的，编译期常量不会漂移。字典表的列定义作为**内核常量**存在，
引导页只回答一件事：**它的段在哪**。

**自举链**：

```text
块 0 文件头（格式硬编码）
  └─ 块 1 引导页（格式硬编码）：最小自举集的段头位置
       └─ 读 obj$ / col$ / seg$ —— 至此其余一切（含字典表自身）的定义与位置都可查到
            └─ 用户对象
```

**位置约定一旦发布不可变更**（或必须以 `format_version` 区分）。

**自描述与恢复**：`obj$` / `tab$` / `col$` / `ind$` / `seg$` 中**都含字典表自己**的行——
与 Oracle 一致（`tab$` 里有 `OBJ$` / `TAB$` / `COL$` 自己的记录）。
由此得到一条恢复路径：**引导页两副本皆坏时，可扫描 file 0 找段头页**（段头页带 `dataobj#`）重建引导页。
引导页因此不是单点——但仍**保留两份持久副本**（与 InnoDB 那种"双写缓冲"不是一回事：
这里存的是两份**持久副本**，不是一次写之前的临时副本）。它太小，而重建有成本。

**冗余副本范围收敛为引导页**：字典表**不做副本**——它们是普通段，由页校验、WAL 与备份保护。
原设计"表空间头 / 段目录 / 对象目录各写两份"随固定目录格式一并取消。

> **注意其局限**：副本防的是**页级**损坏，**不防文件丢失**。file 0 整个文件损坏仍会导致表空间不可用——文件级冗余由控制文件与备份承担。

**一个工作区一份字典**：每个工作区（含 `public`）自包含一套字典表，与"无跨工作区读写"的隔离模型一致（§13）。
对象号只需**工作区内唯一**。

**字典表段只存在于 file 0**；file 0 可**动态增长**（append 至文件末尾）以容纳元数据增长。

#### 3.1.2 字典表清单

**① 自举层**——上表 7 张表及其唯一索引，位置在引导页中。

**字典表分三层，判据是"这个事实属于对象、还是属于段"：**

| 层 | 表 | 回答什么 |
| --- | --- | --- |
| **对象层** | `obj$` | 数据库里**有哪些对象**、叫什么名字、**什么种类** |
| | `tab$` / `ind$` | 表与索引**各自特有**的属性 |
| | `undo$` | **undo 段本身**——自成一类，不在 `obj$` 里 |
| **段层** | `seg$` | 每个**段**的头在哪 |
| **物理层** | 段头页（§5.11） | 段的**物理组织**：区清单、HWM、表选项副本、段类型 |

**`obj$` 与 `seg$` 是"一对零或一"**：有对象**不一定**有段（视图、过程、函数没有），
有段**一定**有对象。**`dataobj#` 就是这条联系的载体**——`0` 表示无段。

**`seg$` 登记的是"持久且有对象"的段**——表段、索引段。**另两类不走这里**，
理由不在"统一好看"，而在**它们各自的持久性**：

| | 在哪 | 为什么 |
| --- | --- | --- |
| **表段、索引段** | `seg$` | 有对象、有名字、会被查询——本节就是它们 |
| **Undo 段** | **`undo$` 自成一路** | V1.0 **单段、位置固定、N = 256**（§14 第 28 项）。绕 `obj$` → `seg$` 要多两张表两行，换不来任何东西 |
| **临时段** | **不入任何字典** | 它**不持久化**（§4.8）——分配状态在**内存池**里，与 file 2 一起重置。在**持久**字典里给它留行，反而要多维护一套"失效登记怎么清理"的逻辑 |

**判据是持久性，不是形状**：三者都是段，但只有前两类会跨崩溃存活，
字典表的名字叫"持久化元数据"。

**② 普通字典表**——由自举层描述，可增删：

| 表 | 作用 | 备注 |
| --- | --- | --- |
| `stat$` | 访问计数、行数估计等**启发式统计** | **非事务表**：`logging = redo_only`，统计可丢，不参与恢复 |

**V1.0 不设的字典表**（是"推迟"，不是"不需要"）：

| 表 | 为什么不设 |
| --- | --- |
| `con$` / `ccol$` | **V1.0 不支持约束对象**。唯一性由**唯一索引**提供——那是 `ind$` 上的索引属性；列可空性由 `col$` 的标志位表达——那是列属性。两者都不是"约束" |
| `dependency$` | V1.0 不支持视图，无依赖关系可记 |

→ **V1.0 的字典表 = 自举 7 张 + `stat$` + `seq$`**。

**③ 明确不需要的**——照抄 Oracle 会把用不上的东西一并搬进来：

| Oracle 表 | 为什么不需要 |
| --- | --- |
| `user$` | **一个工作区一个属主**，无授权模型；属主身份记在控制文件（§2.6），不进字典 |
| `ts$` | **工作区即表空间**，一一对应，无多表空间概念 |
| `file$` | 文件清单的唯一权威是**控制文件**（§2.6）——见下方说明 |
| `tsq$` | 无表空间配额，工作区独占自己的文件 |
| `uet$` / `fet$` | 那是**字典管理**表空间的区分配方式；我们用**页分配位图**（§3.2） |
| `tabpart$` / `indpart$` | V1.0 不做分区 |
| `cluster$` | 不支持簇表；本库的聚簇需求由图表的邻接页承担（§5.6、§8） |
| `bootstrap$` | 由**引导页**承担，且不存 DDL 文本 |

**`file$` 与 `ts$` 的取舍（关键）**：Oracle 的控制文件存 `file$` 的**冗余副本**、`file$` 是权威，
两者必须一致，不一致即 `ORA-011xx`。我们**反过来**：控制文件本来就定长、可直接读、
且必须在任何字典表之前读出（否则解不开自举），它天然就是权威。
再维护一份 `file$` 只会制造一致性负担而无收益。
**运行期的查询需求由引擎内置的**固定表 `file$` **暴露**——内容取自控制文件的内存映像，
不落盘、不入 `obj$`（§3.1.4）。**它不是视图**：视图建立在表之上，而固定表在更底层。

**字典表用什么表选项**（属 §8 的五种表类型之一，选项上无特殊）：

| 选项 | 值 | 理由 |
| --- | --- | --- |
| `transactional` | ✅ | DDL 必须可回滚、可恢复 |
| `logging` | `full` | 字典不一致 = 工作区打不开，不是"丢少量数据" |
| `update_mode` | `in_place` | 字典行会被更新（`status`、`mtime`），且字典表小、行迁移风险低 |
| 其余 | 默认 | |

→ 字典表就是**普通关系表**。这一点本身即"结构通用"的直接结果。

#### 3.1.3 字典表的列定义

**十二张表**：普通工作区九张（自举层七张 + `stat$` + **`seq$`**）+ `public` 独有三张（§2.11）。
**这十二张都落盘**；此外还有**一张固定表 `file$`**（§3.1.4）——它不落盘，故不计入。

**四条贯穿全表的类型选择**（先说清，免得逐表重复）：

| 选择 | 理由 |
| --- | --- |
| **对象号、序号、计数一律 `INTEGER`**（= `NUMBER(38,0)`，REQ-TYP-003） | 不引入机器整数类型。`NUMBER` 的编码**保序**（§6.5），所以字节比较即值比较——字典表的索引照样能走 |
| **段的位置存 `file_id` + `block_id` 两列，不用 ROWID** | ROWID 是对内定位用的，**类型系统里没有它**（§7：不得作为对外持久引用）。拆成两个整数**既避开新类型，又语义更清楚** |
| **标识存 6 字节整数** | `CONV §1.1/§1.2`：对外 ID 由**序列**产生（每工作区 `seq$` 一条），**48 位无符号**。存储按 6 字节整数（与 ROWID、提交序号同宽），**比较即数值比较** ✓ |
| **内部时序用提交序号，对外时点用 `TIMESTAMP`** | 字典表的 `ctime` / `mtime` 是**提交序号**（`INTEGER`）——持久、可比，且能与其他内部时序（检查点、最老快照）**直接比大小**（§5.4、§11.7）。`user$` / `ws$` 的 `ctime` 是**给人看的时点**（`TIMESTAMP`，UTC，`CONV §5.4`） |

> **两种 `ctime` 的代价要写明：提交序号与墙上时间之间没有换算。**
> 想回答"这张表是什么时候建的"，现在只能拿到一个序号。
> **已定（§14 第 52 项）**：不设映射表——控制文件记最近 8 个检查点的 (序号, 时刻) 对，查询时线性内插并标注近似。
> **不预先存两列**——那会把"同一个事实存两份"再犯一次。

#### 自举层七张

**`obj$`** —— **数据库中所有对象的根定义**。任何对象——表、索引、undo 段、临时段，
以及将来的分区、过程、函数——都在这里有且**只有一行**。

**它不是"段的信息"**：段那一层在 `seg$`。`obj$.dataobj#` 是**指针**，指向该对象在
`seg$` 中的那一行；**无段的对象为 0**（视图、过程、函数都没有段）。

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `obj#` | INTEGER | 对象号，**主键**；工作区内唯一 |
| `name` | VARCHAR2 | 对象名 |
| `namespace` | INTEGER | 命名空间——**1 = 表，2 = 索引**。两者独立，故表与索引**可以同名**（同 Oracle 的概念） |
| `type#` | INTEGER | **对象种类**——见下 |
| `dataobj#` | INTEGER | **指向 `seg$`** 的指针；无段的对象为 0 |
| `ctime` | INTEGER | 创建时的提交序号 |
| `mtime` | INTEGER | 最后修改的提交序号 |
| `status` | INTEGER | 有效 / 失效（`Move` 之后索引失效即落在此，§4.7） |

**`type#` 的编号空间照 Oracle 预留——V1.0 不支持的也留着号，不挪用：**

| `type#` | 对象种类 | V1.0 |
| --- | --- | --- |
| 1 | 索引 | **用** |
| 2 | 表 | **用** |
| 3 | 簇 | 留位（不支持簇表，§3.1.2） |
| 4 | 视图 | 留位（待冻结项 25） |
| 5 | 同义词 | 留位 |
| 6 | 序列 | 留位 |
| 7 / 8 / 9 / 11 / 12 / 14 | 过程 / 函数 / 包 / 包体 / 触发器 / 类型体 | 留位（V1.0 无 PL/SQL，REQ-TYP-009） |
| 13 | 类型 | 留位 |
| 19 / 20 | 表分区 / 索引分区 | 留位（V1.0 不做分区） |
| 22 / 23 | 库 / 目录 | 留位 |

> **1–23 取自 Oracle 的 `obj$.type#`。** 其中 `1=INDEX`、`2=TABLE`、`3=CLUSTER`、`4=VIEW`、
> `5=SYNONYM`、`7/8/9/11/12/14`（六种程序单元）、`13=TYPE`、`19=表分区`
> （**非分区表仍是 2**）、`22=LIBRARY`、`23=DIRECTORY` 都经知识库确认。
>
> **有段、但不在 `obj$` 里的东西有两类**——它们不占 `type#`：
>
> | | 为什么不在 `obj$` 里 |
> | --- | --- |
> | **Undo 段** | 它自成一路（见下 `undo$`）——V1.0 单段、位置固定 |
> | **临时段** | 它**不持久化**（§4.8）——分配状态在**内存池**里，与 file 2 一起重置，字典表里给它留行反而是负担 |
>
> **`obj$` 只登记"持久且有名字"的对象**——这是它的判据。

> **对象号的两个方向**：
>
> | | 起点 | 方向 |
> | --- | --- | --- |
> | **自举对象**（字典表及其索引） | 1 | 向上，**≤ 99** |
> | **用户对象** | **100** | 向上 |
>
> **耗尽时的行为：显式报错，绝不回绕。** `NUMBER(38,0)` 在现实中不会耗尽，
> 但**回绕是必须排除的**——它会让陈旧引用指向**另一个对象**，
> 与"ROWID 不含代次""对象号不回绕"是同一条思路（§7、§4.6.3）。
> **一个用不完的编号空间不需要回绕策略，只需要一个到顶就报错的断言。**

> **1 / 2 是我们自己的取值**：知识库未确认 Oracle `obj$.namespace` 的数值
> （检索到的 `namespace` 是**库缓存**的那个概念，不是 `obj$` 的这个）。
> 这里只采纳它**同一概念**——"表与索引分属两个命名空间，因而可以同名"。

**`seg$`** —— **持久段的登记**：表段、索引段。`obj$.dataobj#` 是进入这张表的入口。
（undo 段与临时段不走这里，理由见 §3.1.2——**判据是持久性**。）

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `dataobj#` | INTEGER | 数据对象号，**主键** |
| `file_id` | INTEGER | **段头位置**——拆成两列而非 ROWID |
| `block_id` | INTEGER | |
| `iniexts` | INTEGER | 初始区数 |
| `ctime` | INTEGER | 创建提交序号 |

> **`seg$` 不存区清单**——那在**段头页**的区映射（§5.11）。这里只回答"**这个段的头在哪**"。
> 区清单要按段取，段头是权威；`seg$` 是**从对象号到段头的跳板**。
>
> **`seg$` 也不存段类型**。段的物理种类在**段头页**里（自描述，§4.2 的"段自描述"），
> 对象的种类在 `obj$.type#`（权威），索引的种类在 `ind$.type#`。
> 三层各司其职——`seg$` 再存一份就是**第三份副本**，而它不像 `ind$.status` 那样在热路径上。

**`undo$`** —— **Undo 段本身**，含它的位置。

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `seg#` | INTEGER | undo 段号，主键 |
| `status` | INTEGER | 空闲 / 活动 |
| `file_id` | INTEGER | **段头位置**。V1.0 恒为 1，但**保留列**——"单段"是 V1.0 的取值，不是格式 |
| `block_id` | INTEGER | |
| `ctime` | INTEGER | 创建提交序号 |

> **它为什么自成一路，不进 `obj$` / `seg$`**：undo 段**不是被查询的对象**——
> 它没有名字、没有命名空间、没有用户可见性；而 `obj$` 的三个关键列
> （`name` / `namespace` / 用户可见性）对它全是空的。
>
> **它也不该绕路**：位置就一个（V1.0 单段、固定 file 1），
> 直接记在这里，自举链是"引导页 → `undo$` → undo 段头"；
> 走 `obj$` → `seg$` 则变成"引导页 → `obj$` → `seg$` → undo 段头"——
> **多两张表两行，换来的只是形状上的一致**。
>
> **对比一下临时段**：它连这一行都不该有（§4.8：不持久化）。**两者都不在 `obj$` 里，
> 但理由不同**——undo 是"不需要"，临时是"不能"。

**`col$`** —— 列定义。

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `obj#` | INTEGER | → `obj$` |
| `col#` | INTEGER | 列序号，自 1 起 |
| `name` | VARCHAR2 | 列名 |
| `type#` | INTEGER | 类型编码（§6.5、§6.6） |
| `length` | INTEGER | CHAR/VARCHAR2 的**声明字节上限**（`CONV §5.4`）；**VECTOR 的维度** |
| `precision` / `scale` | INTEGER | 仅 NUMBER |
| `nullable` | BOOLEAN | |
| `deflt` | **字节串** | 默认值，**存该列的物理编码**（不是文本）——插入时可直接用，不必再解析。**见下** |
| `flags` | INTEGER | 保留 |

> **`deflt` 在字典表里是一列"无类型字节串"**——它的含义由同行的 `type#` 给出，
> 自己不带类型标记。**这是字典表的内部列类型，不进用户可见的类型系统**
> （与"字典表的列定义是内核常量"是同一层次，§3.1.1）。
>
> **为什么存编码而不存文本**：存文本意味着每次插入都要解析一遍。
> 而 V1.0 的默认值**必须是常量**——不支持 `SYSDATE` / `CURRENT_TIMESTAMP`
> 这类"每次插入求值"的形式。否则 `deflt` 就不能是预编码的值，
> 插入路径要拖一个表达式求值器进来。
>
> **为什么不另设一个长度列**：Oracle 的 `COL$` 用 `DEFAULT$` + `DEFLENGTH` 两列，
> 而它的已知故障 **`ORA-936`** 正是**这两列不一致**——`DEFAULT$` 为 NULL
> 而 `DEFLENGTH` 不为 NULL，解析器就找不到默认表达式。
> **一个值不该拆成两列存。** 我们的行格式本就带变长列的长度
> （`var_offsets`，§6.7）——`deflt` **自定长，不需要第二列**。

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `obj#` | INTEGER | 索引对象号，主键 |

| `type#` | INTEGER | 0 = B+Tree / 1 = ANN / 2 = 邻接（图的边） |
| `cols` | INTEGER | 键列数 |

> **ANN 的物理参数（`m` / `ef` / 距离度量）不在这里，在段头**（§5.11：metapage 并入段头页）。
> 判据是"**段自描述**"——打开段即可分派行为，不必回查目录（§4.2 的同一条理由）。

**`status` 在 `obj$` 与 `ind$` 两处都有，是刻意的性能冗余，不是疏漏**：

- **`obj$` 是段层的统一登记**——表段、索引段、undo 段在那里各有一行，
  统一回答"有没有段、段号是多少、状态如何"。**这是所有对象种类共有的那一层。**
- **`ind$` 是索引这一种类的元数据**（键列、唯一性、类型）。
  索引有效性在索引访问路径上是**热的**，每次多回查一次 `obj$` 不值得。

**权威是 `obj$`**（§4.7：`Move` 之后索引失效即落在 `obj$.status`），
`ind$` 是它的副本。**两者只在同一个事务里一起改**——单写入路径，因此不会漂移。
**冗余是为了读得快，不是为了写得随意。**

**`tab$` 的段同样属于 `obj$`**——表、索引、undo 段一视同仁；
`tab$` / `ind$` / `undo$` 只放各自种类特有的事实，不放段的位置。

#### 自举层的索引

§3.1.1 定了"每个自举表至少有一个唯一索引，**并同样进引导页**"，
**条目数 = 表数 + 索引数**。这里是那份清单——**与列定义一样，是内核常量**。

| 表 | 索引 | 键列 | 为什么必须有 |
| --- | --- | --- | --- |
| `obj$` | 主键 | `(obj#)` | **按号**解析——建表之后的一切路径 |
| `obj$` | `i_obj_name` | `(namespace, name)` | **按名**解析——`CREATE` / `DROP` / 名字解析的第一步 |
| `tab$` | 主键 | `(obj#)` | 由对象号取表属性 |
| `col$` | 主键 | `(obj#, col#)` | 取列定义 |
| `ind$` | 主键 | `(obj#)` | 由索引对象号取索引属性 |
| `icol$` | 主键 | `(obj#, pos#)` | 取键列组成 |
| `seg$` | 主键 | `(dataobj#)` | 由数据对象号取段头位置 |
| `undo$` | 主键 | `(seg#)` | 取 undo 段 |

**八项索引**（`obj$` 两个，其余各一）**+ 七张表 = 引导页 15 个条目**。

**同一张表的多个索引**：`obj$` 的两个**都要，不是冗余**——
`(obj#)` 走号、`(namespace, name)` 走名，两条路都是热路径。

**为什么"主键"也要单独列出来**：V1.0 **没有约束对象**（§3.1.2），
**主键在这里就是"一个唯一索引"**——它同样有段、同样要登记进 `seg$`、
同样要进引导页。不列出来，自举时就少了一段位置。

**键序是照访问模式定的，不是照规范化**：

- `col$(obj#, col#)` 与 `icol$(obj#, pos#)` 把 `obj#` 放在**最前**——
  "取某对象的全部列"于是是**一次范围扫**，而不是 N 次点查
- `seg$` 的键是 `dataobj#` 而**不是** `obj#`——`seg$` 的入口就是数据对象号（§3.1.2 的分层）

#### `public` 独有的三张

**`user$`** —— 主体。

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `user_id` | INTEGER | 主键；**48 位序列值**（`CONV` §1.2、§3 的"标识存 6 字节整数"）——**不是 UUID**（见下方注） |
| `name` | VARCHAR2 | 登录名；**唯一索引**（登录名不可重复） |
| `passwd` | VARCHAR2 | **不可逆的验证子**——不是口令，也不是可解密的口令密文（见下） |
| `status` | INTEGER | 有效 / 停用 |
| `ctime` | TIMESTAMP | |

> **`passwd` 的做法参照 Oracle 的 `USER$.PASSWORD`**，但**格式自描述，一列装完**：
>
> ```text
> $<算法>$<迭代数>$<盐>$<哈希>
> ```
>
> **为什么把算法与迭代数一起存进值里**：换算法时存量口令仍要能校验。
> 若参数只写在代码里，改一次算法所有用户立刻登不进来。自描述格式让
> "一组参数对应一批用户"成为可能，改口令时自然迁移到新参数。
>
> **为什么必须是不可逆的**：可逆就意味着"拿到 `user$` 即可还原全部口令"。
> 而 `user$` 会进 redo、进备份、还会被 reflink 克隆复制（§2.7）——
> **验证子即使在那些地方泄露也不能反推出口令**。
>
> **一处诚实的边界**：口令**变更**的 undo 记录里留有旧验证子。
> 这是所有 MVCC 数据库的共同性质，暴露窗口由 undo 的保留期与配额限定（§4.6.5）。
>
> **已定（§14 第 49 项）**：**PBKDF2-SHA512**、盐 16B 随机、迭代数自描述（初始 ≥ 10 万）。

> **注（2026-10-04 修正）**：`user$` / `ws$` 两表的 `user_id` / `workspace_id`
> 曾写作 `UUID`——那是 D-01（对象 ID 方案）落定**之前**的 128 位随机 ID 时代的遗留。
> 现行口径：**所有对外可见 ID 由系统级序列产生**（`CONV` §1.1；"不采用随机数"），
> `workspace_id` 与 `user_id` 均为 **`public` 的实例级序列**值、48 位、存 6 字节整数
> （本文件"类型与编码纪律"）。`UUID` 只是**类型系统**里的一个列类型（`TYP` 域），
> 与标识分配无关。

#### 3.1.4 固定表：权威在文件或内存里的信息

有一类信息**权威不在任何表里**——它在控制文件、在内存结构里。它们同样需要被查询。

**用固定表（fixed table）暴露**：固定表的行由引擎在**查询时即时产生**，不来自任何段。
它**没有段、不在 `obj$` 里、只读**，定义是引擎里的代码而不是数据。

> **它不是视图。** 视图是建立在**这一层之上**的东西——Oracle 里恰好是反过来的：
> `V$` 视图建在 `X$` 固定表**之上**，那些视图的 SELECT 文本本身还存在一张固定表里
> （`X$KQFVT` 的 `KQFTPSEL`）。固定表是**更底层**的取数机制：
> 不占命名空间、不入 `obj$`、不是数据库对象。（V1.0 本来也不支持视图——待冻结项 25。）

**为什么叫"固定表"**：这个概念直接取自 Oracle 的 `X$` 表族——`X$KCCFE`（控制文件的数据文件条目）、
`X$KCCDI`（数据库条目）、`X$KCCCP`（检查点进度）都是**从控制文件读出内容**的固定表。

##### 名称：不加 `X$` 前缀

Oracle 的 `X$` 前缀含义是"**内部、不受支持、随时可变**"。
**我们不采纳**：我们的固定表是**对外承诺的稳定接口**——`file$` 是查询数据文件清单的
**唯一途径**，它必须能用、能被依赖。那个前缀要传达的"不稳定"在我们这里不存在。

**`$` 后缀照旧**（与 `obj$`、`seg$` 一致）：**从使用者角度看它们都是"元数据表"**，
不需要知道内容来自段还是来自内存。**区别落在引擎内部，不落在名字上。**

##### 第一张（也是当前唯一一张）：`file$` —— 数据文件清单

| 列 | 来源 |
| --- | --- |
| `file_id`、角色、状态、**创建时大小**、创建时间、**完整路径** | 控制文件的**数据文件记录**段（§2.6） |

**它为什么必须是固定表**：

- 若**落盘**：控制文件与它就有两个真相源，而控制文件是唯一权威（§3.1.2）
- 若**不做**：运行期查不到"这个工作区有哪些数据文件"——一个合理的运维需求

**Oracle 在这里有第二个真相源，我们没有**：

| Oracle 的 | 内容来自 | 我们的对应 |
| --- | --- | --- |
| `V$DATAFILE` | **控制文件** | **`file$`** |
| `DBA_DATA_FILES` | 字典表 `FILE$` | **不设**——它就是要避免的第二份 |
| `V$DATAFILE_HEADER` | **数据文件头** | 由**文件头页**直接承担（§3.2） |

**前两者可以不一致**——这是"文件已在控制文件登记、但字典里没有"这类故障的常见根因。
我们只留一份。**而我们与 Oracle 的后两行分工完全同构**：控制文件存**创建时大小**，
文件头自述**当前大小**（§2.6 的既定点）——所以查询形态也一样，
`file$` 回答"登记了什么"，文件头回答"它现在多大"。

##### 通用判据

> 信息同时满足两条时用固定表——**① 权威已经在文件或内存里；② 它需要被 SQL 查询。**
> 只满足 ① 不必暴露；只满足 ② 那它就是一张普通字典表。

**日后会增，且以内存结构为主**：缓冲池与工作集的状态（§5.10）、检查点进度、redo 组状态。
**判据不变，但每加一张都要先问：它会不会造出第二个真相源？** 不会才能加。

##### 两条实现约束（取自 Oracle 的教训）

| | Oracle | 我们 |
| --- | --- | --- |
| **访问路径** | 专门的计划 `FIXED TABLE FULL` / `FIXED TABLE FIXED INDEX` | 行数**有界且小**（数据文件 ≤ 1024，§2.6）——全扫即可，**不引入专门的访问路径** |
| **行数估计** | 无统计信息时**默认估 10 万行**，实际可差 80 倍（`X$KTFBUE` 的已知案例），足以让优化器选错计划 | **引擎直接给出基数**——固定表在产生行之前就知道自己有多少行，**不靠统计信息，也不靠默认值** |

**第一条是"轻量"的直接推论；第二条是必须避开的坑。**
固定表**不需要统计信息**，这是它与字典表的一处实现差异。

##### 只读、单写路径

`file$` 不可写。要改文件清单只能走 DDL / 管理操作——它们去改**控制文件**，
下次查询固定表时自然反映。**这保证了文件清单只有一个写入路径。**
### 3.2 数据文件（file 3+）

每个数据文件的头部含：

| 项 | 说明 |
| --- | --- |
| 文件头 | file_id、所属表空间、格式版本、大小 |
| **区分配位图** | 本文件内哪些块已分配给段（`page_type = 8`） |

**区分配位图（LMT）的页体与文件布局见 §5.11**；**预留式布局**（2026-10-05 定案）：
位图区**全量预留**在文件头之后（块 1 起 320 页 = 5 MiB，覆盖到 4 TiB 上限），
数据区从预留区之后向上、尾部纯数据——**增长 = 尾部追加数据块，位图区永不搬移**
（§5.11 / §3.3）。

**区分配位图放每个文件头部（不集中在 file 0）**：文件因此**自描述**——单独移动、校验、恢复时能自证；区分配操作只触碰目标文件。

数据文件的**增长方式**（自动扩展、自动新增、到顶报错）见 §3.3。

### 3.3 数据文件的增长

空间不足时有**四级阶梯**，前两级完全不出段、不出文件：

```text
① 段内找空间（页级 → 区级，§4.5）
② 回收失效段（§4.7）——不扩任何文件
③ 扩展已有数据文件（自动扩展）
④ 新增数据文件（自动新增；创建前须先探测容量，§2.8）
────────────────────────────────
⑤ 到顶 → 明确报错
```

**前两级几乎总是够用**——这是"不主动回收"（§4.7）换来的：回收的成本被推迟到
真正需要空间时才付，而付的时候正好解决了问题。

#### ③ 扩展已有文件：便宜，且不碰控制文件

创建数据文件时设定四项属性：

| 属性 | 默认 | 说明 |
| --- | --- | --- |
| `initial_size` | 工作区默认 | 创建时的文件大小 |
| `autoextend` | **开** | 不足时自动增长 |
| `next_size` | 工作区默认 | 每次增长多少 |
| `max_size` | 4 TiB | 单文件上限 |

**`max_size` 的 4 TiB 不是随手定的**——它就是 ROWID 的
`block_id 28 位 × 16KB`（§7）。文件不可能超过它，因为超过之后
**页地址就编不进 ROWID 了**。这不是策略选择，是格式的硬边界。

**扩展是"原地长大"，不改控制文件**——这是一个有意设计的便宜：

> 控制文件的数据文件记录只存**创建时大小**（§2.6），**当前大小由文件头自述**。
> 于是扩展只需"追加文件尾部 + 更新文件头"，**一次操作，不碰双副本控制文件**。

**追加不会撞上任何结构**（2026-10-05 定案）：位图区**全量预留**在**文件头之后**
（块 1 起 320 页 = 5 MiB，覆盖到 4 TiB 的文件上限），数据区从预留区之后向上、
尾部是纯数据——**扩展 = `set_len` + 一次文件头页写**（`DataFile::extend`），
位图区永不搬移（§5.11"预留式布局"）。

这让"扩展"便宜到可以作为常态，而"新增文件"才需要走控制文件的慢路径。
（§2.6 当初把"大小"定义为*创建时*大小，就是为了这个。）

#### ④ 新增数据文件：走控制文件的慢路径

当前文件都到 `max_size` 时，**默认自动创建下一个数据文件**：

- 新文件按**工作区级默认模板**创建（默认大小、自动扩展、上限）
- 需要更新**工作区控制文件 + 全局控制文件**（§2.6 的更新时机表）——**低频**
- **完整路径写进工作区控制文件**（§2.6 的"文件路径"一节）；命名沿用规则 `<ws>_data_NN`（§2.2）

**也可以人工添加**：自动新增是**默认**行为，不是唯一途径。管理员可以显式指定
文件大小与属性来添加——两条路径产出同一种文件，只是触发者不同。

> 自动新增与自动扩展都**不是必须**：`autoextend` 可关，自动新增可关
> （关掉后到上限就报错，等管理员介入）。默认开是因为它更省事，
> 而不是因为系统"猜"用户想要更多空间。

#### ⑤ 到顶：明确失败

**硬上限是 1024 个数据文件**——同样来自 ROWID（`file_id 10 位`，§7）。

到顶时**返回明确的错误**，不静默截断、不降级：
"工作区数据文件数已达上限 1024"。

> 1024 × 4 TiB = **4 PiB/工作区**。对单工作区而言这在物理上不可达，
> 所以这条上限不会成为实际约束——但**报错路径仍须实现**：
> "不可达"是当前的判断，不是永恒的保证。

#### 与配额的关系：两条独立约束

§2.2 的配额按角色分设，它与文件增长的边界**不是一回事**：

| 约束 | 性质 | 达到时 |
| --- | --- | --- |
| `max_size` / 1024 文件 | **物理**上限（由 ROWID 位宽决定） | **无法**再增长 |
| 工作区配额 | **策略**上限（管理员设定） | 不再自动增长，**调额后可继续** |

自动扩展**必须同时受两者约束**——先撞到哪个就停在哪个。两者撞线时**报不同的错误**：
配额撞线是"可调额后重试"，物理上限是"到此为止"。混在一起报会让使用者无从区分
"我该去调额"还是"我该去清理"。

### 3.4 数据文件的 MOVE

把一个数据文件从一个文件系统挪到另一个——用于**加盘后平衡容量、换盘、或把热点分散**。

#### 协议：暂停写访问，窗内完成复制与切换（已定案：待冻结项 40）

**暂停该工作区的写访问（读继续）→ 复制 → 迁移元数据 → 清理原文件 → 恢复写**：

```text
① 暂停：该工作区的写访问停止（与 §2.14 的冻结同义：拒新写、等在途写结束；读继续）
② 复制：文件内容送达目标文件系统
        ——同文件系统且支持 reflink ⇒ **近瞬时**（元数据操作）
        ——跨文件系统 ⇒ 真实数据复制，**窗口 ∝ 文件大小**（如实记录，见下）
③ 迁移元数据：控制文件中**该文件的路径字段**（§2.6 存完整路径）改指新位置
④ 清理：删除原文件
⑤ 恢复写访问
```

**为什么不做 redo 追平**（旧稿的"复制在窗口外 + 按 `file_id` 重放增量"形态，弃用）：
它把窗口与文件大小解耦，代价是一条"筛 redo、按文件重放"的专用路径与两段冻结的复杂度。
本库画像下不值：文件量级 MB–GB、MOVE 是低频运维，**同盘移动在 COW 文件系统上走 reflink，
窗口本来就是毫秒级**。"先要简单"——追平形态留作实测后的增量优化（纯增量、不改格式与协议）。

**如实记录的代价**：跨文件系统（或非 reflink）时，**暂停窗口与文件大小成正比**——
这是简化换来的；把 MOVE 安排在低峰是运维决策。

**中断与残留**：MOVE 是运维操作、非事务，崩在任一步都**以控制文件的路径字段为唯一权威**——
它指向的文件是"源"；另一份（若存在）是残留：重试 MOVE 或下次打开时清理。
协议顺序保证"控制文件已指新文件 ⇒ 复制必已完成"（③ 在 ② 之后、同在暂停窗内）✓。

#### ROWID 不受影响——这是 file_id 设计的兑现

**文件挪了窝，页地址没变**：ROWID 里的 `file_id` 是**逻辑文件号**，不是物理位置（§7）。
所以：

> **文件 MOVE 不改变任何 ROWID**——索引、行引用、undo 链统统不需要动。

这是 §7 把 ROWID 定义为"表空间内相对地址"而不是"文件路径 + 偏移"的直接收益。
反过来说，**如果 ROWID 里编了物理位置，这个操作就要重建所有索引**——
和下面那个 `Move` 一样贵。

#### 与 §4.7 的 `Move` 区分（务必分清）

| | §4.7 的 `Move` | **本节的 MOVE** |
| --- | --- | --- |
| 搬什么 | **段**——表的数据 | **文件**——整份数据文件 |
| ROWID | **变化 ⇒ 该表索引全部失效，必须重建** | **不变** |
| 用途 | 整理碎片（§4.7） | 平衡文件系统容量、换盘 |
| 频度 | 低频**重活** | **运维常态** |

两者的名字相近，代价却差一个数量级。**挪文件是常态，挪段是重活。**
