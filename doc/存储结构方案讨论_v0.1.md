## 1 检索到的 Oracle 机制

### 1.1 逻辑层次与物理承载

```
表空间 (tablespace)   ← 段的逻辑容器
  └─ 段 (segment)      ← 为某对象（表/索引/undo/临时）分配的区集合
      └─ 区 (extent)    ← **一次分配**获得的**逻辑连续**的块集合
          └─ 块 (block) ← 最小 I/O 单位
```

对应到物理层：段存储在表空间中；表空间由**数据文件**承载。

关键约束（知识库明确）：

| 约束 | 内容 |
| --- | --- |
| 表空间与数据文件 | 一个表空间包含**一个或多个**数据文件；可为空但不能使用 |
| **文件归属唯一** | **一个数据文件只能属于一个表空间**，不可跨表空间 |
| 段与表空间 | 段存在于某个表空间中；表被映射为段，不单独作为存储结构 |
| 物理与逻辑独立 | 可移动/重命名/增减数据文件而对应用透明 |

> 最后一条是这套分层**存在的理由**——不是为了好看，而是让物理文件的运维不影响逻辑结构。

### 1.2 两个**独立**的管理维度（最容易混淆的一点）

Oracle 有两个正交的空间管理问题，各有自己的机制。混为一谈会导致设计错误：

| 维度 | 解决什么问题 | 旧方案 | 现代方案 |
| --- | --- | --- | --- |
| **区管理**（extent management） | 数据文件里**哪些块已分配给段** | 字典管理（`sys.uet$`/`sys.fet$`） | **本地管理 LMT**：数据文件头部的**位图** |
| **段空间管理**（segment space management） | 段内**哪些块还能放新行** | MSSM：**FREELIST**（段头维护空闲块列表） | **ASSM**：段头中的**位图** |

两者的位图在**不同位置、不同粒度**：

- **LMT 位图**：位于**数据文件头部**，粒度是"块是否已分配给某个段" → 服务于**区分配**
- **ASSM 位图**：位于**段头块**，粒度是"段内块的空闲程度" → 服务于**插入时找可用块**

字典管理被淘汰的原因（知识库）：产生**递归空间操作**、**数据字典争用**与**额外回滚生成**；LMT 消除了这些，并能**自动合并相邻空闲区**。

MSSM 的问题：FREELIST 在高并发插入时造成**段头热块**（`buffer busy waits`）。ASSM 以位图替代，消除了这一争用点。

LMT 的区分配有两种方式：
- `AUTOALLOCATE`：由系统按段大小自适应决定区大小
- `UNIFORM SIZE`：所有区固定同一大小

### 1.3 容量限制（对 ROWID 设计有直接影响）

| 模型 | 数据文件数 | 单文件上限 |
| --- | --- | --- |
| **Smallfile**（传统） | 每表空间最多 **1022** 个 | **2²² − 1 块**；8K 块 ≈ **32 GB** |
| **Bigfile** | **只能 1 个** | 块大小 × 2³⁶；8K 块 = **32 TB**，32K 块 = 128 TB |
| 整库 | 最多 64000 个数据文件 | — |

> **32GB 这个数字不是随意的**——它直接来自 Oracle 扩展 ROWID 中"块号 22 位"的编码限制（见 §1.5）。

### 1.4 只读表空间，以及它的**缺口**（对本项目至关重要）

知识库给出的事实：

- 只读表空间的数据文件在正常操作期间**不会被写入**；非只读表空间即使数据没变，每次打开/关闭/检查点都要更新文件头
- 只读表空间无需定期备份；恢复时通常无需前滚
- 只读属性同时记录在数据字典与控制文件中，文件头保持"过时"状态

**但有一个重要缺口**：

> 只读表空间**只限制写数据文件**，**不阻止只修改数据字典的 DDL**。
> 实测语义：只读表空间中**不能新建表**（`ORA-01647`），但**可以 `DROP TABLE`**——
> 因为 drop 只改数据字典，不写该表空间的数据文件。

**这条直接影响我们的 `public` 设计**：如果用"只读表空间"作为 public 只读的**实现机制**，那么 `DROP TABLE` 这类操作会**绕过**该限制。public 的只读必须在**引擎与授权层**强制，不能只靠文件只读性。

### 1.5 ROWID 与"对象号"的由来

| 版本 | 结构 | 问题 |
| --- | --- | --- |
| Oracle 7（受限 ROWID） | 文件号 + 块号 + 行号 | 文件号**非全局唯一**，无法跨表空间唯一标识 |
| Oracle 8i+（扩展 ROWID） | **对象号** + 相对文件号 + 块号 + 行号 | 增加对象号以解决上述问题 |

内部 10 字节：`Object ID(4) + DBA/RFN(4) + Row(2)`；外部 base-64 编码 18 字符。

**为什么加对象号**：因为**相对文件号只在一个表空间内唯一**。同一实例中不同表空间可以有相同的文件号。

**这条对我们的启示**：如果采用"每用户一个表空间"，那么不同用户的表空间里会有**相同的 (file_id, page_id)**。这带来两个后果：
1. 由于用户隔离，跨用户不会互相访问 ROWID —— 安全性上可接受；
2. 但**任何进程内的共享结构**（缓冲池缓存键、诊断输出、日志、审计）若只用 `(file_id, page_id, slot)` 定位，会**跨工作区碰撞**。

设计文档 §7 已要求"数据页包含 WorkspaceId 或其受校验映射"，正是为此。

### 1.6 高水位线（HWM）

- HWM 是段内"**已格式化且可能含数据**的块"的边界；其下可能含空块，其上为未格式化块
- **删除不降低 HWM**：大量删除后全表扫描仍扫过空块，需段收缩或 `TRUNCATE` 才重置
- 插入时 HWM 推进：初始每次 1 块，之后每次 5 块或至区边界（取小）

对读多写少的产品，HWM 的"扫空块"代价值得警惕，但 ASSM 位图本身已缓解分配争用。

## 2 对你提出方案的逐点分析

| 你的要点 | 分析 | 建议 |
| --- | --- | --- |
| 层次：tablespace → datafile → segment → extent → block | 与 Oracle 一致，可直接采用 | ✅ 采用 |
| 每个用户独立 tablespace | 满足隔离，且与"数据文件不可跨表空间"配合良好 | ✅ 采用 |
| 每个 tablespace 含 1 或多个 datafile | 两者都支持会增加管理面。我们的场景是单机中等规模 | ⚠️ 见 Q3 |
| 用户只能访问自己的 tablespace + public | 与总体方案 §3 一致 | ✅ 采用，但**只读需引擎强制**（§1.4） |
| 元数据存放在 public tablespace | **存在矛盾**，见下 | ❓ 见 Q1 |
| admin 元数据存放在 system tablespace | 与总体方案 §4"平台控制目录"一致 | ✅ 采用 |

### 关于"元数据放 public"的矛盾

总体方案 §3、需求文档 REQ-ISO-004 规定 **public 对普通用户只读**。若全库目录（描述"哪些用户有哪些表"）也存在 public，则：

1. **普通用户建表时无法写目录**——public 只读，而目录必须可写；
2. 即使允许写，**普通用户能读到其他用户的对象名**，直接违反 REQ-ISO-006（"普通用户不能判断另一用户对象是否存在"）与 REQ-ISO-007。

Oracle 的解法是：数据字典在 **SYSTEM** 表空间（可写），但用户**只能经引擎间接访问**，且有权限体系约束可见范围。

> 因此"元数据放 public"需要澄清具体指哪一种元数据。见 Q1。

### 关于隔离的强化建议

即使每个用户一个 tablespace，仍建议：

- **每个工作区独立的数据文件与目录**，不使用硬链接、不共用文件（总体方案 §4）
- 页头保留 **workspace 受校验映射**（设计文档 §7），使跨区误读可被检出
- 缓冲池缓存键**必须包含工作区标识**（§1.5 的碰撞问题）

## 3 建议的方案

```text
实例
├── system tablespace        ← admin 元数据（工作区注册表、额度、进程状态）
│     文件：system.dbf
│
├── public tablespace        ← 公共工作区数据（向所有用户只读）
│     文件：public_01.dbf, public_02.dbf, ...
│
└── 每个用户工作区
       ├── <ws>_data tablespace   ← 该用户的表/索引/JSON/向量
       │     文件：<ws>_data_01.dbf ...
       ├── <ws>_undo tablespace   ← 该用户的事务 Undo
       │     文件：<ws>_undo_01.dbf
       └── <ws>_temp tablespace   ← 排序/哈希/分词溢出
             文件：<ws>_temp_01.dbf
```

**为什么每用户是 3 个表空间而不是 1 个**：

| 表空间 | 分离的理由 |
| --- | --- |
| data | 主体数据，需备份 |
| **undo** | ① 与数据争用空间会导致数据无法增长；② 备份策略不同（Undo 不必长期保留）；③ 回滚/一致性读需独立回收；④ **绝不能跨用户共享**——共享 Undo 会使 A 的旧版本可被 B 访问 |
| **temp** | 临时空间不应进入持久备份；泄漏时可直接重建；避免污染数据文件的空闲空间统计 |

这与 Oracle 的 SYSTEM / UNDO / TEMP 分离思路一致。

**管理机制的选择**：

| 维度 | 选择 | 理由 |
| --- | --- | --- |
| 区管理 | **本地管理（LMT 式）** | 位图在数据文件头部；避免字典争用与递归空间操作；自动合并相邻空闲区 |
| 段空间管理 | **ASSM 式位图** | 避免 FREELIST 的段头热块；与读多写少画像相容 |
| 区大小 | **UNIFORM 优先**，必要时 AUTOALLOCATE | UNIFORM 可预测、便于核算配额；AUTOALLOCATE 减少小对象浪费 |
| HWM | 采用，但需可收缩 | 避免删除后扫描空块（§1.6） |

**只读实现**：public 的只读**不能仅靠文件只读性**（§1.4 缺口），必须：
1. 引擎层拒绝任何写入 public 的语句；
2. 授权层不向普通用户授予 public 的写权限；
3. public 的 DDL 只能由 public 发布身份执行。

## 4 待决策问题

### Q1（最关键）：你说的"元数据存放在 public tablespace"具体指哪一种？

| 选项 | 含义 | 后果 |
| --- | --- | --- |
| **A** | `public` 工作区**自身对象**的目录（描述 public 里有哪些表） | 只读对象，可与数据同放 public ✅ |
| **B** | **全库**对象目录（描述所有用户有哪些表） | ❌ 与 public 只读矛盾，且泄露用户对象名 |
| **C** | 全库对象目录，但放在 **system**（用户仅经引擎间接访问，可见范围受工作区约束） | 与 Oracle 一致 ✅ |

**我的建议：C**。即 public 只放公共**数据及其自身目录**；全库目录在 **system**，用户不能直接查询，只能经引擎解析本人对象。

### Q2：每个用户是否需要独立的 undo 与 temp 表空间？

- **A（建议）**：是，每用户 3 个表空间（data / undo / temp）
- **B**：每用户 1 个数据表空间，undo/temp 作为工作区内文件但不建模为表空间
- **C**：undo/temp 由系统级共享（**不建议**：跨用户共享 Undo 破坏隔离）

### Q3：数据文件数量模型？

- **A（建议）**：默认 **1 表空间 = 1 数据文件**，但架构上支持多文件（便于后续拆盘/扩容）
- **B**：完全 bigfile 式，永远单文件，上限 = 块大小 × 2³⁶
- **C**：完全 smallfile 式，单文件 ≤ 2²²−1 块（8K → 32GB），可多文件

> 注意 B/C 的区别会**反过来影响 ROWID 位宽**（D-07）：smallfile 的 32GB 限制正来自块号 22 位。

### Q4：ROWID 是否包含工作区/对象标识？

§1.5 说明 Oracle 因"文件号仅表空间内唯一"而引入对象号。我们面临同样问题。

- **A（建议）**：ROWID 保持 `(file_id, page_id, slot, generation)`，但**规定 ROWID 必须在工作区上下文中解释**，且所有共享结构（缓存键、日志、诊断）必须同时携带工作区标识
- **B**：ROWID 内嵌工作区标识或对象号，使其**自包含、实例内全局唯一**

B 更安全但更宽（影响索引项大小与 B+Tree 扇出）；A 更省空间但依赖"处处带上工作区"的纪律。

**这同时是 `spec/README.md` 中 D-07 的输入**，建议与 Q3 一并决定。
