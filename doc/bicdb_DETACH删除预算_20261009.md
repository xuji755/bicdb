# DETACH DELETE 关联边预算（2026-10-09）

`DETACH DELETE` 现在有独立的关联边数上限，覆盖 GRP-003 的默认 10,000 条与可配置要求。超限拒绝整个 Cypher 语句，不发布部分节点、关系、属性树、邻接树或全文源事件。普通 `DELETE n` 仍要求节点已无关联边。

## 配置与生效

在工作区的 `bicdb.ini` 中配置：

```ini
[graph]
detach_edge_limit=10000
```

取值为整数 `0..500000`，缺省为 `10000`。`0` 允许删除孤立节点，禁止 DETACH 自动移除关联边。该参数重启生效，不在运行中轮询配置文件。启动时 `-c graph.detach_edge_limit=N` 优先于文件，但不把覆盖值写回文件。旧参数文件没有 `[graph]` 节仍使用默认值。

```bash
bicdb start -p /path/to/workspace -c graph.detach_edge_limit=20000
```

直连 `bicdb sql` 和 `bicdb shell` 也接入文件及 `-c` 配置。若 `bicdb sql` 连接正在运行的服务，则使用服务启动时的值；客户端的 `-c` 不会重配置服务。认证后的客户端 `STATUS` 增加 `graph_detach_edge_limit`，表示服务实际值；`bicdb params` 表示所读取文件及命令行的参数值，两者应分别理解。

SQL 的可信 Session API 提供 `set_graph_detach_edge_limit`，非法范围拒绝且保留原值。Cypher 不能调用它。初始化模板不复制实例运行参数，目标工作区独立设置预算。

## 计数与原子性

预算属于一条 Cypher 语句，共用同一个执行器计数器。多个删除子句、WITH、相关 CALL 子查询、UNION 分支共同累计，不能在子查询中重新开始计数。

删除子句先收集目标节点，再从当前暂存图的正反邻接集合惰性读取关系键，去重并检查剩余预算，成功后才开始移除本子句的对象：

- 自环、两端均被选中的关系、重复匹配的同一关系，按物理关系 ID 只计一次；平行关系分别计数。
- 同一子句 `DETACH DELETE n,r` 中，`r` 若仍关联到所选节点，仍计入预算，不能通过同时显式选中关系绕过限制。
- 更早的子句已实际删除的关系不再计数。仅显式 `DELETE r` 不消耗 DETACH 预算，适合先分批清理关系，再删节点。
- 累计超限时丢弃整个语句的暂存变化，包括先前子句的 SET、CREATE、DELETE。外层 SQL 事务中此前**其他成功语句**的修改仍保留，可以继续提交或回滚。

错误包含 `DETACH DELETE relationship budget exceeded`、限额与已使用数，并建议先分批删除关系。现有 affected 统计保持显式选中节点/关系数量，不把隐式删除关系加入返回数量。

这里检查的是执行时当前拓扑，而不是按记忆或缓存推断节点的度。预检查超限时立即停止，不先构建整座高出度节点的关系列表。邻接键检查也消耗现有扩展/表达式工作预算；重复方向键虽不重复消耗边数预算，仍消耗工作预算。因此把关联边限额调高，不等于取消默认 100,000 次的扩展/表达式约束。

## 验证及限制

证据目录：[bicdb-graph-detach-budget-20261009](evidence/bicdb-graph-detach-budget-20261009/README.md)。核心测试覆盖默认 10,000/10,001 条边边界、自环、平行边、共享端点、零值、跨子句/CALL/UNION 和工作预算；装配测试覆盖直连、REPL、可信 Session 配置及回滚；真实认证服务测试覆盖文件与启动覆盖优先级、重启边界、属性/邻接树、节点与关系全文、源队列、失败语句、回滚、进程异常退出恢复和已提交删除的重启持久化。

仍采用当前单写者与整图暂存写路径。本功能限制单语句隐式删除关系的工作量，不宣称解决大型图写入内存、专用邻接段、并发端点锁或旧段回收。测试写入均在独立 bicdb 实例中进行，本功能运行时不连接 Neo4j。
