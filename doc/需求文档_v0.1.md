## 1 文档说明

### 1.1 目的

本文定义 bicdb 在 V1.0 范围内需要满足的需求，作为设计评审、任务拆分、验收判据与覆盖度检查的共同基线。

本文**不描述实现方案**。凡涉及"怎么做"的内容一律回到总体方案，本文只回答"必须做到什么、如何判定做到了"。

### 1.2 与总体方案的关系

| 本文 | 总体方案 |
| --- | --- |
| 需求（做什么、判定标准） | 设计（怎么做、模块边界、阶段） |
| 编号需求，可逐条追溯 | 契约与协议条款 |
| 需求覆盖度检查的依据 | 阶段与验收流程 |

两者冲突时以本文为准（需求优先），但**修改需求必须同步更新总体方案的对应章节**，不得只改一处。

### 1.3 需求编号与优先级

编号格式 `REQ-<域>-<三位序号>`。域代码见各章标题。

优先级采用 RFC 2119 语义：

| 级别 | 含义 |
| --- | --- |
| **必须** | V1.0 不满足即为发布阻断项 |
| **应当** | 应当满足；不满足需给出理由并记入已知限制 |
| **可选** | 有余力则做，不影响发布 |

### 1.4 需求条目的字段

| 字段 | 说明 |
| --- | --- |
| 需求 | 一句话可判定的陈述 |
| 优先级 | 必须 / 应当 / 可选 |
| 验收 | 如何判定满足；可测、可复现 |
| 追溯 | 总体方案对应章节 |
| 备注 | 边界、例外、开放项 |

### 1.5 术语

| 术语 | 含义 |
| --- | --- |
| 工作区 | 用户私有数据边界；另有保留工作区 `public` |
| public | 保留工作区及数据所有者，向所有用户只读共享。**不是** SQL 的 PUBLIC 角色 |
| 记忆 | 中期（任务/会话）与长期（事实/偏好/经验）数据 |
| 资产 | 受管理的外部不可变文件（模型包、文档、图片等） |
| 拓扑 | 以属性图表达的实体关系，用于 Agent 的知识结构 |
| 水位 | 派生索引相对源数据的同步进度标记 |

## 2 产品定位与工作负载画像

### 2.1 定位：非典型 RDBMS

bicdb **不是**通用关系型数据库，不以替代现有 RDBMS 为目标。其服务对象是 AI Agent，核心用途为：

| 用途 | 说明 | 域 |
| --- | --- | --- |
| **知识** | 文档、片段、事实及其来源与派生关系 | 检索、图 |
| **记忆** | 中期任务状态与长期事实/偏好，含版本与生命周期 | 记忆 |
| **配置** | 版本化配置、提示模板、工具参数、模型配置 | JSON 与配置 |
| **拓扑** | 实体关系、依赖结构，支持有界遍历与关联查询 | 属性图 |
| **资产** | 不可变大对象（模型、文档、图片） | 资产 |

由此产生与典型 RDBMS 的显著差异：

| 维度 | 典型 RDBMS | bicdb |
| --- | --- | --- |
| 主要负载 | 混合，写占比高 | **读占绝对多数** |
| 写入并发 | 高，热点争用常见 | **有限并发，争用低** |
| 数据模型 | 关系为主 | **多模型**：关系 + JSON + 向量 + 图 + 外部资产 |
| 写入形态（存储层） | 原地更新 + Undo | **同为原地更新 + Undo**（与此项**无差异**） |
| 多版本表达 | 通常由应用自行设计 | **由数据模型层表达**（主节点 + 版本节点等），非存储层特性 |
| 事务形态 | 长短混合 | **短事务**，无长事务、无跨工作区事务 |
| 查询形态 | 复杂多表 JOIN | **点查 + 语义检索 + 范围扫描 + 有界图遍历** |
| 隔离模型 | 角色/授权体系 | **工作区硬隔离**，不支持跨用户授权 |
| 生命周期 | 用户自行管理 | **内建 TTL、撤销、派生依赖传播** |

> **⚠ 层次边界：多版本在哪一层**
>
> 这是本文最容易被误解的一点，必须明确：
>
> - **存储层只做原地更新 + Undo**，与典型 RDBMS 一致。**不采用 ASTORE 式堆内
>   多版本**，不以 LSM-Tree 作主存储组织，主堆中不保留每次更新的完整旧版本。
> - **"多版本"是数据模型层的表达**。记忆 revision、配置 revision 等，在实现上
>   是**额外的行/节点**——例如用图的**主节点 + 版本节点**，或 `memory` +
>   `memory_version` 两张表。对存储引擎而言，这些只是普通的插入与原地更新，
>   **不存在"版本追加"这种存储机制**。
> - 因此本数据库的写入形态在存储层**并不特殊**。认为"记忆是版本化的，所以底层
>   要版本化存储"是错误推导，会导致堆内版本膨胀、Undo 与回收语义混乱、恢复
>   协议复杂化。见 REQ-STO-004、REQ-STO-014。

### 2.2 工作负载画像

以下画像是全部性能与并发需求的推导依据。**若画像变化，须重新审视第 5.1 节。**

| 特征 | 描述 | 对设计的含义 |
| --- | --- | --- |
| 读:写比例 | 读占绝对多数 | 读路径是优化重点；写路径以正确性为先 |
| 写并发 | 有限（少量并发写事务，无高频热点行争用） | 保留多写者正确性，但**不必**为热点争用做复杂优化 |
| 读并发 | 高（大量 Agent 并发检索） | 读必须无锁、可并发、可缓存 |
| 事务时长 | 短，无长事务 | 快照注册与 Undo 回收压力可控 |
| 单次写入量 | 小。一次业务更新通常为少量行（如"插入一个版本节点 + 更新主节点指针"）；偶有大向量/JSON | 跨页协议必须支持，但非主路径 |
| 写放大 | 由数据模型决定（版本节点模式使单次业务更新为 2 次行操作），**不是存储层特性** | 存储层不为此做特殊优化；见 REQ-STO-014 |
| 数据规模 | 单工作区中等规模 | 索引可常驻内存的比例高 |
| 读延迟 | 敏感（Agent 交互链路） | p99 读延迟是核心指标 |
| 写延迟 | 不敏感 | 以耐久性优先（如必须等 WAL 落盘） |

### 2.3 由此确定的取向

以下四条是本画像对需求的直接约束，贯穿全文：

1. **读路径无锁化**：读不获取行锁、不阻塞写、不依赖写路径进展。见 REQ-TXN-005。
2. **写路径正确性不降级**：并发低不等于可以放松持久化、隔离与恢复要求。见第 4.4 节全部"必须"项。
3. **不为不存在的负载付费**：不实现针对高争用热点的复杂机制。见 REQ-TXN-009。
4. **版本化留在数据模型层**：存储层只做原地更新 + Undo，多版本由额外的行/节点表达。见 REQ-STO-014、REQ-STO-015。

| 主体 | 本人私有区 | 他人私有区 | public 区 |

## 4 功能需求

### 4.1 用户隔离与工作区（ISO）

| 编号 | 需求 | 优先级 | 验收 | 追溯 |
| --- | --- | --- | --- | --- |
| REQ-ISO-001 | 每个用户具有独立工作区，私有数据、索引、日志、临时文件与资产不得与其他工作区混放 | 必须 | 两个用户 + public 各自独立根目录；测试工作者无法打开他人目录 | §3、§4 |
| REQ-ISO-002 | 用户标识必须来自认证结果，不得以请求体中的 user_id 作为可信身份 | 必须 | 伪造 user_id 的请求被拒绝或路由到本人工作区 | §3 |
| REQ-ISO-003 | 不得提供任何跨用户授权、所有权转移、代理读取或共享链接能力 | 必须 | 接口清单中不存在此类能力；尝试调用被拒绝 | §3 |
| REQ-ISO-004 | 只有 public 工作区向所有用户只读共享；public 是保留工作区与数据所有者，不是 PUBLIC 角色 | 必须 | 普通用户对 public 的写入被拒绝；读成功 | §3 |
| REQ-ISO-005 | owner 不可变；不提供跨工作区外键、可写联结或级联关系 | 必须 | 相关 DDL 被拒绝 | §3、§13 |
| REQ-ISO-006 | 普通用户不能判断另一用户的对象是否存在；拒绝响应不得泄露名称、内容或精确规模 | 必须 | 对象 ID 猜测、同名表探测的响应与"不存在"不可区分 | §3 |
| REQ-ISO-007 | 文件操作必须检查路径穿越、符号链接与检查使用间竞态 | 必须 | 恶意路径与符号链接用例全部拒绝 | §4 |
| REQ-ISO-008 | 工作区根目录使用服务端生成的不透明 ID，不得直接拼接用户输入 | 必须 | 目录名不可由用户输入推导 | §4 |
| REQ-ISO-009 | 备份恢复必须校验 WorkspaceId 与格式版本，不得把用户 A 的备份导入用户 B 的工作区 | 必须 | 跨用户恢复被拒绝 | §4、§21 |
| REQ-ISO-010 | 隔离失败属于发布阻断项，不得以概率或平均成功率验收 | 必须 | 隔离用例通过率必须为 100% | §3 |
| REQ-ISO-011 | 私有工作区之间不使用硬链接、不共用资产目录、不做跨用户内容去重 | 必须 | 校验和相同的资产仍各自独立存储与计费 | §4 |
| REQ-ISO-012 | 克隆**不得作为跨用户数据转让通道**——只能在同一 owner 的范围内执行 | 必须 | 跨 owner 克隆被拒绝 | §3、§21 |

### 4.2 数据类型（TYP）

参考环境：Oracle 19c、AL32UTF8、`MAX_STRING_SIZE=STANDARD`，固定 NLS。

| 编号 | 需求 | 优先级 | 验收 | 追溯 |
| --- | --- | --- | --- | --- |
| REQ-TYP-001 | 提供 CHAR、VARCHAR2、NUMBER、INTEGER、DATE、TIMESTAMP 六类标量，行为与 Oracle 参考环境兼容 | 必须 | 每类至少 100 条确定用例与 Oracle 差分一致 | §5 |
| REQ-TYP-002 | NUMBER 不得以 double 承载；裸 NUMBER 不得归一为 NUMBER(38,0) | 必须 | 超出双精度精度的十进制逐值精确比对通过 | §5 |
| REQ-TYP-003 | INTEGER 语义为 NUMBER(38,0)，不得退化为 32/64 位机器整数 | 必须 | 38 位边界值读写往返一致 | §5 |
| REQ-TYP-004 | 类型兼容是声明、取值、赋值、转换、比较与客户端往返的**行为契约**，不要求内部字节编码相同 | 必须 | 比较、哈希、索引键、常量折叠、客户端编码结果一致 | §5 |
| REQ-TYP-005 | SQL 空字符串按 Oracle 字符规则处理；JSON 空字符串保持其文档语义 | 必须 | 两者分别验证，互不串用 | §5、§6 |
| REQ-TYP-006 | 提供扩展类型 BOOLEAN、UUID、FLOAT32、FLOAT64、TIMESTAMP_TZ、JSON、VECTOR、ASSET_REF | 必须 | 各自独立规范与参考模型；不宣称全量 Oracle 兼容 | §5 |
| REQ-TYP-007 | 时间事件统一保存 UTC 时刻，需要时保留原始时区；DATE/TIMESTAMP 仍按无时区处理 | 必须 | 跨时区往返与夏令时用例通过 | §5 |
| REQ-TYP-008 | 合计不少于 1 万条生成用例，记录版本、NLS、SQL、绑定与结果 | 应当 | 用例集可复现 | §5 |
| REQ-TYP-009 | 完整 PL/SQL、DDL 隐式提交不由类型兼容要求推导 | 必须 | 不在 V1.0 范围内（见第 6 章） | §5 |

### 4.3 存储与页式结构（STO）

| 编号 | 需求 | 优先级 | 验收 | 追溯 |
| --- | --- | --- | --- | --- |
| REQ-STO-001 | 以工作区内表空间、段、区、**16KB** 块与槽位堆表组织数据 | 必须 | 页格式规格与检查器一致 | §7 |
| REQ-STO-002 | 数据页包含格式版本、页类型、WorkspaceId（或其受校验映射）、FileId、PageId、页代次、pageLSN、校验和、空闲区与槽位目录 | 必须 | `page_dump` 可读出全部字段；`db_check` 校验通过 | §7 |
| REQ-STO-003 | ROWID 稳定表示记录身份。删除在行头打删除标记，**索引项随事务维护**；提交后槽位即可复用。ROWID **不含代次**——由"索引项不晚于其行消失"这一机制保证不出现陈旧引用 | 必须 | ①行迁移后经稳定入口可定位到当前片段；②删除提交后复用槽位，不存在指向旧行的存活索引项；③删除回滚后索引项与行一并恢复 | §7 |
| REQ-STO-004 | 常规更新优先修改当前行，历史信息进入 Undo；不得采用 ASTORE 式堆内多版本，不得以 LSM-Tree 作为主存储组织 | 必须 | 堆表不保留完整旧版本；无 MemTable/SSTable/Compaction 主路径 | §7 |
| REQ-STO-005 | 行增长与跨页值必须通过行片段、稳定入口与可恢复链接支持；超出**单页容量（16KB）**的 JSON 与高维向量必须纳入跨页协议 | 必须 | 超页 JSON 与向量存取原型验证通过 | §7 |
| REQ-STO-006 | BufferPool 提供 pin、latch、脏页与 pageLSN 管理；PageGuard 控制引用生命期，**不得向 SQL 层返回裸页面指针** | 必须 | 接口层无裸指针暴露 | §7 |
| REQ-STO-007 | 持 latch 期间不得等待事务、不得执行文件 I/O、不得阻塞网络 | 必须 | 代码审查 + 运行时断言 | §7、§15 |
| REQ-STO-008 | 提供 B+Tree 索引，支持唯一键、复合键与范围访问 | 必须 | 至少 100 万键的建、查、删、分裂、键更新测试通过 | §7 |
| REQ-STO-009 | 索引候选回表时必须检查可见性。**索引项随删除/键更新事务一并维护**（删除即移除、回滚即恢复），延迟回收的是**堆空间与 Undo**（受最老快照约束），**不是索引项** | 必须 | 崩溃后索引与可见堆表对照一致；删除回滚后索引项恢复 | §7 |
| REQ-STO-016 | **已知行为**：RC 下，语句开始后、索引读取前被并发删除的行，索引扫描**可能漏读**（索引项已移除，堆中的 Undo 无机会被使用）。此为 Oracle 同类模型的既有取舍，**不是缺陷**，须在接口文档与测试基线中显式记录 | 必须 | 该行为在文档中标注为已知语义；测试用例断言的是"允许漏读"而非"必须可见" | §7、§8 |
| REQ-STO-010 | 页分裂使用单独审查的系统操作与恢复协议，不得把分裂错误当作业务事务失败简单忽略 | 必须 | 分裂中断后恢复结果可判定 | §7 |
| REQ-STO-011 | 空闲页分配、初始化、位图与控制元数据均受 WAL 保护 | 必须 | 逐点故障注入后结构一致 | §7 |
| REQ-STO-012 | 页面编码、检查器与损坏处理必须先于完整 SQL 执行器交付 | 必须 | `page_dump`/`db_check` 在 P2 可用 | §7、§17 |
| REQ-STO-013 | 资产文件是独立对象，不得混入堆表页链 | 必须 | 资产与页存储路径分离 | §7、§9 |
| REQ-STO-014 | **存储层不得实现版本化存储**。多版本（记忆 revision、配置 revision 等）必须由数据模型层表达为额外的行/节点（如主节点 + 版本节点、`memory` + `memory_version`）。存储层对它们的处理就是普通的插入与原地更新 | 必须 | 堆表中不存在"版本链"结构；存储接口无版本参数；代码审查确认 | §7、§10 |
| REQ-STO-015 | 任何"因业务需要多版本"而要求存储层保留旧版本的提案，必须先经 ADR 评审 | 必须 | ADR 记录 | §7、REQ-MNT-004 |

### 4.4 事务、并发与恢复（TXN）

**写并发模型：多写者、低争用。** 保留多写者正确性，不针对高争用热点做复杂优化。

| 编号 | 需求 | 优先级 | 验收 | 追溯 |
| --- | --- | --- | --- | --- |
| REQ-TXN-001 | 首版隔离级别为 Read Committed 语句快照 | 必须 | 至少 1 万组随机历史符合 RC 模型 | §8、§18 |
| REQ-TXN-002 | 支持多写事务与行锁 | 必须 | 2、8、32 客户端读写交错测试通过 | §8、§18 |
| REQ-TXN-003 | 支持语句失败回滚、事务回滚与死锁检测 | 必须 | 死锁被检测并解除，不出现永久挂起 | §8 |
| REQ-TXN-004 | Snapshot 使用提交序号，WAL 使用 LSN；**两者不得混用** | 必须 | 类型层面区分，代码审查确认 | §8 |
| REQ-TXN-005 | **读路径不得获取行锁、不得阻塞写、不得依赖写路径进展** | 必须 | 长读与并发写同时进行时双方均不阻塞 | §8、§11 |
| REQ-TXN-006 | Undo 必须同时保存回滚所需信息与旧快照重建信息 | 必须 | 回滚正确性 + 一致性读正确性分别验证 | §8 |
| REQ-TXN-007 | 修改顺序：先写 Undo 与日志描述，再修改受保护数据页 | 必须 | 逐点故障注入后不出现逻辑损坏 | §8 |
| REQ-TXN-008 | 数据页持久化前，对应 WAL 必须已持久化 | 必须 | 崩溃注入后无"数据已落盘但日志缺失" | §8 |

## 6 V1.0 明确不做的范围

以下**不属于** V1.0，需求文档不为其编写条目。若需纳入，须走需求变更。

| 不做项 | 说明 |
| --- | --- |
| 完整 Oracle SQL 兼容、PL/SQL | 仅六类标量的行为兼容 |
| RAC、分布式事务、跨工作区写事务 | 单机；跨区无原子保证 |
| 库内模型执行 / LLM 调用 | 记忆提炼与推理由上层 Agent 承担 |
| 复杂 LSM 主存储 | 明确不采用 |
| ASTORE 式堆内多版本、存储层版本化 | 明确不采用；多版本由数据模型层表达（REQ-STO-014） |
| 库内 LOB（BLOB/CLOB） | 资产走外部文件协议 |
| **分支合并**（把克隆/分支的改动并回主线） | 克隆与分支**支持**，但不提供合并——需比对两个工作区的数据与日志并定义冲突语义，与"存储层不做版本化"的边界冲突 |
| 备库部署（高可用） | 受 REDO 保护的数据在**能力上已可复制**（归档提供连续日志链），但备库进程、日志传输与切换协议为独立工程，不在 V1.0 |
| 复杂查询重写、窗口函数、JIT、单查询并行 | 延后 |
| 无限变长路径、完整 Cypher、图算法 | 仅有限子集与有界遍历 |
| 量化向量、磁盘型 ANN | 容量需求明确后另立项 |
| 跨用户授权、所有权转移、共享链接 | 永久不做（产品约束，非版本约束） |
| 为高争用热点做的复杂并发优化 | 由工作负载画像决定（REQ-TXN-009） |
