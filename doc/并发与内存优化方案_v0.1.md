# 并发与内存优化方案 v0.1

**日期**：2026-10-05　**依据**：两份外部参照材料（`doc/refs/`）+ 两个可复跑基准台
+ 两份证据包（`latch-ab-20261005` / `oracle-pg-txn-lock-20261005`）

**方法（贯穿全案）**：**先测量、后优化、再复测**——每一项都给出"现状实测、
目标、改动点、验收方法、风险"；两个基准台是共同验收工具：

```text
合成闩锁台（锁形态）  cargo test -p bicdb-common  --release --test lock_contention   -- --ignored --nocapture
真实路径台（池路径）  cargo test -p bicdb-storage --release --test pool_contention   -- --ignored --nocapture
批 DML 台（P1 验收）  cargo test -p bicdb-txn    --release --test dml_batch         -- --ignored --nocapture
前台 pwrite 探针      cargo test -p bicdb-txn    --release probe_frontend_pwrites_per_record -- --ignored --nocapture
```

> **机器注意**：现有基线全部采自 **128 核 Neoverse-N1 单 socket**（arm64）。
> 换机（x86_64 / 少核 / 多 socket）**方向应一致、交叉点位置会移动**——重跑两台即可。

## P0　闩锁与统计的快路径（**部分已落地**）

**现状实测**：见上表前四行。**目标**：把"每次操作的共享写"从 6–8 个降下来，
真路径 2–16 线程吞吐提升 ≥30%（我们常见画像）。

**已落地（2026-10-05，提交见日志）**：

1. **计数器分片**（`Latch`）：线程按**栈地址**（零成本、零 unsafe）落到 8 片、
   片间 cache line 对齐；写只碰本片行，读**逐片求和——仍然精确**（不是采样）。
   `gets ≡ immediate + spin_gets + sleeps` 由此派生，快路径从 2 个共享 RMW
   降为 1 个私有 RMW。
2. **`wait_ns` 采样估计**：睡眠路径原先每次争用要两次 `Instant::now()`
   （aarch64 各 ~20–30ns）+ 一次 RMW；改为每 64 次睡眠实测一次 ×64 折算。
3. **`DEFAULT_SPIN 40 → 8`**（实测最优点：低争用拿住 86% 收益、高争用不掉崖）。

**实测效果（真路径台）**：2 线程 307 → **492**（+60%）；4 线程 254 → 285；
8 线程 188 → 201；16 线程 166 → 174。合成台在噪声内（±10–15%）。
**回归**：419 用例全绿。

**余量（P0 续作，按实测触发）**：

- `BufferStats.hits` 等**每操作一次**的字段：它们在结构闩锁内（无原子成本），
  但每次 `pin` 会连带把统计行拉进本核——**与 O3 同源**，见 P3 的取舍；
- `Latch` 与同形包装仍有 ~35% 差距（合成台）：下一步定位需要 profiler
  （`perf stat -e l1d_cache_refill,...`），**没有数据不动手**；
- `LogBuffer`/`WalShared` 用同一 `Latch` 类型 ⇒ 分片收益自动继承。

## P1　undo 页"写后立即 flush"的前台 pwrite（**已落地，2026-10-05**）

**现状（改动前实测）**：每个撤销记录后 `write_undo_page_change` 立即
`pool.flush(key)`——**实测前台 pwrite 数：稳态 2 次/条 DML（撤销记录页 + 段头页），
首条（开新页）5 次/条**。Oracle（只写 redo + 延迟清除）与 PG（clog 是缓存）在这里
都是**零前台写**。

**根因**：CR/回滚**直读段文件**（`UndoChain::read` 走 `DataFile`，不经池）⇒ 必须让
"池里写"与"文件里读"没有窗口（§12.3.1 的纪律）。

**落地形态（与勘察结论一致，但发现的直接读者比预估多）**：给 `UndoChain` 加
**读取源**（`Direct`（恢复/诊断）/ `Pool`（活系统，`with_pool`）），链内**所有**读
走它 ⇒ 撤销页转 **no-force** ⇒ 删掉三类 flush。**实际改动的读路径清单**
（每一处都是"读后决定写"，直读会静默用旧像）：

| # | 直读点 | 症状（实测） |
| --- | --- | --- |
| 1 | 链的记录/段头读（`read`/`page(0)`） | 主目标；`plan_append` 判槽活动 |
| 2 | **`Segment::append_position`**（直读段头页的 `append_pos`） | 追加位永远"没推进"⇒ **重复使用同一逻辑页，覆盖活跃事务的撤销记录** |
| 3 | **`find_recyclable_page`**（`read_page_raw` 扫归属页） | 文件里的零页被误判"未写过"⇒ 重置掉活跃快照仍需要的页（CR `TooManyRounds`） |
| 4 | **计划器基准**（`plan_extend`/`plan_allocate_extent`/`plan_materialize_bitmap_page` 的读-改-写） | 用文件像做基准 ⇒ 把池里已改的字节（**段头页上的事务表**）写回旧值（`SlotNotActive`） |
| 5 | **⓪"新页先落盘"的 `page_lsn` 预置**（`appended_lsn()`） | 预置值 = 本轮第一条记录的 LSN ⇒ `<=` 门把它自己跳掉；no-force 下盘上只有空页像 ⇒ 槽目录变更永久丢失（崩溃恢复 `MalformedRecord`） |
| 6 | 执行器侧事务表查看（`lookup`）、测试辅助读 | 同类，一并改经读取源 |

**防线（防回归）**：写路径各持池入口（`begin`/DML/`commit`/`rollback`/`lock_row`/
`reclaim`）**强制校验"链绑的就是手上这个池"**——`TxnError::UnboundUndoChain`；
池绑定链若走到"兜底直写扩展"也**报错**而不是静默直写。计划器改为**显式接收
当前像提供者**（`CurrentPages = &mut dyn FnMut(u32) -> Option<Page>`），签名上
就不可能"忘了取池像"。

**验收（全部达成）**：

1. **探针** `probe_frontend_pwrites_per_record`：稳态 **2/条 → 0/条**；
   首条 **5 → 1**（唯一保留：新撤销页"先格式化落盘"，§11.5.4——**1 次/页**）；
2. **崩溃恢复用例**首次真正走"撤销页从 redo 重建"：`crash_after_dml_*`、
   `crash_during_migration_*`、`recycled_undo_page_survives_crash_recovery` 全绿
   （撤销页不再被前台 flush，断电容错靠 WAL 规则 2 + 重放）；
3. **真实路径批 DML 曲线**（新增 `crates/txn/tests/dml_batch.rs`，`#[ignore]`）：
   `DML_N=2000` 单线程 **4 870 → 11 888 条/秒（2.44×）**，两轮复现
   （介质 MemFileIo——**次数差是硬结论，墙钟差是下界**，真实块设备上更高）；
4. 全量回归：**419 用例全绿**（debug）/ 418（release），clippy 零告警。

**代价/风险**：`UndoChain` 在读路径上多一次池查找（命中为主，池命中成本已被
P0 压过）；链读与数据页读共享同一写列表，DBWR 压力略增（同批刷出）。**语义
不变**：恢复路径仍用 `Direct`（无池）。

## P2　ITL 空间不足 / 事务表槽耗尽：报错 → 等待

**现状**：`NoSlotAvailable`（ITL 涨不动）与 `NoFreeSlot`（事务表满）是**报错**；
Oracle 对应 `enq: TX - allocate ITL entry` 与 `enq: US` 都是**等待**
（KB: Note:549074.1；证据包 `oracle-pg-txn-lock-20261005/` 动作③）。

**改动点**（随执行器/会话层）：把等待登记在**"该块全部活动事务 / 该段全部活动
事务"**上（`WaitRegistry`/`WaitGate` 天然支持一个等待者挂多个持锁者），任一结束
即唤醒重试；带超时与可取消（复用 `WaitPolicy`）。**在此之前**：执行器把两个错误
当**可重试资源类**（`CONV` §4.3）。
**验收**：同页 33+ 并发写事务的用例从"报错"变"等待后成功"（构造：块内 ITL 涨满 +
若干活动事务，逐个提交）。
**风险**：等待图的边从"行锁"扩到"块资源"——我们的 DFS 仍然成立（全为硬边，
无模式升级）；需在 §5.4.2 的"前提条件"注记里补这条边的来源。

## P3　O3 桶分片（**已落地，2026-10-05**）

**现状实测（改动前）**：真路径的负扩展主要来自"共享字数量"；桶分片只去掉
**结构闩锁**这一个共享点（统计、帧 `pins`、帧内容锁词仍在）。触发判据
（§2.7 口径）复测成立：4 线程起 `misses/gets≈0.65`、`sleeps/gets` 0.11→0.18。

**落地形态**（完整设计注记见 §5.10；`chains → 桶分片 → 帧元数据锁` 的次序）：

1. **桶分闩锁**（新 `db_bucket`，默认 ≈ 桶数/8、2 的幂）：命中路径 = 桶闩下
   "链上按**条目自带的键**匹配 + `pins++` + TCH 原子"，**完全不进结构闩锁**
   （键变更规则保证"持桶闩看到 `(K, idx)` ⇒ 该帧不可能正被换键"）；
2. **统计分片**（`BufferStats` → 8 片原子，线程按栈地址选片）+ **TCH 进帧槽**
   （原子、三秒规则频次限制）——命中路径的共享字只剩桶闩状态、桶链行与本帧两词；
3. **提升改为尽力**（`try_lock`，且先用 TCH 判据挡掉绝大多数尝试——实测：
   无此闸门时 2 线程每命中一次 CAS 结构闩，反被拖慢）；
4. **腾帧新增竞态关**：候选帧在**旧键的桶闩下复核 `pins==0`**（与命中路径的
   `pins++` 串行）；被钉住 ⇒ 放弃候选重选；发布前在**新键桶闩下查重**
   （绝无同键双帧），撞重则本帧退回未分配（净帧，安全）。

**实测（真实路径台 A 曲线：不同块 `pin`，万次/秒）**：

| 线程 | 1 | 2 | 4 | 8 | 16 | 32 |
| --- | --- | --- | --- | --- | --- | --- |
| 改前 | 828 | 474 | 275 | 188 | 184 | 170 |
| 改后 | **734** | **848** | **1129** | **1682** | **1704** | **1681** |

**32 线程 ≈ 10×，负扩展消除**；`db_cache` 的 `misses/gets` 0.65 → ≤0.18、
`sleeps/gets` ≤0.004。代价：单线程 −11%（多一次桶闩取放与分片统计间接层）。
`pin_shared` 与独占同档维持；全量 420 用例绿（含两条新回归：声明被钉候选必须
失败、4 线程 × 3000 次 churn 的**串页防线**）。
