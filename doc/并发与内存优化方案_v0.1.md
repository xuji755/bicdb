# 并发与内存优化方案 v0.1

**日期**：2026-10-05　**依据**：两份外部参照材料（`doc/refs/`）+ 两个可复跑基准台
+ 两份证据包（`latch-ab-20261005` / `oracle-pg-txn-lock-20261005`）

**方法（贯穿全案）**：**先测量、后优化、再复测**——每一项都给出"现状实测、
目标、改动点、验收方法、风险"；两个基准台是共同验收工具：

```text
合成闩锁台（锁形态）  cargo test -p bicdb-common  --release --test lock_contention   -- --ignored --nocapture
真实路径台（池路径）  cargo test -p bicdb-storage --release --test pool_contention   -- --ignored --nocapture
```

> **机器注意**：现有基线全部采自 **128 核 Neoverse-N1 单 socket**（arm64）。
> 换机（x86_64 / 少核 / 多 socket）**方向应一致、交叉点位置会移动**——重跑两台即可。

## P0　闩锁与统计的快路径（**部分已落地**）

**现状实测**：见上表前四行。**目标**：把"每次操作的共享写"从 6–8 个降下来，
真路径 2–16 线程吞吐提升 ≥30%（我们常见画像）。

**已落地（2026-10-05，提交见日志）**：

1. **计数器分片**（`Latch`）：线程按**栈地址**（零成本、零 unsafe）落到 8 片、
   片间 cache line 对齐；写只碰本片行，读**逐片求和——仍然精确**（不是采样）。
   `gets ≡ immediate + spin_gets + sleeps` 由此派生，快路径从 2 个共享 RMW
   降为 1 个私有 RMW。
2. **`wait_ns` 采样估计**：睡眠路径原先每次争用要两次 `Instant::now()`
   （aarch64 各 ~20–30ns）+ 一次 RMW；改为每 64 次睡眠实测一次 ×64 折算。
3. **`DEFAULT_SPIN 40 → 8`**（实测最优点：低争用拿住 86% 收益、高争用不掉崖）。

**实测效果（真路径台）**：2 线程 307 → **492**（+60%）；4 线程 254 → 285；
8 线程 188 → 201；16 线程 166 → 174。合成台在噪声内（±10–15%）。
**回归**：419 用例全绿。

**余量（P0 续作，按实测触发）**：

- `BufferStats.hits` 等**每操作一次**的字段：它们在结构闩锁内（无原子成本），
  但每次 `pin` 会连带把统计行拉进本核——**与 O3 同源**，见 P3 的取舍；
- `Latch` 与同形包装仍有 ~35% 差距（合成台）：下一步定位需要 profiler
  （`perf stat -e l1d_cache_refill,...`），**没有数据不动手**；
- `LogBuffer`/`WalShared` 用同一 `Latch` 类型 ⇒ 分片收益自动继承。

## P1　undo 页"写后立即 flush"的前台 pwrite

**现状**：每条撤销记录后 `pool.flush(key)` ⇒ **每条 DML 一次 16 KB 前台 pwrite**
（无 fsync，但 syscall 与写流量与修改次数同阶）。Oracle（只写 redo + 延迟清除）
与 PG（clog 是缓存）在这里都是**零前台写**。

**根因**：CR/回滚**直读段文件**（`UndoChain::read` 走 `DataFile`，不经池）
⇒ 必须让"池里写"与"文件里读"没有窗口（§12.3.1 的纪律）。

**改动点**：给 `UndoChain` 加"经池读页"的口（或让 `cr::reconstruct`/回滚链回放
接收一个链读取器）⇒ 撤销页转 **no-force**（与数据页同规）⇒ 删除 `flush`。
**验收**：① 小事务（1 行）提交路径的 pwrite 数从 2 → 0（WAL 除外）；
② 跨页/跨链的 CR 用例与崩溃恢复用例全绿（撤销页由 WAL 规则 2 保护）；
③ 真实路径台加一条"批 DML"曲线对照。
**风险**：链读取改经池后，"快照起点权威性"依赖池的 `page_lsn` 门控——
恢复/CR 的既有用例是主要防线；先做小切片（只改读路径，保留 flush）再删 flush。

## P2　ITL 空间不足 / 事务表槽耗尽：报错 → 等待

**现状**：`NoSlotAvailable`（ITL 涨不动）与 `NoFreeSlot`（事务表满）是**报错**；
Oracle 对应 `enq: TX - allocate ITL entry` 与 `enq: US` 都是**等待**
（KB: Note:549074.1；证据包 `oracle-pg-txn-lock-20261005/` 动作③）。

**改动点**（随执行器/会话层）：把等待登记在**"该块全部活动事务 / 该段全部活动
事务"**上（`WaitRegistry`/`WaitGate` 天然支持一个等待者挂多个持锁者），任一结束
即唤醒重试；带超时与可取消（复用 `WaitPolicy`）。**在此之前**：执行器把两个错误
当**可重试资源类**（`CONV` §4.3）。
**验收**：同页 33+ 并发写事务的用例从"报错"变"等待后成功"（构造：块内 ITL 涨满 +
若干活动事务，逐个提交）。
**风险**：等待图的边从"行锁"扩到"块资源"——我们的 DFS 仍然成立（全为硬边，
无模式升级）；需在 §5.4.2 的"前提条件"注记里补这条边的来源。

## P3　O3 桶分片（**降级为部分解，排在 P0 之后**）

**现状实测**：真路径的负扩展主要来自"共享字数量"，而桶分片只去掉**结构闩锁**
这一个共享点（统计、帧 `pins`、帧内容锁词仍在）；4 分区对**同一工作区**的
线程并行无帮助（按工作区哈希）——这两条都已被基准证实。

**改动点**（届时）：`chains → 桶分片 → 帧元数据锁` 的固定次序（§5.10 已记），
帧元数据从结构闩锁移入每帧自带的锁（PG `BufferDesc` 形态）。
**触发**：P0 复测后，若 `db_cache` 的 `misses/gets` 高 ∧ `sleeps/gets` 也高
（判读口径照参照材料 §2.7）。
**风险**：多把锁的次序与"持结构闩不等待内容锁"的纪律需重证；先出设计注记再动码。
