配套文档：小型多线程数据库总体开发方案 v0.2
文档版本：0.2　编制日期：2026年10月3日　状态：知识库使用基线（待P0评审确认）

**v0.2 修订说明**：对 v0.1 的全部命令做了批量实跑验证（54 条），补充第 1.4 节验证结论与第 4.12 节用法修正和能力缺口，附录 A 全部改为实测状态并标注正确用法，实测原始记录留档 `doc/evidence/kbcheck-20261003/`。v0.1 中标注 `[待验]` 的命令至此全部核验完毕。

## 2 能力边界：能回答什么、不能回答什么

### 2.1 强项（可放心引用，仍需记录核验日期）

| 能力 | 实测证据 |
| --- | --- |
| 数据库**机制/原理**解释 | 一致性读与 UNDO 前映像、CR 克隆、MVCC 可见性规则（xmin/xmax/CLOG） |
| **源码级实现**细节 | pgvector HNSW 结构、Lehman-Yao B-Tree 并发协议、InnoDB 页结构文件定位 |
| **故障模型与案例** | FaultModel + CaseStudy + 诊断链（`diagnose`/`diagnostic`） |
| **官方文档全文** | `doc_retrieve` 返回正文，并给出源文件路径（如 `case_studies/cs_digoal_*.md`） |
| **PL/SQL 对象与包** | `plsql_kg` 返回结构化定义、重载、参数、异常、证据 ID |
| 系统对象/参数/等待事件 | `entity view/table/column/function/param/wait`，带 `--version`/`--scope` |

### 2.2 弱项与陷阱（必须在方案中约束）

| 弱项 | 实测表现 | 应对 |
| --- | --- | --- |
| **条目质量不均，存在占位内容** | `entity knowledge 'HNSW'` 返回"该条目为占位内容，具体细节需参考相关文档" | 关键结论必须二次下钻到具体条目或原始文档，禁止单条占位条目作为依据 |
| **召回有界，非穷尽** | 工具自述"候选覆盖有界：按召回或显示预算选取，未宣称全库穷尽" | 证据包注明"已检索范围"，不表述为"已穷尽全部资料" |
| **措辞敏感** | 同一主题：`'B-Tree 页分裂 Lehman Yao 并发 索引'` 命中 Lehman-Yao 协议（强）；`'行迁移 行链接 跨页行 大行存储'` 首位命中无关 MOS Note（弱） | 使用多关键词 `batch`、中英词变体、换词重试；结果不理想时改写而非放弃 |
| **聚合条目不等于正文** | `detail` 汇总条目只返回摘要与目录，正文在单篇条目/`DocText` | 用 `doc_retrieve` 取正文；用 `detail` 逐篇下钻 |
| **知识库是 DBA 视角为主** | 面向运维诊断与原理，非面向"如何实现一个数据库" | 源码类需求优先走"源码学习"系列，其余靠设计文档与官方资料 |
| **版本/范围语义按库甚至按实体类型不同** | 实测：OB **系统对象**的 scope 是租户类型（`ORACLE`/`MYSQL`），但 OB **OpSQL** 的 scope 是 `SYS`/`MYSQL`；Oracle 是容器语义、GaussDB 是架构；MySQL 兼容解析 `--scope` 但不据此筛选。传错不报参数错误，而是"未找到"——易误判为无数据 | 查询前确认该库**该实体类型**的 scope 取值（见附录 A 注②）；不确定时不传先试；不把版本集合与范围集合的笛卡尔积当作已验证组合 |
| **字段清单是跨版本并集** | 实测：`entity view` 输出自带声明"合并字段总数（跨版本/范围并集，**不代表单个版本列数**）" | 引用字段时必须落到单一"版本/范围组合"分节，不引用并集数字 |

### 2.3 定位声明

知识库是**证据来源之一**，不是决策者。本项目自主决策必须显式标记（总体开发方案第 22 节）。知识库内容与官方文档、目标版本源码、本项目 ADR 冲突时，以官方文档与源码为准，并在证据包中记录冲突。

## 3 访问方式与运行约定

### 3.1 环境准备

```bash
source /u01/deepseek/scripts/env.sh
cd /u01/deepseek/scripts
python3 health_check.py --daemon        # 每会话首次调用前确认可用
```

### 3.2 工具选型速查

| 需求 | 入口 |
| --- | --- |
| 综合知识/故障/源码检索 | `kb_graph.py <db> problem\|analyze\|batch\|entity\|detail` |
| 官方文档、MOS、案例正文 | `doc_retrieve.py '<关键词>' --db <db>` |
| 知识关联证据链 | `kg_deep_diagnose.py <db> '<关键词>'` |
| 日志/错误码规范化后再检索 | `kg_log_search.py --db <db> --stdin` |
| SQL 优化方案 / 改写规则 | `search_kg.py` / `search_sqlgen.py` |
| PL/SQL 语法、包、API | `plsql_kg.py <db> search\|detail\|context\|entity` |
| PL/SQL 静态检查 | `plsql_full_check.py <db> --stdin` |
| 系统对象 JOIN 关系 | `view_join_search.py '<视图名>' --db <db> --trusted-only` |
| 指标 / 等待事件 | `metric_lookup.py` / `wait_event_info.py` |
| 已发布运维 SQL | `kb_graph.py <db> entity opsql\|opsqllist` |

本项目主力为 **`kb_graph.py`**（探索）与 **`doc_retrieve.py`**（取正文），辅以 **`plsql_kg.py`**（P5 及类型/PL 兼容）。

### 3.3 检索纪律（写入任务卡与评审检查项）

1. **先窄后宽**：先用精确术语（`problem`/`entity knowledge`），不理想再用 `batch` 多关键词扩展。
2. **中英词变体**：同一概念分别用中文术语与英文术语检索（如"一致性读"与"consistent read"）。
3. **二次下钻必做**：对进入证据包的结论，必须用 `detail <elementId>` 或 `doc_retrieve` 打开原始条目/正文。
4. **显式版本与范围**：涉及系统对象、参数、SQL 兼容时，必须带 `--version`、`--scope`；不使用不存在的版本。
5. **按需检索，不重复全库**：已冻结证据不重复检索；同一问题一次证据包，避免每次小改动重跑。
6. **识别分库边界**：`oracle`(2101)、`mysql`(2102)、`postgresql`(2104)、`oceanbase`(2203) 为独立知识域，不因语法相似互相替代（同 GaussDB/openGauss、GBase 8a/8c 的隔离原则）。
7. **失败即记录**：检索无结果或仅命中占位内容时，在证据包标记"未核验"，不推断、不补写。

### 3.4 资源与缓存

- 检索走常驻 daemon，查询结果有服务端缓存；图谱更新后需清理缓存（`health_check.py --clear-cache`，属变更运行时状态，由维护者执行）。
- 批量检索优先用 `kb_graph.py <db> batch ...`（Rust 后台可按配置并发并按输入顺序合并），减少往返。
- 单次会话内的探索性检索不写入证据包；只有经核验的结论进入。

### 4.12 实测发现的用法修正与能力缺口

2026-10-03 对本计划全部命令做了批量实跑（54 条：51 条返回有效内容，3 条非零退出——其中 1 条为有意设计的负例，2 条为下列用法错误）。以下修正已具备强制力，使用前必须遵守。

**用法修正（原写法会失败）**

| # | 错误写法 | 正确写法 | 现象 |
| --- | --- | --- | --- |
| 1 | `plsql_full_check.py --db oracle --sql '...'` | `plsql_full_check.py oracle --sql '...'`（数据库为**位置参数**） | 返回 `{"status":"input_error","message":"first argument must be database"}` |
| 2 | `kb_graph.py ob entity view 'GV$OB_MEMORY' --scope SYS` | `--scope ORACLE`（OB **系统对象**的 scope 是**租户类型** ORACLE/MYSQL；但 **OpSQL** 的 scope 是 **SYS**/MYSQL，取值随实体类型不同，详见下方） | "未找到同时符合版本和范围条件的对象；未放宽筛选条件" |
| 3 | `kb_graph.py ob entity view 'GV$OB_MEMORY'`（裸名） | `'SYS.GV$OB_MEMORY'`（**schema 限定**） | "匹配多个对象，请用 schema.name 限定" |
| 4 | `kb_graph.py <db> entity knowledge '<主题>' --limit N` | 去掉 `--limit`（该子命令不支持） | "当前命令不支持参数：--limit" |

**能力缺口（不要写入计划依赖）**

| 能力 | 状态 | 影响 |
| --- | --- | --- |
| `equivalent` 跨库等价视图 | **不可用**：`EQUIVALENT_TO` 边尚未构建 | 本项目不需要跨库等价映射，仅记录 |
| `discover` 共现发现 | 默认参数下无输出 | 属知识维护类能力，不进研发流程 |
| `impact` | 需实体可解析才能返回关联；`impact view GV$SESSION` 返回 0 条 | 用 `fault`/`diagnose` 替代 |
| `diagnostic` | 需**精确故障别名**，"归档日志空间满"未定位 | 先用 `fault '<关键词>'` 找别名再展开 |

**工具自带的版本/范围警告（印证第 2.2 节）**

`entity view` 输出明确声明："合并字段总数（跨版本/范围并集，**不代表单个版本列数**）"。因此引用字段清单时必须落到单一"版本/范围组合"分节，不能引用并集数字。

### 6.2 触发规则：何时查、何时不查

**必须查知识库**：
- 引入本项目尚无先例的机制或协议（新索引结构、新恢复路径、新并发协议）。
- 涉及 Oracle 兼容语义的边界（类型、比较、转换、空值）。
- 设计中出现"两种做法取舍"且需要外部经验证据时。

**不必查**：
- 已在证据包中冻结的结论（不重复检索）。
- 纯本项目内部约定（工作区隔离契约、目录结构、错误码定义）。
- 已有明确官方文档可直接引用的场合（直接引官方文档更权威）。

**禁止**：
- 依据单条占位/摘要条目改变已冻结的工作区、类型或提交语义。
- 把知识库的运维诊断结论直接当作本项目恢复协议的设计依据。
- 在未记录版本与范围的情况下引用系统对象结论。

### 6.3 闭环流程

```
任务卡 → 检索（本计划第4节对应阶段条目）
      → 证据包（第5节模板）
      → 冲突时开 ADR
      → 实现（冻结接口与不变量内）
      → 门禁与人工审查
      → 故障/修复回流（第7.4节）
```

### 6.4 降级预案

检索服务不可用时（daemon 不可达、许可证失效、图谱维护中）：
- 可继续实现已冻结证据覆盖的独立任务，但**必须标记未核验项**。
- 新机制类任务暂停，不得以记忆或推测代替证据。
- 恢复后优先补做被跳过阶段的证据包。

## 7 质量控制与风险

### 7.1 主要风险

| 风险 | 表现 | 控制措施 |
| --- | --- | --- |
| 占位条目被误当证据 | 单条占位内容进入设计 | 二次下钻必做；占位内容显式列入"未命中" |
| 召回不穷尽被表述为"已全部核实" | 证据包过度声明 | 强制"检索范围声明"字段 |
| 措辞敏感导致漏检 | 换词即可命中（实测） | 多关键词 `batch` + 中英变体 + 改写重试 |
| 版本/范围误用 | 把存在版本当作已验证版本 | 显式 `--version`/`--scope`；不虚构版本 |
| 知识库结论覆盖本项目决策 | AI 依知识库改动隔离/提交语义 | 第 6.2 节禁止事项；冲突开 ADR |
| 引用过期 | 核验日期缺失 | 证据包强制核验日期；超期重核 |

### 7.2 与官方文档、源码的关系

优先级：**目标版本源码 > 官方文档 > 知识库条目 > 本项目推测**。

知识库的价值在于**快速定位**（哪个文件、哪个函数、哪个机制）与**故障经验**，最终实现细节以冻结源码提交为准。

### 7.3 安全与合规

- 知识库为只读检索，不写入图谱；导入/维护类工具不在本项目日常使用范围。
- 不检索、不引用、不落盘任何凭据类内容；项目密钥不进入源码、文档与日志（总体开发方案第 22 节）。
- 引用第三方内容时记录来源，第三方代码实际复用前审查许可证与线程环境依赖。

### 7.4 故障修复回流

修复完成后，按总体开发方案第 22 节要求整理触发历史、根因、不变量、修复与回归，**人工确认后**写回知识库（经维护通道，不在本项目内直连写入）。

**注①（schema 限定）**：视图查询必须用 `schema.name` 形式，裸名会报"匹配多个对象"。但**查询参数不要加引号以外的转义**：`'SYS.GV$OB_MEMORY'` 需单引号防止 shell 展开 `$`。
**注②（scope 语义随库与实体类型变化）**：`--scope` 传错**不报参数错误**，而是返回"未找到同时符合版本和范围条件的对象"，**极易被误读成"知识库没有这个数据"**。实测取值规则：

| 数据库 / 实体类型 | scope 取值 | 实测 |
| --- | --- | --- |
| Oracle（容器语义） | `PDB` / `CDB_ROOT` / `NON_CDB` | `entity view 'DBA_TABLESPACES' --version 19c --scope PDB` ✓ |
| OceanBase **系统对象**（view/table/column/function/param） | 租户类型 `ORACLE` / `MYSQL` | `entity view 'SYS.GV$OB_MEMORY' --scope ORACLE` ✓；`--scope SYS` ✗ |
| OceanBase **OpSQL**（opsql/opsqllist） | 目录范围标签 `SYS` / `MYSQL` | `entity opsql '合并阻塞' --scope SYS` ✓；`--scope ORACLE` ✗ |
| MySQL | 兼容解析但不据此筛选 | — |

不确定时不传 `--scope` 先试一次（OpSQL 不传可正常返回），或先跑 `opsqllist` 看该条目的实际范围列。
**注③（负例）**：`entity <未知类型>` 会正确报错"未知实体类型：want；不限类型请使用 entity all"，可用于校验参数拼写。



数据库代码：`oracle`=2101、`mysql`=2102、`postgresql`=2104（别名 pg）、`oceanbase`=2203（别名 ob）、`linux`=1111。完整注册表见客户端 `config/db_type_config.json`。

## 附录 C 术语与引用约定

- **知识库条目 ID**：形如 `4:8ed6c541-fe08-4ade-ae68-a79bf45316f4:548233`，供 `detail` 复现。
- **版本**：知识库中的"存在版本"不等于"已验证版本"；支持范围与实际执行回执分别理解。
- **范围**：Oracle 容器（CDB/PDB）、OceanBase 租户（SYS/MYSQL）、GaussDB 架构含义不同，不可混用。
