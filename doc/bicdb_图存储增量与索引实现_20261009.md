# bicdb 图存储增量与索引实现

2026-10-09。延续“完成 bicdb 的图数据库存储、检索、索引增强”目标。
本轮不连接 Neo4j，不修改其数据、索引或配置。全部验证使用本地独立测试库和合成数据。

## 已实现的存储变化

首版图使用一个 JSON 快照，每次写入删除、重插全部分片。现在升级为
`bicdb-graph-records-v2`，仍使用受保护的 GRAPH 对象和原生事务 heap / undo / WAL，
但每个顶点、每条边独立存储：

| 记录 | ordinal 编码 | data |
| --- | --- | --- |
| 图清单 | 0 | 格式、节点数、边数、分配器高水位 |
| 顶点校验 | `(1 << 60) \| (id << 10)` | 本顶点 JSON 的 SHA-256 |
| 边校验 | `(2 << 60) \| (id << 10)` | 本边 JSON 的 SHA-256 |
| 实体内容 | 对应校验键加 1～1023 | 连续的 4096 字节 JSON 分片；最后一片可短 |

元素 ID 保持 48 位；ordinal 使用精确 NUMBER，不经浮点。每个实体最多
1023 个内容分片，属性仍受 1 MiB / 深度 32 等约束。默认总图存储与结果字节预算
改为 **100 MiB**，存储预算计入清单、校验和及内容。

读取验证：版本、连续分片、长度、SHA-256、记录键与实体 ID、跨节点 / 边 ID
唯一性、端点、清单计数、高水位以及资源预算。不使用静默丢行或截断掩盖损坏。
48 位分配器耗尽的图仍可读取，后续新建元素明确报错。

## 增量维护与原子性

执行器继续先在图副本计算并校验返回结果。持久化侧比较前后节点 / 边：

1. 未变化的实体不序列化、不修改存储行。
2. 变化实体只处理自己的校验及内容分片，相同分片保留；移除的尾片删除。
3. 通过有界参数批次进行 DELETE、UPDATE、INSERT；UPDATE 的 CASE 分支为
   二进制参数显式指定字节类型上下文。
4. 一个图语句的所有批次位于同一个原生事务 / 外层语句撤销标记内。
   显式事务中的失败只回滚该语句，之前成功语句保留。

因此写入量跟变化实体相关，而不再跟整个图的字节量成正比。参数批次有上限，
不把几十 MiB 内容拼成一条巨型 SQL。

## 原生记录键索引

新图在创建图的同一 DDL 事务内，建立唯一 B-tree：
`i_graph_<graph_object_id>$`，键列为 ordinal。
字典中有对应 obj$ / ind$ / icol$ / seg$，正常 WAL 和恢复覆盖该树。
其名字使用保留后缀，普通 CREATE INDEX 无法占用；DROP INDEX / 重建接口拒绝
管理图所属索引，DROP GRAPH 才级联删除。

内部图批量 UPDATE / DELETE 使用该树逐点探测，再按语句快照及自身事务回表。
索引项可能保留陈旧条目，WHERE 始终复核；增长迁移的转发 ROWID 先解析成当前
物理 ROWID，并去重，避免将转发槽交给写侧。普通表 DML 的访问路径保持既有行为。
非键列更新不插入新的 B-tree 项。

此索引是**存储记录键索引**。它不能被描述为 db_type、名称、全文或持久化邻接索引。
节点标签和双向邻接映射仍在装载图时构建于内存。

## 旧图升级

- 旧版 `bicdb-graph-v1` 全图分片继续校验和读取；只读操作不建索引、不迁移。
- 自动提交的图写入在执行前补齐旧图缺失的记录键树。这个 DDL 是独立提交的，
  即使后续图查询失败，索引准备仍可保留；业务图内容不会因此迁移。
- 图内容在首次成功写入时以同一图事务转成 v2，失败 / 回滚保留旧内容。
- 旧图在显式事务中也能写入和回滚。该事务不会执行独立索引 DDL；若原图没有树，
  当前写入走扫描回表。之后首次自动提交写入会补齐树。
- 元素 ID、elementId 的工作区 / 图身份、原生用户权限保持稳定。

SQL 使用方式保持：

```sql
CREATE GRAPH knowledge;
SHOW GRAPHS;
CYPHER knowledge 'CREATE (n:Document {db_type:"2123",name:"example"})';
CYPHER knowledge 'MATCH (n:Document) WHERE n.db_type=$domain RETURN n.name AS name'
  PARAMETERS '{"domain":"2123"}';
```

## 验证与发布

代码：`crates/graph/src/storage.rs`、`crates/sql/src/graph_sql.rs`、
`crates/sql/src/dml_index.rs`、`crates/sql/src/session.rs`、`crates/catalog/src/ddl.rs`。

验证包括独立记录增量、大片增长 / 缩短、损坏拒绝、预算边界、分配器耗尽，
图索引的所有权和级联删除，以及真实服务的工作区隔离、PUBLIC 只读、事务回滚、
崩溃恢复和已发布 v1 二进制创建旧图后的升级。
另有大于 8 MiB 的合成图验证；不能把它当作 100 MiB 或大型生产图的完整规模压测。

**长事务日志压力修复（同日续）**：先前 10 MiB 原子创建在两个 4 MiB 日志组
下被日志切换阻塞，尺度用例曾临时增大组容量。现已补齐活动事务的检查点：
在完整行写入 / 索引维护结束后的安全边界，保存数据、undo 和事务槽；回收日志前
依据已耐久的提交记录补齐提交标记，保留正确的提交序号水位。运行期全事务 / 语句
回滚以及普通实例恢复的 undo 补偿，也在完整逆操作之间推进检查点。
恢复检查点先同步所有已重放的文件和 undo 文件，再发布控制文件进度；
恢复返回前也同步尾部直接文件写入，避免运行期新缓存看不到这些脏页。

该尺度测试已恢复默认两个 4 MiB 日志组，验证 10 MiB 创建、单点更新和重启，
以及 10 MiB 内容替换的主动回滚、未提交事务 SIGKILL 后恢复和再次重启。
专项回归覆盖“提交日志耐久、事务槽尚未标记”和“回滚只完成部分逆操作后检查点”
两种边界。本改动不增加部署实例日志组大小，不改变 PITR 的目标点重放路径。
归档未完成、磁盘 / 同步失败、单次原子页操作超过日志组容量仍按原有具名错误处理；
此项验证不等同于 100 MiB 图或所有故障点的完整规模测试。

续作证据将保存于 [长事务验证记录](evidence/bicdb-graph-long-wal-20261009/README.md)。

最终统一构建发布：`python3 scripts/build_bicbot_v2.py`。
测试、发布回执、安装版实测及 SHA-256 见
[验证记录](evidence/bicdb-graph-storage-v2-20261009/README.md)。

整体目标仍未完成，本轮完成的是增量持久化和记录键访问路径：

1. **按需读取**：节点 / 边 / 正反邻接持久化访问，替换当前每次查询装载全图；
   查询核心也仍复制图和检查全图序列化预算，读取 CPU / 内存仍与图规模相关。
2. **属性索引及 SQL 管理已补齐本阶段**：分标签 / 类型、标量 / JSON 对象路径、
   组合前缀及范围、唯一性、CREATE / DROP / REBUILD / SHOW 和只读 PROFILE；
   见 [图属性索引实现](bicdb_图属性索引与SQL管理_20261009.md)。全文索引与按需读取仍待实现。
3. **全文检索**：接入已设计的延迟 / batch 维护、倒排、检索排名、发布水位，
   保留分字段轮转与域过滤。现有 searchNodes 仍返回 bounded_scan。
4. **图关系表值接口与关联**：GRAPH_TABLE、SQL 联查、图模板和受管引用。
5. **规模验证和维护**：多批次恢复、空间回收、失效索引维护、大图基准与交接文档。
   已补齐活动事务检查点；继续验证更大数据量及更细的恢复中断点。

本阶段索引沿用原生树的“只插不删、回表判活”机制。删除留下的陈旧项尚无图专用
维护命令；原生事务槽 / 已删除行空间回收也仍是后续存储维护目标。
不能用本轮测试宣称完整实现旧 GRP 规格的邻接段、Move、受管引用或 Neo4j 全部能力。
